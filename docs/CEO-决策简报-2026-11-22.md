### B8. 预算分母 / 追加预算按钮语义（0049 §12(B) → 0045 §7）
- ⚠ **本条的「现状」那段已被后来的实现追过，口径以 r25 + 0072 为准（2026-11-27 核对）**：那扇门今天的分母是 `COALESCE(budgets.limit_cents, 命令行)` —— **有预算行时那一列说话**（设计文档 §1.1 的 **r25**：CEO 拍板「预算列 = 生效值」，四候选一个没选、拍的是门与界面共用同一分母，(B) 那半「界面改读进程里的参数」随之作废）。所以「把那一列改了门不动」不是今天的形状，「卡点：该写哪一列」也已有了答案 ⇒ **本条剩下的只有产品选择**：要不要给「追加预算」建一个真按钮（今天预算页手填 `task/<id>/per_task` 那一格已经真能开门，0072 实测）。上面「实测 UPDATE 后门不变」是 **round360 之前**的读数，0049 §12 已就地标注作废。
- **现状**：看板上的预算条有一列 `budgets.limit_cents`，而实际挡门的**分母是进程里那个命令行数字**（`serve/driver-pump.ts:518` 绑 `o.taskLimitCents`）。同一条任务屏上挂着两个都叫「上限」而相差 $15.00 的数（实测：参数 500→2000 后 B 列停在 500）。
- **卡点**：`budgets.limit_cents` 这一列该怎么办 —— 三个候选在 0045 §7 摆着（A/B/…）。「追加预算」按钮不自己做的原因：最省事实现是一颗**点了没反应**的按钮（04:15 实测 UPDATE 后门不变），比没有按钮更坏。
- **你要输入什么**：定那一格 —— 追加预算该写哪一侧（进程参数 or 库里那列）。
- **后果**：要么预算条右半边改用服务端随响应发下来的当前进程参数（`driver.task_limit_cents` 已在下发，见 0049 §12.3——但预算条那侧还没改用，且要认「离线读库的人看到没有上限的账本」），要么正式声明库里那列是记录而不是生效值。
- **建议**：采纳候选 (B) 的语义（生效值 = 进程参数，`limit_cents` 列降为记录；明确离线读库无上限是设计选择），并给「追加预算」按钮一个真实语义或干脆不建。这个决策同时解开 0049 §12 挂的那条。

- **现状**：待办条目的 `state` 有五个取值，DB 的 CHECK 约束（`packages/hub/resources/migrations/0018_backlog.sql:28`）与契约枚举（`packages/contracts/src/backlog.ts:11`）都把五个写死。而今天**全仓没有任何一条路径能把一条待办写成 `scheduled` / `doing` / `done`** —— 建条目时 INSERT 的字面量恒为 `'backlog'`（`packages/hub/src/backlog/service.ts:103`，拆分出的子项 `packages/hub/src/backlog/service.ts:120`、调研卡同款），能改状态的只有两处 UPDATE，且都是写死 `'cancelled'` 的取消与合并（`packages/hub/src/backlog/service.ts:111`、`packages/hub/src/backlog/service.ts:114`）。`PATCH /api/v1/backlog/:id` 按设计只认 `group_id` / `due_at` / `priority` 三选一，状态不在里面（`packages/hub/src/http/work.ts:154`）。⇒ 界面那一行 pill 今天只会显示「待办」或「已取消」两样。
- **另一处对不上**：设计文档写的面板状态是 **待办 / 进行中 / 待评审 / 已上线 / 已取消**（`docs/design-2026-11-23-群角色上层.md:401`），而落地的枚举是 `backlog / scheduled / doing / done / cancelled`（待评审、已上线两个语义在枚举里没有对应物，scheduled「已排期」在设计里没有）。名字与个数都不是一套，先对齐哪一个也得先拍。
- **为什么卡在这里（不是工程债）**：补齐写入路径需要先定三件事，都在产品口径上：① 状态集合到底是上面哪一套（或第三套）；② 哪些跳转合法（例：`done` 之后能不能回到 `doing`？`cancelled` 是不是终态——取消那条已经写了「已完成只能由老板取消」`packages/hub/src/backlog/service.ts:539`）；③ 由谁触发——界面上人手推进、任务立项时自动同步（迁移 0018 头部注释设的就是这条路：「立项 ⇒ 建 task 并回填 task_id，之后状态各自演进」，而那条回填本身今天也不存在），还是两者都要。**我单方面发明一套跳转规则 = 把产品口径当工程决定用了**，所以它不在工程可决的范围内。
- **它挡住了什么**：列表查询的 `state` 过滤器（`packages/contracts/src/backlog.ts:116` + SQL `packages/hub/src/backlog/service.ts:90`）与 0080 刚补的「按群筛」是同一格形状，但**在状态机有生产者之前，界面上放一个状态下拉就是把一个永远筛不出东西的控件挂上去**（0063/0077 记的正是这种「有消费者、无生产者」的账）。所以这条不是一句「顺手补个下拉」，它是那条下拉的前置。
- **选项与后果**：
  - 甲 · 先对齐状态名（照设计文档里「待办 / 进行中 / 待评审 / 已上线 / 已取消」那一行那五个），再加 `POST /backlog/:id/state` 一类的显式推进端点 + 界面推进按钮：口径最全，代价是要一次迁移（CHECK 约束换值 + 存量行映射）。
  - 乙 · 保留现枚举，只补 `backlog → doing → done` 三个真能到的态（`scheduled` 挂账）：改动最小，且与「设计文档那一行的五个名字要不要照搬」这条一并解决；`待评审 / 已上线` 语义留给任务状态机那侧，待办只管「做没做」。
  - 丙 · 保持现状：状态字段继续只作「取消 / 合并」的记账位，界面不出现状态筛选，`state` 查询参数登记为「等状态机」。零改动，但列表按状态筛这个用户可见能力一直不存在。
- **建议**：选乙 —— 它与已落地的实现距离最近，且把「设计文档那五个名字」和「已迁移的 CHECK 五个名字」这两套命名收敛到一处；丙 也可以，但要把设计文档那一行改成实现的样子，别留两套。
