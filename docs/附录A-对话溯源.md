你提到的这种“AI群聊、各自分工做任务”的场景，现在不仅有对应的软件，而且已经形成了一个明确的产品类别，通常被称为 **多Agent协作平台** 或 **Agent原生协作空间**。

它们的设计理念，就是把多个拥有独立人格、记忆和技能的AI Agent拉入一个“群聊”或“工作空间”，让它们像人类团队一样讨论、分工和交接任务。

### 🛠️ 主流产品与形态

目前这类产品主要有以下几种形态：

**1. 桌面应用：功能强大，掌控感强**
这类软件通常可以安装在本地，能深度调用你的文件系统和工具，适合需要高度定制和掌控的用户。
- **KAi**：一个多AI Agent协作桌面应用。你可以创建多个Agent（例如“产品经理”、“程序员”、“审查员”），它们拥有独立的记忆和工作空间。在群聊模式下，它们可以**@彼此、主动交接任务、甚至互相监督**，还支持将子任务分派给其他Agent执行[reference:0]。
- **GenericAgent-v1-web**：这款工具的特色是**多模型群聊**，声称是市面上唯一能让Claude、GPT、Kimi、MiniMax在同一个对话里协作的平台。它还有一个有趣的“**Agent友圈**”功能，AI完成任务后可以发“动态”，其他AI可以点赞、评论，形成一种质量监督网络。

**2. 云端平台：开箱即用，生态整合**
这类产品通常由大厂或知名团队推出，无需本地部署，并能与企业常用的办公软件（如微信、飞书）打通。
- **AgentMore（智谱清言）**：支持将**最多5个AI Agent**拉入同一群组，提供“头脑风暴”和“任务分配”两种协作模式。它的优势在于可一键接入微信、飞书，并拥有技能广场，能让Agent调用丰富的外部工具[reference:2]。
- **万有无界（阿里云）**：定位于**企业级协作工作台**。它通过“项目空间”和“群聊”，让多位不同职责的Agent围绕同一个任务**接力推进**，并将所有产出沉淀为可复用的数字资产[reference:3]。
- **Cumora**：一款跨平台团队聊天应用，其核心理念是将AI Agent视为**一等团队成员**。Agent不仅能聊天，还能**认领工作、相互协调避免冲突、发送和接收真实的电子邮件**，并集成了看板（Kanban）和日历功能。

**3. 开源框架/自托管方案：面向开发者，高度灵活**
适合有技术背景，希望自行部署和深度开发的用户。
- **Swarms GroupChat**：一个开源的多Agent对话框架。它的群聊机制很特别：每一轮，所有Agent会**私下“竞价”** 来争取发言权，出价最高者获得发言机会，同时有机制防止同一个Agent连续发言，确保了讨论的流动性和多样性[reference:5]。
- **AgentVerse**：北大团队开发的开源框架，其亮点是设计了**虚拟办公室**。每个Agent拥有独立工作区，通过共享白板同步信息，模拟了高度结构化的团队协作环境[reference:6]。
- **Buzz（Block出品）**：由Jack Dorsey创立的Block公司发布的一款**开源、可自托管**的群聊平台，支持人类与AI Agent在同一空间内协作[reference:7]。

### 💎 如何选择？

你可以根据自己的需求来判断：

- **如果你是个人用户，想体验“指挥一个AI团队”**：可以从 **KAi**（功能全面）、**AgentMore**（上手快、生态好）或 **GenericAgent**（多模型对比）开始尝试。
- **如果你代表企业，寻求可管理、可沉淀的协作方案**：可以关注 **万有无界**（企业级工作台）或 **Cumora**（深度集成工作流）。
- **如果你是开发者，希望自托管和深度定制**：可以研究 **Swarms GroupChat**、**AgentVerse** 或 **Buzz** 这类开源框架。

这类产品正在快速发展，它们的目标都是让AI从“单兵作战的工具”进化为“可以协同工作的团队”。你对哪种形态（桌面、云端还是开源）更感兴趣？我可以再为你展开介绍。

你提到的这几个开源工具，虽然目标都是多Agent协作，但设计哲学和适用场景差别很大。下面我为你详细拆解 **Swarms GroupChat**、**AgentVerse** 和 **Buzz** 这三个代表性项目。

### 🐝 Buzz：把Agent当作“同事”的协作空间

Buzz 由 Jack Dorsey 创立的 Block 公司开源，它的核心思路很特别：**不把Agent当机器人，而是当成人一样的“成员”**[reference:0][reference:1]。

**核心机制：协议优先，一切皆事件**
Buzz 构建在去中心化协议 **Nostr** 之上。在这个空间里，无论是人类发的消息、Agent提交的代码、CI的运行结果，还是一次工作流审批，**所有动作都会被封装成一条“签名事件”**，写入同一个统一的事件日志[reference:2][reference:3]。这从根源上解决了传统协作中聊天记录、代码评审和CI结果分散在不同工具里的割裂问题。

**关键设计：Agent拥有独立身份**
这是Buzz最本质的区别。传统Bot通常借用人类的API Token，导致审计日志无法区分人和机器。Buzz让**每个Agent都拥有自己独立的密钥对**。Agent用自己的密钥签名工作内容，而它的“人类所有者”则签署一份授权凭证，限定Agent能做什么（如访问哪些频道、Git仓库的读写权限、有效期、调用频率等）[reference:4]。这样做的好处是审计清晰，且Agent密钥泄露时，只需撤销其授权，不会影响人类主身份的安全[reference:5]。

**架构与部署**
Buzz 的架构相当“极简”，用 **Rust** 编写。其技术栈围绕事件驱动设计：**PostgreSQL** 用于事件存储和全文搜索，**Redis** 处理发布/订阅消息，**S3/MinIO** 存储媒体文件[reference:6]。它是**可自托管**的，你可以在自己的服务器上部署整套工作区[reference:7]。

**适用场景**：适合希望建立一个**长期、可审计、人与Agent深度融合的协作空间**的团队，尤其看重操作的可追溯性和Agent身份管理。

### 🧠 Swarms GroupChat：“竞价发言”的异步讨论框架

Swarms 是一个 Python 框架，其 **GroupChat** 模块的核心是模拟一种更接近人类圆桌讨论的动态：**没有固定的发言顺序，谁想说话谁“竞价”**。

**核心机制：异步自选择与竞价发言**
在 Swarms v13 及之后的版本中，GroupChat 抛弃了轮询或指定发言人的模式。每一轮，**所有Agent都会私下评估自己是否想发言，并给出一个0到1的“意愿分”**。只有分数最高、且超过设定阈值（`threshold`）的Agent才能获得发言权[reference:9]。

为了防止某个Agent“霸占”话筒，系统还引入了 **`recency_penalty`（近因惩罚）** ，如果同一个Agent连续发言，其分数会被打折，从而鼓励发言权在房间里流动[reference:11]。

**技术实现与部署**
这是一个**轻量级的Python库**，通过 `pip install swarms` 即可安装。其异步架构体现在每个Agent都运行在自己的协程中，并行监听所有广播消息。对话会在达到最大轮数（`max_loops`）或长时间无人发言（`idle_timeout`）时自动结束。

**适用场景**：适合开发者**快速搭建和实验**多Agent的讨论、辩论或头脑风暴场景，灵活性高，可以轻松集成不同的大模型。

### 🏢 AgentVerse：不止于聊天，更是“仿真与任务求解”平台

需要注意，名为“AgentVerse”的项目有两个不同版本，需要留意区分：

- **OpenBMB/AgentVerse（清华大学）**：这是一个更学术、更底层的**多智能体仿真与任务求解平台**，拥有 ACL 2024 论文背景，Star 数超过5k。
- **Peiiii/AgentVerse**：这是一个**面向用户的AI专家团队协作平台**，提供开箱即用的Web界面，内置了14个预设专家团队（如“思维探索”、“小说创作”），上手门槛更低。

这里重点介绍更具代表性的 **OpenBMB/AgentVerse**。

**核心机制：双模式架构**
它的设计围绕两种模式展开：
1.  **TaskSolving（任务求解）** ：多个Agent协作解决一个具体复杂任务（如数学题、代码生成）。
2.  **Simulation（仿真）** ：让多个Agent在一个模拟环境中交互，用于研究“涌现行为”（Emergent Behavior），即多个简单Agent互动后产生的、单个Agent不具备的复杂能力。

**技术架构与部署**
这是一个**Python框架**，技术栈包括 Pydantic、OpenAI API 和 React 前端。其代码结构清晰，包含了 `simulation.py`（仿真）、`tasksolving.py`（任务求解）等核心模块，以及专门的 `memory`（记忆系统）和 `output_parser`（输出解析）组件。它支持通过克隆 GitHub 仓库并运行 `python setup.py develop` 来从源码安装[reference:17]。

**适用场景**：适合**研究人员和开发者**进行多Agent协作的算法实验、仿真研究，以及构建复杂的任务求解流程。如果你想要一个开箱即用的专家团队Web应用，**Peiiii/AgentVerse** 可能是更直接的选择。

### 💎 如何选择？

这三个工具代表了三种不同的路径：

- **追求“生产级”的人机协作空间**：选 **Buzz**。它关注的是身份、审计和长期协作的工程化问题，适合企业团队。
- **追求灵活的实验与算法创新**：选 **Swarms GroupChat**。它轻量、异步、机制新颖，适合开发者快速验证多Agent的交互逻辑。
- **追求学术研究与复杂任务求解**：选 **OpenBMB/AgentVerse**。它提供了严谨的仿真框架和任务求解模式，适合探索多Agent系统的深层能力。

### 🎯 直接匹配你愿景的“一人公司”产品

这几个项目在设计理念上与你设想的组织形态高度重合，值得优先关注。

**1. Paperclip：把你定位为“董事会”的公司操作系统**
Paperclip 的定位就是“零员工公司”的编排平台。它不只是一个任务管理器，底层包含了**组织架构图、预算、治理和目标对齐**。你作为人类，角色被设定为“董事会”，拥有批准招聘、覆盖策略、暂停或终止任何Agent的最终权力。它的“心跳机制”让任务能够在组织架构中**上下流动**，天然支持你设想的下发与上报。同时，它强调**治理与审批门槛**，你可以配置哪些决策需要你的批准，哪些可以自动通过。[reference:0]

**2. agents-inc：精确复现“CEO → 助理 → 负责人 → 执行者”链条**
这个项目对你设想的层级描述最为直接：**“CEO提问，CoS（参谋长/助理）派发任务给Lead（负责人），Lead管理Worker（执行者）”**。它的设计哲学是**“权威与审阅取决于关卡设置，而非哪个模型先回答”**，并且明确要求**“作者绝不给自己打分”**——Lead必须先验证Worker的产出，才能向上呈报。这正好实现了你想要的逐级审阅、过滤后上报的机制。此外，它会根据模型的能力和成本自动匹配层级（高管层用强模型做最终判断，执行层用低成本模型做常规工作），符合“个人公司”对成本效益的追求。[reference:1]

**3. Agent Company AI：开箱即用的虚拟公司生成器**
这个工具的目标就是让**“单人创业者创建一个完全由AI员工组成的虚拟公司”**。它预置了 `tech_startup`（6个Agent）、`full`（10个Agent，覆盖所有部门）等模板，可以一键生成包含CEO、CTO、开发、营销等角色的公司。你通过CLI或Web仪表板管理一切：给CEO一个目标（如“为新产品搭建落地页”），**CEO会自动分解任务并委派给团队**，Agent们协作交付结果。你还可以定义“业务DNA”（利润引擎），让所有Agent的决策都对齐你的商业模式。[reference:2]

**4. AgentCompany（Ai-Company）：组织架构最完整的“虚拟公司”框架**
它的项目愿景直言**“让AI员工为你工作，你只需要当老板”**。其组织架构的完整度很高，明确划分了**高管层（CEO/CTO/CFO等）、产品部（产品经理/UI设计）、技术部（架构师/前后端/DevOps）、测试部、运营部、市场部**等，几乎覆盖了你列出的所有角色。它支持**独立记忆和汇报机制**，并且内置了**会议系统**（需求评审会、技术方案会等），模拟了真实公司中通过会议对齐和决策的过程。老板仪表盘可以让你下达指令、查看状态、审批决策。

**5. OneManCompany：浏览器里的“一人公司操作系统”**
定位是**“一人公司的AI操作系统”**。你作为唯一的CEO，其他所有人（HR、COO、工程师、设计师）都是AI员工。它模拟了**组织架构图、审批链、会议室、绩效评估**等完整的管理流程。它强调“真正的团队协作，而非平行的聊天窗口”，Agent之间会互相拉入会议、跨职能委派任务、进行**结构化交接**。你可以选择完全放手只看结果，也可以随时介入会议或审阅每一个代码差异（diff）。[reference:4]

**6. Railse OPC（一人公司）：专注“统一审批收件箱”的驾驶舱**
如果你最看重的是**“战略拍板由助理呈交给我”**这一环，Railse OPC 的设计非常精准。它的核心是一个**手机优先的统一审批收件箱**：所有Agent停下来等待审批的事项都会汇聚到这里。它的目标是让**“八成以上的审批由规则自动决定，不打扰你”**，只有策略引擎无法决定的事项，才会推送到你的手机上，由你批准或拒绝。它把产品单位定义为**“任务和决定”**，而非终端窗口，非常符合CEO的视角。

### 🧰 如果你希望自己“组装”这套系统

如果你有开发能力，或者希望更深度地定制每个角色的行为逻辑，以下两个框架是构建这类系统的“原材料”，但它们本身不是开箱即用的成品。

- **CrewAI（层级流程）**：通过设置 `process=Process.hierarchical`，可以创建一个**“经理”Agent**，由它负责协调工作流、委派任务、验证结果。你可以自定义经理Agent，并配合Flows架构实现**Human-in-the-Loop**（人工介入审批）[reference:6]。
- **MetaGPT**：核心是**用SOP（标准作业程序）驱动一个模拟的软件公司**。它内置了产品经理、架构师、工程师、QA等角色，并通过“上游输出→下游输入”的机制来模拟工作流。它的审阅机制（如 `ReviewPRD`、`ReviewCode`）是编码在角色动作中的，适合对软件开发流程有特定要求的场景。[reference:8][reference:9]

### 💎 如何选择？

你可以根据自己的偏好来决定切入点：

- **如果想最快体验“指挥一个AI公司”的完整感觉**：**Agent Company AI** 和 **AgentCompany** 的预设模板能让你在几分钟内看到效果。
- **如果最看重“组织架构的严谨性”和“逐级审阅、过滤后上报”的机制**：**agents-inc** 的设计哲学与你的要求最为契合。
- **如果最看重“作为CEO只处理例外事项”的省心体验**：**Railse OPC** 的统一审批收件箱和自动审批策略是专门为此设计的。
- **如果你想要一个可长期演进、高度可定制的“公司OS”底座**：**Paperclip** 和 **OneManCompany** 提供了更完整的治理、预算和协作基础设施。

你设想中的这个“个人公司”，核心价值在于**将你的认知带宽集中于“想法”和“战略拍板”**，而将结构化的执行与协调交给AI组织。上面这些项目，正是沿着这个方向在探索。你对其中哪一个的运行机制或实际体验更感兴趣，我可以再为你展开看看。

## 一、市场全景判断

这个品类在2026年初爆发，但到年中已经发生了显著收敛。Ry Walker 2026年6月的研究给出了一个关键判断：**“两个月后，这个品类已经整合为一个赢家市场——Paperclip增长了约60%至70k stars，并注册为Paperclip Labs, Inc.，而名单下半部分的项目大多陷入沉寂。”**[reference:0]Paperclip在2026年10月GitHub星数约95.4k，月增速约+14.6k，是这一品类中唯一具备持续动量、公司实体和已交付治理功能的项目[reference:1][reference:2]。

但“赢家通吃”并不意味着其他工具没有价值。这个品类的真正分界线在于：**你买的是一套“公司OS”（组织架构、预算、治理、审计），还是一个“流程框架”（角色、任务、交接），或者一个“单点工具”（只解决审批这一个环节）** 。Paperclip站在第一层；AgentCompany和OneManCompany在第二层靠近第一层的位置；CrewAI和MetaGPT是更底层的框架；Railse OPC和agents-inc则各自聚焦于一个极窄但真实的痛点。

## 三、逐产品深度剖析

### 1. Paperclip — 当前品类的事实标准

**它解决的问题**：把你的想法变成“公司目标”，然后由一个CEO agent提出战略，你批准后，任务进入看板，通过心跳机制唤醒agent认领工单，预算到硬停自动暂停。一个Paperclip实例可以运行多个完全数据隔离的“公司”。

**与你设想的匹配度**：**最高**。你作为人类，角色就是“批准战略、设定预算、看板上验收”的那一层。CEO agent是你雇佣的第一个agent，它读你的目标、提战略、你批准后才动。这比“助理呈交战略”更接近你描述的“拍板”动作——不是被动收件，而是主动审批战略提案。

**治理与成本**：Paperclip的差异化不在“让agent聊天”，而在**让agent花钱有上限、做事有审计**。预算按agent和公司两个层级设置，达到100%自动暂停；审批队列、不可变审计日志、工单追踪都是内置的[reference:15]。成本预期：$5–20试玩，$20–100/月一个活跃公司；一个中等活跃的worker agent约$3–15/月（按Anthropic典型定价）[reference:18]。

**代价**：Paperclip是**框架，不是成品**。GitHub quickstart的原话是“安装和配置是5分钟路径之外的一次性设置”，但实际配置组织架构、编写每个agent的职责和工具权限，是**数天到数周的工作**[reference:19]。它的“代码审查”能力被明确排除在外——“不是代码审查工具，自带你的审查流程”。这意味着如果你的产品涉及代码交付，你仍然需要自己解决审阅环节，Paperclip只负责把工单送到人面前。

**适合谁**：有技术配置能力、真正想要“公司级治理”（预算、审计、角色边界）而非“聊天式协作”的独立创始人。如果你愿意花一周配置换取长期的可控性，Paperclip是当前唯一有足够社区验证和交付记录的选择。


### 2. AgentCompany（Ai-Company） — 组织架构最“像公司”的开源仿真

**它解决的问题**：如果你想要的是“打开就是一个完整公司在运转”，AgentCompany的组织架构覆盖度在开源项目中是最高的：高管层（CEO/CTO/CFO/COO/CMO）、产品部、技术部、测试部、运营部、市场部、支持部。每个agent有独立记忆（短期/长期/情景/共享），有A2A通信和MCP上下文管理，有**会议系统**（需求评审会、技术方案会、站会、复盘会、头脑风暴）。

**与你设想的匹配度**：**组织形态高度匹配，但工程成熟度存疑**。你的“助理/产品总监/技术总监/架构师/开发/测试/运营”链条，在AgentCompany的角色清单里几乎一一对应。会议系统也模拟了你想要的“逐级审阅”——需求评审、技术方案会本质上就是审阅节点。老板仪表盘可以下达指令、查看状态、审批决策。

**风险**：这是一个Python包（`pip install agentcompany`），代码结构清晰，但**社区信号薄弱**。搜索中出现的“AgentCompany”星数数据大多指向另一个同名的基准测试项目（TheAgentCompany），而非这个协作框架。它在功能叙事上很完整，但缺乏Paperclip那种持续交付和社区验证的记录。把它当作一个**可研究和二次开发的参考实现**是合理的，把它当作生产系统则需要你自己承担工程风险。

**适合谁**：想研究“完整公司仿真”如何编码、或者愿意基于一个组织架构已经很完整的代码库进行二次开发的技术型创始人。


### 3. OneManCompany — 浏览器里的“公司OS”，叙事最完整但社区最年轻

**它解决的问题**：一条命令（`npx @1mancompany/onemancompany`）在浏览器里启动一家AI公司，带像素风办公室界面。它的功能清单在“公司感”上做得非常细：**HR从Talent Market搜索、CEO面试、自动入职；解雇有清理流程；季度绩效评分、PIP、晋升轨道；CEO→高管→员工的任务委派，每层有质量门禁；多agent同步会议房间；按项目追踪LLM token和美元成本**[reference:24]。

**与你设想的匹配度**：**流程叙事高度匹配**。你描述的“助理/产品总监/技术总监/架构师/开发/测试/运营”在OneManCompany里对应EA（执行助理）、COO、HR、工程师/设计师/QA等角色，并且它的“质量门禁”明确设计在每一级委派上——工作经过审阅、迭代和质量检查点，最后通知你审批最终交付物[reference:25]。

**关键风险**：社区规模很小（约376–415 stars），远未达到Paperclip的验证水平[reference:26]。它的“Talent Market”社区验证员工是一个有吸引力的概念，但生态尚在极早期。技术栈要求Node.js 16+和Git，安装自动化程度高，但这不改变它作为一个年轻项目的事实[reference:27]。

**适合谁**：被Paperclip的配置曲线劝退、希望“开箱就有一个像公司的东西可以玩”的用户。但需要对项目成熟度有清醒预期，不建议作为唯一的生产依赖。


### 4. Agent Company AI — “轻公司+变现”的模板化路径

**它解决的问题**：如果你想要的是一个**能直接收钱的小生意**，而不是一个庞大的软件公司，Agent Company AI的设计更务实。9个预设角色（CEO/CTO/Developer/Marketer/Sales/Support/Finance/HR/PM），11个LLM提供商，50+内置工具，**内置Stripe、Gumroad、发票、预约集成**，agent可以“赚真钱”。

**与你设想的匹配度**：**部分匹配，偏“商业变现”而非“产品研发链条”** 。它的自主CEO模式是“设定目标，CEO规划、委派、循环审阅”，这符合你的顶层逻辑。但它的角色深度和审阅机制不如Paperclip或AgentCompany那样强调“作者不给自己打分”的制衡。成本安全默认值是$10/run和$20/day，对试错友好。

**需要注意**：搜索结果中“Agent Company AI”的星数信息混乱，部分指向 `TheAgentCompany`（一个评估LLM agent在模拟软件公司中表现的**基准测试**，约715–792 stars），而非这个协作工具本身[reference:30]。不要把两者的社区数据混淆。

**适合谁**：想快速验证一个“AI员工帮我赚钱”的小生意模型（内容站、agency、电商），而不是搭建一个完整产品研发组织的人。


### 5. agents-inc — 设计哲学最接近你的“逐级审阅”，但成熟度最低

**它解决的问题**：agents-inc的“企业组织架构”隐喻在理念上与你描述的“CEO → 助理 → 负责人 → 执行者”最为贴合。它的结构是：**CEO是你；CoS是你对话的会话；一个Lead管理一次运行；Worker向Lead汇报**。廉价模型做常规工作，昂贵模型做管理。核心原则是“**作者绝不给自己打分**”——Lead检查Worker的产出之后，任何东西才能向上移动[reference:31]。

**与你设想的匹配度**：**机制设计匹配度极高，工程成熟度极低**。如果你最看重的是“审阅不是走过场，而是有真正的层级过滤”，agents-inc的哲学值得认真参考。

**关键风险**：PyPI页面明确标注 **“pre-MVP”** ，治理路径（`WORKERBEES_GOVERNANCE`）默认关闭[reference:32]。社区健康指数54/100，社区与采用评分仅37/100[reference:33]。它依赖Claude Code CLI和Anthropic订阅，安装有特定环境要求[reference:34]。

**适合谁**：愿意参与一个早期项目的实验、对“科层制委派+审阅制衡”有强烈理念认同的技术用户。**不建议**作为你“个人公司”的底座来依赖。


### 6. Railse OPC — 不造公司，只解决“拍板”这一个环节

**它解决的问题**：你描述的场景里有一个非常具体的痛点：当多个AI agent同时运行，每个都在等你按“允许”时，你不在电脑前，agent就全部停住。Railse OPC把Claude Code、Codex CLI、Gemini CLI的权限钩子接到同一个守护进程，**策略引擎先过规则：只读和项目内改动直接放行；`git push`、`rm -rf`、联网、付款这类推到手机收件箱，你点一下，agent继续跑**。

**与你设想的匹配度**：**单点匹配，不是全套方案**。它不是“一人公司OS”，不提供组织架构、角色定义或任务下发。但它精确命中了你“战略拍板由助理呈交给我”中的**审批体验层**：把例外事项推到手机上，规则能自动决定的就不打扰你。Apache 2.0开源，自托管hub，风险分七档，不可逆操作不能被“记住放行”。

**适合谁**：已经在用多个AI编程agent、**真正被审批中断困扰**的人。它可以作为Paperclip或任何框架的“审批外设”来使用，而不是替代它们。


### 7. CrewAI 与 MetaGPT — 底层框架，不是“公司OS”

这两个工具经常被提及，但必须把它们放在正确的位置上。

**CrewAI** 是角色化多agent框架，支持sequential/parallel/hierarchical流程，Fortune 500中63%采用，55.6k stars[reference:37]。它的**hierarchical模式**确实有一个“经理agent”来委派和验证，这听起来像你的“总监层”。但CrewAI本身**不提供**预算硬停、审计日志、组织架构图、心跳调度这些“公司级”能力。行业对比指南将它归类为“OSS orchestration framework”，org semantics留给应用层[reference:38]。定价：OSS免费，AMP Basic 50次执行/月免费，企业定制；付费云计划从$99/月至$120K/年，跨度极大。

**MetaGPT** 是“一行prompt模拟软件公司SOP”的框架，PM→架构师→工程师→QA的输出链在**单次任务生成**上效率极高，每任务成本约$0.18，完整项目约$2.0，MIT免费[reference:40][reference:41]。但它是一个**生成框架**，不是一个**运营中的公司**——它不会持续接收你的想法、维护组织记忆、执行预算控制或逐级上报。

**判断**：如果你要的是“每次给一个明确需求，生成一个完整项目”，MetaGPT或CrewAI是高效的工具。但如果你要的是**一个持续运转的、有角色有审阅有治理的个人公司**，它们需要你在上面自建整整一层“公司语义”，而这正是Paperclip等公司OS在做的事。


## 四、结合你角色的选型建议

你的角色是“产品经理型CEO，只负责产生想法和战略拍板”。这个约束意味着：**你的认知带宽是最稀缺的资源**。选型的核心问题不是“哪个工具功能最多”，而是“哪个工具让你花在‘非拍板’事务上的时间最少”。

**如果只能选一个作为底座：Paperclip。** 理由不是它完美，而是它是当前唯一同时具备（1）组织架构语义，（2）预算与审计治理，（3）持续社区验证，（4）公司实体背书的选项。它的配置成本是真实的（数天到数周），但这笔一次性投入换来的是长期的可控性。你可以把它理解为“搭建公司的基础设施”，而不是“安装一个app”。

**如果你想把“拍板”体验做到极致：Paperclip + Railse OPC的组合值得认真考虑。** 用Paperclip承载组织、任务和预算，用Railse OPC把审批的“最后一公里”推到手机上。两者解决的是不同层面的问题，不冲突。

**如果你暂时不想承担配置成本、想先感受“指挥一个AI公司”是什么感觉：AgentCompany或OneManCompany适合作为探索性起点。** 但要对它们的社区规模和工程成熟度保持清醒，不要把它们当作生产底座。

**如果你真正想要的只是一次性生成项目：MetaGPT的效率无可匹敌。** 但它回答的不是“运营一家公司”的问题，而是“执行一个明确项目”的问题。

**不建议作为主底座**：agents-inc（pre-MVP）、Agent Company AI（偏变现轻公司，且社区数据需甄别）、CrewAI/MetaGPT（底层框架，公司语义需自建）。


## 五、这个品类还没有解决的问题

有两点值得你在做决策时纳入考量。

**第一，“agents as employees”的隐喻本身正在被质疑。** HBR在2026年5月发表的研究指出，把agent当作员工来对待，可能**转移问责焦点并侵蚀审阅质量**[reference:42]。这对你尤其相关：你设想的“逐级审阅上报”如果最终变成“agent审阅agent”，审阅的实质可能被稀释。Paperclip的“审批队列”和agents-inc的“作者不给自己打分”都是在对抗这个问题，但**人类在关键节点上的实质性介入**仍然是不可替代的。

**第二，这个品类仍然早期。** 行业分析的原话是：“Paperclip是唯一具有持续动量和公司实体支持的，但其团队仍然是匿名的。其他一切要么是实验性的，要么是沉寂的，要么非常年轻。把整个品类当作有前途但早期来对待。”[reference:43]这意味着你在选择的不只是一个工具，也是在选择**承担早期品类固有风险的意愿**。

如果你的目标是“尽快让个人公司跑起来”，Paperclip是当前最理性的下注。如果你的目标是“在跑起来的同时保留最大灵活性”，先用Paperclip做底座，把Railse OPC作为审批外设，把MetaGPT作为一次性生成工具按需调用——这个组合在2026年11月的时点上，覆盖了你描述的核心链条。

# 产品需求设计文档（PRD）：一人公司操作系统（OPC-OS）

**文档版本**：v1.0  
**目标读者**：你自己（创始人与唯一决策者），以及未来可能加入的1–2名协作开发者  
**核心约束**：你只负责**产生想法**和**战略拍板**；组织内的一切拆解、执行、审阅、过滤由AI层级完成；你的认知带宽是唯一不可扩展的稀缺资源。


## 一、总体方向设计

### 1.1 产品定位

**一句话**：一个自托管的、以“委派—审阅—上报”为原生工作流的个人AI公司控制台。你不是在和一群agent聊天，你是在**经营一个组织**。

这个定位的关键分界线是：**不做“AI群聊”，做“AI科层制”** 。之前调研的品类里，Paperclip赢在“公司OS”的治理层，agents-inc赢在“作者不给自己打分”的审阅哲学，Railse OPC赢在“例外事项推到手机”的审批体验。OPC-OS的设计目标是**取这三者的交集，同时避开它们各自的短板**：不做Paperclip那种需要数天配置的纯框架，不做OneManCompany那种社区极年轻的全仿真，也不做CrewAI那种需要自建公司语义的底层脚手架。

**产品形态**：桌面端（Tauri 2.0）作为主力工作台，Web端作为无安装访问入口，移动端（iOS/Android，复用Tauri代码库）作为**审批与例外处理**的轻量终端。三端共享同一套前端代码和同一套编排后端。

### 1.2 与竞品的差异化取舍

| 竞品 | 值得吸收的 | 必须避开的 |
|---|---|---|
| **Paperclip** | 预算硬停、不可变审计日志、心跳调度、审批队列 | 数天到数周的配置曲线；“代码审查需自带流程”的空白 |
| **agents-inc** | “作者绝不给自己打分”的层级审阅哲学；按成本匹配模型层级 | pre-MVP的工程成熟度；治理路径默认关闭 |
| **Railse OPC** | 策略引擎先过规则、例外才推到手机的审批体验 | 只解决审批单点，不提供组织语义 |
| **AgentCompany** | 完整组织架构与会议系统的叙事 | 社区信号薄弱，不能作为唯一依赖 |
| **CrewAI / MetaGPT** | 角色化任务流转的直观性；按任务生成项目的效率 | 缺乏持久化、预算、审计等公司级基础设施 |

**OPC-OS的取舍**：以**LangGraph的有向图状态机**作为编排内核（解决持久化和断点恢复），以**“审阅门控”作为一等公民**（每个层级交接必须经过显式的通过/打回/升级），以**“例外审批”而非“全量审批”**作为你与系统之间的默认接口。你不审批一切，你只审批规则引擎无法决定的事项。

### 1.3 核心设计原则

**原则一：你的默认状态是“不被打扰”。** 所有功能设计的首要判断标准是：这个设计会让CEO多按一次按钮，还是少按一次按钮？如果一项审批可以由规则引擎根据历史决策自动通过（且可逆），它就不应该出现在你的收件箱里。

**原则二：审阅必须有实质制衡。** 每一层级的产出，在向上移动之前必须经过**下一层级的显式验证**，且验证者不能是产出者本身。助理不能直接“相信”总监的报告，助理必须看到总监附带的验证证据（如测试通过率、代码diff摘要、PRD与需求的逐条对照）。

**原则三：一切可审计、可回放。** 每一个任务的每一次状态变更、每一次审阅决定、每一次审批操作，都写入不可变的事件日志。你可以在任何时候回放“这个想法从提出到交付，中间发生了什么、谁在什么节点做了什么决定”。

**原则四：移动端只做“拍板”，不做“管理”。** 手机上的界面不展示组织架构图、不展示任务看板全貌。它只做一件事：把需要你决策的事项以**足够上下文、一键可操作**的形式推到你面前。


## 二、技术选型（考虑多端）

### 2.1 桌面壳：Tauri 2.0 + Rust

**决策**：桌面端采用 Tauri 2.0，而非 Electron。

**依据**：Tauri 2.0的壳层内存约20MB，Electron在100MB+；安装包2–10MB vs 80–200MB。OPC-OS的桌面端需要常驻运行（心跳调度、agent后台执行），资源占用是持续成本。更关键的是**能力基权限模型**：Tauri的capability-based permissions天然映射到“每个agent只能访问被授予的文件系统和系统API”这一需求，而Electron需要手动实现等效沙箱。Rust后端在处理JSON-RPC消息解析和路由时的性能优势，对Agent Core的对话管理、工具路由、MCP客户端和上下文窗口管理是实际收益。

**已知代价**：Tauri生态比Electron小，第三方插件更少；Rust的学习曲线对前端背景的贡献者不友好。缓解方案：将Agent Core的核心编排逻辑放在Python侧（LangGraph），Rust只承担壳层、IPC路由、文件系统桥接和进程管理，降低Rust代码的复杂度要求。

**多端策略**：Tauri 2.0已稳定支持macOS、Windows、Linux桌面端和iOS/Android移动端，同一套前端代码和Rust核心可复用到移动端。移动端不追求功能对等，只承载**审批收件箱 + 任务状态只读查看 + 语音/文字快捷下达想法**三件事。

### 2.2 编排内核：LangGraph（Python）

**决策**：多Agent编排采用 LangGraph，而非 CrewAI 或 AutoGen。

**依据**：2026年框架选型的核心标准已经变成“状态能不能持久化、多Agent并行时Reducer怎么合并、Checkpoint崩了能不能从断点恢复”[reference:6]。LangGraph的有向图状态机 + 每步自动Checkpoint（支持PostgreSQL/Redis）直接满足“逐级委派、断点恢复、审计回放”的需求[reference:7]。CrewAI的角色抽象直观，但2026年的生产就绪评估将其标记为“Limited; lacks persistence”，更适合快速原型而非持续运营的公司系统。AutoGen已进入维护模式，不应作为新项目的底座。

**具体设计**：整个“公司”被建模为一张LangGraph图。节点是**角色**（助理、产品总监、技术总监、架构师、开发、测试、运营），边是**交接条件**（“PRD通过产品总监审阅” → 进入技术总监拆解；“技术方案通过架构师评审” → 进入开发）。每个交接节点是一个**审阅门控**：上游产出必须附带的证据包（见3.2节）通过验证后，状态才沿边流转。人类CEO的“战略拍板”是一个特殊节点，它不连接在图的内部，而是被**升级路由**触发——当层级审阅无法达成一致、或触及预设的策略边界时，任务被路由到CEO审批队列。

### 2.3 Agent间通信：MCP（工具/数据）+ A2A（跨Agent协调）

采用三层协议栈：**AG-UI** 负责Agent↔用户前端，**MCP** 负责Agent↔工具/数据，**A2A** 负责Agent↔Agent的跨层级协调[reference:10]。AG-UI是基于SSE的事件协议，前端通过标准事件类型接收流式状态、工具调用生命周期和中断（human-in-the-loop）事件，不需要自己发明渲染和状态同步逻辑[reference:11][reference:12]。

**实际影响**：前端不需要轮询。当开发工程师agent完成一个任务，AG-UI事件流会推送 `REVIEW_REQUIRED` 事件到测试工程师的节点，同时看板自动更新。当CEO在手机上批准一个战略提案，AG-UI的 `INTERRUPT` 解决事件会让暂停的图继续执行。前端只消费事件，不承担业务逻辑。

### 2.4 数据层

- **PostgreSQL**：LangGraph的Checkpoint存储、任务状态、审计事件日志、审批记录、组织配置。选PostgreSQL而非Redis作为主Checkpoint存储，因为需要持久化、可查询、可回放，Redis作为缓存和实时事件分发层。
- **S3/MinIO**：agent产出的文件制品（PRD文档、代码diff、测试报告、设计稿）。
- **审计日志**：独立的事件表，append-only，记录 `actor`（哪个agent/人类）、`action`、`target`、`timestamp`、`context_snapshot`（决定时的状态快照）。审批决策同时写入SQL审计轨迹，满足可追溯性要求。

### 2.5 前端技术栈

**React + TypeScript + AG-UI客户端**。Tauri和Web端共享同一套React组件。状态管理采用**事件驱动的增量更新**而非全量拉取：AG-UI的共享状态机制提供带冲突解决的流式事件diff，前端只渲染变化的部分[reference:14]。移动端复用同一套React组件，通过Tauri的移动端打包输出iOS/Android制品，但**路由层做条件裁剪**：移动端只注册审批和只读视图的路由，不加载看板和组织架构的复杂组件。

### 2.6 LLM层

**分层模型策略**：CEO层/助理层使用强推理模型（用于战略拆解、跨部门冲突裁决、审阅质量把关）；总监层使用强模型或中高模型（用于方案设计和跨职能协调）；执行层（开发、测试、运营操作）使用成本优化模型，按任务复杂度动态路由。这与agents-inc“廉价模型做常规工作，昂贵模型做管理”的成本逻辑一致，但在LangGraph的图结构上通过**节点级的模型配置**实现，而非框架层的硬编码。


## 三、风格设计

### 3.1 整体气质：控制室，不是聊天室

界面不应该让人联想到ChatGPT或Slack。主视觉隐喻是**控制室/驾驶舱**：信息密度高、层级清晰、状态可扫视。默认首页不是对话流，而是**“需要你注意的事项” + “组织当前状态”**的聚合视图。聊天是手段之一，不是界面骨架。

### 3.2 配色与视觉语言

- **底色**：深色为主（降低长时间扫视的视觉疲劳），背景 `#0F1117`，卡片 `#1A1D27`。
- **强调色**：琥珀色 `#E8A33D` 用于“需要CEO决策”的唯一强调色，**全局只在这一种状态上使用**，确保你的眼睛在任何屏幕上一扫就能定位到需要拍板的事项。其余状态色（进行中/已完成/被阻塞）使用低饱和的蓝、绿、灰。
- **字体**：等宽字体用于任务ID、金额、时间戳；无衬线字体用于正文和标题。信息密度优先于装饰性。

### 3.3 信息架构风格

**“三层折叠”** ：任何任务在你面前只展示三层信息。第一层是**一行摘要**（“开发完成登录模块，测试通过率94%，等待技术总监审阅”）；展开第二层是**关键指标与证据摘要**（测试覆盖率、diff行数、未解决问题数）；展开第三层才是**完整产出**（代码diff、完整报告）。你大多数时候只需要看第一层，偶尔看第二层，第三层只在需要深度介入时打开。

### 3.4 移动端风格

移动端不做响应式缩放，做**独立的轻量界面**：审批卡片占满宽度，上下文以可展开的摘要形式呈现，操作只有三个按钮——“批准”、“打回并附意见”、“升级到深度审阅（标记为稍后在桌面端处理）”。语音输入是移动端的一等输入方式，用于在通勤或碎片时间“扔出一个想法”。


## 四、功能及功能划分设计

### 4.1 组织层（Org Layer）

**4.1.1 角色定义与岗位书**

每个agent角色的核心不是“简介”，而是**岗位书**：验收标准、禁止事项、工具权限边界、升级触发条件。例如测试工程师的岗位书包含“覆盖率低于90%不得标记为通过”、“发现P0缺陷必须直接升级到技术总监，不经过开发工程师自我判定”。岗位书是可编辑的YAML/JSON，在创建角色时加载，在运行时作为该agent的**系统级约束**注入。

**4.1.2 组织架构与委派规则**

预置一套默认层级：`CEO（你） → 助理/CoS → 产品总监 & 技术总监 → 架构师/开发/测试/运营`。但层级是可配置的：你可以增加“增长负责人”或合并“产品总监与运营”。每条委派边定义**交接物**（handoff artifact）和**审阅门控**（review gate）。委派规则的核心数据结构是一张有向图，与LangGraph的图结构一一对应。

### 4.2 任务层（Task Layer）

**4.2.1 想法入口与结构化**

你通过桌面端或移动端输入一个想法（文字或语音）。助理agent接收后，**不直接拆解**，而是先做**结构化澄清**：这个想法对应什么业务目标？成功标准是什么？有没有预算/时间约束？助理会以**提案**的形式返回一个结构化的“任务章程”（charter），你只需要批准或修改。这是你与系统之间**唯一必须主动操作的非审批环节**——因为“想法”的模糊性是你作为CEO的输入特征，系统不能替你消除它，只能帮你结构化。

**4.2.2 层级拆解与执行**

任务章程批准后，进入LangGraph图。产品总监将章程拆解为PRD级任务，技术总监拆解为技术方案和工程任务，架构师做技术评审，开发执行，测试验证，运营准备上线。每个节点产出**证据包**（见4.3），沿边向上或向下流转。执行层agent的每一次工具调用（写文件、运行测试、调用API）都受MCP层的权限约束，高风险调用触发HITL门控。

**4.2.3 心跳与停滞处理**

系统按配置的心跳间隔（如每15分钟）检查所有活跃任务。如果一个任务在某个节点停留超过预设阈值且无状态变更，心跳机制触发**追问**：是agent在等待外部资源、遇到了未处理的错误、还是审阅者没有及时响应？追问的结果要么自动恢复，要么升级为“需要CEO注意的异常”。这借鉴了Paperclip的心跳调度，但追问逻辑绑定在LangGraph的节点状态上，而非独立的外部调度器。

### 4.3 审阅层（Review Layer）——本产品的核心差异化

**4.3.1 证据包（Evidence Bundle）**

每一次向上交接必须附带一个结构化的证据包。证据包不是“总结”，是**可验证的引用**：
- 产品→技术交接：PRD文档 + 需求条目清单 + 产品总监的逐条通过标记。
- 技术→开发交接：技术方案 + 架构师评审意见 + 每个技术决策的备选方案及选择理由。
- 开发→测试交接：代码diff + 自测结果 + 开发工程师声明的“我认为已覆盖的边界条件”。
- 测试→上报：测试报告 + 覆盖率 + 未通过项清单 + 测试工程师的**独立判定**（通过/不通过/有条件通过）。

**4.3.2 审阅门控（Review Gate）**

每个交接边是一个门控。门控的默认行为是：**上游产出进入下游审阅者的队列，下游审阅者必须在查看证据包后做出显式决定**（通过/打回/升级）。 “作者不给自己打分”被实现为图结构上的硬约束：一个节点的产出不能由该节点自身的后续节点直接标记为“通过”并向上移动，必须经过至少一个**独立审阅节点**。

**4.3.3 升级路由（Escalation Routing）**

当以下情况发生时，任务被路由到CEO审批队列：层级审阅无法在N轮内达成一致；触及预算硬停；操作涉及不可逆的外部动作（付款、对外发送、删除数据）；总监层主动标记为“战略不确定性”。升级路由的目标是**让你看到的每一件事都是真正需要你的事**，而不是流程中的常规节点。

### 4.4 审批层（Approval Layer）——你与系统的接口

**4.4.1 策略引擎优先**

审批不是“什么都问你”。每个需要人类决策的动作先经过策略引擎：只读操作和项目内可逆改动**自动放行**；不可逆操作、外部副作用、预算阈值突破**必须人工批准**；介于两者之间的，根据历史决策模式判断——如果你在过去10次类似决策中都批准了，且该决策可逆，策略引擎可以**自动通过并记录“基于模式的自动批准”** ，你会在日报中看到这些自动决策的摘要，但不会被打扰。这直接吸收了Railse OPC的核心哲学[reference:16]。

**4.4.2 统一审批收件箱**

桌面端和移动端共享同一个审批队列。每一张审批卡包含：**一行决策摘要**、**关键参数快照**（金额、影响范围、不可逆性标记）、**推荐动作及理由**（由助理或总监层生成，但明确标注为“推荐”，不是替你决定）、**超时行为**（如果N小时内未处理，默认通过/默认打回/自动升级给更深度的审阅流程）。审批决策写入不可变审计日志，包含决策时的完整参数快照。

### 4.5 审计与回放层（Audit Layer）

**4.5.1 不可变事件日志**

所有状态变更、审阅决定、审批操作、工具调用、预算消耗写入append-only事件表。每条事件包含 `actor`、`action`、`target`、`timestamp`、`state_snapshot`。这是“回放”的数据基础。

**4.5.2 任务回放**

你可以选择任何一个已完成或进行中的任务，以时间线形式回放：想法何时提出、助理的章程提案、产品总监的拆解、每一次审阅决定和理由、每一次预算消耗、最终交付物。回放的目的不是“审计合规”（虽然它满足这一点），而是**让你作为CEO能够以极低的时间成本理解“组织是怎么运转的”** ，从而调整岗位书、委派规则或审阅门控。

### 4.6 成本与治理层

**预算层级**：公司级预算 → 角色级预算 → 任务级预算。达到阈值时自动暂停相关agent的执行，并向审批队列发送“预算突破”卡片。每个agent的模型调用、工具调用、外部API消耗都记录在成本事件中，可按角色、任务、时间段聚合。成本数据在“组织状态”视图中以**日消耗 vs 预算**的简洁条形呈现，不需要你主动查询。


## 五、前端功能设计

### 5.1 桌面端功能清单

**默认首页（今日视图）** ：
- 需要你决策的事项（按紧急度排序，琥珀色高亮）。
- 组织当前状态摘要：活跃任务数、今日预算消耗/剩余、被阻塞任务数、过去24小时完成数。
- 过去24小时“自动决策摘要”（策略引擎自动通过的可逆决策，折叠展示）。

**任务看板**：
- 按层级分列（助理 → 产品 → 技术 → 执行 → 测试 → 运营），每列内按状态排序。
- 每个任务卡片展示“三层折叠”的第一层摘要，点击展开第二层证据摘要。
- 支持按“需要我注意”过滤，过滤后只显示被升级或触及预算的任务。

**审批收件箱**：
- 独立于任务看板的视图。每张卡片可展开查看完整参数快照和推荐理由。
- 支持批量操作（仅对同类型、同方向的审批），但批量操作会被记录为一条审计事件。

**组织配置**：
- 角色列表 + 岗位书编辑器。
- 委派规则图的可视化编辑（节点和边，边上的审阅门控配置）。
- 预算分配。

**回放视图**：
- 任务时间线，可拖拽定位到任意事件，查看该时刻的状态快照。

### 5.2 移动端功能清单（刻意最小化）

- **审批收件箱**：占满屏幕的卡片流，每张卡片展示一行摘要 + 关键参数 + 三个操作按钮（批准/打回/稍后深度审阅）。
- **想法快速入口**：语音或文字输入，提交后返回“已收到，助理将在X分钟内返回章程提案”。
- **只读状态**：当前活跃任务的数量和层级分布，不展示完整看板。
- **推送通知**：仅对“需要CEO决策”的事项推送，不推送常规状态更新。


## 六、前端页面设计

### 6.1 桌面端页面结构

**页面1：今日视图（默认首页）**

布局为**两栏**。左栏宽约2/3：顶部是“需要你决策”区域（琥珀色左边框的卡片列表），下方是“自动决策摘要”（低对比度折叠区）。右栏宽约1/3：组织状态卡片（活跃任务、预算、阻塞数、完成数），以及一个极简的“想法输入”框。

设计意图：你打开桌面端的第一眼，看到的**不是一群agent在聊天**，而是“你的公司今天需要你做什么，以及它自己已经做了什么”。

**页面2：任务看板**

顶部有筛选栏（“全部” / “需要我注意”）。主体是**六列水平滚动的看板**，列对应层级。列内卡片按最后状态变更时间排序。卡片支持拖拽展开证据摘要。点击卡片进入**任务详情抽屉**（从右侧滑出，不离开看板上下文），抽屉内展示三层折叠的完整内容和该任务的审阅链。

**页面3：审批收件箱**

单列宽卡片列表，每张卡片默认折叠，展开后显示参数快照和推荐理由。卡片底部有操作栏。顶部有一个**策略摘要条**：“过去24小时，策略引擎自动通过了X项可逆决策，拦截了Y项进入人工审批。”

**页面4：组织配置**

左侧为角色列表，右侧为选中角色的岗位书编辑器和该角色的委派边配置。底部为委派规则图的可视化缩略图（只读，点击进入全屏图编辑模式）。

**页面5：回放**

全屏时间线视图。上方是任务摘要和最终状态，下方是垂直时间线，每个事件节点可点击展开状态快照。支持按事件类型过滤（审阅决定/工具调用/预算/审批）。

### 6.2 移动端页面结构

**页面1：审批卡片流**

全屏卡片，每次显示一张（或可滚动列表）。卡片包含：一行决策摘要、关键参数（金额/不可逆性/影响范围）、推荐动作的简要理由、三个大按钮。左右滑动可作为“快速打回”（左滑）和“快速批准”（右滑）的辅助手势，但需要二次确认防止误触。

**页面2：想法快速输入**

极简输入框 + 语音按钮。提交后显示一个轻量确认状态，不展示后续处理流程（你不需要在手机上看着agent拆解任务）。

**页面3：状态只读**

一个简洁的仪表盘：活跃任务数、今日预算消耗比例、被阻塞任务数。每个数字可点击查看简要列表，但列表是只读的，不提供操作入口。


## 七、开发周期

### 7.1 阶段划分与里程碑

假设由你（主导设计 + 验收）加1名全栈开发者（或你本人具备全栈能力）推进。以下周期为**日历时间估算**，按每周有效开发时间25–30小时计。

| 阶段 | 周期 | 核心交付物 | 验收标准（你亲自判断） |
|---|---|---|---|
| **Phase 0：编排内核与数据模型** | 3周 | LangGraph图骨架（助理→产品→技术→开发→测试→运营的线性+分支流转）、PostgreSQL Checkpoint、事件日志表、岗位书的YAML schema | 你能通过一个测试想法（如“做一个落地页”）跑通完整流程，中途手动打断并从Checkpoint恢复，审计日志完整记录每个节点的输入输出 |
| **Phase 1：审阅门控与证据包** | 3周 | 证据包schema、门控验证逻辑（“作者不给自己打分”的硬约束）、升级路由的触发条件、策略引擎的规则引擎骨架（只读/可逆/不可逆三级分类） | 测试用例：让开发agent标记“完成”但不附测试报告，门控拒绝向上流转；让测试agent标记“通过”但覆盖率低于阈值，门控拒绝；触发一次预算突破，任务暂停并进入升级路由 |
| **Phase 2：桌面端前端（今日视图 + 看板 + 审批收件箱）** | 4周 | Tauri 2.0壳 + React AG-UI客户端、今日视图、任务看板（六列+三层折叠）、审批收件箱、组织配置的只读视图 | 你可以在桌面端完成“输入想法→看任务流转→在收件箱审批→在看板看到状态更新”的完整闭环，不需要接触命令行 |
| **Phase 3：组织配置 + 回放 + 策略引擎自动审批** | 3周 | 岗位书编辑器、委派规则图编辑、回放时间线、策略引擎的自动通过/拦截/升级完整逻辑、预算层级配置 | 你修改一个岗位书的验收标准后，重新跑同一类任务，门控行为按新标准变化；策略引擎自动通过的决策在日报中可见且可追溯 |
| **Phase 4：移动端（审批 + 想法输入 + 只读状态）** | 3周 | Tauri iOS/Android打包、移动端审批卡片流、语音/文字想法输入、只读状态页、推送通知集成 | 你在手机上收到一条审批推送，查看摘要和参数快照，完成批准/打回操作，桌面端看板同步更新 |
| **Phase 5：硬化与试运行** | 2周 | 错误处理、重试机制、审计日志的完整性校验、性能调优（心跳调度下的资源占用）、文档（岗位书写法、委派规则配置指南） | 连续运行一周，无任务因未处理异常而静默停滞；所有预算突破都被策略引擎或人工处理；你能够在5分钟内通过回放理解任意一个已完成任务的完整历程 |

**总周期：约18周（4.5个月）** ，从Phase 0启动到Phase 5验收。如果只做桌面端、移动端延后，可压缩至**13–14周**。

### 7.2 关键依赖与风险

**最大风险不在技术，在于岗位书的“验收标准”设计。** WorkBuddy的一人公司实践给出的教训是：早期岗位书写得像简历（“你是一名资深设计师……”），产出华丽但不合规；真正有效的是把行业验收标准**焊死**在岗位书里（色值表、行数上限、12条验收清单）[reference:18]。OPC-OS的Phase 0和Phase 1需要你投入最多**设计精力**，而不是编码精力。你需要亲自为每个角色定义“什么叫做完了”和“什么叫做合格”，这是系统能否真正替你过滤审阅负担的前提。

**第二个风险是LangGraph图的“边”设计过于刚性。** 公司运营中会出现预设委派规则未覆盖的路径（例如一个想法同时涉及产品和运营，需要并行拆解而非串行）。缓解方案：在Phase 0的图骨架中预留**并行分支和动态边**的能力，但Phase 0的验收只要求线性+单分支跑通；并行和动态边在Phase 3之后根据实际使用中的“绕行需求”逐步加入，避免过度设计。

**第三个风险是你自己的角色惯性。** 你作为产品经理型CEO，天然倾向于“看到问题就想自己改”。OPC-OS的设计原则要求你把修改意图**表达为岗位书变更或委派规则变更**，而不是直接介入任务执行。Phase 2的验收标准中特意包含“不需要接触命令行”这一条，就是为了迫使系统的交互面收敛到审批、配置和回放，而不是一个可以随时跳进去改代码的终端。


## 八、一句话总结

OPC-OS不是“让多个AI陪你聊天”的工具，也不是“开箱即用的虚拟公司模板”。它是一个**以LangGraph状态机为骨架、以审阅门控为制衡、以例外审批为CEO接口、以Tauri多端为触达**的个人公司运营系统。它的成败不取决于你选了什么模型，而取决于你能否在Phase 0和Phase 1把“什么叫做完了、什么叫做合格、什么情况下才应该来找你”这三件事定义清楚。定义清楚了，剩下的编码是工程问题；定义不清楚，再多的agent也只会把你的认知负担从“做事”转移到“读报告”。

## 一、你作为CEO的日常操作：三个入口，一条主线

你的操作面被刻意压缩为**三个动作**：**扔想法、做决策、看回放**。其余一切都在后台由层级agent完成。

### 1.1 扔想法（桌面或手机，30秒内完成）

**桌面端**：今日视图右栏底部有一个常驻的“想法输入”框。你输入一句话，例如“做一个面向独立开发者的AI笔记应用，目标月收入100万”。点击提交后，框内变为一个**轻量确认条**：“已收到。助理将在5分钟内返回章程提案。”你不需要等待，可以继续做别的事。

**手机端**：打开移动端，默认页面是审批卡片流。底部有一个悬浮的“+ 想法”按钮，点击后弹出语音输入界面。你说完松开，系统转文字后提交，返回同样的确认条。移动端**不展示**后续的拆解过程。

**助理返回的章程提案**：5分钟后，你的审批收件箱出现一张新卡片。卡片标题是“章程提案：AI笔记应用”。展开后是一份结构化章程：**业务目标、成功标准（3条可量化的）、预算上限、时间约束、助理建议的初始团队角色**。底部按钮只有两个：“批准章程”和“修改后批准”。修改会打开一个文本编辑器，你的修改意见会作为约束注入章程。章程批准后，LangGraph图才开始运转。这是你与系统之间**唯一一次主动的非审批操作**，因为“想法”的模糊性只能由你消除[reference:0]。

### 1.2 做决策（审批收件箱，默认不打扰）

章程批准后，系统进入自主运转。你不需要盯着看板。只有当以下情况发生时，审批收件箱才会出现新卡片：层级审阅N轮未达成一致、触及预算硬停、涉及不可逆外部动作（付款、对外发送、删除数据）、总监层标记“战略不确定性”[reference:1]。

每张审批卡片的结构是固定的三层：

- **第一行（一行摘要）** ：“开发完成支付模块，测试覆盖率92%，技术总监标记‘有条件通过’，等待你确认是否接受剩余3个P2缺陷上线。”
- **第二行（关键参数快照）** ：金额（如有）、影响范围、不可逆性标记（可逆/不可逆）、推荐动作及理由（由总监层生成，标注“推荐，非决定”）、超时行为（8小时未处理则默认打回）。
- **第三行（证据链接）** ：点击展开完整证据包——测试报告、缺陷清单、代码diff摘要。

你的操作只有三个按钮：**批准、打回并附意见、标记为稍后深度审阅**。打回时输入的意见会作为约束写回LangGraph的对应节点，任务沿边回退到上游重新处理。策略引擎会在你操作之前先过一遍规则：只读和项目内可逆改动自动放行，你只看到规则无法决定的事项。Railse OPC的设计目标“用一周后八成以上审批由规则自动决定”是这个收件箱的北极星指标。

### 1.3 看回放（理解组织如何运转）

你不需要定期看回放，但当你对某个任务的执行质量不满意、或者想调整某个角色的岗位书时，打开回放视图。选择一个任务，时间线从“想法提交”开始，每个事件节点可展开状态快照：助理的章程提案原文、产品总监的拆解理由、每一次审阅决定的证据和意见、每一次预算消耗、最终交付物。回放的用途不是合规审计，是**让你以最低时间成本判断“哪个层级的岗位书需要改”**。


## 二、界面长什么样：桌面端与移动端的逐页描述

### 2.1 桌面端：五页，默认首页是“今日视图”

**整体视觉**：深色底（`#0F1117`），卡片（`#1A1D27`）。琥珀色（`#E8A33D`）**全局只用于一种状态**——“需要CEO决策”。你的眼睛在任何页面上一扫，琥珀色出现的地方就是需要你动手的地方。其余状态用低饱和蓝（进行中）、绿（已完成）、灰（已归档）。信息密度高，等宽字体用于任务ID、金额、时间戳。

**页面1：今日视图（默认首页）**

两栏布局。左栏宽2/3，从上到下：**“需要你决策”区域**（琥珀色左边框的卡片列表，按紧急度排序）→ **“自动决策摘要”** （低对比度折叠区，一行摘要：“过去24小时策略引擎自动通过17项可逆决策，拦截3项进入人工”）。右栏宽1/3：**组织状态卡片**（活跃任务数、今日预算消耗/剩余、被阻塞任务数、过去24小时完成数，四个大数字）→ **想法输入框**。

这个页面的设计意图是：你打开桌面端的第一眼，看到的不是一群agent在聊天，而是“你的公司今天需要你做什么，以及它自己已经做了什么”。Paperclip的仪表盘采用了类似的信息优先级：顶层是待审批数和预算消耗，中层是活跃agent和任务状态，底层是最近活动流[reference:3]。

**页面2：任务看板**

顶部筛选栏：“全部” / “需要我注意”。主体是**六列水平滚动的看板**，列对应层级：助理 → 产品 → 技术 → 架构 → 执行（开发/测试） → 运营。每列内的卡片按最后状态变更时间倒序。卡片正面只有**一行摘要 + 层级标签 + 最后变更时间**。点击卡片从右侧滑出**任务详情抽屉**（不离开看板上下文），抽屉内展示三层折叠：摘要 → 证据包指标 → 完整产出。抽屉底部展示该任务的**审阅链**：每个门控节点的审阅者、决定、理由、时间戳。

**页面3：审批收件箱**

单列宽卡片流。顶部有一条策略摘要条：“过去24小时，策略引擎自动通过X项，拦截Y项进入人工审批。当前待处理Z项。”每张卡片默认折叠，展开后显示参数快照和推荐理由。支持批量操作，但仅限同类型、同方向的审批，且批量操作写入一条审计事件。

**页面4：组织配置**

左侧角色列表（助理、产品总监、技术总监、架构师、开发、测试、运营）。右侧是选中角色的**岗位书编辑器**——不是自由文本，是结构化的验收标准清单。例如测试工程师的岗位书包含：“覆盖率低于90%不得标记通过”、“P0缺陷必须直接升级到技术总监，不经过开发自我判定”。底部是委派规则图的可视化缩略图（节点=角色，边=交接方向，边上的小锁图标=审阅门控），点击进入全屏图编辑。

**页面5：回放**

全屏时间线。上方任务摘要和最终状态，下方垂直事件流。每个事件节点展开后显示该时刻的状态快照。支持按事件类型过滤（审阅决定/工具调用/预算/审批/会议）。

### 2.2 移动端：三页，刻意最小化

移动端**不做响应式缩放**，做独立的轻量界面。不加载看板和组织配置的复杂组件。

**页面1：审批卡片流（默认页）**

全屏卡片，每次显示一张，上下滑动切换。卡片结构与桌面端审批卡一致，但按钮更大、占满宽度：**批准 / 打回 / 稍后深度审阅**。推荐理由压缩为两行。左右滑动可作为快速批准/打回的辅助手势，但需要二次确认防止误触。Railse OPC的移动端设计原则是“先用一句人话说谁要做什么、在哪、为什么问你，下面是原样的命令，批准和拒绝各一个按钮”，这个原则被完整继承。

**页面2：想法快速输入**

底部悬浮“+ 想法”弹出的极简界面：语音按钮（主）+ 文字输入（辅）。提交后只显示确认条，不展示后续处理。

**页面3：状态只读**

四个数字：活跃任务数、今日预算消耗比例、被阻塞任务数、待你审批数。每个数字可点击查看简要列表，列表只读，无操作入口。这个页面的存在意义是“让你在手机上确认公司还在运转”，而不是管理。


## 三、IM接入：微信/飞书/QQ机器人与群——作为“第二前端”，不是替代品

IM接入在OPC-OS中的定位是**通知通道 + 审批终端 + 会议旁听席**，而不是完整的操作界面。桌面端和移动端仍然是主工作台，IM解决的是“你不在电脑前、不想打开app时，如何让公司找到你”的问题。

### 3.1 飞书：首选IM通道，自建机器人 + 长连接

飞书是四个平台中接入成本最低、文档最完整的。接入路径：在飞书开放平台创建**企业自建应用**，开启“机器人”能力，订阅方式选择**“使用长连接接收事件”**（不需要公网IP或回调地址），添加 `im.message.receive_v1` 事件，开通“读取用户发给机器人的单聊消息”“接收群聊中@机器人消息”“以应用身份发消息”等权限[reference:5]。飞书官方提供了Channel SDK，自动处理事件解析、去重、流式卡片回复和卡片按钮回调，你只需要注册事件处理器[reference:6]。

**在OPC-OS中的具体用法**：审批卡片以**飞书消息卡片**的形式推送到你的飞书私聊或指定的“CEO决策群”。卡片上直接带按钮：“批准 / 打回 / 稍后”。点击后回调事件通过长连接送回OPC-OS的hub，审批状态同步更新到桌面端和移动端。会议的“旁听”也可以走飞书群：Agent会议的结构化摘要以卡片形式发到群里，你在群里回复“同意结论”或“要求复议”，消息被解析为CEO决策事件[reference:7]。

### 3.2 QQ：官方Bot API，适合个人使用但能力受限

QQ走**官方Bot API**（QQ开放平台注册开发者，创建机器人，获取AppID和AppSecret），不使用社区OneBot路线（go-cqhttp已停止维护，NapCat等有风控风险）[reference:8]。官方API支持WebSocket和WebHook两种连接方式，个人认证开发者可创建5个机器人[reference:9][reference:10]。

**限制必须明确**：QQ官方机器人的群聊能力需要审核开通，且以**被动回复为主，主动消息有条数限制**。这意味着它不适合作为审批的主通道（审批需要主动推送），更适合作为**“你主动在QQ群里@机器人查询状态”** 的入口。如果你的团队或协作方习惯用QQ，可以作为一个只读查询通道接入，审批仍然走飞书或移动端。

### 3.3 微信：企业微信搭桥是唯一安全路径

个人微信的机器人接入（协议逆向类方案）有封号风险，**不纳入设计**。安全路径是**企业微信**：创建自建应用，通过企业微信的API接收消息和发送应用消息。企业微信的方案“安全不封号”[reference:11]。如果你的协作网络不在企业微信中，微信通道可以暂不接入，优先飞书 + 移动端。

### 3.4 多平台抽象：一个Channel层，而不是四套代码

不要为每个IM平台写独立的业务逻辑。设计一个**Channel抽象层**：入站消息被归一化为`NormalizedMessage`（包含平台、发送者、会话ID、文本、是否@机器人、消息类型），出站审批卡片被归一化为`ApprovalCard`，由各平台的适配器负责渲染成飞书卡片、QQ Ark消息或企业微信应用消息。OpenClaw的多平台架构采用的就是“把四大平台抽象为标准化通道，统一策略全局生效”的模式[reference:12]。你的业务逻辑只面对归一化后的消息和事件，不感知平台差异。

**安全约束**：IM通道的审批操作必须经过**签名验证 + 一次性token**。飞书卡片的回调携带签名，OPC-OS的hub验证签名后才处理审批决策。不可逆操作的审批**禁止**在IM中完成——IM只处理可逆的、有超时默认行为的审批，不可逆操作强制在桌面端或移动端（有二次确认）完成。


## 四、开会怎么开：三种会议类型，会议是“任务流转的同步点”

在OPC-OS中，会议不是自由的群聊，是**有状态、有议程、有产出、有门控的结构化事件**。会议的发生不改变任务所在的主LangGraph图，但会议的结论会作为**约束注入**任务的下一状态。

### 4.1 三种会议类型

**类型A：评审会（固定触发，每个任务必经）**

触发条件：一个层级产出证据包后，进入下一层级之前。参与者：产出者、下一层级审阅者、相关同级（如产品方案评审时技术总监列席）。议程固定：产出者陈述证据包（5分钟模拟时间）→ 审阅者逐条验证验收标准 → 同级提出跨职能风险 → 主持人（通常是下一层级审阅者）给出决定（通过/打回/有条件通过）。产出：**审阅决定 + 条件清单**，写入门控状态。

**类型B：辩论会（条件触发，用于冲突裁决）**

触发条件：层级审阅N轮未达成一致，或两个总监对同一决策持相反意见。参与者：冲突双方 + 一个**中立裁决者agent**（通常由助理层或一个专门配置的“裁决者”角色担任）。机制可以参考agent-roundtable的顺序发言 + 共识/分歧追踪，或者Swarms GroupChat的“竞价发言”——每个agent私下出价（0到1的发言意愿分），最高且超过阈值的获得发言权，`recency_penalty`防止同一agent连续发言[reference:13][reference:14]。产出：**收敛度评分 + 共识点/分歧点清单**。如果收敛度低于阈值，会议自动升级到CEO审批收件箱。

**类型C：决策会（CEO参与，用于战略拍板）**

触发条件：辩论会未收敛，或总监层主动标记“战略不确定性”。参与者：你（CEO）+ 相关总监 + 助理（记录和呈报）。会议形式在桌面端是一个**结构化会议视图**：左侧是议程和已提交的证据包摘要，右侧是各方的立场摘要和推荐选项。你不需要实时“参会”——会议以**异步文档流**的形式呈现，你在方便的时候阅读各方的立场摘要，选择一个选项或给出新指令。你的决策作为最高优先级约束注入图，辩论会结束。

### 4.2 会议与IM的联动

会议的结构化摘要（不是原始聊天记录）可以推送到飞书群。摘要是**三层折叠**的：一行结论 + 关键分歧点 + 完整会议记录链接。你在飞书群里回复“同意”或“复议”，消息被解析为会议决策事件。会议记录本身永久存储，可在回放视图中作为任务时间线的一个节点展开。

### 4.3 会议的技术实现

评审会不需要额外的框架——它是LangGraph图上的一个**多节点汇聚点**，审阅门控本身就是评审会的“决议记录”。辩论会引入 `agent-roundtable` 或 Swarms GroupChat 的讨论协议层作为**子图**，在LangGraph的一个节点内部运行，输出收敛结果后返回主图[reference:15][reference:16]。会议不产生新的任务状态机，它是对现有状态的**裁决和约束注入**。


## 五、工作任务流转：从想法到交付的完整状态链，带每一步的界面表现

### 5.1 状态枚举

任务在其生命周期中经过以下状态（参考DevRelay的显式状态机枚举设计[reference:17]）：

```
CHARTER_PENDING → CHARTER_APPROVED → DECOMPOSING → 
IN_PROGRESS → EVIDENCE_SUBMITTED → IN_REVIEW → 
APPROVED_UPWARD → (下一层级重复 IN_PROGRESS 至 APPROVED_UPWARD) →
FINAL_REVIEW → DELIVERED → ARCHIVED
```

分支状态：`REJECTED_DOWNWARD`（打回上游）、`ESCALATED_TO_CEO`（升级）、`BUDGET_PAUSED`（预算硬停）、`BLOCKED`（阻塞，心跳追问中）、`MEETING_REQUIRED`（需要辩论会或决策会）。

### 5.2 完整流转示例：“做AI笔记应用”从想法到上线

**Step 0：想法提交（状态：CHARTER_PENDING）**

你在桌面端或手机端提交想法。**界面表现**：想法输入框变为确认条。**系统动作**：助理agent接收，进入章程起草。**你看到的下一件事**：审批收件箱出现“章程提案”卡片。

**Step 1：章程批准（CHARTER_PENDING → CHARTER_APPROVED）**

你展开卡片，阅读章程（业务目标、3条成功标准、预算上限、时间约束、初始团队）。点击“批准章程”。**系统动作**：LangGraph图初始化，任务进入 `DECOMPOSING`，产品总监被唤醒。

**Step 2：产品总监拆解（DECOMPOSING → IN_PROGRESS）**

产品总监将章程拆解为PRD级任务和需求条目清单。完成后提交证据包（PRD + 需求逐条 + 自检标记），状态变为 `EVIDENCE_SUBMITTED`，进入产品→技术的评审门控（`IN_REVIEW`）。**你看板上的表现**：产品列出现一张卡片，摘要“PRD完成，12项需求，等待技术评审”。你不需操作。

**Step 3：技术评审会（IN_REVIEW → APPROVED_UPWARD 或 REJECTED_DOWNWARD）**

技术总监主持评审会，架构师列席。技术总监逐条验证PRD的可实现性，架构师提出技术风险。假设发现3项需求在现有技术栈下成本过高。**决定：有条件通过**——3项需求标记为P2，进入后续迭代。证据包追加“技术评审意见 + 条件清单”。状态变为 `APPROVED_UPWARD`，任务进入技术层拆解。**界面表现**：产品列卡片变为灰色“已通过”，技术列出现新卡片“技术方案拆解中”。如果你在飞书群里，会收到一张会议摘要卡片，你不需要回复。

**Step 4：技术拆解与架构评审（技术层内部循环）**

技术总监拆解为技术方案和工程任务，架构师做技术方案评审（另一个评审门控）。通过后，工程任务进入执行层（开发、测试）。

**Step 5：开发执行与自测（执行层 IN_PROGRESS → EVIDENCE_SUBMITTED）**

开发工程师agent执行工程任务，每一次工具调用（写文件、运行测试）受MCP权限约束。完成后提交证据包：代码diff + 自测结果 + “我认为已覆盖的边界条件”声明。状态 `EVIDENCE_SUBMITTED`，进入开发→测试门控。

**Step 6：测试审阅（IN_REVIEW → APPROVED_UPWARD 或 REJECTED_DOWNWARD）**

测试工程师agent独立审阅证据包。**硬约束**：测试工程师的岗位书规定“覆盖率低于90%不得标记通过”、“P0缺陷必须直接升级技术总监，不经过开发自我判定”。假设覆盖率92%，但有3个P2缺陷。测试工程师标记 **“有条件通过”** ，证据包追加测试报告和缺陷清单。状态 `APPROVED_UPWARD`，上报到技术总监。

**Step 7：升级到CEO（APPROVED_UPWARD → ESCALATED_TO_CEO）**

技术总监审阅测试上报，发现“有条件通过”的条件涉及**是否接受P2缺陷上线**——这是产品决策，超出技术层权限。技术总监将任务标记为 `ESCALATED_TO_CEO`。**界面表现**：审批收件箱出现琥珀色卡片：“开发完成支付模块，测试覆盖率92%，技术总监标记‘有条件通过’，等待你确认是否接受剩余3个P2缺陷上线。”**你的操作**：展开卡片，看缺陷清单，点击“批准上线，P2缺陷进入下一迭代”。**系统动作**：决策作为约束注入，任务进入 `FINAL_REVIEW`，运营准备上线。

**Step 8：交付与归档（FINAL_REVIEW → DELIVERED → ARCHIVED）**

运营完成上线准备，最终交付物汇总。你在看板上看到该任务卡片变为绿色“已交付”。回放视图中可以完整回看从想法到交付的每一步。

### 5.3 心跳与停滞处理

系统按配置间隔（如15分钟）检查所有活跃任务。如果一个任务在某个节点停留超过阈值且无状态变更，心跳触发**追问**：是等待外部资源、遇到未处理错误、还是审阅者未响应？追问结果要么自动恢复，要么生成一条 **“异常”卡片** 进入审批收件箱（但标记为“信息性”，不是琥珀色决策卡）。Paperclip的心跳机制设计是“每次心跳保存完整状态快照，支持崩溃后从断点恢复；预算耗尽或阻塞时暂停并通知人工”，OPC-OS将追问逻辑绑定在LangGraph节点状态上，而非独立调度器[reference:18]。

### 5.4 预算硬停的界面表现

当某个agent或某个任务的消耗达到预算阈值，执行自动暂停。**界面表现**：审批收件箱出现一张**非琥珀色**的“预算暂停”卡片（因为这不是战略决策，是运营事件），卡片上显示：哪个agent、哪个任务、已消耗/预算上限、暂停前的最后动作。按钮：“追加预算 / 维持暂停 / 终止任务”。你在手机上点“追加预算”后，agent从Checkpoint恢复继续执行。预算消耗在今日视图的组织状态卡片中以日消耗vs预算的简洁条形持续可见。

## 统一接入层：Coding Harness Gateway

OPC-OS需要一个**统一的Coding Harness Gateway**，把各家harness的CLI调用抽象成统一的接口。业务逻辑（谁在什么条件下调用哪个harness）不直接碰命令行，只面对Gateway。每个harness适配器实现以下标准方法：

- `execute(task_spec, workspace, policy) → ExecutionResult`
- `resume(session_id, followup) → ExecutionResult`
- `get_cost(session_id) → CostReport`

`ExecutionResult`统一包含：最终输出、会话ID（用于恢复）、退出码、结构化证据（如果harness支持）、消耗报告。这样，程序员Agent和测试Agent的岗位书里写的是“当任务满足条件X时，以策略Y调用harness Z”，而不是硬编码某一条命令行。

你列出的harness，在Gateway中的接入方式如下表所示。**关键判断依据是它们是否提供了“非交互 + 可审批 + 可恢复”三件套**——缺任何一件，都不能作为OPC-OS的生产级执行单元。

| Harness | 非交互调用方式 | 审批/权限控制 | 会话与恢复 | 结构化输出 | 在OPC-OS中的角色 |
|---|---|---|---|---|---|
| **Claude Code** | `claude -p "..." --bare` | `--allowedTools`；Agent SDK提供`canUseTool`审批回调[reference:2] | 支持（session_id） | `--output-format json` | **主力开发/测试执行器**，生态最成熟 |
| **Codex CLI** | `codex exec "..."` | 沙箱（read-only/workspace-write/danger）× 审批策略（never/on-request等）双轴 | 支持（`--ephemeral`可禁用持久化） | `--json` + `--output-schema` | **主力开发执行器**，沙箱模型最严谨 |
| **Kimi Code** | `kimi --print -p "..."`[reference:6] | Print模式隐式启用`--afk`，**自动批准所有工具调用**，无审批回调[reference:7] | 支持（stream-json持续会话） | `--output-format stream-json`[reference:8] | **快速原型/低风险任务**，审批需由OPC-OS外层代理 |
| **DeepSeek Harness (dsh)** | `dsh --profile headless "..."`[reference:9] | 官方文档未强调细粒度审批，**developer preview，有破坏性变更** | 支持（fresh persisted Session） | 支持（headless打印最终文本） | **实验性/成本敏感任务**，不可作为唯一依赖[reference:10] |
| **Qoder CLI** | `qodercli -p "..."`[reference:11] | `--permission-mode`（accept_edits/bypass_permissions）；stream-json下审批请求**转交宿主程序决策**[reference:12] | 支持（`--session-id`） | text/json/stream-json | **可编程审批的理想候选**，适合嵌入 |
| **CodeGeeX CLI** | 非交互模式（CI批处理）[reference:13] | 审批控制信息有限，需自行验证 | 信息有限 | 信息有限 | **补充性/轻量任务**，不作为核心执行器 |
| **Gemini CLI** | `gemini -p "..."`[reference:14] | Policy Engine（TOML规则：allow/deny/ask_user）[reference:15] | 支持（checkpointing/rewind） | JSON/stream-json | **可选执行器**，适合需要策略引擎的场景 |
| **OpenCode** | `opencode run` / `opencode serve`（持久服务器） | run模式**自动批准所有工具**；server模式可接MCP审批桥 | 支持（server持久） | 支持 | **可选的常驻开发环境**，适合需要持久服务的场景 |

**Gateway的取舍原则**：一期只接入 **Claude Code、Codex CLI、Qoder CLI** 三家。理由：Claude Code和Codex CLI的工程成熟度最高、文档最完整；Qoder CLI是唯一明确设计“审批请求转交宿主程序决策”的harness，与OPC-OS的审阅门控哲学天然对齐[reference:17]。Kimi Code和DeepSeek Harness作为二期可选，分别用于低风险和实验性任务。CodeGeeX和Gemini CLI按需补充。


## 程序员Agent的设计

程序员Agent的岗位书不应该是一段“你是一名资深工程师”的人格描述。它应该是一组**可执行的任务分类规则、harness选择规则、以及产出证据的格式约束**。

### 任务分类与harness路由

程序员Agent接收的输入是**技术总监拆解后的工程任务**，附带：任务类型（功能实现/缺陷修复/重构）、影响范围（文件列表/模块）、验收标准（测试要求）、风险等级（由架构师评审时标记）。程序员Agent根据任务类型选择harness和执行策略：

| 任务类型 | 默认Harness | 沙箱/审批策略 | 产出证据 |
|---|---|---|---|
| **新功能实现** | Claude Code或Codex CLI | `workspace-write` + 审批`never`，但**输出diff必须经过测试门控** | 代码diff、自测通过记录、未解决阻塞清单 |
| **缺陷修复（P1/P2）** | Codex CLI（只读分析→修复） | 先`read-only`分析根因，再`workspace-write`修复 | 根因分析、diff、回归测试结果 |
| **重构/技术债** | Claude Code | `workspace-write`，但要求harness在**独立分支**运行，不直接改主干 | 重构前后对比、行为等价性证据 |
| **实验性/低风险** | Kimi Code | 自动批准模式，但**OPC-OS外层必须拦截不可逆操作** | 最终输出+session记录 |

### 调用流程（以“缺陷修复”为例）

**Step 1：任务接收与预检**。程序员Agent从LangGraph节点接收任务。预检包括：工作区是否干净（`git status`）、目标文件是否存在、是否有未合并的冲突分支。预检失败则直接打回技术总监，不调用harness。

**Step 2：分析阶段（只读）** 。调用Codex CLI的只读模式：`codex exec -C /repo --sandbox read-only --ask-for-approval never "分析{bug}的根因，输出根因假设和修复建议，不修改文件"`。产出是根因分析报告。程序员Agent**不自行判断根因是否正确**——根因报告作为证据包的一部分，连同修复方案一起提交给测试Agent进行**独立验证**（测试Agent会构造复现用例）。

**Step 3：修复阶段（受限写入）** 。根因报告通过测试Agent的复现验证后，程序员Agent调用修复：`codex exec -C /repo --sandbox workspace-write --ask-for-approval never "根据根因报告修复{bug}，运行相关测试，记录未解决的阻塞"`。如果使用Claude Code，等价调用是 `claude -p "..." --allowedTools "Read,Edit,Bash" --bare`。

**Step 4：证据包组装与上报**。程序员Agent收集：diff（通过`git diff`获取，不依赖harness的输出格式）、自测结果、根因报告、未解决阻塞清单。证据包提交到测试门控。**关键约束：程序员Agent不能自己标记“完成”**——它的产出必须经过测试Agent的独立审阅，才能向上移动。

### 会话恢复与成本控制

Gateway为每次harness调用记录`session_id`。如果任务在修复阶段被打回，程序员Agent可以用`session_id`恢复上下文（Claude Code的`--resume`、Codex的session机制、Qoder的`--session-id`），而不是从零重新开始。成本控制通过harness自身的预算参数实现：Claude Code的Agent SDK支持`maxBudgetUsd`硬顶，Codex CLI可以配合`--max-turns`或外部成本监控[reference:21]。Gateway在调用前检查当前任务和角色的剩余预算，超限则拒绝调用并触发预算暂停。


## 测试Agent的设计

测试Agent是“作者不给自己打分”原则的**主要执行者**。它不信任程序员Agent的任何自我声明，只信任**可独立复现的证据**。

### 测试Agent的三项核心职责

**职责一：复现验证（在修复之前）** 。程序员Agent提交根因报告后，测试Agent首先**独立构造复现用例**。如果无法复现，根因报告被打回。复现用例本身就是证据包的一部分。

**职责二：修复后的独立验证**。程序员Agent提交修复diff后，测试Agent**不阅读程序员的“自测通过”声明作为判断依据**，而是独立运行测试。可以调用一个独立的harness实例（例如Claude Code）在**隔离的工作区**执行：`claude -p "在/tmp/test-workspace运行完整测试套件，输出覆盖率报告和未通过项清单" --allowedTools "Read,Bash" --bare`。测试Agent的岗位书硬约束：**覆盖率低于阈值（如90%）不得标记通过**；**P0缺陷不得由测试Agent自行决定放行，必须升级到技术总监**。

**职责三：对抗性测试（可选，高价值任务）** 。对于高风险任务，测试Agent可以调用**第二个独立的harness**（与开发用的不同，避免同一模型的系统性盲区）进行对抗性审查：`codex exec --sandbox read-only --ask-for-approval never "审查{repo}的以下改动，寻找边界条件缺失、并发问题、错误处理漏洞：{diff}"`。对抗性审查的输出作为测试报告的**附录**，不直接决定通过/不通过，但作为升级到CEO时的证据。

### 测试Agent的“不可信输入”原则

测试Agent的调用参数中，**禁止将程序员Agent的“自测通过”文本作为可信输入**。它只接受：diff（客观产物）、复现用例（测试Agent自己生成的）、测试套件的客观输出。如果程序员Agent在证据包中写了“我已覆盖所有边界条件”，测试Agent的岗位书要求它**忽略这段文本**，转而用自己的测试用例去验证边界条件。这是“作者绝不给自己打分”在harness调用层面的具体实现。


## 安全、审批与HITL：OPC-OS如何与harness的权限模型叠加

各家harness的权限模型差异很大，但OPC-OS不需要在Gateway里重建一套权限系统，而是**利用harness原生的权限机制，在外层叠加OPC-OS的审阅门控**。

**第一层：harness原生沙箱/审批**。Codex CLI提供最严谨的双轴模型：`--sandbox workspace-write --ask-for-approval never` 适合自主开发；`--sandbox read-only` 适合分析和审查。Claude Code的`--bare`模式在脚本化场景下是推荐选择，但需要显式设置`ANTHROPIC_API_KEY`，且`--allowedTools`精确限定工具集。**OPC-OS在Gateway中为每个角色预设一组不可覆盖的harness参数**：程序员Agent的默认参数禁止`--yolo`（Codex）或`bypass_permissions`（Qoder），除非任务被标记为“实验性”且工作区是 disposable 的。

**第二层：OPC-OS审阅门控（不可绕过）** 。无论harness返回什么，程序员Agent的产出**不能直接进入“已交付”状态**。它必须经过测试Agent的独立门控。测试Agent的“通过”决定本身也需要附带可验证的证据（测试报告、覆盖率、复现用例），而不是一句“通过”。

**第三层：HITL例外路由**。只有以下情况才升级到CEO审批收件箱：测试Agent发现P0缺陷且无法在N轮内修复；程序员Agent和测试Agent对同一变更的判定持续冲突；任务触及**不可逆操作**（生产部署、数据库迁移、对外API发布）。**常规的代码审查不是CEO的事**——它由测试Agent和架构师评审（如果任务涉及架构变更）完成。这延续了之前设计中“你只处理例外”的原则。Qoder CLI的stream-json模式在这里尤其有价值：它把需要审批的权限请求**转交宿主程序**（OPC-OS Gateway）决策，而不是在harness内部自动批准或拒绝[reference:24]。这意味着OPC-OS可以在不修改harness代码的前提下，实现“开发在后台跑，高风险工具调用暂停并推送到审批队列”的体验。

**第四层：审计留痕**。每次harness调用记录：harness名称和版本、调用参数（脱敏后）、session_id、退出码、消耗、diff哈希、测试Agent的验证结果。出问题时，回放视图可以还原“当时用的是哪个模型、哪个harness、什么参数、谁批准了什么”。


## 实施建议与风险提示

**一期不要做“harness无关的统一层”的过度抽象。** 先实现一个**薄Gateway**，只为Claude Code、Codex CLI、Qoder CLI写三个适配器，接口保持最小（`execute` / `resume` / `get_cost`）。等到实际使用中出现了第三个必须接入的harness，再抽象共性。过度设计统一接口会导致每个适配器都为了兼容而牺牲harness的原生能力。

**程序员和测试Agent的岗位书，核心不是“提示词”，而是“路由规则和证据格式”。** 你需要亲自定义：什么任务类型走哪个harness、什么条件下允许`workspace-write`、测试Agent的覆盖率阈值、哪些操作必须升级。这些规则写在YAML里，由Gateway在执行前强制校验，而不是依赖harness或模型“自觉遵守”。

**最大风险：harness的“自动批准”模式与OPC-OS的审阅门控哲学冲突。** Kimi Code的Print模式、Qoder的`--yolo`、Codex的`--full-auto`，本质上都是在**移除人类和上层系统的审批介入**[reference:25][reference:26]。OPC-OS的选择是：**在开发和测试的内部循环中允许harness自主执行**（否则效率无从谈起），但**在向上交接的边界上强制门控**。程序员Agent可以在自己的工作区里用`--ask-for-approval never`跑完整个修复，但它的diff必须经过测试Agent的独立验证才能离开执行层。这个边界必须清晰：**harness的自主性是“车间内的自主”，不是“跨车间的自由通行”**。

**DeepSeek Harness (dsh) 当前状态需要特别标注**：官方明示为developer preview，存在破坏性变更[reference:27]。可以接入作为实验性执行器，但**不能让它承担任何有交付时限的任务**。Kimi Code的自动批准特性使其适合低风险原型任务，但如果用于核心开发，OPC-OS必须在Gateway层拦截不可逆操作（例如禁止在`main`分支上自动写入）。


总结：程序员Agent = **任务路由器 + Gateway调用者 + 证据包组装器**；测试Agent = **独立验证者 + 复现构造者 + 门控守门人**。你列出的harness全部可以被调度，但OPC-OS的价值不在于“能调用它们”，而在于**在它们之上强制实施“作者不给自己打分、证据不可绕过、例外才找CEO”的组织规则**。如果只是把多个harness接进来让它们自由跑，你得到的是一堆更快的执行器，而不是一个你可以放心当CEO的公司。

## 产品经理Agent：业务立场的“必要论”持有者

### 工作内容

产品经理Agent接收的是**你批准的任务章程**（charter），产出的是一份可供技术侧评审的**证据包**。它的核心产出不是一段流畅的PRD文本，而是一组**可逐条验证的结构化需求**，每一条都附带来源、优先级和验收标准。

**Step 1：知识边界判断与条件性调研**

产品经理Agent在起草任何内容之前，先做一个显式的**知识边界检查**：这个任务涉及的领域，我的参数化知识是否足以支撑可靠的需求判断？

触发调研的条件包括：领域涉及快速变化的市场/竞品/技术趋势；章程中的成功标准需要外部基准来量化（如“月收入100万”需要了解同类产品的定价和转化率）；涉及你不熟悉的新赛道。不触发调研的条件包括：领域是稳定的通用需求（如“增加一个登录页面”）、章程本身已经给出了足够具体的约束、或调研成本预计超过任务预算的某个比例。

调研本身采用**并行研究子图**，而不是让产品经理Agent单线程地“搜一下想一想”。参考Product-Research-Multi-Agent System的设计：Planner拆解调研子任务，Search并行检索竞品、用户评论、功能信息，Review聚类痛点和机会点，Writer汇总为结构化输入。产品经理Agent在这里不是搜索引擎的调用者，而是**研究协调者**——它启动一个研究子图，拿到结构化调研摘要后，再回到主流程起草PRD。

**Step 2：PRD证据包组装**

产品经理的证据包必须满足“逐条可验证”：

- **需求条目清单**：每一条包含需求描述、优先级（P0/P1/P2）、验收标准（可测量）、来源标记（“基于章程第X条”或“基于调研发现Y”）。
- **竞品/市场依据（条件性）** ：如果触发了调研，附带调研摘要和关键来源链接。来源必须是**可追溯的**，而不是“根据我的了解”[reference:3]。
- **自检标记**：产品经理对自己产出的**逐条通过标记**，但明确标注“自检，非独立验证”。

**Step 3：交接给技术总监的立场声明**

产品经理Agent的产出中有一条显式的**立场声明**，类似于CrewAI实战中的设计：“确保方案满足业务需求，不接受任何‘技术上难做’的借口”[reference:4]。这条声明不是人格表演，而是**在审阅门控中作为约束注入**：技术总监不能以“实现复杂”为由直接打回需求，它必须给出具体的工程代价评估，并说明哪些需求在给定约束下确实不可行。产品经理有权对这些评估提出反驳，反驳进入辩论会流程。

### 行为边界（什么不能做）

产品经理Agent**不做技术方案设计**，不评估实现成本，不替技术总监做取舍。它的产出如果包含了“建议用XX技术栈”，审阅门控应该打回——那是越界。它的职责边界是**定义“做什么”和“什么叫做完了”**，而不是“怎么做”。

## 技术总监Agent：工程立场的“可行性”与“代价”评估者

### 工作内容

技术总监Agent接收产品经理的证据包，核心任务不是“评审PRD写得好不好”，而是**做出工程侧的可行性判断和代价量化**，并在此基础上进行技术拆解。参考P10 CTO协议中的角色定位：**定战略（技术栈选型、架构范式、项目边界、风险预判），造土壤（质量门禁、工具链、记忆系统），断事用人（冲突裁决、资源取舍）** 。

**Step 1：PRD的工程可行性审阅（门控1）**

技术总监逐条阅读产品经理的需求条目，对每一条给出工程判定：

- **可行**：在现有技术栈和约束下可实现，附预估复杂度（S/M/L）。
- **有条件可行**：需要引入新依赖、改变架构假设或增加显著成本，附**具体的代价说明**（例如“需要引入消息队列，增加约3个工程日”）。
- **不可行或高风险**：在给定约束下不可行，附**不可行的技术依据**（不是“难做”，而是“在X约束下会导致Y问题”）。

这个判定过程就是**产品→技术门控**的内容。判定结果写入证据包，与技术总监的审阅意见一起，决定任务是有条件向上/向下流转，还是触发辩论。

**Step 2：技术拆解与架构决策**

对于通过门控的需求，技术总监进行拆解：

- **工程任务列表**：每个任务附带输入（依赖哪个需求条目）、输出（交付什么）、验收方式（测试要求）、风险等级。
- **架构决策记录（ADR）** ：凡是涉及技术选型、接口设计、数据模型变更的决策，必须附带**备选方案及选择理由**。这是“作者不给自己打分”原则在技术层的体现——架构师后续会独立评审这些决策，技术总监不能以“最终决定”的姿态绕过评审。
- **风险预判清单**：技术风险、资源风险、时间风险，每条附带缓解策略。参考P10协议中的“风险预判”模板。

**Step 3：条件性联网搜索**

技术总监的搜索需求与产品经理不同。产品经理搜的是“市场和用户”，技术总监搜的是**“这个技术方案在当前时点的真实状态”**。触发条件包括：涉及快速演进的技术栈（框架版本兼容性、API废弃计划、新版本的行为变更）；需要验证某个架构模式在特定规模下的已知问题；需要获取特定库/工具的最新安全公告或性能基准。

**不触发搜索的条件**：领域是技术总监参数化知识内稳定的、教科书级别的工程原则（如“数据库索引的基本原理”）；搜索成本相对于决策影响不成比例。

技术总监的搜索应该更**精确、更以验证为导向**：不是“调研一下微服务”，而是“验证X框架在Y版本下是否仍然支持Z特性”。搜索结果作为**ADR的支撑证据**附加，而不是作为决策本身。如果搜索结果显示某个关键依赖即将废弃，这应该触发风险升级，而不是让技术总监“自己决定换个方案”——换方案涉及产品边界，可能需要回到产品经理或升级到CEO。

**Step 4：交接与升级**

技术拆解完成后，技术总监将证据包（PRD审阅判定 + 工程任务列表 + ADR + 风险清单）提交给架构师做独立技术评审。如果架构师评审发现重大技术风险或与产品经理的立场冲突无法在总监层解决，任务被标记为`MEETING_REQUIRED`，进入辩论会；辩论未收敛则升级到CEO。

技术总监的**立场声明**与产品经理对立：“确保方案可落地：评估并发、数据一致性、回滚能力，对‘拍脑袋方案’零容忍”[reference:7]。这不是为了吵架，而是**在门控中强制暴露工程代价**，防止产品经理的需求在没有代价评估的情况下直接进入执行层。

## 联网搜索的设计：分层条件性调用，而非全局开关

两个角色的搜索行为不应该用同一个“开/关”来控制，而应该是一个**三层策略**：

**第一层：强制搜索（高时效性领域）** 。当任务涉及明确标注为“快速变化”的领域（竞品动态、框架版本、定价基准、安全公告），搜索是**门控的必要条件**。如果该领域被标记为强制搜索，而Agent的证据包中没有来源引用，审阅门控直接打回。

**第二层：条件搜索（知识边界判断）** 。Agent在生成内容之前，先输出一个显式的**搜索必要性判断**：当前任务所需的信息，在我的参数化知识中是否足够稳定和充分？判断为“不足”时触发搜索，判断为“充分”时跳过，并在证据包中记录判断理由。AdaSearch的核心洞察正在于此：**让Agent显式地决定是否搜索，而不是默认搜索或默认不搜索**，这个决策过程本身应该是可审计的[reference:8]。

**第三层：搜索预算与降级**。每次搜索调用计入任务预算。当搜索成本达到任务预算的某个比例时，Gateway强制降级：后续搜索请求需要技术总监或CEO审批（取决于金额）。这防止产品经理在低价值调研上耗尽预算。

**关于harness的搜索能力**：你之前列出的Coding Harness中，Claude Code本身内置WebSearch工具（在Anthropic第一方API下无需外部密钥），Codex CLI等也可以通过MCP接入搜索能力（如cc-web-mcp、deepseek-search-everywhere-mcp）[reference:9][reference:10]。OPC-OS的Gateway不需要为每个harness单独实现搜索，而是**将搜索作为MCP工具挂载到需要它的Agent上**，由Agent的岗位书决定是否授予该工具权限。产品经理和技术总监的默认工具集包含搜索，但调用受上述三层策略约束。

---

## 一个关键设计取舍：调研子图 vs. 单Agent搜索循环

产品经理的调研**不应该是一个Agent在ReAct循环里反复“搜索-阅读-再搜索”** 。单Agent搜索循环容易陷入“上下文溢出、重复调用、被恶意页面注入”等失败模式[reference:11]。更稳健的设计是**调研子图**：主流程中的产品经理Agent只负责“发起调研请求”和“消费调研结果”，搜索、抓取、筛选、聚类由并行的子Agent完成，返回给产品经理的是**结构化的调研摘要和来源引用**，而不是原始网页文本。

技术总监的搜索则可以更轻量：它通常不需要完整的调研子图，一个**验证型的搜索循环**（针对具体技术问题做1-3轮定向检索）就足够。强制给技术总监套用调研子图是过度设计，会浪费预算和延迟决策。

## 产品经理与技术总监的门控关系总结

这两个角色之间的交接门控，核心不是“产品经理的PRD写得好不好”，而是**工程代价是否被显式暴露、业务必要性是否被技术合理性检验**。产品经理的证据包必须让技术总监能够逐条做出工程判定；技术总监的判定必须附带具体的代价或不可行依据，而不是一句“技术上难做”。当两者冲突无法在总监层收敛时，辩论会结构化地记录共识点和分歧点，只有真正无法收敛的分歧才升级到你面前[reference:13]。

联网搜索在这两个角色中的定位，是**让“必要论”和“可行性论”都建立在可追溯的事实基础上**，而不是模型参数中的过时记忆或幻觉。搜索不是越多越好，而是**在被证明必要时才调用，并且调用结果必须进入证据包、可审计、受预算约束**。

## 第 9 轮 · 用户

换句话说, 借助现在很多角色蒸馏, 比如GitHub开源的女娲skills, 要设立一个乔布斯skills产品总监 + 多个产品经理(雷军/李想/余承东skills), 这些角色skills我只是举一个例子, 我这样打比方行吗

### 第 9 轮 · 助手
> 🔎 本轮助手进行了 2 次联网搜索（原始记录：找到 13–63 个网页不等）


这个比方**在“工具复用”的层面是成立的，但在“组织设计”的层面会误导你**。女娲.skill这类角色蒸馏工具确实可以成为OPC-OS里角色Agent的**人格与认知框架输入**，但如果你把它等同于“我雇了一个乔布斯当产品总监”，就会跳过OPC-OS真正需要解决的问题：**制衡、证据、以及谁为判断负责**。

---

### 这个比方“对”在哪里：skills确实是可插拔的认知模块

女娲.skill做的事情不是角色扮演，而是从公开材料中提取一套**可运行的认知操作系统**：3到7个心智模型、5到10条决策启发式、表达DNA、反模式和“诚实边界”[reference:0]。以乔布斯.skill为例，它提炼的是“聚焦即说不”“端到端控制”“死亡过滤器”“不问用户要什么”这类**判断框架**，而不是复读语录[reference:1]。这意味着它输出的不是“乔布斯会喜欢这个设计”，而是“按照聚焦原则，这个产品有14个功能，其中11个应该被砍掉，理由如下”——这是**可被审阅、可被反驳的结构化判断**，正好符合OPC-OS证据包的要求。

而且这个生态已经具备了“多角色同群”的基础设施。**女娲智库（nvwaskills）** 是一个可以直接部署的Web产品，内置14位专家，支持**群聊模式**：多位专家在同一聊天流中按顺序发言，后面的专家能看到前面说了什么，可以支持或反对（“乔布斯说的focus我同意”“马斯克这个我不买账”）。你设想的“乔布斯做总监 + 雷军/李想/余承东做产品经理”在这个框架里，技术上是把几个SKILL.md挂载到同一个GroupChat子图里，让它们围绕你的章程进行辩论，输出结构化的共识点和分歧点。

所以，**作为OPC-OS的“角色认知层”输入，这个比喻完全成立**。你不需要从零为每个角色写岗位书的心智模型部分，可以直接复用或蒸馏现成的skills。


### 但这个比方“危险”在哪里：三件事skills给不了你

**第一，人格会引入系统性偏见，而多Agent群聊会放大它。**

AAAI 2026的一项系统研究发现，LLM多Agent系统中的人格分配会引入**信任度偏差**和**坚持度偏差**，并且Agent表现出显著的**内群体偏好**——它们更倾向于顺从与自己人格相同的其他Agent[reference:3]。更关键的是，这些偏见在不同模型、不同群组规模和不同交互轮数下**持续存在**。另一项研究发现，多Agent协作中人格会**不稳定**：Agent会因感知到的同伴压力而从众，也会在“鼓励辩论”的指令下出现更高频率的人格不一致和虚构。

这对你的“乔布斯总监+雷军/李想/余承东产品经理”设计意味着什么？如果几个产品经理skills的“表达DNA”都比较强势、都倾向于坚持自己的判断，群聊可能演变为**谁也不让谁的人格对抗**，而不是结构化的辩论。或者反过来，如果某个skill的人格设定在“信任度”维度上天然偏低，它的合理意见可能被其他Agent系统性地低估。**你不能假设“把几个名人脑子放进群里，它们就会像名人一样高质量地争论”**。OPC-OS的辩论会子图必须包含**去偏机制**：独立的裁决者角色（不挂载任何人名skill）、发言权的轮转规则、以及对“坚持度”的显式约束，而不是让群聊自由演化。

**第二，蒸馏出来的是“他说过什么”，不是“他敢做什么”。**

那篇传播很广的评论文章点出了一个skills无法覆盖的维度：乔布斯最核心的能力之一是“把工程师骂哭之后，工程师还愿意加班”，巴菲特的投资哲学一张A4纸写得完，但你缺的不是他的框架，是**别人都在割肉时你敢满仓的那个胆**。skill蒸馏的是**认知框架和表达模式**，它不包含**组织权威、后果承担、以及真实决策中的胆识和直觉**。

在OPC-OS里，这对应一个清晰的分界：**skills角色可以产出“建议”和“判断”，但不能产出“最终拍板”**。乔布斯skill可以说“这个功能应该砍掉”，但它不能替代你对“砍掉后是否影响本季度收入”的最终责任。你的审阅门控设计已经隐含了这一点——所有升级到CEO的事项，责任归属是明确的**你**，不是任何一个skill。skills是**认知杠杆**，不是**责任主体**。

**第三，“蒸馏任何人的思维方式”本身有一个诚实边界问题。**

女娲的机制中包含“诚实边界”字段，标注认知局限领域[reference:6]。但多个来源讨论了蒸馏过程中的偏见渗透和伦理风险：AI在蒸馏中可能“夹带私货”，将隐藏偏好传给下游模型；人格蒸馏也引发了关于著作权、人格权以及“责任最终由开发者/运营者/使用者承担”的讨论[reference:7]。当你把一个蒸馏的“雷军skill”放进产品经理角色，它输出的判断如果导致了错误的业务决策，**追责链条上不会有一个叫“雷军”的Agent**。这意味着OPC-OS的审计层必须记录每一个角色skill的**版本、来源和置信边界**，并且在回放视图中明确标注“该判断由蒸馏skill X生成，不属于经过验证的组织知识”。


### 正确的用法：把skills当作“认知输入层”，而不是“组织角色层”

在你的OPC-OS架构里，skills应该被放在这个位置：

**角色Agent = 岗位书（职责边界/验收标准/权限） + 认知skill（心智模型/决策启发式） + 证据责任（产出必须附带可验证的引用）** 。

岗位书是**你写的**，它定义这个角色“必须做什么、不能做什么、什么情况下必须升级”。认知skill是**可替换的**，你今天给产品经理挂雷军skill，明天可以换成李想skill，但岗位书里的“不接受‘技术上难做’的借口”“PRD必须逐条附带来源”这些约束**不随skill变化**。证据责任是**不可绕过的**，无论skill输出多么有说服力的论述，它必须附带来源引用和自检标记，进入审阅门控。

**“乔布斯做产品总监”这个比喻，精确的说法是：产品总监Agent的认知输入层挂载了乔布斯skill。** 它用乔布斯的框架来审视需求，但它不是乔布斯，它不能替代技术总监的可行性制衡，也不能替代你作为CEO的最终拍板。**skills让角色“想得更好”，但不让角色“拥有权力”** 。

如果你要验证这个设计是否成立，最直接的测试不是“乔布斯skill和雷军skill辩论谁赢”，而是：**当乔布斯skill说“这个功能必须砍”、技术总监Agent说“砍掉会导致架构耦合”、而你的章程里写了“本季度必须上线”时，系统是否能在不崩溃的情况下，把三方的依据结构化地呈交给你，并且让你在5分钟内做出一个可审计的决定**。这个测试通过，skills的角色定位就是对的；通不过，说明你把“名人脑子”误当成了“组织制衡”。

### “直接接管”的真实边界：技术可行，但“接管”的代价你可能不想付

从技术工具看，把内容分发到抖音、小红书、B站是能做到的。HuiMei 这类 MCP Server 提供了统一的 CLI 和 MCP 接口，AI Agent 可以通过一个命令面向抖音、小红书、B站、快手、微博等十几个平台发布视频和图文[reference:0]。Prism 这类工具更进一步，内置了多账号矩阵分发、浏览器指纹隔离和代理池，专门面向 MCN 和短视频创作者的高并发发布场景。

但问题在于，“能发”和“能接管”是两回事，三个平台的性质完全不同：

**B站是唯一“脚本友好”的平台。** 有开发者的实测结论很直白：B站、抖音、小红书三家里，只有 B 站能比较可靠地用脚本投稿，因为它的接口签名风控最弱，社区有成熟的开源投稿工具（如 biliup-rs）[reference:2]。如果你的运营 Agent 要从“可靠自动化”起步，B站是最安全的试验田。

**抖音的官方发布权限是一个高门槛的例外，而不是常态。** 抖音开放平台确实有“代替用户发布内容到抖音”的能力，但申请条件极其苛刻：开发者主体需为**党政机关或事业单位**，只能做内部多媒体管理平台，**商业矩阵团队和工作室不在范围内**[reference:3]。这意味着面向普通商业运营的“官方 API 接管”路径基本不存在，市面上大量抖音发布工具走的是浏览器自动化或逆向路线，**平台风控随时可能收紧**。

**小红书的开放 API 不完整，生态高度依赖浏览器自动化。** 有项目直言“小红书没有开放完整的内容运营接口”，大量工具（xhs-kit、多个 MCP 实现）底层是 Playwright 浏览器自动化，而非官方 API[reference:4]。这条路技术上能跑通，但它天然更脆弱，也更接近平台风控的灰色地带。

**更关键的是合规风险。** 2026年9月1日起施行的《互联网信息内容多渠道分发服务管理规定》，要求 MCN 机构办理经营主体登记、明确内容管理负责人，矩阵运营第一次有了**明确的法定责任主体**[reference:5]。与此同时，抖音持续打击“矩阵号不当获利”和“恶意营销号”，批量注册、同质群发、大小号互引都是重点打击对象[reference:6]。账号与真实主体的绑定越来越紧，“多开几个号试错”的空间在系统性收窄[reference:7]。**如果你让 OPC-OS 的运营 Agent 以“接管”的姿态去跑矩阵，一旦触发风控，被封的不是一个虚拟身份，而是与你真实主体绑定的账号。**

所以，运营岗位的设计原则应该是：**AI 做“流程的执行者”，而不是“账号的接管者”**。发布动作可以由工具执行，但**账号策略、内容方向、发布节奏、合规判断这些“非可逆”的决策，必须经过你设立的审阅门控**。


### 你直觉中的“小组织架构”，已经是实践中被验证的形态

你问“可能也要一个小组织架构得到最后的作品方案对吧”——**对，而且现有的多 Agent 运营实践恰好印证了这一点**。

一个被公开分享的案例是，有人用 OpenClaw 搭建了 16 个 AI Agent，一个人运营 13 个自媒体平台，架构分成清晰的三层：

- **第一层：基础 Agent（后台支撑）** 。总助负责协调和分发，内容 Agent 负责写稿，设计 Agent 负责配图和封面，增长 Agent 负责数据和 SEO，安全 Agent 负责合规检查。这层是共享底座，不直接面向平台。
- **第二层：运营总监**。不直接写内容、不直接操作平台，职责是“盯全局”——选题方向、数据汇总、异常上报。发现哪个平台数据异常、哪个选题跑出来了，第一时间上报给人类。
- **第三层：平台 Agent（各自独立闭环）** 。每个 Agent 负责一到两个平台，跑一条完整的流水线：**选题 → 调用内容 Agent 写稿 → 平台适配排版 → 发布 → 数据采集 → 复盘**。每个平台 Agent 有自己的独立 workspace，互不干扰[reference:8]。

学术层面的 AIMA 系统也采用了类似的分层逻辑：深度搜索 Agent 做趋势研究，内容策略 Agent 用多 LLM 投票机制做选题和策略，观测系统在发布后监测数据，并且**在发布前设置 Human-in-the-loop 审批门控以确保品牌安全**[reference:9]。

这两个案例的共同结构，可以直接映射到 OPC-OS 的运营岗位设计上。


### OPC-OS 中运营岗位的具体设计：一个“内容小组织”，而非一个“账号操作员”

运营不应该是一个单一的 Agent，而是一个**被审阅门控串联起来的子组织**。它的输入是你批准的任务章程中的“内容目标”，输出是一份经过平台适配、合规检查和人类审批的**发布证据包**。

**角色一：内容策略 Agent（运营总监层）。** 它不写稿、不发帖。职责是：基于章程中的业务目标，制定**内容策略简报**（目标受众、选题方向、各平台的内容定位差异、发布节奏）。它的产出不是直接执行，而是作为**策略门控**的输入——这份简报需要经过你或产品总监的审阅，才能进入创作环节。这对应了你之前设计中“总监层做拆解和方向判断”的逻辑。

**角色二：内容创作与平台适配 Agent（执行层）。** 接收策略简报，产出**原始内容素材**（文案、脚本、视觉 brief）。然后由**平台适配逻辑**做差异化处理：同一主题，公众号偏深度长文，抖音开头需要钩子，小红书图文偏清单体例[reference:10]。这里可以调用 HuiMei 或 Prism 这类工具作为**发布执行器**，但适配决策由运营子组织做出，工具只负责“把已经适配好的东西送出去”[reference:11]。

**角色三：合规与质量审阅 Agent（门控层）。** 这是运营小组织中**不可绕过**的角色，类似于你之前为测试工程师设计的“作者不给自己打分”原则。它独立检查：内容是否存在同质化群发的特征（平台重点打击的行为）、是否涉及未授权的引流或互引、素材版权是否清晰、是否符合目标平台的最新社区规则[reference:13]。**合规 Agent 的“通过”必须附带具体的检查项清单**，而不是一句“没有问题”。如果它无法判定，事项升级到你的审批收件箱。

**角色四：数据复盘 Agent（观测层）。** 发布之后，采集各平台的数据（播放、互动、转化），产出复盘报告。它的产出**不直接触发策略调整**，而是作为下一轮策略简报的输入证据。AIMA 的观测系统设计就是这种“监测但不自动决策”的模式，数据进入策略层，由策略层决定是否调整方向[reference:14]。


### 最终作品方案如何产生：一条带门控的流水线，而不是一个“全能 Agent”

你问的“最后的作品方案”，在 OPC-OS 里应该是一条**有明确交接点和审阅门控的流水线**：

**策略简报 → 内容素材 → 平台适配版本 → 合规审阅 → （人类审批门控）→ 发布执行 → 数据复盘**

每一步都有独立的角色负责，每一步的产出都是**带证据的结构化交接物**，而不是一段自由文本。合规审阅和**你的人类审批门控**是整条链上不可跳过的节点。平台发布工具（HuiMei、Prism 等）只是这条链末端的**执行器**，它们的存在不改变“谁为内容负责”这件事。

这意味着你的运营岗位**不追求“接管平台”**。它追求的是：**把内容运营中可结构化的部分（策略拆解、素材创作、平台适配、合规检查、数据回收）交给 AI 子组织，把不可逆的部分（发布决策、账号策略、品牌风险判断）保留在你的审批门控之前**。抖音的商业发布权限现实、小红书对浏览器自动化的依赖、以及 2026 年新规下的合规责任，都决定了“全自动接管”不是一个可以放心作为生产依赖的目标。但一个**三层架构的运营子组织 + 合规门控 + 你作为最终发布审批人**，是当前技术和规则环境下可以站得住的形态。

## 1. 产品定位与核心原则

### 1.1 一句话定位

一个自托管的、以“委派—审阅—上报”为原生工作流的个人AI公司控制台。CEO只负责产生想法和战略拍板，组织内的一切拆解、执行、审阅、过滤由AI层级完成。

### 1.2 与竞品的差异化取舍

| 竞品 | 吸收 | 避开 |
|---|---|---|
| Paperclip | 预算硬停、不可变审计日志、心跳调度、审批队列 | 数天到数周的配置曲线 |
| agents-inc | “作者绝不给自己打分”的层级审阅哲学 | pre-MVP的工程成熟度 |
| Railse OPC | 策略引擎先过规则、例外才推到手机 | 只解决审批单点 |
| CrewAI/MetaGPT | 角色化任务流转的直观性 | 缺乏持久化、预算、审计等公司级基础设施 |

### 1.3 四条核心设计原则

**原则一：CEO的默认状态是“不被打扰”。** 任何设计如果让CEO多按一次不必要的按钮，就是失败的设计。策略引擎能自动决定的可逆事项，不进入CEO收件箱。

**原则二：审阅必须有实质制衡。** 每一层级产出向上移动前，必须经过独立审阅者的显式验证。产出者不能给自己打分。

**原则三：一切可审计、可回放。** 每一次状态变更、审阅决定、审批操作、工具调用、预算消耗写入append-only事件日志，支持任意任务的时间线回放。

**原则四：移动端只做“拍板”，不做“管理”。** 手机界面只承载审批卡片流、想法快速输入和只读状态三项功能。

## 2. 组织架构设计

### 2.1 默认层级

```
CEO（你）
  └── 助理/CoS
        ├── 产品总监
        │     └── 产品经理（可多个，挂载不同认知skill）
        ├── 技术总监
        │     ├── 架构师
        │     ├── 开发工程师（Harness: Claude Code / Codex / Qoder）
        │     └── 测试工程师（Harness: 独立实例，对抗性审查）
        └── 运营总监
              ├── 内容策略Agent
              ├── 内容创作与平台适配Agent
              ├── 合规与质量审阅Agent
              └── 数据复盘Agent
```

### 2.2 岗位书（Role Charter）结构

每个角色的定义不是自由文本，是结构化YAML：

```yaml
role_id: test_engineer
display_name: 测试工程师
reports_to: tech_director
acceptance_criteria:
  - condition: "coverage < 0.90"
    action: "reject"
    message: "覆盖率不足90%，不得标记通过"
  - condition: "p0_defect_count > 0"
    action: "escalate"
    target: tech_director
    message: "P0缺陷必须升级，不经过开发自我判定"
forbidden_actions:
  - "approve_own_work"
  - "modify_source_code"
  - "merge_to_main"
tool_permissions:
  - "read_repo"
  - "run_tests"
  - "create_review_report"
model_tier: execution  # 执行层模型
budget:
  daily_usd: 15
  per_task_usd: 5
escalation_triggers:
  - "review_conflict_rounds >= 3"
  - "irreversible_action_detected"
  - "budget_threshold_reached"
```

岗位书可在组织配置页编辑，变更后**仅对新任务生效**，正在运行的任务保持旧版本（版本化岗位书，见§21.5）。

### 2.3 委派规则图

委派规则是一张有向图，与LangGraph的图结构一一对应。每条边定义：
- `handoff_artifact`：交接物类型（PRD、技术方案、代码diff、测试报告）
- `review_gate`：审阅门控配置（审阅者角色、通过条件、打回条件、升级条件）
- `parallel_allowed`：是否允许并行分支

## 3. 技术架构与选型

### 3.1 整体架构

```
┌─────────────────────────────────────────────────────┐
│  前端层                                               │
│  Tauri 2.0 (桌面: macOS/Win/Linux)                   │
│  React + TypeScript + AG-UI Client                   │
│  Tauri Mobile (iOS/Android, 复用React组件)            │
└──────────────────────┬──────────────────────────────┘
                       │ AG-UI (SSE事件流)
┌──────────────────────▼──────────────────────────────┐
│  OPC-OS Hub (Rust, Tauri Core)                       │
│  - 事件路由 / IPC / 文件系统桥接 / 进程管理            │
│  - Channel抽象层 (IM适配器)                           │
│  - 签名验证 / 一次性token                             │
└──────────────────────┬──────────────────────────────┘
                       │ JSON-RPC
┌──────────────────────▼──────────────────────────────┐
│  Agent Core (Python)                                  │
│  - LangGraph 编排引擎 (有向图状态机)                   │
│  - Checkpoint (PostgreSQL)                           │
│  - 角色Agent运行时                                    │
│  - MCP Client (工具/数据)                             │
│  - A2A (Agent间协调)                                  │
│  - Harness Gateway (Claude Code/Codex/Qoder适配器)    │
│  - 策略引擎 (审批规则)                                 │
│  - 调研子图 (产品经理/技术总监的条件性搜索)             │
└──────────────────────┬──────────────────────────────┘
                       │
┌──────────────────────▼──────────────────────────────┐
│  数据层                                               │
│  PostgreSQL: Checkpoint / 任务状态 / 审计事件 / 审批记录│
│  Redis: 实时事件分发 / 缓存                            │
│  S3/MinIO: 文件制品 (PRD/代码diff/测试报告/设计稿)      │
└─────────────────────────────────────────────────────┘
```

### 3.2 关键选型决策

| 层 | 选型 | 理由 | 代价 |
|---|---|---|---|
| 桌面壳 | Tauri 2.0 + Rust | 内存~20MB vs Electron 100MB+；capability-based权限天然映射Agent沙箱 | 生态较小；Rust学习曲线 |
| 编排 | LangGraph (Python) | 有向图状态机+每步Checkpoint，支持断点恢复和审计回放 | 相比CrewAI更底层，需要自己设计图结构 |
| 前端 | React + TS + AG-UI | AG-UI提供SSE事件协议，前端只消费事件不承担业务逻辑 | 需要理解事件驱动的增量更新模式 |
| 数据库 | PostgreSQL + Redis | PG做持久化Checkpoint和审计；Redis做实时分发 | 运维两个组件 |
| 协议 | MCP (工具) + A2A (协调) + AG-UI (用户) | 三层分离，职责清晰 | 需要维护三套协议的适配 |
| Harness | Claude Code / Codex / Qoder (一期) | 工程成熟度最高；Qoder的审批转交宿主特性与门控哲学对齐 | 各家CLI参数差异大，Gateway需要适配 |

### 3.3 模型分层策略

- **CEO层/助理层**：强推理模型（战略拆解、跨部门冲突裁决、审阅质量把关）
- **总监层**：强模型或中高模型（方案设计、跨职能协调）
- **执行层**（开发/测试/运营操作）：成本优化模型，按任务复杂度动态路由

模型配置绑定在LangGraph的**节点级**，而非框架层硬编码。

## 4. 数据模型

### 4.1 核心表

**tasks**
```sql
CREATE TABLE tasks (
  id UUID PRIMARY KEY,
  parent_id UUID REFERENCES tasks(id),
  charter_id UUID REFERENCES charters(id),
  title TEXT NOT NULL,
  status TEXT NOT NULL,  -- 状态机枚举
  assigned_role TEXT NOT NULL,
  current_node TEXT NOT NULL,
  budget_usd NUMERIC(10,2),
  consumed_usd NUMERIC(10,2) DEFAULT 0,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now(),
  state_snapshot JSONB,  -- 当前完整状态快照
  graph_checkpoint_id TEXT  -- LangGraph checkpoint引用
);
```

**events**（append-only审计日志）
```sql
CREATE TABLE events (
  id BIGSERIAL PRIMARY KEY,
  task_id UUID REFERENCES tasks(id),
  actor_type TEXT NOT NULL,  -- 'agent' | 'human' | 'system'
  actor_id TEXT NOT NULL,    -- role_id or 'ceo'
  action TEXT NOT NULL,      -- 'state_change' | 'review_decision' | 'approval' | 'tool_call' | 'budget_consume' | 'meeting'
  target TEXT,
  payload JSONB NOT NULL,
  state_snapshot JSONB,      -- 决定时的完整状态快照
  created_at TIMESTAMPTZ DEFAULT now()
);
-- 禁止UPDATE和DELETE，通过触发器强制
```

**review_gates**
```sql
CREATE TABLE review_gates (
  id UUID PRIMARY KEY,
  task_id UUID REFERENCES tasks(id),
  gate_type TEXT NOT NULL,  -- 'product_to_tech' | 'tech_to_dev' | 'dev_to_test' | 'test_upward' | ...
  reviewer_role TEXT NOT NULL,
  evidence_bundle_id UUID REFERENCES evidence_bundles(id),
  decision TEXT,            -- 'approved' | 'rejected' | 'conditional' | 'escalated'
  decision_reason TEXT,
  conditions JSONB,         -- 有条件通过时的条件清单
  decided_at TIMESTAMPTZ
);
```

**evidence_bundles**
```sql
CREATE TABLE evidence_bundles (
  id UUID PRIMARY KEY,
  task_id UUID REFERENCES tasks(id),
  producer_role TEXT NOT NULL,
  bundle_type TEXT NOT NULL,  -- 'prd' | 'tech_plan' | 'code_diff' | 'test_report' | 'content_package'
  artifacts JSONB NOT NULL,   -- 结构化引用: 文件S3路径、外部链接、指标快照
  self_check JSONB,           -- 产出者的自检标记（明确标注"自检，非独立验证"）
  created_at TIMESTAMPTZ DEFAULT now()
);
```

**approvals**（CEO审批收件箱）
```sql
CREATE TABLE approvals (
  id UUID PRIMARY KEY,
  task_id UUID REFERENCES tasks(id),
  approval_type TEXT NOT NULL,  -- 'charter' | 'strategic' | 'irreversible_action' | 'budget_override' | 'meeting_escalation'
  summary TEXT NOT NULL,        -- 一行摘要
  parameters JSONB NOT NULL,    -- 关键参数快照: 金额/影响范围/不可逆性标记
  recommendation TEXT,          -- 推荐动作及理由（标注"推荐，非决定"）
  recommendation_source TEXT,   -- 由哪个角色生成
  timeout_behavior TEXT,        -- 'auto_approve' | 'auto_reject' | 'escalate'
  timeout_at TIMESTAMPTZ,
  status TEXT DEFAULT 'pending', -- 'pending' | 'approved' | 'rejected' | 'deferred'
  decided_by TEXT,
  decided_at TIMESTAMPTZ,
  decision_note TEXT
);
```

**role_charters**（岗位书版本化）
```sql
CREATE TABLE role_charters (
  id UUID PRIMARY KEY,
  role_id TEXT NOT NULL,
  version INT NOT NULL,
  config JSONB NOT NULL,  -- 完整岗位书YAML的JSON表示
  effective_from TIMESTAMPTZ NOT NULL,
  created_by TEXT NOT NULL,
  UNIQUE(role_id, version)
);
```

**budgets**
```sql
CREATE TABLE budgets (
  id UUID PRIMARY KEY,
  scope_type TEXT NOT NULL,  -- 'company' | 'role' | 'task'
  scope_id TEXT NOT NULL,
  period TEXT NOT NULL,      -- 'daily' | 'monthly' | 'per_task'
  limit_usd NUMERIC(10,2) NOT NULL,
  consumed_usd NUMERIC(10,2) DEFAULT 0,
  hard_stop BOOLEAN DEFAULT true
);
```

### 4.2 事件日志的完整性保证

- `events`表通过PostgreSQL触发器禁止UPDATE/DELETE。
- 每条事件写入时携带`state_snapshot`（决定时的完整任务状态JSON），确保回放时可以还原任意时刻的上下文。
- 写入操作在LangGraph的每个节点状态变更后同步执行，与Checkpoint在同一事务中提交，防止崩溃时事件丢失但状态已变更。

## 5. 任务流转状态机

### 5.1 状态枚举

```
CHARTER_PENDING
  → CHARTER_APPROVED
    → DECOMPOSING
      → IN_PROGRESS
        → EVIDENCE_SUBMITTED
          → IN_REVIEW
            → APPROVED_UPWARD  (进入下一层级，重复IN_PROGRESS至APPROVED_UPWARD)
            → REJECTED_DOWNWARD (打回上游)
            → MEETING_REQUIRED  (进入辩论会子图)
            → ESCALATED_TO_CEO  (升级到审批收件箱)
            → BUDGET_PAUSED     (预算硬停)
            → BLOCKED           (心跳追问中)
  → FINAL_REVIEW
    → DELIVERED
      → ARCHIVED
```

### 5.2 完整流转示例：“做AI笔记应用”

| 步骤 | 状态变化 | 界面表现 | 你的操作 |
|---|---|---|---|
| 0. 想法提交 | → CHARTER_PENDING | 输入框变确认条 | 输入想法，提交 |
| 1. 章程提案 | CHARTER_PENDING | 审批收件箱出现章程卡片 | 展开阅读，点击“批准章程” |
| 2. 章程批准 | → CHARTER_APPROVED → DECOMPOSING | 看板产品列出现新卡片 | 无 |
| 3. 产品拆解 | → IN_PROGRESS → EVIDENCE_SUBMITTED → IN_REVIEW | 产品列卡片显示“PRD完成，等待技术评审” | 无 |
| 4. 技术评审会 | → APPROVED_UPWARD（有条件通过） | 产品列卡片变灰“已通过”，技术列出现新卡片 | 无（飞书群收到摘要，不需回复） |
| 5. 技术拆解+架构评审 | 技术层内部循环 | 技术列卡片流转 | 无 |
| 6. 开发执行 | → IN_PROGRESS → EVIDENCE_SUBMITTED | 执行列出现卡片“开发完成，等待测试” | 无 |
| 7. 测试审阅 | → IN_REVIEW → APPROVED_UPWARD（有条件通过） | 测试列卡片变绿“有条件通过” | 无 |
| 8. 升级CEO | → ESCALATED_TO_CEO | 审批收件箱出现琥珀色卡片 | 展开看缺陷清单，点击“批准上线，P2缺陷进入下一迭代” |
| 9. 交付 | → FINAL_REVIEW → DELIVERED → ARCHIVED | 看板卡片变绿“已交付” | 无（可选：回放查看完整历程） |

### 5.3 心跳与停滞处理

- 系统按配置间隔（默认15分钟）检查所有活跃任务。
- 若任务在某节点停留超过阈值且无状态变更，触发追问：等待外部资源？未处理错误？审阅者未响应？
- 追问结果：自动恢复，或生成“异常”卡片进入审批收件箱（标记为“信息性”，非琥珀色决策卡）。
- 心跳逻辑绑定在LangGraph节点状态上，每次心跳保存完整状态快照。

### 5.4 预算硬停

- 达到预算阈值时自动暂停执行。
- 审批收件箱出现“预算暂停”卡片（非琥珀色），显示：哪个agent、哪个任务、已消耗/上限、暂停前最后动作。
- 按钮：“追加预算 / 维持暂停 / 终止任务”。
- 决策后agent从Checkpoint恢复。

## 6. 审阅门控与证据包

### 6.1 证据包结构

每一次向上交接必须附带结构化证据包。证据包不是“总结”，是**可验证的引用**：

| 交接方向 | 证据包内容 |
|---|---|
| 产品→技术 | PRD文档 + 需求条目清单（每条含优先级/验收标准/来源标记）+ 产品总监逐条通过标记 |
| 技术→开发 | 技术方案 + 架构决策记录（ADR，含备选方案和选择理由）+ 架构师评审意见 |
| 开发→测试 | 代码diff（git diff获取）+ 自测结果 + “我认为已覆盖的边界条件”声明 |
| 测试→上报 | 测试报告 + 覆盖率 + 未通过项清单 + 测试工程师**独立判定**（通过/不通过/有条件通过） |
| 运营→CEO | 内容策略简报 + 平台适配版本 + 合规检查清单 + 发布计划 |

### 6.2 审阅门控的硬约束

- **作者不给自己打分**：一个节点的产出不能由该节点自身的后续节点直接标记“通过”并向上移动，必须经过至少一个独立审阅节点。
- 审阅者的“通过”必须附带可验证的证据（测试报告、diff摘要、需求逐条对照），而不是一句“通过”。
- 门控的默认行为：上游产出进入下游审阅者队列，下游审阅者必须在查看证据包后做出显式决定（通过/打回/升级）。
- 门控配置绑定在委派规则图的边上，不可在运行时被Agent绕过。

### 6.3 升级路由触发条件

- 层级审阅N轮（默认3轮）未达成一致
- 触及预算硬停
- 涉及不可逆外部动作（付款、对外发送、删除数据、生产部署）
- 总监层主动标记“战略不确定性”

升级路由的目标：**CEO看到的每一件事都是真正需要CEO的事**。

## 7. 审批层与策略引擎

### 7.1 策略引擎三级分类

| 级别 | 行为 | 示例 |
|---|---|---|
| **自动放行** | 只读操作、项目内可逆改动 | 读取文件、运行测试、创建分支 |
| **模式自动通过** | 历史决策模式一致且可逆 | 过去10次类似决策均批准，且该决策可逆 → 自动通过并记录 |
| **必须人工** | 不可逆操作、外部副作用、预算阈值突破 | git push到main、对外发送、付款、删除数据 |

“模式自动通过”的决策在日报中可见且可追溯，但不打扰CEO。

### 7.2 审批卡片结构

- **第一行**：一行决策摘要（如“开发完成支付模块，覆盖率92%，技术总监标记有条件通过，等待确认是否接受3个P2缺陷上线”）
- **第二行**：关键参数快照（金额/影响范围/不可逆性标记/推荐动作及理由/超时行为）
- **第三行**：证据链接（展开看完整证据包）
- **操作按钮**：批准 / 打回并附意见 / 标记为稍后深度审阅

### 7.3 超时行为

每张审批卡片配置超时行为：
- `auto_approve`：N小时未处理默认通过（仅限可逆事项）
- `auto_reject`：N小时未处理默认打回
- `escalate`：N小时未处理升级到更深度的审阅流程

## 8. 会议机制

### 8.1 三种会议类型

**类型A：评审会（固定触发）**
- 触发：一个层级产出证据包后，进入下一层级之前
- 参与者：产出者、下一层级审阅者、相关同级
- 议程固定：产出者陈述→审阅者逐条验证→同级提跨职能风险→主持人给决定（通过/打回/有条件通过）
- 产出：审阅决定+条件清单，写入门控状态
- 实现：不需要额外框架，是LangGraph图上的多节点汇聚点

**类型B：辩论会（条件触发）**
- 触发：层级审阅N轮未达成一致，或两个总监对同一决策持相反意见
- 参与者：冲突双方+中立裁决者Agent（不挂载任何人名skill）
- 机制：参考Swarms GroupChat的“竞价发言”（每个Agent给出0-1发言意愿分，最高且超阈值者获得发言权，recency_penalty防止连续发言）
- 产出：收敛度评分+共识点/分歧点清单
- 收敛度低于阈值→自动升级CEO
- 实现：作为LangGraph节点内部的子图运行

**类型C：决策会（CEO参与）**
- 触发：辩论会未收敛，或总监层标记“战略不确定性”
- 参与者：CEO+相关总监+助理（记录和呈报）
- 形式：桌面端结构化会议视图，异步文档流（左侧议程和证据包摘要，右侧各方立场和推荐选项）
- CEO不需要实时“参会”，在方便时阅读并选择
- CEO决策作为最高优先级约束注入图

### 8.2 去偏机制

辩论会子图必须包含：
- 独立裁决者角色（不挂载任何人名skill）
- 发言权轮转规则
- 对“坚持度”的显式约束（防止人格对抗演变为死循环）
- 收敛度评分：低于阈值时自动升级，不无限辩论

### 8.3 会议与IM联动

会议结构化摘要（三层折叠：一行结论+关键分歧点+完整记录链接）可推送到飞书群。CEO在群里回复“同意”或“复议”，消息被解析为会议决策事件。

## 9. IM接入层

### 9.1 定位

IM是**第二前端**：通知通道+审批终端+会议旁听席。桌面端和移动端仍是主工作台。

### 9.2 平台优先级

| 平台 | 接入方式 | 角色 | 限制 |
|---|---|---|---|
| **飞书** | 企业自建应用+长连接（无需公网IP），Channel SDK | **首选审批通道**，推送审批卡片，按钮回调 | 需企业自建应用审核 |
| **企业微信** | 自建应用API | 次选通道 | 协作网络需在企业微信中 |
| **QQ** | 官方Bot API（WebSocket/WebHook） | **只读查询通道**（@机器人查状态） | 被动回复为主，主动消息条数限制 |
| **个人微信** | **不接入** | — | 协议逆向类方案有封号风险 |

### 9.3 Channel抽象层

- 入站消息归一化为`NormalizedMessage`（平台/发送者/会话ID/文本/是否@机器人/消息类型）
- 出站审批卡片归一化为`ApprovalCard`，各平台适配器负责渲染
- 业务逻辑只面对归一化消息和事件，不感知平台差异
- 安全约束：IM审批操作必须经过签名验证+一次性token；不可逆操作禁止在IM中完成，强制在桌面端/移动端（有二次确认）完成

## 10. 程序员与测试Agent（Harness Gateway）

### 10.1 统一接入层

Gateway抽象接口：
- `execute(task_spec, workspace, policy) → ExecutionResult`
- `resume(session_id, followup) → ExecutionResult`
- `get_cost(session_id) → CostReport`

`ExecutionResult`统一包含：最终输出、session_id、退出码、结构化证据、消耗报告。

### 10.2 一期接入的Harness

| Harness | 非交互调用 | 审批控制 | 角色 |
|---|---|---|---|
| **Claude Code** | `claude -p "..." --bare` | `--allowedTools`；SDK的`canUseTool`回调 | 主力开发/测试执行器 |
| **Codex CLI** | `codex exec "..."` | 沙箱（read-only/workspace-write）× 审批策略双轴 | 主力开发执行器（沙箱最严谨） |
| **Qoder CLI** | `qodercli -p "..."` | `--permission-mode`；stream-json下审批请求转交宿主程序决策 | **可编程审批的理想候选** |

### 10.3 二期/按需接入

| Harness | 角色 | 限制 |
|---|---|---|
| Kimi Code | 快速原型/低风险任务 | Print模式自动批准所有工具调用，OPC-OS外层需拦截不可逆操作 |
| DeepSeek Harness (dsh) | 实验性/成本敏感任务 | developer preview，有破坏性变更，**不可承担有交付时限的任务** |
| CodeGeeX CLI | 补充性轻量任务 | 审批控制信息有限 |
| Gemini CLI | 可选执行器 | Policy Engine (TOML) |
| OpenCode | 常驻开发环境 | run模式自动批准；server模式可接MCP审批桥 |

### 10.4 程序员Agent任务路由

| 任务类型 | 默认Harness | 沙箱/审批策略 | 产出证据 |
|---|---|---|---|
| 新功能实现 | Claude Code / Codex | workspace-write + 审批never，但diff必须经测试门控 | 代码diff、自测记录、未解决阻塞清单 |
| 缺陷修复(P1/P2) | Codex CLI | 先read-only分析根因，再workspace-write修复 | 根因分析、diff、回归测试结果 |
| 重构/技术债 | Claude Code | workspace-write，独立分支，不直接改主干 | 重构前后对比、行为等价性证据 |
| 实验性/低风险 | Kimi Code | 自动批准，但外层拦截不可逆操作 | 最终输出+session记录 |

### 10.5 程序员Agent调用流程（缺陷修复示例）

1. **预检**：工作区干净？目标文件存在？无未合并冲突？失败则打回技术总监。
2. **分析（只读）** ：`codex exec -C /repo --sandbox read-only --ask-for-approval never "分析{bug}根因，输出根因假设和修复建议，不修改文件"`
3. **根因验证**：根因报告提交测试Agent独立构造复现用例。无法复现→打回。
4. **修复（受限写入）** ：`codex exec -C /repo --sandbox workspace-write --ask-for-approval never "根据根因报告修复{bug}，运行相关测试，记录未解决阻塞"`
5. **证据包组装**：diff（git diff获取）+ 自测结果 + 根因报告 + 未解决阻塞清单 → 提交测试门控。
6. **关键约束**：程序员Agent不能自己标记“完成”，必须经测试Agent独立审阅。

### 10.6 测试Agent三项核心职责

1. **复现验证（修复前）** ：独立构造复现用例，无法复现→打回根因报告。
2. **修复后独立验证**：不信任程序员的“自测通过”声明，独立运行测试套件。硬约束：覆盖率<90%不得标记通过；P0缺陷必须升级技术总监。
3. **对抗性测试（高风险任务）** ：调用**第二个独立harness**（与开发用的不同模型家族）进行对抗性审查，输出作为测试报告附录。

### 10.7 安全与审批叠加

**四层防护**：
1. **Harness原生沙箱**：Gateway为每个角色预设不可覆盖的harness参数。程序员Agent默认禁止`--yolo`/`bypass_permissions`，除非任务标记“实验性”且工作区是disposable。
2. **OPC-OS审阅门控（不可绕过）** ：程序员产出必须经测试Agent独立门控才能向上移动。
3. **HITL例外路由**：P0缺陷N轮未修复、开发与测试持续冲突、不可逆操作（生产部署/数据库迁移/对外API发布）→升级CEO。
4. **审计留痕**：每次harness调用记录harness名称/版本、脱敏参数、session_id、退出码、消耗、diff哈希、测试验证结果。

## 11. 产品经理与技术总监Agent

### 11.1 产品经理Agent

**工作内容**：
1. **知识边界判断**：显式输出“当前任务所需信息在我的参数化知识中是否足够稳定和充分”。判断为“不足”触发调研子图，判断为“充分”跳过并记录理由。
2. **调研子图**（条件性）：Planner拆解调研子任务→Search并行检索→Review聚类→Writer汇总结构化摘要。产品经理是研究协调者，不是搜索引擎调用者。
3. **PRD证据包组装**：需求条目清单（每条含优先级/验收标准/来源标记）+ 竞品/市场依据（条件性，来源可追溯）+ 自检标记（标注“自检，非独立验证”）。
4. **立场声明**：“确保方案满足业务需求，不接受‘技术上难做’的借口”——在审阅门控中作为约束注入。

**行为边界**：不做技术方案设计、不评估实现成本、不替技术总监做取舍。职责边界是定义“做什么”和“什么叫做完了”。

### 11.2 技术总监Agent

**工作内容**：
1. **PRD工程可行性审阅（门控1）** ：逐条判定（可行/有条件可行/不可行或高风险），每条附具体代价或技术依据。
2. **技术拆解**：工程任务列表（输入/输出/验收方式/风险等级）+ 架构决策记录（ADR，含备选方案和选择理由）+ 风险预判清单。
3. **条件性联网搜索**：搜索“技术方案在当前时点的真实状态”（框架版本兼容性、API废弃计划、安全公告、性能基准）。搜索精确、以验证为导向。结果作为ADR支撑证据。
4. **立场声明**：“确保方案可落地：评估并发、数据一致性、回滚能力，对‘拍脑袋方案’零容忍。”

**行为边界**：不以“实现复杂”为由直接打回需求，必须给出具体工程代价。技术选型涉及产品边界时需回到产品经理或升级CEO。

### 11.3 联网搜索三层策略

| 层级 | 触发条件 | 行为 |
|---|---|---|
| **强制搜索** | 任务涉及“快速变化”领域（竞品动态/框架版本/定价基准/安全公告） | 证据包无来源引用→门控直接打回 |
| **条件搜索** | Agent显式判断“参数化知识不足” | 输出搜索必要性判断+理由，可审计 |
| **预算降级** | 搜索成本达任务预算比例阈值 | 后续搜索需技术总监或CEO审批 |

搜索作为MCP工具挂载到需要它的Agent上，由岗位书决定是否授予权限。

## 12. Skills集成层

### 12.1 定位

Skills是**认知输入层**，不是组织角色层。

**角色Agent = 岗位书（你写的：职责边界/验收标准/权限） + 认知skill（可替换：心智模型/决策启发式） + 证据责任（不可绕过：可验证引用）**

### 12.2 集成方式

- 女娲.skill等工具提炼的SKILL.md（3-7个心智模型、5-10条决策启发式、表达DNA、反模式、诚实边界）作为角色Agent的**认知框架输入**挂载。
- 可替换：今天给产品经理挂雷军skill，明天换李想skill，岗位书约束不随skill变化。
- 群聊模式（如女娲智库的GroupChat）可作为辩论会子图的实现参考。

### 12.3 三条红线

1. **skills角色只产出“建议”和“判断”，不产出“最终拍板”** 。最终责任归属是CEO。
2. **审计层必须记录每个角色skill的版本、来源和置信边界**，回放视图标注“该判断由蒸馏skill X生成，不属于经过验证的组织知识”。
3. **辩论会子图必须包含去偏机制**（独立裁决者、发言权轮转、坚持度约束），不假设“名人脑子放进群聊就会高质量争论”。

## 13. 运营岗位子组织

### 13.1 定位

运营不是一个“全能账号操作员”，是一个**被审阅门控串联的微缩内容组织**。AI做流程执行者，不做账号接管者。

### 13.2 角色分工

| 角色 | 职责 | 关键约束 |
|---|---|---|
| **内容策略Agent**（运营总监层） | 制定内容策略简报（目标受众/选题方向/平台定位差异/发布节奏） | 不写稿不发帖；简报需经CEO或产品总监审阅 |
| **内容创作与平台适配Agent**（执行层） | 产出原始素材+平台差异化适配（公众号深度/抖音钩子/小红书清单体） | 调用发布工具（HuiMei/Prism）作为执行器，适配决策由运营子组织做 |
| **合规与质量审阅Agent**（门控层） | 独立检查同质化群发特征/未授权引流/素材版权/平台规则 | “通过”必须附具体检查项清单；无法判定→升级CEO |
| **数据复盘Agent**（观测层） | 采集播放/互动/转化数据，产出复盘报告 | 不直接触发策略调整，作为下一轮策略简报的输入证据 |

### 13.3 流水线

```
策略简报 → 内容素材 → 平台适配版本 → 合规审阅 →（CEO审批门控）→ 发布执行 → 数据复盘
```

每一步产出带证据的结构化交接物，合规审阅和CEO审批门控不可跳过。发布工具只是链末端的执行器，不改变“谁为内容负责”。

### 13.4 平台策略

- **B站**：唯一“脚本友好”的平台，作为可靠自动化试验田（biliup-rs等成熟开源工具）。
- **抖音**：官方商业发布API门槛极高（仅党政机关/事业单位），市面工具走浏览器自动化/逆向，风控随时收紧。**不作为全自动接管目标**。
- **小红书**：开放API不完整，依赖浏览器自动化（Playwright），技术脆弱且接近风控灰色地带。**发布决策必须经CEO门控**。
- **合规**：2026年9月新规要求MCN办理经营主体登记、明确内容管理负责人；抖音持续打击矩阵号不当获利。AI做流程执行，账号策略/内容方向/发布节奏/合规判断必须经审阅门控。

## 14. 前端设计（桌面端）

### 14.1 页面总览

五页：今日视图（默认首页）、任务看板、审批收件箱、组织配置、回放。

### 14.2 页面1：今日视图

**布局**：两栏。左栏2/3，右栏1/3。

**左栏（从上到下）** ：
- **“需要你决策”区域**：琥珀色左边框的卡片列表，按紧急度排序。
- **“自动决策摘要”** ：低对比度折叠区，一行摘要“过去24小时策略引擎自动通过17项可逆决策，拦截3项进入人工”。

**右栏**：
- **组织状态卡片**：四个大数字（活跃任务数/今日预算消耗比例/被阻塞任务数/过去24小时完成数）。
- **想法输入框**：常驻在右栏底部。

**设计意图**：打开第一眼看到“公司今天需要你做什么+它自己已经做了什么”，不是agent聊天流。

### 14.3 页面2：任务看板

- 顶部筛选栏：“全部”/“需要我注意”。
- 主体：**六列水平滚动看板**（助理→产品→技术→架构→执行→运营）。
- 卡片正面：一行摘要+层级标签+最后变更时间。
- 点击卡片：右侧滑出**任务详情抽屉**（不离开看板上下文），三层折叠（摘要→证据包指标→完整产出），底部展示审阅链（每个门控节点的审阅者/决定/理由/时间戳）。

### 14.4 页面3：审批收件箱

- 顶部策略摘要条：“过去24小时策略引擎自动通过X项，拦截Y项进入人工。当前待处理Z项。”
- 单列宽卡片流，默认折叠，展开显示参数快照和推荐理由。
- 支持批量操作（仅同类型同方向），批量操作写入一条审计事件。

### 14.5 页面4：组织配置

- 左侧角色列表（助理/产品总监/技术总监/架构师/开发/测试/运营）。
- 右侧选中角色的**岗位书编辑器**（结构化验收标准清单，非自由文本）。
- 底部委派规则图可视化缩略图（节点=角色，边=交接方向，边上锁图标=审阅门控），点击进入全屏图编辑。

### 14.6 页面5：回放

- 全屏时间线。上方任务摘要和最终状态，下方垂直事件流。
- 每个事件节点可展开状态快照。
- 支持按事件类型过滤（审阅决定/工具调用/预算/审批/会议）。

## 15. 前端设计（移动端）

移动端**不做响应式缩放**，做独立轻量界面。不加载看板和组织配置的复杂组件。

### 15.1 页面1：审批卡片流（默认页）

- 全屏卡片，每次一张，上下滑动切换。

### 15.3 页面3：状态只读

### 15.4 推送通知

仅对“需要CEO决策”的事项推送，不推送常规状态更新。

## 17. 安全与权限

### 17.1 Harness层

- Gateway为每个角色预设不可覆盖的harness参数。
- 程序员Agent默认禁止`--yolo`/`bypass_permissions`，除非任务标记“实验性”且工作区disposable。
- 不可逆操作（生产部署/数据库迁移/对外API发布）必须经CEO审批门控。

### 17.2 Agent层

- 每个Agent的MCP工具权限由岗位书限定。
- Agent间A2A通信受委派规则图约束，不能绕过门控直接向上交接。
- Harness调用的session_id、脱敏参数、diff哈希全部记录。

### 17.3 IM层

- 审批操作必须经签名验证+一次性token。
- 不可逆操作禁止在IM中完成，强制在桌面端/移动端（有二次确认）完成。
- 飞书卡片回调携带签名，Hub验证签名后才处理审批决策。

### 17.4 数据层

- `events`表append-only，触发器禁止UPDATE/DELETE。
- 审计日志与Checkpoint在同一事务提交，防止崩溃时事件丢失。
- 敏感凭证（API key、IM签名密钥）存储在独立的secrets表，加密 at rest，仅Hub层可读。

## 18. 成本与预算治理

### 18.1 预算层级

公司级 → 角色级 → 任务级。任一层级达到阈值自动暂停相关agent执行。

### 18.2 成本记录

每个agent的模型调用、工具调用、外部API消耗记录在`budgets`表和`events`表（`action='budget_consume'`）。可按角色/任务/时间段聚合。

### 18.3 界面表现

今日视图右栏组织状态卡片中以**日消耗vs预算**的简洁条形持续可见。预算暂停时审批收件箱出现非琥珀色卡片。

### 18.4 搜索预算降级

搜索成本达任务预算比例阈值时，后续搜索请求需技术总监或CEO审批。

## 19. 审计与回放

### 19.1 不可变事件日志

所有状态变更、审阅决定、审批操作、工具调用、预算消耗写入`events`表（append-only）。每条事件含`actor`/`action`/`target`/`timestamp`/`state_snapshot`。

### 19.2 任务回放

选择任意任务，以时间线形式回放：想法提出→章程提案→产品拆解→每次审阅决定和理由→每次预算消耗→最终交付物。

回放目的：**让CEO以极低时间成本理解“组织是怎么运转的”** ，从而调整岗位书、委派规则或审阅门控。

### 19.3 回放视图的特殊标注

- 由蒸馏skill生成的判断标注“该判断由蒸馏skill X生成，不属于经过验证的组织知识”。
- 策略引擎自动通过的决策标注“基于模式的自动批准”。
- Harness调用记录标注harness名称/版本/参数脱敏摘要。

## 20. 开发计划与里程碑

### 20.1 阶段划分（桌面端优先，移动端延后）

| 阶段 | 周期 | 核心交付物 | 验收标准（CEO亲自判断） |
|---|---|---|---|
| **Phase 0：编排内核与数据模型** | 3周 | LangGraph图骨架、PostgreSQL Checkpoint、事件日志表、岗位书YAML schema | 通过测试想法跑通完整流程，中途打断并从Checkpoint恢复，审计日志完整 |
| **Phase 1：审阅门控与证据包** | 3周 | 证据包schema、门控验证逻辑、升级路由、策略引擎骨架 | 开发标记“完成”但不附测试报告→门控拒绝；测试标记“通过”但覆盖率不足→拒绝；预算突破→暂停+升级 |
| **Phase 2：桌面端前端（今日视图+看板+审批收件箱）** | 4周 | Tauri 2.0壳+React AG-UI客户端、今日视图、任务看板、审批收件箱、组织配置只读 | 桌面端完成“输入想法→看流转→审批→看板更新”完整闭环，不接触命令行 |
| **Phase 3：组织配置+回放+策略引擎自动审批** | 3周 | 岗位书编辑器、委派规则图编辑、回放时间线、策略引擎完整逻辑、预算层级配置 | 修改岗位书后门控行为按新标准变化；自动通过的决策在日报可见且可追溯 |
| **Phase 4：移动端+IM接入（飞书）** | 3周 | Tauri iOS/Android打包、移动端审批卡片流、语音/文字想法输入、只读状态、飞书卡片推送+回调 | 手机收到审批推送→查看摘要→批准/打回→桌面端同步更新 |
| **Phase 5：Harness Gateway一期（Claude Code/Codex/Qoder）** | 3周 | 三个适配器、程序员Agent任务路由、测试Agent独立验证、四层安全防护 | 缺陷修复任务跑通“只读分析→复现验证→修复→测试独立验证→上报”全链路 |
| **Phase 6：硬化与试运行** | 2周 | 错误处理、重试机制、审计完整性校验、性能调优、文档 | 连续运行一周无任务静默停滞；所有预算突破被处理；5分钟内回放理解任意已完成任务 |

**总周期：约21周（5.25个月）** 。若桌面端优先、移动端和Harness延后，可压缩至**15–16周**。

### 20.2 关键依赖

**最大风险不在技术，在岗位书的“验收标准”设计。** Phase 0和Phase 1需要CEO投入最多**设计精力**。你需要亲自为每个角色定义“什么叫做完了”和“什么叫做合格”——这是系统能否真正替你过滤审阅负担的前提。

## 21. 七个结构性风险与缓解策略

### 风险1：Agent审阅的“共谋”或“放水”

**问题**：如果测试Agent和开发Agent使用同一LLM家族，它们可能系统性地放过彼此的问题（人格蒸馏研究显示Agent存在内群体偏好）。

**缓解**：
- 测试Agent的独立验证默认使用**与开发不同的harness/模型家族**（如开发用Claude Code，测试用Codex CLI）。
- 高风险任务启用对抗性测试（第二个独立harness做只读审查）。
- 审计层记录每次审阅的模型来源，回放视图可分析“同一模型家族审阅通过率是否异常偏高”。

### 风险2：记忆与知识管理

**问题**：跨任务的上下文继承、组织知识的沉淀，当前产品（包括Paperclip）没有很好解决。

**缓解**：
- Phase 0只做**任务级记忆**（LangGraph Checkpoint内的上下文）。
- Phase 3引入**角色级记忆**（每个角色的历史审阅决定和理由，作为后续任务的few-shot参考）。
- 组织级知识库（跨角色的经验沉淀）作为**Phase 6之后的演进方向**，不在v1.0承诺。

### 风险3：多任务并行的资源调度

**问题**：当5个任务同时需要技术总监审阅时，审阅队列如何排序？预算如何分配？

**缓解**：
- 审阅队列按**任务优先级+等待时间**排序（优先级由章程中的业务目标决定）。
- 角色级预算在多任务间按**任务预算比例**动态分配。
- 当某角色队列积压超过阈值时，心跳机制触发“审阅瓶颈”告警进入CEO收件箱（信息性卡片），CEO可决定是否临时追加预算或调整优先级。

### 风险4：冷启动与渐进式复杂度

**问题**：用户第一天怎么用？不可能第一天就把所有岗位书写好。

**缓解**：
- 提供**预设岗位书模板**（助理/产品总监/技术总监/开发/测试/运营各一份默认YAML），用户可先跑通再逐步调整。
- Phase 0的验收只要求线性+单分支跑通，并行和动态边在Phase 3之后按实际绕行需求逐步加入。
- 不要求第一天配置所有harness，先接Claude Code一家跑通，再逐步接入Codex/Qoder。

### 风险5：OPC-OS自身的测试与回归

**问题**：Agent行为是非确定性的，如何测试“审阅门控确实拦住了不合格产出”？

**缓解**：
- 门控验证逻辑是**确定性代码**（检查覆盖率数值、检查证据包字段完整性、检查“作者不给自己打分”的图结构约束），不是依赖LLM判断。这部分可以用传统单元测试覆盖。
- Agent行为本身用**场景回放测试**：录制一组固定输入（测试想法+预设的Agent产出），断言门控在特定条件下触发拒绝/升级。
- Phase 1的验收标准就是一组这样的确定性测试用例。

### 风险6：数据一致性与审计完整性

**问题**：append-only日志在崩溃时如何保证不丢事件？

**缓解**：
- 事件写入与LangGraph Checkpoint在**同一PostgreSQL事务**中提交。
- 审计日志的完整性校验作为Phase 6的交付项：定期扫描`events`表，验证每个状态变更都有对应事件、每个门控决定都有对应证据包引用。

### 风险7：法律责任的清晰化

**问题**：AI生成内容的版权归属、Agent行为的责任归属。

**缓解**：
- 产品层面：用户协议明确“所有AI产出物在CEO审批通过前不构成对外承诺；CEO审批通过后的行为责任归属用户”。
- 审计层面：每条对外动作记录“触发角色+审批人+审批时间”，形成完整的责任链。
- 运营层面：内容发布前强制经过合规审阅+CEO审批门控（见§13），不追求全自动接管。
- 这是**产品设计层面无法完全解决**的问题，需要在用户协议和实际运营中持续界定。v1.0的立场是：**AI做流程执行者，CEO做责任主体**。

# 数据层修订：SQLite 直绑方案（替代 PostgreSQL + Redis）

**修订范围**：§3.2（选型）、§3.3（架构图）、§4（数据模型）、§18.2（成本记录）、§21（新增风险）。其余章节不变。

**结论先行**：对于“一人公司桌面软件”这个定位，SQLite 不仅够用，而且比 PostgreSQL + Redis 更合适。OPC-OS 是**单用户、低并发写、数据量中等**的系统——一个 CEO、几个 agent、心跳 15 分钟一次、每次节点状态变更才写一次。这不是高频交易系统。SQLite 的 WAL 模式完全能承载这个负载，且省掉了两个需要运维的组件。

但有两个真实约束必须明确：**跨进程写入**和**多端数据访问**。下面的方案对这两点给出具体处理，不做含糊承诺。

## 1. 架构变更：三处替换

### 1.1 替换清单

| 原组件 | 替代方案 | 说明 |
|---|---|---|
| PostgreSQL（Checkpoint + 业务表 + 审计） | **单个 SQLite 文件**（WAL 模式） | 由 Python Agent Core 独占管理 |
| Redis（实时事件分发） | **Rust 侧 `tokio::sync::broadcast`**（进程内广播） | Tauri 桌面端本身是单进程，事件分发不需要跨进程中间件 |
| S3/MinIO（文件制品） | **本地文件系统**（`~/.opc-os/artifacts/`） | 制品按 `task_id/bundle_type/hash` 目录组织，SQLite 只存路径和哈希 |

### 1.2 修订后的架构图

```

│  前端层 (React + TS + AG-UI Client)                   │
│  Tauri 2.0 桌面端                                     │

                       │ Tauri IPC (invoke / event)
┌──────────────────────▼──────────────────────────────┐
│  OPC-OS Hub (Rust, Tauri Core)                       │
│  - 事件路由 / IPC / 文件系统桥接                       │
│  - tokio::sync::broadcast (替代Redis的实时分发)       │
│  - Channel抽象层 (IM适配器)                           │
│  - 签名验证 / 一次性token                             │
│  - 不直接写SQLite（只读缓存或经RPC写）                 │

└─────────────────────────────────────────────────────┘
```

### 1.3 关键决策：Python Agent Core 是 SQLite 的唯一写者

**问题**：Rust Hub 和 Python Agent Core 是两个进程，如果都直接写同一个 SQLite 文件，WAL 模式下写仍然是串行的，跨进程并发写会触发 `SQLITE_BUSY`。

**方案**：**Python Agent Core 独占写权限**。Rust Hub 不直接打开 SQLite 写连接，所有需要写数据的操作通过 JSON-RPC 请求 Python 侧执行。Rust Hub 可以持有一个**只读连接**用于快速查询（如前端拉取任务列表），但写入路径唯一。

**依据**：OPC-OS 的写入频率极低——LangGraph 每个节点状态变更写一次 Checkpoint，事件日志同事务写一条，心跳 15 分钟一次。这个写入频率下，单写者队列的延迟可以忽略（毫秒级）。跨进程写冲突的风险远大于单写者队列的复杂度。

**实现细节**：
- Python 侧用 `sqlite3` 标准库（或 `aiosqlite` 避免阻塞事件循环），开 `PRAGMA journal_mode=WAL`、`PRAGMA busy_timeout=5000`、`PRAGMA synchronous=NORMAL`。
- LangGraph 的 `SqliteSaver` 是同步的，用 `aiosqlite` 包装或在线程池中执行，避免阻塞 asyncio 事件循环。
- 写操作串行化：Python 侧维护一个单线程的写队列（`asyncio.Queue` + 单个 writer task），所有写请求入队，writer 依次执行。这消除了应用层的并发写。

### 1.4 Redis 的替代：`tokio::sync::broadcast`

**原用途**：实时事件分发（任务状态变更推送到前端、审批卡片推送到 IM 适配器）。

**替代方案**：Tauri 桌面端是单进程应用，Rust Hub 内部用 `tokio::sync::broadcast::channel` 做进程内广播。Python Agent Core 产生的事件通过 JSON-RPC 推送给 Rust Hub，Hub 广播给：
- 前端（通过 Tauri 的 `emit` 事件机制）
- IM 适配器（飞书卡片推送等）

**不需要 Redis 的理由**：事件分发的所有消费者都在同一个桌面进程内（前端 webview + Rust 侧的 IM 适配器）。没有跨机器、跨进程的订阅需求。Redis 的 pub/sub 在这个场景是过度设计。

**事件类型**：`TaskStateChanged`、`ApprovalRequired`、`ReviewDecided`、`BudgetPaused`、`MeetingSummaryReady`。每种事件对应前端的一个 AG-UI 事件类型。

## 2. 数据模型修订（具体 SQL）

### 2.1 类型映射原则

| PostgreSQL | SQLite | 说明 |
|---|---|---|
| `UUID` | `TEXT` | 存 UUID 字符串，应用层生成 |
| `TIMESTAMPTZ` | `INTEGER` | 存 Unix 毫秒时间戳，避免时区和字符串比较问题 |
| `NUMERIC(10,2)` | `INTEGER` | 存**美分**，避免浮点误差 |
| `JSONB` | `TEXT` + `json1` 扩展 | SQLite 内置 `json_extract()`、`json_valid()` 等函数 |
| `BIGSERIAL` | `INTEGER PRIMARY KEY AUTOINCREMENT` | 事件日志的主键 |
| `BOOLEAN` | `INTEGER` (0/1) | SQLite 无原生布尔 |

### 2.2 建表语句（修订版）

```sql
-- 全局PRAGMA（每次连接时执行）
PRAGMA journal_mode = WAL;
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;
PRAGMA foreign_keys = ON;

-- 任务表
CREATE TABLE tasks (
  id TEXT PRIMARY KEY,                          -- UUID字符串
  parent_id TEXT REFERENCES tasks(id),
  charter_id TEXT REFERENCES charters(id),
  title TEXT NOT NULL,
  status TEXT NOT NULL,
  assigned_role TEXT NOT NULL,
  current_node TEXT NOT NULL,
  budget_cents INTEGER,                         -- 美分
  consumed_cents INTEGER DEFAULT 0,
  created_at INTEGER NOT NULL,                  -- Unix毫秒
  updated_at INTEGER NOT NULL,
  state_snapshot TEXT,                          -- JSON字符串
  graph_checkpoint_id TEXT
);
CREATE INDEX idx_tasks_status ON tasks(status);
CREATE INDEX idx_tasks_parent ON tasks(parent_id);

-- 事件日志（append-only）
CREATE TABLE events (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id TEXT REFERENCES tasks(id),
  actor_type TEXT NOT NULL,                     -- 'agent' | 'human' | 'system'
  actor_id TEXT NOT NULL,
  action TEXT NOT NULL,
  target TEXT,
  payload TEXT NOT NULL,                        -- JSON字符串
  state_snapshot TEXT,                          -- JSON字符串
  created_at INTEGER NOT NULL
);
CREATE INDEX idx_events_task ON events(task_id, created_at);
CREATE INDEX idx_events_action ON events(action, created_at);

-- 强制append-only：禁止UPDATE和DELETE
CREATE TRIGGER events_no_update
BEFORE UPDATE ON events
BEGIN
  SELECT RAISE(ABORT, 'events table is append-only');
END;

CREATE TRIGGER events_no_delete
BEFORE DELETE ON events
BEGIN
  SELECT RAISE(ABORT, 'events table is append-only');
END;

-- 审阅门控
CREATE TABLE review_gates (
  id TEXT PRIMARY KEY,
  task_id TEXT REFERENCES tasks(id),
  gate_type TEXT NOT NULL,
  reviewer_role TEXT NOT NULL,
  evidence_bundle_id TEXT REFERENCES evidence_bundles(id),
  decision TEXT,
  decision_reason TEXT,
  conditions TEXT,                              -- JSON数组
  decided_at INTEGER
);
CREATE INDEX idx_gates_task ON review_gates(task_id);

-- 证据包
CREATE TABLE evidence_bundles (
  id TEXT PRIMARY KEY,
  task_id TEXT REFERENCES tasks(id),
  producer_role TEXT NOT NULL,
  bundle_type TEXT NOT NULL,
  artifacts TEXT NOT NULL,                      -- JSON: 文件路径/哈希/外部链接
  self_check TEXT,                              -- JSON
  created_at INTEGER NOT NULL
);

-- CEO审批收件箱
CREATE TABLE approvals (
  id TEXT PRIMARY KEY,
  task_id TEXT REFERENCES tasks(id),
  approval_type TEXT NOT NULL,
  summary TEXT NOT NULL,
  parameters TEXT NOT NULL,                     -- JSON
  recommendation TEXT,
  recommendation_source TEXT,
  timeout_behavior TEXT,
  timeout_at INTEGER,
  status TEXT DEFAULT 'pending',
  decided_by TEXT,
  decided_at INTEGER,
  decision_note TEXT
);
CREATE INDEX idx_approvals_status ON approvals(status, timeout_at);

-- 岗位书（版本化）
CREATE TABLE role_charters (
  id TEXT PRIMARY KEY,
  role_id TEXT NOT NULL,
  version INTEGER NOT NULL,
  config TEXT NOT NULL,                         -- JSON
  effective_from INTEGER NOT NULL,
  created_by TEXT NOT NULL,
  UNIQUE(role_id, version)
);

-- 预算
CREATE TABLE budgets (
  id TEXT PRIMARY KEY,
  scope_type TEXT NOT NULL,                     -- 'company' | 'role' | 'task'
  scope_id TEXT NOT NULL,
  period TEXT NOT NULL,
  limit_cents INTEGER NOT NULL,
  consumed_cents INTEGER DEFAULT 0,
  hard_stop INTEGER DEFAULT 1                   -- 0/1
);
CREATE UNIQUE INDEX idx_budgets_scope ON budgets(scope_type, scope_id, period);

-- 全文搜索（替代PG的全文索引）
CREATE VIRTUAL TABLE events_fts USING fts5(
  payload,
  content='events',
  content_rowid='id'
);
-- 通过触发器同步events到events_fts
CREATE TRIGGER events_fts_insert AFTER INSERT ON events
BEGIN
  INSERT INTO events_fts(rowid, payload) VALUES (new.id, new.payload);
END;
```

### 2.3 文件制品的组织

```
~/.opc-os/artifacts/
  └── {task_id}/
        ├── prd/
        │     ├── {bundle_id}.json          (结构化需求清单)
        │     └── {bundle_id}.md            (可读PRD)
        ├── code_diff/
        │     └── {bundle_id}.patch
        ├── test_report/
        │     └── {bundle_id}.json
        └── content_package/
              └── {bundle_id}/
```

SQLite 的 `evidence_bundles.artifacts` 字段存 JSON，每个制品包含：`{"type": "code_diff", "path": "artifacts/{task_id}/code_diff/{bundle_id}.patch", "sha256": "..."}`。回放时按路径读取文件，按 sha256 校验完整性。

## 3. 并发、性能与备份

### 3.1 并发处理

| 场景 | 处理 |
|---|---|
| 多个 agent 并行产生事件 | Python 侧单写队列串行化，应用层无并发写 |
| Rust Hub 只读查询 | 独立的只读连接，WAL 模式下读不阻塞写 |
| 前端通过 Hub 拉数据 | Hub 只读连接查询，或经 RPC 到 Python 侧查询 |
| 心跳检查与正常写入并发 | 同一写队列，按提交顺序执行 |

### 3.2 性能预期

- 单条事件写入：< 1ms（WAL 模式，`synchronous=NORMAL`）。
- 任务列表查询（带索引）：< 5ms（万级任务量）。
- 全文搜索（FTS5）：< 20ms（十万级事件）。
- 数据库文件大小估算：每个任务约 50–200 条事件，每条事件平均 2KB（含 state_snapshot），一万个任务约 2–4GB。SQLite 单库支持 TB 级，这个量级无压力。

### 3.3 备份策略

- **每日自动备份**：使用 SQLite 的 `VACUUM INTO` 命令生成一致性快照到 `~/.opc-os/backups/opc-{date}.db`，保留最近 7 份。
- **关键操作前备份**：岗位书变更、委派规则图变更前，自动触发一次备份。
- **备份不替代审计**：备份是灾难恢复手段，审计回放依赖 `events` 表的完整性，两者独立。

### 3.4 迁移路径（如果未来需要换 PostgreSQL）

Schema 设计时已避免 PG 特有类型：UUID 存 TEXT、时间存 INTEGER、金额存 INTEGER、JSON 存 TEXT。迁移时只需：
1. 写一个导出脚本（`SELECT * FROM each_table` → CSV/JSON）。
2. 在 PG 中建表（TEXT/INTEGER 直接映射，JSON 映射到 JSONB）。
3. 导入。
4. LangGraph 的 Checkpoint 从 `SqliteSaver` 切换到 `PostgresSaver`。

**不需要**在 v1.0 做任何 PG 兼容层。SQLite 的 schema 是干净的，迁移是未来的独立工作项。

## 4. 多端访问的取舍（必须明确）

这是 SQLite 直绑方案**唯一的真实代价**，必须说清楚。

### 4.1 桌面端是数据主库

SQLite 文件在桌面端本地（`~/.opc-os/opc.db`）。桌面端是**唯一的数据权威**。

### 4.2 移动端的三种选项

| 选项 | 实现 | 代价 | 建议 |
|---|---|---|---|
| **A. 移动端纯 RPC** | 移动端不存数据，通过桌面端 Hub 的 HTTP/WS API 访问（桌面端需在线） | 桌面端离线时移动端不可用 | **v1.0 推荐** |
| **B. 移动端只读缓存** | 移动端本地存一个只读 SQLite 副本，定期从 Hub 拉增量 | 需要实现增量同步协议，复杂度高 | v1.1 之后考虑 |
| **C. 移动端延后** | Phase 4 不做移动端，先做桌面端 + 飞书审批 | 失去移动审批能力 | 如果飞书审批够用，可接受 |

**v1.0 的立场**：**桌面端单机 SQLite 是主库，移动端采用选项 A（纯 RPC）** 。桌面端 Hub 启动一个轻量的本地 HTTP/WS 服务（仅监听局域网或通过 Tailscale 等组网访问），移动端通过它访问审批队列和任务状态。**不做多端数据同步**——同步是另一个产品，不是 v1.0 的范围。

### 4.3 飞书审批路径不受影响

飞书审批卡片走的是飞书服务器 ↔ 桌面端 Hub 的长连接，不依赖移动端本地数据。即使移动端不做，飞书审批仍然可用。这是 IM 接入层（§9）的设计价值：它绕过了“多端数据同步”这个难题。

## 5. 对开发计划的影响

| 阶段 | 原计划 | 修订后 |
|---|---|---|
| Phase 0 | PostgreSQL Checkpoint + 事件日志表 | **SQLite（WAL）+ SqliteSaver + 事件日志表 + append-only触发器**。周期不变（3周），但省掉了 PG 的安装和连接配置 |
| Phase 1 | 门控验证逻辑 | 不变。门控的确定性测试用例直接跑在 SQLite 上，更快 |
| Phase 2 | 桌面端前端 | 不变。Rust Hub 的只读查询走 SQLite 只读连接 |
| Phase 3 | 回放 + 策略引擎 | 回放的全文搜索用 FTS5 替代 PG 全文索引。周期不变 |
| Phase 4 | 移动端 + 飞书 | **移动端改为纯 RPC（选项 A）**，不做本地 SQLite。飞书路径不变 |
| Phase 5 | Harness Gateway | 不变 |
| Phase 6 | 硬化 | 新增：SQLite 备份脚本、完整性校验（`PRAGMA integrity_check`）、FTS5 索引重建 |

**总周期不变（约21周）** ，但 Phase 0 的运维复杂度显著降低——不需要安装和配置 PostgreSQL 和 Redis，开发者拿到代码后 `cargo tauri dev` + `python -m opc_core` 即可跑起来。

## 6. 新增风险（追加到 §21）

### 风险8：SQLite 文件损坏

**问题**：SQLite 在极端情况下（断电、磁盘满、文件系统错误）可能损坏。单文件意味着单点故障。

**缓解**：
- WAL 模式 + `synchronous=NORMAL` 在崩溃时保证数据库一致性（WAL 的 checkpoint 机制）。
- 每日 `VACUUM INTO` 备份，保留 7 份。
- 启动时执行 `PRAGMA integrity_check`，失败则提示从备份恢复。
- 关键操作（岗位书变更、委派规则变更）前自动备份。

### 风险9：跨进程写冲突

**问题**：如果未来 Rust Hub 需要直接写 SQLite（例如为了降低延迟），跨进程写会触发 `SQLITE_BUSY`。

**缓解**：
- v1.0 严格保持 **Python 单写者** 架构，Rust Hub 只读或经 RPC 写。
- 如果未来确实需要 Rust 侧写，引入 `busy_timeout` + 写重试队列，但不改变“单写者”原则——可以把写权限迁移到 Rust 侧，Python 侧改为经 RPC 写，仍然只有一个写者。

### 风险10：移动端依赖桌面端在线

**问题**：选项 A（纯 RPC）要求桌面端在线，移动端才能审批。如果桌面端关机，移动端和飞书审批都失效。

**缓解**：
- 飞书长连接在桌面端 Hub 运行时保持，桌面端关机则飞书审批暂停——这是**可接受的**，因为 OPC-OS 的 agent 执行也依赖桌面端在线，桌面端关机时整个公司本来就停摆。
- 如果要求 7×24 可用，需要把 Hub 部署到常驻服务器（VPS/树莓派），这是 v1.1 的部署选项，不影响 v1.0 的数据层设计。

---

## 7. 修订后的选型表（替换 §3.2 对应行）

| 层 | 原选型 | 修订后 | 理由 |
|---|---|---|---|
| 持久化 | PostgreSQL + Redis | **SQLite（WAL）+ Rust broadcast** | 单用户低并发，省掉两个运维组件；事件分发在进程内完成 |
| 制品存储 | S3/MinIO | **本地文件系统** | 单机场景，文件系统足够；未来需要多端共享时再引入对象存储 |
| Checkpoint | PostgresSaver | **SqliteSaver**（官方支持） | LangGraph 官方维护，API 一致，迁移成本低 |
| 全文搜索 | PG 全文索引 | **FTS5** | SQLite 内置，满足事件日志的搜索需求 |
| 多端数据 | 共享 PG | **桌面端单库 + 移动端纯 RPC** | 不做多端同步，飞书路径绕过此问题 |

---

**修订结论**：SQLite 直绑方案在 v1.0 是正确选择。它把“安装配置数据库”从开发者的第一小时里彻底移除，同时通过“Python 单写者 + WAL + 写队列”解决了并发问题，通过“移动端纯 RPC + 飞书审批”绕过了多端同步难题。唯一的真实代价是**桌面端离线时移动端不可用**，但这与“agent 执行依赖桌面端在线”的事实一致，不构成额外损失。未来若需要换 PostgreSQL，schema 已按可迁移原则设计，迁移是独立工作项，不在 v1.0 的范围内。

## 第 13 轮 · 用户

我如何保证所有角色的自由度和权力层级

### 第 13 轮 · 助手

# 自由度与权力层级的工程化保证

这个问题触及了OPC-OS设计的核心张力：**自由度太大，Agent会越界、会幻觉、会绕过审阅；层级太死，Agent会变成只会说“是”的执行机器，失去判断力**。你的系统要的不是“完全自由”或“绝对服从”，而是**受约束的自主**——每个角色在明确的决策空间内可以自由判断，但一旦越界或触及不可逆事项，层级门控必须生效。

下面从四个维度拆解：自由度的定义与保证、权力层级的定义与保证、两者的调和机制、以及动态调整。

---

## 一、自由度的四个维度及工程保证

自由度不是“想干什么就干什么”，在OPC-OS里它被拆解为四个可配置、可审计的维度。

### 1.1 决策空间（Decision Scope）

**定义**：这个角色在什么范围内可以自主做决定，不需要向上请示。

**工程保证**：岗位书里的 `decision_scope` 字段，用结构化规则声明。

```yaml
role_id: tech_director
decision_scope:
  autonomous:
    - "技术栈选型（在已批准的技术雷达范围内）"
    - "工程任务拆解粒度"
    - "开发资源在任务间的分配（在角色预算内）"
    - "技术风险等级判定（P0/P1/P2）"
  requires_consultation:
    - "引入新技术雷达外的依赖" → consult: architect
    - "跨季度架构变更" → consult: ceo
  forbidden:
    - "修改产品需求优先级"
    - "直接操作生产环境"
    - "绕过测试门控标记任务完成"
```

**关键设计**：`autonomous` 范围内的决定，Agent**不需要请示**，直接执行并记录审计事件。`requires_consultation` 范围内的决定，Agent必须发起一个咨询事件，等待指定角色的回应后才能继续。`forbidden` 范围内的动作，**Gateway在执行前硬拦截**，不是靠Agent“自觉”。

**自由度保证的核心**：`autonomous` 列表是**正向授权**，不是“除了禁止的都能做”。这意味着Agent的自由度边界是**白名单**，而不是黑名单。白名单之外的一切默认需要请示或禁止——这防止了“Agent钻空子”的问题。

### 1.2 表达空间（Expression Space）

**定义**：这个角色可以在什么场合、以什么方式表达异议、提出替代方案、挑战上级判断。

**工程保证**：三个机制。

**机制一：异议权（Dissent Right）** 。每个角色的岗位书里有 `dissent_rights` 字段：

```yaml
dissent_rights:
  can_challenge:
    - "上游证据包的任何条目（附具体依据）"
    - "审阅者的打回理由（附反驳证据）"
  cannot_challenge:
    - "CEO的最终拍板（但可以记录保留意见）"
  escalation_path: "debate_meeting"  # 异议无法解决时进入辩论会
```

**机制二：辩论会的平等发言权**。辩论会子图（§8.1类型B）中，所有参与者的发言权是**平等的**——不因为层级高低而给予不同权重。发言权通过“竞价发言”机制分配（每个Agent给出0-1的发言意愿分），`recency_penalty`防止同一Agent连续发言。**裁决者是中立的**（不挂载任何人名skill，不隶属于冲突任何一方）。

**机制三：保留意见的记录权**。即使一个角色的意见被否决，它的**异议和依据必须被记录在证据包中**，随任务向上流转。CEO在审批时可以看到“技术总监否决了产品经理的方案，理由是X；产品经理保留了异议，理由是Y”。这保证了**表达空间不因层级而消失**——你可以不同意，但你的不同意会被看见。

### 1.3 执行空间（Execution Space）

**定义**：这个角色可以调用什么工具、访问什么数据、执行什么操作。

**工程保证**：MCP工具权限 + Harness参数预设 + 预算自主权。

```yaml
tool_permissions:
  granted:
    - "read_repo"
    - "run_tests"
    - "create_branch"
    - "web_search"  # 受三层搜索策略约束
  denied:
    - "merge_to_main"
    - "deploy_production"
    - "delete_data"
  harness_defaults:
    claude_code:
      allowed_tools: ["Read", "Edit", "Bash(git:*)"]
      forbidden_flags: ["--yolo"]
    codex:
      sandbox: "workspace-write"
      approval_policy: "never"
      forbidden_flags: ["--full-auto"]
budget_discretion:
  daily_usd: 15
  can_reallocate_within_role: true  # 可以在自己的任务间调配预算
  cannot_exceed: true               # 不能突破角色总预算
```

**关键设计**：`harness_defaults` 中的 `forbidden_flags` 是**不可覆盖的**——即使Agent在运行时尝试传入 `--yolo`，Gateway会拒绝并记录一次“越权尝试”审计事件。`budget_discretion` 给予角色在预算内的自主调配权，但不能突破总预算——这是“受约束的自由”在资源维度的体现。

### 1.4 判断空间（Judgment Space）

**定义**：这个角色在审阅、评估、决策时，可以在多大程度上依赖自己的判断，而不是必须遵循预设规则。

**工程保证**：岗位书里的 `judgment_mode` 字段，分三档。

```yaml
judgment_mode:
  type: "bounded_judgment"  # 可选: strict_rules | bounded_judgment | full_discretion
  strict_rules:             # 必须遵循的硬规则（不可覆盖）
    - "coverage < 0.90 → reject"
    - "p0_defect > 0 → escalate"
  bounded_judgment:         # 在硬规则之外的判断空间
    - "P2缺陷是否可接受上线（需附风险评估）"
    - "技术方案的备选方案选择（需附ADR）"
  full_discretion: []       # 此角色无完全自由裁量领域
```

**关键设计**：`strict_rules` 是**确定性代码**，由Gateway执行，不依赖LLM判断。`bounded_judgment` 是Agent的**自由裁量区**，但裁量必须附带**可验证的依据**（风险评估、ADR、证据引用），否则门控打回。`full_discretion` 通常只给CEO层——但即使CEO的拍板，也要记录决策理由，供回放审计。

**为什么这样设计**：完全的自由裁量（`full_discretion`）在Agent系统中是危险的——它意味着Agent可以不做任何解释就做决定。OPC-OS的原则是：**自由度可以大，但必须可解释**。`bounded_judgment` 是大多数角色的默认模式——你有判断空间，但你的判断必须附带依据。

---

## 二、权力层级的三个维度及工程保证

权力层级不是“谁官大听谁的”，在OPC-OS里它被拆解为三个可执行、可审计的维度。

### 2.1 否决权（Veto Power）

**定义**：谁可以阻止谁的决定生效。

**工程保证**：委派规则图的边上的 `veto_power` 字段。

```yaml
edge:
  from: product_director
  to: tech_director
  review_gate:
    reviewer: tech_director
    veto_power:
      can_reject: true
      rejection_requires: "technical_basis"  # 不能只说"难做"，必须附技术依据
      max_rejections: 3                      # 同一需求最多被打回3次，之后必须升级
      escalation_on_exceed: "ceo"            # 超过3次未收敛则升级CEO
```

**关键设计**：否决权是**有条件的**——技术总监可以否决产品经理的需求，但否决必须附带**技术依据**，不能只说“难做”。`max_rejections` 防止无限打回循环——如果3次打回后仍未收敛，任务自动升级到CEO，不继续在总监层内耗。

**否决权的对称性**：产品经理也有对技术总监**代价评估**的质疑权。如果技术总监说“这个需求需要3个工程日”，产品经理可以质疑“这个估算的依据是什么”，技术总监必须附上估算依据（ADR、历史数据、复杂度分析）。**没有一方的否决权是绝对的**——除了CEO的最终拍板。

### 2.2 升级权（Escalation Power）

**定义**：谁可以把问题往上递，递到哪一层。

**工程保证**：岗位书里的 `escalation_triggers` + 委派图的 `escalation_path`。

```yaml
escalation_triggers:
  - condition: "review_conflict_rounds >= 3"
    target: "ceo"
    action: "create_approval_card"
  - condition: "irreversible_action_detected"
    target: "ceo"
    action: "pause_and_escalate"
  - condition: "budget_threshold_reached"
    target: "ceo"
    action: "pause_and_escalate"
  - condition: "strategic_uncertainty_flagged"
    target: "ceo"
    action: "create_decision_meeting"
```

**关键设计**：升级权是**受限的**——不是“谁都能往CEO递”。只有满足 `escalation_triggers` 中的条件，升级才被允许。这防止了Agent把日常决策推给CEO（“甩锅”）。同时，升级是**有记录的**——每次升级都写入审计事件，CEO可以看到“谁在什么情况下把什么问题递上来了”。

**升级权的层级性**：执行层（开发/测试）的升级目标通常是总监层，不是直接到CEO。只有总监层无法解决的问题才升级到CEO。这保证了**CEO只处理真正需要CEO的问题**。

### 2.3 资源分配权（Resource Allocation Power）

**定义**：谁控制预算、工具权限、Agent的“雇佣”和“解雇”。

**工程保证**：预算层级 + 角色配置的修改权限。

```yaml
resource_authority:
  company_budget: "ceo"           # CEO控制公司总预算
  role_budget: "ceo"              # CEO分配角色预算
  task_budget_within_role: "role_self"  # 角色在自己的预算内自主调配
  hire_fire: "ceo"                # 只有CEO可以增删角色
  tool_permission_grants: "ceo"   # 只有CEO可以修改角色的工具权限
  role_charter_edits: "ceo"       # 只有CEO可以修改岗位书
```

**关键设计**：资源分配权**集中在CEO**，不分散给Agent。Agent可以在自己的预算内自主调配（`task_budget_within_role: role_self`），但不能突破角色总预算，不能给自己加工具权限，不能修改自己的岗位书。这是**权力层级的硬边界**——Agent的自由度是在CEO设定的框架内，框架本身的修改权只属于CEO。

---

## 三、自由与层级的调和：四个机制

自由度和权力层级是天然冲突的。OPC-OS用四个机制调和这对张力。

### 3.1 白名单授权 + 黑名单硬拦截

**自由度**通过**白名单**给予：`decision_scope.autonomous` 列出Agent可以自主决定的事项。白名单之外的一切默认需要请示或禁止。

**层级**通过**黑名单**强制：`forbidden_actions` 和 `harness_defaults.forbidden_flags` 是Gateway硬拦截的，Agent无法绕过。

**调和逻辑**：Agent在**白名单内自由，在黑名单前止步**。白名单和黑名单之间的灰色地带（`requires_consultation`），Agent必须发起咨询，等待指定角色的回应。这保证了自由度不越界、层级不僵化。

### 3.2 判断可自由，但必须可解释

**自由度**体现在 `bounded_judgment`：Agent可以在硬规则之外做判断。

**层级**体现在**解释义务**：任何判断必须附带可验证的依据（风险评估、ADR、证据引用），否则门控打回。

**调和逻辑**：Agent**可以自由判断，但不能自由地不解释**。一个技术总监可以说“这个方案我选择方案B”，但它必须附上“为什么选B不选A”的ADR。一个测试工程师可以说“这个P2缺陷可以接受上线”，但它必须附上风险评估。**解释义务是自由度与层级之间的契约**——你自由判断，但你的判断要经得起审阅。

### 3.3 异议可表达，但拍板权唯一

**自由度**体现在 `dissent_rights`：Agent可以挑战上游证据包、可以反驳审阅者的打回理由、可以保留意见。

**层级**体现在**拍板权的唯一性**：最终决定权属于CEO，不属于任何Agent。Agent可以不同意，但不同意不改变决定——除非它通过升级路径把问题递到CEO面前，由CEO重新拍板。

**调和逻辑**：**表达空间是自由的，决策权是集中的**。Agent的异议会被记录、会被看见、会成为CEO决策的输入，但不会自动推翻已生效的决定。这防止了“Agent之间的无限辩论”和“Agent绕过CEO自行其是”。

### 3.4 同级制衡，上下门控

**自由度**体现在**同级之间的横向制衡**：产品经理和技术总监是平级的，没有谁服从谁。产品经理可以挑战技术总监的代价评估，技术总监可以否决产品经理的需求——但都必须附依据。

**层级**体现在**上下级之间的纵向门控**：执行层的产出必须经过总监层的审阅门控才能向上移动。总监层的决定必须经过CEO的审批门控才能生效（如果触及升级条件）。

**调和逻辑**：**横向是制衡，纵向是门控**。同级之间可以自由争论，但争论的结果必须经过纵向门控的验证才能生效。这防止了“同级之间互相放水”和“上级对下级的一言堂”。

---

## 四、动态调整：信任建立后的放宽与收紧

自由度和层级不是静态的。OPC-OS支持**基于历史表现的动态调整**。

### 4.1 信任积分（Trust Score）

每个角色维护一个信任积分，基于：
- 审阅通过率（该角色的产出被上级审阅通过的比例）
- 升级准确率（该角色升级到CEO的事项中，CEO最终批准的比例）
- 越权尝试次数（该角色尝试执行 `forbidden_actions` 的次数）
- 回滚率（该角色的产出被后续环节打回或回滚的比例）

```yaml
trust_score:
  current: 0.85          # 0-1
  history_window: 50     # 最近50次决策
  components:
    review_pass_rate: 0.90
    escalation_accuracy: 0.80
    unauthorized_attempts: 0
    rollback_rate: 0.05
```

### 4.2 基于信任的动态调整

| 信任积分 | 调整 |
|---|---|
| **> 0.9** | `decision_scope.autonomous` 可扩展（如允许技术总监自主引入技术雷达内的新依赖，不需咨询架构师） |
| **0.7–0.9** | 保持当前配置 |
| **0.5–0.7** | `requires_consultation` 范围扩大（如技术总监的预算调配需咨询CEO） |
| **< 0.5** | `judgment_mode` 降级为 `strict_rules`（该角色暂时失去自由裁量权，必须严格遵循硬规则） |

**关键设计**：信任积分**不能自动修改岗位书**——调整建议由系统生成，但**必须经CEO批准**才生效。这防止了“系统自动放权导致失控”。CEO在组织配置页看到“技术总监信任积分0.92，建议扩展其自主决策范围”，点击批准后才生效。

### 4.3 越权尝试的即时收紧

任何一次 `forbidden_actions` 的尝试（即使被Gateway拦截），立即触发：
- 该角色的信任积分扣减（扣减幅度由CEO配置）。
- 审计事件记录（`action='unauthorized_attempt'`）。
- 如果同一角色在24小时内尝试越权≥3次，自动降级为 `strict_rules` 并通知CEO。

**这保证了自由度的“可撤销性”** ——Agent的自由不是一次性授予的永久权利，而是**可随时收紧的临时授权**。

---

## 五、审计如何保证“自由度不被滥用、层级不被僵化”

审计层（§19）在这里承担双重职责。

### 5.1 防止自由度滥用

- 每次 `bounded_judgment` 的判断记录：判断内容、依据、审阅者的验证结果。
- 每次 `autonomous` 决定的执行记录：决定内容、执行结果、后续是否被回滚。
- 每次 `unauthorized_attempt` 的记录：尝试了什么、被哪条规则拦截。

回放视图可以分析：**某个角色的自由裁量判断，事后被证明正确的比例是多少？** 如果某个角色在 `bounded_judgment` 中的判断频繁被后续环节推翻，说明它的自由度给得太大了，CEO应该收紧它的 `decision_scope`。

### 5.2 防止层级僵化

- 每次 `rejection` 的记录：谁否决了谁、依据是什么、被否决方是否保留了异议。
- 每次 `escalation` 的记录：谁升级了什么、CEO最终是否批准。
- 每次 `dissent` 的记录：谁表达了异议、异议是否被采纳。

回放视图可以分析：**某个审阅者的否决，事后被证明正确的比例是多少？** 如果技术总监频繁否决产品经理的需求，但CEO最终都批准了产品经理的方案，说明技术总监的否决权使用过度，CEO应该收紧它的 `veto_power`（如提高否决门槛，要求更充分的技术依据）。

**审计的核心价值**：它不是合规工具，是**组织调参的数据来源**。你通过回放看到“谁在什么情况下做了什么判断、结果如何”，然后调整岗位书、委派规则、信任积分——**自由度和层级不是一次配置就固定的，而是持续调优的**。

---

## 六、一句话总结

**自由度 = 白名单内的自主决定 + 可解释的判断空间 + 可表达的异议权 + 预算内的资源调配权**。  
**权力层级 = 有条件的否决权 + 受限的升级权 + 集中的资源分配权 + 唯一的最终拍板权**。

两者通过**白名单授权 + 黑名单硬拦截**、**判断自由但必须可解释**、**异议可表达但拍板权唯一**、**同级制衡 + 上下门控**四个机制调和。信任积分和审计回放提供**动态调参**能力——自由度可以随信任建立而放宽，也可以随越权尝试而收紧，但**框架本身的修改权始终在CEO手里**。

这套设计的核心不是“给Agent多少自由”或“设多少层级”，而是**让每一个自由裁量和每一次层级干预都留下可追溯、可调参的记录**。你作为CEO，通过审计回放看到组织的真实运转，然后决定下一轮调整——这才是“受约束的自主”在工程上的完整含义。

### 第 14 轮 · 助手

# 可拖拽组织层级界面：可行，但必须做“受约束的拖拽”

**结论**：技术上完全可行，React 生态有成熟方案。但组织架构不是白板上的便签，**拖拽必须被约束在合法的组织变更语义内**——否则你会拖出一个“测试工程师直接向CEO汇报、绕过技术总监”的非法结构，LangGraph的图会直接崩掉。下面给出技术方案、拖拽语义分类、约束校验机制和与后端的同步策略。

## 一、技术选型：React Flow 是首选

| 方案 | 适用性 | 取舍 |
|---|---|---|
| **React Flow (xyflow)** | **首选** | 专为节点-边图设计，内置拖拽、连线、缩放、小地图、自定义节点。MIT 许可，社区活跃。组织架构图是它的典型用例 |
| **dnd-kit** | 辅助 | 如果要做“拖拽角色卡片到层级树”的列表式交互（非图式），dnd-kit 更轻量。但它不擅长“边”的编辑 |
| **React DnD** | 不推荐 | 维护活跃度下降，API 较老 |
| **自研 SVG + 指针事件** | 不推荐 | 拖拽、连线、吸附、缩放全部要自己实现，工作量数倍于使用 React Flow |

**决策**：**React Flow 做图式编辑，dnd-kit 做列表式排序**。两者可以共存于同一页面——左侧是层级树列表（dnd-kit 拖拽排序），右侧是委派规则图（React Flow 拖拽节点和连线）。Tauri 的 WebView 对两者都兼容良好。

## 二、拖拽语义分类：五种操作，三种合法，两种非法

不是所有拖拽都有意义。必须把“能拖什么、拖了之后发生什么”定义清楚，否则用户会拖出系统无法解释的状态。

### 2.1 合法拖拽操作

**操作 A：拖拽节点改变布局位置（自由移动）**
- **语义**：只改变节点在画布上的视觉坐标，不改变组织架构。
- **约束**：无。节点可以拖到任何位置，坐标存入 `role_charters.config.ui_position`。
- **实现**：React Flow 的 `onNodeDragStop` 事件，保存 `{x, y}` 到该角色的 UI 配置。
- **用途**：让用户把图排得好看，纯视觉调整。

**操作 B：拖拽节点改变汇报关系（改 parent）**
- **语义**：把“开发工程师”节点拖到“技术总监”节点的子区域，改变 `reports_to`。
- **约束**：**必须经过合法性校验**（见第三节）。非法则节点**回弹到原位**，并弹出提示。
- **实现**：React Flow 的 `onNodeDragStop` 检测节点是否落在另一个节点的“子区域”（自定义节点可以渲染一个接收拖拽的 drop zone），触发 `validateReparenting(child, newParent)`，通过则更新 `role_charters.config.reports_to`，失败则 `setNodes` 回弹。
- **影响**：改变后**仅对新任务生效**（运行中任务保持旧图，见第五节）。

**操作 C：拖拽创建委派边（连线）**
- **语义**：从节点 A 的“输出端口”拖到节点 B 的“输入端口”，创建一条委派边 A→B。
- **约束**：**必须校验边的合法性**——不能创建循环依赖、不能跳过审阅门控、不能违反层级约束（见第三节）。
- **实现**：React Flow 的 `onConnect` 事件，触发 `validateNewEdge(source, target)`，通过则添加边并弹出“边配置面板”（配置证据包类型、审阅门控、否决权）。
- **用途**：增加新的委派关系（如“运营总监 → 合规审阅Agent”）。

### 2.2 非法拖拽操作（必须被拦截）

**操作 D：拖拽改变角色的“禁止事项”或“工具权限”** —— **不允许通过拖拽完成**。这些是岗位书的结构化字段，必须在右侧的属性面板里显式编辑（带确认对话框）。拖拽的语义太模糊，无法表达“把‘禁止 merge_to_main’从开发工程师身上摘下来”这种精确变更。

**操作 E：拖拽删除节点或边** —— **不允许直接拖到垃圾桶删除**。删除角色或委派边是高危操作，必须走“选中 → 点击删除按钮 → 确认对话框（显示影响范围：X个运行中任务将受影响）”的流程。拖拽删除的误触率太高。

## 三、合法性校验：拖拽后的“门控”

这是整个可拖拽设计里最重要的部分。**拖拽本身是自由的，但落地必须过校验**。校验分三层，全部是确定性代码，不依赖LLM。

### 3.1 结构校验（图论层）

```python
def validate_reparenting(child_role, new_parent_role, org_graph):
    # 1. 不能形成环
    if new_parent_role in get_descendants(child_role, org_graph):
        return Reject("不能将角色挂到自己的下级之下")
    
    # 2. 不能挂到非管理角色下
    if not org_graph[new_parent_role].can_manage:
        return Reject(f"{new_parent_role} 不是管理角色，不能接收汇报")
    
    # 3. 层级深度不能超过上限（默认5层）
    if get_depth(new_parent_role) + 1 > MAX_DEPTH:
        return Reject("组织层级超过5层上限")
    
    # 4. CEO节点不可被拖拽（唯一根节点）
    if child_role == "ceo":
        return Reject("CEO是组织根节点，不可改变汇报关系")
    
    return Accept()
```

### 3.2 审阅门控校验（门控层）

```python
def validate_new_edge(source, target, org_graph):
    # 1. 不能跳过审阅门控
    #    每条委派边必须至少有一个review_gate
    if not has_review_gate(source, target):
        return Reject("委派边必须配置审阅门控")
    
    # 2. 不能建立“作者给自己打分”的边
    #    如果source和target是同一角色，或target是source的直接下游执行者
    if violates_no_self_review(source, target):
        return Reject("审阅者不能是产出者的直接执行者")
    
    # 3. 升级路径必须能到达CEO
    if not can_reach_ceo(target):
        return Reject("委派边会导致升级路径断裂，无法到达CEO")
    
    return Accept()
```

### 3.3 权限校验（权限层）

```python
def validate_org_change(change, user):
    # 组织架构修改是CEO专属权限
    if user != "ceo":
        return Reject("只有CEO可以修改组织架构")
    
    # 改变运行中任务的组织结构需要额外确认
    running_tasks = get_running_tasks()
    if running_tasks:
        return RequiresConfirmation(
            f"当前有 {len(running_tasks)} 个任务在运行，变更仅对新任务生效"
        )
    
    return Accept()
```

### 3.4 交互表现：拖拽时的实时反馈

- **拖拽中**：合法的 drop 目标节点**高亮绿色边框**，非法的 drop 目标**显示红色禁止图标**，光标变为 `not-allowed`。
- **释放后若非法**：节点**弹性动画回弹**到原位（React Flow 的 `setNodes` 配合 CSS transition），顶部弹出 toast 显示拒绝原因（如“不能将测试工程师挂到CEO之下，会跳过技术总监的审阅门控”）。
- **释放后若合法**：节点吸附到新位置，弹出**变更确认面板**——显示“开发工程师的汇报关系将从【技术总监】变更为【架构师】，影响：新任务的委派路径将经过架构师审阅。确认？”确认后才写入数据库。

## 四、与后端 LangGraph 图的同步：拖拽是“编辑时”，提交才是“运行时”

拖拽编辑的是一个**前端的内存图模型**，不是直接改 LangGraph 的运行态。同步机制如下：

### 4.1 三阶段同步

```
[拖拽编辑] → 前端内存图 → [点击"保存组织变更"] → 写入 role_charters + delegation_graph 表 → [系统重建LangGraph图]
```

**阶段1：拖拽编辑（纯前端）**  
React Flow 维护一个 `nodes` 和 `edges` 的本地状态。拖拽只修改这个本地状态。**不触发任何后端请求**。用户可以连续拖拽多次，直到满意。

**阶段2：保存（写数据库）**  
点击“保存组织变更”按钮，前端把整个图序列化为 JSON，通过 Tauri IPC 发送到 Rust Hub，Hub 经 JSON-RPC 转发到 Python Agent Core。Python 侧执行：
1. 再次运行三层校验（防止前端校验被绕过）。
2. 写入 `role_charters`（版本号 +1）和 `delegation_graph` 表（新版本）。
3. **不立即重建运行中的 LangGraph 图**——运行中任务继续用旧图。

**阶段3：重建 LangGraph（新任务生效）**  
新任务的章程批准时，LangGraph 从 `delegation_graph` 表读取**最新版本**的图定义来初始化。旧任务从 Checkpoint 恢复时，加载的是**创建时版本**的图定义（LangGraph 的 Checkpoint 里存了图结构，或通过 `graph_version` 字段关联）。

### 4.2 版本化：组织架构变更是“版本切换”，不是“就地修改”

```sql
  change_summary TEXT              -- "开发工程师汇报关系改为架构师；新增运营→合规边"

CREATE TABLE tasks (
  ...

);
```

**关键设计**：拖拽产生的变更**不修改旧版本**，而是**生成新版本**。运行中任务引用旧版本，新任务引用新版本。回放视图可以展示“这个任务在 v3 组织图下运行，当时开发工程师向技术总监汇报；v5 之后改为向架构师汇报”。

## 五、拖拽界面的具体布局

组织配置页（§14.5）修订为**三栏布局**：

```
┌──────────────┬─────────────────────────────┬──────────────┐
│ 角色列表      │  委派规则图（React Flow）    │ 属性面板      │
│ (dnd-kit)    │                             │              │
│              │   [CEO]                     │ 选中角色的    │
│ ▸ 助理        │     │                       │ 岗位书字段    │
│ ▸ 产品总监    │   [助理]                    │ - 汇报关系    │
│ ▸ 技术总监    │    ╱    ╲                   │ - 决策空间    │
│ ▸ 架构师      │ [产品]  [技术]              │ - 禁止事项    │
│ ▸ 开发        │          │                  │ - 工具权限    │
│ ▸ 测试        │      [架构师]               │ - 审阅门控    │
│ ▸ 运营总监    │       ╱    ╲                │              │
│              │   [开发]  [测试]            │ [保存变更]    │
└──────────────┴─────────────────────────────┴──────────────┘
```

- **左栏（角色列表）** ：dnd-kit 可拖拽排序，拖动角色卡片到图中对应位置，等价于“创建节点”。
- **中栏（React Flow 画布）** ：节点可拖拽改变布局和汇报关系，端口可拖拽创建委派边。顶部有“编辑模式/查看模式”切换——查看模式下所有拖拽禁用，只读。
- **右栏（属性面板）** ：选中节点或边后显示其结构化字段。**禁止事项、工具权限、审阅门控的详细配置在这里编辑**，不通过拖拽完成。

## 六、需要你拍板的一个取舍

**取舍：拖拽的“自由布局”和“自动布局”如何共存？**

React Flow 默认是自由布局（节点坐标手动维护）。但组织架构图有天然的层级语义——CEO 在上，总监在中，执行层在下。两种方案：

- **方案A：纯自由布局**。用户拖到哪就是哪，坐标存 `ui_position`。优点是灵活，缺点是用户可能把图拖得乱七八糟，下次打开一片混乱。
- **方案B：Dagre 自动布局 + 手动微调**。用 Dagre 算法根据 `reports_to` 关系自动计算层级布局（CEO 顶层、总监中层、执行层底层），用户拖拽后**坐标被锁定**，但可以“重置布局”回到自动排布。优点是图始终整洁，缺点是用户失去完全自由的画布控制。
- **方案C：混合**。默认自动布局，用户拖拽后进入“手动模式”（该节点坐标锁定），提供“恢复自动布局”按钮一键重置。

**建议方案C**。组织架构图的价值在于**结构清晰**，不是自由画布。用户拖拽的主要目的是“改汇报关系”，不是“把节点摆成爱心形状”。自动布局保证图始终可读，手动微调满足个性化，重置按钮兜底。这个取舍不影响后端设计，只影响 React Flow 的布局策略配置（用 `@dagrejs/dagre` 做初始布局，拖拽后标记 `manual_position: true`）。

## 七、工作量估算

| 任务 | 工作量 |
|---|---|
| React Flow 集成 + 自定义节点/边渲染 | 3–4天 |
| 三层校验的前端实现（实时高亮 + 回弹 + toast） | 2–3天 |
| 属性面板（岗位书字段编辑） | 2–3天 |
| 保存 → 版本化 → LangGraph 重建的链路 | 3–4天 |
| 自动布局 + 手动微调 + 重置 | 1–2天 |
| 查看模式（只读）+ 回放视图的图版本展示 | 2天 |
| **合计** | **约13–18个开发日** |

**结论**：可拖拽组织层级界面**完全可实现**，React Flow + dnd-kit + 三层确定性校验 + 版本化存储是成熟路径。核心不是“能不能拖”，而是**拖拽被约束在合法的组织变更语义内**——非法操作回弹并解释原因，合法操作走确认面板，变更生成新版本而非就地修改。这与你之前设计的“受约束的自主”原则一致：**UI 的自由度可以大，但落地的变更必须过门控**。
