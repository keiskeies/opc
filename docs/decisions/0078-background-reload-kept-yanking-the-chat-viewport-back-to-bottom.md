# 0078 · 往上翻着读旧史，一刷新就被拽回最新消息 —— 三处「跳到底」里只有一处是用户要的

**日期。** 2026-11-27（round393）。
**落地。** `packages/web/public/group.js`（新增 `CHAT_BOTTOM_STICK_PX` /
`chatScrollAnchor` / `applyChatScrollAnchor`，`renderMain` 与 `loadMessages` 各装一对
「拆之前读、画完压回」的锚点，两处压回都过窗口归属门）；`packages/web/public/group.css`
不动；新守卫 `test/web/chat-scroll-anchor.test.ts`（9 发：跳底归属名单 + 读锚点时机 +

## 1. 一句话

`packages/web/public/group.js` 里 `stream.scrollTop = stream.scrollHeight` 出现过三次，
其中只有 `sendMessage` 那一发是用户自己要求的（按下回车 = 我要看刚发出去的那条，
这一发无条件跳到底是对的，本轮一个字没动）；另外两处根本不是「用户要去底部」，
而是「反正每次重画都回底部」—— `loadMessages` 成功路径收尾无条件跳底（任何一次背景
重读：点「刷新消息」、别人插话后补拉、切回这一会话），`renderMain` 每发
`view.replaceChildren()` 拆掉整格重画、把视口留在新节点的天然值 0（点「回复」、取消
回复、切页签，内容一条没变，屏幕却回到流头）。三处都不违反契约、都不报错、内容判据
全绿 —— 被破坏的东西只有一个：人的眼睛正停在哪一屏。

## 2. 为什么静默：断点落在没有判据的那个维度

修法本身是三行级别的（重画前读一枚锚点，画完压回去），这一族能活这么久不是因为难，
是因为**现有全部判据都不看几何**。0077 那一发的五根线读的是 `rows` / `firstSeq` /
`firstText` / `ascending` / `button` —— 全是内容；`test/e2e` 里其余用例读文本与请求；
`test/arch` 读源码字节。跳底不改这些里的任何一个，所以它对着 4200 多发测试全绿。

另一半原因更值得记：**e2e 此前从没在任何地方设过 `scrollTop`**。每一发用例都从页面
顶部开始、或者干脆不滚 —— 于是所有用例都天然跑在「用户贴在最新消息上」这一条件里，
而这一条件恰好是这个缺陷的无害区（贴底的人本来就该在底部）。缺陷需要「往上翻」这个
前置动作才现形，而自动化里压根没有这个动作。所以本轮真正新增的能力不是那三行修复，
是**把视口变成一个可以被断言的量**（`setChatScroll` + 与内容同一帧读的几何探针）。

## 3. 病根的形状：判据要量「位置」，而位置最容易量错时刻

第一版判据写成「重读前后 `scrollTop` 相同」，在错误的时刻量会**恒成立**：

- 在 `state.messageLoading = true` 那一帧读，屏幕上画的是 `chatSkeleton()`（3 行占位、
  撑不满一屏 ⇒ 没有溢出），量出来是「距底 0 ⇒ 贴底」，于是「贴底 ⇒ 跳到底」这条规则
  每次重读都成立 —— 判据量的是加载骨架，不是用户那一屏。这个形状 0077 §5 在「按钮是否
  存在」上撞过一次（骨架帧喂饱了缺席判据），本轮撞的是它的前半段。
- 在 `view.replaceChildren()` 之后读旧节点，摘下来的节点量不到任何几何（实测见 §4）。

而「什么时候读锚点」本身是代码里一个可错的顺序，编译与内容测试都无感 ⇒ 时机也得钉住，
这就是守卫里那一发「`chatScrollAnchor(` 的下标必须早于 `state.messageLoading = true` /
早于 `view.replaceChildren()`」的由来。

## 4. 落地：一枚锚点、两把尺子、一道归属门，外加两次实测

**实测一：摘下来的节点量不到几何。** 用真 Chromium 量过一次（探针
`.workbuddy/round393-detach-probe.mjs`，Playwright 起页、造一个 `clientHeight` 120 /
`scrollHeight` 2000 的容器、`scrollTop = 500`）：在树上的节点读回
`{top: 500, sh: 2000, ch: 120}`；同一个节点 `remove()` 之后读回
`{top: 0, sh: 0, ch: 0}`。这三个 0 会让 `scrollHeight - clientHeight <= 80` 直接成立
⇒ 恒判「贴底」⇒ 每次整格重画都跳到底。所以 `renderMain` 那一眼必须读在拆之前
（`packages/web/public/group.js:1985`），而不能等进了 `renderChat` 再读
（那里旧节点已经不在了：本轮第一版就写错在 `renderChat` 里，把整对锚点删掉测试一发
都不红 ⇒ 移走；守卫另有一发判 `renderChat` 里既不许出现 `chatScrollAnchor(` 也不许
出现 `.scrollTop =`）。

**实测二：贴底判定必须留容差。** 浏览器把 `scrollTop` 按**向下取整的整数**交回来，
分数 DPI / 分数行高下 `scrollHeight - clientHeight` 落在两行之间，滚到底读回的「距底」
可能是 0 也可能是 1；反过来差几像素没到底的人，被要求「精确为 0 才跟随」会莫名其妙地
不再跟随。所以阈值是一个非零常量 `packages/web/public/group.js:712`，两侧都兜：小于它
算贴底，明显往上翻了才算「在读旧史」。这一格不是装饰 —— 变异机把阈值改成 0（E7）之后，
守卫在整数取底的假流上判贴底就漂了。

**两把尺子各管一头，不许互相「统一」。**
`loadOlderMessages`（0077）留的是**距底距离**，落地在
`packages/web/public/group.js:2223`：往旧翻是往**上方**加内容，只有距底距离能让用户
眼里那一条停在原处。本轮这一对留的是 **`scrollTop` 本身**（读取
`packages/web/public/group.js:732`，落地 `packages/web/public/group.js:747`）：背景重读
新增的消息落在**下方**，上方那段一条没动 ⇒ 同一个 `scrollTop` 就是同一屏像素；换成距底
距离反而会把屏幕连着一块往下滑。两者形状相近、都能编译、内容判据对两者全无感 —— 所以
守卫点名钉住「`loadOlderMessages` 仍用距底、且压根不调用 `chatScrollAnchor`」。把
`loadOlderMessages` 的锚点「统一」成 `scrollTop`（E9）与抹掉它那一发恢复（E8）红的是
同一个字段，这正是「两把尺子被当成一个 bug」的下场。

**一道窗口归属门。** 两处压回都要求屏幕上显示的正是这一会话：刚切会话时
`loadMessages(新 id)` 读到的锚点属于上一个会话，压到新会话上会让新会话停在半屏而不是
最新消息。锚点读取在 `packages/web/public/group.js:2125`，它必须早于
`packages/web/public/group.js:2129`（那一行开始画骨架），落地在
`packages/web/public/group.js:2160` / `packages/web/public/group.js:2161`（无锚点 = 首次
打开或那一屏不是这一会话 ⇒ 落到最新消息；有锚点 ⇒ 交回锚点）。`renderMain` 那一头在
`packages/web/public/group.js:2041`。

## 5. 判据：e2e 真滚动几何 + 源扫描点名每一处跳底

**e2e（`test/e2e/group-workbench.spec.ts:2764`，标题「会话滚动位置」）** —— 五根线，每根
对应一次它自己该管的动作：

1. 翻到半途（`setChatScroll` 写一个实测可达的像素值）→ 背景重读 → `top` 与 `dist`
   逐字段相同（尺子用实测读数，不写死行高）。
2. 贴底时**来一条新消息**再重读 → 跟着走到底（`dist === 0`）。这条不能省：只测
   「贴底 → 重读 → 还在底」的话，把 `pinned` 恒写成 `false` 也能过 —— 内容不变时
   `anchor.top` 正好等于最大可滚值，写回去看起来就是贴底。
3. 整格重画（点某一条的「回复」）→ 位置不动。行用页内探针挑**已在视口内**的那一条，
   因为 Playwright 的 `scrollIntoViewIfNeeded` 自己会改 `scrollTop`，会让这一发量不出东西。
4. 从半途发消息 → 跳到底。这条的前置是先滚回半途并断言 `dist > 80`，否则删掉那一发
   无条件跳底也照样绿（两种情形下贴底的人都会到底）。
5. 每一根线读的是与内容同一帧的原子快照（骨架帧一律不算数），且断言读到的是**新帧号**
   —— 第 1 根线的正确结果是「逐像素相同」，只能靠帧号自证量的是重读之后。

**守卫（`test/web/chat-scroll-anchor.test.ts`，9 发）** —— 钉「谁许跳底、什么时候读」：
无条件跳底的归属名单必须恰好是 `["loadMessages", "sendMessage"]`
（提取器 `test/web/chat-scroll-anchor.test.ts:139`，按字节位置认主人，所以散文里提一句、
或别处出现相似写法都不算数）；背景重读那一跳必须挂在「没有锚点」那一支而不是
`if (stream)`；两处读取各自早于它不该晚的那个动作；两处压回各过窗口归属门；
`loadOlderMessages` 保留距底尺子。**与同目录源扫描守卫的区别**：这一族的两个函数是纯的
（只吃一个长得像滚动容器的对象），所以守卫把 `const` 那一行加两个函数声明切进
`node:vm` 真跑（`test/web/chat-scroll-anchor.test.ts:146`）—— 扫描只能证明「字在」，
证明不了「阈值 80 真的在承重、上界真的夹住、骨架帧真的交回 null」。判别力自证放在最后
一发（八处负向改写 + 两发「取材失败」控制）。

## 6. 变异机

`.workbuddy/round393-mutation.mts`：预检 4 发（两条 e2e + 两份守卫，未变异必须绿）→
19 发期望红 + 2 发控制（只加无关注释，必须绿）→ 每发自己 `finally` 还原并核 sha256。

- E1/E1b `loadMessages` 不读锚点 ⇒ e2e 第一根线红 + 守卫报窗口归属门消失。
- E2 `renderMain` 不读锚点 ⇒ 第三根线红。
- E3/E3b `pinned` 恒 `false` ⇒ 第二根线红（贴底的人不再跟着新消息走）+ 守卫的单位执行红。
- E4 `pinned` 恒 `true` ⇒ 第一根线红（翻上去读旧史的人被拽回底部）。
- E5 去掉上界夹持 / E6 去掉骨架那一格 / E7 容差归零 ⇒ 全部由守卫的真跑读出来。
- E8 抹掉往旧翻的恢复 / E9 往旧翻改用 `scrollTop` ⇒ 0077 那发的新几何线红。
- E10/E10b 抹掉发送那一发 ⇒ 第四根线红 + 守卫的归属名单少一个人。
- E11/E11b 背景重读退回「有流就跳底」；E12/E12b 抹掉整格重画的恢复；
  E13/E13b 把 `renderMain` 的读取挪到 `replaceChildren()` 之后 ⇒ 各自红在该管的那根线。

⚠ 机跑之前先靠分析堵掉两个**会存活的变异**（都是测试形状缺陷，不是判据太松）：第二根线
原来只测「贴底 → 重读 → 还在底」（E3 存活），第四根线原来从已贴底的屏幕发消息
（E10 存活）。这正是本仓反复记的那条：剪线变异存活 ⇒ 先怀疑测试不承重。

## 7. 记下来但没动的

1. 其它长列表（待办表格、文档列表、成员列表）整格重画后同样回到顶部 —— 本轮只给消息流
   装了锚点。别处没有对应判据，就先不动：没有判据的修复无法证明它没被下一次重构抹掉。
2. 用户停在半屏读旧史时，界面上没有「有 N 条新消息，跳到最新」的提示条。现在他是安全的
   （留在原地），但也就不知道下面来了新东西。要做属于界面/文案决策，归 CEO 简报那一族。
3. 发送那一发仍无条件跳底：即使用户几秒前才翻上去，按回车就到底。按 §1 的口径这是用户
   自己的动作；但如果以后支持「引用一条旧消息再发」，这一发要重新判。
4. 窗口缩放后不重算贴底（浏览器自己按新 `clientHeight` 夹），没有判据也没动。
