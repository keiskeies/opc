## 0. 复算：接上之前 `restoreDrill` 有几个生产调用方

**先说我在这条上犯的第三个错，因为它比结论更该被读走**：
我第一版把复算方式写成 `git grep -n restoreDrill HEAD -- 'packages/*/src'` 去掉定义处 ⇒ 空。
落盘之后我照自己写的那行敲了一遍 —— **那条命令对任何函数都返回空**：
`git grep` 的 pathspec 是相对仓库根匹配的，而 `'packages/*/src'` 这一层的 glob
不匹配 `packages/hub/src/...` 这种多段路径，于是它连**定义处那一条**都扫不到。
「去掉定义处之后为空」于是是一句**用一条没有判别力的命令得到的正确结论** ——
0029 §3 那一族（恒真判据）的**普查版**：命令没错、输出没错、结论也没错，
错的是**它给不出反例**，所以它说什么都是「空」。
⇒ 复算命令要配**阳性对照**：同一条命令换一个【已知有调用方】的函数必须**非空**。

**可用的那条**（`$B` = 本篇之前的那个 commit）：

```bash
B=8d9c0f2
count(){ git grep -n "$1(" $B -- 'packages' ':(exclude)*/dist/*' \
  | grep -vE "(src|test)/db/backup\.ts|src/heartbeat/maintenance\.ts" \
  | grep -vE ":[0-9]+: *(\*|//)" | grep -v "/test/"; }
count createBackup    # ⇒ 1 条（serve/assemble.ts 那处）  ← 阳性对照，必须非空
count restoreDrill    # ⇒ 0 条                            ← 本篇要的那个读数
```

三条排除各有各的用处，缺一条就会把「不是调用方」的东西数进来：
`dist/`（编译产物里注释也在）、定义所在文件本身、**注释行**
（`maintenance.ts` 文件头一直就引着 `restoreDrill` 这个名字 —— **注释里的引用不是调用方**），
以及 `test/`。⚠ 光去掉定义文件还不够：`maintenance.ts` 那两行注释在旧的 `HEAD` 读数里
会被算成调用方，我第一版正是因此才去动了 pathspec —— **错的是过滤条件，我以为是扫描范围**。

它在 `packages/hub/test/db/backup.test.ts` 里有四发用例（本篇之前是三发），
在两份决策文档里被谈到过，在 `maintenance.ts` 的文件头注释里被引用过。

⚠ 而这一格有一个**本仓已经记过一次的形状**：`maintenance.ts` 当初接的三块
（integrity / backup / patrol）就是这么接上的，而**那一次接完的当天**，
`backup.ts` 里的 `createBackup` 有了调用方、`restoreDrill` **仍然是零**。
⇒ **「这个文件接上了」与「这块能力接上了」是两个不同的问题**，
而我当时只回答了前者就收工了。同 0013 §7 那一发「22 条用例、零生产调用方」，
只是这次的隐藏方式更隐蔽：**同一个文件里既有接上的部分，也有没接上的部分**。

接完之后：`src/` 里 `restoreDrill` 的调用方 **1 处**（`heartbeat/maintenance.ts`），
`createBackup` 在 `src/` 里的调用方从 2 处变 1 处 —— 因为维护那一轮
现在**只调 `restoreDrill`**，而它内部自己会 `createBackup`。
这一句是本篇第二个决定的全部理由，见 §3。

## 1. 代价是量过的，而我上一轮记下来的那个百分比是错的

**本轮实测**（本机、离线，node v24.14.0，夹具：跑过迁移的真库、5 万条事件、20.4 MB，
payload 带中等长度中文文本；备份与恢复各跑三轮，脚本在 `/tmp`，注入方式同常）：

| 轮次 | `createBackup` | `restoreBackup` | 比值 |
| --- | --- | --- | --- |
| 1 | 357 ms | 507 ms | 1.42 |
| 2 | 352 ms | 504 ms | 1.43 |
| 3 | 350 ms | 509 ms | 1.45 |

⇒ 每天那一轮多出的不是「约 75%」，是**约 1.43 倍**（绝对值 +0.5 秒）。

**我上一轮记的是 102 ms / 76 ms ⇒ 约 75%**（就写在 `maintenance.ts` 那段注释里，
本轮已改）。那一对数字来自另一个夹具：13.7 MB、同一份迁移、payload 更短。
所以这次读到的比上次的**大**，而方向也不同（上次恢复**比备份快**，这次慢一半）。

值得留下的不是那个百分比，是**两件事**：

1. **恢复比备份慢这件事，只有在夹具够大时才看得出来。**
   上次的夹具太小（13.7 MB），慢的那一侧（多次 `openSnapshotReadonlyDb` +
   `PRAGMA integrity_check` + 行数比对）还没开始 dominate，
   于是我得出「演练很便宜」。⇒ **「开销可忽略」这类结论必须带着夹具形状一起记**，
   否则下一个人拿到大库会发现结论反了，而他会先怀疑代码。
2. **我这次是「重跑一遍才发现自己记错了」，不是「读了一遍注释发现单位不对」。**
   也就是说那条错话在树上活了一段时间，而且**它被写进了一句论据**
   （「代价量过 ⇒ 所以每天一次可以接受」）。
   ⇒ 一条被用来支撑决定的读数写进注释时，要连**复算方式**一起写，
   不然它退化成一个「权威数字」，而下一个人只会读到结论。
   本轮那句注释已经改成带夹具形状与轮次的版本。

**顺带一个读数**：整轮 `restoreDrill`（备份 + 恢复 + 校验）在同一夹具上 842 ms ≈ 上面两列之和。
对一个「每天一次、单用户、Hub 本来就在跑心跳」的入口，这个量级仍然可以忽略 ——
这一点与上次结论一致，只是依据换成了这次的读数。

## 2. ⭐ 那条自毁守卫：一次「演练成功」其实是把现网库删了

**实测**（写守卫之前撞的，手法：把 `drillTargetPath` 直接传成 `dbPath`）：

```
restoreDrill({ dbPath: X, drillTargetPath: X, … })   ⇒   返回 { ok: true }
```

而它期间做的事是 `rmSync(X)` → `copyFileSync(备份, X)` → 清掉 `X-wal` / `X-shm`。
后果有两条，第二条更麻烦：

1. 现网库被换成**备份那一刻**的内容，之后写进去的全在 `-wal` 里而 `-wal` 已被删 —— 数据没了；
2. **调用方手上那条连接当场变成 `database is not open`**，
   而下一次写入发生在离这次演练很远的一处。
   ⇒ 没有任何一条日志会把这两件事连起来看。

**为什么 `restoreBackup` 那道 `target_exists` 闸门没拦住**：
`restoreDrill` **自己传 `confirmOverwrite: true`**（演练目标是它自己的临时文件，
覆盖它不需要问人）。那道闸门防的是「使用者不知情地覆盖」，
而知情的那一位恰好不知道两格可以是同一个文件。
⇒ **一条闸门如果被自己的调用方合法地关掉，它对调用方就不存在**。
这不是 `restoreBackup` 的缺陷（它对它的调用方口径是对的），是**跨函数组合**才出现的洞，
而这类洞在本仓已经出现过几次（0013 §8 那条「对目标缺陷分辨能力为零的用例」是它的测试版）。

**真实触发条件**（我先想错了一次，值得记）：我以为 `--db /x/a.db --backup-dir /x`
就会撞上。**不会** —— 演练目标叫 `drill-target.db`，与库不同名，所以目录相同也不相等。
真正能凑出等式的只有一种：**库文件本身就叫 `drill-target.db`**，
最可能的来路是「上一次演练失败留下的那个目标文件被当成现网库跑了」
（失败时它被留在备份目录里当现场，见 §4）。

⇒ 所以我在 catch 里写的那句告警，**第一版是「--backup-dir 指到了库所在的目录」，那是一句不对症的报错**：
读到它的人会去改 `--backup-dir`，改完照旧触发。措辞改成先给等式（谁 = 谁）、
再点出来路。**写报错要先问「照这句做，问题会不会修好」** ——
这与 0031 §2 那条「把人支去检查自己参数的报错」同族。

**为什么抛 TypeError 而不是返回失败值**：这是**接错线**，不是运行期状况，
与 `keep` / `backupName` 那两处同类（那两个也是抛）。
返回失败值会给出「记录一下然后继续」这个选项，而这里唯一正确的继续方式是**改代码**。

**为什么比较要归一化**：`/a/b.db` 与 `/a/x/../b.db` 字符串不等、是同一个 inode。
用 `resolve` 不用 `realpathSync` —— 后者要求文件已存在，而演练目标常常还不存在
（创建它正是恢复要做的事）。测试里那条带 `..` 的夹具**只能用字符串拼接造**：
`path.join` 内部就 normalize，会把 `/sub/../..` 直接折掉，
得到与源库一模一样的字符串，于是「字符串确实不同」那句断言当场红
（我第一版就是 `join`，红在那句上，而红的原因在夹具不在判据）。

**它落在维护入口里怎么接**：`runMaintenance` 承诺「不抛」，
而它现在**必须靠一个 catch 才兑现**（那句注释以前只是声明）。
catch **只接 TypeError**，其余上抛 —— 一并吞掉会把真故障（磁盘满、权限）
洗成一条「备份没跑成」，那是拿「不抛」这条契约去掩盖别的问题
（同 `patrol.ts` 只捕自己那一类失败、`backup.ts` 只捕 `openSnapshotReadonlyDb` 的写法）。
变异 M-F 就是把它改成 `if (e) throw e` ⇒ 红在那一条自指用例上。

## 3. 第二个决定：这一轮**只**落一份备份

`restoreDrill` 内部自己调 `createBackup`，所以维护那一轮**把 `createBackup` 换成它就够了**。
我第一版的直觉是「在外面先 `createBackup`，再调演练」，而那会把每轮变成**两份**备份，
于是 `KEEP_BACKUPS = 7` 的语义从「留 7 份」悄悄变成「留 3.5 份的量」。

⇒ **一个包住另一个的接法，要先读被包住那个的函数体，再决定谁是外层。**
这次读函数的收益是**少写一份备份**；如果反过来（先写、跑测试发现「目录里两份文件」再去查），
那条断言会红成一个「测试写错了」的样子，而实际上是接线错。

顺带定了演练产物住哪：**备份目录里、名字叫 `drill-target.db`**，
而这个名字**刻意不匹配备份名形状**（`opc-…Z.db`）。
所以 `pruneBackups` / `listBackups` / `backupNameToMs` 都看不见它。
这一条不是洁癖：它一旦叫 `opc-….db`，一次演练就产出一份与真备份**完全同权**的「备份」，
7 个保留位被演练挤掉 —— 0018 §1 第 3 条那个「看起来正常而含义不是那件事的文件」的又一个形状。
有测试同时钉住两侧（`isBackupName(DRILL_TARGET_NAME) === false` +
正常库名一律不算同一个文件），所以改名或改常量都会红。

**演练成功 ⇒ 删掉目标；失败 ⇒ 留着。** 删的理由是备份目录体积不能翻倍，
而「事后再看一眼」那个好处已经被 `integrity_check` + 事件行数比对给掉了；
留的理由是出事时那个文件是唯一的现场。删的时候三件一起删（主文件、`-wal`、`-shm`）——
0018 §1 第 3 条实测过「留着一个不属于这个库的 `-wal`，下一次恢复会静默采纳它」，
所以**只删 `.db` 比不删更糟**：它把「上次演练的库」和「这次的 `-wal`」拼成一个
通过完整性检查而内容不是任何一份备份的东西。`removeDrillTarget` 单独成函数、单独一发用例，
就是为了「只删 `.db`」这个最容易犯的形式能被点名。

## 4. ⭐ 我给函数许过的两条兑现不了的性质

**第一条：「演练目标是个目录 ⇒ 备份目录里一份备份都不该写」。**

我在 `restoreDrill` 里前置了一道抛门，并配了一条断言 `readdirSync(dir) === []`。
它当场红了：目录里躺着一份新备份。
真相是这个函数**必须**先 `createBackup` 才有东西可恢复 ——
「跑不了」这件事**只能在备份之后知道**。

我最初的反应是「判据写错了」。实际的修法是承认：
**这条性质不是这个函数能兑现的性质**，于是我
① 把那道前置门撤掉，改成「只在它是普通文件时删它」，
② 让 `restoreBackup` 有一个有名字的失败态 `target_not_writable`（不是一段裸 `ERR_FS_EISDIR`），
③ 断言改成实测形状：备份 `ok: true`、`restore.reason === "target_not_writable"`、那个目录**还在**、告警恰好一条。

`target_not_writable` 是新加的一格而不是复用 `target_exists`，理由与 0031 §2 同族：
`target_exists` 的修法就是「传 `confirmOverwrite`」，而演练一直在传它 ——
**一个目录是传那个参数也修不好的**。两个情况共用一个词，运维照那句做会**二次失败在同一处**，
第二次他会以为是自己的参数还没加对。

**第二条：「维护入口那边有一条断言要用 `isSamePath` 这同一个谓词」。**

我把这条理由写进 `isSamePath` 的导出注释之后，才去写那条断言。写出来是：

```ts
expect(isSamePath(path, join(dir, DRILL_TARGET_NAME))).toBe(true);   // path 就是上一行这个 join
```

**恒真** —— 等式两边是同一行代码算出来的同一个值（0029 §3 那一族，我自己又造了一条）。
删掉它之后，「两个消费方」这个导出理由就不成立了，注释跟着改成
「**这条判据的消费方需要能直接测它**，因为它的失效方向是静默放过」。

⇒ 两条合起来是同一个毛病的两侧：**先有结论（一句听起来对的道理 / 一条听起来该成立的性质），
再去补配得上它的证据**。顺序应该是：
**先写下断言、跑一次反向对照，再决定要不要为它写那句理由 / 加那道门。**
反向对照在这里的具体作用就是拦下第二条：
如果我给那条断言配过一个反向对照（换一个**不该**相等的路径对），它立刻就红了。

顺带：`isSamePath` 自己有一条直测用例（三对正例三对反例，反例防它退化成恒 true）。
它同时**不再**被任何测试「跨模块引用」—— 那个动机没了，就别留那句动机。

## 5. 判据形状上值得抄的两处

- **`ok` 是四块合取，而 `drillProblem` 今天在上面是冗余的**（它只由「同路径」那一支置起来，
  那一支同时置 `backupProblem`）。仍然写进表达式，理由与 0025 §8 那条口径一致：
  「备份成功 + 完整性过 + 演练可用」**三条一起**才算灾难恢复在位。
  一条今天恒假的判据写在表达式里，与这句话只写在注释里，**证据强度不同档**（0020 §2 那一族）；
  而将来任何「只让演练失败而不让备份失败」的新形状会在改那一支时自动生效。
- **`drill` 与 `drillSkipped` 的语义必须互斥**：`drill` 缺席**只**意味着「这一轮没东西可练」，
  「练了而练败」住在 `drill.restore` 里，**不搬到 `drillSkipped`**。
  把两者合成一个值，读的人会以为有过一次失败的演练。
  `report()` 里那一行**无条件**打印（跑过 / 没跑成都有一行）——
  只在成功时出现的输出行看不出「今天压根没演练」，而「看不见的失效」正是这个模块防的东西。

## 6. 别当成做到了

- **仍然没有调度器。** 0025 §7 那格一字未动：`hub:maintenance` 是一条**要人手工敲**的 script，
  【规格】§6.5 那句「每日备份」今天仍然依赖「人记得跑」。本篇只是让**跑一次的时候多验一件事**，
  没有让它自己跑起来。（`serve/assemble.ts` 文件头把这条登记得很清楚，本轮复核仍成立。）
- **恢复演练的端到端那一半仍然没有**：验的是「恢复出来的文件能打开、完整性过、
  事件行数一致、触发器与 FTS 仍在」，**不是**「恢复之后能 `hub resume` 继续跑未完成任务」——
  后半需要 `@langchain/*`，本机装不上（0009 §2），在 `backup.test.ts` ⑤ 里钉成一条零调用方断言。
- **本篇新增那 10 发不发一条承诺「现网不会自毁」**：守卫拦的是**这一个**已知的自毁路径。
  `restoreBackup` 依然是一个能覆盖现网库的动作（它靠 `target_exists` + 名字形状两道门），
  那两道门的强度由 `backup.test.ts` ⑤ 那批发测，不由本篇。
- **`pnpm verify` 仍然跑不起来**（`vitest` 解析不到，复算 `node packages/hub/scripts/deps-resolvable.mjs`）
  ⇒ 下面那些绿是 **node:test + 自制 harness** 给的，**不是门禁过了**。
- **格式未经校验**：`@biomejs/biome` 装不上，新增代码的排版是我手工对齐的。
