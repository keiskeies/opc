# 0008　Phase 1 门控的三处语义收紧，以及「等 CEO」到底等的是哪一件事

- 状态：已接受（§1–§6 是实现层的既有决定；§7 是等 CEO 的一项，已登记在 `docs/INDEX.md`）
- 关联：0005 §（`KIND_TO_ACTION` 与 seq 来源）、0006 §8 / §9（两项等 CEO 的出口判据，本篇不重复也不覆盖）、0007 §1.3（`test/` 不进 `tsc -b`）
- 范围：Task 1.1–1.7 的产出。三处收紧都在【判定方向】上，不改任何数据形状；一处状态机补边；一条扫描守卫修复。

## 1. 为什么这六件事写进同一篇

它们不是六个独立的功能决定，而是同一个缺陷形状的六次现形：**一个模块默认放行它其实判不了的东西，
而另一个模块对同一件事写了相反的期望，先跑的那个生效。**

这个形状在本篇里出现了三次，每次都表现为「全套单测全绿，验收标准同时失效」：

| 位置 | 一侧的期望 | 另一侧的实际 | 谁生效 |
|---|---|---|---|
| 门控 vs 升级路由 | `escalation.ts` 把「有标准没判定」定成 `insufficient_evidence` 触发条件 | `evaluateGate` 对同样情况返回 `pass` | 门控先跑 ⇒ 升级那条触发条件【永远走不到】 |
| §8.1 表 vs 门控 | 每个交接方向该收固定一种 `bundle_type` | 门控不读这张表（全仓零生产调用方） | 「开发不交测试报告」无从判起 |
| 卡片起草 vs 状态机 | 预算突破要出升级卡片（规格 §7.4 收件箱三按钮） | `BUDGET_PAUSED` 出边为空 | 卡片【起草成功、投递非法】 |

三条的共性是：**没有任何一个单测会红**。每个模块在自己的边界内都「对」。
这正是 Task 1.7 那个验收文件存在的理由（见 §6），也是本篇要留档的原因 ——
否则下一次有人看到「门控返回 pass 却带着非空 unresolved」，第一反应仍会是「加个字段让调用方自己判」。

## 2. 判据：**无法判定 ⇒ escalate，不是 pass**

### 2.1 洞的实际形状

改之前：`evaluateGate` 一路走到 `return { decision: "pass", unresolved }`，把判不出的标准挂在返回值上。
`unresolved` 没有任何强制力 —— 调用方不读它，就等于什么都没发生。

绕过成本因此是【零】：agent 不需要伪造覆盖率数字，只要【不在证据包里写 metrics】，
岗位书里那条 `metric:coverage` 标准就永远走 unresolved，门控恒 pass。

这个方向值得单独记一句，因为它推翻了我自己原先的假设。我原本以为要防的是「编一个 91%」，
而编数字至少还会被「指标该来自 harness」那一层的对账撞上。**最省事的假绿方式是不提这件事**，
它连对账都绕开了 —— 没有声明，就没有可核对的东西。

### 2.2 为什么是 escalate 而不是 reject

reject 会告诉产出方「你不合格」，可他没做错任何事，缺的是【这条标准在这儿无法判定】。
更坏的是 reject 会给出一个**错误的修法**：「把 metrics 填上让标准能判」——
于是逼出来的是编一个指标值，那正是规格 §14.4 红线二禁止的形状（自评数据当证据）。
escalate 的语义恰好是「这件事需要人看」，而且它给出的是两条正确的出路
（改成 `metric:` 形状并带上该指标，或者承认这条只能人判、别写成门控标准）。

### 2.3 空标准为什么仍然是 reject（不要顺手统一成 escalate）

`criteria.length === 0` 走 reject，`unresolved.length > 0` 走 escalate，这个不对称是有意的：
前者是【配置缺陷】（岗位书压根没写标准），后者是【这一次的证据不足】。
把缺陷 escalate 上去，CEO 会每周重看同一个没修的配置问题；
把证据不足 reject 掉，就会得到 §2.2 说的那个错误修法。
`determinism.test.ts` 里有专门一条钉这个不对称，防止将来有人「顺手统一更整洁」。

### 2.4 代价（说清楚，不要只报好处）

CEO 收件箱会变吵：凡是标准写成自然语言的岗位书，每一闸都升级。
按 §7 的口径，7 份模板目前全是占位串，所以**门控现在对每个真实产出都会 escalate**。
这是【要的】方向：那是「门控还没被喂进可判定的标准」这件事唯一的可见方式。
但它是可感知的噪音，若 CEO 的判断是「先让 Phase 1 跑起来再说」，
正确做法是补 `metric:` 形状的标准（§7 那张脚手架表），不是把这条改回 pass。

## 3. §8.1 那张表接进门控；以及未知方向为什么不抛错

`HANDOFF_BUNDLE_TYPES` 在 contracts 里躺到本轮为止，**没有任何生产调用方**（实测：只有它自己的单测在调）。
表在、函数在、校验在，接线缺失 —— 于是 §8.1 只是【文档上存在】：`dev_to_test` 收任何 `bundle_type` 都照收。

反向绕过也很便宜：交一个 `bundle_type` 写成 `test_report`、内容只有两句话的包，类型这一维就过了。

**未知方向不抛错**，这与它旁边的 `requiredBundleType()` 相反，理由不同必须不同：
那个函数被调用的场合已经有人在栈上等结果，抛错是明确的失败信号；
而 `evaluateGate` 是【全函数】，运行时传进来的 `gate` 名远不止五个交接方向
（中断载荷里实测出现过 `"qa"`、`"ceo"`），在门控里抛错的默认表现是【这一闸整个跳过】。
所以未知方向记入 unresolved，走 §2 那条 escalate。

**这条改动会让已经存在的中断路径开始 escalate。** 目前那些路径没有生产调用方接门控
（`evaluateGate` 的生产接线是 Task 1.3/1.4 之后的事），所以本轮不产生实际影响；
接线时必须给中闸门控登记包类型，或者显式承认它不收证据包 —— 别让它默认落进未知方向。

## 4. 补一条状态机边：预算暂停态可以往上升级

> 标题刻意【不写】目标状态的常量名。`pending-decisions` 那条守卫认「标题里出现 CEO」=
> 这一节在等 CEO 拍板，而 `ESCALATED_TO_CEO` 这个常量名里就带着 CEO 三个字母 ——
> 写进标题会被判成一条待决事项，逼我去登记表里登记一个根本不存在的决策。
> 守卫没有错，是我的标题借用了一个恰好含关键词的标识符。状态名在正文里照常写。

### 4.1 为什么这条边该补，而它的兄弟那条不该

`status.ts` 的边表原先把 `BUDGET_PAUSED` 写成死路，注释是
「规格未给出路（§7.4 预算硬停落地时【必须补】）」，
`status-machine.test.ts` 再把这个缺口显式断言成 `toEqual([])`，并写明「届时本文件相应断言会红，逼人来对账」。

Task 1.6 让硬停真的能触发了，绊线如设计所愿变红。对账结论：

- **升级边有原文依据，补。** §8.3 第二条逐字列着「触及预算硬停」是升级触发条件；
  规格 §7.4 又写明预算暂停卡片的三个按钮（追加预算 / 维持暂停 / 终止任务）出现在 CEO 的收件箱里。
  两处合起来就是「暂停态必须能升到 CEO」。不补的结果是 §1 表格第三行那个组合。
- **恢复边没有依据，不补。** 规格 §7.4 只说「决策后 agent 从 Checkpoint 恢复」，
  没点名恢复到【哪个状态】。回 `IN_REVIEW`（接着被打断的审阅往下走）与回 `IN_PROGRESS`
  （当作重做一轮）是两种不同语义，选错会静默改变「预算追加之后要不要重审」这件事的答案。
  `status-machine.test.ts` 文件头那条口径仍然成立：不替规格编语义，
  编出来的恢复边会让「非法跃迁」检查松掉 —— 什么都能跃迁就等于什么都不检查。
  所以这一半缺口继续显式钉住（见 §7）。
- **「维持暂停」不需要边。** CEO 什么都不放行就是不跃迁；为此写一条重复状态的事件会撞上
  「自环一律非法」（`status-machine.test.ts` 同名用例），而那条禁自环防的是中断重放重复写事件。

### 4.2 这次改动被谁抓住了

`escalation.test.ts` 里那条遍历全部状态交叉验证 `canEscalateFrom` 与边表一致的用例当场变红
（`["IN_REVIEW","APPROVED_UPWARD"]` → 多出 `BUDGET_PAUSED`）。
这是那条遍历用例第一次真正起作用，值得记下来 —— 它此前从未被边表改动红过，
所以「它能抓住东西」这件事只有它自己那条合成反例在证。
三个方向都验过它拦得住：加边没改名单 ⇒ 红（本轮实际发生的）；删边没改名单 ⇒ 红；
`canEscalateFrom` 与 `EDGES` 脱钩 ⇒ 红。

## 5. 两处与门控无关但同轮修的守卫缺陷

### 5.1 `production-deps.test.ts` 的 `packageName()` 会整类漏认带子路径的 scoped 包

旧实现先判 `spec.includes(sep)` 就 `return null`，于是

```ts
import type { RunnableConfig } from "@langchain/core/runnables";
```

被当成【不是包】而完全跳过 —— 而该文件注释一直写着 `@scope/pkg/sub → @scope/pkg`。
后果恰是这条测试存在的理由落空：`@langchain/core` 若被挪进 `devDependencies`，
`src/` 里唯一引用它的那一行【恰好带子路径】，于是 `pnpm install --prod` 之后 Hub 起不来，
而这条测试全绿。分隔符的判断只能对相对/绝对路径生效；**包名本来就可能含斜杠，
那是 npm scoped 包的语法，不是路径。**

补了一条正向用例（点名 `@opc/hub :: @langchain/core` 与 `@langchain/langgraph` 必须在实到集合里）。
它不是装饰：`seen.size > 3` 那条只保证「扫到了点东西」，
少认一整类包时其余条数照样能超过阈值，于是扫描器坏了而门禁全绿。

### 5.2 `evidenceBundleSchema` 外层补 `.strict()`

`artifacts` / `claims` 两个内层对象一直是 strict，外层漏了。
而**外层恰恰是字段改名会发生的地方**：内层改名会让整条记录对不上形状、当场报错；
外层改名（`produced_by_role` → `producer_role`）只会让旧字段变成「缺失但没人发现」，
只要新字段一起传上来就通过校验。代价是多带一个字段整包被拒 ——
这是要的方向（fail-closed，与策略引擎「未知即不可逆」同一立场）：
宁可当场拒一个包，也不要门控读不到 `produced_by_model_family` 却照样判「审阅者不同源」。

### 5.3 顺带：新增 `metrics` 可选字段（相对计划接口的偏离）

计划的 Task 1.1 接口里没有 `metrics`。加它是因为 §8.2 第 5 条要求门控
「检查覆盖率数值」且必须是确定性代码，而纯函数要判 `coverage >= 80`，
唯一出路是数值随证据一起进来。没有这个字段，`evaluateGate` 对所有数值条件只能一律升级 ——
那 §23.1「八成审批由规则自动决定」这条北极星就无从谈起。
缺省即「本包没带任何可判定数值」，此时按 §2 走 escalate，不臆断通过。

## 6. Task 1.7 那个验收文件为什么不能省

`test/acceptance/phase1-gates.test.ts` 的三条用例跑在【真迁移 schema + 真 recorder + 真总线 + 真制品存储】上，
判的是 §23.1 Phase 1 那三条。它与 `test/gates/`、`test/budget/` 的分工值得写死，否则看着像重复劳动：
单测问「各模块在各输入下返回什么」，验收文件问「CEO 关心的三件事端到端会不会真的发生」。

这两问会分叉，而且分叉方向很不友好 —— 每个模块各自全绿，拼起来不满足验收标准。
§1 那三条里没有一条能被任何单测抓到，因为每条都需要【两个模块同时在场】。

文件里还留了两条反面用例（方向对、引用实、覆盖率达标 ⇒ `pass`）。
它们不是礼貌性补充：**少了反面用例，「reject」这一组断言与「永远 reject」不可区分**，
而这恰好是 §2.3 那个不对称最容易被后人改坏的方式。

## 7. 等 CEO 的一项：7 份岗位书的验收标准由谁写

### 7.1 这一项我不会代写，理由不是畏难

计划对 Task 0.9 写的是硬边界：「开发者不得代写验收标准（规格 §23.2）」「此时宁可推迟 Phase 1，不可代写」
「若 CEO 未签完，本任务不得提交」。而 Task 0.7 留下的模板头注释把机制讲得比计划更直白：

> `charter.test.ts` 断言它已从模板消失 —— 没签完 CI 就一直红，不需要人工催办。
> 开发者不得代笔：代笔只是把红灯变成假绿（计划 Task 0.9）。

也就是说：**那个占位串和那条红色断言是设计好的升级触发器，不是一个等着被填的空。**
把 `CEO-PLACEHOLDER-ACCEPTANCE` 换成任何我能写出来的标准，都是**亲手拆掉产品自己装的报警器**。
拆掉之后 §8 全部设计失效，而且失效方式是「全绿」。

第二条独立于计划文本的理由：交付物包括 `signed_by: ceo` 与 `signed_at`。
那两个字段是一份**签字声明**。我写下去就是一句我说不上是真的的话 ——
它伪造的是审计记录本身，而这一整篇的前提是审计记录不可伪造
（`events` 表上那对 `RAISE ABORT` 触发器讲的是同一件事）。

### 7.2 为什么这一项和 0006 §8 / §9 那两项不同

`docs/INDEX.md` 的「等待 CEO 决策」那一节按规矩要求标题里带 CEO（`PENDING_HEADING`），
而本篇没有这样的标题 —— 因为那两项需要 CEO【选一个字母 / 选一种读法】，
我可以在文档里把材料备齐并给出倾向。

这一项需要的是另一件事：**CEO 对「什么叫做完了」的原始判断**，
它不是从材料里能推出来的选项，而是规格 §23.2 明确划给 CEO 的输入。
我这边没有可倾向的答案 —— 有的话就变成代写了。所以按**本节 §7.1 的正文**登记（见 INDEX 那一行），
而不是造一个假标题把守卫绕过去。

### 7.3 我能先备好的部分：把「写标准」的成本降到填一行

标准必须 `metric:` 形状才可机械判定（否则按 §2 一律 escalate），
而**指标词表此前在整个仓库里不存在**（实测：`docs/` 与 `packages/*/src` 里没有任何登记处）。
所以「CEO 写标准」这件事此前不是措辞问题，而是要连词表一起发明 —— 那才是它真正没被推进的原因。

下面这张表是我能给的脚手架，**不是已签字的标准**。取值全部照抄规格已有的数字
（§8.1 证据包内容、§23.1 的验收示例、各模板注释里出现过的例子），
CEO 可以直接用、改数值、或换指标名。`--opc-offline` 之外没有任何东西依赖它。

| 角色 | 建议 condition（不合格情形） | 需要证据包带的 metric | 规格出处 |
|---|---|---|---|
| product | `metric:requirement_items_without_acceptance > 0` | `requirement_items_without_acceptance` | §8.1 产品→技术「每条含可测量验收标准」 |
| tech | `metric:adr_missing_for_risky_choice > 0` | `adr_missing_for_risky_choice` | §8.1 技术→开发「ADR 含备选方案与选择理由」 |
| dev | `metric:p0_defect_count != 0` | `p0_defect_count` | 各模板注释与 §23.1 示例 |
| test | `metric:coverage < 80` | `coverage` | §23.1 与模板注释里的 80 例 |
| ceo | `metric:approaches_present < 2` | `approaches_present` | §9.2 要求给出备选，不凭单一方案点头 |
| assistant | `metric:schedule_conflicts_unflagged > 0` | `schedule_conflicts_unflagged` | §8.1「逐项，非『没问题』」的形状套用 |
| ops | `metric:platform_versions_missing > 0` | `platform_versions_missing` | §8.1 运营→CEO「平台适配版本」 |

注意方向口径（`determinism.test.ts` 文件头也写着，这是本仓最容易整体写反的地方）：
`condition` 写的是【不合格的情形】，配 `action: reject` 读作「成立即拒」。
写成 `metric:coverage >= 80` 配 reject 表达的是「覆盖率好就拒」，
症状是全绿而门控从不拦任何东西 —— 我自己第一版就这么写错过一次，
症状恰好是本仓点名最难发现的那一形。

签完之后要做的事只有三件：替换 `acceptance_criteria` 段、每个 YAML 顶部加
`signed_by: ceo` 与 `signed_at`、把 `charter.test.ts` 那条「模板仍是占位串」的断言
改成「断言占位串已消失且 `signed_by` 存在」。断言方向我留好了，不需要重新设计。
