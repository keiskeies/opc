# 0003　Checkpoint 与 events 的事务作用域：原方案成立（ALS 贯穿框架调度）

- 状态：已采纳
- 日期：2026-11-06
- 关联：规格 §6.3、§24 风险 6；计划 Task 0.4a / 0.4b；决策 0001 §2.2
- 探针：`packages/hub/test/checkpoint/tx-scope-probe.test.ts`（5 例，全部进仓库，非临时脚本）

## 1. 决策

**走原方案**：用 `AsyncLocalStorage` 建立事务作用域（`txScope()`），节点执行体、
框架回调的 `Saver.put` / `Saver.putWrites`、以及审计事件写入，全部从同一个作用域取
**同一个连接**，一次作用域结束统一 `COMMIT`。规格 §6.3「Checkpoint 与 `events` 同一
事务提交」**原样成立，不需要降级**。

决策 0001 §2.2 只证明了 ALS 能在 Node 原生调度下跨 `await` / `setTimeout` /
`Promise.all` 传递。真正没被证明的是 LangGraph 自己的调度 —— `put` 与 `putWrites`
是框架在我们代码之外调用的，我们拿不到它的调用上下文。这条缝只能实测。

## 2. 实测依据（一次真实图执行，非模拟）

`RecordingSaver` 的 `put` / `putWrites` **只从 ALS 取连接**：取不到就不写，让 ALS
缺失暴露成「表里少行」，而不是静默换一条连接写进去。每次调用记录连接身份。

| 断言 | 实测结果 |
| --- | --- |
| 框架调用 `put` / `putWrites` 时 ALS 上下文存活 | 通过。串行图一次 invoke 触发 7 次 Saver 调用（4 次 `put` + 3 次 `putWrites`），`hadScope` 全为真，连接身份全部等于作用域内那条 |
| 提交前，第二条连接到同一文件读不到未提交行 | 通过。三张表的未提交行数对外部连接均为 0，而写者自己看得见（差异断言，见 §4） |
| 节点抛错 → 三张表全部无残留 | 通过。框架在失败前已写入 3 条 checkpoint，`ROLLBACK` 后三表计数都是 0，无孤儿事件 |
| 并行兄弟节点不被并行调度分走连接 | 通过。`left` / `right` 两条分支拿到的连接 `===` 事务连接，两条审计行落在同一个库 |
| 两个 thread 并发事务互不串用 | 通过。两次执行的节点轨迹确实交错（`A start < B end && B start < A end`），两库路径不同且互相查不到对方的审计行 |

框架调用顺序实测为 `put → putWrites` 交替，最后一个超步只有 `put`（没有 writes 就不调
`putWrites`）。Task 0.4b 的 `writes` 表外键可以依赖这个顺序。

## 3. 顺带测出的两条硬事实（会影响实现，不只是「通过」）

### 3.1 外层事务持写锁期间，另一条连接写入直接被阻塞到 `SQLITE_BUSY`

> **证据性质说明**：本节结论来自一次**一次性变异实验**（临时给记录器加「自带连接」开关跑出 `database is locked`，随即把开关删掉）。**仓库里没有对应的可重放测试** —— 该行为要等到 Task 0.4b 有真实 Saver 实现后，由其契约测试的「同事务原子性」用例覆盖。在此之前，它是一条已被观测到、但未被自动化的事实。

变异 M7（让 Saver 自带一条连接，即官方 `SqliteSaver` 的自然写法）没有让断言变红，
而是抛 `database is locked`。这条错误本身就是结论：

> 只要 Hub 里存在一个未提交的外层事务，**任何绕过 `txScope()` 自己开连接写入的代码
> 都会撞上 busy**，而不是「写成功了但不在事务里」。

两个后果：

1. 这层隔离由 SQLite 强制，不靠人自觉 —— 架构上「所有写都走单写者 Hub + WriteQueue」
   与事务作用域天然一致，混用会被数据库拒绝而不是被静默容忍。
2. 反过来讲，**任何忘记提交的路径都会把整个库写死**直到 `busy_timeout` 超时。所以
   `tx()` / `txScope()` 必须让「忘了提交」在编译期或运行期不可能（决策 0001 的
   `tx()` 用回调式 API 正是为此）。

### 3.2 事务粒度必须是【每个超步】，不是【每次 invoke】

探针为了简洁，把整次 `invoke` 包进了一个事务。**实现不得照抄这个粒度**，理由有两条，
任一条单独成立都足以否决：

- **会废掉崩溃恢复**。checkpoint 的意义是中间态可恢复；整图一个事务意味着中间态永远
  不会 `COMMIT`，进程一崩就全回滚，退化成「要么全成要么全无」。而决策记录 V11 已经
  实测过：重新 `invoke` 会**重放所有已完成节点**。两者叠加 = 每次崩溃都把整条流水线
  重跑一遍，checkpoint 形同虚设。
- **会把写锁按住整张图的执行时间**。审批节点要等人（规格 §10），LLM 调用动辄几十秒；
  SQLite 的写锁是**库级**的，不是 thread 级 —— 一个长事务会冻住整个 Hub 的全部写入，
  而且 `busy_timeout` 只有 5 秒（决策 0001），其他写者必然报 busy 而非排队等待。

所以 §6.3 里的「同一事务」应理解为：**一个超步的 checkpoint + 它的 writes + 它对应的
events 是一个原子单位**，超步之间分别提交。这也是探针断言真正证明的东西 —— ALS 让
作用域能贯穿框架调度，至于作用域开多大是实现的自由，粒度由本条约束。

## 4. 这些断言不是摆设：变异测试记录

探针最怕的是「空转也能绿」。四轮变异，逐个证明每条断言可被证伪。**最后一轮是在 biome 格式化、并删掉临时开关之后重跑的**（文件已非变异当时的形状，拿旧战报充数没有意义）：M2、M3、M5、M10、M12、M13 六条全部由断言杀死。
判定标准沿用决策 0001 的口径：**因语法错误而失败的变异不算杀死**。

| 变异 | 结果 | 说明 |
| --- | --- | --- |
| M2 断言 1 不再用 als.run 包裹 invoke | ✓ 断言杀死 | 7 次调用全部 hadScope 为假，正是本决策要防的失效模式 |
| M3 txRun 失败时不回滚 | ✓ 断言杀死 | 回滚后 checkpoints 必须为 0：expected 3 to be 0 |
| M5 撤掉哨兵行 | ✓ 断言杀死 | 观察连接必须看得见已提交的哨兵行 |
| M4 观察连接改读另一个空文件（复刻 4.1 的假通过） | △ 运行时异常杀死 | 该变异代码自身崩溃（EPERM），不能证明断言有效；它的有效性由 M5 侧面证明 —— 撤掉哨兵后同一位置立刻变红 |
| M7 让 Saver 自带一条连接（官方 SqliteSaver 的写法） | △ 运行时异常杀死 | 抛 `database is locked`，见 §3.1。该实验所需的临时开关已在收尾时作为死代码删除，故**本行不可重放**；它不是断言的功劳，只是恰好被数据库挡住 |
| M8 断言 4a 里 B 复用 A 的库 | △ 运行时异常杀死 | cannot start a transaction within a transaction（同连接嵌套 BEGIN），是 SQLite 性质挡住了，不是断言的功劳。真正的交叉污染由 M12 正面证伪 |
| M6 txRun 忘记 BEGIN | △ 运行时异常杀死 | cannot commit - no transaction is active（4 条红）；不是断言的功劳，但故障确实进不了主干 |
| M9 并行节点自开连接写 events | ✓ 断言杀死 | 并行节点拿到的连接必须就是事务连接：left 与 right 皆为假 |
| M10 写者计数改用外部连接（差异断言退化为「两个 0」） | ✓ 断言杀死 | 写入连接应当看得见 checkpoints 的未提交行 —— 正是这句让断言 2 不再是同义反复 |
| M12 A 库里混入标记为 B 的审计行 | ✓ 断言杀死 | A 库里不得出现 B 的审计行：expected 1 to be 0 |
| M13 外部连接的未提交计数改用写者连接（让原子性断言空转） | ✓ 断言杀死 | 提交前外部连接不该看到 checkpoints 的新行：expected 2 to be 0 |
| M1 记录器无视 ALS、直接用 this.db | 等价变异 | 探针里 this.db 与 ALS 里的对象是同一个，行为恒等；改不动可观察行为，不是缺口 |
| M11 撤掉 journal_mode = WAL | 等价变异 | 原子性在 DELETE 日志模式下同样成立；WAL 的价值是「读不阻塞写」，由 driver-preflight.test.ts 里 journal_mode 必须为 wal 那条断言覆盖 |

### 4.1 两个必须记下来的假通过（都是探针自己写错造成的）

写这个探针的过程中，出现过两次「全绿但其实什么都没测」，都靠后来加的守卫抓出来，
记在这里免得重犯：

1. **观察连接打开了另一个文件**。最初的断言 2 里，写入库路径带自增序号，而观察连接
   另拼了一个路径，于是两边打开的是**不同文件** —— 外部读到 0 是必然，与原子性无关。
   当时的代码里还留着一行 void path; 赋值，说明写的时候已经觉得不对，但没有处理。
2. **只数「外部看见 0」而不数「写者看见几行」**。两个 0 不叫原子性，那只是「什么都没
   写」的同义反复。真正的原子性是一个**差异**：写者可见、外人不可见。现在断言 2 同时
   数两边，并由 M10 保证这句差异断言可被证伪。

另外，观察点的顺序也错过一次：先读后写会让 events 永远数到 0，于是「提交后可见」
必然失败 —— 那条守卫当时把设计缺陷抓了出来。

## 5. 降级方案（未启用，留作后备）

若将来 ALS 在某种调度下失效（例如引入 Worker 线程执行节点，跨线程不传递 ALS 上下文），
按下述降级，**并且必须写进本文件、不得静默**：

- events 表以 checkpoint_id 外键关联 checkpoint，各自短事务提交；
- Task 3.4 增加两条对账查询：「有 Checkpoint 无事件」与「有事件无 Checkpoint」，
  命中即在审批收件箱置顶告警；
- Hub 启动时先跑对账，不一致则拒绝启动。

规格 §24 风险 6 的「宁可停，不可丢事件」在两种方案下都必须成立 —— 降级改变的是
**原子性的边界**，不是**审计完整性的承诺**。

## 6. 对 Task 0.4b 的实现约束

1. txScope() 提供连接；Saver 的 put 与 putWrites **不得自行 BEGIN**，只从作用域取连接。
2. 无作用域时的行为必须显式决定：短事务自提（用于 Hub 自己的读写）还是抛错（禁止
   框架外的裸写）。默认抛错更安全 —— 静默自提会让 §6.3 的原子性在最常见路径上失效。
3. 粒度按 §3.2：每个超步一个事务。
4. 五个抽象方法一个都不能少（含极易漏的 deleteThread）；put 是**四参数**，以基类
   为准，不得照抄官方 SqliteSaver 的三参数。基类 putWrites 的文档注释额外要求：
   getTuple 与 list 返回的 pendingWrites 必须按 writesSortKey（task_path、task_id、idx）
   排序 —— 乱序会让顺序敏感 reducer 在重放时重建出不同的值。这条在契约测试里必须有
   对应用例（计划原文未列，见本次核对）。
5. 不要让 Saver 自己持连接写库（§3.1：与外层事务不共存，会 busy）。
