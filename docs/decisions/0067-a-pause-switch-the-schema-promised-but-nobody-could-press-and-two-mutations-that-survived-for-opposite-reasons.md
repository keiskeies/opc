# 0067　一张「规则本身可停用」却没有任何人能按的开关 —— 以及两发同样存活、死因相反的变异

## 1. 一句话

迁移 0025 建 `cos_dispatch_rules` 时文件头写着「规则本身可停用」，而那句话在实现上是一句
**做不到的话**：`enabled` 与 `priority` 两列除了 6 条种子，全仓**零生产写入路径** ——
消费侧（`co.ts` 两条 SQL 各带一个 `WHERE enabled = 1`）天天在读它，改它却只能手改库。
本档记的是把这一格补上（契约 4 schema + 服务读/建/改 + 3 个 HTTP 端点 + 29 发测试
+ 主张链 r27），以及收尾时最有价值的两件产物：**两发存活的变异**，它们各自暴露一件
全绿测试面盖住的事（一发盖住死代码，一发盖住「写痕从没被断言过」）。

## 2. 为什么是这一格：零写入方普查的入选判据

对 `docs/OPC-OS-功能优化设计.md` 收尾普查时列出的零写入方表共 7 张
（`artifacts_meta` / `charters` / `conversations_new` / `cos_dispatch_rules` /
`secrets` / `skill_mounts` / `trust_scores`）。入选本格要同时过三条，缺一不可：

| 判据 | 为什么必须存在 |
| --- | --- |
| **已拍板的规格依据** | 字段语义、错误码、停用 vs 删除这些口径必须已有权威出处，否则是我在发明产品。本格的依据是迁移 0025 文件头那句「规则本身可停用」，加上 `docs/design-2026-11-23-群角色上层-实施计划.md` T8「CoS 规则优先分发（规则表 → LLM 兜底）」—— 建表与消费侧都在计划里排过，配置侧只是没排进来。 |
| **不依赖模型、不由我发明数值** | 信任分聚合权重、辩论会收敛度阈值那一类要的是 CEO 数值，不是代码；写出来是假实现。 |
| **不需要给状态机加态** | 加态属 CEO-gated（0062 那条口径）。本格是纯配置 CRUD，一条状态迁移都不碰。 |

其余六张全部至少卡在第 1 条上：没有任何一份已拍板文档说过它们该由谁来写、写成什么形状。
**「表是空的」不是开工依据，「规格说该有人写」才是** —— 否则零写入方普查会退化成
「看见空表就去填」，而那正是 0065 §3 判塌的那类动作（为到不了的输入造数据）。

## 3. 为什么没有删除端点

迁移 0025 给的语义是**停用**，不是删除。删一行会抽掉 `events` 里 `cos_dispatch` 那几条审计
指向的 `rule_id` —— 回放时查不到「那条消息是谁命中的规则派出去的」。
「不想再用了」与「这条规则从没存在过」是两件事，迁移 0025 选了前者（`enabled INTEGER ...
CHECK (enabled IN (0,1))` + 注释写停用），配置面就照做：三条端点 GET / POST / PATCH，
没有 DELETE。**少一个方法是被规格决定的，不是我嫌麻烦**；要真删得先回答审计悬空怎么办，
那一格没有依据，所以没写。

## 4. 冲突判据必须与消费侧同源：两套口径必然分家

判「新规则关键字撞车」这件事有两种写法，选错的那一种是默认写法：

- **错的**：`WHERE lower(keyword) = lower(?)` 交给 sqlite。
- **对的**（落地）：把同作用域规则捞出来，在 JS 里 `row.keyword.toLowerCase() === want`，
  与消费侧 `co.ts` 命中判据 `lowered.includes(rule.keyword.toLowerCase())` 同一个 `toLowerCase()`。

理由不是风格。消费侧命中靠 JS 的大小写折叠，所以 `BUG` 与 `bug` 是**行为上的重复**
（永远同时命中，谁赢只看 priority/rule_id），必须判成冲突；而 sqlite 的 `lower()` 只做
ASCII 折叠，西里尔字母与希腊语最终 sigma 那类字符两边结论不同 —— 同一件事放两处、
两套口径，就是 0063 记过的那族「口径分家」。判据范围取 `group_id IS ?`（null 安全相等）
= 同一作用域，因为全局规则与本群规则**本来就该**同关键字共存，那正是「同优先级本群优先」
要用的形状；跨作用域判冲突等于把这个设计判死。

这两格各有变异承重：把 JS 折叠改成 sqlite `lower()`（三处编辑一起打）被杀，
把冲突判据改成跨作用域（`WHERE group_id IS ? OR 1 = 1`）也被杀。

## 5. 两发存活的变异，死因相反 —— 这是本篇真正的产出

自回滚探针第一版跑了 11 发，其中 **2 发活了下来**（测试仍全绿）—— 而这两发的病因相反，
分辨方法写在下面。修完之后终版脚本仍是 11 发：「抹掉 `excludeRuleId`」那发换成了
「UPDATE 顺手改写 `created_at`」（死代码删掉后，原变异的靶子不复存在），终版 **11/11 被杀**。
### 5a. 死代码：`excludeRuleId` 那一格根本到不了

变异「抹掉 `keywordClash` 的 `excludeRuleId`（改关键字时该排除自己）」存活。
第一反应是「测试没写够」，但先沿调用链推了一遍：

- create 侧：`createDispatchRule` 调 `keywordClash` 时**根本不传** `excludeRuleId`；
- update 侧：`updateDispatchRule` 只在
  `nextKeyword.toLowerCase() !== before.keyword.toLowerCase()` 时才进冲突判定，
  而库里那一行自己归一化后**必然相等** ⇒ 自身那行按判据永远不可能命中。

⇒ 这是一条**不可达分支**，测试不承重是**正确的**。正确动作不是给它补一发测试（那是
给死代码上户口），是**删掉它**：参数去掉，文件头注释从「要排除自己」改成
「这里【不需要】排除自己 + 为什么」，并把那发旧用例的标题
「PATCH 把关键字改回自己（同值）不撞自己：excludeRuleId 生效」换掉 —— 那句标题是一条
**假主张**，它断言的机制从未生效（用例本身绿，是因为同值 PATCH 走的是另一条短路：
归一化相等 ⇒ 压根不进冲突判定）。

**登记**：变异存活 ⇒ 先怀疑测试不承重，但**第二种可能是分支不可达**；
后者活着时，变异是比覆盖率更好的死代码探测器。分辨法 = 沿两个调用方各推一遍可达性。

### 5b. 反向断言全绿 ≠ 字段有写入方：`updated_at` 的写痕从没被断言过

另一发存活：把 UPDATE 的 `updated_at = ?` 绑成 `before.created_at`（写痕消失，
`updated_at` 恒等于 `created_at`）。这一发**必须**红而它没红 —— 查遍两个测试文件，
关于 `updated_at` 只有**反向**断言（「只改 A 时 B 不动」那一类 `toEqual(before)`），
没有一条正面断言「改过之后 `updated_at` 就是这次的时间」。
于是「UPDATE 漏写痕」这种最典型的失效方向是**无人看守**的。

补法是把那发废用例的位置换成一条正面断言（`rules.test.ts`）：`created_at` 不动 +
实测读回 `updated_at` 等于本次 `nowMs`，见 `rules.test.ts` 里这一行——

    expect(same.rule.updated_at).toBe(NOW + 1);

并追加一发「UPDATE 顺手把 `created_at` 也改写成写入时刻」的变异（SQL 参数 5→6）；
两发现在都被杀。

**登记**：一族的**反向**断言全绿，不能推出「这个字段有写入方」。
每个「随写而变」的字段要有**至少一条正向断言**承重，否则删掉那处写入不会有任何反应。

## 6. 终版 11 发变异的落点（一组真抹字节 → 必须红 → `finally` 逐字节回滚核对 sha256）

消费侧两条 SQL 各抹一次 `enabled = 1`（各红在对应那发「停用后不再命中」）·
冲突判据退化成大小写敏感 · 冲突判据搬进 sqlite `lower()`（§4）·
冲突判据跨作用域（§4）· UPDATE 顺手改写 `created_at`（§5b）· `updated_at` 恒等
`created_at`（§5b）· 抹掉 `auditSeq = 0` 哨兵（全等值 PATCH 谎报有新审计行）·
抹掉 PATCH 的 `changed` 数组（审计说没改过任何字段）· 抹掉 POST 的 `writerMissing`
短路（未接装配仍去写）· 把 `keyword_conflict → 409` 改成 404。
最终一遍：**11/11 被杀，所有文件逐字节还原。**

首跑还踩了一次工具坑：Windows 下 `subprocess.run(["npx", ...])` 找不到 `.cmd`
（`FileNotFoundError`），而崩溃发生在**第一发变异已落盘之后** —— 文件留在变异态。
修法两步：命令改 `shell=True`，还原挪进 `try/finally`（回滚不能在被捕的异常路径上丢掉）。

## 8. 主张链 r27

判据 `dispatchRuleConfigSurfaceCheck` 四格，各对应一种「端点在，但那条线断了」：
① 生产装配真的调用 `registerDispatchRuleRoutes(router);`（文件在 ≠ 接上了）；
② 路由文件里 `router.add(` 恰 3 处（**读侧在 ≠ 写侧在**）；
③ 服务里 INSERT 真的落在 `cos_dispatch_rules`（取材落点不漂）；
④ `co.ts` 里 `WHERE enabled = 1` ≥ 2 处 —— 配置面写 `enabled`，而停用真正生效靠消费侧
**两条** SQL 都带这个条件；少一条，PATCH 就只是个好看的开关。
配 6 发合成变异（含控制组该绿、只加无关行该绿、取材文件整份不见该响亮抛）。
O14 表那一行用**既有入库脚本** `append-registry-row.mjs` 追加，不手抄渲染结果。

## 9. 别当成做到了

- **没有任何界面调用这三条端点。** desktop 的通用领域 RPC 按
  `API_ENDPOINTS.filter(e => e.includes("/api/v1/"))` 建白名单，所以端点**可达**；
  可达 ≠ 有人调。按设计文档开头那条口径（「有实现 + 有测试 + 零调用方，在用户那边的
  读数是 0」），这一格到老板手上还差配置页那一格 —— 那是前端排期，属 CEO 决定，不是我能
  顺手补的。**交付的是「开关装上了」，不是「老板能按了」。**
- **创建时不判「目标岗位在本群有没有人坐着」。** 派发的真实链条是「规则命中 target_role_id
  → 从本群席位挑该岗位成员 → 挑不到就不派」，所以指向空岗位的规则不报错、只沉默，
  与「没命中规则」同一个观察结果。要不要在创建时就拦，是产品判断，且全局规则本来
  不可能预知每个群的编制 —— 登记为缺口（已写在 `rules.ts` 文件头），不是遗漏。
- **`keyword` 没有长度上限。** schema 只 `trim().min(1)`：迁移 0025 的 DDL 没写 VARCHAR 长度，
  而迁移不可回改 ⇒ 在契约里加 `.max()` 会出现「过得了契约、过不了库」还是「过得了库、
  过不了契约」的口径分家，两边哪边都不比我说了算。超长的现实后果（列表页与命中判据
  都还撑得住，只是难看）没有到需要现在发明的程度。
- **`PATCH` 是覆盖式写回**（先由请求算出下一份完整值，一条 UPDATE 落 5 个值），
  不是四条窄 UPDATE。这在四个字段上是划算的，但若以后加一个「要按 kind 分支才能算」的字段，
  这个形状要重读 `plugins/service.ts` 那一族再决定。
- 两件工具的入库待遇不同，各自照仓内既有惯例：**重钉脚本入库**
  （`.workbuddy/fix-claim-coords-381.mjs`，与已入库的 `fix-claim-coords-314*.mjs` 同一族）；
  **变异探针不入库**（`.workbuddy/scratch/` 那批历来不入库）。于是 11 发的原文/替换对
  只活在那一份不持久的文件与 §6 摘要里 —— 下次改这张表要重写探针（与 0066 末尾
  「`fix-rekey.mjs` 随 `.tmp` 不入库」是同一个已知代价）。
- **配置页那一格没做，且不是我漏的。** 三条端点在生产装配里注册、在 IPC 白名单里可达，
  但渲染侧一行都没调 —— 把配置页做出来要选放在 web 还是 desktop、要定列表与表单的信息密度，
  这两件都在已拍板文档里没有依据，属要跟 CEO 对齐的排期，不是能顺手补的格。
  ⚠ **【本篇写完后的复核：原话为真，但当时登记的证据是假探针，已在 0068 修】**
  本节第一版把证据写成 `grep -rn "api/v1/dispatch" packages/web/src packages/desktop/src`
  ⇒ 0 命中。那一发【量不到任何东西】，两处各自独立都足以让「0」失去意义：
  ① **扫错面** —— 渲染侧不住在 `packages/web/src`（那份目录只有 dev-server、签名、
