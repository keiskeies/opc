## 1. 一个平台账号只能有一条绑定

`CREATE UNIQUE INDEX im_bindings_identity ON im_bindings(platform, external_user_id)`。

这条不是「顺手加的整洁」。【规格】把这张表定义成「绑的是【人】不是会话」，
而唯一索引是**唯一能兑现那句话的形状**：没有它，同一个飞书账号可以有两行，
一行 `ceo_role='dev'` 一行 `ceo_role='ceo'`，于是读侧必须**挑一行** ——
而「挑哪一行」在库里没有任何依据（没有优先级、没有版本、没有生效区间）。
后果只能靠 `LIMIT 1`（不带 ORDER ⇒ 取决于查询计划，换 SQLite 版本能给出另一个答案）
或者「取最新的」（⇒ 谁最后被插进去谁当 CEO，而插入时间只说明有人插了一行，
不说明任何人认可过这件事）。两种都在**静默**决定「这个账号是谁」。

所以判据的形状是：**歧义不允许存在**，而不是「存在了以后怎么挑」。

索引里**不带** `ceo_role`：一个真人可以有两个平台的账号都指向同一个角色
（【规格】§11.5 三通道并存时最常见的情形）。反过来「一个角色在同一平台上被两个账号绑」
是**要拦的那一种**（共享账号 ⇒ 审计里「CEO 批了」再也指不出是哪个人），
而它正好被这个索引拦掉。

**这条索引同时是 §7 那个假签名的成因之一**：唯一性只认 `platform + external_user_id`，
所以「换身份」在那张表上只能走 UPDATE 或 UPSERT，不能靠插一行新的 ——
而 UPDATE 那条路上署名与 verified 各自独立，就漏出了 §7。

## 2. 平台白名单：0002 那条排除从此不再只由注释拦着

0002 §4 量的正是这一格：`platform` 是一列**看起来开放**的 TEXT，
「schema 不拦一个 `platform='wechat'` 的 INSERT，拦它的是那条决定加那行注释」。
0002 §6 第 2 条把「改成枚举或加校验」列为需要重读那篇的时机之一，
并要求「那一刻要把 §4 那条注释一起改成**机器可判**的」。**本文件就是那一刻。**

为什么用触发器而不是 CHECK：SQLite 不能对已有列 ADD CONSTRAINT（`ALTER TABLE` 只支持
ADD COLUMN），要 CHECK 就得重建表，而重建表在一张有历史行的表上是「把历史挪一次家」
（同 0002/0003/0004 文件头那条立场）。0001 自己就用了 5 个触发器拦 UPDATE/DELETE。

白名单里**没有** `wechat`，也**没有** `fake`，两件是**不同的事**，
所以 `normalizePlatform` 给它们两个**不同的 reason**（`unknown_platform` / `test_channel`）：

- `wechat` 是【规格】§11.5 与 0002 排除的通道；比封号更硬的那条理由是
  「逆向接入给不出签名，接不进【规格】§11.4 那条『IM 审批必须签名验证』」
  ⇒ 一个不能证明「这条批准来自 CEO」的通道不能承载审批。修法是**不接这个通道**。
- `fake` 是测试通道（`channels/abstraction.ts` 的 `ChannelPlatform` 第四位）。
  它不该进这张表的理由不是「假平台不存在」，是
  **「绑定表是一张真表，测试夹具不该能通过它拿到真角色」** ——
  一个 fake channel 配上 `verified=1` 的绑定就能走完整条读侧，
  那正是 0028 §2 那条冒充通道换了入口。修法是**换测试写法**，不是放宽白名单。
  ⇒ `ChannelPlatform`（4 值）**严格大于**白名单（3 值）是刻意的，
    有一条测试专门钉住这个不相等。

归一化（trim + 转小写）在**校验之前**做，触发器只做最后一道兜底 ——
顺序反了会变成「用户手滑打个大写 ⇒ 一句数据库报错」。
而 SQLite 的 TEXT `=` 默认 BINARY 排序（区分大小写），所以那列里从此只有三种精确写法，
于是「写侧存 'Feishu'、读侧查 'feishu' ⇒ 恒 null，而界面上显示『已绑定』」
这一整类静默失效被关在门口。

⚠⚠ **实测撞出来的第一格**：条件写的是 `(NEW.platform IS NULL OR NEW.platform NOT IN (…))`。
第一版写的是 `NEW.platform IS NOT IN (…)` —— **SQLite 没有 `IS NOT IN`**，
迁移当场 `near "IN": syntax error` 并整体回滚（这一发是响的，算运气好）。
改成 `NOT IN` 就够了吗？**不够，而且是静默的不够**：
`NULL NOT IN ('a','b')` 求值为 **NULL**，而 `WHEN NULL` **不成立** ⇒ 放行。
于是 `platform IS NULL` 的一行能插进来。那列是 NOT NULL，所以今天走不到 ——
但那是**另一条**约束在替这条兜底，而它属于 0001，改表的人不一定看得到。
把 NULL 支路**显式写进条件**，判据就不借「旁边还有一条 NOT NULL」这种迟早会被人挪走的依赖
（同 0021 §2 那一族：判据不能靠它自己之外的东西成立）。

INSERT 与 UPDATE 各一条触发器：只拦 INSERT 的话，「先插一行 feishu 再 UPDATE 成 wechat」
就是白名单的洞，而那条路径**看起来比直接插 wechat 更无害**（它经过了一次合法的写）。

## 3. 一行绑定不许「出生即已验证」

这一条是本文件全部重量所在，因为它拦的是 0028 §2 量出来的那个陷阱：
`ceo_role TEXT NOT NULL DEFAULT 'ceo'` 配 `verified INTEGER DEFAULT 0`。
0028 §2 原话：「**把 actorFor 直接接到这张表上**这一行代码今天会造出：
任何一个在这个平台上发过消息、且有人替他插过一行绑定的账号，**默认就是 CEO**」，
而「今天全部测试都会绿」（fake 的假定正是「这个人就是 CEO」）。

**光靠读侧判 `verified = 1` 够不够？不够，而且不够的理由值得写下来。**
读侧判 verified 挡的是「读的时候没验过的不算数」；
它挡不住「有人**写**了一行 `verified=1`」—— 而那一句 INSERT 才是把冒充变成事实的那一步。
两条判据各挡一半，缺一半就剩下那一半的洞。

有了这条触发器，「一个 IM 账号能批审批」在库里必须是**两次分开的写**：
第一次 INSERT（只能落 `verified=0`，即「有人在申请」），第二次 UPDATE（那次人工校验），
而第二次被 §4 要求交出**是谁验的、什么时候验的**。
「申请」与「认可」之间隔一次显式的人工写 —— 这就是那次校验从**约定**变成**性质**的地方。

⚠ **这一句我原本写成「中间那次 `verified=0` 是可见的『正在申请』状态，界面能读出来」，
而本篇 §0 自己就记着本模块没有任何界面**（无路由、无 CLI、无 IPC）。
那句是**把设计意图写成了已兑现的性质** —— 它在这一节的论证里不是装饰：
§5 在「改身份必须落回 0」与「改身份必须换新署名」两种修法之间选前者时，
靠的正是「中间状态**能被读出来**」这条（§5 第 ② 点）。
如果那条只是意图而不是性质，那次选择就有一半依据落在了一件不存在的东西上。

真实的、**今天成立**的性质弱一档而仍然有用：**那个中间状态是可查询的**
—— `listBindings` 把已校验与未校验一起交出来，
`im.test.ts` 里「listBindings：已校验排前面，其余按申请先后」那一发
断言的是 `[["L2", true], ["L1", false], ["L3", false]]`，
**两个 `false` 是断言的一部分**（不是只数长度），所以「未校验的行读得出来」
是被验过的事实而不是我的说法。
差别不是咬文嚼字：「可查询」意味着**接上界面那天不需要改数据模型**，
而「界面能读出来」意味着今天已经有个界面在读 —— 后者是假的。
把这一格写准之后，§5 那次选择的依据也跟着改写：它真正的依据是
**「两条语句之间留一个库里可查的中间态」**，不是「界面上看得见」。

⚠ 判据写的是 `IS NOT 0` 而不是 `<> 0`：后者在 `verified IS NULL` 时求值为 NULL
⇒ WHEN 不成立 ⇒ **放行**。而 `verified INTEGER` 是可空列（0001 没写 NOT NULL），
`INSERT … VALUES (…, NULL, …)` 完全走得通，那一行既不是「没验过」的 0 也不是 1，
是一个**第三种状态**（读侧 `verified = 1` 判它 false ⇒ 拒，方向是安全的，
但「没验过」与「不知道验没验过」在那张表里长成一件事，下一个人就分不清了 ——
同一族在 §6 又长出来一次，而那一次是**我写完 §3 之后自己开的口子**）。
`IS NOT 0` 把 NULL 一并拦掉，宁可让写侧报错也不留第三态。

## 4. 改成已验证时，必须同时交出是谁验的、什么时候验的

有了 §3，人工校验成为唯一能把 verified 置 1 的路径 ⇒ 那一次写必须留下来源，
否则库里只留下「有一行是已验证的」而**没有任何东西说明谁认为这算验证过**。
那一天真正要问的那一句是「谁断定这个飞书账号就是 CEO」，
而这个问题在库里没有答案的时候，整套「IM 只能批可逆审批」的口子就失去了唯一那层人为责任 ——
【规格】§11.4 要求「签名验证 + 一次性 token」，签名验的是**消息**，
「这个账号属于谁」这件事从第一天起就没人负责过。本文件把它落到一次**有署名的写**上。

**为什么这两列加在 `im_bindings` 上，而不是写进 `events`**：
【规格】§22.1 那个十值 action 枚举里**没有一个**表达「身份绑定」
（逐项核过：state_change / review_decision / approval / tool_call / budget_consume /
meeting / harness_call / unauthorized_attempt / dissent / escalation）。
沿用既有值（`approval`？`unauthorized_attempt`？）会造出一行**语义错位**的审计：
0021 §2 抓的就是这个形状（「记录是真的、它表达的含义是假的」⇒ 审计越全，失真越可信），
而 §22.1 那个枚举与本表一样是 append-only 的口径（不开第 11 个值）。
⇒ 本次把来源落在**绑定行自己身上**（有列可放），
把「要不要给身份绑定开一种审计事件」留给 CEO 拍（§9 里一并登记）。

两列都**可空**，且是刻意的：§4 的触发器只约束「`NEW.verified` 非 0 时不得为 NULL」，
所以对 0005 之前存在的老行零作用（生产库里 0 行，因为这张表从来没有写方），
也不必**编**一个 `verified_at` / `verified_by` 回填进去 ——
0004 给 `created_at` 记过同一条：编一个时间戳会让「什么时候验的」这一格永远说谎。

⚠ `verified_by` 是**可追责性，不是认证**。这句话在 `markVerified` 的文件头也写着，
理由见 §8 后半段（我在那儿写过一句错话，而错的那句和对的这句在 review 里完全同形）。

## 5. 已验证的绑定不许【就地换身份】—— 第一条探针撞出来的洞

**这一条不是设计出来的。** 前四条写完我以为判据闭合了，于是写了一发探针
（`/tmp` 那份，跑完即弃）专门去试我没想到的形状：

```
① INSERT (feishu, u1, dev, verified=0)     放行（申请）        ← §3 允许
② UPDATE verified=1 + 署名 + 时刻           放行（人工校验：这是 dev）← §4 要求
③ UPDATE ceo_role='ceo'                    ← 【放行】
```

第 ③ 步之后库里是一行 `verified=1` 的 **feishu:u1 → ceo**，
而 `verified_by='ceo'` 那句署名说的是【另一次校验】—— 它从来没有校验过
「这个账号是 CEO」这件事。§3、§4 一起把 INSERT 那条门锁死了，
于是冒充改走 UPDATE 那一侧，而 `verified` 一字未动、时刻没变、署名还在，
**审计上一切看起来都是干净的**。这正是 0028 §2 那个陷阱换了个入口：
「默认就是 CEO」变成「改一下就是 CEO，而且带着别人给 dev 做的那次校验」。

**为什么 §4 拦不住它**：那条触发器是 `BEFORE UPDATE OF verified` ——
SQLite 的 `OF` 只在**被点名的列出现在 SET 里**时触发。③ 里 SET 的是 `ceo_role`，
那条触发器**根本没被唤起**（不是求值为假，是压根没跑）。

> 这一格是本篇最该被读走的一条经验：**`UPDATE OF col` 的形状意味着
> 「没被点名的列」上的判据由谁负责，必须逐个想清楚**。
> 而「我把 verified 管住了」这句话当时的真实范围只有「改 verified 时」——
> 我以为我在描述一张表，实际上我描述的是我自己的那几条 SQL。

修法选的是「**改身份必须先把 verified 落回 0**」，而不是「改身份时必须同时交出新署名」：

1. 它让 `verified=1` 获得一条**性质**而不是约定 ——
   **已验证这一格永远指的是它旁边那一组 `(platform, external_user_id, ceo_role)`**，
   读侧不必知道这行被改过几次；
2. 「改绑 + 立刻重新校验」压成一条语句也能做到「有署名」（就是第二种修法），
   而那条语句**长得和合法操作一模一样**，于是判据退化成「看有没有写那两列」，
   而署名可以是从旁边一行抄来的。两条语句之间那次 `verified=0` 的中间状态
   是库里**可查询的**「正在重新申请」中间态（`listBindings` 读得到，见 §3 末尾那段更正）；
   一步到位的版本什么都读不出来。

代价：改绑在最顺的路径上也是两次写。这个代价我认 ——
省下的那一次写在**冒充**那一侧同样只省一次。

⚠ 条件里用 `IS NOT` 而不是 `<>`：`platform` / `external_user_id` / `ceo_role` 在 0001 里
全是 NOT NULL，所以 `<>` 今天等价。但这条触发器的**整个存在理由**是
「判据不能靠旁边那条约束成立」（§2 末段同一条），而 `NULL <> 'x'` 求值为 NULL ⇒ 放行。
用 NULL 安全的 `IS NOT`，这发触发器就自己闭合，不需要 0001 替它担保。

⚠ **我自己写错的一处理由**（原文留着，因为它错的方式正是本仓抓过的那族）：
`REBIND_ROLE_SQL` 文件头我原本写的是「拆成两句会留一个窗口，并发读者能看到假的 CEO」。
**那句是错的** —— `WriteQueue.node()` → `txScope()` → `BEGIN IMMEDIATE`（实测），
一个 node 里的语句共享一个事务，中间状态对并发读者**不可见**。
真实理由是那条拆分**根本跑不通**：§5 这条触发器会拦下第一步
（先改 `ceo_role` 而不在同一条语句里把 verified 落 0 ⇒ RAISE）。
结论没变（一条语句），**理由变了**，而注释里挂着的那个理由是别人以后唯一会读的东西。

## 6. `verified` 只能是 0 或 1 —— 第三条探针撞出来的「第三态」

§3 把 INSERT 钉死在 0，但**没钉上界**：`UPDATE … SET verified=2`（带着署名）是**放行**的
（实测），于是库里多出一个既不是「已校验」也不是「未校验」的第三态。
读侧只认 `= 1`，所以那一行**当前**不会被当成已校验 —— 方向是安全的，
但这一格与 §3 末尾反对 `verified IS NULL` 用的是**同一条理由**：
「没验过」与「不知道验没验过」在那张表里长成一件事，而下一个人只能猜。

更现实的一条：读侧今天是 `verified = 1`，哪天有人「顺手放宽」成 `verified != 0`
（读起来几乎等价，而且看起来像在修一个「2 也算已校验吧」的疑问），
那一行**立刻**变成一个能批审批的身份。**把取值钉成两个，那次放宽就没有东西可以命中。**

这条的可贵之处在于它**不是被攻击出来的，是我自己写完 §3 之后留下的**：
§3 的写法（只判下界）读起来完全像「已经把 verified 管住了」，
而它管的确实只有「不许一出生就是 1」。

INSERT 那一侧不再单开触发器：§3 的 `WHEN NEW.verified IS NOT 0` 已经把 2 拦了。
**加判据时顺手数一数哪几条已经覆盖同一维，比再加一条同义的更好**
（两条同义判据的失效方式是「其中一条被人放宽，另一条还在，于是没人发现那一维被开过」。）

⚠ 为什么 `IS NOT 1` 不会被字符串 `'1'` 误伤（实测）：那列的声明类型是 INTEGER，
SQLite 的列**亲和性（affinity）在触发器之前**就把 `'1'` 转成了整数 1
（`SELECT typeof(verified)` ⇒ `integer`）。所以这一条不会拦住一个合法写入。

## 7. 未验证的行不许留着校验署名 —— 第二条探针撞出来的「一句假话」

这一发撞的形状我事先**完全没想到**：用一条 UPSERT 把已校验的绑定换身份并顺手把
verified 落回 0（**§5 明确允许的做法**），结果是库里躺着一行

```
verified = 0   ceo_role = 'ceo'   verified_by = 'ceo'
```

也就是**一句「ceo 校验过」的署名挂在一个「没校验过」的行上**。
§5 要求「改身份必须把 verified 落回 0」，而它**没有要求同时清掉署名** ——
缺口不在写侧那条 SQL 上（`rebindRole` 两个字段都清了），
在「别人从旁边写」的那一侧：UPSERT、手搓 UPDATE、将来的第二个生产者，都不走那条 SQL。

**后果不是权限洞**（读侧只认 `verified = 1`，那一行拿不到任何批准权），
**是一句已经在库里的假话**：那一行带着 `verified_by='ceo'` 被 `listBindings` 原样交出来，
读它的人（今天是我用 `SELECT`，将来是那个列表界面）会把「校验人：ceo」当成事实，
而这个人此刻**没有**任何校验成立。
⚠ 这一句我原本写的是「**界面上**的一句假话……那个列表会把这行渲染成」，
而本篇 §0 记着**还没有那个列表** —— 写「界面上」反而把这一格**说小了**：
它不是「等有了界面才会有的显示问题」，是**数据今天就在说谎**，
而任何后来的读者都只是必须去信它一次。0021 §2 抓的就是这个形状 ——
记录是真的（ceo 确实校验过**某件事**），它此刻表达的含义（他校验了这个身份）是假的。
本仓把这一族列为最贵的一类，因为它让审计**看起来**更可信而实际上更误导。

判据写成一条性质：**「未验证」这一格与「有署名」这一格互斥**。
于是「谁验的」这句话在那张表里永远与「验过了」同时出现，缺一即另一缺一。
（要把 verified 落回 0，就在**同一条语句里**清掉那两处 —— `REBIND_ROLE_SQL` 本来就是这么写的，
现在它成了唯一能走通的那条路，而不是「推荐写法」。）

⚠ 触发器覆盖 **INSERT 与任意列的 UPDATE**（不是 `OF verified`）。
理由与 §5 完全同构而方向相反：`OF` 只在被点名的列出现在 SET 里才触发，
而这里要拦的正是「改了 `verified_at` / `verified_by` 而没改 `verified`」。
写成 `OF verified` 就漏掉那一发。代价是这张表每次 UPDATE 多跑一次条件判断 ——
行数是个位数量级，不成立为代价。

**§5、§6、§7 三条合起来才是「verified 这一格可信」**：
单独看每一条都像是「本来就该想到的」，而它们在 §3、§4 写完之后的几个小时里
一条都不在脑子里。这就是探针存在的理由，也是本篇开头那句话的落点。

## 8. 角色从哪来：机器给不了，所以我注入，并且登记成缺口

`requestBinding` 的 `knownRoles` 是**注入**的，判据是「给的集合里没有 ⇒ 拒」，
不给（省略）= 不判存在性。为什么不由模块自己求：

- `delegation_graphs` 是权威图（0012），但 0012 §1 第 1 条量的事实是
  **1 号版本一行都不存在**（`tasks.graph_version` 那列从建库起没人写过，全库躺在 `DEFAULT 1` 上）
  ⇒ 拿它判角色存在，答案是**所有角色都不存在**，于是每一条绑定都会被拒。
  方向是安全的，但它不是一次校验，是一次恒假。
- `role_charters` 有 `role_id`，而 0020 §3 记了它的形状：那一列**没有任何形状约束**，
  `Dev` 与 `dev` 都合法而委派边只指得到其中一个 ⇒ 拿它判会把一次拼写错误
  变成一次「绑上了而批不动」。

所以「这个集合该由谁产生」是**计划信息**（跟 Task 3.1 那个组织图端点绑在一起），
机器给不了 ⇒ 登记成缺口而不是替它拍一个。

⚠ **我在这条上编过一次引用**（本篇唯一一处「写了一个不存在的东西」）：
第一版注释里写着「0012 的第十节禁止从 `role_charters` 判角色存在」
（这一句**故意不写成坐标形态**，理由见本节末尾那条脚注）。
**0012 只有 9 节**（复算：`grep -cE "^## [0-9]" docs/decisions/0012-*.md` ⇒ 9），
没有任何东西引过那所谓的第十节 —— 那句话是我为了让一个**其实正确**的结论显得有出处而**造**的来源。
结论本身站得住（上面两条实测就是它的全部依据，而且够），
所以这一发的教训不是「结论错了」而是：**有出处的正确结论并不比无出处的正确结论更对，
而它比后者更危险，因为下一个人会去引一个不存在的节，然后发现自己无法核对别的每一句。**
现在这一节的依据是两条**当场可复算**的读数，没有一条靠权威。
（同族：`markVerified` 文件头那句「由入口回答（这条路只开回环）」——
把「将来应当由它回答」写成了「由它回答」。两句话在代码 review 里完全同形，
只有去数路由表才能分开，而那一步没人会做，所以我替下一个人把它数了：见 §9。）

## 9. 等待 CEO 决策

本篇有两件事留在这里，它们**卡的是同一句话**：「IM 那边能批一次审批」到现在仍然没有主语。

**① 要不要给身份绑定开一种审计事件。**
§4 把校验来源落在绑定行自己身上（`verified_at` / `verified_by`），
代价是「谁校验了一个 CEO 身份」这件事**不在审计流里** ——
它只在绑定表里，而 `events` 是【规格】§22 那条「任何动作都可回放」的那条流。
今天的实际后果：回放一次运行，看不到「中途有人把某个飞书账号校验成 CEO」这个时刻。
三个走法：**A** 就这样（代价：绑定变更在时间线上不可见，而它恰好是**能改变后面所有判决**的那种变更）/
**B** 给 §22.1 开第 11 个 action 值（代价：那个枚举从第一天起是「十个值」的口径，
且【规格】附录是机械提取的，开值要同时改规格）/
**C** 复用 `approval` 并在 payload 里标类型（不改枚举、时间线可见，
代价是 §22 那张表上「审批」一栏混进非审批的行，而 0021 §2 反对的正是这个形状）。
我倾向 **B 的写法 + C 的时机**（先只在绑定表里，等 §22.1 那次真的重读时一起开值），
但**这是【规格】§22 那一层的口径，不是我这一层能定的**。

**② 绑定的入口要不要现在开，以及谁有权校验。**
今天的真实状况（复算方式在 §0 末尾）：`markVerified` 是一个
**能被任何拿到 `WriteQueue` 的代码调用**的函数，而它不判调用者是谁。
它提供的是**可追责性**（出事后库里能问到人），不是**认证**。
本模块**一个入口都没有** —— 没有 HTTP 路由，没有 CLI，没有 IPC，
所以「谁能调它」今天只由「谁能往这个进程里塞代码」回答。

要不要开 HTTP 那一发，代价我**量过** —— 而量完的结果推翻了我自己带进来的两个数，
先记错的（原文照抄），因为它错的方式是本仓抓过的那族：

> 第一版这一段写的是：「`matchRoute` + `Route` 联合类型 + `handleRequest` 分支
> + `contracts/src/api.ts` 里**三张手抄的端点表**（`:35`、`:52`、`:61`）
> + `IMPLEMENTED_ENDPOINTS` + 桌面端 `ipc-surface.ts` + `preload/api.ts`。
> **七处，没有一处会替你报错**」，并且在 INDEX 里把它标成「**代价是量过的不是估的**」。

三处错，都是当场可查的：

1. **「三张手抄的端点表」不存在。** `contracts/src/api.ts` 的 `:35` 实测是 `API_ENDPOINTS`
   **数组中间的一个条目**、`:52` 在**一段注释里**、`:61` 又是 `IMPLEMENTED_ENDPOINTS`

2. **「没有一处会替你报错」是错的，而且错在**最**该有守卫的那两处**：
   - `app.ts:379` 是 `const impossible: never = routeHit` ——
     `Route` 加了一种 kind 而 `handleRequest` 没跟上 ⇒ **编译期就不过**（那段注释自己写着
     「漏分支 ⇒ 这一行编译不过」）；

     **等于** `IMPLEMENTED_ENDPOINTS`，`:71` 断言渲染进程暴露的方法集**恰好等于**
     invoke 通道集（同文件 `:85` 还有一发 canary：注入一个 `dbQuery` 后门，上面那条**必须**变红）。
3. **真正没人管的那个方向是**一个**具体方向，不是「处处危险」**：
   上面那几条判的都是「**有通道 ⇒ 端点必须在清单里**」（多一个会红）。
   反方向 —— 「端点已实现（`matchRoute` 有它、`handleRequest` 有分支、
   两张清单里有它）而**桌面侧没接线**」—— **没有任何断言**：
   `channelFor()` 对没接线的端点**返回 null 是设计行为**

   而 `:134` 那条测试 `channelFor("GET /replay/:taskId")` 断言的正是 null）。
   ⇒ 后果说得准一点：**HTTP 那一条能通、curl 得到 200、测试全绿，而桌面应用里点不到它**
   —— 不是「哪儿都不报错」，是**恰好在这一条边上不报错**，而这条边正好是
   「我以为接完了」与「接完了」之间唯一那条缝。

所以真实的接线代价是（**按声明处数**，不是按 grep 命中数）：
`Route` 联合 + `handleRequest` 分支（这两处**编译期**逼你成对改）、
`contracts/src/api.ts:29` 与 `contracts/src/api.ts:55` 两张清单、`ipc-surface.ts` 的 `CHANNEL_SPECS` 条目
+ `INVOKE_METHODS` 映射 + 渲染侧那个方法（这三处**有断言**，漏了会红）、
以及 `preload/api.ts` 那层转发。
**「漏了不报错」的那一格只有「已实现而未接桌面」这一个方向**，
而它今天**不在任何断言里** —— 这句话比「七处都不报错」小得多，
**也正因为小得多，才是可以被拿来当决策依据的那一句**。

> 这一处值得单独留着的原因是：**我把一个估出来的数标成了「量过的」**，
> 而它一旦带上「量过的」字样，下游（INDEX、下一次读到它的我、任何按它排期的人）

> 是**它让下一个错误也免于被检查**（0029 §3 那个恒真判据、本篇 §8 那个编造出来的 0012 第十节，
> 三个形状的共同点都是**证据的样子代替了证据**）。

> ⚠ 上面两处提到那个编造的引用时，**刻意写成「0012 的第十节」而不是坐标形态**。
> 这不是躲守卫（守卫对坐标形态的判据是「目标必须真实存在」，而它确实不存在，
> 用【篇号 + 节号】那种可提取的形态写出来会当场红 —— 那一红是**对的**，它拦的正是这类引用）。
> 走非坐标形态的理由是另一条：这一句的**用途是叙述「我编过什么」**，

而其中**校验那一条**的安全性质比其余都硬：
它必须与桌面端走同一条鉴权（`http/auth.ts` 那个 HMAC），并且像签票那条一样**只开回环** ——
**远程能自校验绑定 = 任何人可以自己给自己发一个 CEO 身份**，

是**「CEO 身份由谁在人海里认出来」这个产品动作要不要变成一个界面功能**。
它卡的是「手机上批一次」这句话仍然没有主语，同 0027 §7 那一格。

## 10. 强度

**测试**：`packages/hub/test/bindings/im.test.ts`，**74 发 / 14 suite 全绿**。
骨架是**每一发判据跑两条路**：模块那条（走 `requestBinding` 等）+ DDL 那条
（**手搓裸 SQL 绕过模块**）。后者存在的理由是 §7 —— 如果只测模块，
本篇三条探针结论一条都测不出来，而「模块自己写得对」正是被 §7 否掉的那个假设。

每一发**同时带 `legal` 与 `illegal` 两半**（合法写入必须过、非法必须拦）。
理由：**一个恒拦的触发器与一个判得对的触发器，在只测拒绝的测试文件里完全一样。**

守卫几条，每条都在守「守卫本身」：

- `EXPECTED_TRIGGERS` 按**名字点名全部 8 条**（硬编码清单）。
  删一条 ⇒ 红（「有人删了一条判据而测试还绿」）；加一条 ⇒ 不用改这里。
- 「本模块不许 import `src/channels/` 与 `node:http`」+
  「`im_bindings` 不许出现在别的 src 文件里」，
  并配一发**反向对照**：扫描通路**真的读到了东西** ——
  否则前一条恒绿（0020 §2 那个「证据强度分三档」在这里的落点）。
- 迁移文件头的注释剥离函数带自检：剥掉的字符数 > 500 且骨架还在
  （一个把整段 SQL 一起剥干净的 `stripComments` 会让所有「SQL 里不许出现 X」的断言恒绿）。
- ⚠ **我自己写的一发恒红断言**（比恒绿更贵，因为它看起来像有问题的是代码）：
  第一版用 `expect(REQUEST_BINDING_SQL).not.toMatch(/verified[^\n]*\?/u)`
  想证明「verified 是字面量不是参数」，而那个 `?` 命中的是**旁边 `created_at` 的参数**
  ⇒ 无论怎么修都红。改成对整条语句 `toBe()`。
  **一个恒红的断言与一个恒绿的断言一样没用，只是红得更像有问题，所以更容易被放宽。**
- 版本号清单在 `packages/hub/test/db/migrate.test.ts` 里是**硬编码**的（那是刻意加的摩擦：
  加一个迁移必须动一个测试文件，否则「加了迁移而没人知道」在别的仓库里是零成本的）。
