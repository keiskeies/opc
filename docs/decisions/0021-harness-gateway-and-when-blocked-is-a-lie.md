# 0021　Harness Gateway 与四层防护，以及「拦住了」这句话什么时候是假的

- **状态**：已定案（Task 5.1 + Task 5.2 的产出；本篇记实现里被自己推翻的判据，以及一条**该由 CEO 拍的取舍我先把实现做出来了**）
- **产出**：`packages/contracts/src/harness.ts`（契约）、
  `packages/hub/src/harness/safety.ts` + `test/harness/safety.test.ts`（四层防护，Task 5.2）、
  `packages/hub/src/harness/gateway.ts` + `test/harness/gateway.test.ts`（Gateway 与能力闸门，Task 5.1）

  ① 判据的**两侧必须来自不同来源**（我第一版有两处是自己和自己比，永远放行），
  ② 「拦下来了」与「看见了」在审计里必须是两个不同的值（我第一版把两者写成同一个 `blocked`）。

## 0. 先说清楚这一轮的产出**没有**接上线

`callHarness` 在生产里**零调用方**。这条是本仓的甲档强度（0020 §2）：
`grep -rn 'callHarness(' packages/*/src` 只命中定义处那一个文件，而全仓其余命中**全部**在
`packages/hub/test/harness/gateway.test.ts` 里（命中条数我故意不写死：那是个会随我后续加用例
单调上涨的计数，0019 记过同一条纪律）。
所以「每一次 harness 调用都过了这四层」当前成立的强度是
**「凡是走 Gateway 的都过了」+「今天没有任何 harness 调用」**。
接上线要等 Task 5.5（真 SDK）与路由（Task 5.3）。这一格不写清，后面读代码的人会以为系统已经在守了。

## 1. 两处自比判据（本篇最该被抄进 code review 清单的一条）

我第一版里有两个判据是**结构上恒真**的，而且都能通过当时全部测试：

```ts
sandboxTierBlock(req.sandbox, req.sandbox)                       // 永远 ok
forbiddenFlagBlock({ baseline: req.forbiddenFlags,
                     effective: req.forbiddenFlags, args })      // 「缩短」那一支永远走不到
```

它们比一般的漏判更坏，因为**代码看起来是在判**：函数名、注释、返回码、审计载荷全对，
调用点也真的在调用，测试也绿 —— 唯一的问题是**被比的两边是同一个值**。
本仓记过的那一族是「判据不存在」，这一族是**判据存在而语义是空的**，
后者没有任何自动化能抓 —— 这一轮新写的 harness 测试**一条也抓不到它们**，
因为那些用例全都只喂一个档位值（判别力为零，见下面那条）。

修法不是加测试而是**让默认值不可能**：`GatewayDeps.grantedSandbox` 与 `grantedForbidden`
是**必填**，且注释里写明「给了默认值就等于把自比换个写法」。
判据要的两件事只能由调用方交出：岗位书授权的档位、岗位书声明的基线禁止项。
拿不到就说明调用方还没接岗位书 —— 那该在装配期炸，而不是在运行期静默放行。

**能被抓到的那条测试长什么样**（`test/harness/gateway.test.ts`）：

> ⭐ 提级判据【不是自比】：**同一个请求**在两个不同的授权档位下各跑一次，要求一个过一个拒。

只喂一个档位的用例对这类 bug 的判别力是**零**，这一点值得单独记：
写「授权 read-only、请求 workspace-write ⇒ 拒」看着像在判提级，
实际上代码里根本没有第二个值参与，所以那条用例**恒过**。
必须有「同请求 + 不同授权 ⇒ 结论翻转」这一对，才是那条判据的活样本。

## 2. 只有 `tsc` 报得出来的那一类：`costReportSchema` 忘了 transform

契约里 `costReportSchema` 第一份版本是**裸的 snake_case schema**，没有 transform，
而 gateway 一路按 camelCase 读 `cost.spentCents`。两边只可能对一边。

它**没有**变成假绿只因为我在同一个文件里同时写了映射与读取，`tsc` 报了 `TS2551`。
如果那一格当时的类型是 `number | undefined`，读取处写的是
`cost.spentCents ?? 0`，那么读一个不存在的属性给 `undefined`、被 `?? 0` 吃掉，
得到的是**一条「这次调用花了 0 美分」的审计记录** —— 而预算侧全按美分对账。
所以这不是「编译错误顺便修一下」：**`?? 0` 写在一处读跨包字段的地方，
就等于把类型错误兑换成一条看起来合法的假数字**。

同一类形状本篇另有两处，都是同一个模式（一个函数在两个调用点上语义相反 / 覆盖面为空）：

1. `sandboxTierIndex` 把不认识的值排到**最严档**。对**请求侧**这是多拦（方向正确），
   对**授权侧**恰好是少拦（最严档 = 任何请求都不算提级 = **全放行**）。
   同一个下标函数服务不了两个相反的期望方向。
   修法是 `sandboxTierBlock` 先单独判「两侧是不是已知档位」⇒ 新码 `sandbox_tier_unknown`。
   授权侧的实际来源是岗位书 YAML / 路由表，是**读进来再转型**的，`SandboxTier` 类型拦不住一个写错的名字。
2. `event_after_finish` 第一版写在 `finished` 分支**里面**，于是它只能在**第二个 finished** 上触发；
   `finished` 之后来一发 `usage` 会被静默收下并**覆盖已定下的消耗**。
   判据提出来放到 `for await` 的第一行，现在覆盖每一个事件。
   （测试第一版恰好用的就是第二个 `session_started`，撞上的是 `duplicate_session_event`，
   所以那条用例**测的是另一件事而它自己不知道**。）

## 3. `Bash(git:*)` 对任何真实调用都不生效（测试把我抓住的那条）

规格 §4.1.3 那份 YAML 里白名单同时有两种形状：`"Edit"` 与 `"Bash(git:*)"`。
我第一版把参数 `JSON.stringify` 之后比前缀，于是 `{command:"git status"}` 变成
`{"command":"git status"}` —— **以 `{` 开头**，永远不以任何命令名开头。

失效方向值得单独看：它不是漏放，是**全拒**。
后果不是安全洞，是**岗位书里那条授权变成废纸**：接上真 harness 的那天所有人看到的是一屏
`tool_not_allowed`，而最省事的修法必然是「先把白名单放松一下」——
于是**一条写不通的收紧，最后换来的是一次放松**。这类账最终都往宽松方向结。

修法：新增 `argCandidates()`，对象参数按已知键（`command`/`cmd`/`script`/`args`/`path`/…）
各取值作为候选，再把整份 JSON 当一个兜底候选。
**这条是测试逼出来的**：`safety.test.ts` 里那两条 `Bash(git:*)` 用例最初是红的（我先写测试断言
「`{command:"git status"}` 应该被 `Bash(git:*)` 放行」，代码不同意，于是代码错了）。

## 4. ⭐ 事后审批会留下一条**真的但含义是假的**记录（本轮最重要的一条）

工具调用有两条路进 Gateway：

| 路 | 时机 | 我们有没有否决权 | 该做什么 |
|---|---|---|---|
| `onApproval` 回调 | 适配器动手**前**问（Claude 的 `canUseTool`） | **有** | 问人 |
| 事件流的 `tool_call` | 适配器把它的动作**通报**给我们 | **没有**（已经做了） | **绝不问人**，记 `approval_too_late` |

第二行右列是我这一轮想得最久的一件事。直觉做法是「两条路都推审批卡片，反正是同一个判据」，
而它会产生一条**「CEO 批准了这次 `rm -rf`」的审计记录，而那次 `rm -rf` 在他看到卡片之前就跑完了**。
记录本身是真的（他的确点了同意），它表达的含义（有人事前把关过）是假的。
`§12.7` 第四层点名要「谁批准了什么」，而如果那一格被读成「事前有人看过」，
**审计越全，失真越可信** —— 一句空话没人当证据，一条带审批人、带时间、带参数的记录会被当证据。

所以我选了那个看起来更没用的方案：事件流那一路**不问人**，只记一条
`approval_too_late`（新码），且**不往 `approvals` 那一格里写任何东西** ——
那一格从此只装「真的问过某个人」的条目。

顺带被这条设计修掉的两个问题：
- **同一次调用被问两次**（回调问一次 + 事件流又问一次）⇒ 一张卡片变两张、审计多一行。
  修法：`verdictCache`，键是 `工具名 + 参数 JSON`，判定恰好做一次。
- `blocked_attempts` 翻倍。修法：**从缓存派生而不是单独累加**。
  口径因此是「**几个不同的动作被拦**」，不是「几行审计」—— 同一个动作被拒后又出现在事件流里
  会有**两行**审计（那是另一件事：我们拒了而它照做，`proceeded_after_verdict: true`），
  而那一格仍然算一个。**两个口径都留着**：行数在 `events` 表里数得出来。

## 5. ⭐ 一条该由 CEO 拍的取舍，我先把实现做出来了（请复核）

`Stop hook` 让我自行按产品设计的出发点判断，所以这一条我做了决定，但它**是**一个
产品级取舍，写在最显眼处请 CEO 复核：

> **观测到一次未授权的工具调用 ⇒ 中止整次调用**（新码 `violation_aborted`）。

判据不是「那一次调用被我们挡住了」—— 它已经发生了，我们挡不住。
中止的是**它之后还没发生的那些动作**。依据分两半，一半我能证、一半不能：

- **能证的那半**（已钉成用例，见 `gateway.test.ts` 那条「中止真的触发适配器的清理钩子」）：
  `for await` 里 `return` 会调用异步迭代器的 `return()`，于是适配器侧的 `finally` 会跑。
  这是语言语义，我用一个不依赖任何 SDK 的生成器复算过（`finally` 计数 = 1）。
- **不能证的那半**：适配器在那个 `finally` 里能不能真的把 harness 停下（SDK 的 cancel 语义、
  以及「已经发出去的动作会不会被撤回」）。我**不打算**断言「三家 SDK 都是 abort/cancel 形状」——
  离线状态拿不到任何一家，而那句话正是本篇 §9 一路在防的形状：**按惯例补一条我没测过的外部事实**。
  修法在 Task 5.5：接上真适配器，让那半截变成可观察的。

为什么不能「记一笔然后继续」：继续消费会让这次调用带着**越权动作的产物**
（工作区外那个文件、被推上去那个分支）以 `ok:true` 返回，于是门控与独立审阅拿到的是一份
**被污染而看起来完全正常**的产出。失败会被重试、会被人工介入；
污染会被当成证据继续往下游走（§14.4 红线一同一方向）。

代价说清楚：中止会丢掉这次调用的**全部**产出，包括合法那部分，一次任务失败对 CEO 是一次停顿。
我按**「宁停不污」**判的。如果 CEO 认为「保住半截产出 + 打个污染标记」更好，
改的是这一个 `return`（`gateway.ts` 里那一段注释已经写明理由），不用动判据。

⚠ 有一条我**没做**，因为做不了：中止之后没有真正的 kill 通路。
真实适配器要能把 `return()` 翻成 SDK 的 cancel 才算真停住 —— 那是 Task 5.5 的活。
今天这条中止只是「我们不再消费、迭代器正常结束」，**在真适配器上等于什么，我离线状态无从核验**。

## 6. `prevention: enforced | observed_only`：`status: "blocked"` 是个会骗人的词

`blocked` 读起来像「拦住了」。但在一条**声明它不会问我们**的适配器上
（`capabilities.toolApproval=false`，或策略 `never` 而它按 never 就不问），
我们整场**一次否决权都没有**，事件流里那些 `tool_call` 全是事后通报。
此时把那一行读成「防住了一次」，就是 §12.7 第四层最怕的那种失真：**审计存在、数字对、含义是假的**。

所以那一行多一格 `prevention`，判据只用**能推出来的部分**：
`adapter.capabilities.toolApproval && approvalPolicy === "on-request"` ⇒ `enforced`，其余 ⇒ `observed_only`。
`observed_only` **不是**「一定没拦住」，而是【我们无从知道自己有没有拦住】——
而审计里「不知道」必须有它自己的值，不能借用两个它无法表达的确切值。

这一格的真正用途在 Task 5.3 路由：一份带 `forbidden_flags` 且会碰不可逆工具的岗位书，
不该被路由到 `observed_only` 的那一家。

## 7. 两个拒绝码必须分开的那两对

- `approval_handler_missing` vs `approval_denied`：一个是**缺陷**（装配漏传回调），
  一个是**正常业务结果**（有人审过说不了）。混成一个码，「审批系统根本没接上」
  在审计统计里就与「CEO 拒了」同形。
  我第一版的 `requireHandler()` 更糟：它在缺回调时**自己编一条** `approved:false` 交回适配器，
  于是那看起来像一次【由 gateway 做的拒绝】，而真相是【根本没有审批者】。
  现在缺回调那一路把 `undefined` 一路传到 `approvalBlock`，由它定性。
- `duplicate_session_event` vs `event_after_finish` vs `no_result`：三种不同的适配器坏法。
  合成一个 `adapter_protocol_error` 等于把「哪种坏法」这个唯一有用的信息扔掉 ——
  第一种是【会话身份不确定，恢复会接错】，第二种是【结果之后还有事，审计与执行不一致】。
  （但**第二个 `finished`** 与 **finished 后的一发 `usage`** 我**合并**成了
  `event_after_finish`：那两者讲的是同一件事，而码表里多一个近义码只会让统计口径分裂。
  —— 分不分码的判据是**修法是否不同**，不是**事件是否不同**。）

## 8. `blocked` 那一路的返回码为什么不透出 safety 的码

`safety_blocked` 而不是把 `tool_not_allowed` / `forbidden_flag` 直接透出：
两套码回答的是**两个维度**的问题 —— `GatewayRejectCode` 答「这次调用跑了吗、为什么没跑」，
`SafetyBlockCode` 答「是哪一层拦的」。透出会让按码统计调用结果的人看到六个不同的「没跑」。
具体那一层**不丢**：它在同一批 `unauthorized_attempt.kind` 里。

对照 §7 那两处：那里我**合并**了码、这里我**拒绝**透出，判据是同一条 ——
**同一个维度有两份词表就是重复定义（合并）；两个维度共用一份词表就是统计口径污染（分开）。**

## 9. 我自己这一轮写错的（按被抓顺序）

1. **两处自比判据**（§1）。最贵，因为不可测。
2. **`costReportSchema` 忘了 transform**（§2）。靠 `tsc` 侥幸没变成假数字。
3. **`toolAllowed` 前缀比 JSON 串**（§3）。方向是「全拒 ⇒ 下次有人放松」。
4. **`sandboxTierIndex` 一个函数两处用、两处期望方向相反**（§2）。
5. **`event_after_finish` 覆盖面为空**（§2）。
6. **`wanted` 算出来不用**：预算那条只判了 `b.over`，于是
   「`max_budget_usd` 写成 $20 而总额度只有 $10」在额度尚有余量时能放行。
   「变量算了不用」在这里不是浪费，是**一个看起来在判而实际没判的断言**（与 §1 同族）。
7. **脱敏用错函数**：payload 对 `string[]` 用了 `redact`。`redact` 只认对象键名，
   对数组里的字符串**原样返回** ⇒ 一条「调过脱敏而 `--token sk-…` 原样入库」的记录，
   而 `events` 是 append-only，删不掉。改成 `redactArgs`（按 `--token X` / `--token=X` 两种形状）。
   这一条我**把两种行为都钉成了用例**（包括「用错函数确实静默失效」那半边）。
8. **`requireHandler` 编造审批者**（§7）。
9. **`finish()` 一个函数干两件事**（写库 + 决定返回什么），于是必须用 `null` 表达「这次不干第二件事」，
   而 `null` 恰好是本文件一路在防的那个值（「没记」与「记了但是空」混在一个编码里）。拆成 `finish` / `finishReject`。
10. **`HarnessAttemptPayload.kind` 手抄了一份 safety 的码表** —— 同一维度两份词表（§8 那条判据的反面教材，
    我自己刚写完那条就在同一轮里犯了）。改成 `kind: SafetyBlockCode`。
11. **三条零判别力的断言**：`expect(at[0].detail).toBeTruthy()`（写错的 target 也非空）、
    `expect(v.ok && "无").toBe(false)`（对任何对象都假）、
    「【规格】§9.1 与【规格】§12.7 同源」那条**只断言了 needsApproval 一侧**（与被测函数是同义反复）。
    第三条我**先按自己写的变异实验验了一遍，而那个变异本身是惰性的**
    （`String(o.args)` 对对象给 `[object Object]`，注入的那条判据永远走不到）——
    于是「测试没红」当时**什么也没证明**。换成生效的变异（`argText(...).includes("refactor")`）之后才真的红。
    **这条是 0006 §7「否定性主张只能由变异实验证明」的一个新变体：
    一个惰性变异比不做变异更糟，因为它给了一条已经没判别力的断言补上一张「验证过」的标签。**
12. **四条测试编码的是旧行为**（记了就继续跑）。改代码之前我先确认新行为更对（§5），
    然后改测试，并把理由写在测试里 —— 反过来做（改代码迁就已有断言）会把 §5 那条取舍悄悄否掉。
13. **两条用例假设了不存在的约束**：以为 `diff_hash` 有 sha256 形状校验（它是
    `z.string().nullable()`，**没有任何形状约束**，所以 `SHA256_RE` 那一条我在 evidence 侧见过的
    约束在这里并不存在），以及「四个能力缺口」那条忘了显式写 `approval_policy: "on-request"`
    （schema 没有默认值，我那个 `req()` 夹具给的是 `never`，于是第一条缺口根本不成立）。
    两条都是**按「这类字段一般会有校验 / 这类开关一般有默认值」补的事实** ——
    0020 §5 第 5 条（我给 `role_id` 补了一条仓库里不存在的正则）同一形状第二次现形。

## 10. 这一层证不了的（写在这里而不是等人踩）

1. **「审批被拒 ⇒ 动作没发生」是假设，不是结论。** fake 适配器可以被写成拒了照跑（有用例），
   也可以被写成老实不动手（也有用例）。真实 harness 是哪一种，是它那侧的语义，
   离线状态**无从核验**（本机无网络，依赖目录里只有 `typescript` / `zod` / `@types` / `@opc`，
   拿不到三家 SDK）。所以 `proceeded_after_verdict` 那一格与 §5 的中止都只有在 Task 5.5 才能被验证。
2. **`needsApproval` 对真实工具参数形状多半判成「默认不可逆」。**【规格】§9.1 那张表全是人类语言子串，
   而 harness 传进来的是 `{"path":"/repo/x.ts"}`。方向正确（宁可多问），

   这条我钉成了用例（`safety.test.ts` 那条 ⭐）而不是修掉 —— 修它需要一份 harness 工具名表，
   而那份表该由路由（Task 5.3）与岗位书一起定。
