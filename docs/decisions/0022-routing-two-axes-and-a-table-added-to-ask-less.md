- **状态**：已定案（Task 5.3 的产出；本篇记的是这一轮我自己推翻的四处，以及一次
  **把 0021 钉住的断言翻过来**的改动 —— 那种改动最容易悄悄做错，所以理由写在最显眼处）
- **产出**：`packages/hub/src/harness/routing.ts` + `test/harness/routing.test.ts`（37 条用例），
  另外动了三处已有文件：`policy/engine.ts`（`KIND_TIERS` 加 harness 工具名）、

  真正改变系统行为的是那张加进 `KIND_TIERS` 的表，而它是本仓第一次
  **为了少拦而改一张安全表** —— 所以它的风险边界比表本身更需要被写下来。

## 0. 这一层同样没接上线（0021 §0 同一格，不重复论证只报状态）

## 1. ⭐ 第三处自比判据：它长在**路由层**，而且是我自己新写的

0021 §1 记了两处（`sandboxTierBlock(req.sandbox, req.sandbox)` 与
`forbiddenFlagBlock` 的两侧同源）。这一轮我在一个新地方**又造了一处**：

> 路由既要交出「这一段想用的档位」，又要交出「岗位书授权的上限」。
> 如果两侧都由路由查**同一张** `CATEGORY_DEFAULTS` 得到，
> 那么 gateway 那条「档位不得提级」在所有**路由来的**请求上结构性地永不触发。

这一处比前两处更隐蔽，因为**它不是写错的代码，是一个省事的写法**：
「反正档位是路由算的，上限也让它算好了」读起来完全合理。
它躲过 0021 那次的教训（那次我记住了「被比侧要必填」）是因为
`charterCeiling` 我确实写成了必填 —— 但**必填**只保证调用方交出一个值，
不保证那个值不是从同一个来源抄来的。

所以这一层的做法是把两个名字**在类型里分开**并各写一句来源：
`RoutePlan.charterCeiling`（岗位书 `harness_defaults.<id>.sandbox`）
与 `RouteStage.sandbox`（类别表算出来的）。
**能抓到的还是同一形状的测试**（0021 §1 那条纪律现在有了第二个活样本）：

> ⭐ 同一个任务在两个不同上限下各路由一次，要求结论翻转
> （`read-only` ⇒ 拒、`workspace-write` ⇒ 成、`danger` ⇒ 成）。

变异实验做过（三条，每条都先验证变异**真的打上去了**才读结果 —— 见 §5）：
把上限比较改成自比 ⇒ 2 红。

## 2. 一次「加表是为了少拦」的改动，以及它的风险边界

`KIND_TIERS` 加了 9 个 harness 工具名（`read`/`grep`/`glob`/`websearch`/`webfetch` → read_only；
`edit`/`write`/`multiedit`/`notebookedit` → reversible）。

**这是本仓第一次为降噪去改一张安全表。** 它推翻的是我自己上一轮钉住的东西：
Task 5.2 的 `safety.test.ts` 里有一条 ⭐ 用例断言
`needsApproval({tool:"Read", args:{path:...}}) === true`，
注释写着「降噪的正确改法是把工具名映射进 KIND_TIERS，而**不是**在 safety 里再写一张表」。
这一轮就是那次。**断言翻过来了**，而这不是「测试碍事所以改掉」：
被钉住的是「那张表还不存在」这个前提，前提变了结论就得变（0021 §9 第 12 条讲的正是这个方向）。
改的时候我把「它为什么现在可以翻」写在了用例里，而不是删掉了事。

**风险边界**（这是这一节真正要留的东西，不是那张表）：
命中 `KIND_TIERS` 之后，**不可逆文本表仍然先判**（`classifyAction` 里那段
「自报的 kind 盖不住危险描述」是既有代码，我没动它）。所以：

- `Write` 的参数里写着「改完直接发布上线」⇒ **仍然** irreversible（用例钉住）；
- 没被列进来的名字（`Bash`、任何厂商工具）⇒ **仍然**默认 irreversible（用例钉住）。

也就是说这张表能改变的只有「**光看名字**时按哪一档」。
于是每个取值断言的是一件**与「这个名字到底存在于哪家 harness」无关**的事：
「**若**有这么个工具，它光看名字的效果是只读/可改工作区」。
名字写错（那家其实没有 `Grep`）零代价；档位写错（把写工具写成 read_only）才有代价 ——
所以表里每条都带一句效果依据，而不是只写名字。

`Bash` **故意不进表**：`git status` 与 `git push --force` 是同一个工具名，
光看名字什么都判不出来，只能由参数文本决定。

还有一条同源的用例：`Read`/`Write`/`Edit`/`Grep`… 在 `needsApproval` 与
`classifyAction` 两处必须给出同一个答案。**它不测任何逻辑，它防的是
「有人在 routing 或 safety 里再写一张写工具表」**（0020 记过同一类错）。

## 3. `prevention` 从「审计里的一格」变成「路由的输入」，代价是它现在有两份

0021 §6 预告的就是这一步。这一轮它真的开始做决定了：
风险档 = `irreversible` ⇒ 需要 `enforced` ⇒ 候选里每一家都给不了 ⇒ **路由期就拒**
（`prevention_gap`），而不是运行时一次没人看见的自动批准。

顺手把那一份 ternary 提成了 `safety.ts` 的 `preventionFor`，gateway 改调它。
理由不是复用：**两处各写一份的话，加一项条件就会只加在一边**，
得到「审计里写着 enforced 而路由当初是按 observed_only 判的」——
那比两边都写错更难查，因为审计看起来是自证干净的。
用例钉的是「路由产出的那一格 === 直接调 `preventionFor` 的值」。

⚠ 但提出之后出现了一个我**没解决、只写下来**的问题：
`RoutePlan.prevention` 是**计划级**，`harness_call.prevention` 是**单次调用级**，
两者同名同形而**粒度不同**。它们会在一种情况下取到不同值：
风险档 = irreversible 时写段被抬到 on-request（那一次记 enforced）
而只读段照旧 never（那一次记 observed_only）。
我选择在类型注释里写清这个差别，而不是把它们强行统一 ——
因为「读代码的人会把两个同名字段当成同一个」这条我在 0021 §8 已经付过一次学费，
而**统一成同一个粒度**要么牺牲审计的问题（那一次有没有否决权），
要么牺牲路由的问题（这份计划该有否决权的段有没有），两个问题都是真的。

## 4. 风险轴：**只有收紧的那一半被实现，而这是设计不是遗漏**

【规格】§12.4 那张表没有说风险轴改变什么（它只说风险等级由架构师评审时标记）。
我给的口径是**只有一条作用**：不可逆档 ⇒ 非只读段的 `approval_policy` 抬到 `on-request`。

**放松的那一半我故意不做**（比如「风险低就跳过 verify 段」）。
理由不是保守：每一次「这次风险低所以少跑一段」都是在削【规格】§12.5 的步骤，
而声明风险低的那个主体正是被约束的那个主体。
所以 `risk` 不是「能不能少跑」的开关，要删步骤得改【规格】§12.4 那张表（= CEO 的事）。

代价说清楚：风险档读起来像一个能双向用的输入，而它只能单向用。
这条被钉成一条**逐段比较**的用例（低风险与高风险的段档位、只读性、发起方必须完全相同；
唯一允许变化的方向是 never ⇒ on-request）。

### 4.1 只读段**不**被抬（这一条是注释与实现不一致被抓出来的）

我第一版的代码是「risk=irreversible ⇒ **每一段**都抬到 on-request」，
而注释里写的是「只读段不抬，否则审批队列里会出现一张『可以 read 这个文件吗』的卡片」。
**注释承诺了实现没有的性质**（本仓在 `evidence/store.ts` 的 sha256File 上踩过同一次）。
这次是写完注释回头读代码时发现的，改完之后那条 ⭐ 用例才真的有对应实现 ——
变异实验第 3 条把那一支删掉，用例立刻红。

## 5. 三次变异实验，以及为什么这次每条都先验证「变异打上了」

0021 §9 第 11 条记过那次最贵的教训：**惰性变异比不做变异更糟**，
因为它给一条已经没判别力的断言补上「已验证」的标签。
所以这一轮三条变异都在脚本里带 `assert 变异生效`，打不上就直接失败：

| 变异 | 结果 |
|---|---|
| 上限比较改成自比（`indexOf(s.sandbox) > indexOf(s.sandbox)`） | 2 红 |
| 只读段闸门条件改成永不等（`tier === "definitely_not_a_tier"`） | 5 红 |
| 删掉「只读段不抬」那一支 | 1 红 |

三条都是**活的**变异。这条纪律现在的具体形状是：**变异脚本必须自己断言变异改到了字节**，
否则「没红」这句话仍然什么也没证明。

## 6. 我自己这一轮写错的（按被抓顺序）

1. **第三处自比判据**（§1），而且是在一个**新位置**（路由层，不在 safety 里）。
   「被比侧必填」这条纪律没覆盖它 —— 必填 ≠ 来源不同。
2. **注释承诺了实现没有的性质**（§4.1）：只读段那一条。
3. **两段不可达代码**。第一版在选完适配器之后又写了一段「这家没有审批回调就把 on-request
   降回 never」—— 上面的 `needEnforced` 判据与候选过滤已经让那两个条件不可能同时成立。
   它是本文件一路在防的那个形状：**一段看起来在做安全判断而永远走不到的分支**。
   留着它不是无害的：下一个人会以为路由有一条「降级适应」的路，
   而真要有那条路，`prevention_gap` 那条拒绝就得同时拆掉。删掉，并把
   「要求 == 实际」这条不变量钉成用例（钉住的是**哪种改法会破坏它**，不是现在的代码）。
4. **一条零判别力断言**：`expect(cond ? "same" : "tightened").not.toBe("loosened")` ——
   两个分支都不等于 `"loosened"`，对任何代码都真。这是 0013 / 0016 记过两次的那一族，
   我第三次写出来。发现的方式是回头读它在防什么，结果发现它什么都防不住。
5. **一条报错误的用例，而错的是我**：我断言「上限不足时报错误点名 [implement]」，
   实到 [reproduce]。五段里**第一个**需要 workspace-write 的正是复现段（它要写用例文件）。
   代码报的是第一个越界的段，口径对；我按「修复段才需要写」想，
   那是【规格】§12.5 那段流程**读漏了第 3 步**。
   （这一条与 0021 §9 第 13 条同一形状：**按印象补事实**，只不过这次印象来自自家规格。）
6. **一条指向不存在小节的引用**：我在注释里引用 0021 的一个**带小数的子小节**，
   而那一节底下是编号列表、没有子小节。`comment-citations` 守卫直接把我抓红了 ——
   这是那台守卫第一次在我**写完的当下**而不是事后起作用（0021 §9 第 13 条那次是我给
   `role_id` 补了不存在的正则，同一族：都是**按「这类文档一般有子小节 / 这类字段一般有校验」
   补的事实**）。
7. **一次实验性分支的判定顺序**：`experimental` 那一行今天没有适配器，
   所以它必然同时命中「找不到合格候选」。第一版先跑候选过滤，
   于是报错说的是「找不到适配器」，而真正的原因是「开关没打开」——
   当事人会被引去接一家根本没打算接的执行器。**同一个输入命中多条判据时，
   报哪一条取决于判定顺序，而顺序是一种语义**，不是一种实现细节。
8. **`sandboxTierIndex` 的一个新变体**：路由里遇到「上限是一个没听过的档位」时，
   `indexOf` 给 -1 会让任何段都不越界 ⇒ 全放行。修法是按最低处理（拒），
   同时**不**在这里报 unknown（那是 gateway 的 `sandbox_tier_unknown` 的活）：
   两处都判会漂移成「路由放行而 gateway 拒」这种看起来像随机故障的组合。
   0021 §2 第 1 条讲的是同一个函数在两个调用点方向相反；这是它在**第三个**调用点上的表现。

## 7. 这一层证不了的（写在这里而不是等人踩）

1. **「只读段不许写」判的是观测到的那一发，不是拦住的那一发。**
   `--sandbox read-only` 交给 harness 执行；如果它那侧实现有 bug，
   这一段闸门只能在**事件流里看到那一发 tool_call** 时报违规 —— 也就是**已经写了**。
   两层都留着（【规格】§12.7 表头说的「叠加」），但**外层那一层不是预防**。
   与 0021 §10 第 1 条同一状态，也要等 Task 5.5。
2. **`readOnlyTools` 靠名字里的动词剔工具**。它对 `apply_patch` 这种形状有效（用例钉住），
   对「一个不含写动词的写工具」（假想的 `Fs.Modify`）**无效** ⇒ 只读段里放行它，
   只读闸门仍会按参数判它（两道都在）。
   反向的误剔（把 `ReadonlyCopy` 剔掉）代价是「那一段少一个工具」，会报错而不是静默越段。
3. **`branchIsOnMain` 只认 `main` / `master`**。`release/*`、`trunk` 我不假装认得 ——
   列一条离线状态核验不了的约定，会换来「在那个仓里照样放行」。
4. **`CATEGORY_DEFAULTS` 是我按【规格】§12.4 那张表 + Task 5.3 那句「五段」写的**，
   而【规格】§12.5 的六步里第 1 步「预检：工作区是否干净，**预检失败直接打回技术总监，
   不调用 harness**」**没有**成为一段。它是**故意的**：预检不是 harness 调用，
   把它列成一个 `precheck` 段会让人以为它由 Gateway 执行。
   今天它没有任何实现点 —— 这一格缺，写在这里而不是假装做了。
