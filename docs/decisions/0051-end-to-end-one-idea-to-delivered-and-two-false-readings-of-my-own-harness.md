## 1. 分段各自的绿盖不住的是【接缝】，而我是在探针里撞到的，不是想到的

那一发用真装配：任务由 `real-deps.insertTask` 建（生产唯一建任务入口）、章程卡由
`engine/charter.ensureCharterCard` 起草（不是手搓一张卡）、`dispatch` 的 deps 出自
`engine/runtime.makeRuntime`（`loadTask` / `lastProducer` / `rejectionCount` / `ceoApproved` /
`modelFamily` / `onCost` **全是生产 SQL**），只替换 `runTurn` 那一格（导演出每一轮的嘴），
CEO 那几步走 `approveCard`，每一轮之后按 `driver.ts` 那个形状调 `rt.recordTurn`。

**撞到的第一发探针死在第二步**：任务落地时如果把 `assigned_role` 写成 `ceo`，第二轮 dispatch 就被
**人类席位**那道门挡死（`dispatch.ts` 的守卫：任务挂在 CEO 手上 ⇒ 不起子进程扮演 CEO），
而 `dispatch` / `approve` / `driver` **三边各自的测试全绿**。
这不是假设 —— 本篇 §5 的 M6 把 `approveCard` 的原值回填拆掉，撞出来的正是同一句报错。
**这一格就是「端到端」这三个字唯一买得到的东西**：三段各自自洽，接起来走到一半没人接手。

第二发探针死在第四步：汇报树做成 `ceo ← director ← dev` 时 `intake` 是**叶子**，
`DECOMPOSING` 那一格 handoff 给 dev 撞 `handoffGate` 的 `not_downstream`。
所以图是 `ceo ← intake ← director ← dev` 三层 —— **三层是「到顶」这条路能走完的最小形状**：
`director` 通过之后还有 `intake` 要接手，`intake` 通过之后上级才是 CEO 本人，
于是 `planEdge` 的 `topmost` 分支与「上级是 CEO 本人」那条分支**各走一次**，少一层只测到其中一条。

## 2. ⭐ 上一条提交里有两处是我写假的，而两处都在我刚编辑过的文件里

写这篇之前我回去核 0050 引的证据（因为要在 §6 里引用它）。两处：

**(a) 一句全仓范围的反命题是假的。** 0050 写着 `budgets.limit_cents`「全仓**没有任何一处**读它做判定」，

| 读它的人 | 拿它判什么 | 生产可达 |
| --- | --- | --- |

**也就是说「行号对、符号名错」这类错，本仓的文档守卫结构上抓不到**：
它防的是行号漂移（那一行不再是这句话），防不住我把两个都在文件里的名字接错。

**(a) 的可迁移形状**：全仓范围的反命题（没有任何一处 / 唯一 / 全都）不能用「我 grep 了我关心的路径」支撑。

- **状态边我以为 9 条，实测 11。** `EVIDENCE_SUBMITTED → IN_REVIEW` 那一对自动补格
  是**每次向上 pass 各发一次**（dev 交一次产出、intake 再交一次），不是一个任务一次。
  我现在把那 11 条**逐格写在断言旁边**，而不是留一个数字。
- **CEO 那一步我以为会把 `assigned_role` 变成 ceo。** 不会 —— `approveCard` 是**原值回填**，
  一次「升给 CEO 看」不是一次组织分配（0047 §1）。这一格由**一条断言**守着
  （`role() === "intake"`），不是我口头承诺。

另外三发是**断言的形状**而不是数字：

- **每轮的不变量是「要么推进，要么交到人手上」**，不是「必然推进」。
  我第一版写的是 `expect(r.moved).toBe(true)`，在 B 发**合法地红了** —— 同源豁免那一轮**就是不推进**。
  真的空转是「既没推进也没建卡」：钱花了而屏幕上什么都没有（0050 §6.1 那一族）。
- **留痕归在谁名下**（`harness_calls.agent_role`）按 0048 §4.1 量出来的口径断：
  它是「这一轮跑完之后 `assigned_role` 的值」，换人时是接手人、升到 CEO 那两支是产出方自己。
  只断**条数**挡不住角色记错 —— 五条全记成 `dev` 也是 5 条，而查账的人会以为每格都是 dev 在干活。
  排序用 `created_at` 而不是 `id`：**探针里 `id`（`randomUUID`）碰巧和插入顺序一致**，那不可依赖。
- **广播与 events 表两个集合相等**，而不是「广播数 > 0」。
  总线包了一层**只为抄一份 seq**，每一发都原样转给真 `InMemoryEventBus`（两条守卫照旧参与）。
  ⚠ 不能 `for await` 那个订阅：它是一条活着的流，队列空而没 close 时 `next()` 一直等（`bus.ts:256`），
  在同步推进的测试里会挂住。

## 4. 我自己在那一发里犯的四个错（每一个都是「绿灯下的错」）

1. **轨迹漏格子**：点击那一支忘了往轨迹里 push，于是「点掉一张卡」这一步在轨迹里不存在。
2. **不变量要错了**（§3 那条 `moved`）。
3. **章程那一轮的钱没落账**：我给 `ensureCharterCard` 传了一整套 deps 而**漏了 `onCost`**，
   少的不是近似值而是整整 3 美分，而两侧各自全绿。修法是把 runtime 给 dispatch 的**同一个函数**传过去。
   **这一条后来成了变异 M7**（把那一行注掉 ⇒ 红 2）。
4. **`expect(r.moved)` 之外我还写过一句「豁免那跳轨迹里会出现两次同一格」** ——
   那是我对 B 发的**预期**而不是观察。观察是轨迹相同、点击多一次（§3）。

**还有第五个错，它不在测试跑出来的结果里**：手工按 `tsconfig.base.json` 那套口子单查这个新文件
（`test/` 不在任何 tsc 程序里，而 `--experimental-transform-types` 只剥类型**不检查** —— 0007 记过），
**红 4 条**，全部真实：

- `Object is possibly "undefined"` **×3** —— `.get()` 返回 `T | undefined`、`pending[0]` 是索引访问
  （`noUncheckedIndexedAccess`）。运行时那一行**确实拿到了行**，所以测试跑得过而类型不通过。
- `onCost: rt.deps.onCost` 不合法 —— `DispatchDeps.onCost` 是**可选**的，而
  `exactOptionalPropertyTypes: true` 下 `{onCost: undefined}` 不是合法的对象字面量。
  **这一条恰好指着我 §4 第 3 条那个错**：我为了让 `onCost` 接上而写的写法本身在类型层是坏的。

第 4 条改成生产装配那种形状（`...(x === undefined ? {} : { onCost: x })`）。
三处 `undefined` 用**显式判一次并抛**而不是 `!`：那个 `!` 在这里确实安全，
但它把「为什么安全」交给读者脑补，而这一发文件从头到尾的原则是**安全的那一步也要写出来**
（`onlyCardId` 那个函数就是这么来的，它旁边那发断言已经判过「恰好 1 张」）。

**这一组值得单独记的理由不是"有类型错误"**，而是：四条都在同一份文件里、都能被一条命令查出来，
而我是在写完文档、跑完全量绿之后才去查的。`pnpm verify` 离线装不上（本仓的老约束），
所以我**本来就该**手工补这一发 —— 0049 §8 为同样的理由手工单查过一次，我读了那一段，
这次仍然等到最后才做。

## 5. ⭐ 变异实验自己翻的两次车，两次都是同一个形状

七发变异，脚本 `/tmp/mutE2E.py`，锚点命中次数当场断言恰好 1，跑完立刻还原并逐字节比对。

**第一次：六发变异全打出「红 0 条」，而那是代码默认值。**
脚本先把统计存成 `d["fail "]`（带尾空格），再去查 `d2.get("fail ", 0)`——
存和查用的字面量不同，于是**每一次查找都落到默认值 0**，
于是脚本对每条变异都自信地打出一句读起来像【这条变异没被抓到】的话，
而那个 0 是**字典默认值**，不是测量结果。
发现它靠的是**手跑一发**（M3 手工注入 ⇒ 立刻红 2）：**「六发全绿」太不合常理，所以先怀疑实验而不是先怀疑被测对象**。

**第二次：我修脚本时用的 `assert` 自己算错了次数**，改动没落盘，我拿**旧脚本**又跑了一遍，
拿到一份和第一次一模一样的「全 0」输出 —— 这一次我差点当成「确认了第一次的结论」。
同一个输出出现两次可以有两种成因（**结论稳定** / **跑的是同一份坏代码**），
而我区分它们的唯一办法是去看脚本本身，不是再看一遍输出。
（这与 0048 §9 记的 v1 那十一条「新红 0 条」是**同一个错在我手上第二次发生**，
那次的成因是恢复环节没生效而坏状态一直留在磁盘上。）

还有一处**同类但更隐蔽**的读数错（我一度据此写下「M1 在别处有覆盖、这里 0 红是范围边界」）：
收集失败测试名时我用「行首是 `✖` 且含括号」当判据，而套件会打**文件级**的
`✖ packages/hub/test/xxx.test.ts (12ms)`，**那行含括号而括号前没有空格**，
于是我把「文件名」当成「测试名」收进去了。
M1 的「0 红」里有一部分是这么读出来的。**修法是数 `ℹ` 那三行而不是数 `✖`**（0048 §8 早就记过这条，
我读了、写进了脚本注释、又在自己的过滤条件里把它犯了）。

## 6. 本篇没做的（不写成「换种方式做到了」）

4. **两发用的是同一份汇报树形状**（三层、一条链）。层数不同、或者审阅者不在直接上级上，**没测**。

6. **`doc-refs` 抓不到「行号对而符号名错」这一族**（§2b）—— 我**没有加守卫**。
