## 1. 先给实测

本机 `node:sqlite`（SQLite 3.51.2 / Node v24.14.0），复算命令在 §7。

1. **一份迁移过而【空】的库，完整性检查报 `ok=true`。** 实测七条检查里
   `page_integrity` 是 ok，其余六条全是 `not_observable`，`events=0`，整份报告 `ok=true`。
   这条决定了巡检入口【绝不能创建库】：`openDb` 会建文件，
   于是「库文件路径打错一个字母」会产出一份【全绿】的巡检报告。
   入口因此先 `existsSync` 再动，且理由写进报错文案。

2. **只 `openDb` 而不迁移的库，报的是 `could_not_run` 而不是 `violated`。**
   实测：`state_machine_agrees_with_events` 抛 "no such table" ⇒ `could_not_run`，
   其余 `not_observable`。0018 §4 那张表里 `could_not_run` 的分工在这一库里第二次被观察到，
   而且这一次它给的答案是对的：库没坏（页面 ok），是尺子放不下。

3. **中段覆写 512 字节之后，`PRAGMA integrity_check` 仍然报 "ok"。**
   写的字节落在 freelist / 未使用区，btree 结构完好。
   这条否掉了备份测试的第一版夹具 —— 那份夹具【什么都没 corrupt】，
   而它看起来是在测损坏处理，断言还会全绿。

4. **把中段【整页】（page size 从文件头第 16 字节读，本机 4096）覆写掉，
   连接开得了而检查报 `violated`。** 拿到的是
   `*** in database main *** Tree 9 page 9: btreeInitPage() returns error code 11`。
   这才是「库能打开而检查说坏了」那个态，也是 §5 那条决定唯一能被测出来的形状。
   与 0018 §1 第 11 条合起来读，损坏库有【两种不同的失效】，要分开测：
   截断 ⇒ 连开都开不了；整页坏 ⇒ 开得了而检查报 violated。

5. **`openDb` 自己会抛。** 截断到 50% 的库在 `applyPragmas` 那一步就抛
   "database disk image is malformed" —— 连 `PRAGMA integrity_check` 都没跑到。
   这条直接改掉巡检入口：见 §4。

6. **`json_extract(payload,'$.kind')` 在内存 sqlite 上可用**，
   而载荷缺 `kind` 时返回 NULL，`NULL <> 'x'` 是 NULL 而不是 true ⇒ 那种脏行
   【不】算真实事件。两种写法（显式 `IS NOT NULL` 与靠三值逻辑）实测结果相同（都取到 200），
   所以 §3 里那条 SQL 加显式判据【不是为了改行为】。

7. **完整性扫描自己会往 `events` 里加一行。** append-only 探针撞触发器之后
   必须由应用层补一条安全审计（0018 §1 第 7 条：触发器里的写会被 `RAISE(ABORT)` 回滚），
   于是「跑过一次检查」这件事本身让 events 从 1 行变 2 行，
   备份拿到的必然是【检查之后】的状态。备份条数因此不能断言成夹具里写的那个数。

8. **`DELETE FROM events` 被自家触发器挡下**（"events table is append-only"），
   而且这一次是在【测试夹具】里挡下的。0018 §6 第 6 条记过同一条坑，本轮原地重犯。

### Task 6.4 基准轮补的实测（同一台机器，10 万事件 / 50 任务，复算见 §7 最后一条）

> 下面带「复算」字样的每一档，`packages/hub/scripts/bench-recompute.mjs` 都能重出来。
> 这一节第一版没有这个脚本，于是 §7 写着「可复算」而【三个数重不出来】——

9. **`json_extract` 的表达式索引让巡检从 417 ms 掉到 0.25 ms，写侧代价【几十个百分点】。**
   同一份库只差这一条索引、各取 9 趟中位：PATROL_SQL 417.2 → 0.25 ms；FTS 单条查询不受影响。
   为什么必须修而不是登记成阈值偏差：巡检跑在主线程上而 node:sqlite 是同步 API，
   那 417 ms 期间写队列、HTTP、SSE 全停（第 12 条是对此的直接验证）。
   【撤回】本节第一版写的「写侧 +18%」（批量 2000 行 121.3 → 142.9 ms）：
   复算时同一个量在三档交替下打印过 +35%、+43%，另起一发（库大小梯度）打出 +6% / +18% / +93%。
   那【不是数错了】—— 是【这个指标的方差比样本数大】：三档交替是 append-only 库上能做到的
   最好配平（§1 第 13 条那条纪律），而每个样本里都混着「B 树深了多少」「WAL 有没有 checkpoint」，
   三个数的中位数不是收敛的估计。
   所以这里只留【方向 + 量级】：这条索引确实让每次 INSERT 多维护一份 B 树，
   代价不为零、在几十个百分点这一档；脚本现在把【逐轮原始值】连同中位数一起打出来，
   并明写「单次值不可引用」。这个取舍不改变结论：读侧省的是 417 ms 的主线程冻结，
   写侧多付的是几十毫秒的延迟，两边失效方向不同（0003 文件头那笔账）。
   列序 (task_id, kind, created_at) 才对：kind 放末位实测 13.0 ms（用了它 4/4 个探测，
   却比 0003 的形状慢 50 倍 —— max(created_at) 拿不到区间边界）；
   【部分索引】要看列清单：(task_id, kind) WHERE kind IS NOT NULL 是 243.8 ms（只覆盖 2/4 个探测），
   而 (task_id, kind, created_at) WHERE 同样的条件是 0.33 ms。
   所以本仓【撤回】过一句写进 0003 文件头的话（「部分索引完全没用，仍 389 ms」），
   详见那个文件里的撤回段与 §5 第 16 条。
   ⚠ 「部分索引只覆盖 2/4」那句的对照有问题（一次差两个变量），见 §5 第 20 条；
   三个形状各自的覆盖面复算见第 14 条。

10. **FTS 限定任务那一发的两种写法【结果逐行相同】而代价差两个到三个数量级。**
    `rowid IN (SELECT id FROM events WHERE task_id = ?)` 的计划是
    `LIST SUBQUERY` + `CREATE BLOOM FILTER`：先把该任务全部 id 物化再建过滤器。
    两种序都在【同一份库、同一个词、同一个任务、同一个 LIMIT】下测（只差 SQL 写法）：
    命中 10 万那一档 时间序 86.4 ms → 0.48 ms（179×），最近序 18 338 ms → 34.2 ms（536×）。
    复算脚本默认那一档用【命中 12 345】的词（18 秒那一发会把复算脚本变成 4 分钟，
    而慢到没人跑的复算脚本等于没有），那一档是 1 113 → 2.3 ms / 1 983 → 11.0 ms。
    18 338 ms 那一格离计划「搜索 P95 < 500 ms」差 37 倍，而它【今天没有生产调用方】
    （buildReplayView 只走限定任务 + 时间序那一档）—— 这条格差一点就被「实测 0.7 ms」盖掉。
    【撤回】本节第一版写的是「限定+时间序 83 ms → 0.46 ms；限定+最近序 14 975 ms → 31 ms」：
    那两个「旧」数是【两份不同库】上各取一发拼出来的，而 §1 第 13 条记的正是这个错。
    上面那对 86.4 / 18 338 是同一份库上重测的。
    顺带一条量不到的教训：旧写法的绝对耗时【在库与库之间差 7 倍】
    （10 万命中那一档我量过 18.2 s、18.6 s、135 s 三种），
    差别不在索引（把 0003 那条建上再拆掉，同一份库上是 18 190 / 18 329 ms，没动）——
    所以我只能承认【它随库的布局漂】，而不能引用任何一个单独的「旧写法是 X ms」。
    【比值】和【计划形状】才是稳的，perf-thresholds.test.ts ③ 断的就是这两样。

11. **未守卫的表达式索引会让【升级】在有脏行的库上失败，还会悄悄改写语义。**
    库里有一行 payload 不是合法 JSON 时（今天写得进去：payload 只有 NOT NULL）：
    `CREATE INDEX … json_extract(payload,'$.kind')` 报 "malformed JSON" ⇒ 0003 整个迁移失败；

    计划不变差（仍 COVERING INDEX，0.25 ms），写语义一字不变。
    顺带抓出一个【潜伏 bug】：没有守卫时 PATROL_SQL 遇到那行脏数据直接抛
    ⇒ 一行不相干的脏数据让所有任务的停滞检测永久失效。这条本仓量过两次

12. **卡住写队列的是「主线程被同步查询占住」，不是锁、不是 WAL。**
    证据是【两侧占用时长被配平】的空转对照：并发 20 次写，另一侧分别跑

## 2. 加了一个模块，它只回答一个问题

`packages/hub/src/heartbeat/patrol.ts` 判的是「哪些任务【悄悄停了】」，
定义是四条同时成立：还在干活的状态里、超过阈值没有真实事件、没有人在等它、
而且这一轮还没报过。默认阈值取【两个】心跳间隔（规格 §7.3 的 15 分钟 ×2），
理由不是保守：一个间隔意味着「调度抖一下 + 一个慢 LLM 调用」就能让 CEO 收到一张卡，
而这种卡片出现三次之后，巡检真正想报的东西就没人看了。

三条不做什么，每条都有出处，且每条都有测试钉住：

- **不改 `tasks.status`。** 规格 §7.1 里 `BLOCKED` 只有【一条】入边（`IN_REVIEW→BLOCKED`），
  所以「检测到停滞就置 BLOCKED」对停在 `IN_PROGRESS` 的任务是【非法跃迁】，
  而跃迁写进 append-only 的 events 就永远在那儿。
- **不往 `approvals` 插卡片行。** 规格 §7.3 要的是【信息性】异常卡，
  而 `approvals.approval_type` 五个取值没有一个表达信息性；那张表装的是
  「能被 `POST /approvals/:id` 回答」的决策卡，而它的 id 来自 LangGraph 的 interrupt。
  异常卡没有 interrupt，回答它没有语义。多插一行反而会造出一张【永远批不掉】的卡。
  写 `HeartbeatStalled` 事件就够了 —— 计划 §6 那张四卡片表说的就是卡片由事件投影。
- **不是独立调度器。** 规格 §7.3 最后一条明确「而非独立外部调度器」。
  恢复（把任务推回图里）要真图执行，那一半要 `@langchain/*`。

停滞时钟的两个方向都必须对，否则会写出「第一天好用、第三天开始说谎」的代码：

| 若… | 后果 |
| --- | --- |
| 把 `HeartbeatStalled` 算进「最后动作」 | 报给 CEO 的停滞时长每巡检一次归零，一张停了三天的卡永远显示「已停滞 15 分钟」 |
| 完全不记它 | 每轮都为同一个任务再写一条事件，收件箱被同一个任务刷屏 |

所以：时钟只认真实事件；「这轮报过没有」= 最后一次心跳事件是否【不早于停滞起点】。

## 3. 与规格 / 计划字面的偏离

- **「挂着未决审批卡片」是【永久】免检，不是「阈值内免检」。**
  规格 §7.3 把「审阅者未响应」列为追问成因之一，看着像该由心跳催。
  但催它不是心跳的职责：`approvals` 表自带 `timeout_at` / `timeout_behavior` 两列，
  那才是「卡片挂了多久、超时之后怎么办」的机制。心跳管「悄悄停了」，超时管「问出去没人答」。
  做成阈值内免检（超阈值就报）看着更严，实际是拿 30 分钟的节奏催人类审批。
  **代价照记**：一张被【忘掉】的卡片不会由本模块报出来。今天这个代价是零，
  因为 `approvals` 在生产里【一次 INSERT 都没有】（0013 §10.1 实测），
  而 `timeout_at` 那两列同样没有任何读方 —— 两条通道都还没接通。接线那天要重看这一格。
- **「有没有人在等这张卡」由【事件配对】得出，不查 `approvals.status`。**
  配对靠 `target`：`recorder.ts` 的 `targetOf` 把 `ApprovalRequired` 与 `ApprovalDecided`
  都映射到 interruptId，注释里写明「必须能在 target 上 join 得起来」。
  不查 `approvals.status = 'pending'` 的理由是实测的：那张表在生产里零 INSERT，
  查它的巡检在真库上【恒为 false】，于是「等 CEO 的任务不被催」这条保护一条都不生效，
  而它在测试里也测不到 —— 测试得自己造卡片行，于是测试绿而生产不生效。
- **`TERMINAL_STATES` 含 `DELIVERED`。** 规格 §7.1 里它只有 `DELIVERED→ARCHIVED` 一条出边，
  而 `ARCHIVED` 是归档不是工作。把它当活跃任务的结果是：
  每一个交付完而未归档的任务在两天后都长出一张异常卡。
- **计划根 scripts 表那行 `backup: tsx packages/hub/src/db/backup.ts` 落不到 backup.ts 上。**
  `backup.ts`【没有 CLI 入口】，那是刻意的：它的一条门禁是「除 node:* 与自身外零 import」，
  测试扫的是它的可执行 import（`backup.test.ts` ⑤）。给它加个入口去 `openDb` / `WriteQueue`，
  那条门禁当场作废。可执行面因此落在 `heartbeat/maintenance.ts`，
  `backup.ts` 保持纯函数库。新增脚本 `hub:maintenance`。
- **计划 Task 6.1 的 Test「注入网络错误 / harness 崩溃 / LLM 超时三类故障」只做到等价类那一层。**
  真注入要真图执行（`@langchain/*` 装不上，0009 §2）。交出来的是
  三个可重试分类 + 一个 `sleep`/`now` 全注入的执行器 `withRetry`，
  以及【分类】本身 —— 见 §4 第二条。
- **Task 6.1 的「用巡检测试守孤儿活跃任务」这一条【做到了】**，
  而且是真库跑：`patrol.test.ts` ② 用真迁移库、真事件、真写队列，
  四格任务（该报 / 终态 / 刚动过 / 等人）同时存在时只有该报的那格被报。
- **计划 Task 6.4 的「2000 条事件批量事务写入 < 50 ms」这条阈值【未达标】，
  而且它量的不是它名字说的那件事。** 本机实测：批量与逐条事务的【比值】4.5~5.2×
  ⇒ 规格 V9「必须走批量事务」的实质要求满足。
  但 50 ms 这条线【跨不过去的原因不在批量】：同一张 events 表、同样 2000 行、
  【交替】跑三档（append-only 决定了库只会变大，分批会让每档面对不同大小的库，
  见 §1 第 13 条那条纪律），10 万行量级的库上：
  带 `events_fts_insert` 触发器 175 ms、摘掉它 57 ms ⇒
  **FTS 索引维护占批量写的 64%~70%**（本机五次观察；脚本每次重出这个百分比与逐轮原始值。
  这一节第一版写的是「67~69%」，那是【两次】观察被写成了一个区间的形状 —— 见 §5 第 21 条末段）。
  那条阈值实际测的主要是「FTS 触发器有多慢」，不是「批量事务有多快」。
  【撤回】本节第一版写的是「带触发器 50.0 ms、摘掉 5.4 ms、裸表 2.1 ms ⇒ 约 90%」：
  那三个数是在【近乎空的库】上量的，被当成 10 万行那一档的数写在这里。
  方向没错（触发器确实是主导项），比例偏了 20 个百分点，
  而【绝对值差 3 倍】（50 ms vs 175 ms）—— 后者更要紧，
  因为它会让人以为「再优化一点点就够到 50 ms 了」，而实际差 3 倍多。
  **我没有把阈值改成 200 ms 让它变绿**：改成那样抓到的是零 ——
  有人把分片大小改成 1（等于逐条写），200 ms 照样绿。
  所以 `batch.test.ts` ⑤ 与 `perf-thresholds.test.ts` ① 断言的是【比值】（批量必须
  显著快于逐条，判据 2×）加上【计划形状】，绝对毫秒数只打印、在本节存档。
  真要让 2000 行落进 50 ms，要改的是 FTS 的维护时机（攒一批再 rebuild），
  而那换来的是「刚写入的事件暂时搜不到」—— 这是【搜索新鲜度】的取舍，归 CEO 拍，
  不在这里替他决定（与 0018 §5 那条「FTS rebuild 只能读侧跑」是同一格的两半）。
  **本轮替那一格补了代价**：rebuild 一趟在 11.8 万行的库上实测 1 048~1 092 ms，
  而它【只能】在写连接上跑（只读连接报 "attempt to write a readonly database"），
  也就是说省下的那 ~120 ms/2000 行会换来一次【比巡检最坏情况（420 ms）还长 2.5 倍】
  的主线程冻结。这条路不是「免费的性能」，是拿一种阻塞换另一种更长的阻塞。

## 4. 七处「不这么做就会静默」的修补

1. **`openDb` 抛 ⇒ 入口必须说人话。** 巡检入口存在的全部意义，
   是在库坏掉那一刻告诉使用者「先停 Hub、先把现网库改名留一份、然后按 scripts/restore.md 走」。
   不捕 `new WriteQueue(dbPath)` 的抛错，那一刻交出来的是裸 SQLite 报错 + 堆栈 + 非零退码，
   而那句话说不出来。退码用 1（库坏了）而不是 2（命令写错）——
   运维脚本按退码分支，2 会让人去检查命令行而不是去恢复数据。

2. **重试的分类比「重试三次」重要。** 「失败就重试三次」是错的默认值，
   本仓有三类失败重试只造成损失：预算硬停（再跑只是多烧钱，规格 §7.4 要的是暂停 + 卡片）、
   越权（第 N 次仍然越权，且每次都留一条审计）、非法状态跃迁（我们自己的边表在报错）。
   混在一起重试的后果是 events 里出现四份同类失败，
   而回放把这段读成「agent 反复尝试」—— 一个从未发生的意图被写进了 append-only 的历史。
   `unknown` 也归到【不可重试】，与 `policy/engine.ts` 的 fail-closed 同一个立场。

3. **`withRetry` 不向调用方抛，而是返回 `ok:false` + `lastError` + `attempts`。**
   重试执行器把异常重新抛出去，等于把三次失败压成一条 rejection，
   而调用方最省事的写法是 `.catch(() => log(e))` —— 那一支就是 Task 6.1 要防的静默停滞本身。

4. **备份前先看页面检查，不过就不备份。** 保留策略只留最近 7 份，
   一份已知损坏的备份写进去就成了【最新】那份并挤掉一份好备份，
   而 `restoreDrill` 之后验的正是最新那份可用。
   不备份的代价是「今天少一份备份」，备份的代价是「少一份好备份 + 一份看起来好的坏备份」，
   后者不可逆。判据只看 `page_integrity`，不看整份报告的 `ok`：
   「没有门控决定可核」(`not_observable`) 跟「文件坏了」是两件事，后者绝不该拦备份。
   **这一条不替 0018 §8 拍板**：那一节问的是「多久跑一次」，
   这里定的只是「既然要跑，先查还是先拷」。

5. **批量写的校验必须在入队之前对【整批】做完。** `appendAuditBatch` 先把整批
   过一遍 `eventParams` + `assertParamCount` 才碰写队列。边校验边写的形状会在
   「第 4 行 action 写错」时留下【前三行已落库】的状态，
   而 append-only 挡不住事后清理 —— 参数写错是这里最高频的错误，
   把它变成一次部分写入是最贵的那种。用例打在【事务计数 = 0】而不仅是「抛错了」上：
   只断言抛错的话，一个「先写完再抛」的实现也能过。

6. **分片之间【不是原子的】，并且我把这条写在了显眼处而不是藏成实现细节。**
   2000 行 ⇒ 两个事务，第一个成功第二个失败就是留下前 1000 行。
   不为了「全有或全无」把分片上限抬到装得下全部：那正是 0001 §2.2 那条
   【只知道下界、上界从未穷尽】的绑定参数边界。
   append-only 在这里帮了忙：重试同一批写出的是【可辨认的重复行】，
   而不是半条事件或损坏的库。需要「必须整体可见」的调用方（超步事务里的
   checkpoint + events）本来就该走 `WriteQueue.node()` 那条路，不该走这里。

7. **巡检的 kind 表达式与 0003 那份 DDL 的表达式【必须逐字同源】，这一点由测试钉住。**
   表达式索引匹配的是字面写法。两侧漂移（比如 patrol 侧把 CASE 换成 IIF、
   或多写一个空格）之后，SQLite 只是【不再选这条索引】—— 不报错、不变红，
   生产静默退回 413 ms。`kindOf()` 因此导出，测试拿它的产物与 DDL 文本比对；
   而 `perf-thresholds.test.ts` ② 那条 EXPLAIN 断言是第二道（它抓漂移的【后果】）。

    前者不能自动保证后者。
    处理方式不是把理由①删掉重写一遍（那会看不出它错在哪），是
    ① 在 0003 里按仓规【撤回】并留原文，选型的理由从两条减成一条（结论不变）；
    ② 把覆盖面这件事【钉成断言】（`patrol.test.ts` ⑤ 那条「恰好三个」+
       「计划里必须有四个探测」的前提检查，外加「等列清单的部分索引给出【同样三个】」），
    以后「几个探测走这条索引」不再由任何人【声称】，包括我。
    附带一条：第四个探测不走那条索引是【对的】而不是漏配 ——
    见 §1 第 14 条那组尾部 kind 对照，掰过来反而会把巡检自己写的事件变成代价。

21. **我在三处写下同一个「+18%/+19%」，而它压根不是一个数。** 复算时同一档在三档交替下
    打印过 +20%、+35%、+43%，另配一组「库大小梯度」的探针打出 +6% / +18% / +93%。
    最像事实的那个错法恰好【又演了一遍】：第三次运行打出 +20%，紧邻我先写下的那两个数
    （0003 的 +19%、§1 第 9 条的 +18%），于是它【看起来验证了它们】——
    而我写下「同一台机器跳过 35%~93%」这句话的【那一次运行】就打出 +20%，
    当场证伪了我自己刚写下的那个区间。梯度里最小值口径还给出过 −6%。
    真正的结论是【这个指标的方差比样本数大】：append-only 决定了每个样本都在不同的库上
    （§1 第 13 条那条纪律只能靠交替把增长过程摊平），样本里混着 B 树深度与 WAL 状态。
    所以三处都改成【方向 + 量级】（不为零、几十个百分点），脚本改成【逐轮原始值 + 中位数】
    一起打印并写明「单次值不可引用」。同一轮里 §3 那个「FTS 触发器占 67~69%」也跟着
    改成了区间 64%~70%（五次观察）—— 它是同一个指标的比值口径，不可能比方差更小却
    【恰好】一直落在 67~69% 那两格上；原来的写法是把【两次】观察写成了一个区间。
    教训的形状：前几轮的错是【两个自洽的事实】，这一条是它的变体 ——
    【一个自洽的事实，加上一次恰好对上它的复现】。
    判别办法也记下来：引用任何百分比之前先看【逐轮原始值】，
    原始值跨度大于结论本身量级的，只能写成区间或量级；
    而【区间本身也要标它是在几次观察上得出的】—— 否则「67~69%」读起来像
    一个测量过的带，其实只是两个点。
22. **我差点把「第四个探测走 idx_events_task」当成漏配写进去，并顺手打算写一条
    「把它掰到 0003 那条索引上」的待办。** 拦下它的不是判断力是运气：为了确认
    「这算不算退化」我做的那组对照（只差尾部 kind：0.079 vs 2.186 ms）说明
    它走 idx_events_task 是【对的】—— 那条索引让 max(created_at) 天然有序、
    撞到第一条满足判据的行就停，生产形态下第一步就停。
    如果按「四个探测都该走新索引」这个直觉去「修」，得到的是一条【等值定位】的索引
    把尾部全是心跳事件的任务变成全任务扫 —— 也就是让巡检自己写的事件变成性能代价。
    教训：「覆盖面没占满」不是一个【待修的观察】，它得先回答「少掉的那一发现在靠什么」。

Task 6.4 基准轮之后的缺口：

- **全库检索那一档（不带 taskId）仍然会阻塞写队列，而且比本文件第一版写的更贵：
