## 2. 边界：类型检查【也】抓不到 Phase 0 那条审计缺口

必须把两件事分开，否则会用错工具：

- `currentNode` 这类【多余键】是类型问题：若 `test/` 参与检查，`TS2353`（多余属性）会当场报。
  实测分布里确实有 `TS2353:5`。
- `events.state_snapshot` 全库 0/14 是【需求缺口】，不是类型错误：`recorder.ts` 的
  `stateSnapshot` 本来就是可选参数，不传完全合法，类型系统对「该传没传」一无所知。
  只有断言能抓，而计划里没有任何一条任务的验收标准提到它（见 Phase 0 出口门禁汇报）。

所以「把 `test/` 纳入 `tsc`」值得做，但它不会替你回答「需求实现全不全」。

## 4. 本节真正的结论：守卫必须【自证有效性】

第一版守卫长这样：一条扫描 + 一条「检查守卫自己有没有把键名写成整串字面量」的元断言。
元断言听起来很稳妥，实测它【不提供任何保护】：

| 变异 | 结果 |
| --- | --- |
| M1 把扫描用的键名值改错（`current` + `Zed`） | `Tests 11 passed` 全绿 |
| M2 键名值错，同时把真违规塞回调用点 | `Tests 11 passed` 全绿 |
| M3 把键名写成整串字面量（值不变） | `Tests 11 passed` 全绿 |

M1/M2 说明扫描静默失效时，扫描断言自己永远「绿」；M3 说明我原先给元断言写的理由
（「写成整串会命中自己，所以会红」）是错的 —— 命中需要「键名 + 冒号」的形状，
声明行是 `键名 = "…";`，扫不到自己。一次都没被证伪的推理，就是我以为成立而其实没验的推理。

重写后的形状：把扫描逻辑提成纯函数 `findDeadKeyLines(text, key)`，然后【种一个真违规】要求
它必须被抓到，再【种一句注释】要求它不被误判。重跑的变异电池 5 条全部被杀：

| 变异 | 被谁杀 |
| --- | --- |
| G-A 死键塞回真实调用点 | 扫描断言 |
| G-D 键名值改错（上一版静默失效的场景） | 「扫描器能抓到种下的违规」 |
| G-G 扫描器短路返回空数组 | 「扫描器能抓到种下的违规」 |
| G-E 把注释豁免改成永不匹配（等价变异） | 扫描断言 + 「扫描器不把注释当违规」两条同时红 |
| G-F 通道清单少一项 | 「通道清单与 src 的 Annotation.Root 同步」 |

补注 G-E 的方法学：先前我把它写成「删掉那段 filter」，跑出来是 `Tests no tests` ——
语法被破坏，按规矩既不算杀死也不算存活（0006 §7 第 3 条）。换成语法合法的等价变异
（三个豁免前缀改成永不匹配的字符串）之后才拿到有效结论。

规矩（适用本仓一切检测类测试）：

> 一个负责「发现 X」的守卫，必须内建一个人工构造的 X 并要求它被发现。
> 只断言「现在没查到东西」的守卫，其失效方式与「恒真」不可区分。

`production-deps.test.ts` 里的 `expect(seen.size).toBeGreaterThan(3)`（0006 §6.1 第 2 条）
就是这个规矩的雏形，本节把它一般化。

## 5. 留给 CEO 的一项决定
### 5.1 决策依据先校正一处：`test/` 并非【完全没有工具】

本节讨论成本之前，我先入为主地以为 `test/` 既没有类型检查也没有 lint ——
如果真是那样，§5 就不是「要不要补类型检查」而是「要不要补一整套工程护栏」，成本量级完全不同。
所以做了两个探针实验：

**实验一：`test/` 到底有没有被 lint 覆盖。** `biome.json` 的 `files.includes` 第 2 条
就是 `test/**/*.{ts,tsx}`，第 1 条 `packages/**/*.{ts,tsx,js,mjs,json}` 也已经覆盖各包的
`test/`。光读配置不算证据，于是往 `packages/hub/test/` 放了一个故意写坏的临时文件
（未使用变量 + 少空格少分号）：仓库级 lint 立刻 `exit=1`，同时报
`lint/correctness/noUnusedVariables` 和 `format` 两项，`Checked 66 files` 变成 `67`。

> 所以准确说法是：**格式与 lint 覆盖 `test/`，只有类型检查不覆盖。**
> §5 的成本只是「清 32 个类型错误 + 加一份 `tsconfig.test.json`」，不是重建护栏。

**实验二：依赖边界的 lint 规则真的在界上生效吗。** `biome.json` 第 41–50 行把
`node:sqlite`、`node:sqlite/promise`、`better-sqlite3` 登记进 `noRestrictedImports`
（level=error），第 63–75 行又用 `overrides` 给 `packages/hub/**` 把这条规则关掉 ——
意图是「SQLite 只准待在 hub」（规格 §5.6.1 / 计划 §2，对应 V5/V6）。
在 `desktop/src`、`web/src`、`hub/test` 各放一个 `import { DatabaseSync } from node:sqlite`
的探针，结果 `Checked 3 files`、`Found 2 errors`：两个包外探针被 `noRestrictedImports` 拦下，
hub 内的探针【无报警】。规则方向正确 —— 界外禁止、界内放行，正是想要的语义。

两个探针都已删除，`git status` 只剩本文档。

> 【自查，同一轮】上面那句「hub 内无报警」差点被我写成「三处都被拦下」，从而把结论
> 写成规则的边界形同虚设。原因是我当时按【文件名 basename】去匹配 lint 输出，三个探针
> 同名，于是 desktop/web 的报错行同时冒充了 hub 探针的命中 —— 一条恒真的判定。
> 与 §4 是同一个毛病，只是这次藏在报告脚本里：按名字匹配多目标输出时，名字必须唯一，
> 否则应当数【条数】而不是数【是否出现】。


### 5.2 收益 / 成本 / 风险与我的建议

要不要把 `test/` 纳入 `tsc`，并让它进 `pnpm verify`。给全成本，不替你决定：

- 收益：`currentNode` 这一整类死输入在写下的那一刻就红；`import` 路径写错也不再需要靠
  `vitest` 的 `Tests no tests` 事后暴露。
- 成本：先清 32 个既有错误（数字与依据见 §1.3 的【计数更正】）。真实根因写在下面的
  【撤回】块里，其修法与「新增一份工程配置」是两件独立的事，不要混成一个任务。
  其余分布：`TS2532:7`（缺类型收窄）、`TS2322:9`、`TS2835:2`（相对导入缺 `.js`
  扩展名）、`TS2556:1`。数小时量级。

> 【撤回】本节初稿对 `TS2345` 的根因写过一句猜测：「`Db` 类型不匹配，多半是 `openDb`
> 返回类型与 `DatabaseSync` 的别名/包装不一致」。**这句未经任何验证，而且是错的**：
> `driver.ts:30` 的签名就是 `openDb(path: string): DatabaseSync`，既没有别名也没有包装层。
> 实测真因是测试侧自己手写了三份互不相同的 `type Db` 桩 ——
> `driver-preflight.test.ts:17` 用 `InstanceType<typeof import(...)[DatabaseSync]>`，
> 而 `migrate.test.ts:17` 与 `schema-0001.test.ts:19` 各写了一份结构体桩，于是传给要
> 真 `DatabaseSync` 的函数时报 missing the following properties: aggregate,
> loadExtension, enableLoadExtension 等。修法是把三份桩收敛成一处（或直接删掉、用真实
> 类型），与新增工程配置无关。
> 留【撤回】而不是静默改掉，是因为本节已随 `d686087` 之后的提交入档；静默删会让下一次
> 复盘看不见「一句没验的猜测是怎么混进决策文档的」。这正是 0006 §7 第 10 条说的毛病，
> 而它是在写下那条规矩的同一轮里发生的。
- 风险：`noEmit` 的工程一旦进 `composite` solution，`references` 图要重排，构建可能
  被拖慢；且 `test/` 引用的构建产物路径（迁移 SQL 等）需要在类型层声明。

我的建议：值得做，但作为独立任务排在 Phase 1 开头，而不是塞进出口门禁。

## 6. 把同一把尺子用到既有断言上（出口标准第 2 条）

§4 的规矩不该只约束新写的守卫。出口门禁第 2 条「中途打断并从 Checkpoint 恢复」我判为绿，
依据一直是 `test/poc/resume.test.ts` 的门禁 #2；但那份信心来自【我读了代码觉得它成立】，
按本节 §4 的标准，那正是「未经证伪的推理」。补做的变异实验：

| 变异（改的是恢复子进程 `poc-resume.mjs`） | 结果 |
| --- | --- |
| R-1 `resumedNext` 硬编码空数组 | 红：`expected [] to deeply equal [ 'approval' ]` |
| R-2 `resumedTrail` 硬编码空数组 | 红：`expected [] to deeply equal [ 'producer', … ]` |
| R-3 用不存在的 `thread_id` 读 state | 红（同 R-1 的形状） |
| R-4 恢复时不带 `resume`，直接空输入 invoke | 红：轨迹少了审批之后的推进 |

R-2 是这组里唯一真正要紧的一条：`resumedTrail` 取自 `before.values.trail`，也就是
**checkpoint 里存的值**，而不是新进程重跑出来的东西。所以它存在一个理论上的假绿形状 ——
万一新进程什么都没恢复出来、而 `phase1.trail` 恰好也是空，就会「空 === 空」恒绿。
实测否掉了这个形状：`phase1.trail` 有 5 个元素，把它换成空数组立刻红。

同一个文件里还有一条形状更可疑的断言：反例守卫断言【坏行为确实发生】
（重复 `invoke` 会重放已完成节点，用 `toBeGreaterThan(1)` 期望重放）。
它是「恢复必须走 `Command`」这条结论的唯一证据。也补了变异：

| 变异（改 `poc-double-invoke.mjs`） | 结果 |
| --- | --- |
| D-1 把错误用法换成【正确】的 `Command resume` | 红：`expected 0 to be greater than 1` |
| D-2 压根不再 invoke，只读 state | 红：同上 |

D-1 的红必须由断言产生而不是缺 import 报 `ReferenceError` —— 已核对子进程第 3 行确实
`import { Command }`，所以它是「用法正确 ⇒ 重放消失」的有效证据。

结论：6 个变异全部被杀，出口标准第 2 条的绿【成立】，且现在是证据而不是判断。
本节记录的是方法而不是结论 —— 一条断言「看起来很强」和「确实很强」之间，差的就是一次变异。

### 6.1 再往下一层：出口标准第 1 条的 251 个用例里，6 个 skip 是什么

第 1 条我原先只数了用例数（251 ≥ 25）。但报告里同时写着 `6 skipped`，我从没查过那 6 条
跳过的是什么 —— 如果某个 skip 恰好覆盖门禁要求的行为，「251」就是个虚数。

查法与结果：全仓 `git grep` 只有【一处】动态 skip（`saver.contract.test.ts:442`），
6 条全部来自它，都是 Checkpoint Saver 契约里「仅对 SqliteWALSaver 成立」的那组：
同事务原子性、外层写锁期间另一条连接被拒、事务内 deleteThread 随外层回滚、事务外调用
put/putWrites 直接抛错、type 列真被使用、中文与嵌套对象往返。

该文件已自带一条元守卫（`expect(exclusiveRuns).toBe(SQLITE_EXCLUSIVE_CASES)`），
注释里声称「B2 变异实测」。那是过去的我写下的声称 —— 按本节规矩，注释里的实测结果
不算证据，我独立复现了一遍：

| 变异 | 结果 |
| --- | --- |
| V1 把 `itSqlite` 的判定写成恒假（`SQLSAVER_LABEL + " "`，语法合法） | 红，且红在元守卫上 |
| V3 计数器不累加（`exclusiveRuns += 0`） | 红，同样红在元守卫上 |
| V4 【取消 skip】：让 MemorySaver 也跑这 6 条 | 红 5 条（失败发生在 MemorySaver 变体里） |

V1/V3 说明元守卫监控的是真实执行次数，不是恰好等于那个常量。V4 最有意思：它是对 skip
本身的【反向证明】—— 取消 skip 之后 6 条里有 5 条在 MemorySaver 下真的失败，所以
「仅对 Sqlite 成立」名副其实，skip 不是图省事的掩盖。

> 规矩：skip 也要做变异 —— 把 skip 取消再看结果。取消后【仍然全绿】说明这条 skip 是
> 多余的（那部分覆盖其实丢了）；取消后失败，才证明 skip 的理由成立。
> 只解释「为什么跳过」而不构造反证，和只读代码就宣布门禁通过是同一回事。

诚实记下 V4 的一个副产品：那 6 条里有【1 条】（中文与嵌套对象往返）在 MemorySaver 下
【也通过】，即它并不依赖 Sqlite 特有机制，集体注释「仅对 SqliteWALSaver 成立」对这一条
过度声称了。不构成覆盖损失（它在 Sqlite 变体里确实跑了），因此本轮不动它 —— 把它改成
常态双实现断言，等于开始锁定第三方实现（`MemorySaver` 是 LangGraph 提供的）的行为，
将来它升级就可能红。这类「扩大锁定面」的改动应当单独决定，不夹在门禁等待里顺手做。

结论：出口标准第 1 条的 251 个通过用例里没有任何假绿占位，6 个 skip 也不掩盖门禁行为；
第 1 条的依据从「数字够大」升级为「数字够大，且差额逐个查明」。

### 8.1 负结果：这类声称【无法】机械审计，别再投入

扫描范围：全部测试目录的 `.ts` / `.tsx` / `.mjs`，27 个文件，只认整行注释与 JSDoc 续行。
结果：

| 类别 | 数量 | 能否交叉核对 |
| --- | --- | --- |
| 强声称（「变异实测」「变异测试」「实测：」「已验证：」「实测证明」） | 28 | —— |
| └ 其中带可查代号（B2 / V1 / R-2 / K-1 这类高区分度记号） | 2 | 能，且 ADR 里查得到 |
| └ 其中【无代号可交叉】 | 26 | 不能 —— 只能重跑变异电池 |
| 弱声称（「实测」「测过」「跑过」无结果口吻） | 43 | 更不可能 |

也就是说：注释里的 28 条强声称，只有 2 条能自动落到某份 ADR 上。剩下 26 条写的是「变异测试
发现的缺口」「12 个变异全部被杀」这类【事实陈述】，没有任何指针能机器化地验证它当时是否真的
成立。唯一的可靠手段始终是【需要时重跑】那套变异电池 —— 这也正是本轮对 `resume.test.ts`、
`saver.contract.test.ts`、`smoke.test.ts` 各自做的事。

**所以这条规矩的正确用法不是「以后注释别写实测」，而是：写声称时【必须同时留下可重放的指针】
—— 代号（B2 / V1 / R-2）或者提交哈希。**否则它就只是一句无法反驳也无法证实的话。

### 8.2 比结果更值钱的：我连写三版扫描器，三版都有缺陷

三版共四类失效，全部落在 §4 那条规矩的延长线上 —— 工具本身也得自证有效性：

| # | 缺陷 | 为什么危险 |
| --- | --- | --- |
| 1 | 把带 `*` 的路径直接喂 `readFileSync` | fs 不做 glob 展开，直接 ENOENT；写文档时能写 glob，代码里不能 |
| 2 | 拿注释前 8 个字符去 ADR 里 `includes` | 短词既会假阳性，也会因措辞差异假阴性；这不是交叉核对，是碰巧匹配 |
| 3 | canary 的【期望值】没验过就当真 | 报 FAIL 的是 canary 自己（行尾注释与整行注释两类混在一个断言里），扫描器行为其实正确 |
| 4 | 用 `/^## 7\s/` 找标题 | 真实标题是 `## 7. 本节不含的东西`，句点导致 0 命中，我差点据此判定文档没有 §7 |

教训：canary 必须【按类别】给期望值，并且必须包含【反向】样例（引用一个不存在的代号，扫描器
要说「查不到」）。本轮加上反向样例后，`ZZ-99` / `QQ7` 都正确报不存在 —— 这才是那 2 条「代号
查得到」结论可信的原因；没有反向样例时，「全部命中」和「扫描器恒真」长得一模一样。

### 8.3 本节不含

这轮排查【没有】去逐条重跑那 26 条无代号声称对应的变异实验：门禁正等裁决，而这类重跑不产出
任何 CEO 决策需要的信息。真要清这笔账，合适的位置是 Phase 1 开头，和 §5.2 的 `test/` 类型覆盖
决定一起做 —— 两者是同一件事：让「我以为有人守过」变成「机器知道有没有」。
