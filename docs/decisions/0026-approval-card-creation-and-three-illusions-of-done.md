## 0. 这一篇填的是什么洞

## 1. ⭐ 创建路径建好了，而「已经接上了」这句话是错的

补了 `approvals/cards.ts`（一张卡 + 一条审计，同一事务）之后，我差点在
`phase3.test.ts` 那条 blocker 守卫上做一件很省事的事：把

```
expect(srcFilesMatching(/INSERT\s+INTO\s+approvals/iu)).toEqual([]);
```

改成 `.toEqual([SRC + "/approvals/cards.ts"])`，然后宣布这一格过了。

**那一步会把两件事合成一件**：

- 「**创建路径存在**」—— 已做（42 条用例钉着）；
- 「**有人调用它**」—— **没做**，`createCard` 在 `src` 里零调用方。

合并之后那条断言**今天就转绿**，而 Task 3.5 的「自动通过一张卡片」仍然只能对
测试自己插进去的行生效。守卫从此不再说明任何东西。

所以两处（`phase3.test.ts` 的 blocker 6、`auto-approve.test.ts` 的 ⑧）都改成了**两条并排**：

```
expect(srcFilesMatching(/INSERT\s+INTO\s+approvals/iu)).toEqual([SRC + "/approvals/cards.ts"]);
expect(callersOf("createCard", "approvals/cards.ts")).toEqual([]);
```

**「生产路径已备好」与「已接线」是两个必须分开钉的事实**，因为它们坏的样子完全不同：
前者坏了一次编译错就报出来，后者坏了**零症状**。这也是本仓反复用的那招
（0013 §10.1 用「只有消费者没有生产者是可接的」区分过同一件事，这次是反方向）。

## 2. ⭐ 第一处代拍（原 0025 §8.2）：`approval_type` 加一个通用 `escalation` 值

0025 §8.2 原文写的是「**这是 schema，得你定**」，并给了三个候选、明写「我倾向第二个」。
CEO 已授权我按产品设计逻辑自行判断，所以这里拍的就是**他自己倾向的那个第二个**：
加一个通用 `escalation` 值，把「为什么升上来」放进 `parameters.escalation.reason`。

**为什么这个能拍**：三个候选里只有这一个**不新增枚举成员**，而枚举成员是审计里
要被长期读的东西 —— 拍错了改不掉（`approvals` 在审计库里，改历史取值等于改历史）。
一个通用值 + 一个自由维度的组合，**将来想改成前者只需要加映射，不需要改历史行**；
反过来先加六个值、后来想收敛成一个通用值，就动了已有数据。
**可逆的那个选项才是我该自己拍的**，这条判据比「我倾向哪个」更该被写下来。

**代价照记，不粉饰**：

1. 按 `approval_type` 统计时，`escalation` 这一格**混装**六种完全不同的事由
   （`insufficient_evidence` / `low_confidence` / `meeting_escalation` / 三类原有的升级触发）。
   要按原因统计必须去解析 `parameters` 里的 JSON 文本 —— **没有索引**，
   10 万卡片量级上是全表扫。今天没有任何代码做这件事；做的那天应当加一条**表达式索引**，
   口径与 `db/kind.ts` 的 `kindOf` 同源。
2. `EscalationReason`（contracts）与 `APPROVAL_TYPES`（hub）现在是**两份清单**，
   前者是后者的 `reason` 维度的取值。它们**故意不同步**：新增一条升级原因不该是一次
   `approval_type` 变更。风险是有人往 `EscalationReason` 加一个值而忘了卡片会落不进
   任何已知类型 —— 而 `query.ts` 的 `escalation_reason` **刻意不是枚举类型**，
   库里出现契约不知道的取值会**原样带出去**让人看见，而不是在解析层整体 500。

## 3. ⭐ 第二处代拍（原 0025 §8.3）：`timeout_at` 写值，而到期什么都不做

0025 §8.3 原文：「**故意没接**：超时之后该做什么（自动批准？自动升级？只提醒？）
是产品行为，不是『有了调度器就该做的事』」。这句话是对的，而它**留了个更糟的中间态**：
`timeout_at` 这一列连值都没有 —— 也就是将来无论拍哪个答案，都**不知道那张卡是几点建的**。

拍下来的答案是：**值现在落库（8 小时），动作留空**。

为什么「什么都不做」是三个候选里唯一今天站得住的（【规格】§9.3 那张表是三值）：

- `auto_approve` 意味着机器替人点头。【规格】把它限定在「仅限可逆事项」，
  而「可逆」的判定来自 `policy/engine` 的风险分级 —— **那份分级今天没有生产写入方**
  （只在超步里被调）。也就是说今天连「这条是可逆的」都还没有可信出处。
- `auto_reject` 意味着 CEO 吃个午饭回来，一晚上攒的卡片被打回一半。
  【规格】§19.1 的效率承诺是「20 秒完成一次审批」，不是「不在时机器替你拒绝」。
- `escalate` 需要一个「更深审阅流程」的落点，那是【规格】§10 的会议机制，Phase 3 才有。

**这条决定被写成了一条会过期的性质**：`cards.test.ts` ⑤ 那一发跑完 `patrolTasks`、
把时钟推过 100 小时，断言卡片**还是 pending** 且 `decided_by IS NULL`。
将来有人接上超时执行者，那一发**会红**，逼他先回答本篇这三个候选。
巡检那一发是**必要的排除**：只推时钟不跑巡检，红的可能只是「没人醒过」，
而那与「没有超时逻辑」是两件事。

⚠ 顺手推翻我自己两处旧注释（原文都留着）：
`patrol.ts` 里「timeout_at 那两列同样没有任何读方」—— 现在有读方了（`GET /approvals` 展示它）。
**但展示不等于执行**，所以那个模块的免检结论**不变**。
`events/bus.ts` 里「对账的那条 REST 源还不存在」—— 现在存在了。

## 4. `GET /approvals`：那条 blocker 的成因不是「做不了」，是估错了成本

0010 §5 把它列为「两处没做」的第一条，理由是：

> 加一个端点要同时改 contracts 的 `API_ENDPOINTS` / `IMPLEMENTED_ENDPOINTS`、
> desktop 的 `CHANNEL_SPECS`、`preload/api.ts` 那份手抄字面量、以及 **5 个 ipc 测试**里那张
> 手抄的 `INVOKE_METHODS` 表 —— 五处一次改完而**没有 Electron 环境可验**，是加漂移点而不是加功能。

**这两条论据当场量的结果都不成立**：

| 它说的 | 实测 |
|---|---|
| 5 个 ipc 测试文件 | `test/desktop/` 下**只有 1 个**（`ipc-surface.test.ts`）|
| 没有 Electron 环境可验 | 那一个文件**不 import electron**（全仓 `from "electron"` 命中 0），本机 **27 条全绿** |

所以那一条 blocker 不是「做不了」，是**当时估错了成本**，而且估错的方向恰好让它看起来
像一次负责任的克制。这类判断最难自查的地方在于：它引用的是**结构**（要改几处、有没有环境），
听起来比引用**数字**更可靠 —— 而结构也是数字，一样能数错。

**所以本篇不写「下次注意」**，写这条：**一句带数量的论据（五处 / 五个文件 / 三条理由）
在写下之前必须当场数一遍**，因为它是**可数的**，而可数的东西说错了就是错的。
0025 §0 那条「`hub:maintenance` 不在任何 npm script 里」是同一种错（当场查 `package.json` 就推翻）；
0024 记的「按印象补事实」是它的近亲。三次了，对象从别人的代码挪到了我自己的注释。

少这一条读路径的代价此前一直在那儿：`events/bus.ts` 的收件箱计数
（`ApprovalRequired` +1 / `ApprovalDecided` −1）**只能靠自己不丢不重来维持正确**，
而「会丢会重」正是 SSE 在断线重连下的默认行为。

## 5. 去重做成了索引，而不是「建之前先查一次」

「同一个决定不要长出两张卡」这条需求，最省事的写法是先 `SELECT` 再 `INSERT`。
那个写法留着一个「两边都查到没有 ⇒ 两边都插进去」的窗口。
`WriteQueue` 把事务串行化，所以走同一条队列的两个建卡方今天撞不上 ——
**但那条依赖是运行期装配给的，不是数据库给的**：0025 §2 实测过「第二个 `WriteQueue`
空闲时照写」，而 `cli.ts` 那条路、测试里手搓的连接、哪天有人直接 `new WriteQueue` 都不在那条链上。

所以判据落在 DDL 上：`CREATE UNIQUE INDEX ... ON approvals(task_id, card_key) WHERE card_key IS NOT NULL`。

`cards.test.ts` ② 最后一发**绕开本模块**、拿裸连接直接 `INSERT` 两次，期望第二次抛
`UNIQUE constraint failed` —— 那一发证的是它是**性质**不是**约定**，去掉 0004 那条索引它当场红。

两个细节：

- **索引里带 `task_id`**：卡片身份的作用域是「一个任务内的某个决定」，不是全库。
  只按 `card_key` 建索引会让两个任务里恰好同名的 key 互相挡掉。
- **不同 key 必须各建一张**（② 第二条反向对照）：若实现拿 `task_id` 或 `summary` 当去重键，
  前面那几发全都绿。而「合成一张」的后果不是吵，是**吞掉一个决定且不留痕迹** ——
  【规格】§8.3 明确允许同一个任务多次升级。

## 6. 三处我自己写错的地方（都能测，都红过）

### 6.1 契约校验把自己校验掉了

`approvalCardDraftSchema` 是 `.strict()`。我第一版直接 `safeParse(draft)`，
而 `draft` 里带着 `taskId` / `approvalType` / `cardKey` —— 那三个是**落库用的列**，
不是卡片内容。`.strict()` 会因为三个「未知键」**整体拒绝**，于是**每一次建卡都抛契约错**。

它不会在任何「测建卡」的用例里暴露成「建不出来」以外的形状，所以补了一发直接钉
「带落库列的完整 draft 喂得进去」。

**`.strict()` 是个好默认，但它让「校验过严」和「校验生效」在报错上长得一模一样** ——
报的都是「不符合契约」。区别只在**谁的契约**：这次是校验器在跟自己约定的形状较劲。

### 6.2 一个永不生效的排序键，和一条测不到任何东西的断言

`APPROVAL_ORDER` 第一版写着：

```
ORDER BY CASE WHEN status = 'pending' THEN 0 ELSE 1 END, ...
```

而 `listApprovals` 的 `WHERE` 是 `status = ?` —— 一次查询返回的**所有行 status 相同**，
那一档**永远排不出任何东西**。我给它配了一条断言「已批的排在待批之后」，
而那条断言只能靠**绕过默认过滤**才测得到，也就是它在测一条**不存在的查询路径**。

发现的过程值得记一句：我先写的断言是红的（默认那一页根本不含已批的卡），
**如果我当时是把断言改绿而不是去问「为什么这条不成立」，那个死键就留下了**。

删掉的同时留了一条 `expect(APPROVAL_ORDER).not.toMatch(/status/u)` ——
**将来若放宽成多档过滤（`status=pending,deferred`），这一发红**，
而他必须同时重新决定排序，那时那一档才第一次有意义。

本仓对「永不被触发的分支」的立场见 `http/app.ts` 里 501 那一支（那里保留有两条明写的理由）；
这里没有那两条理由，所以删。

### 6.3 排序方向：注释说「最老的在最上面」，代码写的是 `DESC`

`DESC` 是**最新在前**。两者不是一回事，而 DESC 恰好是错的那个：收件箱要顶到第一行的是
「已经等了 3 天没人理」那一张。一张等了 3 天的卡在 DESC 下会沉到最底部，
而它正是最该被看到的那一张 —— 那种界面的结局是人只扫前三行，
于是**等待时长越久的越不会被看到**。

改成 `ASC` 之后，`CASE WHEN created_at IS NULL THEN 1 ELSE 0 END` 从「装饰」变成了**承重**：
SQLite 升序把 NULL 排在**最前**，而 0004 之前建的卡（没有 `created_at`）恰恰是最老的那些 ——
它们会顶到收件箱第一行，**看着像「最老的在最上面」这条性质成立了**，
实际是 NULL 抢了那个位置，而它有多老**无从知道**。

写这一段的时候顺手发现：`approvals` 那十三列里**一个创建时刻都没有**（0001）。
有 `decided_at`、有 `timeout_at`，而「这张卡挂了多久」问的那个起点从来没落过库。
补这一列时**刻意可空且不回填**：存量行没有办法推出真实创建时刻，
**编一个**（拿 `decided_at`？拿 0？）会让「等了多久」在存量行上**永远说谎**。
可空 ⇒ 读侧拿到 null 时**不显示**年龄，而不是显示一个假年龄。

## 7. 收件箱角标：一个必须会说「我不知道」的数字

【规格】§5.8 事件表里写 `ApprovalRequired` ⇒「收件箱计数 +1」，而 `web/hub/projection.ts`
的 switch 此前只有 `case "TaskStateChanged"`。补的时候真正的设计问题不是「怎么加」，
是**什么时候不许显示那个数**。

拼法是**水位线**：`pendingTotal`（REST 对账）+ `seq > totalAsOfSeq` 的事件增量。
直接相加会**双计** —— 快照读出来的那一刻，`(0, asOfSeq]` 里那些 `ApprovalRequired`
已经反映在 `pendingTotal` 里，而事件流会把它们**再推一遍**（SSE 建连时的续订本来就重投一段）。

三种「不许显示」：

1. **从没对过账** ⇒ `null`。显示 0 等于在**没有任何证据**的时候宣称「没有东西等你」。
2. **事件流出过洞**（`markGap`）⇒ 标不可信。少一条 `+1` 会让数**偏小**，
   而偏小比偏大危险得多：偏大到 0 会让他**不再打开收件箱**，
   而【规格】§19.1 那条「20 秒完成一次审批」的前提是他会看到有东西在等。
3. **算出负数** ⇒ `null`，**不夹紧到 0**。它在数学上不该发生，一旦发生就是
   「确实丢过事件、而且是在 `trusted=true` 的前提下丢的」的直接证据。
   夹紧会产出一个**最危险的合法值**：一个空的收件箱。

还有一条与 `link` 的区分：`link=down` **不**把角标标成不可信 —— 断线时数字只是
停在断线那一刻，那是「**旧**」不是「**错**」，界面该画一个旧的标记（读 `link`），
而不是画一个「未知」。把两者混起来会让每次网络抖动都变成一次「系统不知道有几张卡」。

更旧的审批快照**整份丢掉**（`asOfSeq < totalAsOfSeq` ⇒ 原样返回）。
这与任务快照的处理**刻意不同**：任务表每行自足，旧快照盖回来下一次会修好；
角标是**跨两次读取算出来的量**（总数 + 水位线之上的增量），
旧总数配新水位线会算出一个**两边都不是**的数 —— 既不是旧时刻的待批数，也不是现在的。
两次 `await` 交错就能发生，而它发生时**没有任何报错**。

### 7.1 ⭐ 而那条「水位线」判据，我第一版**一次都没执行到**

写完这一组我按老规矩做变异实验（把修法改回坏写法，看有没有用例红）。六发里五发红，
**唯独水位线那一挡全绿**：把 `applyInboxDelta` 里的 `if (item.seq <= i.totalAsOfSeq) return p`
改成恒不成立，**34 条一条不红**。

原因不是判据写错了，是**我那条测它的用例走不到它**：那发里 `asOfSeq = 10`，
而快照顺手把 `cursor` 也推到 10，于是重投的 9、10 先被 `seq <= cursor` 那一关吃掉，
**根本到不了水位线那一行**。我的注释在讲双计，代码路径在走"重复" ——
**一条断言可以既绿又既没有执行过它声称在保护的那一行**。

补的那一发造的是**只有水位线能救**的那个场景：**REST 读数跑到 SSE 游标前面**。
`pendingTotal` 是 Hub 在 `events.id = 20` 那一刻从库里数出来的，而 SSE 那条腿还停在 12
（13..20 在路上）。于是那八条**能通过重复检查**（`seq > cursor`），只被水位线挡住 ——
挡住是对的，它们已经在那个数里了。少了那一挡，一次刷新会凭空多出八张卡。
这也不是构造出来的边角：`GET /tasks` 在 SSE 建连时随快照帧来（同一个 seq），

## 9. 留给下一篇的一件事

`isPendingStatus` 我一开始写进 contracts，注释写的是「这条判据的**唯一**出处」。
写完发现**没有任何调用方** —— SQL 里只能是字面量，TS 侧用的是 `APPROVAL_STATUS_PENDING`。
本篇把它删了（连同没人读的 `APPROVAL_STATUS_DEFAULT`）。

**一条「唯一真相」的函数而无人读它，比没有这个函数更坏**：它会诱使下一个人以为
判据已经收口了，而在 SQL 那一侧根本没有。

留给下一篇的问题是：**`real-deps.ts` 那条 `AND status = 'pending'` 该不该改成绑参**。
改成 `?` 就能真正同源，代价是牵动那条 UPDATE 的**幂等**（`assertParamCount` 会跟着变，
而那条断言正是幂等承重的地方）。今天用一发**源码扫描**（`query.test.ts` ⑤）钉住
「SQL 里那一处字面量必须等于 contracts 的常量」。
**那条扫描在 SQL 改成绑参的那天必须删掉** —— 一条失去分母的断言比没有断言更坏。
