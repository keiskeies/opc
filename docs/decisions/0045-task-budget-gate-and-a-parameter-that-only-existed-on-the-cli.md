# 0045　花钱的门：`--task-limit-cents` 一直是必填参数而从来没挡过任何东西

> 复算命令在 §8。动手前先看 §1 那张表 —— 本篇全部的起点是**一次探针**，不是设计。

## 0. 这一篇补的是什么，以及它为什么排在 0044 后面

0044 把「收件箱是空的」那一格补上之后，我去做了一件一直没做的事：
**真的打开泵，喂一条已经花超的任务，看它会不会自己停下来。**

它不会。

`--task-limit-cents` 从 0041 §8 起就是**必填参数**，理由是「花钱的东西不给默认值」。
本篇要说的不是这个默认值立场坏了，而是**它的另一半根本不存在**：

> **必填只保证了命令行上写着这个数，没有保证这个数挡住任何东西。**

这一格不是设计缺口，是**读文档时的一次跳过**。
0041 §7 早就写了原话：「任务级上限今天是一句声明，不是一道闸。」
我写过那句话，然后在 0044 里实现泵的时候**把它读成了"以后再接"，接的时候没有回去看它**。
所以本篇第一条结论与我平时给这条流水线写的结论同族，只是这次落在我自己的阅读上：

> **「我记得那里有个待办」不等于「我实现时看到了它」。待办要生效，得在动手那一刻被读到。**

## 1. ⭐ 探针量到什么（改前形态，逐条实测）

一次 `pumpCharterCards` 的调用，一条已经花掉 500 美分的任务，上限给 100：

| 观察点 | 改前实测 | 应该是 |
| --- | --- | --- |
| 那条任务进不进候选 | **进** | 不进 |
| 起不起子进程 | **起一次** | 零次 |
| 卡建不建得出来 | **建出来**（`charter` 卡进 CEO 收件箱） | 不建 |
| `tasks.consumed_cents` | **500 → 504** | 500 |
| 终端上有没有一句话 | **没有** | 有，且说出该干嘛 |

于是"CEO 给一条想法设了上限、它自己把钱花超了"这条路径当时**只在账单上留痕**，
不在收件箱、不在终端、不在状态里。

第二发探针回答「上限那一侧该读谁」：

```
第一次跑，taskLimitCents = 1000  ⇒ budgets.limit_cents = 1000
第二次跑，taskLimitCents = 1     ⇒ budgets.limit_cents 仍是 1000
```

因为 `packages/hub/src/engine/runtime.ts:132` 那条 `ENSERT_TASK_BUDGET_SQL` 是
`ON CONFLICT(scope_type, scope_id, period) DO NOTHING` —— 那一列**第一次写进去就再也不改**。
**拿它当门 = 门永远按这台机器第一次启动时的那个数字关着**，
而那个数字可能来自半年前另一条命令行。

## 2. 门放在哪：候选 SQL 里，不是逐张卡的循环里

最直觉的写法是在那张卡起草之前判一下。本篇刻意没这么写，理由是**排序**：

候选 SQL 是 `ORDER BY created_at, id ... LIMIT 3`。
不在 SQL 里筛掉超限的，它们就**每轮都占住那三个候选位之一**，
而一条超限的**老**想法会把后面所有能补的想法**永久饿死** ——
这正是本文件头给 `ORDER BY` 写下的那条担心（"这轮没轮到它、下轮也没轮到它"）的另一个版本。
`taskLimitCents` 是"上限的上限"，它不该变成"排队优先级"。

**代价明写在这里**：被门挡住的想法**不出现在候选结果里**，也就是"本轮什么都没发生"
与"本轮有一批被门挡住了"在候选这一侧**长得一模一样**。所以另配一条**同源**计数（§3）。

## 3. 同一个谓词只有一个来源：`underTaskBudgetSql`

```ts
export function underTaskBudgetSql(t: string): string { … COALESCE((SELECT b.consumed_cents
  FROM budgets b WHERE b.scope_type='task' AND b.scope_id=<t>.id AND b.period='per_task'),0) < ? }
```

它导出成**一个函数**而不是就地写在 SQL 里，理由与 patrol 的 `kindOf` 同一条（0026 §0）：
这个谓词有**两个**使用点 —— 候选 SQL 用它筛，`CHARTER_BLOCKED_SQL` 用它数。
两处各抄一份字面，漂了的那一份不会有人发现：

- 候选那一侧漂了 = **门失效**（继续花钱）；
- 计数那一侧漂了 = **门明明挡了而终端一声不响**。

第二条尤其坏，因为它会让测试仍然全绿 —— 门在工作，报告在工作，只有**那个词**不出现。
绑参形状也刻意写成可以直接 `AND` 进去的样子：两个使用点用的必须是**同一个方向**的判据，
一边 `>=` 一边 `<` 就是自相矛盾（而自相矛盾的两份字面不会同时红）。

**实现过程中我自己写错过一次，写法值得留在这里**：第一版是
`underTaskBudgetSql(...).replace(" < ?", " <= ?")` 拼出"取反"的那一侧。
它既是字符串脆弱（改一个字面就悄悄失效），又**算错**：
`NOT (consumed < limit)` 应是 `>=`，我拼出来的 `<=` 会**正好漏掉 `consumed == limit`** ——
而"刚好花到上限"是这一格最常落到的那个取值。改成 `NOT (underTaskBudgetSql(...))`，
两个方向由同一个字面派生，不可能漂。

## 4. 两侧各读谁（这不是风格问题）

**已花的那一侧读 `budgets.consumed_cents`，不读 `tasks.consumed_cents`。**
仓库里有**两个**花费累加器：`LEDGER_SQL` 写前者那条路径上的 `tasks.consumed_cents`，
`ADD_TASK_BUDGET_SQL` 写 `budgets.consumed_cents`；实测一轮真起草**两列都加，都等于 4**。
所以读哪一列**在功能上今天看不出差别**，而正因如此现在必须选对：
**今日视图那条预算条读的就是 `budgets`**（`packages/hub/src/overview/today.ts:293` 求和它），
而【规格】§7.4 那张预算卡要显示的正是「已消耗 / 上限」。
门与界面**读同一个累加器**，"门说它超了而条还空着"才不可表达；
读另一列就是再造一个两源分叉（0041 §2 那一族）。

**上限的那一侧读参数，不读 `budgets.limit_cents`** —— §1 那张表就是原因。

**`<` 而不是 `<=`**：【规格】§7.4 写的是「达到预算阈值时」，达到就是达到。
⚠ `charter/budget-sync.ts` 那条 `silentOverBudgets` 用的是**严格大于**，两者**刻意不统一**：
那条问"已经超了多少"，这一条问"还要不要再花"。
写在这里是因为**两处写法不同而没人写下原因，就是下一次"顺手统一"的引信**。

**不看 `budgets.hard_stop`。** 那列今天全仓**没有任何代码能把它写成 0**
（三条 INSERT 都写字面量 1）。把它写进判据会得到一条**恒真**的判据，
而恒真的判据与恒绿的装饰**不可区分** —— 我造不出一发让它红的测试，
它就只是在骗下一个读代码的人。登记在 §6。

## 5. 「挡下了」与「有人说」是两件事，会各自单独坏

这是本篇真正的产品部分，也是我写完泵之后**第二次**在同一族上栽（第一次是 0044 §8 的 W10）。

门可以**正确地**不花钱、**正确地**不建卡、**正确地**写库，
而那个人看到的画面与**「泵根本没开」完全一样**：收件箱空的、任务不动、终端安静。
`gave_up` 那一格至少三次就完；门**只要不追加预算就一直挡着** ——
沉默从"错过一句"变成"永远没有那句"。

所以 `PumpRoundResult` 多了 `blocked`，`reportPumpRound` 在**早退之前**把它说出来：

```ts
for (const b of r.blocked) { … io.warn("…花钱的门关着…要接着走：追加预算，或把那条想法撤掉。") }
if (r.cards.length === 0) return;   // ← 这句在后面的话，被挡住的一批永远报不出来
```

那句"我先把这段写错了"是字面意思：我第一版把 blocked 循环加在 `return` **之后**，
测试当场红。红得恰到好处 —— 那个位置在**任何**"本轮有卡"的场景里都是对的，
只有"本轮全被挡住"这一支才暴露它，而那正是这一格存在的唯一理由。

**每任务只说一次**（`assemble.ts` 那个 `pumpBudgetWarned` 集合）。
泵 60 秒一轮，一条超限想法永远被挡 ⇒ 每轮都说 = **每天 1440 句同样的话**。
那不只是难看：噪音的实际后果是**这个人把终端静音**，
于是那句只说一次的「到上限不再试了」（`gave_up`）也一起被静音 ——
一个提醒的信号把自己淹掉了同一条通道上唯一的另一个信号。

## 6. 本篇没做的（不写成「换种方式做到了」）

- **`budgets.hard_stop` 恒为 1**：三条 INSERT 都写字面量 1，全仓无人读也无人写 0。
  本篇的门**不使用**它。等哪天"这个格子不许硬停"真有一个入口，§4 那条判断要一起改。
- **`budgets.limit_cents` 永不更新**（`DO NOTHING`）。门改用参数绕过它，
  但那一列**仍然躺在库里并且仍然会出现在任何直接读它的界面上**，
  而它可能在描述半年前那次启动。要么让它 `DO UPDATE`，要么让它别在那儿 —— 这是产品决定，不是我的。
- **追加预算之后不会再说第二次**：`pumpBudgetWarned` 记的是"这个人已经知道了"，
  不是"此刻是否仍然超限"。代价：**追加完又花超**不会得到第二句提示。
  选这一侧是因为 §5 那条静音风险；如果以后有了"额度动过"这个事件，它应该重新武装。
- **【规格】§7.4 那张预算卡仍然不存在**：规格要的是**琥珀以外**的一张卡，按钮是
  追加预算 / 维持预算 / 终止任务。本篇给的是**终端上的一句话**。
  真卡需要【规格】§7.1 里 `BUDGET_PAUSED` 的合法入边（只有 `IN_REVIEW → BUDGET_PAUSED` 一条）
  与"终止"的落点 —— 两格都不在，登记在 0041 §7 与 0044 §9 旁边，**不是本篇能自己补的**。
- **追加预算这条路本身没有入口**（"去追加"这句我在终端上说了，但没给端点）。
  `human-decide` 那侧只有 approve 有出边；这是 0044 §9.1 那一格的另一个面。
- **`tasks.consumed_cents` 与 `budgets.consumed_cents` 双列并存**没被合并（§4 只是选了边）。

## 7. ⭐ 等 CEO 拍的一项：`budgets.limit_cents` 那一列该怎么办

本篇的门**绕开**了那一列（读参数），所以"门失效"这一格已经堵上。
但绕开不等于它没问题 —— 它今天**仍然在被界面读**：

`packages/hub/src/overview/today.ts:293` 那条 SQL 求和 `limit_cents` 当作 `declared`，
也就是**今日视图那条预算条的右半边**。而 §1 第二发探针量到的是
**那一列第一次写完再也不改**。两件事拼起来的可复现后果：

> 第一次用 `--task-limit-cents 1000` 起，第二次改用 `1` 起。
> 门按 **1** 关着（正确），**而那条预算条仍然显示"上限 1000"**（错的），
> 于是同一条任务在**同一台机器**上有了两个"上限"，
> 一个能挡住钱、一个只在屏幕上好看。

这不是"少显示一个数"，是**屏幕上那个数会参与你的判断**：
你会看着"还有一千的额度"而决定不给这条想法追加预算，
而实际上系统一分钱都不再为它花 —— 你基于一个不存在的额度做了决定。

三个候选（都要改语义或改界面口径，所以不在实现层定）：

- **(A)** 三条 `INSERT INTO budgets` 改成 `ON CONFLICT … DO UPDATE SET limit_cents = excluded.limit_cents`
  —— 那一列变成"最近一次声明的上限"。**代价**：同一任务被两个不同参数的进程先后跑到时，
  **最后一次说话的那个赢**，而"谁最后说的"取决于启动顺序而不是任何意图；
  追加预算这条路（还没有入口，见 §6）将来也要跟它抢同一格。
- **(B)** 那一列**只作为初声明的历史**保留，界面**不再读它**，
  预算条右半边改成读**当前进程生效的参数**（由服务端随响应发下来）。
  **代价**：`/today` 要多带一个字段，而"上限"这件事从库里搬进了进程 ——
  离线读库的人（审计、报表）看到的是**没有上限的账本**。
- **(C)** 维持现状。**代价就是上面那段**：界面上的上限可能是半年前那一次启动的。

我倾向 **(B)**：门与界面**已经**共用 `consumed_cents` 这一个累加器（§4 的取舍），
上限那一侧也该只有一个来源，而**那个来源必须与真的在挡钱的那个是同一个** ——
否则本篇修掉的只是"钱花超"，没修掉"屏幕上说它没超"。
但 (B) 要动 `/today` 的响应形状，**改契约不属实现层**，所以停在这里。

## 9. 判别力：变异逐条，以及一条**无效**变异是怎么被认出来的

**门的这一侧**（`charter-pump.test.ts` I 组，7 发）：

| 变异 | 结果 |
| --- | --- |
| G1 把门整条删掉（**改参数个数**） | **无效** —— 红一片，那是编译不过，不是判别力 |
| G1′ 换成**恒真**的门（参数个数不变） | **恰好 4 发红**，全是门那四发 ⇒ 这才是 G1 想要的证据 |
| G2 比较号写反 | 红 |
| G3 门改读错的列（`scope_type='nope'`） | 红 4 |
| G4 绑参错序（上限被绑成 `perRound`） | 红 1 |
| G5 `blocked` 在早退之后才算 | 红 1 |

**说出来的这一侧**（`assemble-pump.test.ts` H 组，3 发）：

| 变异 | 结果 |
| --- | --- |
| A1 早退移到 blocked 循环之前 | 红 2（"说出来了" + "只说一次"） |
| B1 去重拆掉（每轮都说） | 红 1 |
| C1 整段不报（沉默的门） | 红 2 |

**G1 那一发的教训要单独写。** 这是本仓第 N 次撞到同一件事：
`delete the gate` 这个形状顺手的写法是**把参数一起删掉**，
于是一堆测试因为**参数对不上**而红，而我很容易把那一片红读成"这一发很有判别力"。
有效的形态是**保留参数、让判据恒真** —— 它回答的才是"有没有人判这个门"，
而不是"编译器在不在工作"。0044 §8 那两发无效变异是同一个坑的另外两种形状
（插死代码 / 新增一处而原处仍在），这次是第三种。

**「只说一次」那一发带了分母。** 它除了断言只出现 1 次，还断言**确实跑了 5 轮**。
少了分母，"只说一次"与"只跑了一次"**不可区分** —— 这一族在 0042/0044 里被叫做恒绿装饰，
而它最常见的诞生方式就是"我断言了次数而忘了断言总数"。
