# 0062　动作 1 那句「不用改形状」—— 前提实测不成立，于是两维都落在写侧；外加顶层文档第一次进入「编号不许指空号」

## 1. 一句话

O4 动作 1 的原话是把 `sameFamilyReviewBlock`「挪进 `dispatch` 的活路径（它现在是纯函数，不用改形状）」——
**这条前提实测不成立**：那一族七个具名函数有 **5 个在 `src` 里一个调用点都没有**，另两个的唯一调用方
`harness/verifier.ts` 自己躺在死模块基线里。所以这篇交付的不是函数搬家，是**判据本身**在写侧收紧：
`CEO_APPROVED_SQL` 补上**身份**那一维（`decided_by = 'ceo'`），`approveCard` 给豁免卡补上**理由**那一维
（空理由的豁免批准返回 `waiver_note_required`），两发变异各钉住一维、各红一发。
⭐ 副题一件，形状与 0061 §7 完全同形、隔一轮踩在下一层：我在设计文档 O4 落点表里引用「0062」的**那天它不存在**，
而全套 2544 发**一发没红** —— `doc-ids` 那条「编号不许指空号」的判据在**顶层文档**（功能优化设计 / 设计文档 / 附录A）
这一类上**从来没生效过**，就像它当年在迁移文件那一类上从来没生效过一样。补法照抄 0061：**先扩取材、确认它真能红、
再写本篇让它绿**。

## 2. 先量前提，再动手：五个零调用点，另两个吊在死模块上

设计文档那张表把第 3 行写成「不在活路径上」。动手前我量了一遍，那句话其实**说轻了**：

| 函数 | `src` 调用点 | 在哪 |
| --- | --- | --- |
| `gateConfigBlock` | **0** | — |
| `selfReviewEdgeBlock` | **0** | — |
| `independentReviewerPath` | **0** | — |
| `forbiddenRemovalAttempt` | **0** | — |
| `unauthorizedAttemptPayload` | **0** | — |
| `sameFamilyReviewBlock` | 1 | `harness/verifier.ts` —— 而它自己登记在 `test/arch/dead-modules.ts` 基线（零生产调用方） |
| `evaluateGate` | 1 | 同上 |

量法是一个带**阳性对照**的探针（`.tmp/o4/probe-row3.mjs`）：同一份扫描代码先去数【已知存在】的调用点，
数不出来就 exit 4，而不是把 0 报成一个干净的读数。这条纪律当场抓到了**探针自己**：第一版我用 heredoc 写，
`\b` 被 shell 吃成真退格符，于是它对 `evaluateGate` 报 0 —— 与我读码所见（`verifier.ts` 里明明有一处）矛盾。
拦住我的不是「我觉得这个数不对」，是阳性对照先红了。**「红发 0」与「探针死了」输出相同**这件事，0061 §5 记过一遍，
这次是它的镜像：数不出【有】的时候，先怀疑数法。

⚠⚡ **round334 口径标注：这张表从头到尾没写它的尺子是【跨文件】。** 表把 `selfReviewEdgeBlock` /
`independentReviewerPath` 记成 0 调用点，而它们各有一处**同文件**调用（`author-reviewer.ts` 的
`gateConfigBlock` 在 :215 / :183 调它们；那两行字节在 `0e2f2c9`（2026-11-10）就在，**早于本篇落库的
ffae248（11-18）**，round334 在 ffae248 的 blob 上按两种口径各数过一遍 ⇒ 表在当时就没错，
错的是没写尺子）。今天读这张表的人会把「0 调用点」读成"没人用"，而真相分三层：
`sameFamilyReviewBlock` 有 1 个跨文件调用方（verifier）；`gateConfigBlock` **全仓零调用方**；
那两个被 `gateConfigBlock` 调的，调用方自己就是孤儿。**数没错、口径没写，是行号表的第二种骗法** ——
与本行上方那条「数不出有，先怀疑数法」是同一族的下一层：数法对，也可能因为它自己没被写下来而误导。
复算机器：`.workbuddy/round334-o4-callsites.probe.mts`。

⚠ 诚实一条：我在台账初稿里把这一族写成「六个函数、5/6 为零」，**实际探针列了七个名字**。发表前复跑探针才发现——
写进文档的那个「6」是我凭记忆敲的，不是量出来的。设计文档与台账的四处已按实测改成「七个具名函数、5 个零调用点」。

「它是纯函数，不用改形状」这半句也对一半：`sameFamilyReviewBlock` 确实是纯函数（`producer / reviewer / approval`
进，`BlockResult` 出），但它验的是**凭据本身** —— `approval.approvedBy !== CEO_ROLE_ID` 拒、`reason` 空拒，
而 `dispatch` 的 `reviewGate` 拿到的是**已经算好的** `approvedByCeo: boolean`（出自 `ceoApproved`，一条 SQL）。
把它整块挪过去不是「不改形状」，是把**读卡再验凭据**这件事搬进每一轮 dispatch —— 而那件事的正确发生地点是
**批准落库的那一刻**，不是每次查询。所以搬家的形态错了，**判据的内容**才是能复用的东西。

## 3. 能落地的是判据：两维都收紧在写侧

0061 §8 第 4 条留下的原话是「身份与理由必须在**写侧**收紧」。两维各落一处：

**甲、身份。** `CEO_APPROVED_SQL` 从「`status = 'approved'` 就算批过」变成

```sql
… AND status = 'approved' AND decided_by = 'ceo' LIMIT 1
```

证据链：全仓 `UPDATE approvals` 共三处（`http/real-deps.ts`、`engine/approve.ts`、`policy/auto-approve.ts`），
前两处写的是 `'ceo'`（`CEO_ACTOR.actorId` / 写死的 `"ceo"` 两处），**只有第三处**写 `'policy-engine'` ——
而那个模块自己登记在死模块基线里、今天零生产调用方。⇒ 这一维**今天零误伤**，它买的是
**那条路被接上的一天**：策略引擎一旦真能批卡，它写的一行就会直接满足这道活门，而规格 §5.9 第 1 条那个批准口存在的
理由恰好是「人来承担同源审阅的风险」。机器自己批自己审，是那一格里最不该出现的一种「批过了」。

**乙、理由。** `approveCard` 在事务里、**认领卡片之前**判：`button === "approve"` 且 `card_key` 以豁免前缀开头
且理由为空 ⇒ 返回 `waiver_note_required`，什么都不写。三个位置选择各有理由：

- **写侧而非读侧**：读侧一旦要求理由，今天已经存在的「approved 而理由为空」的行就不再算凭据 ⇒ 门继续拦 ⇒
  每轮建一张**新的** pending 卡 ⇒ 收件箱永远清不掉 —— 那正是 0061 刚修掉的「烧键」形状。写侧拦截让
  「无理由的豁免批准」**到不了** approved 那一行，存量行照旧有效，读侧保持干净。
- **认领之前**：拦下时一条审计都不写。决策是 append-only 的，写一条「CEO 批了」而理由缺失，比不写更坏；
  卡保持 pending，CEO 补一句理由重发一次就好。
- **只收豁免卡**：`requiresNote` 的按钮表只要求 `reject_with_comment` 带理由，普通批准（预算、岗位书）
  空理由是对的、不该改。豁免卡是唯一「**理由即凭据**」的一种 —— `sameFamilyReviewBlock` 的原话是
  「空理由的批准等于没有批准」，那条是读侧判据，这一发是它的写侧对偶。把整条批准改成必填理由是
  另一个产品决定，不该顺手做。

豁免前缀字符串现在**只有一个家**：`SAME_FAMILY_REVIEW_KEY_PREFIX`（`approvals/cards.ts` 导出），
`dispatch` 建键与 `approve` 拦卡 import 同一个。此前 `"same-family-review:"` 字面量散在 dispatch 一处，
而 approve 那边**根本不知道有这个前缀** —— 判据要读一张卡是不是豁免卡，先得认识它的键。

## 6. `doc-ids` 在顶层文档这一类上从来没生效过

我在 `docs/OPC-OS-功能优化设计.md` 的 O4 落点表里写了「已在写侧落地等价控制（0062）」，那天 0062 不存在，
守卫全绿。查 `test/arch/doc-ids.test.ts` 的取材：`decisions/*.md` 全体 + `INDEX.md` + `migrations/*.sql` ——
**顶层文档不在其中**。而 O1–O14 的落点与读数**全写在顶层那份【功能优化设计】里**（实测它引用 16 个编号）。
这不是「又来了一个新洞」，是 0061 §7 那个洞的**同一层楼板**：那一轮发现迁移文件不在射程，这一轮发现顶层文档不在射程 ——
取材清单式守卫的失效方式永远是「下一类不在清单上」，而**引用决策编号最勤的两类文件**（迁移、落点文档）恰好都不在。

补法照抄 0061 的顺序：先扩取材（顶层三份 md 全收，INDEX 除外它已在），**确认它真能红** —— 实测点名
`OPC-OS-功能优化设计.md>0062` —— 再写本篇让它绿。三层退化自检与迁移那三层同构（key 在场 / 内容非空 /
空允许集下真的从这一类抽出 ≥1 个编号 —— 下限写 1 不写 16，它防的是**通路坏掉**，不充当账本）。

顺带抓到一条**注释里的计数**：`http/real-deps.ts` 那段写着「approveCard 有【七】条 outcome，只映射得到两条，
剩下五条……其中两条语义是请求不成立」。本篇新增 `waiver_note_required` 之后三个数**全错了**
（八条 / 六条 / 三条）。这条没有任何测试会红 —— `doc-refs` / `comment-citations` 判的是 § 引用与小节号的存在性，
不判「注释里写的数目对不对」。我是写这篇要去抄「这条 outcome 在 HTTP 侧映射成什么」时读出来的。
注释里凡是**数出来的数目**，和「文件:行号」是同一类东西：改 Union 的人不会想起回来数分母。

## 8. 那条「假基线」的纪律，在引用它的这一批里又演了两遍

0061 §5.1 记的就是「我拿一条测的是我的命令而不是文件的命令当基线」。这一批我要量的数是
「biome 对我改过的文件与 HEAD 同数」，方法是对比工作树与 stash 掉改动之后的计数。两遍都坏了：

1. 第一版把**九个**路径一起交给 `git stash push`，其中 `rejected-waiver-still-asks.test.ts` 是**未跟踪**的新文件
   ⇒ git 报 `pathspec ... did not match any file(s)` 而**根本没建 stash**，我的 `&& echo` 链把失败吞了
   —— 于是「HEAD」量的还是工作树本身，两边当然同数。拦住我的**不是**数字看着不对（它看着很好），
   是 `&&` 链里那个 `(stashed)` 没打出来。
2. 改成只 stash tracked 文件之后 stash 真建起来了，立刻量出**净 +1**：`doc-ids.test.ts` 里我新写的一行超宽。
   而我上一版报告里已经写着「14 err / 2 warn，与 HEAD 同数」—— 那句话在**发表时**就是假的。

修成命名局部变量之后逐文件对账：八个 tracked 文件与 HEAD **逐文件同数**，新文件 **0** 条，全仓 **290/109/2** 与基线同数。
教训不是「下次记得看退出码」这么轻：**两向对比有三个前提** —— stash 建没建、还原没还原、
基线侧包不包含未跟踪文件 —— 每一个都得有输出证据，少一个，那条对比就从证据变成装饰。
⭐ 同一批里还有一次**同族的记账错**：我改了两处引用（规格的 `§5.9` 加限定词、`§待办` 改成真小节号），
就在台账写成「守卫当场拒了两处」—— 而实测守卫只拒了**一处**，另一处形状它压根不匹配（§7 第 6 条）。
**「我做了两件事」被记成「守卫抓了两件事」**，把自己的动作当成了守卫的证据 —— 与上面 stash 那两次一样，
三个错都不是判据坏了，是**我把自己算进了读数**。而这一条最该记住的地方是：
它发生在我把 0061 §5.1 写进自己那篇文档的同一次工作里。读过一条教训不等于会用那条教训。
