## 1. 一句话

`POST /approvals/:id` 这一条链上，我原先写下的三句假设**全部**被实测否证：

| 我写下的 | 实测 |
| --- | --- |
| 「并发那一支返回 false，不会打架」 | 同一条连接两次并发决策 ⇒ 一支抛 `cannot start a transaction within a transaction`，**审计只落 1 行** |
| 「决策落库之后图接着跑」 | 图在跑节点时，CEO 的任何审批**都写不进去**（两种形状都测了，见 §2） |
| 「审计写了，前端自然就更新了」 | `appendAudit` 不经 recorder ⇒ **一个字节也没广播**，而 `events.id` 已被消费掉 ⇒ 活着的 SSE 订阅看见一个**seq 空洞** |

三条都不是判据写错，是**形状**写错：三条的共同成因是我拿「调用顺序」去想并发问题，
而这里的失败全部发生在**事务与连接**这一层 —— 那一层不报错的时候最贵。

## 2. 三条实测（都可复现，本机 node:sqlite，不需要任何框架）

复现脚本的形状：`/tmp/opc-probe/p1|p2|p4|p5.ts`（临时目录，不入仓，理由见 0007 一脉：
不往 `node_modules` 塞任何东西）。下面给的是**当场的输出**，不是推断。

### P1 同连接、两个窗口各批一张**不同**的卡片

```
【P1】同一连接上两次【并发】决策（不同卡片）：
   fulfilled ok=true
   rejected ⟵ cannot start a transaction within a transaction
   events 行数 = 1
```

成因只有一行代码：`txScope` 在 `BEGIN IMMEDIATE` 与 `COMMIT` 之间写的是
`await body()`（`checkpoint/tx-scope.ts:82`），于是**即使 body 全同步**，
它也让出一个微任务。第二个 `BEGIN` 就落进第一个事务还没结束的那个窗口。

我原来的注释写的是「并发那一支 info.changes 是 0」。**那句在当时的形状下是错的**：
并发那一支根本走不到 UPDATE，在 `BEGIN` 就炸了，`changes` 那个值它【拿不到】。
`WHERE status = 'pending'` 那道幂等闸门在这次故障里**完全没参与** ——
它挡的是「两次都写成了」，实测是「第二次压根没执行」。

（**这句更正的适用范围要划清**：改走队列之后，那一行注释【又是对的】了 ——
串行化之后两次点击都真的走到 UPDATE，第二次确实拿到 `changes = 0`。
所以本节否证的是「我基于那句推断出的并发安全」，不是那句本身。
现在 `CLAIM_APPROVAL_SQL` 上面那段注释里那句照旧留着，读的人别把它当被撤回的话。
（这里刻意用**常量名**而不是行号指它：doc-refs 守卫自己就写着「更好的写法是把行号换成
可 grep 的特征串」，而我要说的是【那句话还在、还对】—— 那是个语义性质，
用行号去钉它，等于让一次无关的代码挪动把我的更正声明变成一条红守卫。）

> 这条尤其值得记：我把幂等做对了，然后基于「幂等做对了」推断并发安全。
> 闸门是真的，结论是假的。

### P2 / P4 图正在跑节点时，审批写不进去

P2（同库同连接）：

```
【P2】图正在跑节点（超步事务持有同一条连接）时，CEO 点批准：
   决策结果 = ⟵ 报错：cannot start a transaction within a transaction
   超步事务 = step-done
   卡片 status = pending
```

P4 用**真的** `SuperStepAuditor` + 织入后的 saver 复验，不靠我自己模拟：

```
【P4】超步事务是否横跨节点执行？
   节点体内、await 之前 recorder.inStepTx() = true
   await 之后（仍在同一超步内）CEO 点批准 ⇒ ⟵ 报错：cannot start a transaction within a transaction
   inStepTx() = true
   图跑完后 a1.status = pending
```

`inStepTx() = true` 出现在 `await` 前后两次，是这一节的**承重证据**：
超步事务**确实横跨节点体**（`onStepStart` 开事务，下一次 `put` 才提交），
所以「节点在跑」= 「写锁握着」= 「审批进不来」。不是我的夹具的形状，是编排层的形状。

### P3 / P5 换成单写者队列之后：错误换了，**故障没换**

`real-deps.ts` 改走 `WriteQueue` 之后（§3 的修法），同样的场景：

```
【P5】图持有超步事务 6000ms（节点里一次模型调用），期间 CEO 点批准。
      决策写入已改为走 WriteQueue（与图是两条连接）：
      决策 = ⟵ 抛错：database is locked （耗时 5444ms）
      卡片 status = pending
```

5444ms 不是随机数：`BUSY_TIMEOUT_MS = 5000`（`db/pragmas.ts:19`）。
队列把「同连接重入」修好了，**跨连接的库级写锁修不好** —— SQLite 的写锁是库级的。
超步持锁 6000ms，等 5000ms 就报 busy；持锁 200ms 则排队能等到（P3 里 5267ms 那一档同理会红，
区别只在等多久）。**「一次模型调用」和「一次审批写不进去」之间是因果，不是巧合。**

这条**不由实现层修**，见 §7。

### 顺带测出的一条：`grep -rn "new WriteQueue" packages/hub/src` ⇒ **0 命中**

规格 §5.5 那台「进程内唯一写者」在 src 里**从来没有生产调用点**，只有它自己的测试。
也就是说规格 §5.5 一直是纸面性质，而 `SuperStepAuditor` 与 `SqliteWALSaver` 都在
裸 handle 上自己开事务。`http/real-deps.ts` 现在是第一个走队列的写入方 ——
这是**进展**，不是「队列本来就在」。

## 3. 本篇改掉的三处（都能测，红过）

| # | 改动 | 挡住什么 |
| --- | --- | --- |
| 1 | `applyDecision` / `insertTask` 的入参从 `DatabaseSync` 改为 `Writer`（= `Pick<WriteQueue, "node">`） | P1。串行化由队列给，「同连接两个事务」在参数上写不出来 |
| 2 | 决策写成之后 `publishPersisted`，时机在 `node()` **返回之后**（= 已提交） | 事件不可见 + seq 空洞（§4） |
| 3 | `buildHubDeps` 收 `queue` 而不是 `db`；对外读走 `queue.readConnection()` | 装配入口留着一个「能写也能读、写不走队列」的形状 |

`buildHubDeps` 那处是本篇里我自己回头看出的**二阶问题**：我只在 `applyDecision`
那里堵了洞，而装配入口**仍然收一个裸 handle** —— 下一个写入方从入口拿到的还是那个错形状。
推广之后「用错连接」这件事要写出来得先绕开类型。

三条新断言，每条都单独红过（各一次变异）：

| 断言 | 变异 | 结果 |
| --- | --- | --- |
| 两次并发决策都成功、各留一条审计 | 把夹具里的 Writer 换成「不排队」的实现 | 该条红，其余 23 条绿 |
| 广播的 `seq` 就是审计行的 `id` | 注释掉 `publish` 那一行 | 红，报「订阅在 2000ms 内没有收到任何事件」 |
| 广播那一刻**另一条连接**已读到 `approved` | 把 `publish` 挪进事务内（用真 seq，避免总线校验替我报错） | 该条红，其余绿 |

第 2 条那一例**最初是挂住而不是变红**的 —— 我写的是裸 `await it.next()`，
没有广播就一直等，120 秒后被 harness 挪到后台。已改成 `nextBounded()`（限时 2000ms）。
一条在真实回归下**挂住而不报错**的测试比漏测更坏：CI 上看到的是超时，
不是「ApprovalDecided 没广播」。这条写进夹具注释里了。

第 3 条为什么要绕道「另一条连接」：同连接**看得见自己未提交的行**，
在事务里读一次 `approved` 会恒过，看着像断言、实际什么都没证明。
只读连接是 WriteQueue 自己开的第二条，WAL 下读不到未提交数据 —— 正好是判据要的那个视角。

### 回头看出的第三阶问题：`publish` 当时是**可选参数**

写完上面三条之后回头读 `applyDecision` 的签名，发现 `publish?` 带着默认值「不广播」。
而 §1 第三条讲的故障**恰好就是**「写了库、没广播」 —— 我一边记录这个缺陷，
一边在签名上给它的成因留着合法形状：装配时忘了传，TS 不响、测试全绿、
只有前端用户能看见（每次批准把连接标脏一次 + `resnapshotCount` 涨一格）。
改成**必填**，测试要「不关心广播」时**显式**传 `NO_PUBLISH` ——
「我选择不广播」与「我忘了广播」在代码上必须长得不一样。

改完顺手得到一个**先前没有的**不变量，它不是签名改动的副产品而是同一处判据的另一半：
**没落库的决策一个字节都不许广播**。四条 `return false` 的路径
（卡片不存在 / 已被批掉 / 非 pending / 并发抢输）各加一条 `spy.calls.length === 0`。
理由不是「干净」：那几次写入**没有消费任何 `events.id`**，
广播出去只能带一个**编出来的** `seq`，而投影层见 `seq > cursor + 1` 就标 `stale`（§4）。
所以「库里没写」与「没发事件」必须是同一件事的两个说法，不能只钉一边。

| 断言（本轮后加的 4 条） | 变异：让 `wrote === null` 那一支也广播 | 结果 |
| --- | --- | --- |
| 四条 `false` 路径各一条「没广播」 | 抢输那一支照发 `ApprovalDecided` | **恰好这 4 条红，其余 21 条绿** |

这条变异的红名单形状本身就是信息：**四条、全是新加的、零误伤**。
上一轮 §3 那三条各只红一条，因为那时一条不变量只有一处载体；
这轮的不变量是「四路同构」，所以它应当在四处同时红 —— 只红一条反倒说明有一路没被钉住。

顺带一条**没做**的：`buildHubDeps` 里 `publish` 是包了一行的闭包而不是直接传
`o.bus.publishPersisted`。原因是签名不同（总线收的是 `(e, seq)`，而这里要在
提交后拿 `wrote.seq`）；**没有**给它写注释，因为我原写的那句
「忘记传的后果记在 buildHubDeps 的注释里」指向一段**不存在的**注释，
而那段注释要讲的东西现在由**类型**讲掉了（必填 ⇒ 不传编译不过）。
签名处的注释因此重写为只讲仍然成立的部分。

## 4. 一处偏离规格：**新事件类型** `ApprovalDecided`

规格 §5.8 那张事件表是**六行**，没有「CEO 批完了」这一类。规格 §5.8 结尾那句
「CEO 在手机上批准战略提案时，Hub 恢复该图的执行并广播 `TaskStateChanged`」
把这一格的更新挂在**图恢复之后**那条状态跃迁上。实现时我按它写了，然后测出两件事：

**① 「靠后面的 `TaskStateChanged` 带回来」在这条路径上不成立。**
`applyDecision` 写的是 `approvals` 那一行 + `events` 那一行；`tasks.status` 由**图**写。
所以批准之后、图真的推进之前，那段时间里没有任何事件会来。而这段时间正是
§7 那条锁语义决定的 —— **图在跑就是写不进去**。收件箱那个琥珀色卡片（§16.1）
在此期间**停在待批**，而它下面那行 `decided_by` 已经有值了。

**② 不广播会造出一个 seq 空洞，而投影层把空洞读成「链路坏了」。**
`appendAudit` 消费掉一个 `events.id` 却不经 `publishPersisted`（只有
`AuditRecorder.#flush` 会调，而 `applyDecision` 不在超步事务里、用不到 recorder）。
前端 `packages/web/src/hub/projection.ts` 的三态判定是
`seq > cursor + 1 ⇒ markGap ⇒ link = "stale" ⇒ 去拉快照`。
所以后果**不是**「少一个更新」，而是**每次 CEO 点批准，就把连接标成降级一次**，
连带 `resnapshotCount` 涨一格。这个数在投影层是「这一轮里流出洞几次」的观测点，
被我自己的写入路径污染之后，它就不再表示它声称表示的东西。

两条都不在计划里，所以我做的是**加一个 kind**，代价全列在这里：

- **丢了什么**：`DomainEvent` 是计划 pin 死的接口形状（计划正文列了那六个 kind）。
  加一个 ⇒ 任何照计划抄的客户端会收到一个**它不认识的 kind**。
  `feedItemSchema` 是 `passthrough()` 且 `kind` 只要求非空字符串，
  投影层 switch 有 `default` 分支（只推 cursor、不改 tasks），**所以现有前端不会炸** ——
  这一句是本机可测的（`test/web/hub-projection.test.ts` 里加了那条断言）。
  但飞书卡片（Task 4.4）与移动端（Task 4.2）到手时，这个 kind 需要各自处理。
- **为什么不复用 `ApprovalRequired`**：它的语义是「**去**批准」（规格那张表：
  收件箱计数 +1）。把「批完了」也发成它，任何按 kind 计数的消费者会**加两次**，
  收件箱计数从此恒不对 —— 而 §16.1 那个计数恰恰是 Task 2.6 的验收项。
- **为什么不复用 `ReviewDecided`**：规格 §5.8 明写它来自**门控判定**（通过/打回/升级），
  actor 是审阅者。CEO 点按钮不是门控判定。混进去之后，审计里
  「机器判的」与「人点的」只能靠 actor 猜 —— 而 `actor_type` 三值存在的全部理由就是这个。
- **`events.action` 仍是 `approval`**：§22.1 那十个值是 append-only 枚举，
  我不能为实现方便加第 11 个。库里两类事件靠 **actor_type** 区分：
  `ApprovalRequired` 是 `system/hub`（图停下来了），`ApprovalDecided` 是 `human/ceo`。
- **`target` 与 `ApprovalRequired` 同为卡片 id**（刻意）：「这张卡被要求批准」与
  「这张卡被批掉」必须 join 得起来。

顺带把一处**我差点写错的性质**留在代码里：我一开始在注释里写「外键只看已提交的数据，
所以排队才能让父任务先可见」。**那句是错的** —— 同一连接看得见自己未提交的行，
FK 检查也在那条连接上做。队列在这里的真实收益只是**装配一致性**（一个写入方
一半走队列一半不走，走的那半就得去猜没走的那半何时提交）。错的那句已删，
因为「听起来很对的机制」是本仓反复出现的失效形状。

## 7. 需要 CEO 拍的一项：**节点执行期间的写锁语义**

这条**不由实现层定**，因为三个候选各自改的是**产品行为**，不是代码风格。
先把事实摆平（P4 / P5，都实测过）：超步事务横跨节点体 ⇒ 握着库级写锁 ⇒
`busy_timeout` 只有 5000ms ⇒ **一次超过 5 秒的模型调用期间，CEO 点批准必定失败**，
而且是 500 + `database is locked`，卡片停在 pending。

- **U 缩短持锁范围**：节点执行**不持有**事务，只在超步边界开短事务写 checkpoint + events。
  这是 0003 §3.2 已有的思路（「invoke 级事务会把写锁握几十分钟」），但**当前实现
  还差一步**：`onStepStart` 开了事务之后，节点体整个跑在里面。
  代价：0003 §6 第 2 项那条「checkpoint 与 events 同一事务」需要重新表述 ——
  它会变成「同一超步的 checkpoint 与 events 同一事务，而**节点执行不在任何事务里**」。
  这条我认为**方向是对的**，但它改的是本篇之上那一层，且要重跑 0003 那批实测，
  所以我**没有**在实现这一轮里顺手做。
- **V 把审批写进只读路径之外**：审批走**另一条库**或内存队列，由后台线程落库。
  我不建议：单用户本机引入第二份事实源，与规格 §5.5「唯一写者」正面冲突。
- **W 接受它，改**用户看到的东西**：批准请求排队等锁（提高 `busy_timeout`），
  界面上明确显示「正在等当前任务让出，约 N 秒」。
  代价最直白：CEO 手机上点批准，可能要等一次模型调用跑完才生效。
  如果产品接受「批准不是立即生效」，W 是**改动最小**的一条；
  如果不接受（我猜 §19.1 那句「键盘 20 秒完成一次审批」暗示不接受），就得走 U。

**我的倾向是 U**，理由是 P5 那个 5444ms 说明这不是概率性问题：
任何一次正常的模型调用时长都会踩过 5000ms，也就是说**每次审批撞每次**。
但 U 要动 0003 认定为本仓最贵那一类静默的防线（checkpoint 与 events 的原子性），
**换它之前我要你确认**「批准立即生效」值不值那次重构。
在你回答之前，`real-deps.ts` 里那条链的状态是：**图空闲时可用，图在跑时必失败**，
而这两种状态在 UI 上**看不出区别** —— 这句是本篇最该被读到的一行。
