## 1. 一句话

计划要求「保存时 Hub 重跑校验 → 同一事务写 `role_charters`（version + 1）与
`delegation_graphs`（新版本）+ 一条前后快照审计事件」。写之前先量了两件事，
两件都和规格的假设不符：

1. **`tasks.graph_version` 这一列从建库起没有任何代码写过。**
   `git show HEAD~1:packages/hub/src/http/real-deps.ts | grep -c graph_version` ⇒ **0**。
   每条任务都躺在 `0001_init.sql:49` 那个 `DEFAULT 1` 上，
   而 `delegation_graphs` 里 1 号版本**一行都不存在**。
   于是规格 §18.4 阶段 3 那句「旧任务从 Checkpoint 恢复时加载**创建时版本**的图定义」
   不是「没做完」，是**前提不成立**：所有任务的「创建时版本」是同一个假的 1。
   顺着这条，计划要求的两条 Test（「运行中任务仍用旧版图」「新任务用新版图」）
   在补上写入方之前**只能对着恒为 1 的列断言**，那是恒真判定。
2. **从一张组织图造不出一份合法岗位书**，所以 §18.4 ③ 那句
   「同一事务写 `role_charters`（version + 1）」按字面做不到。细节与处置在 §3。

## 2. `graph_version`：这列是谁写的，以及为什么必须在 INSERT 那一发里

补法有两种，我先写了错的那种，留在这里。

**错的那种**：建任务照旧（吃 `DEFAULT 1`），随后补一条
`UPDATE tasks SET graph_version = ? WHERE id = ?`。
它**跑起来是对的**——最终落库的值与现在的实现逐字节相同，
所有断言终值的用例全绿。它留出两段窗口：

- **INSERT 与 UPDATE 之间**，库里存在一行 `graph_version = 1` 而 v1 不存在。
  崩溃正好落在这中间就**永久**留下这么一行。
- **更要紧的是取数时刻**：「读最新版本」发生在事务外，
  于是 `读到 v6 →（别人提交 v7）→ 这一行落成 v6`，而它是 v7 生效**之后**建的任务。
  `WriteQueue` 排的是**事务之间**的顺序，两次 `node()` 就是两个事务，
  中间那次提交完全合法。症状是「这条任务用了旧汇报关系」，**一句报错都没有**——
  而 §18.4 建版本化要防的正是这一件事。

**现在这种**：`INSERT INTO tasks (... , graph_version)` 直接带这一列，
取数走 `org/commit.ts` 的 `currentGraphVersion(db)`，
与 INSERT 共用 `node()` 回调里那条连接、那个事务。
于是版本永远取自库、由 Hub 说了算，不接受调用方传值。

这条区别**必须有用例**，否则下一个人会「顺手优化」回两段写。
难点在于终值相同，所以断言不能打在终值上：
`test/org/versioning.test.ts` 里那条
「建任务**一次写入**就带上版本：不允许再发第二次 UPDATE」
在 `tasks` 上装一只 `BEFORE UPDATE` 的 RAISE 触发器再建任务——
一次写入的写法照旧成功，两段写法被触发器当场拦下。
变异实测（§5 的 G-真）：把它改回两段写，全套**只有这一条红**。

顺带一条口径：空表时 `MAX(version)` 返回 0 而不是 1（`COALESCE`）。
0 的语义是**还没有任何版图**，不是「第 1 版」。
返回 1 会让第一次提交写出 v2 而库里没有 v1，此后每条任务的版本坐标
指向一段缺了起点的历史。`readGraphByVersion(0)` 抛错，这正是想要的：
「任务引用了一张不存在的图」应当看得见。

## 3. 规格 §18.4 ③ 那句「`role_charters`（version + 1）」做不到

`OrgGraph` 的节点只有 `role_id / can_manage / model_family / reports_to`。
而 `charter.ts` 的 `charterSchema` 里 `honesty_boundaries`、`acceptance_criteria`
都是 `.min(1)`，`model_tier` 是必填枚举。**组织图里不带这些字段**，
所以从一次拖拽的结果**推不出**一份能过 schema 的岗位书。

我的处置，两条都不是「按规格实现」：

- **只给 `reports_to` 真的变了、且库里已有上一版岗位书的角色**写新行，
  `config` 由上一版的 JSON 打 `reportsTo` 补丁得到。
  「每个角色都 +1」会造出一堆**内容与上一版完全相同、版本号不同**的行，
  于是「v6→v7 改了什么」这个问题得到「什么都没改」这种答案——版本历史当场作废。
  这一条有用例（变异 D：改成全部 +1 ⇒ 2 红）。
- **没有上一版就跳过，不凭空造一份**。造一份得虚构 `acceptance_criteria`，
  而那些字段的语义属 CEO（0008 §7 立的正是实现层不代笔）。
  **跳过是少写，编造是伪证**。这一条也有用例（变异 E ⇒ 1 红）。

代价说清：规格设想的「一次组织变更同时给所有角色出新版岗位书版本」这条语义**没有实现**。
如果 CEO 要的就是那句字面意思，那需要先决定新岗位书其余字段从哪来
（继承上一版？还是要求编辑者补齐？），这不是实现层能替他定的。→ §4 等一个答复。

另外 `config` 里改的是 **`reportsTo`（camelCase）**，不是 `reports_to`：
库里那份 JSON 是 `charterSchema` 的 `transform` 输出。
写错键名**不会报错**，只会得到一行「汇报关系变了而 config 没变」的岗位书——
那是伪证而不是 bug，所以断言直接打在 config 的内容上。

## 4. 需要 CEO 认账的一项：**「所有角色都出新版岗位书版本」是不是你要的**

规格 §18.4 ③ 的原话是「在同一事务内写入 `role_charters`（version + 1）与
`delegation_graphs`（新版本）」，主语省略了。两种读法：

- **读法 A（我按这个实现）**：只给**受影响**的角色出新版。
  版本历史每一行都对应一次真实变化，`change_summary` 与 diff 都对得上。
  代价：一次组织变更之后，`role_charters` 里各角色的版本号**不再齐平**，
  「当前生效的那一版岗位书」这套问法要按角色各自回答。
- **读法 B（字面全量 +1）**：所有角色一起 +1。版本号齐平、好解释。
  代价是上面那句——多出来的那些行**内容完全相同**，
  而它们和真正变化的那几行混在同一批版本号里，
  审计回放分不清哪些角色真的动过（`events.payload.charter_bumped` 能分，
  但那要读 payload，不是看版本号就能知道）。
  而且它**仍然**要给「库里没有岗位书的角色」决定编一份出来还是跳过——
  也就是说读法 B 并没有省掉 §3 那半个问题。

我倾向 A，理由全在 §3。但这条不是我该单方面定的：**它决定的是
「岗位书版本号」这个词在审计里到底承不承载「这个角色的职责变了」这层意思**。
选 A，它承载；选 B，它只承载「组织动过一次」。

选 B 还需要补一个决定：新岗位书那些必填字段从哪来（继承上一版 / 要求补齐 /
只对有岗位书的角色生效）。

## 5. 变异实验：两个变异报 `fail 0`，这次是我的**变异脚本**写空了

0011 §5 立的那条规矩（变异循环里必须有「让改动到达被测方」这一步）本轮执行了：
每个变异跑测试**之前**先 `grep` 一次磁盘，证明那一行真的变了。
八轮结果：

| 变异 | 结果 |
| --- | --- |
| A 空表版本返回 1 而不是 0 | 13 红（版本坐标是全套用例的公共地基） |
| B 跳过 Hub 侧二次校验、采信调用方 | 4 红 |
| D 所有角色都涨岗位书版本（读法 B） | 2 红 |
| E 缺岗位书时凭空造一份 | 1 红 |
| F 建任务时 `graph_version` 写死 1（抽掉本轮补的写入方） | 2 红 |
| H 岗位书写入失败被 `catch` 吞掉（半提交伪装成成功） | 1 红 |
| **C 第一版：把 `appendAudit(db,` 改成 `appendAudit(db as never, /*MUTC*/,`** | **`fail 1`，但一条断言都没跑**（见下） |
| **G 第一版：注入一句 `const vEarly = ...; void vEarly;`** | **fail 0** |

C 那一行的 `fail 1` 我第一轮写成「1 红，但那条红是别的原因」——那是猜的。
补测之后是更硬的一种：**那个变异改出来的不是行为，是一段语法不合法的 TypeScript**。
`ERR_INVALID_TYPESCRIPT_SYNTAX`，整个测试文件**加载失败**，
`ℹ tests 1 / pass 0 / fail 1` 里那 1 条是**文件级**的加载失败，
`✖ test/org/versioning.test.ts` 报的是文件名而不是任何用例名。

所以 `fail 1` 在这个位置上和「有一条断言真的红了」**计数完全相同**。
这是 §5 那条判据（`fail 0` 与「什么都没测」输出相同）的**第三个变体**：
前两个是「变异没到达被测方」（0011 §5）与「变异没改变行为」（本轮 G），
这第三个是「**变异把被测方改坏了，连测都测不了**」。
三种情形下唯一的分辨办法都一样：**看红的是用例名还是文件名**，
而不是看那个数字。本轮之后我读变异结果只认用例名。

G 那个 `fail 0` 什么也没说明——**我插的那句话根本没把取数动作挪出事务**，
被测代码的行为一个字没变。C 第一版同理，只改了一个类型断言。
这正是 0011 §5 那句话的形状：**一个把什么都测绿的实验，和一个什么都没测的实验，
输出是同一个**。区别在于这次是**变异脚本**空了，而不是构建产物旧了——
同一条判据（先看仪器，再怀疑断言）在两种成因上都好用，
而 `grep` 自检这一步在第一种成因下会救我、在第二种成因下**也**救了我：
它证明「磁盘上确实写了这句话」，于是剩下的怀疑对象只剩「这句话没有改变行为」。
（但注意它救不了 C 这种情形：`grep` 只会说「写进去了」，
而写进去的东西**让文件不能编译**——自检证明的是【落盘】，不是【落盘的东西是合法代码】。
真要防这一类，得在变异后加一步 `tsc`，本轮没加，所以 C 那条我只能报事后补测的结果。）

改成真变异之后：

| 变异 | 结果 |
| --- | --- |
| **G-真 建任务退回两段写**（先 INSERT 吃 DEFAULT，再同事务 UPDATE） | **恰好 1 红**：那条「不允许再发第二次 UPDATE」 |
| **C-真 `appendAudit` 的失败被 `catch` 吞掉** | **恰好 1 红**：那条「审计那一发失败 ⇒ 图行也一起消失」 |

G-真 这一行是本轮最值钱的一条证据：它落库的**终值与正确实现完全相同**，
所以「只有那条为它单独写的用例红」恰恰证明**那条用例是唯一分辨得出两种写法的东西**。
这类性质（写法不同、终值相同）在断言式测试里是盲区，
本轮是第一次在 org 这条线上把它堵上，办法是**断言行为次数而不是断言结果值**。

## 6. 一次夹具设计错误：我造的那次失败**根本不可达**

计划 Test ① 要「保存失败 ⇒ 版本号不变、无半提交行」。
第一版夹具是：预插一条 `dev` 的 v2 岗位书，让提交路径的 INSERT 撞
`UNIQUE(role_id, version)`。跑出来两条用例都报「期望 promise reject，实际 resolve」。

那不是断言太弱，是**我的前提不成立**：提交路径先用 `LATEST_CHARTER_SQL` 读最大版本
（读到 v1），写的是 `v1 + 1 = 2`——而我预置的那条正是 v2，
**它被读到了而不是被撞上了**。
那条用例永远不会失败，而它以「期望抛错」的形式出现，
红了之后极容易被读成「回滚坏了」，从而去改**没坏的那部分**。

换成一只 `BEFORE INSERT ... RAISE(ABORT)` 触发器：它和真实故障同形
（磁盘满、FK 违例、误撞 events 的 append-only 触发器，形状都是「事务中途一条语句炸」），
而且失败点确定。教训一句话：**夹具想制造一次失败，得先确认那次失败在真实代码路径上可达。**

顺带把「无半提交」这句拆成了三条，因为一条测不全：
岗位书那一发失败（测图行有没有跟着退）、审计那一发失败（测图行与版本号）、
失败的那次**不占版本号**（重试拿到 1 而不是 2）。
只测前两条的话，「图行 + 审计一个事务、岗位书另一个事务」这种实现能全绿。

## 8. 一次自伤：`git checkout --` 把本轮改动还原掉，而我的校验报「六个文件全一致」

收尾阶段我用一条 bash 把本轮改动的文件搬开做 A/B，命令长这样：

```bash
FILES="a.md b.ts c.ts"; for f in $FILES; do md5 -q "$f"; done; mv $FILES /tmp/x/
```

**zsh 不对未加引号的变量做词分割**。所以：

1. `for f in $FILES` 只循环**一次**，`$f` 是那一整串文件名 —— `md5` 报
   `No such file or directory`，`mkdir -p /tmp/x/<整串>` 报 `File exists`；
2. 紧接着那条 `git checkout -- <五个文件名>` 是**字面量**，不受影响，照原样执行，
   于是**本轮五个已跟踪文件被还原到 HEAD**。未跟踪的 0012 篇、`org/`、
   `test/org/` 因为 checkout 够不着才活下来。

真正该记住的是下一步。我写了一段逐个 `md5` 对比来证明「恢复干净」，输出是
**六个文件全部「同」**。那段对比里 `set -- $pair` 同样因为词分割没生效，
`$1` 是整串、`$2` 是空串，于是两次 `md5` 都失败、两次都返回空字符串，
`[ "$a" = "$b" ]` 恒真。

⇒ **一个对空值恒真的判据，报的「全部一致」和「全部丢失」是同一个输出。**
这是 §5 那条判据（「把什么都测绿的实验，和一个什么都没测的实验，输出是同一个」）
在**校验脚本**上的第四个变体，而且比前三个更危险：前三个我至少看到了
`fail 0` 或 `fail 1` 这种可疑信号，这一次屏幕上是一整列绿色的「同」。
分辨办法也一样，只有两条：**看中间过程有没有报错**（那几次 `md5:` 错误就在输出里，
被我当成噪音跳过了），以及**让判据在输入缺失时失败而不是返回相等**
（本轮之后我改用 Python 显式比较，并把「文件缺失」写成一个与「内容不同」**不同**的返回值）。

损失盘点与恢复：0012 篇与 24 例测试文件（未跟踪）无损；四个文件从 `/tmp/bak33/`
逐字节复原（这次是真 `hashlib.md5` 比的）；真正丢掉的是 `doc-refs.test.ts` 里
我新加的三条快照与 `docs/INDEX.md` 的两条 0012 条目 —— 重做之后
arch 守卫从 **113 / 104 / 9** 回到 **113 / 106 / 7**，
而「回来」这件事本身就是恢复正确的证明：那两条红的正是
`决策索引与 decisions/ 目录一致` 与 `真仓库的待决小节与登记表双向一致`，
它们只在「0012 存在而未登记」时红。
**这是本仓 arch 守卫第一次在我自己的操作事故里而不是在代码漂移里发挥作用。**

## 9. 组织变更**不广播**：留下的 seq 空洞会被【检出】，但检出之后拿不回组织图

`commitOrgGraph` 写完那一行审计就结束了，没有人 `publish`。
这不是我漏了，是**类型上做不到**：它的入参是 `w: Writer`（= `Pick<WriteQueue, "node">`），
结构上拿不到总线。而 `InMemoryEventBus.#seq` 只在 `publishPersisted` 里前进，
所以下一次有人 publish 用的是**新的** `events.id` ⇒ 对活跃订阅者就是跳号。

0010 §2 记过同一个形状（`appendAudit` 一字节未广播而 `events.id` 已消费），
那次直接当缺陷修了 hub 侧。这次我先问**后果到底是什么**，因为两种后果的修法不同：

| 后果 | 该不该修 |
| --- | --- |
| 静默吸收（照常应用、游标照走） | **必修**：组织变更后界面「看起来正常」而缺一段历史 |
| 标 `stale` → 重拉快照 | 不必修：组织图的形状本来就不在任务投影里，唯一正确反应就是去拿全量 |

读代码得不出结论（`applyItem` 的 `default` 分支只推进 cursor，看不出跳号那一路），
所以实测。这一节跨两个包，**因为成因住在 hub、后果住在 web**，
而两侧各自看都是对的 —— hub 侧「审计落库了」，web 侧「未知 kind 不会炸」——
**没有任何一个包的测试看得见另一侧**。这正是 0010 §2 那个盲区的第二种成因：
上次是「一个函数消费了另一个包的序号」，这次是「一条性质需要两个包同时在场才成立」。

测到的结果是**第 2 行**：空洞之后到达的第一条事件 ⇒ `action = "gap"`、
`link = "stale"`、`cursor` 不前进。未知 kind 本身既不被拒也不被当成洞
（`feedItemSchema.kind` 是 `z.string().min(1)` + `.passthrough()`），
所以「不广播」这件事**不会**表现为「前端解不开某一帧」，只表现为跳号 ——
修法相应在「多发一种事件」或「接受多一次快照」之间，而**不是**「让前端学会认这个 kind」。

**但检出之后拿不回来**，这一条才是本节真正的缺口：
`stale` 的处置是重拉快照，而快照里没有组织图 ——
`delegation_graphs` 在 `packages/*/src` 里只被 `org/commit.ts` 与 `http/real-deps.ts` 提到，
后者只用它读 `MAX(version)`；**没有任何读端点**。
于是当前状态是：一次组织变更之后，活客户端会**正确地**判定「我落后了」，
去拉一个**不可能包含组织图**的快照，然后回到 `linked`。
界面不会显示错的汇报关系（因为它从来没显示过汇报关系），
但也不会显示对的 —— 「检出并恢复」这条链路在组织图这一格上是**空转**。

这条不是 Task 3.3 的收尾项，它是 §7 那条「没有生产入口」的**下游**：
入口没建 ⇒ 组织图没有读路径 ⇒ 恢复路径无处可恢复。
所以顺序上该先立约（`contracts` 加端点）再补实现，而不是先给 `commitOrgGraph`
接一个能 publish 的包装 —— 后者会让前端**知道**发生了组织变更而仍然拿不到内容，
把「空转」换成「看得见拿不到」，只多一次无效重拉。
