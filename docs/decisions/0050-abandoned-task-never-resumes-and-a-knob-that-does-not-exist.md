## 3. ⭐ 四发探针，其中两发的**第一次结论是反的**

### 3.1 探针一（`/tmp/probe51.mts`）：CLI 每轮都炸，看板最终会说话吗

会，而且**是收敛的**：

```
第 1 轮  outcome=threw        名单=[空]
第 2 轮  outcome=threw        名单=[空]
第 3 轮  outcome=threw,gave_up 名单=[t1:at_limit]
第 4 轮  outcome=(空候选)      名单=[t1:at_limit]     ← 之后恒在
第 5 轮  outcome=(空候选)      名单=[t1:at_limit]
子进程真被起来过 3 次（maxAttempts=3）
```

这一发顺带证明了**写侧与读侧的接缝是通的**：那行 `DriverTurnAbandoned`
是驱动器自己经 `writeGaveUp` 写的，而读侧 `readDriverStatus` 读到了它。
（`driver-status.test.ts` 那 54 发的放弃行是**手写 INSERT 造的**，见 §4.3。）

### 3.2 探针二：根因修好了，它会自己复活吗 —— **不会**

前三轮抛、第四轮起换成一个健康的 `driveTask`：

```
第 3 轮  outcome=threw,gave_up  名单=[t1:at_limit]
第 4 轮  outcome=(空候选)        名单=[t1:at_limit]
第 5 轮  outcome=(空候选)        名单=[t1:at_limit]
第 6 轮  outcome=(空候选)        名单=[t1:at_limit]
```

候选 SQL 用 `attempts < maxAttempts` 把它**永久滤掉**了，而"修好 CLI"这件事
不改变库里任何一行。**这一发的结论是真的**，也是本篇那句措辞的依据。

### 3.3 探针三：那"重新来到这一格"呢？—— 我的**第一次**跑法给出了**反的**答案

`driverAttemptsSql` 数的是【这一格 + 这个人 + 这一次来到这一格之后】的认领行，
靠的是 marker（最后一次"进入这一格"那条状态边的 id）。所以我造了一条重访，
结果：

```
第 5 轮  格=IN_PROGRESS  outcome=(空候选)  名单=[t1:at_limit]     ← 看起来"重访也不复活"
```

**那是我的夹具坏了**：marker 那条 SQL 问的是 `kindOf(m) = 'TaskStateChanged'`，
而 `kindOf`（`heartbeat/patrol.ts:139`）取的是 **`payload` 里的 `$.kind`**，
我手写的行把 `TaskStateChanged` 写进了 **`action` 列**、payload 里**没有 `kind`**
⇒ marker 恒 0 ⇒ 那一发测的根本不是 marker。
回去照 `dispatch.ts:1207` 那个真实写入点抄了形状（`action='state_change'`、
`target=落点状态`、`payload.kind` 在 payload 里）**同一条探针**：

```
第 4 轮  outcome=(空候选)  名单=[t1:at_limit]
第 5 轮  outcome=threw     名单=[空]        ← 重新变候选，计数归零
第 6 轮  outcome=threw     名单=[空]
子进程被起来过 5 次
```

**重访确实复活它。** 而这件事**早就有测试**（`driver-pump.test.ts` 那条
「放弃之后【再来一条合法重访】⇒ 它重新可驱动（上限不是终身制）」）——
所以这一发的净产出**不是发现**，是**两次错**：

1. 第一次跑出反结论而**我差点就信了**（"修好也不会复活 + 重访也不复活"读起来
   非常自洽，而自洽本身不是证据）。
2. 第二次跑对了，量的却是一件**已经登记并已有测试**的事 ——
   与 0049 §8 那条「量之前先花一行 grep 问有没有人记过」是同一格。

**判据**：探针的**形状**错了不会自称出错。它给一个安静的、看起来合理的答案。
所以"造数据"那一段（谁写这一行、按什么形状写）**必须抄真实写入点**，
不能照着 SQL 反推 —— 这条在 `driver-status.test.ts` 的夹具注释里写着，
我在自己的**一次性**脚本里没遵守。

### 3.4 探针四问出来的：那一档**没有旋钮**（这才是措辞的依据）

到顶那一档最自然的补话是「带更高的 `--max-attempts` 重启」。查了 `serve/config.ts`
认的全部 **14** 个参数：

```
--agent-cwd --backup-dir --bind --ceo --charter-pump --db --driver-pump
--heartbeat --help --max-budget-usd --no-backup --port-file --port --task-limit-cents
```

**没有 `--max-attempts`**。`driverMaxAttempts` 只能由装配层注入
（`assemble.ts:274` 的 `HubOptions`，注释自己写着「没有 CLI 入口，只能由装配注入
（BootOverrides.driverMaxAttempts，**测试用的**）」，`assemble.ts:1646`）。
而尝试次数**住在 append-only 的 `events` 里**：改它 = 篡改审计，删它 = 同一个。

所以那一档此刻**没有任何"放开"的动作**，只有【查为什么这一轮没推进】。
措辞就按这个写，并把"没有旋钮"这件事**说出来** —— 少了它，读的人会继续找一个
不存在的参数（同 0049 §12.3 那句「命令行」是限定词而不是修辞的理由）。

## 4. ⭐ 一条我自己写的守卫，它到底挡什么 —— 量完发现比我以为的窄

给到顶那一档加措辞守卫之前，先问了一句：0049 给钱那一档写的那发（「不许指回屏幕上
不存在的那一步」）在到顶这一档有对应物吗？**没有**。同一块屏幕、两档措辞，
一档有反空按钮守卫、一档一句下一步都不说 —— 这个不对称本身就是缺陷。

### 4.1 改了措辞，加了守卫

```
不再推：第 3/3 次而它还在原格 · 要它继续走得先查那一轮为什么没推进（次数记在审计里，
屏幕上和命令行都没有能放开的地方）· 10 分钟前
```

新那发（`test/web/app-pure.test.ts`）钉两件事：① 不许出现"调次数"那一族说法
（`--max-attempts` / 提高次数 / 加大次数 / 放开次数 / 重置次数 / 清空记录 ——
**钉一族而不是一个词**，理由同 0049 §12.3：只钉一个词，换个说法就溜过去）；
② 不许把**钱那一档**的下一步借过来（`--task-limit-cents`、`上限（`）——
到顶的原因不是钱，两档指向不同的动作，这正是它们本来该分两档的理由。

### 4.2 顺手量的：`hub work` 在这里是不是那句"下一步"

**没有写进措辞**，理由两条而都可复算：

- 屏幕上**已经**有 `hub work` 那句话，而只在「这台 Hub 没开驱动器」那一档
  （`app.js:528`）。那一档里它是**那条路本身**；到顶这一档里它是**同一堵墙的另一次尝试**。
- 驱动器放弃的常见原因就是"跑了一轮而状态没动"，而 `advance` 数的是**单次调用内**
  连续多少轮没动（与驱动器那个跨进程 attempts 是**两个不同的计数器**，
  后者只活在 `events` 里）。所以再跑一次多半得到**同一个结果**，
  而它是**一条花真钱的子进程**。屏幕上那句话不该指着一句可能没用的话。

（同族：`describeAdvance` 给 `stalled` 写的那句"补救话"就是叫人去敲 `hub work`，
而它出现在自动路径上正是 0043 抓过的那类「报错教的那一步跑不起来」——
`driver-pump.test.ts` 的 G 组有一条专门拦它。）

### 4.3 那条写侧↔读侧的接缝测试：**它挡的东西比我注释里写的窄**（量过）

`driver-pump.test.ts` C 组加了两发（一条正向、一条反向对照），正向那发的行
出自 `writeGaveUp` 而不是手抄夹具。我给它写的注释第一版说它守的是
「写侧键名漂 ⇒ 读侧取到 NULL ⇒ 界面上那一行永远不出现，**而两侧各自的测试全绿**」。

**那半句是错的**，三次变异量出来的：

| 号 | 注入 | 结果 |
| --- | --- | --- |
| M16（第一版） | 写侧 `attempts,` 改成 `attempt,` | **7 红** —— 但这是**无效变异**：简写形式引用了不存在的变量 ⇒ `writeGaveUp` 直接**抛** ⇒ 文件级失败。**"文件红了"不等于"守卫有牙"**（0049 §9.1 一模一样的车，我第二次才避开） |
| M16（重做） | 写侧 `attempts: attempts` → `attempt: attempts`（只漂键名、值不变） | **2 红**：我那发 + **既有的**「到顶那一轮留下【一行】DriverTurnAbandoned，内容是【那一格】」 |
| M17 | 读侧 `gaveUpSubquery("g2","attempts")` → `"attempt"` | **5 红**：我那发 + `driver-status.test.ts` 里**四条** |
| M18 | 写侧 + 读侧 + **手抄夹具三处一起**改 | **2 红**：既有那发（直接 json.parse 那一行）+「payload 里的数字写成字符串」——**我那发反而绿**（它跟着读侧一起漂了） |

所以：**两侧各自都已被覆盖，新那发不是唯一能红的**。它唯一的独特之处是
【行出自生产写入点】，因此它挡的是更窄的一格 —— 两侧**各自都改得自洽**、
而只有"真实那一行"能暴露的漂法（例：`appendAudit` 那层的 payload 编码变了）。
注释已按实测改写，并把「**别把它读成"没它就没测"**」写在旁边 ——
那正是 0048 §9 的 M7（给一道恒假分支写「有测试挡着」）与 0049 §0-3
（给一道恒绿守卫写它能挡什么）记过的同一族错。

**M18 里我那发绿而既有那发红**这件事，是这一节真正的产出：
它意味着**"行出自生产写入"这个性质本身不是决定性的**，
决定性的是**断言离那一行有多近**（既有那发直接 parse payload，
我那发隔了一层 `readDriverStatus`）。写接缝测试时我默认"越端到端越强"，
而在**键名**这一类漂移上恰好相反。

## 6. ⭐ 修好打回那条边之后，我造出了一个【此前不可能发生的循环】

前面几节的活是把措辞改诚实。这一节是**我自己改出来的一个真缺陷**，所以单独写。

### 6.1 那条边：三张表两有一无

`docs/OPC-OS-设计文档.md:798`（§7.2 打回路径说明）写着「任务沿边回退到上游重新处理」，
`status.ts:59` 的合法表**一直**有 `REJECTED_DOWNWARD → IN_PROGRESS` 那条补边，
旧的 langgraph 路线（`graph/company.ts:254`）也真的走它。
**而引擎换路线时它没搬过来** —— `dispatch.ts` 的 `AGENT_EDGES` 与 `HUMAN_EDGES`
两张可执行边表**都查不到 `REJECTED_DOWNWARD` 这个键**。五处实测（探针 52，`/tmp/probe52.mts`）：

```
seatOf(REJECTED_DOWNWARD)   = human          ← 因为 AGENT_EDGES 没这个键
DRIVER_ELIGIBLE_STATES 含它  = 否              ← 驱动器不推
needsSeatCard(...)           = 否              ← 不给 CEO 发卡
humanEdge(S, "approve")      = null            ← CEO 手上有卡也推不动
在 ATTENTION_STATUSES / BLOCKED_STATUSES 里 = 否 / 否  ← 屏幕上一列都不出现
```

净效果：**审阅者一说「打回」，这条想法就永久停在一个既没人干活、也没人入口、
屏幕上还不在任何一列的格子里**。而它**没被任何死路快照抓到** ——
`status-machine.test.ts:172` 那条「已知缺口快照」扫的是**合法表**，
合法表**有**那条边（`status.ts:59`），所以它绿得完全合理。
这一发的形状是**三张表两有一无**：合法表说能走、旧路线走过、可执行表没搬。

修法取 `AUTO_AFTER_EDGE`（`EVIDENCE_SUBMITTED → IN_REVIEW` 那一格同一形状）：
落点之后由 hub **不问任何人**再走一格。**不给 `AGENT_EDGES` 加出边**是量出来的判断 ——
那意味着在 `REJECTED_DOWNWARD` 那一格**起一个子进程**让下游角色自己决定接不接，
多烧一轮真钱，而**那个决定审阅者刚才已经替他做过了**。

顺带修掉一处**只差一步的假话**：`AUTO_AFTER_EDGE` 第一版只装 `TaskState` 而把审计那句
note **写死在调用点**（「产出已进入 X 的审阅队列」）。今天只有一个键所以恰好总对；
加第二个键而不动 note，就是往 **append-only** 的 events 里写一句听起来像那么回事的假话。
所以 `to` 与 note 现在**同一个对象里定义**，类型也从 `Partial<Record<TaskState, TaskState>>`
改成 `to` 与 note **成对出现**（不可能加一格而没说那一格发生了什么）。

### 6.2 ⭐ 这条修动的**直接后果**：一个此前不可达的循环

修之前 `IN_REVIEW --handoff--> REJECTED_DOWNWARD` 是**终点**，所以
「dev ⇄ 审阅者来回踢皮球」在生产上**根本不可能发生**。修之后它可能了，
而我得知道**封顶的是什么**。两发探针，答案都不是我以为的那个：

**探针 53**（`advance` 单轮，`/tmp/probe53.mts`）：一台只演打转的假 dispatch，
每轮 `moved: true`（每轮**真的**写了一条边）。


### 6.3 落点：用**已有的那条边**，不新造

`IN_REVIEW` 的三个出口里就有 `blocked → ESCALATED_TO_CEO`（【规格】§8.3「审阅者要求 CEO 裁决」），
而它的 `next: "same"` 正是「不换负责角色」。所以：

```ts

if (edge.to === "REJECTED_DOWNWARD" && (o.rejections ?? 0) >= DEFAULT_MAX_REJECTIONS && cap !== undefined) {
  return { move: true, to: assertTaskTransition(o.status, cap.to), role: o.role, note: … };
}
```

三个位置与两个"不"都是判出来的：

- **落点从边表上读**，这一支里没有字面量 `"ESCALATED_TO_CEO"`。写死字符串会得到
  「两条语义相同的边安静地指向不同格子」；取 `cap.to` 则**同源**（那条边改落点，
  这条上限跟着走）。**取不到那条边 ⇒ 落回原来的打回而【不抛】**：抛会把一整轮
  已花掉的钱变成一次崩溃，而最诚实的行为是照旧打回。
- **只有一条边**：这条上限是**替换**那一跳的落点，不是在打回**之后**又追一跳
  （追一跳会写出 `REJECTED_DOWNWARD → ESCALATED_TO_CEO`，规格里**没有**那条边）。
- **排在 `blockedHandoff` 之后、边表查中之后**。前者保证越权的打回仍先按越权处理
  （不会因为"反正要打回"把机器不认的交接洗成一次升级）；后者保证只有**真的会打回**的
  那一轮消耗额度（一轮 `wait`、一轮动作不合法、一轮执行失败都不该被打断）。
- **负责角色保持 `o.role`**（`next: "same"`）。写 `ceo` 的后果 0047 已经记过：
  `approveCard` 原值回填会把负责角色**永久**改成 CEO —— 一次"升给 CEO 看"变成一次组织分配。
  ⚠ 我第一版在这里加了个 `EdgePlan.keepRole?: true` 标志来"把决定留在计划里"，
  然后发现**没有任何代码读它** —— 那正是本仓在整个仓库里消灭的那一族（写了而没生效）。
  改成由**一条断言**守这个不变量（「升完 CEO 负责角色还是审阅者」），不靠自证。

### 6.5 ⭐ 分子必须**无条件**读（这一发最贵的形状）

装配层那句现在是 `const rejections = deps.rejectionCount(task.id);` —— **无条件**，
排在 `planEdge` **之前**。最省事的优化写法是：

```ts
task.status === "IN_REVIEW" && decision?.action === "handoff" ? deps.rejectionCount(...) : 0
```

**今天它完全等价**，而它把分子与判据拆成两处、各自收窄一次就永久失真：
判据是边表里的 `edge.to === "REJECTED_DOWNWARD"`（由**表**决定），
那个筛是**手抄的状态名 + 动作名**。将来给别的状态加一条落点是打回的边，

两侧刻意相反：装配侧忘了接线 = 上限永不生效（"配置写了而没生效"那族），要 TS 响；
纯函数侧三十来个调用点大多没有"打回"这一维，强制写 0 只会让每一处都得解释那个 0 是什么。

`runtime.ts:108` 那个 `REJECTION_COUNT_SQL` 数的是 `json_extract(payload,'$.to') = 'REJECTED_DOWNWARD'`
