# 0037　worker 线程里那一行 import：跑测试的那条命令比跑产品的多给一层能力，以及我自己那个修法是错的

- **状态**：已定案。本篇修的是一个**从 Task 6.2 就在**的缺陷（`integrity.worker.ts` 引入那一天），
  不是 0036 新写的代码带进来的 —— 0036 只是**照着它抄了第二个入口**。
- **产出**：`src/db/worker-entry.ts` 多两条导出（钩子 `WORKER_RESOLVE_HOOK_URL` +
  `wrappedWorkerUrl()`；钩子源码那个 const 本身**不**导出，导出的是它包好的 data: URL）；
  `integrity.ts` 与 `backup.ts` 各把 `new Worker(入口)` 换成
  `new Worker(wrappedWorkerUrl(入口))`；新测试 `test/db/worker-entry.test.ts`（18 发）
  + 子进程夹具 `test/db/fixtures/worker-hook-child.mjs`。
- **一句话结论**：⭐ 本篇有**两条**方法论产出，第二条比第一条贵：
  1. **那个缺陷能活 30 多篇，不是因为用例写错了，是因为跑用例的那条命令给了产品环境没有的东西** ——
     这类失效**无法靠「多写几条用例」修掉**，只能把判据搬到那条不宽容的命令上去跑（§0、§3）。
  2. ⭐⭐ **我第一版的修法是错的，而我新写的 21 发判据全绿；抓到它的是本仓【既有】的用例**（§2.2、§8 第一条）。
     ⇒ 「我加了 N 发判据」不等于「这个修法被审过」。新判据只审我想到的维度，
     而修法最常见的错在【没想到】那一侧 —— 那一侧只有既有用例覆盖着。
- **⚠ 与 §1 第一版的关系**：第一版给这个缺陷编了一套「三层解释」，其中**两层不存在**
  （是我量了一个不完整的集合就下的结论）。复算过程与更正都留在 §1.1 里，原文不删。

## 0. 先给实测

一张矩阵，问的永远是同一句话：**`import { x } from "./兄弟.js"` 解析得了吗**
（本仓是 NodeNext，源码里所有本地 import 都写 `.js` 而文件是 `.ts`）。
形状是 `/tmp` 里两个 6 行的最小文件（入口 `ent.ts` 静态 import `./dep.js`），
不掺任何仓库代码 —— 掺了就分不清是仓库的问题还是加载器的问题。

| 跑法 | 主线程 | **worker 线程** |
| --- | --- | --- |
| A `node --experimental-transform-types`（纯 type-stripping） | ✗ | ✗ |
| B 同一发 + 代码里 `register()` 一条钩子 | ✓ | ✗ |
| C `tsx`（= `pnpm hub:serve` / `pnpm hub` / `pnpm migrate` 走的这条） | ✓ | **✗** |
| D 命令行 `--import <文件>`（= 本仓跑测试的这条） | ✓ | ✓ |

三行读数各说什么：

- **C 是本篇的缺陷**：产品那条路上，worker 线程**加载得起来，然后死在第一行兄弟 import**。
- **D 是本篇的盲区**：那条 `--import` 落在 `process.execArgv` 里（实测打出来了），
  而 worker 线程**默认继承 execArgv** ⇒ 钩子在**线程里也生效**。
  ⇒ 仓里每一条「走 worker」的用例都在 D 这一格里跑。
- **B 与 D 的分别是这一格存在的理由**：`register()` 只作用于**注册它的那个线程**，
  而命令行上的 `--import` 会被**新线程自己重放一遍**。
  同样是「一条钩子」，一个不跨线程、一个跨。

⚠ A 那一格顺手也被量出来了：**纯 type-stripping 连主线程都不通**。
所以「仓库能 import 自己的源码」这件事，在本仓**一直**是靠那条钩子撑着的
（`node_modules` 里没有 tsx 的那些跑法尤其如此），不是 Node 天生会做。

## 1. 症状，以及它为什么能活到本篇

**症状**（真仓库、真入口、一次 `runIntegrityScan` + 一次 `createBackupOffLoop`）：

```
修之前（tsx）：page_integrity = violated   拒绝启动 = true     backup ran=false worker_error
修之后（tsx）：page_integrity = ok         拒绝启动 = false    backup ran=true  ok=true
```

原文错误是 `Cannot find module '.../src/db/page-check.js' imported from .../integrity.worker.ts`
（备份那一侧同形，换 `backup.js` / `backup.worker.ts`）。

### 1.1 ⭐ 我给它编了一个三层的解释，其中两层不存在

第一版这一节写的是「三层，缺一层它今天就红」：① 兜底分支把失效翻成一条合法结论、
② 跑法比产品宽容、③ 没有一条用例跑在产品那条命令上。**只有第 2 层是真的。**
另两层不是「还没量」，是我**量了一个不完整的集合就下结论**：

| 我写的那句话 | 复算之后 |
| --- | --- |
| 「全仓 10 处 `runIntegrityScan(` 调用里，没有一处断 `page_integrity` 的 verdict 是 `ok`」 | **字面成立**（复算 = 0 处）。**但它不是缺陷活下来的原因**：`integrity.test.ts:339` 断的是 `unavailable).toBeUndefined()`，`backup.test.ts` 断 `ran === true` **5 处**、`result.ok === true` **4 处** —— 这些断言【已经在要求 worker 真的跑成了】，方向是对的 |
| 「没有一条用例跑在产品的命令上 ⇒ 这条路径在产品环境下没被测过」 | **前半句真，后半句假。**`assemble.test.ts` 有 **29 处** `needOk(` 断 `boot()` 的成功路径，而 `boot()` 里就含真 worker + 真页面检查 |
| ⇒ 直接量：缺陷态下那条既有断言到底红不红 | **红**（tsx 跑真仓库：`unavailable = "worker_error"`，而断言要 `undefined`）。修好之后 `undefined`，绿。 |

⇒ **本仓的断言本来是够的。**同一份代码、两条命令、两个读数：
`--experimental-transform-types --import <钩子>` 下全绿，`tsx` 下当场红。
**唯一的原因是那条命令行**，不是断言写得松、不是路径没被测过、不是兜底分支吞掉了它。

⚠ **这一格比那个 bug 值得带走**：三层故事里每一层都**听着像本仓的老毛病**
（兜底分支吞失效本篇确实记到第四次、测试环境比产品宽容正是第 2 层），
所以它们**通过我的检查**恰恰是因为它们眼熟。
我核对「有没有断 ok 方向」的方式是 `grep page_integrity` 再看同不在同一行 ——
方向对的断言写在**另一个字段**上（`unavailable` / `ran`），那个 grep 天生看不见它们。
⇒ **「解释我自己的盲点」这件事有一个具体要求：先把【它本该在哪一发红】的那一发指出来，
再去说它为什么没红。**指不出那一发，就说明「为什么没红」那个问题我还没开始答。

### 1.2 「兜底分支把它翻成一条合法结论」这一层是真的，而且它今天还是一个缺陷

第 1 层作为**缺陷存活的原因**是假的，但作为**代码事实**是真的，而且比我想的更糟 ——
它单独构成第二个缺陷，另见 **0038**：

`runIntegrityScan` 里那一行 `verdict: page.ok ? "ok" : "violated"`
（`integrity.ts:179`）把「检查没跑成」和「查出损坏」压成同一个 `violated`，
于是 `pageIntegrityBroken` 在**一次 instrument 故障**上返回 `true`，
`pnpm hub:serve` **拒绝启动**并指路 `scripts/restore.md` —— 而第 3 步是
**把现网库改名再从备份覆盖**。一台库完全健康的机器会因为
「worker 起不来 / 120 秒没回话 / 路径打错」被引导去**覆盖自己的库**。

⚠ **「库路径打错」这一发我起初也算进去了，那是错的**：`dbPath` 不存在时
`boot` 在 `assemble.ts:291`（`maintenance.ts:479` 同一条）就退回 `EXIT_USAGE` 了，
**根本走不到这个闸门**。所以真实启动路径上能撞上这个闸门的仪器故障**只有三种**
（`INTEGRITY_FAILURES`，`integrity.ts:102`）：`worker_unavailable` /
`worker_timeout`（默认 **120 秒**）/ `worker_error` —— 本篇那个缺陷就是第三种。
（直接当 API 调 `runIntegrityScan` 时，路径不存在会得到 `violated` 而 `unavailable`
是 `undefined`：worker 自己跑起来了、是它开库开不了，那确实更像「库的事」而不是
「尺子坏了」。这一格我第一版也一并算成误报，复算后**不算**。）

而 `pageIntegrityBroken` 自己的注释（`integrity.ts:1135`–`1137`）写的正是相反的话：
「`not_observable` / `could_not_run` 都【不算】损坏：那两格说的是『这条判据没跑成』。
据此拒绝启动，等于让一次 worker 起不来变成整台机器不可用；
**而它该做的（响一声、指路）由调用方在别处做**」——
**「响一声」这一半全仓没有任何地方做**（复算：`src/` 下读 `report.unavailable` 的
非注释代码 **0 处**）。注释把分工写对了，两半都漏了一半。

三层里我只留这一层是真的，而它**不是本篇那个缺陷的帮凶**，
它是**同一行代码上的第二个缺陷**，处置手段也不同（0038）。

## 2. 修法：入口外面包一层；而「递 execArgv」那一版是我写的，它是错的

### 2.1 先说被否掉的四个，其中第三个是我第一版采纳的

| 候选 | 实测 |
| --- | --- |
| 入口里 `import "./worker-loader.js"` 再 `register()` | **那个 import 本身就是解析不了的那个东西**（先有鸡还是先有蛋）⇒ ✗ |
| 入口内联 `register(new URL("./hook.js", import.meta.url))`，然后**静态** import 兄弟 | 静态 import 在**任何顶层语句跑起来之前**就解析完了，`register` 来不及 ⇒ ✗ |
| register 之后**动态** import 兄弟 | ✓，但每个入口的顶层都要改成 await 链，而兄弟模块的**传递图**（`backup.ts → ./pragmas.js`）还是得靠同一个钩子 ⇒ 只治第一跳 |
| **父线程把钩子塞进 `new Worker({execArgv})`**（我第一版） | ⚠ **两条独立的错，见 §2.2** ⇒ ✗ |
| **入口外面包一层 `data:`（选了）** | ✓ 两态、两入口、含传递图；入口那三行一字不改；**execArgv 一个字不碰** |

### 2.2 ⭐⭐ 我那一版 execArgv 错在哪，以及它是谁抓出来的

**它是本仓既有的 `backup.test.ts` ⑦ 抓出来的**（红 6 发 + 整个文件挂死），
而我新写的那 21 发当时**全绿**。两条独立的错：

**错 1：显式传 `execArgv` 会触发一道【不传就没有的】校验。**
实测（`node --test` 之下，同一个真入口 `backup.worker.ts`）：

| 写法 | 结果 |
| --- | --- |
| `execArgv: [...process.execArgv]`（28 条） | `new Worker` 当场抛 `ERR_WORKER_INVALID_EXEC_ARGV: --stack-trace-limit=10, --tls-cipher-list=…` |
| `execArgv: []` | 起得来 |
| **根本不传** | 起得来，而线程里 `process.execArgv` **照样是那 28 条**，含 `--stack-trace-limit=10` 那条**同一个值** |

⇒ 坏的不是「那份旗里有线程不认识的旗」—— 它们待在继承里**完全无害**。
坏的是【显式传】这件事本身。
**我为了递一条钩子，把一条本来不会跑的校验跑了。**
而抛出来的错被 `backup.ts` / `integrity.ts` 两侧的 `worker_unavailable` 兜底分支咽掉，
红的只是「备份没跑成」这个结论 —— **兜底分支吞掉我自己写的洞，这是同一个形状第四次**。

⚠ 还有一格更阴的：**同一个文件那次不是红到结束，而是红完 6 发之后不退出**。
本篇**没有**把「为什么不退出」这件事查清楚（只做到「知道它不退出、知道它在我的改动之后才不退出」），
所以这里**不写成因**。能如实说的是两条观察与一条推论：
 - 观察 1：`--test` 那条命令的 execArgv 里有 `--test-timeout=0`，**一发不结束的测试不会被计时器掐掉**；
 - 观察 2：不退出发生在 `new Worker` 会抛的那批用例之后，而两处调用点的抛都被 catch 掉；
 - 推论（**未证**）：某处 await 的 promise 在抛-被咽掉那条路径上永不 settle。
⇒ 登记为**下一步**（§8）。这条之所以值得单独记：
 **「判据坏了」的失效里，有一类的表现不是红，是【不结束】**，
 而一个 CI 里挂着的 job 和一次失败的 job，对人的提示强度完全不同。

**错 2：就算把旗校验过再递，`--import <钩子>` 这条【内容】也未必是那条能改道的钩子**
（tsx 挂在 execArgv 上的是它自己的 loader）。也就是说这一版即使不抛，
它「在测试跑法下能用」而**在产品跑法下靠的是别人的钩子** —— 正是本篇 §1 说的
「跑法之间的宽容」，我等于**用一个跑法相关的通道去修一个跑法相关的洞**。

⇒ **教训不是「execArgv 要过滤」**（那是症状层的修法，且会随跑法漂），
是**这一层不该碰 execArgv**：
`execArgv` 属于【怎么跑】，而本篇要修的是【不同跑法行为不一致】。
判据也跟着改了：`worker-entry.test.ts` ① 现在第一条断的就是
**两条调用点都不许出现 `execArgv` 这四个字**，外加一条全仓扫描
「src 下任何文件都不许提 execArgv」—— 防的就是未来的我（或别人）
觉得「递 execArgv 更直接」而把它改回去。

### 2.3 载体为什么还是 `data:`，以及它带进去的【唯一】行为代价

`data:` 而不是仓库里一个 `.mjs`：① 文件载体要把自己的扩展名再推一遍，
而「由自己推 `.ts`/`.js`」正是 `worker-entry.ts` 声称**全仓只允许一处**的那种推导；
② `tsc` 在 `allowJs: false` 下**不把 `.mjs` 拷进 dist** ⇒ 产物里少一个 worker 必需的文件，
而症状又是「worker 起不来」⇒ **不红**。

⚠ **代价（这一条是修法自己带进来的，不是缺陷）**：线程里【包装那一个模块】的
`import.meta.url` 是 `data:text/javascript,…`，不是 `…/integrity.worker.ts`。
所以**入口文件自己**不能靠 `import.meta.url` 知道自己是谁 ——
而「拿不到路径」**不抛不红**，它是一个值不对的字符串，用它拼出来的东西安静地指向别处。
两个入口今天各 0 处用它（实测），`backup.ts` 那一处是**它自己这个模块**的 URL
（每个模块的 import.meta 是自己的，包装改不了别人的）⇒ 不受影响。
**这一维有断言**（① 那条「两个 worker 入口自己都不读 import.meta.url」），
不只是一句注释 —— 因为它是这次修法的行为代价，而行为代价的注释会随人员流动失效。
⚠ 那条判据的**射程只能按文件划**（入口文件本身），不能按「入口能碰到的模块图」划：
后者会把 `backup.ts` 那条不受影响的正常用法判红，
那是 0033 §3「更严的核对拒掉了唯一正确的接法」的同一族。

## 3. ⭐ 这条判据只能跑在另一条命令上，所以它得先把「跑法」本身当判据

第一篇写完判据我就差点宣布收工：`worker-entry.test.ts` ①② 那 11 发（在主线程里跑的
那些）在仓库常规那条命令下全绿，而**它们对本篇那个缺陷完全无感** —— 因为 §0 的 D 格。
量出来的证据不是推理：把生产代码那句删掉，① 那几发**红了**，③ 那两发行为断言**也红了** ——
但后者红是因为**我 spawn 的那个子进程用的是我自己写的那条命令**
（`--experimental-transform-types`，不含 `--import`）。
**换句话说：判据有效，是因为我恰好没用它想模仿的那条命令跑它。**

⚠ 这一节写的还是**第一版**的判据形状，而它防的东西与修法无关，所以修法换了（§2）
它**原样成立** —— 只是节号从 ④ 变成 ③、以及「线程那一侧的解析能力来自哪」
那句从「生产代码那句 execArgv」改成「生产代码那层入口包装」。
**这种「判据跟着修法搬家」的事本身值得记一笔**：
本篇真正的产出是那张矩阵（§0）与那条「判据必须跑在不宽容的命令上」的纪律，
而**修法是可替换的**（execArgv 那版活了半天就被既有用例否掉了）。
把判据写成「断言实现里含某个字面」的形态，换一次修法就得重写一次判据；
这里 ③ 那两条断的是**行为**（备份真跑成、页面检查真 ok），换修法不用动它们。

于是这一节的判据分成三条，缺一条整节就退化成「测我自己」：

| 判据 | 它防的失效 |
| --- | --- |
| 子进程必须**报回自己的 `execArgv`**，且断言其中**不含 `--import`** | 有人给 `spawnSync` 顺手加一条 `--import`（那等于把整节退回测 runner，而**它不会变红、只会变绿**）|
| 子进程必须**报回 `process.env.NODE_OPTIONS`**，且 spawn 时把它**摘掉** | §3.1 那一发：这是我自己在量本篇时**踩中的**假绿 |
| CANARY：**不包那一层**直接起真入口 ⇒ 必须**仍然坏**在兄弟模块解析不了 | Node 哪天自己在线程里做 `.js → .ts` 映射。它要是绿了，该删的是**生产代码里那层包装**，而不是把这条放宽 |

⚠ CANARY 那条**刻意不传 `execArgv`**。第一版写的是 `execArgv: [...process.execArgv]`
（那时的「修法」就是递 execArgv，所以「不修」= 只继承不追加），
而那一发**测的根本不是「没修」**：显式传 execArgv 自触发那道校验（§2.2），
它【**永远坏**】—— 而一条永远坏的断言和一条永远绿的断言**一样证不了任何事**。
改成不传之后，它才是修之前那行 `new Worker(WORKER_URL, { workerData })` 的字面形状。
⇒ **「反向对照」的有效性取决于它复现的是不是【修法之前那个形状】**；
 修法换了，反向对照**必须跟着重验**，否则它会悄悄变成一个恒红的摆设
 （而恒红的摆设比恒绿的更少见、更容易被当成「判据很严」而留下）。

### 3.1 ⭐ 我用 `NODE_OPTIONS` 亲手造了一次假绿，并差点据此判「生产代码那句没用」

量「父线程有钩子而生产代码没递」这个对照时，我写的是
`NODE_OPTIONS="--import <钩子>" node …` —— 想着这样**只有主线程**有钩子。
**读数是全绿**（备份 ran=true、页面 ok），于是我差点写下
「生产代码里那句 `execArgv` 是多余的」。

真相是 **`NODE_OPTIONS` 会进 worker 线程**：它和 execArgv 一样被继承，
而它**根本不出现在 `process.execArgv` 里**。
所以那一发量的根本不是我想量的东西，而我手上那条判据（断 execArgv 干净）**看不见它**。

⇒ **两条通路能到达同一个地方时，只关其中一条的判据是在报平安**。
⇒ 修法是**两条都断**，而不是「把环境弄干净然后只断一条」：
   spawn 时 `delete env.NODE_OPTIONS`（**在 spawn 这一层**摘 —— 子进程里
   `delete process.env.NODE_OPTIONS` **挡不住**，Node 启动时就把它读进去了，实测），
   再断言子进程报回来的那一份确实是 `null`。

⚠ 这里有一格**我故意不做**：发起方带着 `NODE_OPTIONS` 时**不把测试判红**。
污染已经在 spawn 处摘掉了，判据的有效性不再依赖环境干净；
把它判红只会逼人为了跑测试去改自己的 shell ——
**一条严错方向的环境判据，下场是别人绕开门禁**（0033 §3 那条同一族）。

### 3.2 「报回来」这条通路自己也必须是可测的

`NODEOPTS null` 在两种世界里都成立：环境真的干净 / **那条读数通路根本是坏的**。
所以配一发反向对照：带一个**无害的**值（`--max-old-space-size=64`）出去，
必须**原样读回来**。
⚠ 刻意不用 `--import` 当那个值 —— 它会真的改变 worker 的解析能力，
那就不是「通路对照」而是另一发实验了（**canary 要挑一个只碰通路、不碰语义的值**）。

## 4. 顺手量到的三条与本篇无关但值得留的事

1. **`packages/hub/dist` 今天不是任何人的运行时路径**。

   tsconfig 的 project references 只用于类型层。⇒ 那条钩子「构建产物那一态透明」

## 6. 与「更严」的距离：本篇**没有**做的四件事

1. **没有把它做成一条通用能力**。钩子只在两个 worker 入口之内的通路上生效。
   全仓第三处 `new Worker` 由 ① 那一发扫出来（当前**恰好两处**，含一条装配自检
   「扫不到文件就等于零处」），但**它只报位置、不自动递钩子** ——
   自动递意味着 `new Worker` 要包一层，而那一层会成为下一个「所有人都从它过」
   的单点，而本篇的教训恰恰是**通路上的宽容比没有通路更贵**。
2. **没有动 `pnpm verify` / vitest**（0036 §7 那条「跑不起来」本篇一字未改，
   但**它已被证伪了一半**，见 §7）。
3. **没有把 `main` 线程那一侧也统一**。§0 的 A 格（纯 type-stripping 连主线程都不通）
   **本篇没修**，它由那条 harness 钩子承担 —— 而那条钩子在 `node_modules` 之外，
   属于「跑法」不属于「仓库」。这是**一个已知的外部依赖**，不是被本篇消掉的东西。
4. **没有加「两份钩子逻辑逐字比对」的断言**。夹具里那份是**刻意副本**（它只服务主线程，
   见夹具文件头），漂了的后果是 ③ 红 —— 而**不是**一条比字符串的断言：
   那种断言在内容等价而写法不同时红，是噪音。

## 7. ⭐「vitest 本机装不上」这句被证伪了一半，而它在本仓**承重**

本篇在做判据时顺手把 `node_modules` 动过（`vitest` 与 `.bin/tsc` 两个软链，
指向 `/tmp` 里离线装出来的一份），**已全部摘除并核对**（`find node_modules -type l -lname '/tmp/*'`
为空，`.bin` 回到空目录）。动的过程里量到两件事：

1. **`vitest` 在【离线】是可得的**：`pnpm` 的 store 里能装出 **4.1.5**，
   而 `package.json` 声明的是 `^4.0.12`（**4.1.5 落在声明区间内**），
   锁文件 pin 的却是 **4.1.12**，而 4.1.12 那份 tarball **不在 store 里**
   （`node_modules/.pnpm/vitest@4.1.12_…` 这个目录**存在但是空的**）。
   ⇒ **「vitest 装不上」这句是假的；「装不上【锁文件 pin 的那一版】」才是真的。**
   ⇒ 顺带一句 `tsc`：`node_modules/.bin/` 原本是**空的**，
   而本仓文档里所有 `tsc -b --force` 的读数都是走
   `node node_modules/typescript/bin/tsc` 那条**绕开 .bin** 的路拿的 ——
   所以那 34 = 基线那个读数**不受 .bin 空着影响**（它本来就没走 .bin）。
2. **但 `pnpm verify` 仍然跑不起来**，而且本篇**没有**把它跑成：
   `pnpm install --offline`（不加 `--frozen-lockfile`）在 `zod` 那一条 tarball 上失败，
   172 条锁定 integrity 里 store 只有 **59** 条。
   ⇒ **本篇所有绿仍然是 `node:test` + 自制 harness 给的，不是门禁过了。**

⚠ **为什么这句话是「承重」的**：`docs/` 下 `grep -rn 装不上` 有 **45 行**，但其中
**只有 8 行讲的是 vitest**（`INDEX.md` 两处 + 0011 / 0026 / 0034 / 0035×2 / 0036 各一处），
其余 **37 行讲的是别的包**（`@langchain/*` 那几个，0009 §2 那一格）——
**那 37 行到今天仍然是真的**，别把本篇的更正套到它们身上。
⇒ ⚠ **我第一版这里写的就是「这句被写在 45 处」，而那是把两件事压成一个数**：
  「装不上」这个短语在本仓**指的不是同一个东西**，
  而我正是靠数那个短语的**总数**得出「影响面很大」这个印象的
  （0036 §0 那条「报结论要连付的价钱一起报」的同族 —— 先要问的是**数的是哪个集合**）。
  其中至少一处是**结论的前提**而不是背景描述：`vitest.config.ts` 的覆盖率阈值那一栏
  写的就是「我【无从测量】，本机没有 vitest」，而据此**没有填** 95 这个阈值。
⇒ **一条被写成「环境不行」的陈述，如果它是某条判据不落地的前提，它就会一直不被复查**
（环境类前提天然没人回去看，因为「回去看」的成本是装一次依赖）。
⇒ 本篇**没有**去改那 8 处（改一处就是一篇的读数，而本篇的读数不覆盖它们；
   且它们在写下当时的语境里是**真的** —— 当时确实没试过离线装），
   只在这里更正它，并把「阈值那一栏的前提已失效」登记为**下一步**（§8 末）。

⚠ **一条我**没能**复现的读数**：把那份 4.1.5 真接进仓库跑全量时，
量到 **71 发失败**（同一棵树在 harness 下是 37 发）。
本篇确认那**其中一部分**就是本篇这个缺陷（`backup.test.ts` 里
`expected null to be an instance of BackupWorkerThrewError` 那一族正是 worker 起不来的形状），
但**本篇没有把它逐发归因**，而且做那次读数所用的 `/tmp` 那份 vitest **此刻已经不在了**
⇒ **71 这个数现在不可复算**，别当成本篇的结论用；
它留下的**真问题**是「**自制 harness 还在别处替产品环境兜了什么**」，
本篇只回答了其中**说明符解析**这一格（§0 那张矩阵）。

- ⚠⭐ **本篇第一版的修法是错的，而它错在被本仓既有用例抓到之前，一路绿灯走完了我自己的全部判据**。
  这一条放在最前面，因为它比下面所有条都重要：
  我新写的 21 发**全绿**，错的是 `backup.test.ts` ⑦（红 6 发 + 整个文件不退出）。

  新判据审的是【我想到要审的那些维度】，而修法最常见的错在【没想到】那一侧，
  那一侧只有**既有**用例覆盖着。所以「改完只跑自己新写的那个文件」是**最危险的动作**，
  本篇差点就这么做了（差点就这么提交，是全量那一轮把它拦下来的）。

- ⚠ **判据只覆盖「说明符解析」这一格**。§0 那张矩阵是**照着一个具体问题量的**，
  它不是「test runner 与产品环境的差异清单」。
  **那份清单本仓没有**，而本篇的失效形状恰好说明它的价值：**差异不在用例里，在命令行里**。
- ⚠ **③ 那两发依赖 `node --experimental-transform-types` 能直接跑 `.ts` 入口**。

  **不会**被本篇的任何一条用例抓到。
