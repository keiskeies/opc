## 1. 一句话

规格 §18.3 给了三段示例代码，我照着实现，然后发现**其中三处照抄会做错事**。
三条都不是我理解偏差，是那段代码自己漏的形状；每条我都改了实现、配了用例、
并在这里写清「按原文实现会出什么」。第四条偏离不是规格错，是规格**自相矛盾**

## 2. 照抄规格 §18.3 会做错的四件事（都可复现）

| # | 规格原文 | 按原文实现的后果 | 我的处置 |
| --- | --- | --- | --- |
| 1 | `getDescendants(child, org).includes(newParent)` 作环判据 | **自环放行**。`getDescendants` 不含自身，所以「把 dev 挂到 dev 之下」判为合法 | 单加一条 `newParent === childRole` 判据，排在环判据之前 |
| 2 | `getDepth(newParent, org) + 1 > MAX_DEPTH` | **超深放行**。它只算被挂节点自己，不算它**带着的下级** | 改成 `parentDepth + heightBelow(child) > MAX_DEPTH` |
| 3 | `hasReviewGate(source, target, org)` | **第一条边永远加不上**。门控配置在 `onConnect` 校验**之后**才填（规格 §18.2 操作 C 自己写的流程），所以校验时那条边还不在 `org` 里，恒判「无门控」 | `reviewGate` 做成入参，缺省 `false` |
| 4 | `const running = getRunningTasks()` | **纯函数不成立**，于是「同一份代码前后端共用」当场失效（前端没有库连接） | 运行中任务作**参数**传入 |

第 2 条的第 4 件事要说清它和另外三条不同：**它不是措辞松，是算术漏**。
本机实测（`/tmp/probe-specdepth.mjs`，纯 node，无需框架）。树 `ceo→tech→dev→junior`
加 `ceo→product→p4→p5`，把带着 junior 的 dev 整支挂到第 4 层的 p5 之下，最深到第 6 层：

```
规格原句 getDepth(newParent)+1 在 dev(带 junior)→p5 上的结论： {"ok":true}
我的实现：                                                  {"ok":false, code:"depth_exceeded",
                                                            reason:"…最深处到第 6 层…"}
```

一句 `ok:true` 就是一张**违反组织层数上限的组织图被保存进库**，而 §18.4 的
版本化提交会把这张坏图写进 `delegation_graphs` 的新版本，此后每个新任务都在它上面跑。

第 3 条也值得单独看一眼，因为它会让功能**看起来**是坏的而不是危险的：
按原文实现，CEO 连线时每次都被弹回并告知「必须配置审阅门控」，而他还没被给过配门控的面板。
规格 §18.2 操作 C 那句 `onConnect → validateNewEdge → 通过后添加边并弹出边配置面板`
与 §18.3 那句 `hasReviewGate(source, target, org)` 是**同一份文档里的先后两句**，
按后一句实现，前一句那个流程走不通。

## 3. 判据顺序的一处偏离：根节点不可拖那一条挪到最前

规格把「CEO 不可拖」列为第 4 条。按 1→2→3→4 的顺序实现，拖 CEO 节点时
**用户看到的是第 1 条的报错**：CEO 的下级是所有人，所以任何「把 CEO 挂到 X 之下」
都先命中环判据，回弹提示是「不能将角色挂到自己的下级之下」。
那句话对他**不可操作** —— 正确回答是「这根本不该发生」，而报错指向了一个不存在的问题。

我把 CEO 那条提到最前。代价是判据顺序与规格示例不一致，四处换位，读规格的人对照代码会看到。

这条偏离值不值一条变异：**值，而且我第一轮没测出来**。
第一版那条用例只断言 `code === "ceo_is_root"`。要证明顺序承重，就得把 CEO 判据
真的挪回规格的位置（环 → 管理角色 → 深度 → **CEO**）再看有没有东西红。
我第一次写变异脚本时写错了 —— 把「挪到末尾」实现成「挪到环判据之前」，
**位置根本没动**，于是报出 `fail 0`，看着像「这条判据不承重」。
真正做对的重排 ⇒ **恰好 1 条红**：

```
✖ CEO 不可拖，且【不能】被环判据抢先报成「挂到自己下级之下」
```

那条用例现在断的是两件事：`code === "ceo_is_root"` **且** reason 里不含「下级」。
前半句已经足够让顺序错变红（顺序错时 code 会是 `would_create_cycle`）；
后半句不增加拦截力，它增加的是**这条用例在讲什么** —— 没有它，
下一个人改顺序时会看到一条 code 不匹配的失败，而看不出「指向错误的方向」
本身就是被守的性质。这个区分很细，我不夸它，但它是这次唯一一处
「断言的形状比断言的强度重要」的地方。

## 4. 一条我自己引入又删掉的参数：`canReach(org, from, to, extra?)`

第一版多带一个 `extra`，用来把「正在校验、还没写进图的那条边」塞进遍历，
注释写的是「加边之后才可达成，所以它必须参与遍历」。**那句是错的**，
而且错得很像对的 —— 「图变了要按新图算」听起来不需要论证。

反证一步：从 `target` 出发、用上了边 `source → target` 的路径，
必然**先回到 `target`** 才能踩到那条边（那条边的头就是 `target`）；把中间那个环剪掉，
就得到一条不使用新边、终点相同的路径。所以「从 `target` 出发的可达集」加这条边前后恒等。

我在三种图形状（新边指向已在链上的节点 / 反向边 / 二元环）上比对过加与不加的可达集，
都一样 —— 那只是**佐证，不是依据**，依据是上面那步剪环论证。
**第四个用例没跑出来**：我那支探针自己写错了（在内层 `for` 里 `shift()` 队列，
某些形状下死循环，挂到超时被中止），所以「四处都测过」这句不能说。

边界划准，免得这条被读成通用结论：加边 u→v 不改变「从 `from` 出发的可达集」的情形
**不止我这一种** —— v 本来就在可达集里时也不变（可达集对传递封闭）。
**会变**的是「u 可达而 v 不可达」。我这一处落在前者里。

删掉而不是留着「以后也许用得上」：恒不生效的参数骗两类人 ——
读的人以为判据考虑了新边（其实没有，他就会**不去想**这件事），
改的人以为传了就一定是按新图判（其实取决于上面那个判据）。
真正需要按新图判的地方是深度判据（`wouldExceedMaxDepth`），那里新边**确实**在路径上，
所以它自己展开了边集而没有走 `canReach`。

## 5. 本篇最该被读到的一节：**变异实验报「全绿」，而那次什么都没测**

我改了判据就要证明用例挡得住改回去。第一轮跑了四个变异（删自环判据、深度退回规格原句、
CEO 判据重排、去掉坏图入口守卫），**四个全部 `fail 0`**。
这个结果本身就是线索：四条互不相关的判据、各自只被一条用例守着，
不可能一起「改坏了也没事」。**一个把什么都测绿了的实验，和一个什么都没测的实验，
输出是同一个。** 顺着这条去查仪器，当场就找到了原因：
**测试 import 的是 `@opc/contracts`，它解析到 `dist/`；而我变异的是 `src/`，
中间没有重新编译。** 那四轮跑的是**同一份未变异的旧构建产物**。

（写在这里是因为差一点就走成另一条路：`fail 0` 最自然的读法是「断言不够强」，
于是我可能去**加一堆本来就多余的断言**，让测试变长而覆盖率性质一点没变。
这次我方向猜对了，不代表判据是「感觉」——判据是**四个一起为零**这个不合理的形状。）

在变异与运行之间插入 `tsc -b packages/contracts --force` 之后，同样的四个变异：

| 变异 | 结果 |
| --- | --- |
| 删掉自环判据 | 1 红：`自环：挂到【自己】之下` |
| 深度退回规格原句（只看 newParent+1） | 1 红：`深度：被挂的那一支【自己带着下级】时…` |
| 去掉 `rejectMalformed` 入口守卫 | 2 红：`图本身有环…` + `汇报关系指向不存在的节点…` |
| CEO 判据挪到深度判据之后 | 1 红：`CEO 不可拖…`（第一次那版脚本没真的挪，见 §3） |

三条教训，第 3 条是新的：

1. **变异实验必须包含「让改动到达被测方」这一步**。我的变异循环里本来「有」编译
   （我在源码编辑之后手工跑过 `tsc -b --force`），但那是**测绿基线**时跑的，
   不在变异循环内。一次实验的有效性由它**最弱的那一步**决定。
2. **`fail 0` 在最坏情形下与「测得很稳」长得一模一样**。判据是：如果四个互不相关的
   变异全都一条不红，先怀疑仪器，不要先怀疑测试。这次我怀疑反了方向。
3. 更一般的形式：**只要被测方与改动方之间有一层构建产物，任何「改了但没重建」
   都会伪装成通过**。0010 那种「测量之后又改了被测对象」是它的近亲，
   但那条至少还会给出漂移的数字；这一条给的是**完整的、干净的红名单为零**。

同一轮里另一个装置缺陷记一下以免重犯：探针 `while` 与内层 `for` 混用 `shift()`
造成死循环，**它挂住而不是报错**（120 秒后被挪到后台）。这与 0010 §3 那条
「一条在真实回归下挂住而不报错的测试比漏测更坏」是同一形状，只是这次挂在探针里。

## 6. 顺带测出的一条性质：坏图上的静默放行

`rejectMalformed` 这个入口守卫不是「防御性编程」。规格那三段示例都假设图是正常的，
而**图坏了的时候往下判会给出 `ok`**：`pathToRoot` 因为有环保护会给出一个**偏小**的深度，
于是「深度超限」在真正超深的坏图上反而不触发。实测（把守卫注释掉，纯 node 探针）：

```
无入口守卫时，在【成环的图】上判 product→dev： {"ok":true}
```

`{"ok":true}` 就是「一张 reports_to 成环的图，任何改动都合法」。
库里存的是 `graph_json`（`delegation_graphs` 表），一次手工修库或一个旧版本写入
就能造出这种图 —— 不是假想输入。恢复守卫后同一条探针：

```
{"ok":false,"code":"report_cycle_present","reason":"当前组织图的汇报关系本身成环（tech → dev → tech）…"}
```

同一层还有两条形状上的收紧（都有用例）：`can_manage` **必填**（漏填不是「不是管理角色」，
是加载期报错），以及 `nodes` 上 `strict()`（把 `reports_to` 拼成 `report_to`
不会退化成「所有汇报关系凭空消失」，而一张没有汇报关系的图在三层校验下**全绿**）。

## 7. 需要 CEO 认账的一项：**§18.3 那段示例代码算不算规格正文**

问题不是「实现对不对」，是**下次遇到同样的矛盾时，实现层该按哪一半**。

规格 §18.3 同时提供了「三段示例代码」与「三层校验必须是确定性代码：纯函数 + zod，
不查 LLM、不读网络」这句加粗要求，二者在 `getRunningTasks()` 那一句上直接冲突；
而 §18.2 与 §18.3 在门控参数上也互相走不通。本轮我**全部按文字要求实现、
把示例代码当示意**，于是三处签名与规格代码不同：

```ts
validateNewEdge(source, target, org, reviewGate = false)   // 规格：无第四参数
validateOrgChange(change, actor, runningTasks)             // 规格：runningTasks 内部取
wouldExceedMaxDepth / 深度判据：parentDepth + heightBelow(child)   // 规格：getDepth(parent) + 1
```

- **认可「文字要求优先于示例代码」**（我倾向这一项）：那三处偏离就此合法，
  §18.3 的示例代码应当就地更新（否则下一个实现者会重新踩一遍，
  而他会以为是他自己没读懂规格）。
- **反过来，示例代码是规格正文**：那么 §2 表里第 1、2 条是**规格缺陷**要改规格
  （自环放行、超深放行都是我按它实现的必然结果），第 3、4 条则说明 §18.2 那个流程
  要重设计。这两件事都不在实现层权限内。
- **第三种：逐条判**（§2 的第 1、2 条按我实现，第 3、4 条回到规格）
  —— 我不建议：第 4 条回到规格会让 contracts 包欠一个库连接，
  「同一份代码前后端共用」这条计划硬要求当场不成立。

为什么这条该你拍而不是我自己定：它不是这三个函数的事，
是**「文档自相矛盾时实现层有多大的裁量权」**这件事的事。
本轮我裁了四次，四次都写在上面；但裁量权本身不该由我给自己。

## 9. 一处**已知重复**，不是漏看

（运行时判定，带批准凭据）与 `org/validate.ts` 的 `violatesNoSelfReview`
