# 0065　`metrics` 的第三态终结：列加上了，而「谁来算这个数」一格照旧没人 —— 以及一次镜像夹具自己演示了自己该死

## 1. 一句话

O5 动作 3 给 `metrics` 两个选项（加列 / 从契约删掉），落地选了**加列**（迁移 0007 +
`register()` 序列化），因为删掉会连带杀死 `metric:` 判据形状 —— 那是全仓唯一可机械
判定的验收标准形状，用一个「暂时没人填」去杀「能判的那根独苗」，方向反了。
但要产出的保证要说准：**这一列修的是「数存在哪」，不是「数谁来算」** ——
「src 没有算这个数的代码」是本轮 grep 全量命中后的口径判定（§4 附表），
而 dispatch 调 `evaluateGate` 的次数是 **0**（本轮实测，§3）。
所以这一列今天的正确读法是「通道铺好了，源头还没接」。

## 2. 为什么加列而不是删字段：两个选项各自的代价被量过

| 选项 | 代价（实测/推演） |
| --- | --- |
| 从契约删掉 `metrics` | `gates/evaluate.ts` 的 `metricCriteriaEvaluator` 读的就是 `bundle.metrics`；删字段 ⇒ `metric:x <op> n` 整族形状失效 ⇒ 岗位书验收标准退回【全部自由文本 ⇒ 全部 escalate】。`how-to-write-a-charter.md` 的整篇 §2 与北极星（§23.1 八成审批由规则自动决定）都挂在这个形状上。 |
| 加列（落地选择） | 一条 `ALTER TABLE ADD COLUMN metrics TEXT` + `register()` 多绑一个参数 + 三处测试钉子同批改。存量库零影响（NULL 缺省），已有部署直接可升。 |

第三态的具体形状（本列要终结的东西）：契约允许内存对象带着 `metrics` 过门控，
而库里没有那一列 —— 于是存在一条【能判而从未落盘】的路：门控判过一个数，
那个数不进任何表、回放看不到、审阅时无法二次核对、sha256 对账（只管 artifacts 文件）也覆盖不到。

## 3. 动作 2 的前提本轮量塌：dispatch 根本没有门控可喂

动作 2 原话：「`dispatch` 的 `pass` 分支在建事件之前算 `integrityOk` 并传给门控。」
这句话假设 pass 分支上有一次门控调用。实测：`grep -c evaluateGate engine/dispatch.ts` ⇒ **0**。
门控在 src 的唯一调用方仍是 `harness/verifier.ts`（死模块基线里；0062 就量过这一格，
本轮复核未变）。给 dispatch 算一个没人收的布尔，是 O4 动作 2 刚论证过的那种事
（为到不了的输入造数据）—— **同族错误不能犯第二次**，所以动作 2 登记为前提不成立：
`integrityOk` 要等的是**门控接进执行路径**那一格（O4 验收句指的正是它），不是 dispatch 单侧先算。

这也是为什么动作 1（最小证据形状）没有单独先做：形状只有配着消费方才不空转，
而消费方（门控上线路）与生产者（dispatch 带包）必须一起设计 —— 先落形状等于再造一个第三态。

## 4. 三态落库：NULL / "{}" / 有值，两个都不许折叠

`metrics` 在契约里是 optional，「没带指标这个概念」与「带了但没声明具体指标」
是两种说法（同 `evidenceRefs` 的 `null` vs `[]` 那一家）。落库必须保得住这个分别：

- 缺省 ⇒ 绑 `null`（列是 TEXT，NULL 就是 NULL）。**刻意不写 `JSON.stringify(bundle.metrics)`**：
  `JSON.stringify(undefined)` 返回 `undefined` 本身，参数位拿到它是绑 NULL 还是抛，
  是实现细节而不是承诺 —— 同文件里 claims / honesty_boundaries 敢裸写，
  是因为 schema 强制它们存在，metrics 没有这个强制。
- `{}` ⇒ 存字符串 `"{}"`。测试里 `coverage: 81.5, p0_defects: 0` 的 **0 是刻意留的**：
  它测「0 不会被 falsy 折叠成缺省」。
- 变异实测：把显式折 null 退回裸 `JSON.stringify` ⇒ 两发红（落库那发 + 三态那发），原样恢复。

## 5. 镜像夹具自己演示了自己该死：改列时它红的方式是【混着两种故障】红

改 INSERT 列清单前，本仓有三处「长得像那条 INSERT」的测试镜像
（`bundle.test.ts` 夹具、`integrity.test.ts`、`schema-0001.test.ts` 的 FK 探测）。
按两向核对纪律，先改 src 跑一遍：预测的两发钉子（migrate 版本清单、bundle 十字段夹具）
**当场红**—— 这一步不是仪式，它把「我预测的钉子表」变成了「实测的钉子表」。

但 bundle 夹具这一发的红因值得记：它是【手抄的列清单与 src 的副本漂移】，
红话读起来却像【落库错了】—— 一次混两种故障。所以修法不是「把镜像改成十一列」，
而是**让夹具直接执行 store 自己那条 SQL**（`db.prepare(sql).run(...params)`）：
src 改列 ⇒ 直接打在真 schema 上，列错了红在 SQL 本身，副本漂移这一类整个消失。
镜像从「三份会各自过期的复印件」减为「零份」。

自己的手滑一个：三态用例第一版按 `ORDER BY created_at DESC` 读回两包，
而夹具的 `now()` 恒为 1 —— 两包时间戳相同，排序退化为主键序，属实现细节。
写完自查发现，改按 bundle id 读回。

## 6. 顺带撞出来的一条过期主张（O14 的现行案例，落在文档不在代码）

改这份文档时发现 `how-to-write-a-charter.md` §6 第 6 条与 §1 表格行都写着
「`saveCharterVersion` 今天零生产调用方 / 改 YAML 今天没有入口」。**这条已经过期**：
`charter/seed.ts`（O2 动作 2，`pnpm hub:charter`，根 package.json 的静态入口之一）
就是它的生产调用方，dead-modules 探针实测 `charter/seed.ts` 可达（作为入口本身）。
本篇同批改这两处为「有入口（seed），而配置页那条通路仍未接」的准确形状。
这就是 O14 立项理由的活样本：这句话过期时**没有任何东西变红**，
它是被一次无关改动顺手撞见的 —— 「靠撞见」正是 O14 动作 2（主张登记表）要替换掉的机制。

## 7. 没做的，别当成做了

1. **谁来算 metrics**：口径写死，否则「0 处」会被读成任何强度的主张。本轮 grep 全量命中
   `metrics` 于 src 的**每一个**位置并逐处归类：契约字段定义（evidence.ts:107）、
   store 的落库序列化（本轮加的）、门控的【读】方（evaluate.ts 一族）、verifier 的
   转发（:618 把注入函数 `assemble` 交回来的 metrics 原样拷进包 —— 它自己不算数，
   且整模块在死基线里）。**没有一处计算或采集任何指标值**（覆盖率从测试报告来、
   缺陷数从缺陷单来 —— 那两个源在本仓都不存在）。今天给 metrics 塞过值的代码全在
   测试夹具里（`bundle.test.ts` 本轮两发、`test/acceptance/phase1-gates.test.ts` 的
   `p0_defect_count` 一族、`phase3.test.ts` 的 realBundle）—— 测试侧，不是生产。
   那需要 dispatch 交接带包 + 门控上线路一起设计（§3），本轮一列没接。
2. **动作 4（卡片显示「背后没有证据包」+ `approvals` 指向证据包的列）**：独立于门控
   可达性，是 O5 里下一格能独立动的；~~本轮没动。~~ **本篇写下后下一轮已独立落地**
   （迁移 0008 + 建卡写侧 + 读侧 `evidenceRefsOf` + 契约 + UI「无证据包」一行；
   round270 补账时核实并补齐台账与变异证据，见设计文档 O5 落点段第 4 条）。
3. **指标词表**：`metric:` 的名字词表仍不存在（charter 指南 §3 反例 ② 的原件立场照旧）。
   加列只是把「存」铺好，第一次有人填数时仍要一起立词表。
4. `EvidenceStore` 对外零 import 的状态**没变**：`register()` 今天仍然只有测试调用方。
   这一列不是生产者，是存放处。
