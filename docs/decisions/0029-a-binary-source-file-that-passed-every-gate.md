# 0029　一个已经 commit 的二进制源文件，以及「编译过、跑得对、测试全绿」为什么不是证据

- **状态**：已定案（修掉那两处字节 + 补一条守卫）。
- **产出**：`packages/hub/src/harness/gateway.ts`（两处字节，运行时值一字未变）、
  `test/arch/no-null-bytes.ts` + `test/arch/no-null-bytes.test.ts`（新守卫，5 发 + 3 发变异）。
- **一句话结论**：这一篇的东西不在「找到一个 bug」，在**那个 bug 穿过了整个门禁系统而没有任何
  一环报警** —— 而它穿过的原因是**每一环检查的都是别的东西**：tsc 检查语法（NUL 在字符串字面量里
  合法）、测试检查行为（运行时值完全正确）、`check-gate` 检查文档。**没有任何一环检查
  「这个文件还是不是一个文本文件」**，而这件事一旦失守，本仓用得最多的那件工具
  （`grep -rn`）**会主动给出假阴性**，且假阴性读起来正是「没有这个毛病」。

## 0. 它是怎么被撞见的（不是我找的）

我在跑一次「哪些模块造好了而没人调用」的普查（脚本随手写的，本篇末尾 §4 记它的读数），
其中一步是 `grep -rn "verdictKey" packages/hub/src`。grep 的回答是：

```
Binary file packages/hub/src/harness/gateway.ts matches
```

**只打文件名，不打行号，不算命中。** 这个文件我此前当作普通源码引用过
（`grep -l gateway.ts docs/decisions/*.md` ⇒ 0021 与 0022 两篇都引过它的行为）。

字节扫描：两个 0x00，在 `verdictKey` 那两行的字符串字面量里。

```ts
return tool + "<NUL>" + JSON.stringify(args ?? null);      // 380
return tool + "<NUL><不可序列化#" + (verdictCache.size + 1) + ">";  // 382
```

来源：`git show 1877e8e:...gateway.ts` 里**那两个字节已经在**，blob 46673 字节、NUL 2 个。
**是 Task 5.1 那一次提交带进来的，从写下到现在一直是这样。**

成因与我早些时候在 `channels/abstraction.ts` 上撞到的是同一个：
写代码时想表达 `"\x00"` 这个分隔符，工具把转义**当成真字节写进了文件**。
`abstraction.ts` 那一次我在写完的当场因为 `grep` 报 binary 抓到了并改成了
`String.fromCharCode(0)` + 一个具名常量；**gateway.ts 这一发我写的时候没看 grep，
它就一路 commit 进了 git**。同一个错，两次，第二次成功入库 —— 这说明
「下次注意」在这件事上不是修法，**修法是一条守卫**。

## 1. 它坏了什么，以及**没**坏什么（两半都要写清）

**没坏的部分**（这部分决定了它能活这么久，别写成「幸好发现了所以没事」）：

- **运行时行为一字不差。** `"\x00"` 与 `"\u0000"` 在源码里是同一个字符，
  那个键（审批去重缓存的键，同一个 `tool + args` 只问 CEO 一次）算出来完全相同。
- **tsc 过、测试全绿、跑起来也对。** UTF-8 里 NUL 是合法字符，Node 与 tsc 都不报警。

**坏了的部分，三件，全是静默的**：

1. **`grep -rn` 从此对它恒返回「Binary file matches」。** 本仓大量纪律的形状是
   「动手前先 grep 一遍再下结论」（0013 §10.1 开的那一族，我自己在 0027/0028 里也各用了一次）。
   一个含 NUL 的文件在这些普查里**不是"读起来费劲"，是根本不出现**。
   现成的例子就在本仓的历史上：那条
   `grep -rn "INSERT INTO approvals"` ⇒「0 命中」的普查是 0026 整篇的地基。
   **如果那次扫的那个文件含 NUL，结论一字不变地还是「0 命中」**，
   而那句话是「这张表没有创建路径」的全部证据 —— 一个假阴性会被当成**证据**用。
   这一条是我在这一篇里学到的最贵的一条：以前我把 grep 当仪器，现在要给它的
   **口径**加一条前提（被扫的文件必须是文本，而这件事今天没人检查）。
2. **git 侧全瞎**：对它的所有 `diff` / `blame` / `log -S` 显示 `Binary files differ`。
   一次改动**看不到改了什么**。我这次是**靠字节扫描才知道它有几处**的，
   而 review 一个含 NUL 的文件的人多半直接跳过它。
3. **Edit 工具的 `old_string` 匹配不到它**（它按文本处理）。想改它只能整文件重写，
   而**整文件重写一个含中文的文件正是 0027 §5-③ 那条纪律要防的事**。
   本次修复就是这条的活证据：那个文件**只能**用字节级脚本改（见 §2）。

## 2. 修法：为什么这次**必须**违反我自己那条纪律

0027 §5-③ 写的是「含中文的文件只走 Edit，不走 shell」。这次走的是 shell 脚本，理由：
**Edit 匹配不到目标**（文件在工具眼里是二进制，`old_string` 里那个 NUL 无法表达）。
所以那条纪律的前提（Edit 能用）在这里不成立 —— 纪律失效的方式不是被打败，是前提被抽走。

脚本做的事只有一件：把 2 个 `0x00` 字节各换成 6 个 ASCII 字节 `\u0000`（源码里的转义序列，
运行时求值成同一个字符）。全程走 `Buffer`，**不解码再编码**（那正是 0027 §5-③ 防的动作）。

自检三件，全过才写回：字节数 `+5 × 2`、替换后不含 NUL、
**把转义文本按 latin1 往返换回一个 NUL 字节后与原文件逐字节相同**
（latin1 是字节↔字符一一对应的编码，所以那条往返无损 —— 这是我敢用 shell 改含中文文件的唯一理由，
而它必须先被证明无损，不是先假定）。

⚠ 顺带把**那处修复本身的反向断言**也写进守卫：不许有人把分隔符换成一个**可打印**字符
（`:` 之类）。那**不是同一个修复的另一种写法，是另一个 bug** ——
`tool` 名与 `JSON.stringify(args)` 里都可能出现可打印字符，用它拼键能被拼出碰撞，
后果是**两次不同的工具调用共享同一个审批判决**：第一次批过的 `git status`
会替第二次的 `git push --force` 放行。所以这个键的分隔符必须是不可打印字符，
本篇只把「字节」换成「转义」，**没有**动那个字符本身。

## 3. 守卫（`test/arch/no-null-bytes.ts`）与它的三发变异

判据扫**字节 0x00**而不是扫内容 —— 「读成什么编码」正是这件事坏掉的那一环，
用它当判据的工具等于用坏掉的那件工具自检。报错时给出**路径 + 行号 + 前后文字**
（`<NUL>` 标位），否则下一次的人还得再手写一遍扫描脚本，而那一步就是本篇的成因。

三发变异（判据本体先被证明有牙齿，才算数）。重跑口径 ——
**结论旁边的数字不记命令就不可复算**（0006 §7 那条纪律，0028 §5 同一做法）：

```bash
# M1：往被扫目录塞一个含真 NUL 的文件，跑守卫，再把探针删掉
node -e 'const f="packages/hub/src/__p.ts",b=require("node:fs");
  b.writeFileSync(f,Buffer.concat([Buffer.from("export const x=\"a"),Buffer.from([0]),Buffer.from("\";")]));'
PATH=~/.nvm/versions/node/v24.14.0/bin:$PATH node --experimental-transform-types \
  --import /tmp/opc-harness/register.mjs --test "test/arch/no-null-bytes.test.ts"
rm packages/hub/src/__p.ts
# M2 反向对照：把上面那个文件写成不含 0x00 的干净内容，守卫必须【无红】
# M3：把 gateway.ts 那处的 \u0000 临时换成 ":"，看「确实被修掉了」那发红，然后还原
```

⚠ 数红的正确姿势（**这一条本身就是本篇的一个读数错**，见本节末）：
从输出里 `failing tests:` **之后**提 `✖` 行，并剔掉父级 suite 与 `failing tests:` 本身 ——
**不能**用 `output.includes(测试标题)`，因为 spec reporter 无论红绿都会打标题，
那个判据**恒真**。

| 变异 | 结果 |
|---|---|
| M1 塞一个含真 NUL 的源文件进 `packages/hub/src` | 红「真仓库：一个 NUL 字节都没有」，报错带探针文件的**路径与行号**（行号指到了那个 NUL 所在行）|
| M2 塞一个**干净**文件（反向对照）| **无红**（守卫不是恒红） |
| M3 把 gateway.ts 的 `\u0000` 换成 `":"` | 红「gateway.ts 那一处确实被修掉了」那条专项断言 |

**而 M2 第一次跑是"红"的 —— 那是我这一篇里唯一一次真错，值得单独记。**
第一版变异脚本的判据写成 `out.includes(测试标题)`，而**测试标题无论红绿都会出现在输出里**
（node 的 spec reporter 把每一发的名字都打出来）。于是三发变异全报"红"，
包括那发本该绿的反向对照。**一个恒真的判据看起来正好就是"这条守卫很有用"** ——
它不会报错，它只会让你以为验过了。修法：从 `failing tests:` 之后提 `✖` 行，
并**照旧剔掉父级 suite 与汇总行**（0027 §4/§5-① 那个「数 ✖ 行数出 3 红，其中一行是父级
describe」是同一个坑，我这次是**提前**用了上次记下来的正确数法，
却仍差点被"标题也算命中"这一维绊倒）。**⇒ 反向对照不是可选的一发**：
如果我只跑了 M1（它真的红了），我会带着「守卫有牙齿」这个**正确结论**离开，
而依据是一次**没有任何判别力的观察**（M1 那条红也可能是别的红）。
「结论对 + 证据无效」这一族在 0027 §4 已经付过一次学费，这里是同一族的第三次。

## 4. 那次普查的读数（记下来，因为它没被采信，也不该被马上采信）

普查脚本数「每个导出符号在**其它 src 文件**里被引用几次」，报出 351 个 0 引用符号，
含 `search/policy.ts`（Task 5.7 那个策略引擎）整模块。抽查两条：

- `searchPolicy` 全仓命中：它自己那一个 src 文件 + 它的测试文件 ⇒ **0 个 src 调用方，成立**。
- `quoteFtsPhrase` / `charterFieldPaths` 我一开始记成「有命中 ⇒ 普查误报」，
  重查发现**命中全在它自己的文件内与测试里** ⇒ 普查其实是对的，
  **是我读错了自己写的判据**（我把"grep 有命中"当成"有调用方"，而脚本问的是"别的文件"）。

两件事因此都记在这里而不是被做成行动：

1. 0 引用 ≠ 该删。这批符号里很多是**接口实现 / 契约类型 / 计划里排了但依赖没装上的那一半**
   （`search/policy.ts` 是 Task 5.7，它等的是 agent 循环；harness 那几个等 `@langchain` 与 SDK）。
   **造好了等装配**与**造好了没人装配**在源码上长得一模一样，区分它需要的是计划信息，机器给不了。
2. 而 0014 那个标题（`a-module-nobody-calls`）说明这一族在本仓已经出现过，
   所以「这次不一样」不是理由。**留下的可操作结论只有一条**：等哪天某个模块接上时，
   要接的是它**已有的**那些判据而不是再写一份 —— 那正是 0028 §1 里
   `channelIneligibleReason` 复用 `isIrreversibleApproval` 的同一条理由。

普查脚本本身**不入库**（一次性的、判据粗、口径要靠人读），
它唯一的产物是这一节那两条被抽查过的读数。

## 5. 强度

`test/arch/no-null-bytes.test.ts` 5 发全绿、3 发变异如上；全量与 arch 的红名单
与基线**逐条相同**（本篇新增的红 0，消失的红 0）；`tsc -b --force` 34 条 = 基线；
