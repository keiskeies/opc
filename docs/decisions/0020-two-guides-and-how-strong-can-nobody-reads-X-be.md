# 0020　两份指南，以及「这个字段没人读」这句话能说到多强

- **状态**：已定案（Task 6.6 的产出就是那两份指南，本篇记的是写它们时量出来的东西与我自己犯的错）
- **产出**：计划 Task 6.6 —— `docs/guides/how-to-write-a-charter.md`、`docs/guides/delegation-rules.md`
  （计划那句要求：岗位书写法指南必须含「如何写可机械判定的验收标准」的正反例，
  因为规格 §23.2 把这件事列为最大风险）
- **为什么 Task 6.6 还要单独有一篇**：指南回答「你动手时该怎么办」，本篇回答
  「指南里那些『今天不生效』的说法，各自的证据强度是什么」。前者对读者有用，
  后者对**下次要改这些地方的人**有用 —— 而且后者如果只写在对话里就等于没送达。

## 0. 一句话结论

写这两份指南之前我以为自己知道门控在判什么；写完时我确认了三件事**不成立**，
而它们全是「读起来像已经做好」的那类：门控有生产调用方、指标有地方存、
模板没签完会让 CI 红。三条都不是新决定，是**此前被自己的注释与文档说成了已成立**。

## 1. 为什么是 `guides/` 而不是再写一篇决策

计划的 Files 列的是 `docs/guides/how-to-write-a-charter.md`、`docs/guides/delegation-rules.md`、
以及「`docs/decisions/` 索引」—— 也就是 Task 6.6 要的产出是**写法**加**一次索引更新**，不是第四条理由。

分工按 `docs/INDEX.md` 里已经写着的那句收窄：`decisions/` 记「最后为什么这么实现、依据是哪次实测」，
`guides/` 记「**要动手的人该怎么写、以及哪些字段今天不产生机器行为**」。
两篇指南里都留了一节「今天还没长手的地方」，那是给动手的人的**前置条件**，
而不是本篇的论据 —— 论据在下面三节。

## 2. 「零读者 / 零调用方」这句话的证据强度分三档（本篇的主张）

指南里我写下了十几条「X 零生产调用方」。这类话本仓有明文规矩：
**否定性主张只能由变异实验证明，不能由「我搜过了没找到」证明**（0006 §7）。
按这个规矩复核自己写的每一条，得到三档，而**我最初是一股脑写成同一档的**：

| 档 | 判据 | 本篇里属于这一档的条目 |
|---|---|---|
| **甲：强**（改它会红 / 调用点可枚举到零） | 全文 grep `函数名(` 只有定义处与测试；或那条断言本身可跑 | `evaluateGate` 零生产调用方、`gateCriteriaForRole` 零生产调用方、`saveCharterVersion` 零生产调用方、`commitOrgGraph` 零生产调用方、`judgeCriteria` 死代码 |
| **乙：中**（只有声明处与读它的那一行命中） | `grep -rn 字段名 packages/*/src` 命中数 = 声明 + transform | `forbiddenActions` / `toolPermissions` / `escalationTriggers` / `honestyBoundaries` / `judgmentMode` / `untrustedInputs` 六者的 camelCase 形态 |
| **丙：弱**（我只证明了没找到） | 需要「改了它也不红」的实验而我没做 | 「`metrics` 没有任何生产写入方」 —— 见 §4，这条恰好有更强的证据，我一开始却只写了 grep |

**这条分级本身就是产出**：指南里甲乙两档我按档写（甲说「零调用方」，乙说「除 transform 那一行再无命中」），
丙档要么找到强证据要么降级措辞。`honesty_boundaries`「会进 prompt」这句就是我按乙档撤掉的 ——
`grep -rn honestyBoundaries packages/*/src` 只有 transform 那一行，
**所以那份诚实边界今天连模型都到不了**，它是写给配置页看的一句话。
我原本在指南里写的是「进 prompt，对模型有约束力」，那是一句**顺着一个必填字段的语义编出来的安慰话**，
和 0019 §5 里那条「给一段走不到的代码编了个成因」同形。

## 3. 三件我原以为成立、实测不成立的事

1. **「模板没签完 CI 就一直红」——不红，签字了才红。**
   `charter.test.ts` 那条断言写的是【模板里仍然含占位串】**为真**。
   这句话在**七份模板自己的头注释**、`@opc/contracts` 那个常量的注释、`docs/INDEX.md` 的等待条目里
   写了三份，全部与实现相反。0006 §7 已实测过（两次变异）并选择不改方向
   （「CI 该不该常红由 CEO 定，不由实现层定」），所以本篇不重复处置，只做一件事：
   把 `docs/INDEX.md` 里那句原话标 **【撤回】** 并补上真实后果 ——
   **没有任何一条 CI 在催这件事**，而七份岗位书全是自由文本 ⇒ 门控一条也判不成（全 escalate）。
   ⚠ 值得留下的是**它为什么能活这么久**：一个"没人被催"的缺陷，表现恰好与
   "有人在被催"完全相同（都是标准还没落地）。**只有去读那条断言的比较方向才能区分两者**，
   而所有人（包括我）都在读注释。
2. **「`dev_to_test` 这一闸收任何 `bundle_type` 都照收」** —— 这句是我从 `evaluateGate` 文件头抄的，
   而它**在文件头的语境里成立、被我抄成不成立**：那段讲的是**整函数**零生产调用方，
   所以那张表在真实运行里没被用过。而函数**内部**确实在判类型（类型不符 ⇒ `reasons` ⇒ reject，
   未知方向 ⇒ `unresolved` 而不是抛错，因为抛错会让整闸跳过）。
   第一版指南里我照抄成「类型这一维没在判」，这是**把「没人调用这段判据」抄成「这段判据不存在」**。
   真正的洞在别处，见 §4。
3. **`tasks.graph_version` 全是假的 1** —— 这条 0012 记过，而我在 delegation 指南里把它写成
   「那一格还漏着」。实测现在 `INSERT_TASK_SQL` 已把这列作为 INSERT 的一列写进去，
   且与 `currentGraphVersion()` 共用 `node()` 回调里那条连接、那个事务（拆两条会留窗口，
   两次 `node()` 是两个事务，中间允许别人提交一版 ⇒ 建出「在 v7 之后建却盖着 v6」而一句报错都没有）。
   **我引用了一份自己写过的决策记录里的旧状态而没有重测**，这是本仓那一族错第 N 次现形。

## 4. 本篇唯一的实测新发现：契约里的 `metrics` 在库里没有列

`packages/contracts/src/evidence.ts` 的 `EvidenceBundle.metrics`（可选的
`记录<string, 有限数>`）是门控所有数值标准的**唯一取值来源**
（`metricCriteriaEvaluator` 从 `bundle.metrics` 取，缺键 ⇒ `unresolved`）。

而它没有落库的位置：

- `evidence_bundles` 的列是 `id / task_id / producer_role / bundle_type / artifacts / self_check / created_at`；
- `0002_phase1_evidence_and_budget.sql` 补的三列是 `model_family / claims / honesty_boundaries`；
- `grep -n metrics packages/hub/resources/migrations/*.sql` ⇒ **零命中**；
- `EvidenceStore.register()` 的 INSERT 列清单里也没有它。

所以今天的形状是：**契约允许一个内存对象带着 `metrics` 过去被门控判，而这个数从未被写过一次磁盘。**
比「没人填」更糟的正是这个 —— 有人接上填充之后，最省事的接法就是手搓一个带 `metrics` 的对象，
于是得到一条**能判而不留痕**的标准：回放看不到它、审阅时无法二次核对、
也不在规格 §5.10 那套 sha256 对账的覆盖范围内（那套对账只覆盖 `artifacts`）。
而规格 §14.4 红线二要拦的恰恰是「自述的数字当证据」，**不留痕正好让这条红线无从判起**。

处置：**这一格我不修，但把它写成一条必须一起做的要求**（指南 §3 反例 ②）——

> 加第一个「真有人填」的 `metrics` 时，必须同时加一个真正存下它的地方：
> 要么给 `evidence_bundles` 加列，要么把指标写进某个受 sha256 对账的制品文件里并进 `artifacts`。

为什么不现在自己修（三句真话）：
① 加列是 schema 变更，而 `evidence_bundles` 的列是规格附录 C 逐字机械取来的（0004 那篇的口径），
动它等于偏离机械取值，那要在迁移文件头写清并给出依据，不是一行 `ALTER`；
② 选「加列」还是「塞进受对账的制品」**取决于指标由谁产出**（harness 直接写制品 vs 组装时算），
而那件事属 §14.4 那一条还没拍板的边界；
③ 定指标词表会踩到 0008 §7 —— 词表与验收标准是同一件事的两半，我不代笔。
**所以这一格留给「第一次真要填指标」的那个人**，并且我把它写在指南最显眼的那条反例里而不是 §6 的缺口清单里，
因为它必须在**写标准的那一刻**被读到。

## 5. 我自己在这次任务里写错的（按被抓的顺序）

1. **`im_binds` / `im_bindings`**（0002 §7 记的就是这条，同一轮）—— 从一行注释的语义反推出表名。
2. **「`honesty_boundaries` 会进 prompt」**（§2 末）—— 从一个必填字段的语义编出它的去向。
3. **「类型这一维没在判」**（§3 第 2 条）—— 抄自家文档，抄丢了限定语。
4. **「`graph_version` 那一格还漏着」**（§3 第 3 条）—— 引用旧决策记录而没重测。
5. **`role_id` 有 `^[a-z0-9_-]+$` 形状约束** —— 我在 delegation 指南里写下了这条正则。
   它**根本不存在**：`role_id` 在 schema 里只是 `z.string().min(1)`，
   全仓 `grep 'a-z0-9'` 只命中扩展名清洗、`METRIC_CONDITION`、迁移文件名三处。
   写它的原因很典型：**别的 schema 字段都有 `.regex(...)`，我按「这里也该有」补了一条**。
   改完之后指南里那段变成「形状上没有任何约束，所以 `Dev` 与 `dev` 都是合法值而委派边只指得到其中一个」，
   那才是有用的那句 —— 而它比一条假正则更值得写下来。
6. **`loadPresetRoles()`「只用于 `--dry-run` 那种展示路径」** —— 我猜的。
   实测它在 `withHub` 里被喂给 `buildCompanyGraph`，是 `hub run` / `hub resume` 真的在用的那份角色表。
   这条改完之后才看清真实形状：**跑图的档位读 YAML，门控要读的标准读 `role_charters`（实测 0 行）**，
   两个源按用途分裂。前一句写成那样会让下一个人以为预设角色表是装饰品。
7. **`dev_to_test` 那条我差点在 §6 里写成「再加一层类型校验就能修」** —— 自己在同一段里把它否掉了
   （那只会让 agent 改填 `test_report`）。留着这句是因为它是**我第三错的第二半**：
   错完之后我立刻生成了一个错误的修法，而修法比错更接近会被写进代码的东西。

**这七条的共同点**：没有一条是「不知道」，全部是**从语义、从惯例、从自家文档的措辞推出来一个事实**，
而每一次手边都有工具能在一条命令内否掉它。0019 §5 第 13 条记过同一句，这是它第 N 次现形，
而且这次出现在一篇**主题是「哪些说法有证据」**的文档的写作过程里。
本篇因此给自己定一条：`grep` 一次就能定的事实（有没有某个字段、有没有某个调用点、有没有某列）
**属于必须现查的一类**，不允许凭「这块我写过」引用。
