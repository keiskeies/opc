### 2b. 为什么测试套件看不见（这不是 bug，是**一条写下来的取舍**的必然后果）

`test/arch/gate-selfcheck.test.ts` 是那份脚本唯一的守卫，六例全绿。它文件头第 4-6 行
**明写**了它不判什么：

> 钉的【不是】门禁此刻是绿的 —— 那是随仓库内容翻转的实时状态，写死它等于往
> 测试里埋一个【现在恰好为真】的断言：哪天门禁真被标记通过，它就以一个不相干
> 的理由变红。永远吵闹的门禁比不装门禁更糟，这条取舍见 0007 §4.1。

它钉的是**记账契约**：退出码 ⇔ 汇总里那个数字、每条打印的 `★FAIL` 都在失败清单里、
仓库外跑必须非零。**这四条在门禁红着的时候全部成立** —— 我实测过（§9 第 ② 条）：
往 INDEX 注入一行含「本轮」，脚本 `★FAIL` + 退出码 1，
而 `gate-selfcheck.test.ts` **6 例全绿**。

所以这条失效链条是完整的、而且每一环都合规：
脚本正确报红 → 守卫正确验证「红被正确记账」→ 测试全绿 → **没有任何人会看到那行红**
（因为没人手动跑它，而它不在测试里）。

那个「不写死现在为真」的取舍本身我仍然认（0007 §4.1 那本账我付过）。
但它漏掉了一种情形，本轮实测到才算数：**当门禁的检查对象是我每天在写的文档时，
「红」是默认态而不是例外态** —— 于是「不钉绿」等价于「这条检查事实上不存在」。

### 2c. 处置：两件事，都不是「把测试改成断言绿」

1. **清掉那 6 处**（已经做了，本轮随本篇提交）。改法不是删词，是**换成数得出来的东西**：
   `本轮最重要的一条` → `Task 3.4 那一篇最重要的一条`、
   `本轮把库内通道做出来了` → `Task 3.6 把库内通道做出来了`。
   任务号在仓库里可 grep、可核对；「本轮」在仓库里**数不出来**（这正是 C7 立这条的理由，
   而我自己六次没照做）。
2. **补一条守卫**（`test/arch/gate-selfcheck.test.ts`）：门禁的**不符项集合**必须
   ⊆ 一份**点名的已知红名单**。今天那份名单是空的（清完之后确实零项），
   但它与「断言恒绿」的**区别在失败时的指令**：红的时候它说「要么修掉，要么把这一项
   **带理由地**加进名单」—— 也就是把「让门禁永久红着」变成一个**要签字的动作**，
   而不是一个沉默的状态。这与 `test-inventory.ts` 那份「唯一带跳过的文件名单」、
   以及红名单基线是同一个惯例，不是我新发明的口径。

   名单为空时它与 `expect(零项)` 在**结果**上等价 —— 我不假装它此刻多做了一件事。
   它多出来的是**下一次的红怎么说**：「已知红名单里没有这一项，请修或登记」，
   而不是「门禁红了，可能是环境问题吧」。

**为什么不顺手把其余 13 篇决策文档里那 353 行也清掉**：脚本自己就写了不判它失败的理由
（那些是失误记录正文，「本轮」在那里是作者的第一人称时间锚点，批量重写等于替 CEO 决定

## 4. 门控说 escalate，升级路由说不用升 —— 两半没接上

CEO 在岗位书里写一条 `action: "escalate"` 的标准（charter 的验收动作枚举允许），
意思是「这条不达标时别直接拒，交给 CEO 判」。实测两侧（`phase3.test.ts` ③ 段钉住）：

```
evaluateGate                    → { decision: "escalate",
                                    reason: "覆盖率不足，需 CEO 判（升级目标 ceo）",
                                    unresolved: [] }        ← 空
decideEscalation({…, unresolvedCriteriaCount: 0}) → { escalate: false }
```

**门控那个 escalate 结论不在升级路由的输入里。** `EscalationState` 十格里没有任何一格
能表达「门控刚说要看一下」：`reasons()` 只看 `reviewRoundNo` / `riskTier` / 预算两格 /
`outsideDecisionScope` / `unresolvedCriteriaCount` / `confidence`。

我一开始以为那条通道是 `state`（传个 `IN_REVIEW` 进去应该就是「审阅中需升级」）——
**实测否证**：`state` 那一格根本不参与判定，只被拼进卡片摘要
（`impact_scope: "任务 T-1，状态 IN_REVIEW"`）。
**我以为的接缝是装饰。** 记它是因为这种错法下次还会犯：接口上有一个名字恰好像答案的字段，
比接口上缺一格更容易骗人 —— 缺一格会让人去加，有一格会让人以为已经通了。

`unresolvedCriteriaCount` 那一维是【按客观标准判不出】，
而 `escalate` 是【判出了、且要求人判】—— 两件事共用不了一个数。

这与 `phase1-gates.test.ts` 文件头记的那次事故是**同一族的镜像**：
那次是「门控 pass + 升级条件看 unresolved」⇒ 两条验收同时失效；
这次是「门控 escalate + 升级条件只看 unresolved」⇒ 一条 CEO 亲手写的标准被静默降级。
两次都是**两个模块各自全绿**。

**不算生产 bug**：`evaluateGate` 零调用方（§1 第 1 条），所以今天没有真链路在丢 escalate。
它算的是**接线那天一定会踩的坑**，而踩到的方式是「全绿」。两条修法：

- **α** 编排层自己分叉：`gate.decision === "escalate"` 直接升，不看 unresolved。
  代价：「要不要升」变成两处判据。
- **β** 给 `EscalationState` 加一格（`gateDecision`），让路由仍是唯一决策点。
  代价：改一个被六处测试引用的接口。

**我倾向 β**，理由与 0016 §5 那条「严格度序只有一处定义」同一条：α 把同一个判断放进两处，
而这两处的**输入不同**（一个看 decision，一个看十格事实），将来必然给出两个答案 ——
那正是 phase1 文件头记的那次事故的成因，而那次是两个模块**已经**各判各的。
但这一条属于接线设计，等真图接起来时定更省（现在定等于在桩上定契约，同 0016 §8 第 1 项
那个「α 该等真模型接入之后」的立场），所以登记而不现在动。

## 5. 与 `charter/store.test.ts` 那一节的分工（不写重复劳动，也说清差在哪一格）

那一节（store.test.ts ③）已经证过「改 `acceptance_criteria` ⇒ `evaluateGate` 结论翻转」。
我一开始以为这条验收已经有人做完了，去读它才发现差**一格具体的东西**：
它的产出包是手搓字面量，`integrityOk` 传的是**字面量 `true`**。

这在单元测试尺度上没问题（它判的是「criteria 从哪来」这一维，文件头也写明了），
但在**验收**尺度上，`integrityOk: true` 是调用方给的一个值 ——
于是「按新标准变」这句话可能是在一份**根本对不上账的产出**上成立的。
phase1 那一轮已经为这个形状付过账（它有一条专门用真 `store.verify().ok`）。

所以 ① 段真正新增的不是「又测一遍翻转」，是这三件事：

1. **完整性是算出来的**（`store.verify(bundle).ok` 传进 `evaluateGate`），
   并且**先断言它为 true** —— 地基不成立时上面所有 pass/reject 都不算数；
2. **制品真落盘**、`sha256`/`bytes` 取自写入结果。这挡的是「哈希写 64 个 a」那种
   **永远 reject** 的夹具：那种夹具下「改标准 ⇒ 结论翻转」也成立（一直 reject 到一直 reject），
   用例照绿；
3. 反向对照补齐：达标产出又 pass、**旧版本岗位书**（回放语义）仍 pass、
   而且 `gateCriteriaForRoleAtVersion(…,1)` 与 `gateCriteriaForRole(…)` 返回的 condition
   **确实不同** —— 少了最后一发，「两个函数返回同一个数组」的坏实现能让整段绿。

另外补了一发排除法：同一 criteria 下换**产出**也会换结论（90→reject、99→pass），
以及「metrics 里根本没这个指标」⇒ escalate 而不是 pass。
少了「换产出也变」这一支，「换 criteria 变结论」就不是唯一解释，整段 ① 可能在证另一件事。
