## 0. 这一篇补的是什么，以及为什么它排在 0043 后面

`INSERT_TASK_SQL`（`http/real-deps.ts:531`）建出来的每一条任务**一落地就是 `CHARTER_PENDING`**。
那一格是**人类席位**：dispatch 见它连 token 都不烧，直接回「等人不等 agent」。
而人要点的是**一张卡**，全仓只有 `engine/charter.ts` 建这种卡，而它当时只有一个调用方
（`hub work`），而那条路要 tsx + `@langchain/langgraph`，两样在本机都装不上（0039 量的那半）。

于是改前的真实表现是一条完整的死路：`POST /tasks` 下发一个想法 ⇒ 任务建出来 ⇒
收件箱**空的** ⇒ 永久停住。0043 让「点批准」真的能推进状态，而**没有任何一条路径会把那张卡建出来**。

改后（`--charter-pump` 打开时）：

| | 改前 | 改后 |
|---|---|---|
| 卡从哪来 | 只有 `pnpm hub:engine`（本机跑不起来） | 常驻 Hub 每个心跳自己补，经 `ensureCharterCard` |
| CEO 看到的第一格 | 空收件箱 | 一张待批章程卡（等批） |
| 起草失败 | 无重试方，静默 | 逐轮留痕、数得出第几次、到上限**响亮地**放弃 |

泵住在 `serve/` 而不是 `engine/`：「什么时候再试一次」是**常驻进程的节奏**，不是**引擎的能力**。
反过来放会让 `engine/` 认识 Scheduler —— 它今天能在 CLI 里单发跑完靠的就是它不认识任何东西。
与 `patrol.ts` 那句「故意不 setInterval，tick 由调用方驱动」同一个形状：`pumpCharterCards` 也叫一次动一次。

## 1. ⭐ 有界性住在审计里，而它的前提是「零花费的失败也算一次尝试」

一个会花钱的重试循环必须有界。有界要数得出「这是第几次」，两种数法：

1. `tasks` 上加一列 `charter_attempts` —— 要一条新迁移，而且那一列与 `events` 是**同一个事实的两个来源**
   （`events` 里本来就有那一轮），也就是 0041 §2「同一个数在两张表上给出两个答案」的新实例。
2. 数 `events` 里这一格试过的次数 —— 现成的，而且**已经有索引**。

选 2。它成立的前提是「`CHARTER_PENDING` 上的 `RoleTurnReported` 只可能是章程起草轮」。
这一条是**查过的**而不是推测：`grep -c 'to: "CHARTER_PENDING"' engine/dispatch.ts` = 0，
也就是说没有任何一条合法边能把任务送回这一格。
⚠ 这条判据断掉时**不会有人发现**，所以 `test/engine/dispatch.test.ts` 里有一发表扫描专门盯着它。

选 2 之后，本篇最重的一条依赖浮出来：**零花费的失败必须也写一行审计**。
本机最可能的失败恰恰是零花费那一支 —— claude 装不上 / spawn ENOENT ⇒ `costCents = 0`。
而 `charter.ts` 旧形状把那一种失败写成 `events` **零行**（0043 §10 实测）。
于是「第几次」永远数出 0 ⇒ 上限永不生效 ⇒ 每个心跳重新起一次子进程，**无限、静默、每次都不花钱所以也不产生账单**。

最后那半句是这一格最容易被轻视的地方：一个**不花钱**的无限循环看起来无害，
而它实际是每 60 秒起一个注定失败的子进程、写零行、留下零条线索。
**它坏了的时候本篇不会红** —— 它只会变成一个花不出钱也停不下来的循环。
这就是为什么这条依赖同时写在 `charter-pump.ts` 文件头与 0043 §10 两处，
而**不是**只写在一处：两处各有一个读的人会读到，而这条依赖坏掉时没有任何测试会响（除 0043 §10 那一发）。

## 2. 候选判据的形状必须与 DDL 的约束同一个形状

`CHARTER_CANDIDATES_SQL` 三个条件各挡一种浪费，其中第二个（`NOT EXISTS` 章程卡）
是本文件最容易被"改严"改坏的一处。判据是**这张卡存不存在**，而**不是**「这张卡是不是待批」：

```sql
CREATE UNIQUE INDEX idx_approvals_card_identity
  ON approvals(task_id, card_key) WHERE card_key IS NOT NULL;   -- 迁移 0004，不带 status 条件
```

一个任务在同一个 `card_key` 上**一辈子只能有一行**，批掉、退回、defer 都不放行第二行。于是
「卡已决定而任务仍在 `CHARTER_PENDING`」这种状态下：

- 按 `status='pending'` 筛 ⇒ 它进候选 ⇒ `ensureCharterCard` 那道前置检查（**也只查 pending**）放行
  ⇒ **起子进程、烧一轮 token** ⇒ `insertCard` 撞唯一索引 ⇒ `already_pending`。
  烧掉的钱换回一句"已经有了"。
- 按**任何状态**筛 ⇒ 根本不进候选，一分钱不烧。

两种写法在**第一次建卡之前**行为完全相同，只在退回/批准之后分岔 —— 而那正是唯一会花钱的那一段。
**判据必须与 DDL 的约束同一个形状**，而不是与"我以为的业务语义"同一个形状。
（`0026 §0` 立这条索引时用的正是同一条理由：判据落在 DDL 上之后它是一条**性质**，不是一条**约定**。）

同一族的第二条在**候选 SQL 里那道 `attempts < 上限`**：它不能指望「判放弃那个循环里的同一道判断」替代 ——
那道判断跑在 `ensureCharterCard` **之后**，只能阻止下一轮，而候选里这一道阻止的是**本轮那一次真金白银的 spawn**。
删掉它的表现是"上限多花一次钱才生效"，所以有一发用例直接数 spawn 次数。

## 3. 计数为什么复用 `patrol.ts` 的 `kindOf`

`CHARTER_ATTEMPTS_SQL` 里那个 `kind` 表达式用的是 `patrol.ts` 的 `kindOf` —— **不是顺手复用，是必须复用**：
`idx_events_task_kind_created` 是**表达式索引**（0003 §6），它匹配的是解析后的字面写法，两侧一漂索引就
**静默失效**（不报错、不变红，只是每轮多一次 `events` 全表扫）。
`patrol.test.ts` 里已经有一条在拿 `kindOf` 与 DDL 逐字比对；在这里另抄一份就是造出第二个抄本
（0006 §7 那族），而抄本漂了不会有第三条用例发现。

索引**真被用上**这件事由 `test/serve/charter-pump.test.ts` 里那发 `EXPLAIN QUERY PLAN` 判，
并配一发反向对照（**真把索引 DROP 掉** ⇒ 计划里那个名字消失）—— 注释会漂，计划不会，
而"计划里有名字"这一发如果没有反向对照，与恒绿装饰不可区分。

## 4. 泵挂在心跳上的形状：非阻塞派发

心跳一轮做的是巡检 + 备份相位；起草一轮要起子进程，上限 **180 秒**
（`engine/claude.ts:85` 那个 `i.timeoutMs ?? 180_000` 到点 `SIGKILL`），
而心跳下界是 **60 秒**（`HEARTBEAT_FLOOR_MS`）。**起草比心跳的节奏慢三倍**，这是设计事实不是意外。

所以泵在 `job` 里是**派发**而不是 `await`（`serve/assemble.ts` 里 `pumpWatch.start(...)`）。
如果 await 它：一轮起草期间心跳不结束 ⇒ 下一轮起跳时 `inFlight` 还在 ⇒
`serve/timer.ts:336` 那个 `skipped++` 分支被走到，**巡检与备份被起草牵连**。
一条章程提案起草不动，不该让停滞检测从此不再运行。

⚠ 我此前把那个分支记成「**静默**跳过」，那是错的，写这篇时读了 `timer.ts` 才发现：
它会 `o.onError?.(...)`，在 assemble 那边接到的是 `io.warn("心跳：上一轮心跳还没结束…")`。
它**不**动的只是 `consecutiveFailures` 与 `onFatal`。
所以 assemble 里那句「本轮跳过章程起草：上一轮起草还在飞」**不是**"从沉默变成有声"，
而是**把主语说对**：通用那句把原因归给"心跳"，而真相是"起草"，
一个人照着"心跳慢"去查会去查 SQL，而该查的是那个子进程。

同一条不牵连还有一处：**单张卡抛错不整轮抛**。抛到 ticker 那一层会变成"心跳失败计数 +1"，
而连番失败之后停掉的是**整条心跳**。所以 `pumpCharterCards` 逐张卡 try/catch，
抛的那一张记成 `attempted` 并把原文带在 `note` 里，由 `io` 那一层说出来。

关机那一侧对称地等：`giveUpGuard` 里两道 `beginCancel()` 都在**任何 await 之前**，
然后 `await backupWatch.settle()` → 若起草还在飞就 `io.warn` 一句「等它落地再关队列」→ `await pumpWatch.settle()` →
才关服务、关队列。最坏等 180 秒。代价写在启动横幅上（`Ctrl-C` 那句），因为**该被知道的是代价而不是机制**：
一个人按 Ctrl-C 看到进程三秒没退，第一反应是 `kill -9`，而那会正踩在"事务写一半"上。

## 5. 上限与开关：一份写了就必须生效的配置

沿用 `--bind` 那条立场而理由更硬：**`--charter-pump` 刻意没有 env 缺省源**。
`--bind` 打开的是对外暴露，这一格打开的是**每隔一个心跳自己起一个 claude 子进程花钱**。
一个从 shell profile / compose 文件 / CI 变量里继承来的开关，等于让这台机器在没有任何人决定的情况下
持续产生 token 账单 —— 而账单是**事后才知道的**，那时"我当时看见过这个参数"那条防线已经不在了。

参数层两头都判（`config.ts` 那两段，测试 39 发全绿）：

- 开了泵而少任一个同伴（`--max-budget-usd` / `--task-limit-cents` / `--agent-cwd`）⇒ USAGE，点名**缺的那一件**。
  不在 `makeRuntime` 才炸：那时 Hub 已在监听、心跳已在跑，一个人会以为"Hub 起来了而泵没起来"，
  实际可能是**泵在跑而没有上限**。参数层这一发是**一分钱都没花**的那一次红。
- **反向**：给了预算而没给开关 ⇒ 也 USAGE。它防一个人写了 `--agent-cwd` 与预算而漏了 `--charter-pump`，
  Hub 照常起来而他**以为自己把泵开了** —— 那与"从没打算开"在症状上一模一样（收件箱一直是空的），
  唯一排查方向是去读自己那条命令行。

`--max-budget-usd` 收小数（`0.5` 是最常见写法，整数判据会拒一个正确用法），
但拒 `NaN` / 负数 / `1e400`：`Infinity` 传到底下就是一个**没有上限的上限**，
而那条参数存在的全部理由就是上限。

`--agent-cwd` 指向不存在的目录 ⇒ **警告而不停**。这一格我在两个做法里选了警告，理由写在 `assemble.ts`：
真那条路会**自己收敛**（ENOENT ⇒ 一轮失败留痕 ⇒ 计一次尝试 ⇒ 三次之后 `CharterDraftAbandoned`），
而且留下的信息比一次拒启动**更多**（拒启动只说"目录不在"，收敛那条路会说"三次都失败，原文如下"）。

## 6. 放弃那一行：一条纯审计行，以及我写错的那一版

到上限 ⇒ 留一行 `payload.kind = "CharterDraftAbandoned"`，纯审计行，形状照
`charter/store.ts` 与 `org/commit.ts` 那两处先例。三条判定：

- **不新开 `DomainEvent` 的 kind ⇒ 不广播。** 加 kind 要么改 contracts（跨包、web 投影要接），
  要么 cast 一个联合外的值。而后者走不通的理由**我原来写错了**，留在这里（下面那条撤回）。
- **⚠ 撤回：我原来写的理由是假的。** 我写的是「`overview/today.ts:41` 把'payload 解不出 kind 的行'判为脏数据，
  前端解不出来会标 stale，等于制造一个脏流」。写这篇时逐处重读，三件事都不符：
  两处坐标指错（`overview/today.ts:41` 是一句 import 注释，脏数据探针实际在 `MALFORMED_PROBE_SQL`；
  `http/sse.ts:48` 讲的是 seq 去重，不是帧形状），而**结论方向是反的**：
  `contracts/api.ts` 的 `feedItemSchema` 里 `kind` 是 `z.string().min(1)` 且 schema 是 `.passthrough()`
  ⇒ 联合外的 kind **通得过**校验；web 投影的 switch 未命中落 `default` 那一支，注释明写
  「其余事件类型【不改 tasks】，只推进 cursor」。
  ⇒ 真后果不是脏流，是**一条被客户端静默丢弃的帧**：库里有、SSE 发了、界面什么都不变。
  **这比脏流更糟** —— 脏流会报错，这一种从头到尾没有任何一处不响，
  正是 `projection.ts` 文件头自己立的那条立场要防的"无人知晓的洞"
  （它写「宁可让界面停在上一帧并报一次错，也不要静默跳过」，
  而那条立场只覆盖 **schema 解不过**那一支；我这个 kind 恰好**解得过**，
  于是从"会被响亮拒绝"掉进"被那条立场保护不到的缝"）。
  所以"发出去了"与"有人收到了"是两件事。这条已同步改进源码注释与那发测试的注释，
  那发断言本身（总线上不该有这一行）**一直有效**，与理由对错无关。
- **不写状态跃迁。** 我初版写的是 `TaskStateChanged{from:"CHARTER_PENDING", to:"CHARTER_PENDING"}`，
  而那是错的，且错得隐蔽：web 的投影按事件**应用跃迁**，一条自指的跃迁是**一次真的状态变更**被凭空造出来，
  而 `events` 是 append-only（0014 §3），**这条假跃迁删不掉**。「泵放弃了」不是一次任务状态变更：
  任务哪儿也没去。
- **`action` 复用 `'state_change'`**（`AUDIT_ACTIONS` 是 §22.1 那十值枚举，加第 11 个值属改规格）。
  ⚠ 于是按 `action='state_change'` 数跃迁的读法会多数到这一行，挡住它的是 `payload.kind` 这一维。
  顺带一条依赖：`MEMORY_ROWS_SQL` 只捞 `('approval','review_decision')`，所以这一行**不进任何角色的 few-shot**。

**判放弃跑在本轮之后**，理由值得单独留：候选 SQL 里的 `attempts` 是**本轮之前**的数字，
本轮这一发可能刚好用完最后一次；下一轮它就不再是候选（SQL 滤掉），
所以**这是它最后一次能被看见** —— 不在这里留一行，它就从"每轮都在报的故障"变成"谁都不知道的沉默"，
而这两种状态之间没有任何东西会响（0016 §1 那一族）。

`CharterDraftAbandoned` 本身**不计入尝试**（否则上限自己数自己，而错的方向是"更早放弃"，最难往回查），
而且**只留一行**（后续轮次不重复写）。

## 7. 还了 phase3 第 6 条一笔账，顺带又抓出一个「绿着改写口径」

改完之后 `packages/hub/test/acceptance/phase3.test.ts` 那份 blocker 清单第 6 条的**前提**变了，
而**没有任何一条断言为那次改变变红**。它是本仓记了五次的那一族第六次：
INSERT / UPDATE 两份全等名单都没动（泵经 `ensureCharterCard → insertCard`，INSERT 语句仍然只在 `cards.ts` 一处），
于是那条"serve/ 与 http/ 里一行都不建卡"的字符串继续绿着，而它已经不真。

这一版把**口径本身**钉成两条**有分母**的断言：

```
callersOf("ensureCharterCard", "engine/charter.ts")  = [engine/work.ts, serve/charter-pump.ts]
callersOf("pumpCharterCards",  "serve/charter-pump.ts") = [serve/assemble.ts]
```

钉**调用方名单**而不是钉 `grep "engine/"`：后者命中的是 import 语句，
而"有一句 import"与"这条链真能走到建卡"是两件事（`real-deps.ts` 顶层那句 `import { approveCard }` 早就在那儿了，
它不建卡）。`ensureCharterCard` 是 `engine/` 里唯一建章程卡的入口，它的调用方名单**就是**那条间接路本身。

⚠ 两条新断言各只判一维，而**这是变异实验量出来的、不是推理出来的**（见 §8 那张表）：
把 assemble 里那一整块派发**删掉**，**两条都照样绿**（`pumpCharterCards(` 这个字样还活在
`pumpVia` 的默认 lambda 里，`ensureCharterCard(` 也还在 `charter-pump.ts` 里），
真正变红的是 `assemble-pump.test.ts`。
所以对得上第一发口径的是反向那一发（往 `http/real-deps.ts` 加一句 `ensureCharterCard()` ⇒ 红）。
**我一度给第二发写的注释是"证明泵真被心跳驱动"，被自己的变异实验证伪，已按实测改掉** ——
一句被证伪而没改的注释比没有注释更贵。

第 6 条**没有被关掉**，只是换了形状：原来缺「链路」，现在缺「有人把这个花钱的开关打开」。
默认不开是刻意的（0041 §8），所以默认配置下的结论与第一版那天**一样**：收件箱是空的。
这句话现在写在 blocker 字符串里而不是只写在我这份文档里 —— 只有前者会在有人改动时被看到。

## 8. 判别力：11 发变异，以及两发差点骗过我的无效变异

`assemble-pump.test.ts` 15 发 / `charter-pump.test.ts` 28 发 / `config.test.ts` 39 发。
（`charter-pump.test.ts` 后来补了 H 组，现在是 **31 发**；28 这个数是这张表**当时**的分母，
不改回去是因为那张表的结论是按那个分母量的 —— 见 §9.2 第 1 条。）
对 `assemble.ts` 的接线跑了 11 发变异（W1–W11），逐发**先验证变异本身有效**再下结论：

| 变异 | 结果 |
|---|---|
| W1 派发挪到 `if (backupDir === undefined) return` **之后** | 红（不备份 ⇒ 泵从不跑） |
| W2 把派发改成 `await`（阻塞心跳） | **第一版无效**，重做后红 3 发 |
| W3 去掉 `pumpWatch.beginCancel()` | 红（关机不等起草） |
| W4 让 `nowMs` 用启动那一刻的常量 | **第一版无效**，改 `Omit<…,"nowMs">` 后红 3 发 |
| W5–W9 各类判据反向（默认开泵 / 上限缺失不判 / 放弃不写行 …） | 各红 |
| W10 到上限那一轮不 `io.warn` | **红 → 补了一发新断言** |
| W11 界面横幅不区分泵开没开 | 红 |

两发无效变异差点把脚手架缺陷登记成产品缺陷：

- **W2 第一版**锚在 `if (backupDir === undefined) return;` 上"插入"了代码，而**块本身没移动** ——
  插进去的是死代码。一个"打不红"的结论**必须先排除变异本身无效**。
- **W4 第一版**是**新增**一处 `pumpWatch.beginCancel()`，而原来那一处仍在 await 之前 ——
  「存在一处在 await 之前」这个判据**仍然为真**。修法是判据改成"每一处都在 await 之前"，
  并配一发真变异的反向对照（第一版那个反向对照写成 `expect(136).toBeLessThan(136)` 才暴露它自己就是假的）。

W10 是这批里唯一的**真缺口**：到上限那一轮库里写了 `CharterDraftAbandoned`，而 `io` 一声不响。
一条"系统不再自己解决"的事实只在库里而不在终端上，等于只有 grep 得动它的人才知道。
补的断言判的是**那句 warn 本身**与**恰好一行审计**两件事。

⚠ **而"W1–W11 打的是接线"这句话的射程要说清**：那 11 发全部打在 `assemble.ts` 上，
`charter-pump.ts` 里 `engineOf` 的**默认那一支**当时**一发都没被覆盖**（P1/P2 两发变异全绿）。
补的那三发（P1 bin 透传 / P2 默认那一支的 recordTurn / P4 子进程 cwd）与整段经过在 **§9.2 第 1 条**，
那里同时记了**第三条 P3 是等价变异**（候选为空那道早退删掉不红）——
一张变异表如果只记"红了所以有判据"，就会让人以为表上没写的都安全。

另一条方法论收获：`createFakeScheduler().advance()` **同步**跑完回调链，
所以我在测试里手动 `tick()` 一次就造出一个自找的 `skipped`。红的是夹具而不是产品，
而**夹具造成的红最容易诱导出最坏的修法**（放宽那条断言）。同理，
「等一个由被测代码决定何时发生的信号，永远优于等一个我觉得它该发生的信号」。

## 9. 需要 CEO 拍的一项，以及本篇没做的其余各格

### 9.1 ⭐ 被退回的那份章程从此【没有去处】

CEO 用 `reject_with_comment` 退回一份章程提案之后：

1. 任务仍停在 `CHARTER_PENDING`（`HUMAN_EDGES` 里只有 `approve` 有出边，0043 §6）；
2. 而那张卡所在的 `(task_id, card_key)` 上**永远不能再有第二行**（§2 那条索引不看 status）；
3. ⇒ 泵**不可能**重新起草第二份，而 [规格] §7.1 那边也**没有** reject 的出边。

一条退回的意见从此**没有去处**：CEO 说了"不行，改成这样"，而系统对这句话的全部回应是沉默。
正确的解法是 **`card_key` 带轮次** + **补一条回到起草的边** 两件事一起做，
不是本篇能顺手补的一格（顺手补其中一件会得到"能重起草而状态仍不合法"或"边合法而建不出卡"）。

本篇能做的是**把它钉成现状而不是假装补上**：`charter-pump.test.ts` B 组那一发
「卡被**退回**也一样不起子进程」判的就是这个缺口存在；补它的那天那一发会红，逼改的人看见自己在改什么。

**等 CEO 的一句话**：退回之后应该发生什么。三个候选，各有代价 ——
**(A)** `card_key` 带轮次（`charter:proposal:r2`）+ 补 `reject → CHARTER_PENDING` 自环边 ⇒ 角色按意见重起草，
代价是审批历史里同一格会出现多张卡（回放与"等了多久"那两格的口径要一起改）；
**(B)** reject 直接把任务打回一个"等 CEO 重写想法"的状态 ⇒ 不猜角色能不能改好，代价是把话退回给 CEO；
**(C)** 维持现状（意见只进审计）⇒ 零代价，代价是"一人公司"里 CEO 唯一那条**下行**反馈通道是断的。
我的倾向是 **A**，因为 (B) 把 CEO 变成瓶颈而他刚说过话，(C) 与产品初衷直接冲突。
但 (A) 要改 [规格] §7.1 的边集与 §22.3 那张标注表 —— **那属改规格，不属实现层**。
