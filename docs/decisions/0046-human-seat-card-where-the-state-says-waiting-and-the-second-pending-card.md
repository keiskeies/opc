# 0046 人席那一格的入口 —— 状态说「等人」而那个人手上没有按钮，以及补上之后冒出来的第二张卡

## 0. 一句话

引擎路线把任务**合法地**推到「等人」那一格，而**全仓没有任何东西能让那个人回应它**：
那一步只写状态边、不建卡片，而 CEO 推进任务的**唯一**入口是 `POST /approvals/:id/decide`，
那个 `id` 只能从一张**已经存在的卡片**拿到。补上之后又量到第二格：**一条任务上可以同时躺着两张待批卡，
而 `approveCard` 只判「这张卡属于这条任务吗」，不判它属于【哪一格】** ⇒ 点旧的那张，
任务按新问题动了，而真正在等的那张还躺着。

本篇的两格都不是设计缺口，是**同一件事的两半**：状态机与收件箱必须一起动，
少一半的那一侧每一层看起来都正常。

## 1. 起点是探针，不是设计（原话留在这里）

上一发（0045 花钱的门）交完之后我照本仓的老规矩问了一句「真跑一次会看见什么」，
而不是「代码读起来对不对」。探针内容：`IN_REVIEW` 上一个独立审阅通过的 `pass`，
角色在组织树顶层 —— 也就是【规格】§7.2 **步骤 8** 那一步（那一行界面表现写的正是
「审批收件箱出现**琥珀色**卡片」）。实测原话：

```
  status = ESCALATED_TO_CEO
  moved  = true
  卡片数 = 0
  审计   = ["state_change/TaskStateChanged"]
```

**审计齐、状态对、收件箱空。** 这一发的贵不贵不取决于它花了多少 token（它一个都没多烧），
取决于它**长得像成功**：回放查得到那一步、`GET /tasks` 显示任务在等人、日报数也数得到。
只有「那个等人的人」发现她**无从下手**。

顺带把 `approveCard` 那条路也读了（它把 `ESCALATED_TO_CEO → FINAL_REVIEW`，步骤 8→9）：
**同样**不建卡。于是症状有两个，第二个更隐蔽：

- 缺前一格的症状是「收件箱是空的」；
- 缺后一格的症状是「**我明明批过了，怎么还没交付**」—— 批一步之后停在 `FINAL_REVIEW`，
  而那一格同样只能靠一张卡推进，交付那一步（→ `DELIVERED`）永远发生不了。

**这一格把 0044 那格的缺口方向纠正了。** 0044 的结论是「卡片没有生产者」，
于是那一篇把章程泵接上、`ensureCharterCard` 真的开始建卡 —— 都对，但**那条缺口不在
「谁建卡」这一层**：`CHARTER_PENDING` 那一格从此有卡了（它本来就有 `charter.ts` 在建），
而任务**往前走到另外两个人席**时那一格仍然没有。所以 `phase3.test.ts` 里那条
「② 的卡片生产者」的 blocker 清单被改写了**第五次**，而这一版的改动是**加一条而不是消一条**：
「有生产者」与「到了等人那一格有入口」是两条缺口，前者由那条名单判，
后者由 `engine/seat-card.test.ts` 判。⚠ **这一格【不消掉】第 6 条 blocker**：
默认配置下（`--charter-pump` 不开）CEO 打开收件箱看到的仍然是空的。

## 2. 卡片身份 = 那一条状态边的 `events.id`

去重键是迁移 0004 那条 `UNIQUE(task_id, card_key) WHERE card_key IS NOT NULL`，而它**不看 status**。
所以键怎么起不是风格问题，三种候选里有两种是错的：

| 键里放什么 | 第二次升到 CEO 时会发生什么 |
| --- | --- |
| 什么都不放（只有状态名） | **撞键 ⇒ 不建卡 ⇒ 那一格又空了**，正是【规格】§8.3 允许的「同一任务多次升级」里那一次真需要人决定的到达 |
| 放时刻 | 同一秒内两次到达合成一张（同一轮里真可能写两条状态边，见下面 chain 那一段） |
| **放那一次到达本身的身份** = 落到人席那条状态边的 `events.id` | 一次到达一个键。全局唯一、单调、不需要另造计数器 |

`chain` 那一族（`EVIDENCE_SUBMITTED → IN_REVIEW` 那一格 hub 自动走）会在**同一轮**里写两条状态边，
所以「取哪一条边的 seq」也要判：取的是**最后那条**（`stateEventSeq` 在 chain 循环之后已经是最后一格那一条），
而**只有最后那条的落点才是人席** —— 中间那一格不是「等人」，是「等下一个人干活」。
测试里有一条专门钉这一发（`chain 的【中间那一格】不是人席 ⇒ 不补卡`）。

⚠ **这个键的代价写在测试里而不是藏起来**：卡片身份依赖 `events.id`，
所以【将来任何重写状态边的路径】都会造出**新的一格**而不是复用旧的。那**正是**我们要的行为
（每一次到达都值得一次独立的决定），但它意味着**「去重」挡不住「重复到达」** ——
挡住重复到达的是**状态机**（不在人席就不能再升一次）。谁哪天加了「重放上一轮」这类东西，
这一句就是它的第一条前置条件。

## 3. 哪些格子要卡：从 `HUMAN_EDGES` 派生，不手抄名单

`needsSeatCard` 的判据是 `HUMAN_EDGES` 的键 **减去** `CHARTER_PENDING`。两个选择都有代价，都值得记：

- **为什么不是 `seatOf`**：`seatOf` 问的是「有没有 **agent** 出边」，它会把 `APPROVED_UPWARD` /
  `BLOCKED` / `MEETING_REQUIRED` 也算成"人席"（它们**两张表里都没有**出边，是【规格】§7.1 的死路）。
  给一条死路建一张 `approve` 卡，等于**假装它有出路** —— CEO 点下去拿到的是「这一格没有出边」，
  而那张卡本来是她今天唯一的新消息。`seatOf` 的 fail-closed 方向（未知状态默认是人）在这里
  **恰好是错的**，因为这一发问的是「这一格有没有**人类**的出路」，不是「要不要让 agent 闭嘴」。
- **为什么不手抄一份名单**：手抄名单的**默认值**是「新加的人席静默地没有卡」；
  从边表派生的默认值是「新加的人席自动有一张卡」。这一族失效（判定写完、没人走到）在本仓抓过二十几篇，
  **默认值往哪边倒**就是它复发与否的分界。
- **`CHARTER_PENDING` 为什么排除**：那张卡的生产者是 `charter.ts` / 章程泵。
  在这里再建一张 = 同一格两张「批准章程」，**而重复比缺失更坏**：点了其中一张，
  另一张**永远点不动**（任务已经不在那一格了，见 §5 那条新判据）。

## 4. 「必须在调用方的事务里」从注释变成一次抛错

`mintSeatCard` 的入参是**一条 `DatabaseSync`**，而调用方手里**同时**有两条：
`requireScopeDb()` 给的**事务内那条**，和 `writeConnection()` 给的**队列那条**。
写错的**那一支不报错、不崩**，只是 autocommit —— 后果是卡片落库而状态边回滚：
收件箱里躺着一张**指向 agent 席位**的卡，CEO 点下去拿到「这一格没有出边」，全程零报错。

我第一版只在文件头**写了那句话**。本轮把它改成**当场判**（比对**对象同一性**，
不比对"在不在事务里" —— 后者答不了「写的是哪条连接」，同一进程里两条写连接各自都能有事务）。
`insertCard` 自己有 `requireScopeDb` 那道门，但它**只在 http 那条 `createCard` 路径上**经过，
`insertCard(db, …)` 收的是调用方给的那条连接，**它无从知道自己被写进了哪笔事务**。

于是这一发留下了本篇最该复用的一条结论：

> **一句「调用方必须 X」的注释，如果违反 X 的后果是「不报错且看起来正常」，那它就不是纪律而是许愿。**
> `cards.ts` 文件头早就写着同一句（「注释拦不住的东西，不要只用注释拦」），
> 而我在本篇第一版里**照着自己的注释写完了代码，没有回头判它**。

判据本身也要能被证明有效 —— 见 §9 的 **M6**：把守卫收窄成「只判有没有作用域」会红**一条**，
那条用例的名字就是「事务内但传的是【另一条连接】」。**没有那一条，M6 就是绿的**，
守卫就退化成一个只挡最笨的错的装饰。

## 5. ⭐ 补卡带来一个此前不存在的形状：一条任务上两张待批卡

补卡之前，一条任务上**只可能有一张** pending 卡（拦截卡那一族的键不含轮次，重复尝试撞键；
而人席根本没有卡）。补卡之后**两张是正常状态**。探针（dev 试一条越权边被拦下留下拦截卡，
任务随后合法升到 CEO 那一格）量到的原话：

```
第一发：moved=false 卡数=1
第二发：status=ESCALATED_TO_CEO 卡数=2
pending 卡 = 2 ["handoff-block:dev->dev / escalation","seat:ESCALATED_TO_CEO:4 / escalation"]
点【旧的那张】(handoff-block:dev->dev) ⇒ outcome=decided edgeExists=true
                                          ESCALATED_TO_CEO → FINAL_REVIEW
  任务现在 = FINAL_REVIEW
  剩下 pending = ["seat:ESCALATED_TO_CEO:4","seat:FINAL_REVIEW:7"]
```

也就是说 `approveCard` 那三道检查（卡片存在 / 属于这条任务 / 是 pending）
对「这张卡属于这条任务的**哪一格**」**一字未提**。后果不是「多点了一下」：

1. CEO 点的是「dev 想把活儿交给 dev，这一跳机器不认」，机器把任务从「等你裁决升级」
   推进到「进终审」—— **她回答的是 A 问题，任务按 B 问题动了**；
2. **那张真正在等的卡还躺着**，而**又多出一张**终审卡 ⇒ 收件箱待批数**不减反增**；
3. 审计里写着「CEO 批准了升级」，**而她没有批准过升级**（`events` 是 append-only，事后删不掉）。

修法判在**认领之前**（认领之后再判会留下一条「已决策而任务没动」的卡片 ——
那与这一格要防的症状**长得一样**，只是换了成因），判据是：

- 当前这一格**有**自己的入口卡 ⇒ 只有它能推进这一格；
- 当前这一格**没有**自己的卡 ⇒ **沿用旧行为**（谁都能推进）。

**⚠ 为什么是【优先】而不是【白名单】。** 更严的那种写法（「只有 `seat:<当前格>:*` 能推进当前格」）
读起来更干净，而它会**当场把存量任务变成永久批不动**：那些补卡之前落库的任务停在人席、
手上只有一张**别的来源**的卡，白名单等于对它们说「谁都不许推进」。
我不能为了判据整洁，造出一格「CEO 看着一张待批卡而**一个按钮都点不动**」——
那**正是本篇在修的那个症状的镜像**。测试里有一条专门跑这一发（`当前格【没有】自己的卡时不挡`），
它是那一格【不】被这一发顺手做掉的**证据**，不是运气。

**只在 `approve` 这一支判。** `reject_with_comment` / `defer_deep_review` 不推进任何状态，
挡掉它们会让 CEO **连「这条不是我此刻要答的」都表达不出来** —— 一张过期的拦截卡从此
既推不动也关不掉，永远挂在待批数里。所以过期卡**仍然可以打回**（测试钉着，并断待批数**减一**：
收件箱能**做减法**，才是「一人公司」看得懂的清单）。

**残余（写成残余，不写成已修完）**：`isSeatOwnCard` 认两种键 —— 补卡自己那套前缀，
以及 `charter.ts` 的 `CHARTER_CARD_KEY`（那一格的生产者是它，所以「它自己的入口卡」由它定义）。
**第三类人席入口卡今天不存在**（【规格】§7.3 异常卡、【规格】§7.4 预算卡都没有创建方，0044 §9 / 0041 §7 旁边），
它们一旦出现就要在这里加一格；**没加时的行为是「不挡」**，即退回今天这个已知缺口，
而不是把一个新生产者判死。

## 6. 本篇没做的（不写成「换种方式做到了」）

1. **`hub decide` 那条 CLI 只多印了一个 `cardKey`**，没有改成「自动挑当前格那张」。
   清单原来打印 `id（approvalType）`，而两张卡**同一个 approvalType**（都是 `escalation`），
   于是清单读起来是两条一模一样的 `escalation` + 两串 UUID，等于把「该办哪张」原样退还给看清单的人。
   现在带 `cardKey`。而 `stale_card` 那一句人话**会指名该点哪张**（`seat:ESCALATED_TO_CEO:…`）。
2. **http 那边这一发仍然被翻成 500。** `HubDeps.recordDecision` 返回 `boolean`，
   而 `approveCard` 今天有**七条** outcome；除了 `decided` / `already_decided`，
   剩下五条全走「抛 → app.ts 的 catch → 500 + 原文」。其中两条（打回没带理由、**点到过期卡片**）
   语义上是【调用方的请求不成立】，**更对的码是 422 / 409 而不是 500**。
   修它要把那个 `boolean` 换成一条**带成因**的结果，同时动 `app.ts`、桌面 IPC、和两边测试 ——
   **与补卡不是同一发**。现状的表现是「界面弹一句原文（原文自己说清了该点哪张）」，**不是静默**，
   所以它排在 §7 之后而不是之前。`real-deps.ts` 那段注释原来写着「六条 outcome」，
   已经跟着改成七条并把新那一格列进去 —— **注释里的计数也是会过期的断言**。
3. **常驻驱动器仍然没人调**：`advance()` 至今没有生产调用方，而【规格】§7.2 步骤 2–7 要求
   **CEO 什么都不做**。这一发只保证「走到人席时她看得见、点得动」，
   不保证「会自己走到人席」。**顺序是刻意的**：先建入口再建泵 ——
   先建泵只会更快把任务送进那一格（0045 §6 同一条判断）。
4. **`MEETING_REQUIRED` / `BLOCKED` 仍然是死路**（两张边表里都没有出边）。
   本篇**刻意不给它们建卡**（§3 那条），所以它们现在的表现是「任务停着、收件箱里没有东西」，
   与本篇之前**一字未变**。补它要【规格】§7.1 先给一条出边 —— 改规格不属实现层。
5. **`approveCard` 的 `orgVersionUnchecked` 照旧**（卡片是 v3 建的而任务在 v4 时批准照走，0041 §5）。
6. 存量那些停在人席而**没有**入口卡的任务，本篇**不回填**卡片。
   回填 = 给历史上每一次到达补写一条 `ApprovalRequired` 审计，而那件事**没发生过**；
   它们的出路是 §7 那一项。

## 7. 等 CEO 拍的一项：过期卡片留在收件箱里要不要紧

现在的事实：CEO 点一张**过期**的卡，系统**什么都不做**并告诉 she 该点哪张。
那张过期卡**仍然 pending**，会一直出现在待批数里，直到她**手动打回/暂缓**它。

三条路，各有代价 ——

- **(A) 维持现状**（过期卡留着，由她手动清；报错里指名该点哪张）。
  代价：收件箱里会攒「已经不是当前问题」的卡，**待批数这个数会变得不纯**（它把 A 格和 B 格的问题混在一起数）。
  好处：一次审计都不多写，且**她保留了对旧问题的最终处置权**（那条越权尝试要不要留档，是她的事）。
- **(B) 补一张新席卡时，把同任务上其他 pending 卡自动标 `deferred`。**
  代价**很重**：`deferred` 是一次**决策**，而**她没做过这个决定** —— 本仓在 `insertCard`
  与 `already_decided` 那两处守的就是这一条（「在 append-only 的历史里说这个人又决定了一次，而没发生」）。
  这一条**不是代价，是违规**，所以我没走它，写在这里是为了让你知道**为什么不选它**。
- **(C) 加第四颗按钮「知道了」（信息性关闭）。** 代价：`APPROVAL_BUTTONS` 明写**没有第四个按钮的位置**
  （一键全批会让【规格】§8.2 第 4 条被 UI 自己绕过），加一颗等于改那条产品口径；
  而且它会把【规格】§7.3/§7.4 那两张**信息性卡**的缺口一起勾出来 —— 那两格的卡片
  「没有按钮语义」正是同一件事的另一面（`cards.ts` 文件头第 1 条口径）。

**我的倾向是 (A) + 界面按格分组**（同一格的卡放一起，非当前格的标在下方），
理由：**(A) 是这三条里唯一不写假审计、不改契约的一条**，而「按格分组」是纯读侧改动
（`card_key` 里已经带着状态名，判据与 `isSeatOwnCard` **同一份**，不必再造第二个）。
但「收件箱该不该显示不欠决定的东西」是**你每天看的那个界面**的口径，归你拍 ——
而且它和**颜色纪律**（0042 §3.1：琥珀全局仅用于「需要 CEO 决策」）**撞在同一格**上：
非当前格的卡要不要标灰，是同一决定的下一行。

**另一条教训：我有一条用例是**运气绿**的，而它长得完全像真绿。**
`cardsIn()` 我第一版写的是 `ORDER BY id`，那条「第二次到达 ⇒ 两个键」的用例断的是
`["seat:ESCALATED_TO_CEO:1", "…:2"]` 这个**顺序** —— 而 `approvals.id` 是 `randomUUID()` 发的
TEXT 主键，`ORDER BY id` 排的是**字典序**，与插入顺序**无关**。单跑一次**恰好**是那个顺序（跑了 24 发全绿），
把 seat-card / dispatch / approve 三个文件**合跑**时它就翻红了。改成 `ORDER BY rowid`（插入顺序），
并把这件事写在 helper 的注释里。**同一件事在本篇出现了两次**：卡片键用 `events.id` 是对的（单调），
而卡片**主键**是 UUID（无序）—— **「id」这个词在同一张表上指两种完全不同的序**，
凡按它排序的地方都要问一句「排的是哪一种」。同一条也解释了 §5 为什么判据是**成员关系**
而不是「取最新那张」：`PENDING_CARDS_SQL` 那个 `ORDER BY created_at, id` 里
`created_at` 同一轮相同、`id` 是 UUID，**那个次序是随机的**，靠它挑一张会得到一条看起来确定、实际随机的判定。
