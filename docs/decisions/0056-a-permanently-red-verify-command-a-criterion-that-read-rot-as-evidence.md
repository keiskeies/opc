# 0056 一条恒红的验收命令、一个把腐烂读成摘要的判据，和两次「审计自己数错」

> 本轮的起点是审计台上一个 report-only 开放项：`docs/review/verify-open-invariants.mjs`
> （门禁要求 CEO/owner 亲自复跑的那条）。要给它补证据时先量到一件事 ——
> **它从来没绿过，也不可能绿**。重写之后又发现两件更该记的事：
> 我为了「让它能验摘要类引用」建的内容索引，恰好会把**改坏一位的真提交引用**
> 判成「已核验的内容摘要」；而 round255 那道专门核对哈希的审计，
> 把一串**真的 sha256**「修正」成了一串 **sha1**，标签还写着 sha256。

## 1. 一句话

| | 旧版（HEAD 里那份） | 本版 |
| --- | --- | --- |
| 在 HEAD 干净工作树上的退出码 | **1（恒红）** | **0** |
| 采集网眼 | 恰好 7 位小写 hex | 7 位及以上、不分大小写 |
| 覆盖到的真提交引用 | 91 个去重 | **100 个去重**（旧版**压根没看过**其中 **9** 个）¹ |
| 对「内容摘要」类引用 | 一律当腐烂 ⇒ **3 条误报** | 机械可验的验、不可验的**逐条豁免并写明理由** |
| 假绿防线 | 无 | 桶分项求和 == token 数、token 下限、索引自检、豁免表活性、**离真提交差一位必红**、探针 9/9 |

¹ 口径：当前工作树、按各版自己的采集网眼去重后现算。**这一格本轮从 97/6 变成 100/9**，
原因值得停一下：**多出来的那 3 个是本篇自己造的** —— §2② 那张表把三个 12 位前缀
（`0bebb09924f5` / `0dbc7a4364ed` / `ef9016923653`）**原样写进了正文**，于是它们成了被扫语料里的
独立 token，而它们**长度 > 7 ⇒ 旧网眼采不到**（旧版只采恰好 7 位）。
⇒ 这不是「新判据更强了」，是「**我写这篇文档这个动作改变了被测语料**」——
§3 第 1 条说的「这些数会随本篇自己被编辑而变」在这里以另一种方式兑现了：
那一条讲**数量**会漂，这一格讲的是**成员构成**也会漂，而后者更阴，因为它看起来像一次覆盖率的提升。

三条贯穿本轮的判断，都比上面那张表重要：

1. **一条恒不可能通过的验收命令 = 一条恒红的断言**（0007 §4.1 记的代价在这里第二次落地）。
2. **「解析得了」不等于「解析成我说的那种东西」** —— 哈希引用有三种身份（提交 / blob 对象 / 内容摘要），
   判据必须知道自己在问哪一种，否则会把腐烂读成证据。
3. **一次「全部核对通过」的审计，覆盖面由它认识几种东西决定**，而不是由它跑了多少文件决定。

## 2. 旧版三处错，逐条实测

复算口径：`cp` 一份 HEAD 版到 `docs/review/` 下就地跑（它按自身位置解析仓库根，
放到临时目录跑会因为找不到 `packages/hub` 而 ENOENT —— 我第一回就是这么误读的）。

### ① 判据问错了问题 ⇒ 3 条红全是误报

旧版对每个 token 只问一句 `git cat-file -e <h>^{commit}`。于是它把**内容摘要**当成**腐烂的提交引用**。
三条红各自到底是什么（全部重算）：

| 那格记的值（完整） | 是提交前缀？ | 真身 |
| --- | --- | --- |
| `03bf24d15241da01b40505d1d9bd4807a8a403a9e98205ade8fe59d4f17e40ec` | 否 | `sha256(git show HEAD:docs/decisions/0008-….md)` |
| `3e1b069891d4d2409001fd1abdaad38a0212e9878f40817acbf52917d6c210a2` | 否 | `sha256(git show HEAD:test/arch/config-match.test.ts)` |
| `8823b0a110ab0f3d2a986736c8431a1e3b359bc9` | 否 | `test/arch/config-match.test.ts` 的 **git blob sha1 对象 id** |

⚠ 本篇一律**写完整长度**而不是截断前缀，理由不是美观：`doc-coords` 守卫按「决策文档里
**恰好 7 位**的 hex ⇒ 断言这是一个提交」判红，而上面三个都是**截断成 7 位**才会看着像提交引用。
更深一层正是 §4 的主题 —— **一个 7 位前缀分不清自己指的是提交、blob 对象、还是内容摘要**，
而写全长就没有这个歧义（我第一版就是写了 7 位，被自家守卫抓住，见 §7 第 6 条）。

三者**从来不是提交** ⇒ 台账没写错，而旧版的汇总语「**台账需更新**」指向了错的对象。
**恒红的信号会让人学会跳过它** —— 这条命令挂在门禁里要求人复跑，而它每一次都红，
所以它既没守住任何东西，又训练所有人无视它。

### ② 网眼太窄，反而漏掉真引用

旧版只采**恰好 7 位小写**，再排除 `/^[0-9]{7}$/`。**6 个真提交引用从来没被看过**（逐个实测都是真提交）：

| 漏掉的引用 | 漏的原因 |
| --- | --- |
| `0575943` | 被那道**纯数字 filter** 吃掉（它恰好 7 位且全是数字） |
| `0bebb09924f5…` / `0dbc7a4364ed…` / `ef9016923653…` | 长度 > 7（旧版只采恰好 7 位） |
| `11cc7459d793` / `615d3d96` | 长度 > 7 |

⇒ 这是「**排除定义处的 filter 永不生效**」那一族（0053 §2）的又一实例：
一道为了「别把十进制常量当哈希」而写的 filter，顺手吃掉了一个**恰好长成大写数字的真提交**。

顺带把旧版那张 FAKE 白名单也量了：**31 项里只有 2 项**（一项是全数字占位 `1234567`，
一项是把真提交 `83697c3` 改末位造出来的那一串）在被扫 prose 里
真的作为独立 token 出现过，**29 项从未出现**。⇒ 这张表**没有被数据约束过**，
它是「我以为会出现的东西」的清单，而不是「实际出现了什么」的清单。
本版把豁免改成**逐条带实测理由且必须可数**（0006 §7 第 28 条：不可数的豁免等于没有判据）。

### ③ 没有下限

待验集若为空 ⇒ 失败数为 0 ⇒ 报「全部解析」而绿。写这次的同一轮我自己就撞了同类：
`git cat-file --batch` 吃**对象名**不吃路径，喂错 ⇒ 450 个全 missing ⇒ 摘要集空 ⇒ 造出 40 条假红。
所以下面是硬断言而不是注释：索引自检（`commits >= 100 && digests == blobs`）、
token 下限（`>= 300`）、**桶分项求和 == token 数**。

## 3. 新判据：不对称决定什么才有资格叫腐烂

* **提交引用与时间无关** —— 一个 commit 哈希要么永远指向某个提交，要么当时就写错了。
  解析不了 = 当时就写错 ⇒ 真腐烂 ⇒ FAIL。
* **内容摘要与时间有关** —— HEAD 会变，今天的 HEAD 对不上不能证明当时写错。
  ⇒ 匹配就 PASS；对不上也不 FAIL，因为**本脚本无法证伪它**，假装能验就是假绿。
* **注入态/变异态的对照摘要** —— 对象被**故意**删掉，机械上根本不可验 ⇒ 逐条豁免 + 理由。

⚠ **顺序是「先解析、后分类」，不是反过来。** 中间版本试过「读上下文判断这一格声称是提交引用还是摘要」，
**两个方向都错**：`sha256 == HEAD blob 03bf24d15241da01b40505d1d9bd4807a8a403a9e98205ade8fe59d4f17e40ec`
里既有 sha256 又有 HEAD，正则按窗口先后判成「提交引用」
⇒ 5 条假红；而同一个正则把 `HEAD: b192b4a` 这类**真提交引用**漏判成「未判定」⇒ 173 个静默少算。
解析是机械的、无歧义的；散文不是。**所以只有「解析不了」的 token 才需要看上下文。**

### 本轮最该记的一个洞：①b

为了「让内容摘要类引用能被机械验掉」，我建了 HEAD 侧索引（`ls-tree -r HEAD` 取 blob sha1，
`cat-file --batch` 取内容再做 sha256），然后写了这条看起来很自然的判据：

```js
if (prefixOf(h, BLOBS) || prefixOf(h, DIGESTS)) { t.digest++; continue; }   // ← 错
```

**错在 `prefixOf` 是「前缀匹配」。** blob 的 sha1 短前缀与**腐烂的提交引用**形状完全一样（7~40 位十六进制），
而「改坏一位之后**恰好也是某个 blob 的前缀**」是**真实存在的** —— 实测当前语料里就有 **3 处**
短 blob sha1 对象 id 前缀（各写出完整 sha1 的前 16 位，理由见 §2 表下那段）：
`3b7d385e409b5d4c…`（0008 那份）/ `23175d7f181d2700…`（`packages/hub/src/index.ts`）/
`8823b0a110ab0f3d…`（`test/arch/config-match.test.ts`），共 11 次出现。
于是这条判据会把**改坏一位的真提交引用**
报成「**已核验的内容摘要**」并**计入通过数** —— 假绿，而且是最坏的一种：**它长得像证据**。

修法按「**位数是否唯一指认一个对象**」切：

* 完整 40 位（sha1 对象 id）/ 完整 64 位（sha256）⇒ 位数本身排除了「同前缀的另一个对象」⇒ 硬通过。
* 短前缀 ⇒ **不接受机械硬通过**，只接受二选一：
  * **(甲) 位数够长**：门槛从索引规模现算（`n / 16^L <= 1e-12` ⇒ 本仓 n=448 ⇒ **13 位**；
    为什么不用散文：round255 那张矩阵表是 `| 前缀 | 路径 | MATCH |` 的表形，**行内没有任何摘要字样**
    （只有表头有），纯靠措辞会把**为真的记录**判成腐烂 —— 第一版就是这么红了 4 条）。
  * **(乙) 同一行正文明确写着** blob / hash / 摘要 / 对象…。

两个放行口**分别计数、分别报数给样本**。⚠ **这一格故意不写「终版实测」几个字**，
理由见下面第 3 条 —— 我在这句话上错过一次，把错过本身写下来比把数写对有用。
读数口径永远是现跑现看：`node docs/review/verify-open-invariants.mjs` 的「计数:」那一行。

1. 这两个数**会随本篇自己被编辑而变** —— 本篇也在被扫范围内（只有脚本自己不扫自己）。
   按文件归属实测（同口径复算脚本自带一条「甲/乙 == 主脚本报的数」自检，PASS）：
   本篇正文自己贡献 **甲 4 / 乙 3**，`docs/INDEX.md` 那条入口 **甲 0 / 乙 2**，
   ⇒ 合起来 **9 处**来自本轮新写的散文。
2. 读数史（每一次都是当时真跑出来的）：写完正文时 **25/40** → 把 hash 前缀改全长
   （§7 第 6 条）后 **29/45**（那批 16 位前缀**落进「位数够长」而不是「只靠措辞」**）→ 本轮收尾 **29/48**。
3. **本节第一版写着「终版实测：甲 29 / 乙 45」，而那个 45 在我把句子写完时就已经是 48。**
   token 总数一分未变（478 ⇒ 不是我新增了引用），纯粹是**我给一个中间读数挂了「终版」两个字**。
   ⇒ 这正是本篇 §5 在批的东西（历史证据里的一个计数，写下来那天就没人能复算），
   也正因为如此本节开头那句把「终版实测」四个字删了：**这类数只能连口径与时刻一起给**，
   和 §4 那批「台账自摘要」同一个处置 —— **写入当时成立，过期不等于说过**。
为什么甲乙必须分开：甲的依据是**概率**，乙的依据是**措辞** —— 措辞是可以被人改写出来的，概率不行。
把它们合并成一个数字，就看不出「这一轮又有多少是靠措辞过的」。

⚠ 两条**放宽**都没有放宽到「腐烂也能过」，理由是机械的：**改坏一位之后就不再命中任何索引**
⇒ 它压根进不到这一桶，多长的位数、多宽的措辞都救不了它（§6 的 M6/M3 是这一句的实测复证）。

## 4. round255 那道「哈希核对」把对改成了错

round255 的专项就是 restore-verify 真值审计：逐份 evidence 核对「字节还原基线」能否在对象库验证。
它对 round241 证据 L24 下的诊断是：

> 「`03bf24d15241da01b40505d1d9bd4807a8a403a9e98205ade8fe59d4f17e40ec` **既非合法 git hash**……
> 真实 hash 应为 `3b7d385e409b5d4c92c57caf0c6c20d6c240ba14`」，并据此**改写**了那两行。

**这个诊断是错的，而改完之后的那一行才是假的。** 三种 hash 混在一格里：

* git blob 的**对象 id** = **sha1**，恰 **40** 位 ⇒ `3b7d385e409b5d4c92c57caf0c6c20d6c240ba14`
* 文件**内容的 sha256** = **64** 位，**从来不是 git 对象** ⇒ `03bf24d15241da01b40505d1d9bd4807a8a403a9e98205ade8fe59d4f17e40ec`

原句「`sha256 == HEAD blob`」读作「**(内容的 sha256)** 与 (**HEAD blob 的内容**) 一致」，
**从来没声称那 64 位串是 git 对象** ⇒ 它一直是对的。复算（关键在**先问是哪一种 hash，再问在哪个库查**）：

```
git show   HEAD:docs/decisions/0008-….md  的内容做 sha256 = 03bf24d1…（64 位，== 原记录）
git rev-parse HEAD:docs/decisions/0008-….md               = 3b7d385e…（40 位，sha1 对象 id）
```

且 `git log 0dbc7a4..HEAD -- 该文件` **为空** ⇒ round241 写下那天与今天同内容 ⇒ 原记录当时成立、今天仍成立。
⇒ **round255 把一串真的 sha256 换成了一串 sha1，而标签仍写着 sha256** ——
它自己造出了「**标签与值不相称**」这一条它声称在修的不一致。已按「**两种都留、各自写明是哪种 hash**」改回。

**为什么它没被发现，而发现它的是本轮**：round255 那次的结论是「其余 17 份**核对通过**」。
它当时通过，是因为它的核对**只认 git 对象**这一种身份。发现这条的是本轮重写时给**内容摘要**建了索引之后 ——
摘要表里冒出了那条 sha256（`03bf24d15241da01…`）。⇒ 上面第 1 节第 3 条那句话就是从这儿来的。

⚠ 还有第二层：`3b7d385e` 正是 §3 里那 3 处「短 blob 前缀」之一。
也就是说，那次「修正」写进去的值，**恰好是旧判据会无条件硬放过、且与腐烂不可区分**的那种形状。

## 6. 变异探针：它真会红，还是只是碰巧绿

假绿的定义就是**改坏了也不红**；而旧版恰好相反（恒红），所以**它的红也没有信息量**。两种都要排除。
`.workbuddy/round260-refscan-mutate.mjs`，**9/9 PASS**，收尾对被改文件逐字节自检：

| 探针 | 注入 | 期望 | 结果 |
| --- | --- | --- | --- |
| M1 | 真提交引用 `be07d9a` 改末位（长度/字符集不变） | 红 | ✅ 红因**指向被注入的那串** |
| M2 | 插入一个**不在豁免表里**的新哈希 | 红 | ✅（证明豁免表不是万能放行口） |
| M3 | 40 位 blob 引用改末位 | 红 | ✅（长度规则不该救它） |
| M4 | 追加一行**无 hex 的散文** | **不该红** | ✅（否则它就是另一个恒红信号） |
| M5 | 把 `walk` 的扩展名匹配打掉 ⇒ 采集面塌 | 红 | ✅（下限那条必须红） |
| M6 | **运行时**取一条真摘要前缀改末位 | 红 | ✅（**熵放行口没有把腐烂放掉**） |
| M7-甲/乙/丙 | 「离真提交只差一位」的三种形状（见 §6b） | 红且**给出撞中的那个真提交** | ✅ 三发都点名 + 给出真身 |

⚠ **「红了」不等于「因为注入的那串红」**（0053 那一族的教训：恒红的断言在它声称要盯的那件事上分辨能力是零）。
第一版探针只断言 `exit != 0`，**没说红在哪一行、因为哪个 token**。补了单独一测：
逐发把 FAIL 行与注入串对齐 ⇒ M1/M2/M3 **三条红都精确指向被注入的 token**，且还原后回绿。

⚠ **M6 不能写成「源码里放一个字面量哈希」**。本轮在这上面**连踩三次**：探针自己就在被扫目录里，
它源码里的**裸 7+hex 字面量**会被扫 ⇒ 探针一落地就把基线弄红/弄脏。
第一次的 M8 因此造出一条**真腐烂**报了出来（红因是探针自己，不是判据）；
第二次更荒唐：**我写那条警告的注释本身**因为举了个真例子而把基线弄红。
⇒ 丙类改成**运行时从文件里取真前缀、就地改末位**，源码里一个 hex 字面量都不留（要举例就拆开写）。

第一版的 M7 也是错的，且错法值得记：它想证「**措辞不许救腐烂**」，
于是挑了矩阵表里的一行注入 ⇒ 但那一节**每一行都带「注入前/还原后」**字样，
**③ 会先把它当「机械上不可证伪」跳过** ⇒ 探针**测不到它声称的那条判据**，会给出一个**假的 FAIL**。
⇒ 选锚点时必须先确认**目标判据是这一行上第一个起作用的那一条**。
⚠ 上面表里现在那个 **M7 是另一发**（§6b 的 ①d 判据探针），与这里被否掉的旧 M7 无关 ——
同号不同物是我这一轮晚些时候加东西时造成的，读的时候按§6b 的定义为准。

补写做完（§3 那张表定稿）之后，我把判据交给一轮对抗性复查，问的是「有没有哪种腐烂
走完 ①→⑤ 既不红也不点名」。回来的主张里有**两条是真的**，都在我自己的脚本里复现了：

而那两个值**恰好就是**「离真提交差一位」的形状 ⇒ **原样写出会被自家 ①d 判成腐烂**。
第一版正是原样写的，于是红因指向本篇这一行，读起来完全像「文档里发现一处腐烂引用」。

仍能**逐字复算**那个注入值 ⇒ 少一点可粘贴性，**没有**少掉可核验性。

⇒ 这两条是**同一个病的两个出口**：腐烂落进了【跳过】桶，而那些桶存在的理由都是
「这一格机械上无法验」—— 可这两串**恰恰能验**：**它离一个真提交只差一位，而「差一位」就是腐烂的定义。**
第二条尤其难看：`纯数字` 那一桶是我这一轮**自己**为了「别把 `1048576` 当哈希」加的，
而它顺手吃掉了一个数字形的真提交引用 —— 与 §2② 批的旧版那道 `/^[0-9]{7}$/`
**是完全同一个错法，我重犯了一遍**（旧版那道 filter 吃掉了 `0575943`，我这道吃掉了它的邻居）。

补法（脚本里的 ①d）：`离某个真提交前缀恰好差一位` ⇒ **直接算腐烂**，不进任何跳过桶，

⚠ 这句话我第一版写成「顺手把 §8 那条『64 位坏掉静默放过』**收窄了**」——**方向对、范围没量**。

64 位那一档**整体仍然不验**（理由没变：sha256 从来不是 git 对象，本脚本没有可对照的对象库）。见 §8。
