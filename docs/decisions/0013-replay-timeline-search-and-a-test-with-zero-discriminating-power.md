先说实现侧的三条，细节在 §2 到 §5：

1. **附录 C.3 的示例代码有一处会让审计检索给出假样本。** 它的 LIKE 兜底是
   `'%' + kw + '%'` 直接拼，关键词 `%` / `_` 不转义 ⇒ 实测命中**全部行**。
   后果不是报错，是 CEO 在回放里看到一堆与该关键词无关的事件并当

   数据来源里的假样本会被拿去做真决定。**给出错的行比给不出结果更坏**，
   因为后者只会让人换个词再搜一次。
2. **同一档 SQL 少了 `ESCAPE '\'` 子句，上面那层转义就是纯装饰**，
   而代码看上去确实转义了。这是本轮最容易写错的一行（我的用例第一版也没能抓到它，见 §8）。
3. **「FTS 说没有 ⇒ 降级 LIKE」这一支在索引健康时永不可达。** 238 个关键词穷举：

   所以那行兜底代码不是在防分词边界，是在防**索引与表脱钩** —— 于是我造了一次真脱钩。

## 2. 本机复测：C.3 那五条结论在 SQLite 3.51.2 上全部成立，示例代码却不成立

规格的 trigram 结论测于 **3.53.4**，本机 `node:sqlite` 内嵌 **3.51.2**
（0004 §文件头那条提醒：『上线前须用同样的用例重跑本表，不得假定行为一致』）。
本轮逐条重跑，**表格五行结论原样成立**：默认 unicode61 查『覆盖率』0 命中、
trigram 1 命中、`MATCH '件通'` 0 命中、`LIKE '%覆盖率%'` 1 命中。

**偏离与新增，五条**（`search.ts` 文件头有同一份，这里是依据）：

| # | 偏离 | 不做的后果（实测） |
|---|---|---|
| ① | LIKE 兜底必须转义 `% _ \` **并带 `ESCAPE '\'`** | 关键词 `%` 命中**全部行**（假样本）；只转义不写 ESCAPE ⇒ `%\%` 变成「找含字面反斜杠的行」（静默换语义） |
| ② | 关键词包成 FTS 短语（C.3 原式，**验其正确**） | 不包时 `AND` 报 `fts5: syntax error`、`覆盖率 OR` 报 `near ""`、`-a` 报 `no such column: a` ⇒ 搜索框打一个 AND 就 500 |
| ③ | 排序要有**末位 tiebreaker**（`…, id DESC` / 时间线用 `ORDER BY id ASC`） | 同毫秒并列时 SQLite 不保证顺序：同毫秒 6 条时只按 `created_at DESC` 翻页与加 `id DESC` 得到**不同序列** ⇒ 「两次回放一致」这条验收会**偶尔**成立 |
| ④ | 关键词长度按 **code point**（`[...kw].length`） | 两个 emoji 被当 4 字符送去 MATCH，而 trigram 要 3 个**字符** ⇒ 0 命中且不报错 |
| ⑤ | 空关键词返回**空**而不是全部行 | C.3 没处理空串，而 FTS 空短语与 `LIKE '%%'` 都返回全部行 ⇒ 回放页变成一个无界全表扫入口 |

顺带量到 ⑥：**trigram 对 ASCII 大小写不敏感**（行里 `CoVeRaGe`，查 `coverage` 与
`COVER` 都命中），LIKE 也不敏感 ⇒ 不需要 `LOWER()`，也不需要提示用户大小写。

**限定单个任务**是本轮新加的一维（回放页必须带：CEO 在任务 A 里搜一个词，
拿到任务 B 的事件是答非所问）。FTS 那一发只能这么写：

```sql
SELECT rowid AS id FROM events_fts WHERE events_fts MATCH ?
  AND rowid IN (SELECT id FROM events WHERE task_id = ?) ORDER BY rowid ASC LIMIT ? OFFSET ?
```

因为 `events_fts` 是 external content 表（`content='events'`），它手上**只有被索引的
payload 列**，`task_id` 不在索引里。探针（同一库两任务各一条）：
限定 t2 的 FTS 与限定的 LIKE 都给 `[2]`，不限定的 FTS 给 `[2,1]`。

## 3. 一次夹具说谎：我把「行里根本不存在的关键词」当成「索引不命中」（同一个坑第四次）

写 FTS 用例时我断言：关键词 `说"你` 在含『他说"你好"』的库上 **0 命中 ⇒ 说明规格有缺陷**。
红了之后先查**夹具**（0012 §6 那条纪律），当场发现原因：
`payload` 列存的是 `JSON.stringify` 的产物，里面的 `"` 已经变成 `\"` ——
库里那一串实际是 `说\"你`，所以搜 `说"你` 命不中是**正确的**。
换成 `你好\"` 立刻命中 1。

这个夹具错误我踩了**四次**：两次在 `/tmp` 探针（拿到 0 命中就判「规格的示例有缺陷」），

形状始终同一个：**我测的是索引里的字节，脑子里想的是用户看到的文本**，
两者在 JSON 转义处分叉。凡是「0 命中所以某处有缺陷」的论证，
必须先证「这个关键词按存储形态确实存在于那一行」。

## 4. 「FTS 0 命中 ⇒ 降级 LIKE」在索引健康时**不可达**

我原本给兜底那一档写了一条『含双引号的 3 字关键词 FTS 不命中 ⇒ via=like』，
前提是编的（§3）。红了之后做了两件事：

1. **穷举**：把 10 条各种形状的文本（中文、ASCII、`a-b_c%d`、带引号、变音符、
   兼容假名、emoji、双空格、中英混排）切成 **238 个长度 3–5 的子串**，逐个比 fts 与 like。
   结果 `fts=0 而 like≥1` 的个数：**0**（用例里同时断言 `seen.size > 100`，
   否则那个 0 可能来自扫得太少）。
2. **想清楚为什么是 0**：trigram 索引的是文本里**所有 3 字符窗口**。
   一个长度 ≥3 的关键词 `kw` 若真是某行的子串，那 `kw` 自己的头 3 个字符必然是
   那一行的某个窗口 ⇒ **必然命中**。所以「kw ≥3 字」时 LIKE 能中的 FTS 必中，
   反向不成立。这不是「我还没找到」，是结构性不可能。

⇒ 规格 C.3 那句『0 命中时降级 LIKE』**在索引健康时是永不可达的一支**。

那这行代码该删吗？**不该**。`events_fts` 是 external content 表，
它的正确性**完全依赖** `events` 上那三个同步触发器（`0001_init.sql` 的注释里
已经写着那两个同步触发器「正常运行期不会被触发」，说明作者也知道它们微妙）。
触发器被改掉、或有人 `ALTER` 重建表时漏挂，索引就会与表脱钩，那时
「FTS 说没有而库里确实有」就真的发生。

所以那支的可达性靠**制造反例**来测：直接对 `events_fts` 下一条 `'delete'` 指令，
再证实「直接查 FTS = 0 行」而 `searchEvents` 仍返回那一行且 `via=like`。
不这么写的话，我交的是一条**恒不执行的分支**的用例，而它看起来像在测东西
（0011 §5 那族问题的第三次）。

## 5. 时间线取行：排序、`IN (…)` 与一次 32766 的探针

`buildReplayView` 有 keyword 时**先检索、再按命中的 id 取行**。三处判断：

**① 检索那一发必须显式传 `order: "timeline"`。** `searchEvents` 的默认排序是
`created_at DESC`（审计页要的「最近在前」），拿它填时间线会得到一份**倒放**的回放 ——
「A 之后才有 B」被读成「B 导致 A」，而 §24 风险 1 防的正是这类因果误读。
两个消费者的默认值**恰好相反**，这件事说明「一个 `searchEvents` 服务两个消费者」有代价。
为什么不拆成两个函数：拆了会把转义 + 双路兜底那套逻辑抄两份（0006 §7 那族「两份抄本」的问题），
而转义那份是本轮最要紧的代码。所以留一个函数 + 一个**必须显式传**的维度，
并用一条用例钉住顺序（带**反向对照**：不加这一半，夹具上两种排序可以同序 ⇒ 恒真）。

**② 过滤发生在取行那一层，不在前端。** 时间线是分页的。
「取一页 500 条再在前端 filter」会得到：命中项在前 5 行时 `offset=2` 直接跳过它们，
界面显示「没有更多结果」，而真相是「命中的在第 1 页已被取走、第 2 页取的是别处」。
那是一条会把 CEO 引向错误结论的空结果。所以 `offset` 落在**命中集合**上。

**③ `IN (…)` 的占位符按 id 个数展开，并有一道上界对账。** 探针：本机 SQLite
接受 **32766** 个 `?`，32767 报 `too many SQL variables`。而本页命中被
`MAX_SEARCH_LIMIT=200` 夹住，两个数此刻差 160 倍、撞不上。
那为什么还写这条检查：因为那个「永远」是**两个文件里的两个常量**维持的，不是类型维持的。
哪天有人为了「一次导出全部审计」把 `MAX_SEARCH_LIMIT` 抬到几万，
这里会当场报错并说出该改哪，而不是让 SQLite 在最不可能重跑的路径上报一句语法错。
（这一条**不是**防御性冗余，也不是保险 —— 它是「两个常量之间的关系」唯一的显式承载点。）

**④ `effective_limit` 进响应。** 不带关键词时 limit 能到 `MAX_REPLAY_LIMIT=2000`，
带关键词时只有 200。调用方传 500 拿到 200 条，按自己手上那个 500 判断「到底了」
⇒ 第 2 页永远不被请求，一次「搜完了，就这些」的假结论。
所以响应里给出**服务端实际用的分母**。这与 `complete` 各管一件事：
那个说「中间缺行」，这个说「后面还有行」。

## 8. 【本轮最重要】那条「最值钱」的用例，对目标缺陷的分辨能力是零

上面那张表里 M10 是**存活**的。原因值得单独一节，因为它不是「少写了一条断言」，
而是**正反对照看起来齐全、而反的那半根本没经过被测代码**：

我第一版的夹具是三行「没有百分号」的文本，断言『搜 `%` 返回 0 行』，
再加一条『搜 `92%` 返回 1 行』当反向对照。删掉 `ESCAPE` 之后：

- `92%` 是 **3 个字符** ⇒ 走的是 **FTS 那一档**并直接命中返回。
  那条「反向对照」**从头到尾没有经过 LIKE 那一发**，也就是没经过被测代码。
- `%` 那一问在没有 `ESCAPE` 时拼出的 pattern 是 `%\%%`，它要求行里有**字面反斜杠** ——
  第一版夹具里一个都没有 ⇒ 两种实现都给 0 行。

于是整条用例对「`ESCAPE` 有没有写」分辨能力为**零**，
而它是我自己评的「本轮最值钱的一条」。**自评的价值判断不能替代变异实验。**

重写后的三条要求，各自对应上面那一条失效原因：

1. **反例必须走被挡那一档** ⇒ 反向对照关键词取 **2 字**（`%的`），≥3 字会被 FTS 截走。
   断言里还查 `via === "like"`，否则「四格都过」可能是四格都走了同一档。
2. **夹具必须带字面反斜杠** ⇒ 库里放一行含 `\` 的文本（真实库里到处都是：JSON 转义、
   Windows 路径）。没有 `ESCAPE` 时 `%\%%` 就命中那一行 ⇒ 「搜 `%` 返回 0 行」
   第一次真的能在实现写错时红。
3. **夹具自身的分辨能力要被断言，而不是被我注释掉** ⇒ 用例里跑一遍
   「同一批 pattern 不带 `ESCAPE`」并断言**至少一个关键词给出不同的行集合**
   （`discriminating.length > 0`）。这条是元断言：如果哪天夹具退化回第一版那种，
   它当场红，而不是留下四条恒真断言。

还换掉了「人肉推算期望行数」这件事：`payload` 存的是 JSON 文本，
我把 `\\` 在 JSON 里被写成 `\\\\` 这件事忘了一次，于是期望值写错。
现在用 **JS 当预言机**（`stored.filter(r => r.payload.includes(kw))`）——
它跑在取出来的字符串上、与 SQL 完全无关，所以是独立第二意见，
而不是把 SQL 的结论抄一遍。同时断言**预言机本身非空**，否则那三格可能是空对空。

最后补一条形状对照：规格原样（不转义也不 ESCAPE）时关键词 `%` 拼出 `%%%`
⇒ 等价于匹配一切 ⇒ 返回**整表**。这一格是把「C.3 示例的真实后果」钉在用例里，
而不只钉在我的文档里。

`review_gates` 这一条要说准一点：**审阅判定本身是有记录的**
（`events.action='review_decision'`，由 recorder 从 `ReviewDecided` 落库），
但那条事件的 payload 只有 `{gate, decision}` —— **不带 `reviewer_role`、
不带 `model_family`**。而门控代码（`graph/gates/author-reviewer.ts`）
**当场是知道 `model_family` 的**：它在缺这个字段时判 `unknown_model_family` 并拒。
也就是说「同源审阅共谋」这条分析要的字段在**判定发生的那一刻是存在的、
落库的那一刻消失了**。`evidence_bundles.model_family`（产出方那一侧）
0002 迁移专门加过、也确实有写入方 —— 缺的是**审阅方那一侧的持久化**。

⇒ **要你拍的**：`review_gates` / `harness_calls` / `trust_scores` / `skill_mounts`
四张表**建好了、没有任何代码往里写、计划里也没有任何任务写它们**
（`grep -c` 在计划里分别是 0 / 0 / 0 / 2，`skill_mounts` 那两次是「表已建好、实现时不需要迁移」）。
于是 §22.3 那四条、以及 §22.4 完整性校验要的「每个门控决定都有对应证据包引用」
（也要 `review_gates`）**在可预见的任务序列里无法验收**。三个选项：

- **A. 补任务**：加一个「把门控判定与 harness 调用落表」的任务（我估 1–2 天，
  写入口就在 recorder 旁边，字段门控代码当场都有）。代价：Phase 3 变长，
  而且 `review_gates` 的写入方一旦定了，Task 3.6「改岗位书验收标准后重跑同类任务、
  门控行为随之变化」那条验收才有「上一次的门控记录」可比。
- **B. 就地降级规格**：§22.3 那四条改成「等相应写入方到位后再接」，
  并在 §22.4 那一节标上前置条件。代价：Phase 6 的「回放可理解任意任务」这条
  CEO 亲自验收的标准会**真的少四样东西**，而 §22.2 的意图正是靠这些标注
  让 CEO 判断「该调岗位书、委派规则还是门控」。
- **C. 删表**：认定这四张表是过度设计，从迁移里去掉。代价最大也最诚实 ——
  但 `trust_scores` 之类我**没有**足够依据说它没用，只是没人写。

**我倾向 A，且只做 `review_gates` 那半**（约半天）。理由：四条里只有它
「数据在判定现场就有、只差落库」，而它支撑的正是 §24 风险 1
（审阅共谋）—— 那是规格自己列为头号风险的条目，且 §22.3 与 §8.2 都指向它。
`harness_calls` 等的写入方在 Phase 5 的适配器里，那时有真数据形状，现在定表单是提前定。

这一项**卡** §22.3 与 §22.4 的验收，**不卡** Phase 3 剩下的任务。
