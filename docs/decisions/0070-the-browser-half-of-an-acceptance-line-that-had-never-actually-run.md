## 1. 这一格在被引用了很多次之后，今天第一次真的跑起来

O13 §E 的验收原文（功能优化设计 1520-1523）：

> **验收。** 一条**全新机器**上的冒烟：`pnpm i && pnpm dev` → 浏览器打开 → 建一个任务 →
> 看到它进收件箱。…… ⚡ 动作 1 落地后该冒烟的口径改为：`pnpm i && pnpm dev` 到看板可用
> （`dev-entry.test.ts` 钉的是各阶段与失败出口，**浏览器那一发今天仍要人眼**）。

`dev-entry.test.ts` 14 发用例全部走注入（假 boot、假 spawn、假 migrate），`devMain` 那一段
【没有任何东西执行过】—— 这不是它的缺陷，它文件头自己就这么说。设计文档也没有说谎，
它说的是「要人眼」。说谎的是第三种人：台账里 `pnpm dev` 出现了十几轮（round264 的挂死
修复、round268、坐标重钉），每一轮都引用这条命令，没有一轮记录过这条冒烟跑过。
本轮先用人眼跑一遍（全部真读数，`.workbuddy/scratch/round384-*`）：

- `OPC_DEV_DB=… OPC_DEV_HUB_PORT=18787 OPC_DEV_WEB_PORT=19797` 起 `dev-entry.ts`：

## 2. 与 ceo-loop.spec.ts 的分工，先说清免得读成重复

ceo-loop 起 Hub 走【编程口 `boot(...)`】：参数写进源码，绕开 `devPaths`、绕开迁移调用、
绕开 `webSpawnArgs`。那条验收说的恰恰是「人走的命令」这一面：env → devPaths → 迁移 →
真 boot → spawn 代理。两边各证各的：ceo-loop 证 CEO 一圈的业务闭环（收件箱、批准、
看板更新，泵是注入的），这一发证那条人用的命令端到端可用（泵没有、库全空、界面裸奔）。

唯一借用的注入是 `waitStop`（`DevDeps` 里【本来就是】注入点，`dev-entry.test.ts` 用它钉
停止顺序）：默认那一发等 SIGINT/SIGTERM，fork 的子进程收不到可靠的信号投递。
换的是「什么时候停」，不是「启什么」。停止编排【不归这一发证】，归 `dev-entry.test.ts`。

## 3. 实测：`tsx cli.mjs 脚本` 会 spawn 孙进程，把 IPC 断在中间

第一版子进程侧是 `fork` + `execPath=node` + `execArgv=[tsx/dist/cli.mjs, 脚本]`（抄
`webSpawnArgs` 的形状）。实测后果：`stop` 永远收不到，`afterAll` 只能走 SIGKILL 兜底。
原因在 tsx 的 cli —— 它会【再 spawn 一个 node 进程】跑真正的代码，`fork` 的 IPC 通道
只到中间那一层。换成 `execArgv: ["--import", "tsx"]` 后本进程直跑 TS，探针实测
（`.tmp` 一次性脚本）：`ready` 消息到位、`stop` 到位、子进程 exit 0、库随目录删干净。
这条写进 spec 文件头：以后有人「顺手统一成 webSpawnArgs 的形状」会静默退化成 SIGKILL 收尾。

## 4. `repoRootOf` 在别的目录深度上数出来的是仓库根【上面】

子进程侧第一版用 `repoRootOf(import.meta.url)` 算仓库根 —— 那个函数数的是「从
`packages/hub/src/serve/` 往上四层」，写在 `test/e2e/` 下的文件拿它数出的是盘符根方向的
上一层。三个路径 env 都给了绝对值所以没炸，但这是一格【错了不响】的：哪天有人用相对
`OPC_DEV_DB` 就会种错地方。改为 `process.cwd()` 并写明理由（spec 以仓库根为 cwd 起子进程）。

## 5. 两发红在尺子上，不红在产品上（都是本仓登记过的老形状）

① `toContainText("0 活跃任务")` 首跑即红。`stat()` 把数字与标签放在同一行的两个兄弟 div
（app.js:618），innerText 归一化后两者之间不保证剩恰好一个空格。按「标签定位卡片、
读同卡片数字」的 DOM 探针重写 —— 别把断言修成 `toContainText("0")`，那会退化到
「任何一格是 0 都绿」。
② `waitForFunction(() => document…)` 在 `types: [node]` 下不过 tsc（TS2584，页内闭包
全红的老坑）。页侧探针一律字符串形态，这一发补上第二例（第一例是 `evaluate` 的闭包）。
两发都是「红了才知道我原来在量自己的拼串/编译面」。

## 7. 别当成「O13 验收全过了」

- **「全新机器」没复现**：`pnpm i` 没重跑（node_modules 在场）。这一发证的是「这条命令
  在这台装了依赖的机器上 + 空库 + 浏览器」，不是「clone → install 的第一分钟」。
- **收件箱那一跳没走**：验收句尾「看到它进收件箱」里的卡是【章程提案卡】，它的产生要
  章程泵起草（`charterPump` + 真 claude 或注入执行点）。dev 的装配【刻意不开泵】
  （dev-entry 文件头：不打开花钱的东西）。人眼跑实测 `待批 0` 是正确行为。
  「进收件箱 + 点批准」那一面由 `ceo-loop.spec.ts` 钉（注入泵的 `pumpCardDeps`）。
  两句合起来才等于那句验收，哪支单独都不等于。
- **两侧 token 不同源时【界面】怎么表现没测**：M1 证的是「不同源 ⇒ 这一发红」，
  不是「界面会给用户一句人话」。红的具体形状（确认条等不来 401 的错误体）没读。
- 停止编排、横幅文案、`--ceo`/飞书缺失提示 —— 全部仍归 `dev-entry.test.ts`，见 §2。
- `o13-dev-child.ts` 走的是 `runDev` 直调，`devMain`/`isDirectRun` 那一段仍无人执行

## 9. 落地之后守卫红了四发，其中三发是【我的改动是对的、守卫本来就该红】

改完 §1 那一发，坐标族守卫接连红四处。四处都不是产品缺陷，也**一处都不该靠放宽判据压掉**，
记录一下每一处「为什么它红得对」：

① **登记表 12 条坐标整体 +3**（`claim-coords`）。我对 `OPC-OS-功能优化设计.md` 的
O13 §E 那一段净增 3 行，插入点之下的 12 条登记坐标全体下移。先立因果再动数字：
**偏移符号与幅度自洽**才改 —— 12 条全在插入点以下且全 +3，插入点以上的（r1 186、
r7 1228、r8 912、r9 180、r16 1478、r17 1441、r18 1414）一条没动。只核「数字对不对」
而不核「符号与幅度能不能由这一次改动解释」，就会把「我插了 3 行」和「别人改了内容」
混成同一串数字。
⚠ 我第一遍写了个脚本用正则从 `claims-registry.ts` 源码里抠 id/line/sentence 来核对，
它把 r8 / r9 / r27 三条报错行**配错到相邻条目**，报了三个假「读不到」。这正是
`claim-coords.test.ts` 文件头骂过的那件事：**别拿一条会错配的正则去核对坐标**。
那三条的 doc/line 我改成逐条 `grep` 原文看，且它们全在插入点以上 ⇒ 与本次改动无因果。

② **`doc-refs` 快照缺一条**（本篇 §5 那条 `app.js` 引用）。按规矩先在目标文件里
`sed -n '618p'` 现读原文再抄进 SNAP，不从本篇正文复制措辞。键仍写裸名 `app.js`：守卫的 `walk` 在**任意深度**跳过 `.tmp`，所以
`.workbuddy/.tmp/head-biome/` 那份副本不在语料里，裸名当前唯一可解析，
与 0050 / 0060 已有的两格裸名键同形（这一点是查过 `walk` 才写的，不是数 `find` 数出来的）。
顺手把 §5 那条引用从**区间形态**改成**单行形态**：区间里只有我钉的那一行
同时装着数字与标签两个兄弟 div，而守卫的判据是「那一行现在还有没有那句」——
钉区间等于钉了一行不属于判据物的东西。
⚠ 写下这段的时候我自己又把区间形态原样贴进了正文，`doc-refs` 当场判它一条
「快照里没有这条引用」。守卫的取材是**整篇散文**，不认「我只是在描述旧写法」：
被它采到就得登记，而登记一条「旧写法」等于宣称它现在还成立。所以改写法，不登记。

③ **`verify-open-invariants` 判我 §1 那行红**：`腐烂=1 —— ddc62928 @ …0070-….md:26`。
`ddc62928` 是看板卡上那个 8 位短 id，实测 = 该轮 dev 库 `tasks` 表里那次提交新建的
`ddc62928-92e9-4b0c-…`，`git rev-parse` 解析不了。它和被扫目录里任何一次 git 声称无关，
但形状与真腐烂逐字一样。表里已有一条同族先例 `360ee441`（引擎开的新卡的短 id），
所以正确的动作是**照先例登记带理由的具名豁免**，而不是把「卡」这个字旁边的 id
加进 ③ 的窗口判据 —— 后者会放行任何行内含该词的未来 token，一个新的腐烂哈希
写在同一行也一起放过。登记后重跑：豁免 58→59、`腐烂=0`、分项和 714 = token 714。
⚠ 这一发**先以另一张脸出现**：它最先炸的是 `exempt-pierce` 的「基线：脚本未变异时可复算绿」，
一条自锁自检。读到「还原后仍红」时我先怀疑的是探针自己坏了（round353c 那族脏基准事件
的形状），而真因在**上游**：verify 脚本本身被我的文档改红了。⇒ 自锁自检报红时，
先去被检对象跑一发裸命令，别在探针里翻。

④ **同一处改动把 `exempt-pierce` 的计数断言也带红**（`expected 17 to be 16`）。这一发是
**设计成必须红的**：那条反向 canary（「合法改动 ⇒ 放行」那一支）的注释原本写着
「多出的那条 `1234` 加 `abcd` 合成值会让"16 条 key"断言红，那是穿透的正常语义」
—— 照 `verify-open-invariants` 文件头那条规矩，注入值在散文里**拆开写**，
任何一段都 < 7 位 hex ⇒ 采不到，而读者仍能对着源码那一段逐字对上。
注释里那个数正是被这一次改动判成过期陈述的那一类（表一长它就不对了，
而它讲的不是今天的数），所以我把注释改成不带数、只指「那条计数断言」。
它是加豁免的入册仪式 —— 逼加的人重数一遍并同步穿透面。
所以我把 16 改成 17 而**没有**改成 `keys.length`：从 `keys` 派生会让这一发恒真，
判据当场归零。只有「逐字节还原后应干净」那句**消息串**改成派生（它不是判据，
是给人看的读数）。穿透面因此从 16 发变 17 发，`穿透 ddc62928` 那一条证明这条新豁免
**今天真在承重**（拿掉 ⇒ 脚本红且点名），不是「加了却从不生效」的空头条目。

⑤ **`lint-baseline` 抓到我自己写的那行**（`format=1` 基线外类目）。我把恢复消息改成模板串
那一行超了行宽。这是棘轮第一次以「新种类的 error 必须先点名」的形式抓我，而它抓得对：
我没有把 `format` 加进 `LINT_BASELINE`，我把那行改成格式化器要的形状。
另：SNAP 那条新增键的值里有 `${esc(n)}`，biome 报 `noTemplateCurlyInString` **warning**
1 条 —— 与该文件已有的两格（0050 与 INDEX 里那两条指向同一行的裸名键）同形状，
且 `countErrorCategories` 只统计 `severity === "error"`，棘轮不受影响；
净新增 warning 用 stash 前后各跑一次 biome、按规则名逐条比出来，不是估的。
