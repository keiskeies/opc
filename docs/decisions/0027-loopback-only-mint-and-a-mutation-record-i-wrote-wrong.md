## 1. ⭐ 我写下「两道门各自独立、缺一不可」，而其中一句当场就能证伪

`POST /approvals/:id/token` 的守卫我写了两道：

1. `remoteTokenAuth` 里的白名单 —— 靠 token 通过的请求**只有** `kind === "decide"` 那一条路由能过；
2. `mintToken` 顶上那一行 `isLoopbackAddress(req.peer)` —— 非回环直接 401。

我在注释里的论证是「两道门各自独立成立，才叫不依赖对方今天长什么样」，
并且**顺口加了一句**：把门一放宽（哪天做「远程读收件箱」时会很自然地放宽），
门二会替我挡着，**而且测试会红**。

第二句是可测的。跑完：

| 变异 | 结果 |
|---|---|
| M-A 只撤门二（删掉 `isLoopbackAddress` 那一行）| **2 红** |
| M-B 只放宽门一（白名单从「只有 decide」改成「decide 或 mint_token」）| **18 全绿，0 红** |
| M-C 两道门同时撤 | **3 红** |

所以「测试会红」是错的，准确的分工是：

- **门二那一发**（直接调 `mintToken`，故意绕开门一）挡「改门二」；
- **端到端那一发**只在**两道门都没了**的时候才红；
- **「只改门一」这件事全仓测不出来** —— 它是被门二**单独**兜住的。

M-B 零红**不是测试没写够**。如果我为了补它写一发「改门一必须有红」的测试，
那发测试的判据会变成「门一和门二必须同时存在」，也就是把两道独立的门
**焊回一条判据** —— 而那恰恰是我这段注释论证要去防的东西。
所以我选择**不补**，并把「不补」的理由写在门一的注释上。

⚠ 顺手量到一个**可达的**后果，它比注释原来写的那条更糟：原来我只写了
「带票打到别的路径 ⇒ 返回 null」这条不可达的分支。实测形状是 ——
**带真签名 + 带票**的远程请求，在「命中后返回 null」那种写法下会 **200 放行**并读到看板数据。
今天到不了（门一先弹），但那是「今天到不了」，不是「结构上写不出来」。
补的那发测试要能区分「**在这一发被拒**」和「反正 HMAC 会失败」，
唯一的写法是：真签名 + 票 ⇒ 401，**同一签名单独用（不带票）⇒ 200**。
两条一起才算钉住「拒的原因是票，不是签名凑巧不对」。

## 2. 一条我以为是结构守卫、实际是装饰的断言

`real-deps.ts` 签票时的 TTL 必须来自 `tokens.ts` 的 `DEFAULT_TOKEN_TTL_MS`（单一来源）。
我第一版写的是行为断言：签一张票，查库里的 `expires_at`，断言它等于 `NOW + 10 分钟`。
**这条断言provably 测不到它声称的那件事** —— 把 `real-deps.ts` 里的 TTL 写死成
`10 * 60_000`，库里的数**一模一样**，断言照样绿。它测的是「值是 10 分钟」，
不是「值来自那个常量」。

换成结构判据：本文件（去掉注释后）**不许出现** `DEFAULT_TOKEN_TTL_MS` 字样 ——
出现就意味着这里自己算了一份。两条变异分别跑：

| 变异 | 只留行为断言 | 行为 + 结构两条 |
|---|---|---|
| 在 `real-deps.ts` 里写死 TTL 字面量 | **32 全绿**（溜过去了）| 1 红 |
| 把 `issueToken(` 那处调用改掉 | — | 1 红 |

顺带那条「去掉注释后行数必须明显变少」的自检不是为了测代码，是防**判据自己变成恒真**：
如果哪天 `readFileSync` 路径写错而读到空串，`not.toMatch` 会绿得很漂亮。

## 4. ⭐ 我自己写下的变异矩阵是错的（重写这一节时又读错一次读数）

`tokens.test.ts` 里那张双保险矩阵（JS 的 `row.used !== TOKEN_UNUSED` 与
SQL 的 `WHERE ... AND used = ?`）我记成了：

> · 只删 JS 那道 ⇒ 25 全绿；· 只不查 `changes === 0`（**等价于删掉 SQL 那道的效果**）⇒ 25 全绿；
> · 两道同时删 ⇒ **3 红**。

本轮为了写 0027 重跑，**三条里两条不对**：

| 变异 | 我记的 | 实测 |
|---|---|---|
| 删 JS 那道 `used` 检查 | 25 全绿 | **25 全绿**（对）|
| 让 `changes === 0` 那一支不触发 | 25 全绿，且**注为「等价于删掉 SQL 那道」** | **25 全绿**（数对），**但「等价」这句是错的** |
| 只把 SQL 的 `AND used = ?` 拿掉 | 没测 | **9 红**（8 发行为 + 1 发形状断言）|
| 同上，但保留 4 个占位符（不撞 `assertParamCount`）| 没测 | **1 红**，红的正是那条形状断言，行为 24 全绿 |
| JS 那道 + `changes` 检查一起删 | 「3 红」 | **2 红**。当时那个 3 是数 `✖` 行数数出来的，其中一行是**父级 describe** —— 同 §5-① 那个读数错，同一个错在两个地方各犯一次 |

**「等价」那一格才是这轮的收获。** 我把「不查 changes」当成了「SQL 那道失效」的等价写法，
于是顺手把三条测出来只有两条的形状讲成了「SQL 与 JS 各挡一次」。诚实的图是：

- **JS 那道与 `changes` 检查是真双保险**：各自单删都全绿，同时删 ⇒ 恰好红那两发连续兑换。
  这一格我原来记的**是对的**（除了「3 红」那个数）。
- **SQL 的 `AND used = ?` 才是没人验证过的那道。** 老记录说「只删 SQL 那道也全绿」，
  数是对的，**但那次跑是无效的**：直接删掉条件会把占位符从 4 个变 3 个，
  `assertParamCount` 当场抛 —— 那一跑测的是「参数个数对不上」，不是「条件被拿掉」。
  把条件改成恒真而**保留 4 个占位符**再跑：行为 24 全绿，**唯一还红的是那条形状断言**。
  也就是说这道防的东西（**两个进程同时写这个库**，单写者队列之外唯一剩下的窗口）
  **在单进程里根本造不出来**，钉它的只有形状，而我把这个「只有形状」的存在
  在注释里讲成了「行为层的第二道保险」。

⚠ 手法更新一条，比结论重要：**一份记下来的变异矩阵必须重跑，因为它带「已验证」的标签**。
没测过的猜想会被质疑，**记下来的数字不会被质疑** —— 我这一轮质疑自己的那份记录，
唯一的原因是「写 0027 时想再确认一遍」，不是因为发现它可疑。
「跑过变异」不等于「变异记录是对的」；两者之间的距离，正是 0006 §7 那条纪律
为什么要求**把命令和结果一起记下来**（记命令就能重跑，只记结论不能）。

## 6. 第 8 个事件 kind，以及为什么它必须广播

`ApprovalTokenRedeemed`（烧票那行）是第 8 个 kind。两个决定：

- **`action` 仍是 `"approval"`，不开第 11 个 action 值。** 十值枚举和 events 表一样是 append-only
  口径，加值会让所有按 action 统计的报表当场少一批。它在库里的身份靠 `payload.kind`。
- **写这行必须走 `publishPersisted`。** `events.id` **就是** SSE 的 `seq`：
  只写行不广播，等于**消费了一个 seq 而不发出它** ⇒ 活着的订阅遇到空洞 ⇒ `link: stale`。
  于是「远程批一次，连接标脏一次」。这就是 `publish` 在这一发里是**必填参数**而不是可选项的原因，
  也是 `real-deps.test.ts` 那发「广播必须在 commit **之后**、seq **等于**那条审计的 `events.id`」
  的由来（配一发反向对照：在 publish 里回读 `used`，读到的是 `[1]`，
  证明「事务里广播」这个坏写法能被区分出来）。
- 它**不进任何角色的记忆**：烧票不是一个决定。这一条靠 `role-memory.ts` 的显式过滤，
  而那个过滤今天有真分母了（0016 §4 那两发之前是没有的）。

## 7. 留给 CEO 的一项决定：远程端自己拿不到票

门二（签票只收回环地址）是**我自己拍的**，理由：一次性票的兑换端点必须能被远程访问
（手机要点「批准」），而**签票**端点如果能被远程访问，就退化成
「一张票换一张票」—— 一次性这个性质当场失效，而它是【规格】§11 那条承诺的全部内容。
这条不需要任何人同意就该这么做，所以拍了。

但它的**产品后果**不该我拍：**手机 / 远程 App 现在没有任何办法自己拿到那张票**。
今天的流程只能是「本机桌面上点『生成一次性链接』→ 把 token 送到手机上 → 手机兑换」。
三个走法：

- **A. 就这样。** 桌面是本机的、签票天然是「人坐在这台机器前」这个动作。
  代价：手机单独在外的场景下，远程审批**根本走不通**，而 §19.1 那条「20 秒完成一次审批」
  承诺的正是那个场景。
- **B. 远程只许「问我要票」，票由桌面推送。** 多一条推送通道（Task 4.4 飞书 / 4.3 App 推送），
  签票仍只发生在回环。安全性质不变，代价是**多一条出站集成**才能用。
- **C. 给远程一个受限签票面：只能给『已经推到我手机上那张卡』签票，且有次数上限。**
  体验最好，代价是**引入一个新的凭据层级**（它必须比兑换票强、比桌面 token 弱），
  而今天这条通道上还没有第二个凭据类型。

我的倾向是 **B**：它不改安全性质，而 A 让「远程审批」这个卖点只在人在电脑前时成立。
这条是产品定位问题（远程审批到底服务谁、在什么场景用），不是实现选型，**所以不代拍**。
