# 0060　一条永远达不到的验收被读成「这项没做完」—— 而我把自己的错误原因写进了下一篇决策记录的正文

- 状态：已接受
- 关联：0016 §1（本篇推翻它第 1 条量的那件事）、0013 §10（「数据在判定现场存在、落库那一刻消失」）、
  0014 §3（一个零调用方的模块让一句现在时断言过期）、0042（判据住在哪一侧 / 「给有判据的那两半，并明写缺的是哪一半」）、
  0056 §1（恒不可能通过的验收命令）、0058 §4（死因表：红的时候要知道是谁杀的）、
  0053（判据吃进了讲它的那句话）、0006 §7（两份抄本）、0020（「这个字段没人读」能说到多强）
- 范围：优化设计文档 O3 的三个动作 —— 记忆进提示词之后，「这一格是空的」怎么在**数据里**可见，
  以及为此换掉的那条判据、那一条被写错的验收、和两发我自己写错的注释。

> 起点是 O3 的验收第 2 条：「**actor 为 `system` 的角色决定行必须为 0**，今天它红，动作 2 做完它绿。」
> 我去把它做成绿的时候发现：这一条在一台正常运行的 Hub 上**永远不可能绿**，
> 因为它把「有件事等着人批」数成了「有个决定没署角色的名」。
> 它不是"还没做到"，它是**判据写错了** —— 而这种错的红方式是"进度落后"，
> 会让下一个人在一条不存在的缺口上再花一轮。
> 更糟的是我在记录这件事的时候，**又犯了一遍本仓那一条反复登记的错**（§5）。

## 1. 一句话

| | 我按字面以为的 | 实测 |
| --- | --- | --- |
| 「actor 为 system 的角色决定行 = 0」 | 一个待修的署名缺陷，今天非 0 | **永远达不到**：`action='approval'` 底下混着 `ApprovalRequired`（**请求**）与 `ApprovalDecided`（决定）。四处生产者把请求署成 `system`/`hub` 是**对的署名**（没人做这个动作，是流程停下来了）。换掉判据之后这一格**今天的读数是 0** —— 它从来没红过，红的是判据 |
| 「先修 actor，否则按 `actor_id` 查记忆恒空」是动作 1 的前置条件 | 有一步没做，做完全档都有数据 | 这句话在 `review_decision` 这一档**从来没成立过**。引擎那一轮做成的审阅判定署的是 `agent` + 审阅者本人的角色名（`engine/dispatch.ts`）；而图中间件写的那种"没署名"的行是 `state_change`，**根本不在** `MEMORY_ROWS_SQL` 的 `IN ('approval','review_decision')` 里 ⇒ 它对记忆**一个数都不影响** |
| 「`memoryCoverage` 进 `GET /today`」 | 接上去就行，字面做得到 | 接上去是 680 ms（50 万行 events，本机）。**加 `(action, actor_type)` 索引后仍然 180 ms** ⇒ 瓶颈是逐行解析 JSON 而不是缺索引，而 `events` 只增不删 ⇒ 这一发**随行数无界**变慢，落在每天必开的那一页。改成交一份**不碰 JSON 的有界探针**（3.6 ms），报**行数**不报**决定数** |
| 「仓库里那发测 coverage 的用例在测署名」 | 它红是因为我改坏了 | 它的**名字**说的是图那种 `state_change` 行，而那种行在这里一个数都不影响；让 `unattributed` 变成 1 的是夹具里**后面那条 approval**，且它是**请求**。这一发一直在**断言一个错的行为**，还带着一个描述另一件事的名字 |
| 「is_decision 折成组内 `MIN(CASE…)` 更省事」 | 一组里不会混，折起来等价 | 等价性挂在**组键的生产者巧合**上（今天 `system/hub` 那一组恰好只有请求）。哪天真有一路用默认 actor 写出一条决定，`MIN` 会把**整组**报成非决定，而 coverage 报出的仍是一个自洽的假分布。改成 GROUP BY 的**维度**；这一条是在**跑任何测试之前**自己纠掉的，而它后来有变异体证明（§4） |

## 2. 判据换掉的那一步：分子与判据不许分处两处

`is_decision` 这条判据原来只活在 SQL 里（按 `actor_type` 数），而 JS 侧的分类器
`classifyMemoryRow` 有**两条各写一遍的 if**（一条挡 `ApprovalRequired`、一条挡
`ApprovalTokenRedeemed`）。这就是本仓抓过最多次的那一族：**同一句话抄两遍，
各自收窄一次就永久失真**。

落地：

```ts
export const NON_DECISION_EVENT_KINDS = [
  { kind: "ApprovalRequired", label: "要求批准" },
  { kind: "ApprovalTokenRedeemed", label: "一次性凭据被消费" },
];
// SQL 侧从同一张表构造，不是抄一份字面量：
const NON_DECISION_KIND_SQL = NON_DECISION_EVENT_KINDS.map((e) => "'" + e.kind + "'").join(", ");
```

三条值得单独说的：

1. **失效方向是「算作决定（保留）」**。这条判据答的是「这一行要不要计入决定数」，
   认不出来时**保留**：宁可 coverage 多报一条决定，不可把一条真决定悄悄丢掉 ——
   后者会让「未署名决定 = 0」这句验收在**有缺口时**读起来像没缺口。
   与 0008 的「判不出 ⇒ escalate 而非 pass」同一条轴。
2. **`is_decision` 是 GROUP BY 的维度，不是组内折叠**（上面表里第 5 行）。
   这条改完之后有一条断言专门钉它：`rows.filter(r => r.actor_id === "hub")` 长度是 **2**
   （同一个 `action × actor_type × actor_id` 组里，请求与决定**各占一行**）。
   折叠写法下这一发红 —— 这是本篇唯一一个「我改之前就想清楚了、改之后有分母」的设计决定。
3. **判据读 `payload.kind`，不读 `action`**。为什么不用 `action`：
   `KIND_TO_ACTION` 是一个 kind 一个 action 的**满射不完射**，
   而 §22.1 那个十值枚举是 append-only 的口径 —— 加一个 action 值会让所有按 action
   统计的报表当场少一批。所以 `ApprovalRequired` 与 `ApprovalDecided` **共用** `approval`，
   区分它们的唯一位置就是 `payload.kind`。这个"共用"不是偷懒，是那张表上写着的价格。

## 3. 成本这一栏：那条「加索引后仍然 180 ms」才是结论

优化设计文档写的是「`memoryCoverage` 进 `GET /today`」。我照字面接过一遍，然后量了：

| 查询 | 37.5 万行 | 50 万行 |
| --- | --- | --- |
| `memoryCoverage` 全表（带 `json_extract`） | — | **680 ms** |
| 只数未署名决定（带 json） | 186 ms | — |
| 同上，**新加 `(action, actor_type)` 索引之后** | **180 ms** | — |
| 不碰 JSON 的 `COUNT`/`SUM` 扫描 | **3.6 ms** | — |
| 存在性 `WHERE action=… LIMIT 1` | 0.03 ms | 0.03 ms |

**承重的是第三行。** 前两行合起来只能推出「JSON 慢」，而那是个谁都会猜的答案；
第三行把它钉成「**加索引救不回来**」，因为 `json_extract` 用不上任何索引，
成本是**每一行解析一遍**。剩下的 3 ms 差异是扫描顺序的边角。

⇒ 结论不是「这一发有点慢，先这样」，是「**这一发的成本随行数无界增长**」：
`events` 是 append-only，仓里**没有任何** events 的 DELETE 或归档路径。
把一条 O3 的验收接成那样，等于用一个真缺口换一条永久变慢、且**明年更慢**的东西。

落地的是 `readMemoryTodayProbe`：一次查询、三条 `SUM`、不碰 payload，
报 `scope_rows` / `gate_rows` / `gate_unattributed_rows` 三个**行数**。
它敢不碰 JSON 靠的是一个**命题**而不是一个直觉：
「映到 `review_decision` 的事件 kind 与 `NON_DECISION_EVENT_KINDS` 交集为空」
⇒ 这一档"是不是决定"恒真。精确数仍在 `memoryCoverage`（门禁与诊断跑那一面）。

⚠ **三条 `SUM` 共用一条 SQL** 不是省两次往返，是为了不在三次查询之间夹进一次写入
（0042 那条同一立场）—— 分三次发会得到一份自相矛盾的今日视图，
而那种矛盾**只在并发下出现**，也就没人能复现。

## 4. 十二发变异，以及**谁**杀的

| 变异 | 结果 |
| --- | --- |
| `renderMemoryBlock` 恒返回空块（**O3 验收第 1 条原话那一发**） | 红（全量 13 发） |
| `unattributed` 写成恒 0 | 红 |
| `is_decision` 从 GROUP BY 折成组内 `MIN` | 红，报 `expected +0 to be 1` —— 正是注释里预言的方向 |
| 探针三条 `SUM` 各改一格 | 红 ×3 |
| 探针零行不兜 0（让 `null` 透传） | 红 |
| `today.ts` 三条 notes 分支各断一支 | 红 ×3 |
| notes 里的 `scope_rows` 数字写死 | 红 |
| `dispatch.ts` 换成硬写 `action: "review_decision"` | 红 |

「全杀」这句话**只覆盖这张表列出的形状**。没有闸门的那一半同样写出来：
`KIND_TO_ACTION` 若新增一个映到 `review_decision` 的事件 kind，那一档的语义自己变了，
而**没有任何一发会红**（枚举交集那条命题仍然为真）—— 那种变更靠 `recorder.ts`
上「加 kind 时回看这里」那条注释。

⚠ **另有一批数字不能复用**：这一格之前我跑过两版变异脚手架
（`.tmp/o3/mutate.mjs` / `mutate2.mjs`），它们的**红/绿判定本身是错的**
（变异写失败时脚本照样记 KILLED），报出来的"杀掉数"里含假阳性。
本篇表里每一发都是**改完文件确认内容变了、再跑全量、按退出码判**重跑过的。
"变异测试"这个词不能替这一句背书。

## 5. 我在记录这件事的时候，又犯了一遍本仓登记过的那个错

上面那张表的第 1 行杀掉了 13 发，其中 5 发在 `memory/prompt.test.ts`。
我在设计文档里写下的是：

> 这一发的分母不在主断言里 —— 那几发有一半靠**反向对照**才红。

**这句是推理出来的，没测。** 推理链是「`prompt.test.ts` 测的是四条路径各说什么话 ⇒
渲染变空 ⇒ 话术仍然会说『有 N 条但一条都没给出』⇒ 主断言大概成立 ⇒ 那是反向对照杀的」，
每一步都像真的，而结论是假的：实测那一发的失败信息是

```
AssertionError: expected '你在这个 hub 里做过 1 次可参考的决定，但这一块【一条都没给出】…'
                to contain '历史决定'
```

红的是**主断言本身**。真机制值得记，因为它是**模块之间互相兜底**的一个例子：
`renderMemoryBlock` 恒返回空块时，`memoryPromptSections` 不跟着返回空串，
它走进自己那条「有候选行而一条都没进块」的分支，于是那句话变成了
「一条都没给出」，而用例找的是块里的内容。
⇒ 杀掉这个变异体的是**渲染块与话术块之间那道"话必须跟着数据走"的契约**，
不是任何一条专门为此写的反向对照。

这件事的形状：**我在写「要知道是谁杀的」（0058 §4）那一条的同时，正在没测就写下是谁杀的。**
发现它靠的是准备给那句话找一个"5 发里哪几发"的明细，而不是靠想到了要检查它。
⇒ 一条关于**归因**的纪律，其自身也是**待归因的**。以后凡是写下「红的是 X 而不是 Y」，
必须有一条贴出来的失败信息，否则那句话只能写成「我不知道是谁杀的」。

## 6. 注释当承诺：写了「有一发测试会先红」，而那发不存在

`today.ts` 里我写下过这句：「`role-memory.test.ts` 里有一发拿真库同时读这两面 ⇒
真出现那种行时是**它先红**，不是界面先说谎。」

写完就去跑测试了。而当时**那一发不存在**：⑦ 节第一发拿的是我手搓的夹具，
它能证明「两条 SQL 的口径没写岔」，**证明不了**「生产库里没人硬写
`action: "review_decision"`」—— 那一天 `today.ts` 会多数，
而我写在注释里的那句"会有人先红"就是**一句空头承诺**。

补上的那一发扫全仓 src（剥掉注释之后，0053 那一族）断两件事：
硬写 `action: "review_decision"` 的地方 **= 0**；
`action: KIND_TO_ACTION.ReviewDecided` **恰好 1 个文件**。
把 `dispatch.ts` 改成硬写 ⇒ 这一发红（§4 表里最后一行）。

代价也说清楚：这一发**认字面**，拼变量或换引号就扫不到。
选它而不是「跑一次真 dispatch 看真行」的理由是命题种类不同 ——
后者只能证明**它跑到的那条边**写对了，而我要的是**全仓没有第二个形状**，
那是一个存在性命题（同 `docs/review/verify-open-invariants.mjs` 的立场：
一次运行证明不了不存在）。

⇒ 记一条：**注释里凡是写「有 X 会先红」，X 必须已经存在且能指到那一发的名字。**
写不出来的那一半要么别说，要么写成「这里没有闸门，靠人不改」。

## 7. 顺带撞开的三件事

1. **`dead-modules` 的基线少了一格**：`memory/role-memory.ts` 的 `CrossRoleScope`
   在基线里登记为"零调用方"，而 `rolePrompt` 一旦 import `readRoleMemory`，
   那个模块整体就可达 ⇒ 基线条目要删。**基线在模块粒度，缺口在函数粒度**，
   所以这不是误报也不是漏报，是这道守卫的分辨率本来就在这里。
2. **`doc-refs` 第【六】次抓同一件事**，这一回抓了 8 个坐标
   （`role-memory.ts` 691→803 / 506→587 / 622→703，`today.ts` 108→111 / 293→338 / 294→339 / 55→58）。
   ⚠ **按 diff 行数推算必错**：同一文件里三格的增量**不同**（+112 / +81 / +81），
   因为中间还夹着别的改动。每个坐标都要 `sed -n '<n>p'` 重读一遍再抄。
   快照内容也变了一处：`has_review_decisions: rows.some(…)` → `decisions.some(…)` ——
   判据换了，被引用的那一行**必然**跟着变，而那次红正是该重读 0016 §1 的时刻。
3. **两条更老的断言确认过期**（不是本篇改的，是量出来的）：
   0041 的「`HUMAN_EDGES` 零调用方」与「`approval_type='charter'` 零生产者」
   分别被 0043/0048 与 `engine/charter.ts` 推翻；
   0026 的「`createCard` 零调用方」**仍然为真**。
   ⇒ 一篇决策记录里几条并列的实测，**会各自以各自的速度过期**，
   而读的人默认它们同生共死。

## 8. 留在原地没做的

- **`review_gates` 那张表仍然零 INSERT**。本篇把 `events` 那一半接上了，
  而 `db/integrity.ts` 那条自检念的就是那张表 ⇒ §22.4
  「每个门控决定都有证据包引用」**依旧无从校验**：判定有审计行，
  审计行里没有指向证据包的引用。这是 O4 动作 4 的射程，不在本篇。
- **`policy/auto-approve.ts` 仍然零生产调用方**，所以本篇换完判据之后
  「未署名决定」这个数在生产上是 0，而这个 0 的含义是【这条链路没接】
  而不是【没人代做决定】。这句话现在跟着数一起出现在 `memoryCoverage.unattributed`
  的注释与 `GET /today` 的 notes 里 —— 一个裸 0 在这一页永远是假的。
- **探针那三个数还没有 UI**：它们进响应（`GET /today` 的 `memory` 那一格，
  键名集合被钉住），而 desktop 侧还没渲染它们。
- **`gate_unattributed_rows` 与 `unattributed` 是两个口径**，
  代码注释里各写了别拿对方去对 O3 验收，但**界面还没有并排显示它们**。
  并排显示之前，"这一格会不会被读错"这件事只能靠注释。
