# 0002　不接入个人微信（这条排除是承重的，不是偏好）

- **状态**：已定案　**决策门**：规格 §25-D1「IM 接入优先级」里的一个选项，不是独立决策门
- **产出**：计划 Task 4.6（该任务唯一的产出条目）
- **拍板方式**：规格 §11.2 / §11.5 已写明「不接入」，执行方不重议；本篇把理由与**边界**钉下来，
  让「以后顺手加个微信机器人」这句话在提出时能立刻对上「先读 0002」。

## 0. 为什么这篇要单独存在

一个「不做某件事」的决定，如果只活在对话里，等价于**没送达**：下一个人（包括半年后的我）
看到 `im_bindings.platform` 那一列，只会看到它是个 TEXT，看不出「微信」是被排除的而不是还没做的。
规格 §11.2 那行「**不接入**」在文档里，但那一行读起来像一句备注，不像一条决定。

所以本篇的价值不是「记录一个理由」，是把这条排除**变成可 grep 的东西**，
并写清它的**边界在哪** —— 因为「不接入个人微信」这句话很容易被过度引申成
「不做 IM 集成」，而事实恰恰相反：Phase 4 整段都在做 IM 集成。

## 1. 排除的是什么，不排除的是什么（先把边界画死）

| 说法 | 在本篇里是否被排除 |
|---|---|
| 个人微信（协议逆向 / 逆向 Web 协议 / `oicq` 类第三方库挂个人号） | **排除** |
| **企业微信**（自建应用 API 收发应用消息） | 不排除，规格 §11.2 列为**次选通道** |
| **QQ 官方 Bot 开放平台**（AppID/AppSecret，WebSocket / WebHook） | 不排除，规格列为**只读查询通道** |
| **飞书**（企业自建应用 + 长连接收事件） | 不排除，是**首选审批通道** |

⚠ 「企业微信」与「个人微信」只差两个字，而它们**不是同一类产品**：
前者是有官方 API、有企业主体、有回调签名的服务端集成；后者没有官方个人号 API，
任何接法都是逆向登录协议。本篇只否后者。把两者混为一谈会让这条排除看起来
比实际更保守，也会让「企微要不要接」这个问题被误答。

## 2. 三条理由，以及它们此刻各自能被核验到什么程度

按本仓的纪律，「写进文档的理由」要区分**我量过的**和**我引用的**。这一节逐条标注。

1. **没有官方个人号 API。** —— 这是**结构性事实**，不是工程难度：
   规格 §11.2 给四个平台各写了「接入方式」，个人微信那一格填的是「**不接入**」，
   而其余三格填的是可执行的接入方式（企业自建应用 / 自建应用 API / 官方 Bot API）。
   我能在仓库内核验到的部分是：**规格里没有任何一处给出个人微信的接入方式**。
   核验不到的部分我也照写：我此刻**在离线环境**（本机 `npm view oicq` 超时、
   registry 取不到，见 §5），所以「微信没有开放个人号 API」这件事我引规格而不引官方文档，
   并且不假装我刚刚验证过它。

2. **`oicq` 一类社区库停更。** —— 这条**引计划 Task 4.6 的原话**（「`oicq` 类库自 2022 年停更」），
   本篇**不把它写成我的实测**：我想核验它（最后一次发布时间），但本环境无网络，取不到。
   写成「2022 年停更」并且不标出处，它就会在下一次被引用时变成一个「仓库里已验证的事实」——
   这正是 0019 §5 那一族错（把一次没复现的观察写成机制）的形状。
   **它需要的核验动作很小**（一次 `npm view oicq time.modified`），
   所以这一条的正确处理是「留给有网的人顺手补」，而不是我替它背书，也不是把它删掉。
   方向上这条不是决定性的：决定性的是第 1 条与第 3 条。

3. **封号代价落在 CEO 的个人身份上，而且不可逆。** —— 这一条是**本篇的主理由**，
   因为它把技术方案问题变成了一个**代价归属**问题，而代价归属是本仓唯一硬的判据。

## 3. 真正让它区别于其他技术选型的，是第 3 条的形状

本仓几乎所有风险都在**组织内部**：慢查询冻住主线程（0019）、备份挤掉好备份（0018）、
静默停滞没人报（0019 §2）。这些坏了，损失在公司范围内，可以由工程侧决定承担。

个人微信逆向接入不是：**冒风险的账号是 CEO 的私人账号，不是公司的资产。**

| 维度 | 其他通道（飞书 / 企微 / QQ 官方 Bot） | 个人微信逆向接入 |
|---|---|---|
| 违反的东西 | 无（走官方 API 与权限模型） | 平台服务条款 |
| 被处置的对象 | 一个可替换的**应用**（应用被封→换一个应用） | 一个**人的账号**（含全部私人关系与聊天记录） |
| 处置的触发方 | 我们自己（配额、权限申请） | 平台风控，**我们看不到判据也无法申诉到有意义的地方** |
| 触发时机 | 集成当天就暴露 | **用得越久风险越高**：接入成功≠安全，只是还没轮到 |
| 可逆性 | 可回退 | 账号被封即不可逆，且不可逆的是**私人社交关系** |

最后一行是重点：**「接入成功」在这一类方案里不是里程碑，是还没出事。**
一个正常的集成跑通了就是跑通了；一个逆向接入跑通了，只意味着风控还没注意到它，
而我们正在把 CEO 的私人账号往「值得被注意到」的方向用（消息量上升、时段变规律、
出现自动化特征）。这与本仓处理「静默」的一贯立场同形：
**失效不报错、只在累积之后一次性兑现的东西，不能靠「现在还好」来判断。**

还有一个具体的错：这个决定**不该由工程侧替 CEO 承担**。
「要不要拿你的私人账号冒封号风险」不是一个技术问题，问错了对象就是一个越权动作 ——
而本仓对越权的默认处置是 fail-closed（0019 §4 第 2 条：越权重试没意义，因为它第 N 次仍然越权）。

## 4. 这条排除已经承重了（不是空话，可 grep）

排除落到代码里的形状，比它写在文档里更硬：

- **`im_bindings.platform` 那一列的注释枚举的是 `'feishu'|'wecom'|'qq'`**
  （`packages/hub/resources/migrations/0001_init.sql:251`，逐字取自规格附录 C）。
  也就是说 `events` / `im_bindings` / `im_tokens` 这套形状从第一天起就没有给个人微信留位。
  **它是一份【看起来开放】的 TEXT 列，这才是需要写这篇的原因** ——
  schema 不拦一个 `platform='wechat'` 的 INSERT，拦它的是这条决定 + 这条注释。
- **`packages/hub/src/http/auth.ts` 文件头**写明了 IM 侧的凭据模型是「签名 + 一次性 token，
  落 `im_tokens` 表」，对应的是「飞书卡片回调」那条路。
  逆向接入**给不出签名**：它模拟的是一个客户端在登录，不是一个服务在回调，
  所以它接不进规格 §11.4 那条安全约束（IM 审批必须签名验证 + 一次性 token）。
  **这一条比封号更硬**：就算明天出现一个「绝对不封号」的微信个人号库，
  它也无法满足本仓对审批通道的基本要求 —— 一个不能证明「这条批准来自 CEO」的通道，
  不能承载审批。
- **`NormalizedMessage` / `ApprovalCard` 那层抽象（规格 §11.3）已经存在**，
  意味着「再接一个平台」的成本被压在一个适配器里。
  于是这条排除**不会**给未来加通道带来难度，它只排除这一个通道。
  如果它没被排除，接它的代价也就一个适配器 —— 所以本篇的全部重量必须落在 §2/§3 那三条理由上，
  不能落在「成本高」上（成本高是个会被推翻的理由，代价归属不是）。

## 5. 我没做到什么（不写成「换种方式做到了」）

- **`oicq` 停更这件事我没验。** 本环境无外网，两次尝试都拿不到东西：
  `npm view oicq time.modified version dist-tags` 挂满 60 s 后被转入后台、
  最终以**零输出**结束（不是「返回了一个旧时间」，是一条字节都没有）；
  改走 `fetch(registry.npmjs.org/oicq)` 直接报 `The operation was aborted due to timeout`。
  所以第 2 条理由在本篇里的地位是**引用**，带出处，不是一个已核验的事实。
  **补法**：有网时跑那一条命令，把结果写进本篇第 2 条并删掉这段。
- **飞书 / 企微 / QQ 三个通道的代码都还不存在**（Phase 4 的 Task 4.1–4.5 依赖 D9 + 网络）。
  本篇排除一个通道，不产出任何通道。今天 `im_bindings` 与 `im_tokens` 两张表是
  **零生产写入**的（与 0013 §10.1 那个「`approvals` 零 INSERT」同一格），
  所以「排除个人微信」此刻的实际效果是**防止未来有人从这里开始写**，而不是挡住了一条在跑的路。
- **规格 §25 第 1 项（IM 接入优先级整体）仍未拍板**（0006 §11 那条入口条目里登着）。
  本篇只固定它的一个子选项。剩下那半 —— 「若协作网络完全不在飞书，是否退到只做 Web PWA +
  Web Push」—— **不是本篇能替它回答的**，因为那一问里根本不含微信。

## 6. 什么时候这篇需要被重读

不是「有人又提议接微信」的时候（那直接驳回即可），是下面三种：

1. 有人提出**用某个具体的第三方「微信机器人」SaaS**（付费、号称合规）。
   这一类不在本篇覆盖范围内，需要重新判：它可能是**企业微信的接入服务商**（那就落到 §1
   的「不排除」那一侧），也可能是代托管个人号（那还是本篇排除的东西，只是把风险外包给了
   一个我们看不到实现的服务商 —— 而「外包风险」在本仓从不消灭风险，只让它更难核对）。
2. `im_bindings.platform` 要改成枚举或加校验。那一刻需要把本篇 §4 那条注释一起改成**机器可判**的，
   否则 TEXT 列的「看起来开放」会一直留着。
3. 真出现一个**官方**的个人微信机器人 API（此前没有）。那会同时拆掉 §2 第 1 条与 §4 第二条
   （签名可谈），本篇应当被**改写**而不是被引用。

## 7. 我自己在这篇里写错的一处

**我把表名写成了 `im_binds`，真名是 `im_bindings`**，而且是在 §4 那条「这条排除已经承重」的论证里 ——
也就是本篇唯一一处拿 schema 当证据的地方。
抓它的不是我，是 `test/arch/doc-refs.test.ts`：那条 `文件:行号` 引用进快照时它对不上目标行。
**但要点不在「守卫抓到了」，在我当时为什么会写错**：我从 §4 那条注释的**语义**
（「platform 那一列枚举了三个平台」）反推出了一个表名，而没有去 `grep CREATE TABLE` 看它叫什么。
读起来完全顺、看起来也不需要查 —— 这正是本仓那一族错（凭印象写事实）的形状，
而它这次落在了一篇**主题是「不要把没验过的理由写成事实」**的文档里。

同类还有 §2 第 2 条（`oicq` 停更）：那一条我**做对了**（标为引用 + 写出补法），
因为它涉及的是外部世界；表名这条涉及的是仓库内部，而我对仓库内部的【记忆】
同样是没验过的来源（0019 §5 第 13 条记过同一句教训，这次是它第 N 次现形）。
差别只在外部世界我手边没有工具、仓库内部我有工具而没用。
