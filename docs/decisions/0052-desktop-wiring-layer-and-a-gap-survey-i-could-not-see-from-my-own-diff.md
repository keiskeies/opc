## 1. 桌面壳缺的那一格，早就有人声明过而没人与过账

`main/channels.ts` 的 `dispatch()`、`ipc-surface.ts` 的通道表与参数闸门、
`preload/api.ts` 的 `onHubEvent()` —— 这三样都写完了，并且各自有测试、各自绿。
而 `MainDeps.signedFetch` 这个**把它们接到 Hub 上的字段**，全仓没有任何一处实现它，
唯一存在的东西是 `test/desktop/ipc-surface.test.ts` 里那个返回固定 JSON 的桩。

同理 `channels.ts` 的 `toPushPayload()` 和 preload 的 `onHubEvent()` 两头都在，
中间的「谁去开那条 SSE、谁把帧递过去」是空的。

两个形状是同一个：**两端各自绿着，中间是空的**，而且中间那一格只被声明过、
从没被记进任何一篇文档的待做清单 —— 所以没有任何一次 `git log` 会提醒它没做。

我这轮的判断：桌面壳今天起不来，缺的**不是** `app.whenReady()` + `new BrowserWindow()`
那两行胶水，是这两格。胶水接上一个没有实现的 fetch，得到的是一扇打开之后每一页都转圈的空窗。
所以先补中间，再谈胶水（胶水仍然没补，见 §7 第 1 条，那是有前提的）。

落了三个文件：

| 文件 | 补的是哪一格 | 测试 |
| --- | --- | --- |
| `packages/desktop/src/main/signed-fetch.ts` | `MainDeps.signedFetch` + 事件流要用的 `signedHeaders()` | `test/desktop/signed-fetch.test.ts` 17 发 |
| `packages/desktop/src/main/event-stream.ts` | SSE → 渲染进程的那条推流桥（含游标续订、退避、停） | `test/desktop/event-stream.test.ts` 23 发 |
| `packages/desktop/src/main/wire.ts` | 装配点：invoke 路由表 + 事件流 + 生命周期 | `test/desktop/wire.test.ts` 16 发 |

三个都不 import electron。这是**必须先付的代价**而不是风格选择：electron 装不上（离线），
而 `test/arch` 里 `tsc -p packages/desktop` 是 0 错的那道闸门一旦见到 `import "electron"`
就整包报 TS2307 —— 那道闸门刚刚在本轮抓出过两个真错（§6），我不能为了少写一个
`IpcMainLike` 接口把它关掉。

三件在实现里改了决定、值得留字的东西：

1. **`fetchImpl` 是必填的**，没有 `?? globalThis.fetch`。理由三条叠在 `signed-fetch.ts` 文件头，
   核心是：本机离线的 `@types/node` 把 undici 的 `Response` 解析成一个**零成员**类型，
   所以"用全局 fetch"这件事在这台机器上会报成「你的代码写错了」（TS2339）而不是「你缺依赖」，
   而一个 `as` 就能把它压掉 —— 压掉的正好是本文件唯一那条"编译过而线上炸"的兼容假设。

   `tsc -p packages/desktop` 在这一格里拦住的**两个真错**值得点名（`wire.ts` 文件头那条
   "别关掉这道闸门"的论据就是它们）：① `?? globalThis.fetch` 报 TS2339；
   ② `body: undefined` 撞 `exactOptionalPropertyTypes`。
   两个都能用 `as` 压掉，而压掉之后的表现都是**线上第一次 invoke 才炸**，
   症状与"Hub 没起来"同形 —— 这就是为什么这两条我留在类型层而不是写成注释。
2. **事件流不能用 `signedFetch`**。它的形状是 `{status, bodyText}`，整段缓冲，装不下一条活着的流
   （`web/src/dev-server.ts` 里同一判断，那边靠 `r.pipe(res)`）。所以签名头抽成
   `signedHeaders()` 两处共用。这一格如果各抄一份，漂了的形状是
   **「只有断线续订 401，而普通 JSON 请求全好」**—— auth.ts 与 dev-server.ts 各记过一次同一个死法。
3. **`invokeChannels()` 从 `CHANNEL_SPECS` 里筛，不手抄通道名**，而 preload 那份名单是手抄的。
   两边写法刻意相反，理由也刻意不同：preload 那份是**安全边界**（少一个键就少一个入口），
   wire 这份是**路由表**（少一个通道就调不通）。同一个"抄"字，两处的失效方向不一样。

## 2. 三份变异实验：33 发里 3 发逃掉，而逃掉的三种成因各不相同

按 0051 §5 立的规矩跑（锚点命中次数当场断言、只读 `ℹ` 三行、每发逐字节还原比对）。

| 批次 | 发数 | 抓到 | 没抓到 | 无效 |
| --- | --- | --- | --- | --- |
| `signed-fetch.ts`（重构后） | 12 | 11 | 1 | 0 |
| `event-stream.ts` | 15 | 15 | 0 | 0 |
| `wire.ts` | 11 | 10 | 1 | 0 |

先说**无效**那一列，因为它差点被读成成绩。第一轮 signed-fetch 的读数是
「抓到 7 / 没抓到 0 / **无效 5**」—— 那 5 发是我把签名构造从 `makeSignedFetch`
抽进 `signedHeaders` 时**搬走了锚点文本**，脚本什么都没改就跑完并交出结论。
如果我只读「没抓到 0」那一句，会写下"12/12"。修复后重跑才是上面那行。

三个没抓到的，**成因不是一种**，分开记才有用：

**① signed-fetch M9「空 token 那次放行」—— 我的测试只走了一条路。**
`assertUsableToken` 有两次调用时机（构造时、每次签时），而 17 发里没有一发直接调
`signedHeaders`；event-stream 的 23 发全部注入固定 token。也就是说：
「事件流那条路会不会把空 token 一路带到线上」这一族**在两个测试文件里都不存在**。
这不是断言太松，是**分母里没有这一族**。补法见 §7 第 2 条（我没在写这段的当口顺手补，
是为了把这条结论原样交出去，而不是补完再回来说"本来就覆盖了"）。

**② event-stream M2/M3「push 抛了还推进游标」—— 真的漏了实现。**
`push` 当时完全没有保护：从 `res.on("data")` 回调里抛出去的东西没人接，
而游标照推。这两发逼出来的改动是**生产代码**（`emit()` 返回布尔、
`if (emit(...)) cursor = seq`）加三发新测试，不是加断言。
顺带暴露第三条：那两行旁边的注释写着一个**我没量的推断**，见 §5。

**③ wire W4/W6/W8 —— 我的断言读的是我自己的内部状态。**
`running` 就是 `stream !== null`，所以"stop 之后 running 为假"这条断言
在实现坏掉时**照样绿**（我把 `stream?.close()` 换成 `void 0`，全绿）。
这是本仓第 N 次撞上「只会绿的断言」，修法不是加断言而是**换观察者**：
让服务端数 `connections` 与 `close` 事件，再补一个 `silentlyDrops` 模式的假 sender
（窗口销毁而 `send` 不抛，这是 electron 里真实的一种）—— 之后 W8 交出的是
"socket 上真的少了一条连接"，不是"我脑子里的变量变了"。

**外加一条等价变异**：`wire` W10（`req.end(init.body)` 里 body 是 undefined）抓到 0 红，
但那次**不是覆盖不足** —— `req.end(undefined)` 与 `req.end()` 发出的字节完全一样，
是**等价变异**。按 0051 §5 的规矩，这一条用直接测量收（对比两条请求的线上字节），
而不是"写一发测试让它红" —— 后者会造出一发永远不可能失败的测试。

## 5. 我发表了一句没量过的话（第二次在同一族上）

`event-stream.ts` 里那句包 try/catch 的理由，我写的是「从 `res.on("data")` 回调抛出去 ⇒
**整个主进程跟着倒**」。那是**推断** —— 形状很合理，我没测。

本轮把它量了（裸 node v24.14.0，`/tmp/opc-probe/throw-in-listener.mjs`）：

| 抛点 | 无 uncaughtException 处理器 | 装了处理器 |
| --- | --- | --- |
| `res.on("data")` 回调里 | 进程 **exit 1** | 存活 |
| `res.on("response")` 回调里 | 进程 **exit 1** | 存活（随后还多一条 `Parse Error: User callback error`） |

所以"必死"这条在 **Node 侧**成立，try/catch 那段理由站得住。
**没量到的那一半写在注释里而不是删掉**：Electron 主进程自己会不会装一个兜底处理器 ——
离线装不上 electron，量不了。所以那句只敢承诺「Node 侧必死」，
不敢写成「Electron 里必死」。这条 try/catch 两条都挡得住，
所以未量的那一半不影响实现，只影响**我敢说什么**。

同族的上一次是 §2 里那个 NaN：我写「`NaN > 0` 是 false ⇒ 每次重连都死在建流上」，
量出来是「每次重连都**不带游标**、于是从头重放一遍」。
两次的共同点不是粗心，是**我把"形状合理的推论"和"我跑过的东西"写进了同一栏**。
本轮起我自己加的规矩：注释里出现"必然 / 整条死 / 一定"这种强度词时，
旁边要么有一条实测，要么写清"这是推断，没量"。

## 7. 待做 / 我判断不该在这一轮做

1. **一份真的 electron main（`app` + `BrowserWindow` + `wireMain`）** —— 这轮刻意没写。
   不是拖延，是它**测不了**：electron 装不上，而写了就是一段永远只有 `tsc` 见过的胶水，
   本仓对"只有编译见过的代码"的口径是先别写。
   现在 `wireMain()` 已经把所有非胶水的东西收进来了，剩下的胶水大约二十行。
2. **`signedHeaders` / `openEventStream` 的空 token 直调测试** —— §2 ① 那一条的实际补法：
   两条路（走 `makeSignedFetch`、走事件流）各要一发「空 token 必须抛，而不是签出必然 401 的头」。
   前者的分母已有，后者**没有**。
3. **`hub:eventsReady` 这个 invoke 通道**（渲染进程挂好监听再开流）。
   现在流可能早于监听者存在，头几条事件落在没人听的地方。
   这是**白名单改动**，必须与渲染进程那一侧的投影同轮落 —— 单独加通道会造出一个
   "能调而没人应答"的入口，那比现在这个形状更糟。
