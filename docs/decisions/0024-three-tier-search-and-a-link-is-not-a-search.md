# 0024　三层搜索策略，以及「包里有链接」不等于「搜过」

- **状态**：已定案（Task 5.7 的判定层）。**传输层今天没有**（§2），所以本篇所有结论的
  强度都是「凡是走这套判据的」，不是「每次搜索都被管着」。
- **产出**：`packages/hub/src/search/policy.ts`、`search/mcp.ts`（一个**接口**，不是 MCP 客户端）、
  `test/search/policy.test.ts`（35 条）、`test/search/mcp.test.ts`（4 条）；
  另在 `packages/contracts/src/evidence.ts` 提出 `isExternalSourceRef`（§3）
- **一句话结论**：【规格】§13.3 第 1 层那句「证据包无来源引用 ⇒ 门控直接打回」
  **编一个 URL 就绕过**，而编 URL 比编覆盖率数字更省事；
  所以这一层真正做事的是那条**观测**判据，而它必须能在**门控**里生效（§4）。

## 0. 这一层没接上线，而且缺的是**两个**东西

`searchPolicy` / `searchEvidenceGate` / `makeSearchCriteriaEvaluator` 在生产里零调用方。
比 0021–0023 那三篇多一层的是：这里缺**两样**，一样能接、一样不能——

1. **传输层**：`SearchTransport` 只有一个方法签名，没有实现（§2）；
2. **观测通路**：第 1 层的强判据要读「审计里搜过几次」，而今天没有任何地方
   把一次搜索落成审计行。这不是「还没写」，是**没有生产者**（同 0014 §3 那条
   「不硬造生产者」的判断：桩出来的审计行是删不掉的伪证据）。

于是第 1 层今天有两种运行状态：**有观测通路时严格**，**没有时 unresolved ⇒ escalate**。
后者是刻意的，理由在 §4。

## 1. ⭐ 计划和规格给的不是同一套三层

| | 计划 Task 5.7 那一行 | 【规格】§13.3 那张表 |
|---|---|---|
| 第 1 层 | 强制搜索 | 强制搜索（该领域无来源引用 ⇒ 门控打回） |
| 第 2 层 | **建议**搜索 | **条件**搜索（Agent 显式判断 + 理由，可审计） |
| 第 3 层 | **禁止**搜索 | **预算降级**（成本达阈值 ⇒ 后续要批） |

按**规格**实现（需求那一层它以 §13.3 为权威，计划是派生物）。计划多出来的「禁止」
我实现成**一条独立开关**而不是第三层，理由是这两者管的不是同一件事：

- 规格第 3 层管**花多少钱**；
- 「禁止」管**这个角色/这类任务根本不该联网**（只碰内部数据、或合规上不许把上下文
  发给外部检索服务）。

合成一层的坏处在报错那一格：禁止若靠「预算设 0」表达，它在审计里**看起来**是
一次预算限制，于是「为什么被拦」是错的（金额问题 vs 资格问题），
而修的人会说出「那我加点预算」——那句话在这个场景里根本不该成立。
两条都钉了用例，其中一条专门钉**判定顺序**（禁止先于预算）。

顺带一条同族的顺序选择：第 3 层在**第 2 层之前**。规格说那一层是「Gateway 强制降级」，
强制的东西不该等 Agent 先表态再生效。

## 2. 传输层：不写一个「看起来是 MCP」的东西

计划要 `@modelcontextprotocol/sdk` 1.32.2 的 Client 加一个搜索 MCP Server（Node 包）。
装不上（0009 §2 那三条通路）。两个选择我都试过形状：

- **写一个假的 MCP 客户端 + 在 node_modules 放桩** —— 否掉。那会把一次临时验证
  伪装成真门禁（仓里已写明这条纪律，且 `vitest` 当年就是这么被要求**不要**塞进去的）。
- **只交出判定侧真正需要的那一个方法**（`SearchTransport.search`）—— 采用。
  于是 `mcp.ts` 今天的价值只有一条：把「搜索由谁提供」收在一个位置，
  让 `policy.ts` 不必知道它是 MCP、内置 WebSearch 还是别的。
  真接 SDK 时改动应当只有「多一个 implements SearchTransport 的类」。

一个具体的收获：`SearchHit.url` 是**必填**而不是可选。如果传输层可以交回一条
没有来源的结果，那「搜索结果必须带来源 URL」那条判据就只能指望 Agent 自己补链接——
而它要防的正是 Agent 不补。**让「缺来源」在编译期就不成立，比在门控里判更省。**

## 3. 「什么算一条外部来源」这个口径必须是**一份**

提 `isExternalSourceRef` 之前，那个正则只活在 `unresolvableClaimIndexes` 里面。
提出来的理由不是复用方便：第 1 层「该领域的包必须带来源」读的是**同一件事**。
两处各写一份正则的话，改一处就会得到「包内引用核对认为算来源、而门控认为不算」——
两边各自自洽、各自绿。与 0022 §3 为 `preventionFor` 写的理由是同一条。

## 4. ⭐⭐ 第 1 层有两个强度，而【规格】只写了弱的那个

【规格】§13.3 的字面要求：**包里有没有来源引用**。这一判据的实际强度是——
`https://never-fetched.invalid/x` 完全合格。而且**编一个 URL 比编一个覆盖率数字更省事**：
覆盖率至少还有个数值范围会被对账，URL 什么都没有。

所以有两条判据，用例把「弱的那条放过的、强的那条拦得住」直接钉成一条断言：

| 判据 | 读什么 | 拦得住 | 拦不住 |
|---|---|---|---|
| `mandatorySourceBlock` | 包里的 URL（【规格】字面） | 完全不带依据的包 | **编造的 URL** |
| `mandatorySearchObservedBlock` | 审计里的搜索次数 | 编造的 URL | 真搜了但没写进包（那种包会被上一条拦） |

两条都留：前者是字面要求，后者才是那句「无来源引用」**想要**的意思。
只留一条的话，留下来的那条给的是它给不了的保证。

### 4.1 「没有观测通路」必须显式，不能靠传 0

`observedSearches` 的类型是 `number | "unobserved"`。如果允许传 0 表示「没看」，
那么**关掉观测通路**就把第 1 层从「要真搜过」降级成「要写个 URL」，
而这条绕过**不需要改任何代码**，只需要调用方不传审计。

接进门控之后这一点更要紧（§5）：那条路径返回 `unresolved` ⇒ 门控 escalate，
**不返回 satisfied**。这是一条刻意的「吵」：CEO 会收到「这条标准判不了」的卡片。

## 5. 「门控直接打回」得**在门控里**，否则它取决于谁记得判

计划那句写的是「**门控**直接打回（不是警告）」。如果判据在门控外面，
那么它拦不拦取决于调用方记得不记得判一次——而 §8.2 第 4 条的立场是门控绑定在边上、
不可绕过。「判据在门控外面躺着」是这一路记过多次的同一族缺口
（`HANDOFF_BUNDLE_TYPES` 曾零调用方、`searchEvents` 曾 22 例零调用方）。

做法是走**已有的注入点** `GateInput.criteriaEvaluator`，内核一行没改——
那个注入点存在的理由就是「内核不解析自由文本，语义由调用方给」（evaluate.ts 文件头）。
`condition` 只认 `search:mandatory_sources` **精确匹配**：
宽匹配会造出「岗位书里写了个近似名字而它其实一次没判」的假防线，
而那比没配更难查（文档看起来是写了东西）。这一格有专门一条用例。

## 6. 我自己这一轮写错的（按被抓顺序）

1. **三次写出「永远不会失败」的断言**，一天之内：
   - `expect("没有返回点的码：" + missing.join(", ")).toBe("")` —— 前缀无条件在；
   - `expect(name + " 应授予").toBe(name + " 应授予")` —— 同一段的自等，我当时是为了
     「报错时看得见是哪个名字」而写的，正好是同一个错误动机；
   - `expect(f("t1")).toBe(f("t1"))` —— 同一个纯函数调用写两遍，注释还写着
     「确定性是回放的前提」，**坏在带着一条看起来在解释为什么需要它的注释**。

   第三次之后我不再靠「下次注意」，改成机械扫：`expect(X).toBe(X)` 同形匹配 +
   「拼接后与空串比」两种形状全仓扫了一遍，扫出这两条（已修）与一条**既有的**
   `expect(true).toBe(true)`（`gateway.test.ts` 末尾，它自己在注释里写明
   「这条断言本身没有信息量，全部作用是让缺口在测试文件里留一行字」——
   那是**声明过的文档行**，与冒充判据的恒绿断言不是一类，留着）。
   教训不是「别写错」，是：**这类断言的成因是给报错加可读性前缀**，
   所以正解是把消息放进 `if (…) throw` 分支里，而不是在 `expect` 的参数里拼字符串。

2. **一条恒绿的夹具断言**（`not.toContain("自测通过")`，而夹具里从来没有那句话）
   与一次**把 transform 输出再 parse 一遍**（camelCase 喂 snake_case schema）。
   两条都在 0023 记过同类，这轮又各撞一次——**记过 ≠ 不会再犯**，
   区别只是这次是当天第二次撞同一族，所以抓得快。

3. **注释里的误授予名字是我编的**。我写「代价是 `resumes` 会被误命中」，
   跑一遍才发现命中的是 `research` 与 `market_research`（`resumes` 不含 `search`）。
   这是 0021 §9 第 13 条、0022 §6 第 5/6 条那一族（**按印象补事实**）的第 N 次，
   而这次的对象是一句我自己刚写的注释里举的例子。
   现在那两个真名字被钉成用例（「它今天确实是 true，而这是代价」），
   `resumes` 钉成 false，免得下一轮又有人按印象把它当误授予写进注释。

4. **一条变异存活，而它不是「这条判据不重要」**。把「观测不到 ⇒ violated」改成恒
   satisfied 之后**零红**：我所有门控用例都用 `observedSearches: 2`，
   于是「有 URL 但没搜过」这条**最该被门控拦**的路径一次都没走过门控。
   正确反应是补一条正向用例（已补，那条变异现在红 3），
   而不是得出「这一支大概没用」。**变异存活定位的是我用例分布的洞，不是判据的价值。**

5. **两处「有返回点吗」没查**：`SEARCH_REJECT_CODES` 初稿里有 `budget_unknown`
   与 `over_search_budget`，而预算那一维产出的是 verdict 不是拒绝；
   `SEARCH_DECISIONS` 初稿里有 `prohibited`，而禁止走的是 block。
   两个都是「取值表里躺着一个取不到的值」——Task 5.4 刚为四个这种码删过一轮，
   **同一个错在同一天第二次撞上**，现在两条都钉成反向断言。

6. **一次把段落标题吃掉的文件编辑**（`describe("码表与取值表"` 那行被当作
   `old_string` 换掉了），以及一次**误诊**：门控那组用例先是六条全红，
   我以为是搜索判据坏了，实际第一条是 `evaluateGate is not defined`（少 import），
   补完还剩两条是**没传 `integrityOk`** ⇒ 门控记一条 unresolved ⇒ 顶成 escalate
   ——正是我几小时前在 0023 §1 里写的那第三个「恒判定」缺陷。
   它第二次以「一整组用例红在无关判据上」的形式出现。

## 7. 这一层证不了的（写在这里而不是等人踩）

1. **「搜过」不等于「读过」**。`hitsToRefs` 落的是传输层给的那条 URL，
   所以链接与实际拿到的东西同源；但 Agent 抄了摘要没读，**结构上不可检**。
   `mcp.ts` 那句注释说「这不解决抄了没读」，指的就是这一格。
2. **观测通路本身可信吗**：审计行由 Gateway 在工具调用时落。
   如果搜索是 Agent 用**未经 Gateway 的通道**做的（内置 WebSearch 直连厂商 API），
   那一发**不会出现在审计里**，第 1 层的强判据就看不见它 ⇒ 报 unresolved。
   方向是保守的（不会假放行），但代价是「用内置搜索的角色每次都要人看一次」。
3. **第 3 层的阈值今天没有来源**。规格只说「取决于金额」，所以阈值是注入的、
   **没有默认值**，而缺省 ⇒ unknown ⇒ 要批。真正上线前得有人（CEO）给那两个比例（§8）。
4. **`searchGranted` 是子串匹配**，`research` / `market_research` 会被误授予（已钉用例）。
   这是一个**放宽**方向，我选了它因为反方向（精确名单）会让「换个工具名」成为
   绕过授予的通路。要收紧就换成显式名单并复核命中面，**别把正则改「准」而没人复核**。
5. **ADR 判据只看引用形状，不看内容**。一份空的 `adr-x.md` 被引用就算过。
   ADR 内容质量不在这一层（【规格】§13.2 那句「必须附备选方案及选择理由」
   是**岗位书 + 架构师评审**的活，不是字符串能判的）。
6. **`matchDomains` 不做语义匹配**：任务声明里没有 `framework_versions` 这个字面名，
   强制搜索就不触发。与 0022 §7 第 3 条同一条理由（列一条离线核验不了的匹配规则，
   会换来「在那个任务里照样放行」）。代价是漏触发靠人补声明，不靠算法。

## 8. 需要 CEO 定的一项

**§8.1 第 3 层的两个比例。** 规格说「取决于金额」而没给数。我要不到数就不编（§7 第 3 条），
所以今天的状态是：阈值未注入 ⇒ 判不了 ⇒ 每次搜索都要技术总监批——
**这在真实运行里会吵到没人批**，而「没人批」的实际效果是搜索这一层不可用。
三个候选：**按角色给**（PM/技术总监高、dev 低）、**按任务预算比例给**（如 60% / 90%）、
**给绝对金额**（如单任务搜索满 0.5 美元起批）。
我倾向**比例 + 一个绝对下限**（比例在小预算任务上会过早触发），但两个数都要你给。
