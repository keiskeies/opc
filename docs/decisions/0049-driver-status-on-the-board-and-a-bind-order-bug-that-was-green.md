## 1. 这一格长什么样（先给结论，再给理由）

`GET /today` 多了一个顶层键 `driver`：

```jsonc
"driver": {
  "enabled": true,                      // 这台 Hub 开了 --driver-pump 吗
  "pumping": true,                      // 承载它的那条心跳【此刻】还在跑吗
  "task_limit_cents": 500,              // 驱动器用的那个分母（不是 budgets 里抄的）
  "stopped": [                          // 停在 agent 那一格而没人推了的想法
    { "task_id": "t1", "state": "IN_PROGRESS", "role": "dev",
      "cause": "at_limit", "attempts": 3, "max_attempts": 3, "since_ms": 1699999880000 }
  ]
}
```

看板上：顶部一条横幅说机器级那一格，卡片底下一行 meta 说这一条为什么不动。

### 1.1 为什么三个数与那份名单【必须】一起发

单发「哪些任务被放弃了」会造出一个**新的**同族谎言：驱动器根本没开时那份名单是空的，
而**空名单在看板上读起来是「没有任何任务被放弃」= 一切正常**，真相是「这台 Hub 从来不推任何东西」。

这就是 0048 整篇要消灭的那个形状换个方向再发生一次。所以 `enabled` / `pumping` 不是补充信息，
它们是那份名单的**读法**：`test/web/app-pure.test.ts` 里有一条专门造
「库里确实有一条被放弃的任务，而 OFF 时报空」的对照，为的就是让
「OFF 时空」这一发不能靠"库里没东西"混过去。

### 1.2 `enabled` 与 `pumping` 为什么是两个字段而不是一个

`assemble.ts` 里承载驱动器的那条心跳连番失败之后，`onFatal` 会「不再安排下一轮」，
而**那一刻 HTTP 仍在服务、看板仍开着**（`assemble.ts` 那句 `io.warn` 原文是
「停滞检测现在不再运行，而 HTTP 仍在服务」）。合成一个字段的话，
「开过而停了」与「从没开」在界面上同形，而那两件事的下一步完全不同 ——
一个去看 Hub 日志，一个去命令行加一个开关。

这也是 `HubDeps.driverState` 是**函数**而不是值的原因（每请求现取），
以及装配层给的是**闭包**而不是启动时算好的常量。
0048 的变异实验里 M8 那一发造出来的正是「把启动时的开关当运行时的真相」这一族，
我在这里差点原地复刻一次。

## 2. ⭐ 绑参顺序：一个 24 发全绿的缺陷

### 2.1 它长什么样

```ts
// 我写的（错）
const params = [...DRIVER_ELIGIBLE_STATES, state.taskLimitCents];
// 应该是
const params = [state.taskLimitCents, ...DRIVER_ELIGIBLE_STATES];
```

`STOPPED_SQL` 里 `?` 在**文本**中的出现顺序是：

```
SELECT ..., NOT (COALESCE(...) < ?) AS over_budget   ← 第 1 个 ?（在 SELECT 列表里）
FROM tasks t WHERE t.status IN (?, ?, ?, ?, ?)       ← 第 2~6 个
```

那份花钱的分母住在 **SELECT 列表**，状态集合住在 **WHERE**。
而我按「读代码的顺序」写成了先状态后上限。

### 2.2 为什么它全绿，以及它坏了什么

- `assertParamCount` 只比**个数**：5 个状态 + 1 个上限 = 6，两边都是 6 ⇒ 过。
- `node:sqlite` 按位置绑，**绑错不报错**（0044 记过一次：把 limit 当成预算去比）。
- 于是 `'CHARTER_APPROVED'` 被当成预算上限去比：SQLite 里「数字 < 文本」恒假
  ⇒ `NOT(...)` 恒真？不 —— `COALESCE(...) < 'CHARTER_APPROVED'` 恒**假**，
  `NOT(假)` 恒**真**，而 `IN` 列表少一格、多出一个 `500`。
- 净效果：**「被钱挡住」那一档的判据换成了一个永远不成立的比较**，
  而**候选集合少了最后一格**（`BUDGET_PAUSED`）。

少最后一格这件事特别隐蔽：`IN (?, ?, ?, ?, ?)` 收到
`(500, 'CHARTER_APPROVED', 'DECOMPOSING', 'IN_PROGRESS', 'IN_REVIEW')` ——
前四格照常工作，只有第五格静默消失。

### 2.3 它是怎么被撞出来的（不是靠聪明）

是我写 C 组那三条「被钱挡住」的用例时撞出来的：它们期望 `no_budget` 而实到 `{}`。
也就是说 —— **缺陷是靠"给这一档写测试"发现的，不是靠"想到要检查绑参顺序"**。

顺带一条更值得记的：**我原本用来当分母的那条用例（挑一个派生集合里的状态）恰好挑不到坏掉的那一格**。
`DRIVER_ELIGIBLE_STATES.find(s => s !== "IN_PROGRESS")` 拿到的是 `CHARTER_APPROVED` —— 第一个位子，
而消失的是最后一个位子。所以即使那条"分母"用例存在，它也照绿。
改法是**逐格过**（`派生集合里【每一格】都报` 那一条），而不是挑一格。

### 2.4 顺手一条：两条 SQL 的顺序不一样

驱动器自己那条 `driverCandidatesSql` 里，上限的 `?` 在 `IN` **之后**（两个都在 WHERE，从上到下）。
读侧这条是**之前**。所以「照着驱动器那条抄绑参顺序」会正好抄错。
这一句写进 `driver-status.ts` 的注释里，因为它不是能从代码看出来的 ——
你得同时读两条 SQL 并且知道它们是两种形状。

### 2.5 变异 M9

把顺序换回错的版本：**4 发红**（三条 C 组 + 那条逐格的）。

## 3. ⭐ 一句"看起来已经量过"的过期数字，比没有数字更坏

`driver-status.ts` 与 `app.ts` 的注释里今天写着「1.25 ms」。
我写下那个数字的时候，测的是**另一版 SQL** —— 那一版还带着一列 `ever_claimed` 的 `EXISTS`，
后来我把那一列删了（今天没有读者，而它值 5 ms），**没回去重量**，旧数字就留在了新 SQL 上。

这一篇里我重新量了，而且换了测法：探针把连接的 `prepare` 包一层，
**把产品代码真正发出的那条 SQL 原样截下来**再拿去计时与 EXPLAIN。
之前那版探针是自己手抄一份 SQL —— 手抄的那份漂了会量出一个假的快数字，
于是探针量的是探针，不是产品。

| 规模 | 中位 |
| --- | --- |
| 10 万事件 / 200 任务 / 40 活跃 / 1 放弃 | **0.56 ms** |
| 50 万事件 / 400 任务 / 120 活跃 / 0 放弃 | **1.53 ms** |
| 50 万事件 / 400 任务 / 120 活跃 / 5 放弃 | 2.30 ms |
| 50 万事件 / 400 任务 / 120 活跃 / 40 放弃 | **3.90 ms** |

差额是那次回表（`ABANDONED_AT_SQL`，取放弃行的 `created_at`）：**约 0.06 ms 一条**。
它的 N 是【已经放弃的任务数】而不是活跃任务数 —— 四十条想法同时停在半路，
本来就已经是要人工看一眼的局面，那 2 ms 不在要紧的地方。
这也是本文件唯一一处 N+1，而它是**故意留下的**（主查询那发不能逐条问，理由在文件头）。

计划里四发相关子查询（`g` / `g2` / `g3` / `g4`，各带一份 marker 子查询 `m`）
全部是 `SEARCH ... USING INDEX idx_events_task_kind_created`。
别名各不不同这件事在这里兑现了价值：**EXPLAIN 每一行指得出是谁**，
所以"某一发没配上索引"在计划里是能指名的（0003 文件头那条排查路径）。

```sh

PATH=~/.nvm/versions/node/v24.14.0/bin:$PATH \
```

（`/tmp` 里的探针是**一次性夹具**，不是仓库资产；换机器要重写。
所以数字旁边永远写清规模，而"这条查询便宜"这件事的承重部分是那条索引迁移，不是这个数。）

## 4. ⭐ 我把「同一格两行放弃记录」这件事想错了两次

### 4.1 第一次：我造的用例根本没测到我想测的东西

`gaveUpSubquery` 取 payload 的两列带 `ORDER BY <别名>.id DESC LIMIT 1`，
取 id 那一发用 `MAX(id)` —— 两者**定义上**指同一行。我写这条的理由是
「同一格合法地可以有多行放弃记录（打回重访之后驱动器重来一轮又到顶）」。

于是我造的用例就是：放弃 → **打回重访** → 再放弃。
然后把那句 `ORDER BY` 拆掉（变异 M11）：**24 发全绿**。

原因：中间那次重访写了新的 marker，而 `id > marker` 已经把第一行排除掉了 ——
那一发 `ORDER BY` **根本没有两个候选行**。我的用例测的是 marker，不是排序。

### 4.2 第二次：我给另一发写的注释是"没量就写的"

于是我加了一条「时钟回拨」的用例（两行放弃记录，后写的那行 `created_at` 反而更早），
并在注释里写「这一发才真正咬住 ORDER BY，因为少了 ORDER BY 时 SQLite 的计划恰好按 created_at 走」。

再量一次：**M11 是被原来那条 b9 抓到的，不是被这条新的抓到的。**
所以后半句关于查询计划的断言是我**没跑就写的**（而且它恰好是我在 0048 §2 刚记过的那族错）。

改正之后的分工是清楚的：

- **b9（普通两行）** 咬住**有没有** `ORDER BY`；
- **b12（时刻倒序）** 咬住**按哪一列排** —— 如果有人把 `ORDER BY` 改成 `created_at DESC`
  （「取最近那次放弃」读起来完全合理），b9 抓不到它（那一发里两个序恰好同向）。

变异验证：**M12**（`id DESC` → `created_at DESC`）红 b12；**M11**（拆掉 `ORDER BY`）红 b9。两条各咬一头。

### 4.3 顺带把源码注释也改了

`driver-status.ts` 里那段讲「为什么三发必须取同一行」的注释，原来写的是
「同一格合法地可以有多行（marker 之后驱动器重来一轮又到顶）」。
那句话**没错但误导**：marker 之后的第二行确实合法，而它同时意味着 marker 会排除第一行，
所以那个场景**不会**产生两个候选行。真正的场景是 append-only 库里躺着**别人写的行**
（人工补录、第二个驱动器、外部脚本）—— 与坏 payload 那一档是同一类防线。

一个"看起来解释得很清楚"的理由，会让下一个人照着它去造一个测不到的用例。我就是那个人。

## 5. 三处「缺失不许被读成一个答案」

这一族本仓记过几次（`HubRequest.peer` 必填、`HubDeps.driverState` 必填、必填不给默认值），
这一篇又长出三处，都在写完之后回头读时才发现：

1. **`DriverStatus` 我第一版写成 `| null`（"不知道"）**。而"不知道"没有任何一个真实构造点会给出：
   那种宿主下「没开驱动器」就是答案（`enabled: false`）。一个没有生产者的取值形状，
   界面就得为它写一条永远走不到的分支。今天「这一维取不到」在屏幕上确实存在，
   而它的形状是 **`GET /today` 整个失败**（`app.js` 里 `t.error` 那一支已经处理了）。
2. **`driverNotice(driver)` 我第一版直接 `if (!driver.enabled)`**。
   于是 `driver: {}`（服务端少发字段）会走到**「这台 Hub 没开驱动器」**那一句 ——
   一句从**缺失**里推出来的**肯定陈述**。改成先验 `typeof driver.enabled === "boolean"`：
   形状不对 ⇒ 答案是"不知道"，而"不知道"的下一步是去看服务端，"没开"的下一步是去起开关。
   同一个改法也用在 `stopped` 不是数组那一档（第一版写的是 `?? []`，于是"响应坏了"读成"没有异常"）。
3. **测试夹具里我写过一发两头都认的断言**：
   `drv["task_limit_cents"] ?? drv["taskLimitCents"]`。那是把守卫写成装饰 ——
   哪一侧坏了它都绿。换成只认 snake_case 那一个名字，另加一条 `toBeUndefined()` 认那个错名字不该在。

## 6. 界面这一侧守的两件事

`test/web/renderer-criteria.test.ts` 加了两条，`test/web/app-pure.test.ts` 加了执行证据。

### 6.1 「发了没人读」这件事，`toContain("driver")` 挡不住

原来那条守卫是「判据字段必须出现在 app.js 代码里」。我直接把 `driver` 加进那个循环，
然后发现它是**假守卫**：`"driver"` 同时也出现在我起的函数名里（`driverNotice` / `driverLine`），
所以「把 `t.driver` 的读取全删掉、只留那两个函数」照样绿 —— 而那**正是**这一发要拦的事。
改成扫属性访问那个形状（`/\b\w+\.driver\b/`）。变异 W3（把 `t.driver` 换成 `undefined`）：红。

### 6.2 界面不许把「试到上限」重判一遍

响应里带了 `attempts` / `max_attempts`，最省事的抄件写法是界面里
`if (attempts >= max_attempts)`。而"到顶"这件事已经在库里判过了；
配置改过一次，两边就会给出相反的答案（屏幕说"还在试"而驱动器已经放弃了）。
所以扫的是**比较运算**而不是那两个词（`driverLine` 必须读它们才能拼那句"第 3/3 次"）。

配套一条自证有效性：**先断言 `function driverLine` 找得到**。
少了它，那条正则在函数被改名之后是恒绿的 —— `indexOf` 返回 -1，`slice(-1)` 剩一个字符，
扫不到比较 ⇒ "通过"。（装载器那边也会红，但本文件不许依赖别的文件来证明自己扫到了东西。）
变异 W2（塞进一句 `row.attempts >= row.max_attempts`）：**双重红** —— 源码扫描红，
`app-pure` 里那句"到顶那一档要说出第几次"也红。

### 6.3 不给琥珀

§19.2 里琥珀唯一的意思是「需要 CEO 决策」。
"驱动器不再推这条了"多半要的是**去查为什么推不动**或**放开预算**，不是决策 ——
涂琥珀会把琥珀贬值（同【规格】§7.4 那句「预算暂停非琥珀色」）。所以这一格用的是横幅 + 一行 meta。

### 6.4 转义只做一次

`driverLine` 交回**纯文本**，`esc` 由 `taskCard` 那一句做。我第一版两边都 `esc`，
而今天那几个片段（中文、数字、`/`、`·`）里没有可转义字符 ⇒ **双重转义看不出来**。
所以那条"只转义一次"的用例第一版本身是同义反复（不注入任何东西，恒真）。
换成注入一个字符串形状的 `attempts`，再断言卡片上没有裸 `<img`。变异 W1（去掉卡片那句 `esc`）：红。

## 12. 为什么「追加预算」那颗按钮我【没有】自己动手做（量过之后停手）

### 12.1 那颗按钮最省事的实现是【一颗空按钮】（实测）

「追加预算」最省事的写法就是 `UPDATE budgets SET limit_cents = ?`。实测它**不产生任何效果**：


因为那道门的**分母是进程里那个命令行数字**，`serve/driver-pump.ts:487` 绑的是
`o.taskLimitCents`，不是库里那一列。**这一条不是我发现的** —— 0045 §4 明写着

### 12.2 它挡着的那一格【已经登记过了】（0045 §7），所以本篇不开新的一格

0045 §7 已经把「`budgets.limit_cents` 这一列该怎么办」连三个候选摆给 CEO 了，

### 12.3 本篇为别的理由加的字段，恰好是候选 (B) 缺的那半件

0045 §7 的 (B) 说：预算条右半边该改成「读**当前进程生效的参数**（由服务端随响应发下来）」，
代价写的是「`/today` 要多带一个字段」。**本篇已经把那个字段发下去了** ——
`driver.task_limit_cents` 就是"当前进程生效的那个参数，由服务端随响应发下来"，
只是我为它写的理由是"名单的读法"而不是"预算条的分母"。

这一条**不能读成"顺手把 (B) 做掉了"**：(B) 要的是**预算条那一侧改用这个字段**
（`today.ts:294` 那个 `SUM(limit_cents)` 换成进程里的数），而那仍然要改响应口径的语义、
还要决定"离线读库的人看到没有上限的账本"这件事认不认 —— 都在那一格的范围里。
我做的只有一件小事：**让我卡片上那一行的数与预算条那个数在屏幕上可分辨** ——


「命令行」那三个字是限定词而不是修辞：少了它，同一屏两个"上限"就无从分辨。
而「屏幕上放开不了…要重启」这一句是我第一版**没有**的 —— 第一版写的是

`test/web/app-pure.test.ts` 里新加的那一发钉的是**措辞不许指回那条不存在的路**：

变异 **W4**（把措辞换回「可追加预算后继续」）：1 红。
