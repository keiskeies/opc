## 0. 本篇补的是什么

§16 那五个页面（今日 / 看板 / 收件箱 / 组织 / 回放）从今天起能在本机打开：
`GET /today` 一个读端点 + `packages/web/public/`（`index.html` + `app.js`，§19.2 深色配色）
+ `packages/web/src/dev-server.ts`（签名代理，Electron 主进程的离线替身）。

`GET /today` 只回答**别处答不了**的四问：窗口内完成数、此刻阻塞数、三类决策次数、预算总额。
待批张数、任务列表、组织图各自已有对账源（`GET /approvals` 的 `pendingTotal`、`GET /tasks`、`GET /org`），
**一个都没重抄** —— 两个来源给同一个数就是本仓反复抓的「两张表两个答案」（0041 §4 那条钱的教训是同一族实证）。

## 1. 判据为什么必须在服务端（不是"整洁"，是"抄件没有分母"）

`packages/web/src/hub/projection.ts` 文件头写着渲染进程内不存在业务状态机，
而它的破法从来不是「别 import 状态机」，是「别为了显得顺自己补一拍判定」。
这一页看着像「数一下列表」的四格，逐个问【判据从哪来】就知道不是：

| 那一格 | 判据 | 为什么界面算不了 |
|---|---|---|
| 被阻塞 | `BUDGET_PAUSED` / `BLOCKED` | 这是**边表**的知识（哪几个状态出边为空或只指向 CEO） |
| 今天完成 | `events` 里那次 `→DELIVERED` 跃迁 | `tasks.updated_at` 答不了这一问（最后一次更新可能是预算列被加了一下） |
| 自动通过 | `payload.auto_approved_by` 有值 | 写侧刻意不开新 action 值（§22.1 枚举 append-only） |
| 活跃 | **排除** `DELIVERED` / `ARCHIVED` | 列举一堆进行中状态会漏新增的（漏的方向是「界面显示 2 个而实际 5 个」） |

三条都是判定，不是排版 ⇒ 判定住在模块（`hub/src/overview/today.ts`），HTTP 只是一个入口
（与 `approvals/query.ts`、`replay/query.ts` 同一个分法，0013 §6 记的就是这条落点偏离）。

**本篇真正承重的一步**不是把判定挪到服务端，而是**把判据本身随响应发出去**：
`blocked_statuses` / `attention_statuses` / `ceo_decision_statuses` / `operational_approval_types` 四个字段。
少了它们，界面只能自己抄一份清单，而**那份抄件没有任何测试能发现它和这里不一致**
（变异测试跑在 hub 侧，看不见 web 侧）。发出判据之后，看板那一页是**拿着服务端给的清单在筛**：

`packages/web/public/app.js:445` —— `attention.includes(tk.status) || overBudget(tk)`，
左边是服务端发的状态集合，右边是两个服务端给的数比一下（算术，不构成状态机判定，所以留在界面）。

**⚠ 这一句在本篇内被修正过一次**：第一版只发**三份**清单，而且把 `active_statuses`
也写进了"随响应发出"那串 —— 后者**从来没成立过**（响应里根本没有那个字段，
`overview/today.ts` 的注释在声称一件不存在的事）。差别不是疏忽而是**有没有消费者**：
看板要拿 blocked / attention 去筛任务 ⇒ 界面必须持有清单；而"活跃"今天只有一个
服务端算好的数在下游客手里，没人拿它筛 ⇒ 没有抄件可漂移。
这一格后来由 `test/web/renderer-criteria.test.ts` 那条「顶层键名集合」照出来（同一发还照出
渲块里 `blocked_statuses` **一个消费者都没有**，见 §3.2 末尾）。

## 2. 三处「算不出来」，写在屏幕上而不是藏在注释里

**① 按天的预算上限在库里不存在。** §16.3 要「今日预算消耗比例」、§21.3 要「日消耗 vs 预算」的条形。
而按天的消耗额今天**没有记录方**：`budgets` 只有累计的 `consumed_cents`，全仓唯一写入是 `+ ?`
（单调不减 ⇒ 它就是「至今总共」），表上**没有** `updated_at`；唯一带时刻的是 `budget_events.created_at`。
于是「窗口内花了多少」能给准数，「日上限是多少」给不出 ——
角色级 `daily` 那一格**没有任何生产者**：`packages/hub/src/engine/runtime.ts:112` 与
`packages/hub/src/budget/tracker.ts:70` 两处 INSERT 都只声明 `task|<id>|per_task` 一种作用域。

取舍：**给有判据的那两半，并明写缺的是哪一半**。
画一根「今日消耗 / 未知上限」的条形比不画更坏 —— 那根条形的长度本身在说谎。
响应里的 `notes` 数组就是这件事的载体（口径本体进响应而不是注释，因为注释只对读源码的人说话）。

**② §16.4 那六个层级列名没有数据来源。** 库里 `packages/contracts/src/org/graph.ts:65` 的
`orgNodeSchema` 只有 `role_id` / `can_manage` / `model_family`，且 `.strict()`
⇒ 加一个 `tier` 字段是一次**契约变更**，不是前端能顺手补的。
于是看板按 `reports_to` 到 CEO 的**深度**派生列，列名写成「深度 N · <角色名>」而**不去套那六个名字**：
套上去会得到一个看起来合规、实则凭猜测的映射（哪个 role 算「执行」？谁定？）。见 §10。

**③ 「自动通过 0 项」在不带话的界面上读起来是「策略引擎很闲」。**
`notes` 里那句「含义是策略引擎今天没有生产调用方（0014 §3），不是『没有可逆决策』」
是这一格唯一的正确读法，所以它跟着数据走。

## 3. 等 CEO 之一：「需要我注意」= 升级 ∪ 阻塞 ∪ 触及预算（我加了一维）

§16.4 原文是「过滤后只显示**被升级或触及预算**的任务」。`packages/hub/src/overview/today.ts:104` 的
`ATTENTION_STATUSES` 是「`ESCALATED_TO_CEO` ∪ `BLOCKED_STATUSES`」—— **多加了阻塞**。

理由是这一格的读者问题：CEO 打开这一列问的是「哪几件在等我或卡着」，
而 `BUDGET_PAUSED` 按规格 §7.1 只有一条出边（→`ESCALATED_TO_CEO`）——它**就是**在等人，
只按「已被升级」筛会把「预算停了但还没升到 CEO 面前」这一类整批滤掉，
表现是那一列**空着**而公司里有事停着。这一维加得让它离原文更远、离那一列要回答的问题更近，
所以按代拍记下，**这一节就是那条待决本身**（登记在 `docs/INDEX.md`「等待 CEO 决策」的 `0042 §3`）。
要按原文收回这一维：改 `ATTENTION_STATUSES` 那一行 + 旁边那条用例即可，**界面不用动**
（判据随响应发出，这正是 §1 那一步换来的东西）。

同一节里刻意**没有**的：`MEETING_REQUIRED`。它同样是死路（出边空数组），
但规格里它的名字属于**会议**而不是「阻塞」，并进来等于替 §10.1 决定「辩论会卡住算不算阻塞」。

**判据是手抄的，所以旁边有分母**：`BLOCKED_STATES 覆盖 edge 表死路` 那条用例会去真边表里
把死路列出来对一遍（抄漏一个方向是「少报」，界面看着像「没坏事」）。

### 3.1 ⚠ 我第一版把「加一维」写成了"代价"，其实那是一处**违反规格**

第一版这一节的结尾是这样写的（原话）：「`BUDGET_PAUSED` 那张卡会在**两处**出现 ——
收件箱（按规格非琥珀）与看板这一列（按 §19.2 的**琥珀**标记）……
**同一件事被标两次**是这一维的真实代价，不是免费的方向改进。」

那段话**把一次违规写成了成本**。去查规格 §19.2 那张色表的原文：
`#E8A33D`（规格 §19.2 原话）「**全局仅用于『需要 CEO 决策』这一种状态**」，用法是「眼睛在任何页面一扫，
琥珀色出现处就是需要你动手的地方」。而 `BUDGET_PAUSED` 在规格里**四处**明写非琥珀：

| 出处 | 原话 |
|---|---|
| 规格 §6 事件表 `BudgetPaused` | 「**非琥珀色**卡片 + 日消耗条变红」 |
| 规格 §7.4 预算硬停 | 「审批收件箱出现**非琥珀色**的『预算暂停』卡片（**这是运营事件，不是战略决策**）」 |
| §21.3 界面表现 | 「预算暂停 → 审批收件箱出现**非琥珀色**卡片（规格 §7.4）」 |
| 附录 D 术语表 | 「在收件箱生成**非琥珀色**卡片」 |

写四遍不叫措辞。所以第一版的看板那一列是在对一件规格连着四遍说"这不是战略决策"的事
**喊"需要你动手"**。"两处都说得通"那句是自我辩护，不是分析。

**根因是把两件事做成了一个字段**：「哪些任务进那一列」和「哪些标琥珀」。
规格里它们**就是两个集合**（交集非空而不相等：预算暂停**该进**那一列 ——
规格 §7.4 那三个按钮追加预算 / 维持暂停 / 终止任务全是 CEO 按的 —— 但**不该**琥珀）。
于是拆成 `ATTENTION_STATUSES`（列成员）与 `CEO_DECISION_STATUSES`（琥珀），随响应各自发出。

**⚠ 而 `CEO_DECISION_STATUSES` 推不出来，只能抄。** 这一点值得单独记：
`BUDGET_PAUSED` 在规格 §7.1 边表里只有**一条**出边（→`ESCALATED_TO_CEO`），
按「下一步在等谁」这条轴推，它**必然**被推成琥珀。规格却明写非琥珀
⇒ 这是一条**规格的断言**，不是边表的定理。任何"从状态机派生颜色"的实现
都会在这一格得出跟规格相反的结论。所以它只能是常量 + 一条守卫
（钉「两个集合的差恰好是那两个阻塞态」），没有更聪明的写法。

顺带同一处轴混淆还有一个（**没**踩但差一点）：`role-memory.ts` 里已有的
`NON_STRATEGIC_APPROVAL_TYPES` 看着正好是"非战略 = 非琥珀"，可以直接复用 —— **不行**。
那条轴问的是「这条决策能不能进 dev 的角色记忆桶」（可见性），这边问的是「现在要不要惊动 CEO」。
反例就摆在规格 §7.2 步骤 1：`charter` 在那边算"非战略"，而 CEO 就是要展开章程卡点「批准章程」
⇒ 在这边**必须**琥珀。两边长度都对不上（2 vs 1）不是疏漏，所以新常量另开一个
`OPERATIONAL_APPROVAL_TYPES`，并用一条用例把"charter 在两边不同属"钉住。

### 3.2 修的时候顺手把琥珀色纪律在整个界面里过了一遍（六处都在违反）

`--amber` 的用法我逐个查了，违规不止看板那一处：

| 位置 | 原用法 | 规格怎么说 | 改成 |
|---|---|---|---|
| 看板"需要我注意"整列 | 全体成员琥珀左边框 | 整列涂琥珀 = 琥珀退化成"这一列"的标记 | 灰（`.tk.flag`），只有升级态琥珀 |
| 收件箱待批卡 | `pending` 一律琥珀 | 规格 §7.4 预算暂停卡**非**琥珀 | 按 `operational_approval_types` 分决策/运营两组 |
| 今日页「被阻塞」数字 | `.statbad`（琥珀） | 阻塞不是"等 CEO 动手" | 默认墨色 |
| 回放里人工决定那一行 | 琥珀圆点 + pill | 那是**已经拍过板**的记录，回放里没有东西在等谁 | 绿（= 已定） |
| `.banner.warn`（取不到数据） | 琥珀 | 系统故障不是等业务决策 | 蓝 |
| 「警报已哑」那一格 | `.pill.s-amber` | 它本身就是"警报没了"，配警报色自相矛盾 | 灰 + 粗体 |

红色同时收紧：`--err` 原来只有**硬失败**三处（连不上的点、错误 pill、错误横幅）+
新加的预算条。**这里我自己又错了一次**：我先写的断言是「红色只有一处合法落点（规格 §7.4 那根条）」，
实跑三红 —— 那三处早就在用红，而且**该**用红：色表没列"异常色"不等于不许有失败色，
那张表管的是**语义色**（CEO 决策强调色这类），"这一页没 load 出来"是系统故障不是业务状态。
所以断言的真实内容是「红只有这两类」，不是我原本写的那句。

同时补了规格 §7.4 要的那根「日消耗条」（原来只有数字没有条），并且**在屏幕上明写**它是一处近似：
判据只能用「累计已花 vs 已声明上限合计」，而规格那句说的是**日**消耗条 ——
日上限没有分母（§2 ①）。红线旁边就写着这句，不让人以为日预算阈值真算出来了。

**这些全是屏幕上才看得见的东西，而屏幕上今天没有浏览器**（§11 第一条）。
所以配色这种在 code review 里根本看不见的东西，唯一能守的方式是把它变成源码级断言：
`test/web/renderer-criteria.test.ts` 把「`var(--amber)` 允许出现在哪几个选择器上」
钉成名单（多一处就红并指名），另有一条反向名单专门钉上面那几处**不许**回到琥珀。
变异跑过：把 `.tk.flag` 改回琥珀 ⇒ **两发红**；把审批类型名硬编码回 app.js ⇒ **一发红**；
把那条守卫自己的"剥注释"写宽到把代码也吃掉 ⇒ **三发红**（其中"不许出现状态名/类型名"那两条
反而**假绿** —— 这正是那条正向对照存在的理由：只写"不许有"的断言，在扫描器坏掉时会全绿）。

**同一发还照出一件更不好看的**：`blocked_statuses` 这个字段 hub 一直在发，
而渲块里**一个消费者都没有**（只在注释里出现过）。也就是说 §1 那套「判据随响应发出」
的立场，在这一份清单上其实没兑现 —— 发了一份没人读的清单。
两种收尾都合法：删字段（没人用就不发），或者让它有消费者。这里选了后者，
因为「被阻塞 3」不带清单时读起来是"三件坏事"，带上才读得到它是**哪几个状态**
（而"哪几个"是边表的知识，界面写不出来）⇒ 现在它挂在 title 上（`blockedTitle()`）。
真正该记的不是这一格怎么修的，而是：**"发了"不等于"有人在用"，而这两件事之间
今天才有断言**（四个判据字段必须都在代码里被读到）。

## 5. `GET /today` 刻意没有 IPC 通道（而且 `EXPOSED_ENDPOINTS` 这个名字在说谎）

`packages/desktop/src/ipc-surface.ts:171` 是 `EXPOSED_ENDPOINTS = IMPLEMENTED_ENDPOINTS` 的**别名**。
所以一个端点一进 `IMPLEMENTED_ENDPOINTS` 就**自动**算「暴露给渲染进程」，
而真正决定渲染侧碰不碰得到它的是 `CHANNEL_SPECS`。本篇落地之后实测（`channelFor` 逐个问）：

```
GET /today in IMPLEMENTED : true
GET /today in EXPOSED     : true      ← 名为「暴露」，实为「已实现」
channelFor(GET /today)    : null      ← 真的没通道
```

这正是 0030 §9 点名的那**唯一**无人断言的方向（「HTTP 能通、curl 得 200、测试全绿，而应用里点不到它」）
上的第二个实例。本篇把这一格**钉成断言**而不是留成事实：
`test/desktop/ipc-surface.test.ts` 里三条一起（在 IMPLEMENTED、`channelFor` 为 null、在 EXPOSED），
第三条专门钉住**那个不一致本身**，因为别名方向是「加一个已实现端点就自动算暴露」，
把它读成「渲染侧能用到」是一次具体的误读。

不给通道的理由是**今天没有消费者**（§16 控制室跑在 dev-server 上，桌面壳本机装不上），
与 `POST /org`（self-escalating，**不该**给）、mint token（回环专用，**不该**给）两类理由都不同，
所以分开写。真接桌面那天该红的是这条断言，红了要做的是「通道 + preload 方法 + 渲染侧调用点」三件一起。

## 6. charter 那条「孤岛」守卫自己红了 —— 一条守卫里塞了两件事

`packages/hub/test/charter/store.test.ts` 里那条「这条通道不经过任何 HTTP / 组织图路径」
原来一个正则同时判两件事：

```
/applyBudgetRowsInTx\(|from ".*charter\/budget-sync/
```

`GET /today` 为了报 §4 那一格 import 了**只读**的 `silentOverBudgets` ⇒ 两条一起判红。
而它们**不是同一件事**：「岗位书里的预算还没流向限流」是个**缺口**（0015 §3 那条结论的全部内容），
「今日视图读了一个只读的预算查询函数」是个**正常依赖**。

## 8. 前端那份签名抄件：边界逼出来的手抄，配了一发逐字节对账

`packages/web` 不许 import `packages/hub`（§5.6.1，`test/web/hub-projection.test.ts` 那条源码扫描守着），
所以 dev-server 那份 HMAC 规范串**只能手抄**。手抄本身是被边界逼出来的，不是疏忽；
不能容忍的是**手抄 + 静默失效**：验签刻意回一句不区分「签名不对 / 时间戳过期 / nonce 重放」的
`unauthorized`（防探测），于是「少拼一个 `\n`」与「token 配错了」在界面上**完全同形**，
而排查的人会去查部署凭据。

所以：签名实现拆进 `packages/web/src/dev-sign.ts`（**没有副作用**的模块 ——
`dev-server.ts` 末尾是 `server.listen()`，import 进测试就是抢端口；
而 hub 那个 `isDirectRun` 在 `packages/hub/src` 里，为了 import 一个谓词去破边界、
或者在 web 里再抄一份，正是 `direct-run.ts` 文件头那句「三份副本只会让同一个错误出现三次」要拦的事），
再配 `test/web/dev-server-sign.test.ts`：同一组输入喂**两边**（服务端那一侧 import 真的
`canonicalString` / `signRequest`，不在测试里重写第三份抄件），三个头逐字节相等；
再加反向一组（body / query / 时间戳 / nonce / token 各自单独扰动 ⇒ 签名必须变），
和一条**大小写方向相反**的（`"get"` 与 `"GET"` 必须**相等** —— 两边都做 `toUpperCase`，
把它混进「必须变」那个循环会让下一个人去把 `toUpperCase` 删掉来让它绿）。

变异跑过三种真实抄错，**每一种都红**（各 2 发）：分隔符 `\n`→空格、签之前剥掉 query、
body 摘要改成原文。基线复原 5/5 绿。
