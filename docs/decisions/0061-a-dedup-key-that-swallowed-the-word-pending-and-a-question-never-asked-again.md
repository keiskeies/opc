## 2. 三个模块各自都对，交集处谁都不负责

失效需要一个交集状态，而三个模块**分开测都绿**：索引测它挡得住（`cards.test.ts` ② 组）、
门控测它拦得对（`dispatch.test.ts` 的 `reviewGate` 那一组）、状态机测 reject 没有出边。

一条任务停在 `IN_REVIEW/director`，产出方 `dev` 与审阅者同一个 `model_family`（**今天全仓就是这一个家族**）：

1. 门 3 拦，建一张 `card_key = "same-family-review:dev->director"` 的豁免卡 —— 对；
2. CEO 按【退回】。`reject_with_comment` 在 `HUMAN_EDGES` 里**没有出边** ⇒ 卡片决策成功而任务原地 —— 对（0041 §7 登记的规格缺口）；
3. 卡片那一行变成 `status='rejected'`，而**它的键还在** —— 索引写的就是这个；
4. 下一轮 `dispatch` 判同族**仍然拦** ⇒ 去建同一张键 ⇒ 撞唯一索引 ⇒ `insertCard` 返回 `skipped="duplicate"` ⇒ **一张卡都不建** —— 三行代码各自都对；
5. 于是 `pendingCards = 0`，收件箱里没有任何东西可点，而那一轮的 note 仍然写着「（已建卡）」；
6. `IN_REVIEW` 在 `DRIVER_ELIGIBLE_STATES` 里 ⇒ 驱动器每个心跳自动重跑，直到那一格的尝试上限。

第 5 步那句 note 我要说准，因为它现在仍然部分为真、部分为假，而**假的那一半不是 0006 该负责的**：
`dispatch.ts` 那两处 `stay(...)` 写的是 `o.review.reason + "（已建卡）"`，**无条件**。
所以「拦门为真而一张卡都没建」这句话它永远分辨不出来。0006 修的是**退回**那一格
（键不再被烧掉 ⇒ 卡真建得出来 ⇒ note 与事实重新对上），
而**待批卡已存在**那一格（`skipped:"duplicate"`，一张新的都没建而确实有一张挂着的）
note 仍然说「已建卡」—— 那一格读作「有卡等你批」是成立的，登记在 §8 第 3 条而不是当成已修。

**这条链上的钱是自动花的**，所以它不是「某个界面少个按钮」。

## 3. 为什么是收窄索引，而不是另外两种改法

三条路我都量过才选，而不是挑第一条看起来合理的：

**(甲) 把键拼成 `…:round-2`。** 它挡得住这一格，但它把**判据**那一侧改坏了：
`engine/runtime.ts` 的 `CEO_APPROVED_SQL` 是按 `(task_id, card_key)` **精确匹配**读
「这件事 CEO 批过没有」的（`"… WHERE task_id = ? AND card_key = ? AND status = 'approved'"`）。
键一旦带轮次，第 1 轮批的那张豁免就匹配不上第 2 轮的键，于是要么改成前缀匹配
（= 把「哪一轮的批准算数」这件事交给 `LIKE` 的语义），要么每次退回都换键而批准永远追不上。
**收窄索引不动判据那一侧**：它仍然精确匹配。

**(乙) 退回就把任务推进一格。** 规格 §7.1 没给 reject 那条出边，而 `HUMAN_EDGES`
只有 `approve` 一条出边这件事**已经登记为规格缺口而不是本地取舍**
（那张表在 `engine/dispatch.ts`，「只有 approve 能推进」那句写在 `engine/approve.ts` 文件头）。
补一条边是**把规格没给的跃迁写进状态机** —— 那是改规格，不属实现层（0044 §9.1 停在这同一条线上）。

**(丙) 收窄索引到 pending。** 选了它，理由里最容易被误读的一条是它**动了 0004 那条索引**，
而 0004 文件头写着「只用 ADD COLUMN + CREATE INDEX，不 DROP / RENAME / ALTER」。
那条立场管的是**数据与读法**：删列、改列义、把某张历史表挪走 ——
「审计库里任何『删掉一个查询路径』的操作都会让历史回放指向不存在的东西」。
**索引不是数据，也不是一条读法，它是写侧的约束。** 删掉它：
一行都没删、一列都没改 ⇒ 历史回放读到的行逐字不变；而**收窄唯一性其实是放宽**，
旧约束是新约束的子集 ⇒ 存量数据不可能违反新约束，这条迁移连「存量会不会撞」的核对都不需要；
被去掉的是「一个键上第二行插不进去」这条**未来的**拒绝，不是任何**已有的**事实。

索引名字**沿用** 0004 那一个：全仓提到 `idx_approvals_card_identity` 的**四处**
（0004 / 0006 两处 / `charter-pump.ts` / `charter-pump.test.ts`）**没有一处是查询**，
全是 DDL 与注释。保留同名是为了不制造第二个名字 ——
**一条约束有两个名字的时候，下一个人不知道哪条还活着。**
（【就地更正】我在迁移注释里先写的是「三处注释提到它」，实测是**四处**。
总数少算一处不影响结论，而那个数是我论证「改名不伤读侧」的依据之一。）

## 4. 收窄之后谁还在挡「白花钱」：那道筛子是**三个地方**，分工不同

`charter-pump` 有一道省 token 的候选筛：任务是候选当前任务**从来没有过**章程卡。
它原来给的理由是「判据必须与 DDL 的约束**同一个形状**」，而那个形状就是 0004 那条索引。
0006 一改，这句话当场变成假话 —— 而**结论不能跟着改**：
「卡被批掉而任务没推进 ⇒ 泵不再起草」这条性质必须照旧成立，否则每个心跳起一个真子进程，
烧一轮 token 换回一句「已经有了」。

我把这道筛改成只查 pending 去量它到底靠谁，而**这里我第一次量错了**：
我以为「这道筛子」是一处，读代码时只看到候选 SQL 那一处。实际是**三处**，
其中两处是**逐字相同**的 SQL 字符串常量（候选 SQL 与 `CHARTER_BLOCKED_SQL`），
第三处是起草循环之前那道 TS 侧的 `hasCard` 前置检查。**分开量的读数不同，后果也不是同一类**：

| 变异 | 改哪一处 | 红发 | 失效方式 |
|---|---|---|---|
| `M3sql` | 那两个 SQL 字符串 | **2 发** | **花钱**：任务进候选 ⇒ `ensureCharterCard` 的前置检查（也只查 pending）放行 ⇒ 起子进程、烧一轮 token ⇒ 又建出一张卡 |
| `M3ts` | 那道 TS 前置检查 | **0 发**（全套 2543 发，实测） | **审计说谎**，见下 |
| `M4` | 把那道 TS 检查整行删掉 | 2 发 | 到上限那一轮恰好起草成功时，给一张**刚建出来的卡**写「试到上限仍没有可批的章程卡」 |

`M3ts` 存活那一次是我这一轮最该记的东西，因为它**不是断言写松了**：
判放弃那一循环要走到那张卡上，需要一个【非 pending 的卡在这一轮里冒出来】，
而那**从测试外部摆不出来** —— 候选 SQL 已经把「有任何卡」的任务滤掉了，
所以本轮能冒出的卡**只有刚起草出来的那张 pending**。两个条件在可达状态上恒同答。
这正是 0057 M5 那条判据（**一个条件若在两个输入下给出同一个答案，它就没在判任何东西**）
落在**我自己刚写的代码**上。

补法不是「再补一行断言」而是**把那一格摆成静态状态**：两条任务 + 一次插入。
泵是 `for` + `await` 顺序跑的，t1 的卡在 t2 那一发起草**之前**就已落库 ⇒ 完全确定，没有时序窗口。
真实场景就是这一格：**CEO 在界面上点了批准，而泵那一趟还在处理队列里下一条**。
只查 pending 的话，会给一张**已被批准**的章程写一行「泵不再试」—— 审计里一条反着说的记录。
补完 `M3ts` 才红，红在承重的那一条上（`expected [ 't1' ] to deeply equal []`），
不红在我那三条前置断言上 —— 这一点要能看出来，所以探针现在把断言明细也打出来。

⇒ 于是「别再拿『与索引同形状』当理由去改它」这句写进了源码，而它带的信息比原句多：
**0006 之前这里与 DDL 同形状是免费的，现在是有意比 DDL 更宽** ——
DDL 只管待批，这里管「这件事有没有人回答过」。

## 5. 「红发 0」有两种，而我先撞到了假的那种

第一版变异探针报 `M1 ⇒ 红发 0`。**M1 是把索引退回 0004 的原状**，
它**必须**红，红发 0 是探针死了而不是变异无害。
原因是 `execFileSync("npx", …)` —— 本机 `npx` 是 `npx.cmd`，无 shell 时直接 `ENOENT`，
`out` 是空串，于是「红发 0」被算出来，与「这个变异没被抓到」**输出完全一样**。

修法不是加一条日志而是加一条**判据**：输出里没有汇总行就 `exit 4` 并打前 1200 字节。
同一族还有第二条：变异落地与否**必须按 sha256 核对**，没变就抛 `NOT APPLIED` ——
否则「我什么都没改成」也会给出一个漂亮的 0。这一条当场抓到我两处锚点写错
（`sed` 式的多行替换我早先就用过一次而留下过悬空 SQL 续行；这次改成 node 脚本比对字节）。

修好之后全部读数（都是**这一轮重新量的**，不是抄上一轮的）：

| 变异 | 改法 | 红发 | 说明 |
|---|---|---|---|
| `M1` | 去掉索引的 `status` 条件（退回 0004） | **4** | 三发新回归 + `cards.test.ts` ② 那两发里的相关项，红因与预测逐条对上 |
| `M2` | 索引整个拿掉 | **7** | 「干脆不去重」那种改法。只有反向对照那一发能区分「正确收窄」与「没有索引」 |
| `M3sql` | 两处 SQL 筛只认 pending | **2** | 见 §4 |
| `M3ts` | TS 前置检查只认 pending | **0 → 1** | 补了那一发之后才有分辨力（§4） |
| `M4` | 删掉 TS 前置检查整行 | **2** | 其中一发是新补的那发 ⇒ 它与 M3ts 现在从两个方向钉同一个条件 |

`M2` 那一列值得单独说一句：**它是唯一一发能证明「收窄 ≠ 没索引」的**。
只跑 M1 的话，"我把索引改成挡 pending" 与 "我把索引删了" 在测试上无法区分，
而后者会把 0004 存在的理由（收件箱里同一个决定出现两张卡）整个放掉。
反向对照那一发（新卡还挂着时第二次不重复建）就是这一格的守门人。

**收窄之后新可达的那个状态**（同一个键上 `rejected` + `pending` 并存）我逐个查过 `approvals` 的读方：
`CEO_APPROVED_SQL` 是存在性检查（每一条候选行都答"是"，不受影响）；
`countSimilarApprovals` 按 `status` 分桶聚合 ⇒ 它**变好**（以前一个键上永远只能有一行，
「同类审批被拒过几次」这一格被索引上限压成恒 0 或恒 1）；
其余读方都按 `status` 或 `id` 过滤。**没有一处读逻辑假设过一个键只有一行。**

### 5.1 同一条纪律在我自己的 lint 基线上又演了一遍，而且这次是**写进文档之后**才发现的

我在本篇初稿写下「biome **290/109/2**，与本篇动工前**同数**，本篇**零新增**」。
那个数**在我量它的那一刻是对的** —— 而后我又加了 `doc-ids` 那条守卫的三层断言，
其中一行 `expect(migKeys).toContain("migrations/0006_….sql")` 超出排版宽度，
biome 从 290 变 **291**。⇒ 「零新增」这句在**发表时**是假的，
而它假的方式与 doc-refs 那七次坐标漂移**是同一件事**：**一个测完就没再重测的数**。

复算过程本身又给出**两个假基线**，都值得记，因为它们都长得像证据：

1. **`biome check --stdin-file-path=…` 在这台机器上不输出任何诊断。**
   我拿 `git show HEAD:<file> | biome check --stdin-file-path=<file>` 当 HEAD 侧基线，
   它对着**明明在报的四个文件**报「什么都没有」⇒ 我当场得出「四个文件 HEAD 与现在都是 0」。
   拦住我的不是这个数看着不对（它看着挺干净），是我顺手拿一个**已知有 6 条**的文件跑同一条命令，
   它也报 0 —— **基线测的是"我的命令"而不是"文件"**。正解是把 HEAD 的内容落到仓库内一个探针文件里再测
   （`biome.json` 的作用域按路径生效，仓库外的临时目录**不在**它的作用域内）。
2. **`grep -oE "Found [0-9]+ (errors|warnings)"`** —— biome 在计数为 1 时打印
   `Found 1 error`（单数），而我这条正则**只认复数**，于是所有"只有 1 条"的文件被读成「没有」。
   同一个坑这一轮我第一次用的写法 `errors?` 是对的，第二次重写时**把它写坏了**。
   ⇒ 与 0055 那条「我自己探针里的计数正则会返回 0 条诊断而同样的输出里写着 `Found 3 errors`」
   是同一个形状：**判据说"没有"的时候，先问它有没有能力说"有"**。

修完的口径：全仓 **290 error / 109 warning / 2 info**（`biome check --write` 只作用于
我自己那一个文件，改的是那一行折行），与动工前**逐数相同**，这一次是**改完之后重测**得出的。

3. `0044 §9.1` 与入口登记表那一行：见 §9。

形状是：**注释承诺了实现没有的性质，比没有注释更坏** —— 而这里更糟一层，
它承诺的是**曾经有**的性质。读的人会拿它当"这一格已经被 DDL 守住了"的证据，
而我的迁移刚好把它挪走了。这条不需要变异来证明，grep 一遍旧措辞就能扫出来，
而它的**成本是零**、漏掉的代价是下一个人重建那条死路。

## 7. 一条守卫在它能红之前，我不能说我加了它

我给 0006 那份迁移的注释写了「详见 0061」，那天 0061 还不存在。
**全套 2543 发一发没红。** `doc-ids` 这条守卫专门判「正文提到的编号不许指空号」，
而它的取材是 `docs/decisions/*.md` + `INDEX.md` —— **迁移文件从来不在里面**。
而迁移恰恰是最爱引用决策记录的一类：0004 里 7 个编号、0005 里 11 个。
⇒ 「文档正文的编号不许指空号」这条判据，**在迁移文件这一类上从来没有生效过**。

先把取材扩到 `packages/hub/resources/migrations/*.sql`，
**再确认它真的能红**（实测：`migrations/0006_….sql>0061`，点名到我引用的那一个号），
然后才写 0061 让它变绿。顺序是有意的，与 0055 那条「搬进 vitest 才算被执行」同形：
**判据存在于但不被执行，与没有判据不可区分。**

加的时候还踩到一个自己的洞，值得记：我第一版只补了 `docs.size >= 7` 那条规模自检。
而 docs 那一类有 60+ 个文件，**迁移那 6 个整个不见了，size 仍然远大于 7** ⇒
判据可以静默退回「只扫 docs」而我以为它扫两边。
所以补了三层，各管一种退化：① `migrations/` 前缀的 key 必须在场；
② 逐条要求内容非空（`readFileSync` 被换成恒返回 `""` 会让"没有违规"永远成立）；
③ 拿**空允许集**跑一遍判据、要求从迁移里**抽出至少 6 个编号** ——
这一层防的是「key 在场而取材是空的」，也就是那一类整个**不可判**：0 个编号永远不违反任何规则。
`docIds` 内建「路径里的编号不算引用」，而我给的 key 带 `migrations/` 前缀，
正好被同一条规则放过 ⇒ **不需要为迁移另开一条豁免**（现有 5 份迁移在扩面后全部可过，实测）。

## 8. 留在原地没做的

1. **O4 的四个动作一个都没动。** 本篇是开工前的普查撞到的一条活缺陷，不是 O4 的交付。
   验收那句「把设计文档那张表第 3、4 行每个函数调用点删掉 ⇒ 各自必须有一发红，今天删掉 0 发红」**今天照旧是 0 发红**。
2. **`HUMAN_EDGES` 只有 `approve` 有出边**这条规格缺口**没补**（§3 乙）。
   本篇让"退回之后能再问一次"成为可能，**没有**让"退回之后任务往哪走"有答案。
3. **note 与建卡结果不同源**（§2 末段）。`skipped:"duplicate"` 那一格读作「有卡等你批」成立，
   所以**没有**为它补断言；但「note 由拦门判定拼出来而不由建卡回执拼出来」这件事仍然没有守卫。
   如果将来有第三种情形（拦门为真、一张挂着的卡都没有），note 会重新变成假话而不会有人发现。
4. **`CEO_APPROVED_SQL` 只验 status**，既不验批准人是不是 CEO，也不验有没有留下理由。
   而 `sameFamilyReviewBlock` 写侧要 `approvedBy === "ceo"` 且理由非空，
   `policy/auto-approve.ts` 写的 `decided_by` 是 `"policy-engine"`。
   ⇒ 策略引擎写的一行今天**能**满足这道活门。这不是 0006 带来的，也**不能**顺手把身份判断
   搬到读侧：那样一张没写理由的批准会**烧掉键**（正是本篇刚修的那个形状）。
   身份与理由必须在**写侧**收紧 —— 登记在 O4 动作 1 里，那里才是在正确一侧动手的地方。
5. **变异探针是手工脚本，不进 CI。** 与 0054 / 0055 同一口径：本篇报的是「这些变异现在会被抓住」，
   不是「以后有人把它们改坏时会红」。
6. `review_gates` 仍然**零 INSERT**（O4 动作 4）。

## 9. 0044 §9.1 那一项**还在等**，但它的价变了（登记在入口，不在这篇）

0044 §9.1 摆过三个候选：**(A)** `card_key` 带轮次 + 补一条 `reject → CHARTER_PENDING` 自环边；
**(B)** reject 把任务打回"等 CEO 重写想法"；**(C)** 维持现状。当时我倾向 A，
理由是 B 把人变成瓶颈而 C 与产品初衷冲突。

0061 改变的是**A 的报价**，而改变的方向值得重读一遍那一节：

- **A 的两半里，键那一半已经不需要了。** 索引收窄之后退回不再烧键，
  第二张卡在 DDL 层面**建得出来**（实测：`rejected-waiver-still-asks.test.ts` 那三发）。
  所以 A 剩下的代价只有「补一条规格没给的边」+「同一格出现多张卡时回放与『等了多久』的口径要一起改」。
- **章程这一格今天仍然不重起草**，原因换成两条，而**都不是键**：泵那道筛有意比 DDL 宽，
  以及没有合法的出口边。
- **另一格（同源审阅豁免）已经不等了**：退回之后它会重新建卡、重新被问。
  所以「CEO 说了不而系统回以沉默」这一条**在审阅那一格已经不再成立**，
  只剩章程这一格，而它卡在规格边集上。

入口登记表那一行与 0044 §9.1 的原句我都就地改了（原话不删，划掉留在原地），
因为那一行原来写着「**永远不能再有第二行**（迁移 0004 那条唯一索引不看 status）」——
一句**现在时**而它今天为假。恒假的前提上面搭着的三个候选，读的人没法正确比。
