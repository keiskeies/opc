## 1. 为什么注入点是「岗位书」而不是「包」，以及这一格此前根本不存在

## 3. ⭐ 我写了一条「更严」的归属核对，它拒掉的是唯一正确的接法

第一版的想法读起来无懈可击：这一层门控的是**作者**的工作（`producer: input.author`），
而本层自己那次审阅调用是**审阅方**的，所以「作者有没有搜过」必须由调用方从**作者那一次**交进来；
为防「顺手把手上的审阅方观测塞进来」，我加了一发 `roleId` 核对 + 一个新拒绝码
`search_observation_not_authors`。

它是错的，而错的方式值得记：**它不是判据太松，是判据太紧以至于排除掉正确答案。**
推理的断点在「门控判的是谁的产出」这一格：

- `evaluateGate` 在这一层拿到的 bundle 是**本层自己产的** `test_report`；
- 那个包里的 claim 是**审阅方**写的（`assemble` 交回来的就是审阅方那一跑的结果），
  `produced_by_role` 那一格填的是审阅方——**这一点 `verifier.ts` 里早就写了**，
  而且是为另一件事写的（【规格】§8.1 的包类型核对读它）；
- `mandatorySourceBlock` 读的是**包的 claims**。

⇒ 第 1 层在这里判的是「**审阅方**那些依赖外部来源的话搜过没有」。
于是三个入参必须同源，而它们恰好**全在本层手上**：
包 = 审阅方产的 · 领域 = 审阅方那份岗位书 · 观测 = 审阅方那一次调用的 `toolSightings`。
我那发核对要求「观测必须来自作者」，**正好把这一条通路封死**，
并逼调用方交出作者的观测——一个第 1 层根本不该问的问题。

那条码删了。⇒ **一条判据在被写下之后，要先问它排除掉的是哪种接法**；
「它更严」不构成它对的理由，而它**不会以红的方式告诉你它错了**——
它只会让正确的接线跑不起来，然后有人来把判据放宽（那时被放宽的会是整条）。

顺带一条同族的、这次**被测试拦住**的：夹具里我把授权名单写成 `web_search`
（岗位书那种写法）而适配器报的工具名叫 `WebSearch` ⇒ 报 `violation_aborted`。
`searchGranted`（授予侧）是**子串**匹配，`toolAllowed`（逐次白名单）是**精确**匹配
（`safety.ts` 里那两条各有其理由，都不是 bug）。⇒ 装配时授权名单必须按
各家**实际报出的名字**写，不是按岗位书里的语义名写。这一格不对称记在这里，
测试文件里也钉了（`verifier.test.ts` 里 `GRANTED_SEARCH` 旁边那段）。

## 4. `null` 不是 `[]`：同一个「没有岗位书」在两遍里的两种处置

`mandatoryDomains` 从 `readonly string[]` 改成 `readonly string[] | null`。
`null` = 没有岗位书可读，`[]` = 岗位书说过而领域为空。四格分开：

| 状态 | 事后那一遍（门控） | 事前那一遍（`searchPolicy`） |
| --- | --- | --- |
| 岗位书说了领域 | 按领域判 | 按领域判 |
| 岗位书说了而列表为空 | **satisfied**（不适用） | 无强制领域 |
| **没有岗位书** | **unresolved ⇒ escalate** | **按无强制领域走**（不拦这次搜索） |
| 无观测通路 | unresolved | 拦（`unobservedSearchBlock`） |

第 3 行那一格两遍**不一致，而这是本篇唯一一个我不能反向的地方**：
- 事后那一问答「这份产出够不够格往下走」——没岗位书就答不出 ⇒ 必须吵
  （按 `[]` 处理就是「装配时不接岗位书 ⇒ 第 1 层自动免检」，
  而不接岗位书**不需要改任何代码**，与 `observedSearches` 那一格同一个攻击面）；
- 事前那一问答「这次能不能发起搜索」——没岗位书说不出「这个领域必须搜过」，
  但也**没有任何依据说不许搜**。停掉一次合法的联网去要一份岗位书，
  修的人会在电话里被绕住（「那先给我岗位书我才让 agent 查个版本号」）。

⇒ 缺装配的代价**恰好落一次**，落在有人读结论的地方。
这一格如果两遍都拦，得到的不是更严而是「整条链路停工」，而停工的第一次发生就会有人来放宽整条。

**领域名不认识**也从 `violated` 改成 `unresolved`，理由与 §3 同一族但成因不同：
`CriterionOutcome` 的 violated 分支**没有 why**（内核刻意不让注入方改写门控措辞），
所以一个**拼错领域名**的人会看到岗位书里那句「必须附带可追溯来源」——
他会去让 agent 补引用，补完照旧每次打回。而该改的是一个 YAML 键值。
（0032 §2 那条「不对症的报错」的又一发，只是这次不对称来自**门控的输出形状不在我手里**。）
测试用**规格里真的写着的那四个名字**当夹具（不是编一个坏名字），
并配同夹具的反向对照（换合法名字必须 pass），否则那条 escalate 是「恒不成立」而不是「名字不对」。

## 5. 三态观测：`silent` 与「确实没搜」不能压成一个数

`observeSearchCalls` 交 `counted / not_granted / silent` 三态。压成两态的两种代价各在一侧：
把「我们什么都没看见」写成 `0` ⇒ 每一次没报工具调用的执行都被判「没搜过」而打回
（**把适配器的沉默变成对 Agent 的指控**）；反过来把「没搜过」写成 `silent`
⇒ 就是 `policy.ts` 文件头那句「看不到就当搜过」的攻击面（关掉观测即可绕过，不用改代码）。

三条实现期的判据，各对应一种坏法：

1. **观测源不能是审批记录**。那格（`approvals`，进 `harness_call` 的 payload）看起来最像能复用，
   而它**只在真的问过人时有一项**——`WebSearch` 是 `read_only`（`policy/engine.ts` 里 `websearch` 那一行），
   `needsApproval` 放过 ⇒ 它**根本不在那格里**。拿它当源等于
   「越是不需要审批的工具越数不到」，而搜索恰好全是那一类 ⇒ 第 1 层会对**所有正常搜索**报 `silent`。
2. **计数单位与判定缓存同键**（`verdictKey`，工具 + 参数）。同一发被 ask 一次又被通报一次是**一次**
   （`gateway.ts` 里那段「一次尝试两行不是两次尝试」讲的就是它）。另算一份会得到两个都对
   而数字不同的「次数」，而那个数会进第 1 层的判据。变异 M-B（只按工具名去重）红在
   「不同参数的同一工具算两次」那发上——那一发就是为这个而存在的。
3. **四个出口都要带它**（成功 / 被拒 / 中止 / 压根没开始）。「看不见」本身就是第 1 层要读的值，
   少一个出口就有一个出口读成 `undefined`。

**这条通路今天的真实强度**（别读完上面就当它是审计库）：
数据来自 Gateway 在那次调用里看见的事件，**易失**（`runToolGate` 随那次调用的返回值一起没了），
且刻意不去数审计库。⚠ **这里我第一次写错了一句更省事的话** —— 第一版写的是
「刻意不去数审计库（那要给 append-only 库再造一份读口径，而 `replay/query.ts` 已经有一份，两份必漂）」，
落盘后去核 ⇒ `replay/query.ts` 里 `grep -n "tool_call\|toolName\|harness_call"` **零命中**：
那一层读的是**事件行与全文检索**，**不是**一份「工具调用计数」口径，所以我拿来当「两份必漂」的第二份
是**我不存在的另一份**（§2 那条「我以为别人给了我一个出处」的第 2 次，就在写下它的那一段下面几寸）。
真实的理由有两条，比那句弱而诚实：① Gateway 确实往审计里写行（`deps.audit`），
但**从审计库反查「这次调用搜了几次」需要新写一份口径**（按 `harness_call` 的 payload 反解
`verdictKey` 那一级），而它是**这一层专属**的第二份口径 —— 漂的预言没错，
只是我把「已经有一份」当成事实写了；② 本层的入口只拿到一份 `GatewayDeps` 形状的依赖，
**没有直接读库的能力**，要读就得给 `VerifyInput` 再加一条读通道
（而那条通道一旦被加，它就变成「第 1 层能从库里补一个数」——
那比易失更坏，因为库里那个数是**事后**取而判据在**当时**用）。
一条**既不 ask 也不报**的搜索（内置 WebSearch 直连厂商 API 那一类）在这里是 `silent` ⇒ escalate。
方向保守，代价真实：**用内置搜索的角色每次都要人看一次**——这一格 0024 §7 第 2 条早就记下，
本篇只是把它接上，所以它现在第一次变成**会发生的吵**而不是注释里的一句话。

⚠ **末段那格代价，别漏**：`criterion` 判成 `violated` 时门控只会报岗位书那条 message，
而我们看到的成因（「这次调用根本没被授予搜索工具」）**在门控输出里没有通道**。
所以它只能进审计（`search_observation`）⇒ **只看看板的人会被引导去「让 agent 补引用」**，
而该修的是装配。我没有去改门控的输出形状（那是内核的口径，不在本篇范围），
所以这一格是**已知未解**，不是已处理。

## 6. 判据形状上值得抄的三处

- **「归属」这件事不写在名字里，写在类型里。** `charterMandatoryDomains` 的入参是
  `Pick<Charter, "searchPolicy">`——**类型里没有 bundle**，所以「从包里推」不是不推荐，是编译不过。
  文件头那条 ⭐ 一直是一句立场，这是它第一次有仪器。
- **Gateway 对搜索一个字都不判**：`harness/gateway.ts` 对 `search/observe.ts` 是
  **type-only import**。写成值 import 的那一刻，Gateway 就在运行期依赖了
  它本该只把数据交给它的那个模块——而那正是【规格】§13.3
  「Gateway 不为每家 harness 单独实现搜索」的反面。这条约束**只有 import 形态能表达**，
  所以它写在 import 语句旁边而不是函数注释里。
- **一句「今天不改变任何行为」的守卫要自己声明自己红不了。**
  `gateway.ts` 里那句 `if (stage !== "pre_call")` 走不到
  （`toolVerdict` 只有两个调用点，传的都是 handler / event_stream，当场数过）。
  它是为**将来的调用点**写的（前置那四层也接进同一个函数是最省事的写法）。
  测试钉的是当下那条真事实（前置命中 ⇒ 观测为空），并在旁边写明
  「这一发今天恒绿的原因」。**不假装它是被测试证明过的判据**——
  0030 §9 那个「炸掉的变异同样什么都证明不了」的注释版。
