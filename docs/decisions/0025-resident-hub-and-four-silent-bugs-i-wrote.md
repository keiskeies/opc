## 1. 启动顺序不是风格问题

三条纪律，各自对应一种坏法：

1. **抢锁最先**（早于 `openDb`，因为**迁移也是写入**）。
2. **打开 + 迁移 + 完整性检查在 HTTP 之前**。反过来的话一个库有问题的实例会先对外
   「运行中」几十秒：界面显示绿色、任务点进去 500。可用性的**假象**比明确的停机更难诊断。
3. **心跳最后**，且第一轮必须在迁移之后（未迁移的库上跑 `PATROL_SQL` 报
   `no such table: tasks`，一个会把人引去查心跳模块的错）。

顺序 1 有一个**例外**，是缺陷修出来的，见 §3 第 4 条。

## 2. ⭐ 实测：WAL 不执行「唯一写入者」

动手前量的两条（本机 `node:sqlite`，WAL 模式，两个 `DatabaseSync` 指向同一个文件）：

| 场景 | 结果 |
|---|---|
| 第一个 `WriteQueue` **持有事务**时开第二个并写 | `database is locked`（挡住了）|
| 第一个 `WriteQueue` **空闲**时开第二个并写 | **不报错，两边都写成功** |

第二行是本篇存在的全部理由。WAL 的「一写多读」只在**写的一刻**互斥，它不管**有几个写者存在**。
所以双开的表现不是报错，是两个进程交错写同一个 `events` 表 —— 而它是 append-only，
交错写出来的东西**删不掉**（0014 §3「脏了的审计库删不掉」同一件事）。

**为什么用锁文件而不是 SQLite 层的写锁**，三个理由：

1. `database is locked` **不报持有者是谁**。人会看到一句「库被占用」，而唯一的排查手段是
   猜哪个进程还活着。锁文件里存 `{pid, startedAtMs, host, who}`，报错能直接给出
   `kill 4321` 这样一条**可执行**的动作。
2. **持有写锁会锁死合法的维护写入**（备份 / 迁移 / 完整性检查在 Hub 运行期就不该还能跑）。
   ⚠ 这一条是**反事实**论证而不是今天的现状，两点都要写清楚，否则读者会以为存在三条要被保护的命令：
   ① `hub backup` / `hub migrate` / `hub integrity` 这几个命令**今天都不存在** ——
   `cli.ts` 的 VERBS 只有 `run` / `status` / `resume`（当场查的，我第一版照着想象写了三个子命令），
   备份与完整性检查今天是**库**（`db/backup.ts` / `db/integrity.ts`）而不是入口，
   能跑的只有 `pnpm migrate`、`pnpm hub`、`pnpm hub:serve`、`pnpm hub:maintenance` 四个 script。
   ② 而且**建议性锁本来就挡不住它们**（§2 实测：第二个 `WriteQueue` 空闲时照写）——
   所以这一条真正在说的是「**如果**改用 SQLite 层的写锁，那些旁路写入会被**真的**锁死」，
   那才是选锁文件的理由。锁文件的语义是「**常驻进程**占着这个库」，
   比「这条连接此刻能写」更贴近【规格】§5.1 那句话真正想说的东西。
3. 判**陈旧**需要能读出「谁留下的、什么时候」。SQLite 层没有这个位置。

**代价说清楚，别把它读成一条安全边界**：这是一条**建议性**（advisory）锁。
它挡的是「双开」和「脚本误伤」这两类**无意**的并发写，**挡不住**一个故意绕过它的写入者
（任何人 `new WriteQueue(path)` 都能写）。所以 `events` 上那两条 append-only 触发器
（0001 的 DDL）仍然要留着 —— 锁负责「少发生事故」，触发器负责「事故发生后仍可诊断」。

陈旧判定用**内容里的 `startedAtMs`** 而不是 mtime：mtime 会被 `cp` / `rsync` / 网盘同步改掉，
而这些恰恰是单用户机器上「备份目录被动过」的最常见来源。另有一条**宽限期**
（`LOCK_WRITE_GRACE_MS = 5000`）：pid 探活已经失败而锁是**刚刚**留下的时候**不抢**。
场景很具体 —— 两个 Hub 前后脚启动，前一个刚写完锁就崩，那一刻「探不到 pid = 陈旧」
会让后一个直接抢，而这场竞争里真正该赢的是后一个**报错让人看一眼**。
反向对照有用例（同一份锁内容，时刻推到宽限期之外就该抢下）。

`O_CREAT|O_EXCL`（`flag: "wx"`）而不是 `existsSync` 再写：检查-动作分离留下的那个窗口，
**正是双开发生的那个瞬间**。用例分两发，任何单独一发都不够 —— 一发用 8 个真子进程证明
`wx` 这个原语**恰有一个赢家**，一发是文本守卫，证明 `acquireLock` 用的**就是这个原语**。
只有前者，有人改成 `existsSync` 再写照样全绿；只有后者，原语在某个平台退化也没人知道。

## 3. ⭐⭐ 我自己写出的四个缺陷，全都是「不会崩、只会静默」

这一节是本篇的主要价值。四个都不是编译错误、四个都不会让测试崩、
四个的后果都是「系统看起来在跑而某件该做的事不做了」—— 也就是本仓反复定义为最贵的那一类。

**补记（写完本篇之后跑的变异实验，日期 2026-11-11）**：我把 §3 那四条逐个「按回旧写法」
重放了一遍，结果比四条本身更难看 —— **三处修法当时没有一条用例守着**：

| 变异 | 结果 | 说明 |
|---|---|---|
| 备份区间里插一句 `await Promise.resolve()`（④ 的原始形状） | **全绿** | 「改成整体同步」这句话只活在注释里 |
| 删掉 job 里的 `if (cleaned) return` | **全绿** | 同步改造废掉「等在飞的备份」之后，这是【唯一】还活着的关机/备份互斥保护 |
| 把 `cleaned = true` 挪到 `giveUp` 末尾 | **全绿**（第一版用例下） | 同一缺陷的另一种写法，第一版用例杀不掉它 |

三条现在都有了专门用例，且三条都以「按回旧写法必红」为准出过（各发红 1 条）。
两个值得留下的教训，都不是代码层面的：

1. **「我修好了」与「有人把它改回去会红」是两件事。** §3 那四条我每条都写了用例，
   但 ④ 的用例断言的是**结果**（备份文件在不在、关机后有没有新备份），
   而 ④ 这个缺陷的**形状**是「区间里跨了一个 await」—— 结果类断言杀不掉形状类缺陷。
   补的那发是**源码形状守卫**（扫那一段里不许出现 `await` / `async` / `.then` / `import(`，
   与 `patrol.ts 不得含 setInterval` 同一族），并写明它**证不了**同步性本身，
   只证「那道保护还在」。它同时**会误伤**：挪进 worker 那天它会红，
   而那时正确的改法是连「等一份在飞的备份」+ cancelling 状态一起补回来，**不是删掉这一发**。
2. **并发用例里凡是靠「顺序刚好如此」绿的地方，都要问一句这个顺序是谁保证的。**
   第一版那发用 `fakeServer`（`close()` 立刻 resolve），恢复时机交给微任务排队 ⇒
   拆掉守卫能红，而「`cleaned` 挪到末尾」杀不掉。换成 `pausableServer`
   并**显式断言 close 确实挂住**之后两种都红。真机上「`server.close()` 慢」恰恰是常态。

另外还抓到一条**判据本身的假阳**（不是我的代码，是守卫）：短哈希扫描的边界
`(?<![0-9a-f])…(?![0-9a-f])` 只看两侧是不是十六进制字符，于是**英文单词会被切成一个短哈希** ——
`succeeded` 从第二个字母起、`feedback` 去掉最后一个字母、`deadbeat` 从第二个字母起，
各被切出**恰好七个合法的十六进制字符**（三个词全都含字母，
连「七位纯数字放过」那条豁免也挡不住）。
这里【故意不把切出来的那三段原文写出来】：它们一旦落成字面量，
就正好是这条判据要找的那种东西（七个十六进制字符、而仓库里没有这个提交），
**这段解释自己的文字会被它解释的那个判据报红** —— 这条守卫今天真的这么红过一次。
本篇的 INDEX 条目也因为写了 `succeeded` 红过一次，
而我第一反应是**改措辞**（把它换成「成功标志位」）—— 那是把判据的错
算到被检查的东西头上。改的是判据（两侧都收紧成非字母数字），
实测本仓文档**少扫到的条目恰好只有那一条假阳、74 条真引用一条没丢**；
配一发用例同时钉住「三个词都不报」与「真哈希挨着括号/反引号/句号/中文照样扫得到」。

同一天还抓到**第二条判据自身的错**，形状一样（代码与它自己的注释相反）：
否定重述判定（「这句说不存在 ⇒ 目标真的不存在才放行」）的子句边界，
注释写的是**到下一个 `。；！？` 为止**，代码写的是
`Math.max(tail.indexOf("。"), tail.indexOf("；"), …)` —— **Math.max 取的是最后一个终止符，
不是第一个**。在普通多行注释里两种切法几乎同结果，所以这条错**藏到了遇到
docs/INDEX.md 才现形**：那种文件一条条目就是一整行（实测 4470 字符），
「子句」于是铺到行尾附近，同一行里任何一处无关的否定词都被算到引用头上 ——
当场报了「0025 §3 这句说不存在」，而那句「没有」在 436 个字符之外、说的是 `boot` 的 try。
改回**第一个**终止符（`Math.min` of 非 -1），本仓文档上命中从 2 变 0，
**少的两条都是假阳**、真判定一条没丢；配一发用例（含反向对照：同子句内的否定仍须判真，
且 `。；！？` 三种非句号终止符各钉一发 —— 只修句号的那版实现会被它红）。
两条判据错合起来的教训：**守卫报错时，先怀疑守卫**。本仓的口径一直是
「红的时候先复现判据自己」，这两次我都是先改了被检查的东西（措辞 / 准备改子句逻辑绕过去），
被「当场量一遍」这个习惯才拉回来。

### ① 一个同步抛错的心跳 job 会把心跳**永久锁死**

第一版 `createTicker` 里是 `(async () => { try { await job() } … finally { inFlight = null } })()`
然后 `inFlight = p`。看着等价，实际不等价：**async 函数体在第一个 `await` 之前是同步执行的**。
所以一个同步抛错的 `job` 会先在 `finally` 里把 `inFlight` 置 null、安排好下一轮，
**那时** `inFlight = p` 才执行 ⇒ 一个**已经落地**的 promise 被永久留在 `inFlight` 上。

后果不是崩，是**心跳从此每轮都报「上一轮还没结束」并跳过**，而日志里那句跳过
看起来像「巡检有点慢」。一个同步 `throw` 的 job 在测试里最常见，在生产里也真实存在
（`runPatrol` 的 SQL prepare 阶段就是同步的）。

修法是**从根上消除竞态而不是加补救**：`Promise.resolve().then(() => job())` ——
让调用发生在微任务里，于是 `inFlight = p` 一定先落地。
**五条**用例为这一发而红（把它们按回去重放旧写法，红的正是专门那一条）。

### ② 装配中途失败**不还锁**

`boot` 的 `try` 只有 `catch`、**没有 `finally`**。而 `boot` 的绝大多数失败是**就地 `return`** 的：
完整性检查未通过、迁移失败、HTTP 起不来、心跳参数不合法 —— 四条 `return` **一条都没还锁**。
`catch` 只接住**抛出来**的那一条，而它只有一条。

测出来的现象：一次页面损坏的库被拒绝启动之后，第二次启动报的是
「另一个进程已经持有这个库 · pid 是刚才那个**已经退出**的进程」。
也就是本篇想消灭的那个形状 —— **把一次数据事故伪装成另一个凶手**。

修法是 `try/finally` 配一个成功标志位（下面那个 `giveUp` 只在未成功时被调），且**成功路径的 `shutdown` 与失败路径的
清理走同一段代码**（`giveUp`）。两份清理一定会漂移，漂移的形式是「失败路径少了某一步」。

顺带修的是**校验顺序**：`catch` 之外还漏了一条 —— `acquireLock` 自己会抛（目录不存在、EACCES），
而 `boot` 的契约是**不抛**。就地接住之外还要**补还一次锁**，因为 `acquireLock` 有两种抛法：
写之前抛（没留文件）与写之后抛（读别人锁时 EACCES，此时**可能已经有**一个我们的文件）。

### ③ 一个局部的同名声明让「等备份落地」永远读到 `null`

`backupInFlight` 在 `try` 外面声明了一次、在 `job` 里又声明了一次。内层那份遮蔽外层，
于是清理里那句 `if (backupInFlight !== null) await …` **恒不成立**。

④ 的修法把这一格连带解决了，但这条缺陷本身值得单独留着：它说明**遮蔽**（shadowing）
造成的失效在测试上是**不可见的** —— 那条「shutdown 会等备份」的用例当时是绿的，
因为它断言的是**结果**（备份文件在不在）而不是**这次等待有没有发生**。

### ④ 备份关键区里跨了一个 `await`，于是「等备份」是一个**有时生效**的保护

第一版的备份是 `backupInFlight = (async () => { const {createBackup} = await import(…); … })()`。
两个缺陷：

- 动态 `import` 在模块**已加载**时**仍然让出一个微任务** ⇒ 赋值发生在备份真正开始**之前**，
  而清理读 `backupInFlight` 是**同步**的。那个缝里它读到 `null` ⇒ 不等、直接关队列。
- 前面那句 `await lastBackupAtMs(dir)`（读目录 + 解析文件名，被我写成 async 只是因为签名）
  是**同一族**问题：**判定**与**执行**之间跨了一个 await。

「有时生效的保护」比没有保护更糟：它让写的人以为已经防住了。
修法是**让这一段整体同步**（`createBackup` / `listBackups` 顶层静态 import，区间内零 await），
并加一条 `if (cleaned) return`：关机已经开始时**不再开始**新备份 ——
否则那会是一份**没有锁保护**的备份（清理已经还了锁、关了队列）。

代价写清楚，不粉饰：**备份期间 HTTP 请求会停一拍**（`createBackup` 是同步的 `VACUUM INTO`，
一份大库是秒级）。这里不叫它「不阻塞关键路径」。真要做到不阻塞，唯一稳的形状是挪进
worker/子进程 —— 那时**缝依然存在**，只是变成「谁都能撞上」，所以那时候要配的是一个**显式的
cancelling 状态**而不是这条同步路径。登记在 §7 第 2 条。

## 4. 启动闸门：为什么不是 `report.ok`

`integrity.ok` 会被 `could_not_run` 与 `not_observable` **拉下来**（这是 0007 §4 取舍三的
既定设计：「有一格没跑成」的报告不能被人当「全绿」读走）。**照 `ok` 键启动闸门会挡掉
一大半正常启动** —— 例如调用方没给写队列时 `append_only` 就是 `not_observable`。

所以闸门判的是**一个具体检查的具体取值**：`page_integrity === "violated"`
（`integrity.ts` 的 `pageIntegrityBroken`）。两个消费方（备份 vs 启动）在这里方向相反：
备份那边希望「有一点可疑就别备」，启动这边希望「只挡真的坏了」。
`not_observable` / `could_not_run` **刻意不算**，理由写在那个函数的注释里。

**夹具的形状是被迫纠正过一次**：整文件截断会让 `new WriteQueue` 在 `applyPragmas` 上直接抛，
于是测到的是「库打不开」而不是「拒绝启动」。真正要造的状态是**库打得开、迁移过得去、
只有 `integrity_check` 看得见** —— 也就是「带伤运行」这个诱惑**真实存在**的那个位置。
做法：填 3000 条事件让中间那一页是**数据页**（空闲页写坏不报错，那会让断言绿在错位上），
再把 `floor(size/2/4096)*4096` 那一页整页写成 `0xFF`。

## 5. 每日备份：判据是**日历日**，不是 24 小时计时器

一台笔记本不会连着跑 24 小时。用「距上次 24 小时」的计时器有两个坏法：

- **相位绑在进程启动时刻**。一天重启四次 ⇒ 四份备份，而 7 份保留位被同一天挤满，
  **把上周那份真正有用的挤掉**。
- 反过来，一台**总是当天开机当天关掉**的机器可能**永远到不了**那个 24 小时点
  ⇒ 「每日备份」静默变成「从不备份」。

所以判据是 `shouldBackUp(上次备份的日历日, 今天)`，且**在心跳那一轮上判**
（不是一个独立的定时器 —— 独立定时器同样有相位问题，而心跳已经在跑了）。
用例钉的是三条：同一天 23 小时不备、跨 UTC 零点一秒就备、一天四次重启只有一份
（**外加**第二天同样的四次要多出一份 —— 少了这发反向对照，那个「1」可能只是恒不备）。

「上次备份」的时刻读的是**文件名里的时间戳**而不是 mtime，理由与 §2 陈旧判定同源，
并且**必须与 `backup.ts` 保留策略同一个判据** —— 两处用两个来源，就会出现
「保留策略认为有 7 份而相位判断认为一份都没有」。为此在 `backup.ts` 补了
`backupNameToMs`（`backupName` 的反函数）而不是让调用方手搓正则：手搓的那份在
改名字格式时**不会有人想起去改**，而症状不是报错，是每天重新备一份。解析失败返回 `null`
（= 该备）而不是抛：**多备一份是浪费磁盘，少备一份是丢掉灾难恢复**，方向必须朝浪费那边。

## 6. ⭐ 图运行时**没接**，而这是本篇唯一一个被声明为不可用的能力

我第一版照 `cli.ts` 的 `withHub` 装了一套真图。**那一版是错的**：
它需要 `new SuperStepAuditor({ db: queue.writeConnection() })`，而 HTTP 侧的写入走 `queue.node()`
—— 同一条连接上的**两个提交点**。`real-deps.ts` 文件头量的正是这个形状（P1/P2/P4，
带实测数字）：同连接两次事务 ⇒ `cannot start a transaction within a transaction`，卡片停在 pending。

也就是说那一版会把一个**已知会炸的形状**装进唯一的常驻进程，而它在离线机器上一次也跑不了
（缺 `@langchain`，0009 §2），所以**测试也不会红**。「看起来接上了、跑起来必炸、测试全绿」
是本仓定义为最贵的那一类交付。

修法不在这里：要动的是**超步事务的持锁范围**（0003 那条决策），0010 已经把 P2/P4 带数字
挂给 CEO。我在这里改不动它，也不该顺手改（超步事务横跨节点执行是刻意的：节点体里就是模型调用）。

所以交出的默认工厂是 `unavailableGraphFor()`：**装配时不抛，用到时必抛**。
- 装配时抛会让 `boot` 整个失败 ⇒ 看板也打不开，而真相只是「恢复这一步要人喊一声」。
- `getState` 也走同一条报错，**不能**返回一个「看起来是空状态」的对象：那会让
  `makeResumeGraph` 的选路判成「没有中断」而去 `invoke(null)`，
  而那在已完成 thread 上**不重放节点**（0006 §1）—— 一个**假的成功**（HTTP 200、日志一个字没有）。
- 启动时**警告一次**「本入口未接图运行时」，判据是**装配上用的是哪个工厂**而不是
  「@langchain 装没装上」（后者在这里判不了，而前者就是事实本身）。注入真图时这一句**不该**出现。

**除图恢复之外的一切都是真的**：任务能建、卡片能批、审计能落、看板能读、心跳与备份照跑。
批准之后的行为是 `real-deps.ts` 早就写明的那条补救路径 —— 决策**已提交**（200），
图恢复失败沿 promise 冒到 500 + 原文，报错直接教你跑 `hub resume --task <id>`。

## 7. 已登记的代价（不卡实现，卡「别以为已经做完」）

1. **两个可执行入口**（`cli.ts` 与 `hub-serve.ts`）。原因是 `cli.ts` 顶层 import
   `@langchain/langgraph`，挂上去之后「serve 的启动顺序/退出码/清理」在离线机器上
   **一行都测不了**。代价是人要记住两个命令。
2. **备份仍然占住事件循环**（§4 末）。挪进 worker/子进程是独立一篇，
   且必须**同时**补回「关机时等一份进行中的备份」那一发 + 一个显式的 cancelling 状态。
3. **锁是建议性的**（§2）。故意绕过它的写入者挡不住；append-only 触发器仍然必须留着。
4. **`waitForShutdown` 的窗口**：`boot` 起好 ticker 而信号还没挂上的那一段里
   心跳 fatal 会**静默丢掉**。用一个 `fatalBeforeStop` flag + 挂上时补判一次堵住了，
   但这一格**只被 `runServeCli` 覆盖**，测试进不去那个窗口（要真信号）。
5. **`pnpm hub:serve` 还没有被任何进程管理器管起来**（launchd / systemd / Electron 主进程）。
   （不叫 `hub serve` —— 那个子命令不存在，cli.ts 的 VERBS 只有 run / status / resume。）
   本篇交出的是一个能被 `Ctrl-C` 正常停掉的进程，不是一个**会自动重起**的进程。
6. **本机的可验证性上限**（下面这段是写给读这份文档就想知道「哪些没验」的人）：
   - `test/serve/assemble.test.ts` 里**只有一发**碰真的 `serveHub`（真回环端口 + 真 401）；
     其余都换掉 server —— 「真在听那个端口」由 `test/http/server.test.ts` 覆盖。
   - 跨进程抢锁那一发证的是**原语**（8 个真子进程 + 文本守卫的合取），不是「两个 Hub 真的会撞到这里」，
     因为本仓装不上 `tsx`（0009 §2），带相对 `import` 的 `.ts` 子进程起不来。
     **写一条在本机恒红的用例并把红归因给环境，正是本仓反对的形状。**
   - `pnpm verify` **没跑**（同样原因）。跑过的是：全量测试对基线、`tsc -b --force` 对基线、
     `check-gate.mjs`、以及 §3 那四个缺陷各自的**变异实验**。
7. ⭐ **全量测试同时跑两路会自己造出红条**（本篇写作过程中实测到的，与 Hub 无关，
   但形状与 §3 同族，所以记在这里而不是只写在提交说明里）。
   一次我后台挂着一发全量、前台又跑一发，前台报的是 **1287 tests / 63 fail**，
   其中 **26 条**新红全是同一句 `unable to open database file`。
   我当时给的三个解释（fd 耗尽、macOS vnode 压力、我改的 `integrity.ts`）**三个都是错的**：
   `ulimit -n` 是 1048576、`kern.num_files` 8174 / 上限 245760、而**减掉我这四发 serve 测试里的
   任何一发**都回到 37 fail（减 A 也 37、减 B 也 37 ⇒ 不是任何单一文件的责任）。
   真相：**测试夹具在固定路径**（`packages/hub/.tmp/<名字>`，按测试文件名分，不按进程分），
   而每个测试文件在 `beforeAll` 里 `rmSync` 自己那个目录 —— 于是**同时跑两路全量时，
   两路互相删对方正在用的夹具**。
   最小复现（同一批 4 个 DB 重的文件）：单独跑 **99 tests / 2 fail**；
   两路同时跑 **96 pass / 95 pass**，且**两路红的是不同的条目**。
   这就是 §3 第 ② 条那个形状换了个现场 —— **一次事故伪装成另一个凶手**：
   那 26 条红指的是 `page-check` / `append-only` / `回放指纹` 这些**根本没被改动过**的代码。
   代价与出口：① 全量只能**串行地跑一发**（并行的那一发见下），看到一批同种报错时
   第一件事是 `pgrep -fl "node.*--test"` 确认没有第二路；② 真正的修法是夹具**目录**按
   `process.pid`（或 `mkdtemp`）分。注意 `integrity.test.ts` 里**库文件名**已经带了 pid
   （`ig-<pid>-<序号>.db`）而**目录名没带**，`beforeAll` 又是整目录 `rmSync` ——
   所以**光是加 pid 不够**：文件名分开了，删的还是同一个目录。
   得连「删整个目录」换成「只删自己那些前缀」才闭合。这一格**留给独立一篇**，
   不在本篇顺手改：它要动 24 个测试文件的夹具层（`grep -rl '"\.tmp"' packages/hub/test` 数的），
   而本篇的证据链不依赖它。
   顺带把**跑法的约定**写下来，免得下一个人数出第三个数：本篇说的
   「37 fail」是运行器的**失败用例条数**，「60」是基线文件里 `✖` 行的**去重条数**
   （后者还含 suite 行、文件行与 `failing tests:` 那一行，所以两个数本来就不该相等）。
   两者都出自**独占机器**的那几发：默认并行、`--test-concurrency` 取 1/2/4/7/8，
   五发的红集**逐条相同**（对五份红条清单取摘要，只有 1 个摘要；并与基线文件 diff 过，空 diff）。

## 8. 等待 CEO 决策

见 `docs/INDEX.md` 的登记表。这里只写清楚**为什么这三格不是我定的**：

### 8.1 0010 的超步事务持锁范围 —— 它现在**卡住的是 `pnpm hub:serve` 的图接线**

0010 把 P1/P2/P4 带数字挂出来的时候，读者看到的是一句「approve 在节点跑着的时候不work」。
本篇把它推进了一格：**同一个决定现在决定的是常驻进程要不要装图**。
三个候选，我不选：

1. **超步事务不覆盖节点体**（节点执行完再开事务写审计）。最干净，但要在节点崩溃时接受
   「节点副作用已发生而审计没有这一超步」——那是一个**产品口径**，不是实现细节。
2. **两条连接 + 两个提交点**（HTTP 决策一条、超步审计一条）。不崩了，但两者不再原子：
   批准的审计落了而超步没落，或反之。审计与状态的一致性从「同一事务」降级成「事后对账」。
3. **保持现状 + 人工 `hub resume`**（今天的行为）。多一步人工，代价**全部落在你身上**，
   但一致性口径不变。

今天的默认是 3，而这是**我的临时选择、不是定案**：它不需要动任何既有事务边界，
所以我不必在 CEO 没定的时候替 0003 改口径。**要换成 1 或 2，只需要给 `boot` 传一个真 `graphFor`**
（装配层的其他东西都不用动，这是本篇特意维持的形状）。

### 8.2 `EscalationReason` 到 `approval_type` 的映射缺三格

接常驻 Hub 时才发现的一个具体缺口：升级卡片要落 `approvals`，而 `approval_type` 的枚举里
**没有**放 `insufficient_evidence` / `low_confidence` / `meeting_escalation` 的位置。
今天这三类升级**写不出卡片**（要么塞进一个语义不符的现有类型，要么不落卡片）。
我不编类型名 —— 审批类型是审计里要被长期读的东西，编一个以后改不动。
候选：给 `approval_type` 加三个值 / 加一个通用的 `escalation` 值 + 把 reason 放 payload /
让升级根本不走 `approvals` 而是一张独立表。我倾向**第二个**（枚举不膨胀，reason 本来就是自由维度），
但**这是 schema，得你定**。

### 8.3 `timeout_at` 没有执行者

`approvals.timeout_at` 这一列有、被读、被展示，而**没有任何代码因为超时而动作**。
本篇新增的心跳是**第一个**天然能干这件事的位置（停滞检测已经在扫全表了），
所以我可以顺手接上 —— 但**故意没接**：超时之后该做什么（自动批准？自动升级？只提醒？）
是产品行为，不是「有了调度器就该做的事」。写在 §7 之外是因为它**需要一个决定而不是一行代码**。
