## 0. 本篇补的是哪一格，以及它补完之后仍然没补的是哪一格

0030 §0 末尾登记的事实是：`src/bindings/im.ts` 判据、写侧、读侧全绿，
而**运行时生产调用点 0 处** —— 没有任何一条路径能走到它们。
0030 §9 ② 把它挂成「要不要现在开入口」，并且把我第一版写在 `markVerified` 注释里的
「由入口回答（这条路只开回环）」判为**错话**：当时**一个入口都没有**。

本篇就是那个入口。开完之后，那句话**不再是错的**，但它换成了另一句需要限定的话，
所以两处都改了而不是删掉（`markVerified` 与 `im.ts` 文件头第 2 条，写法见下）：

- **入口有了，但只有 HTTP，而且只有回环。** 没有 CLI，界面只有**读**。
- **「生产调用点」这个数在本篇之后不能再按「函数有没有人 import」来数。**
  本篇之后 `requestBinding` / `markVerified` / `rebindRole` 都有了生产调用方（`http/bindings.ts`），
  而 `resolveBinding` 与 `makeChannelActorResolver` **仍然是 0 处** ——
  复算方式（每个函数名单独 grep，排除 `src/bindings/im.ts` 与它自己的测试）：
  `requestBinding` / `markVerified` / `rebindRole` / `listBindings` 各有生产调用方，
  `resolveBinding` / `makeChannelActorResolver` **一份都没有**。
  ⇒ **「IM 那边能批一次审批」这句话到今天仍然没有主语。**
  本篇开的是**管理这张表的入口**（有人在命令行上把一个人的身份录进去、校验掉），
  不是**消费那张表的入口**（一条真消息进来 ⇒ 解析出角色 ⇒ 允许批审批）。
  0028 §2 那个陷阱的运行时路径**今天仍然不存在**。
  把这两件事混起来读，就是 0030 §0 反复防的那件事：**「接上了」与「跑通了」不是一回事**，
  而本篇之后接上的是**上游**，下游还是空的。

`knownRoles` 那格同样**没变**：`requestBindingRoute` 不注入它（`http/bindings.ts:193`
那条注释点明了 `unknown_role` 这一支今天结构上不可达），
所以「角色存在性被校验」今天仍然**空转**（0030 §8 登记的那格一字未动）。

## 1. 四条路由，全部只开回环 —— 而「全部」这个词我当时是量出来的，不是推出来的

0030 §9 给的判据只针对一条：「远程能自校验绑定 = 任何人可以自己给自己发一个 CEO 身份，
那比『远程能签票』还严重一档」。那条说的是 `verify`。
另外三条**按同一把尺子量**，量完的结论是三条也都只开回环，但**理由各不相同**：

| 路由 | 远程开放最坏的后果 | 是哪一类坏 |
| --- | --- | --- |
| `POST /bindings/verify` | 任何人自封 CEO 身份 | **权限洞**（最重） |
| `POST /bindings/rebind` | 任何人把任意已校验身份打回「正在申请」 | **拒绝服务形状的写** |
| `POST /bindings` | 垃圾能进一张真表，而「有申请」将来是 CEO 要清的队列 | **队列污染**（不是洞） |
| `GET /bindings` | 泄露「谁绑成什么角色、谁在等校验」 | **信息暴露** |

`rebind` 那条是我没先想到的：它**削弱**而不是**授予**权限，
直觉上「它又不给人权力，松一点没关系」。但一次 `rebind` 让 CEO 本人的绑定落回 `verified=0`，
效果是**他从此批不动任何审批**，直到有人在机器上重新校验他 ——
攻击者不需要拿到权限，只需要让权限**暂时失效**，而恢复要人在场。
⇒ **「不授予权限的写」不等于「风险低的写」**。这条判据形状值得单独留着。

`GET` 那条不是我推出来的，是**读回【规格】§20.3** 读出来的：那一条授权「走出本机」的
只有**审批**这一件事，`im_bindings` 这张表不在其中。
我第一版的写法是「读是无害的，只开写就够了」，
那是把「读」当成**信息量低**的操作 —— 而这张表恰好是**整仓信息量最高的一行**
（它说的是「谁能替这家公司做决定」）。

四条**共用一个函数** `assertLoopbackBindingRoute`，而不是在四个 handler 里各写一句
`if (!isLoopbackAddress(...))`：同一判据写四遍，改的人只会改到他正在看的那一遍
（与 `remoteTokenAuth` 复用 `matchRoute` 同一条理由，0027 §1 写过）。

**它返回的响应与「鉴权失败」逐字同形**（只有 `{ error: "unauthorized" }`，不带 reason）。
这是我改了的一次决定：第一版写的是 `{ error: "forbidden", reason: "绑定路由只开回环" }`，
理由很正当（报错要可操作）。
而它的效果是**向一个非回环对端确认「这里有一条绑定路由，而且它有一道回环门」** ——
一个还没通过 HMAC 的探测者，本来只知道「401」，改完就知道「401 + 一条只对回环开放的路由存在」。
今天到不了这一层（非回环签不出名），所以这是一次**纯结构上的收紧**，
但 0027 §1 已经量过同形状的事：**「今天不可达」不是「结构上写不出来」**。

⚠ 这一道门与 `remoteTokenAuth` 那道门**独立成立**，论证与 0027 §1 那条一模一样，
连带**那条「不补」的决定也一样**：端到端上非回环请求在鉴权层就 401，
所以「回环门有没有生效」**在端到端测试里永远测不到**。
本篇的那一发是**直接调 handler**（带真签名的 `peer` 写成非回环 ⇒ 401，
**同一发请求**把 `peer` 换回回环 ⇒ 不是 401）——
一个恒绿的端到端断言与一条根本不需要写的断言，在绿屏上一样，
所以这里**不写端到端那一发**，并把「不写」写在测试文件里。

## 2. `verified_by` 只能从服务端装配来源取：DDL 判据验的是「有没有值」，验不了「这句话是不是真的」

这一节是本篇最值钱的一格，而它**不是安全设计**，是 0030 §4 那条 DDL 判据的**必然推论**：

那条触发器（0005）判的是 `NEW.verified = 1` 时 `verified_by IS NOT NULL AND verified_at IS NOT NULL`。
**它问的是这一格有没有值。** 如果 HTTP 层接受 `{platform, external_user_id, verified_by: "ceo"}`，
那么每一次校验都会**交出**一个非空署名，触发器**永远放行**，
而库里得到一行「ceo 在 14:32 校验过这个账号」—— 写那句话的人就是攻击者本人。
判据一字未改地生效，而它守的东西**整条没了**。

所以：

- `bindingVerifyRequestSchema` 里**没有** `verified_by` 这个键，而且是 `.strict()` 挡着
  （「多带一个键」是一个看得见的 422，不是一次静默的采纳）。
  对应那一发测试断言的是**两件事**：请求被拒，**而且库里那一行仍然没有署名**
  —— 只断前半段的话，「先采纳再报错」这种写法能过。
- 署名只从 `HubDeps.bindingVerifier` 取，来源是 `pnpm hub:serve --ceo <名字>`。
  **刻意没有 `OPC_CEO` 这个 env 缺省源**，与 `--bind` 同一条立场：
  一个会改变「谁能被写进那张表」的参数不该能从环境里漂进来
  （`--bind` 那一条防的是「意外监听公网」，这一条防的是「意外有个默认校验人」）。
- **没配 ⇒ 那条路由 501，而不是 401/403。** 口径值得写清，因为三种码都会被顺手用错：
  401 说「你没凭据」——他有，而且凭据是对的；403 说「有但不许」——策略上确实许，
  是这台 Hub **还没被告诉**「谁算校验人」。
  「还没装配」才是事实，而它的修法（重启时带上那个参数）**只有 501 讲得出来**。
  这条口径与 `api.ts` 文件头那三种「没有」是同一族的**第四种**：
  401 改凭据 / 404 改参数 / 403 换地方 / **501 去装配**。
- `assemble.ts` 里对空白串**再判一次**（不只靠 `config.ts` 的参数校验），
  因为 `boot()` 是公开 API：一个空白串会走到 `markVerified` 被 `invalidText` 拒成 **422**，
  症状指向「你请求写错了」，而真相是启动参数没给。**一个把人支去检查自己参数的报错**，
  正是 `api.ts` 里给 403/404 写过的那同一种病。
- 启动时 `--ceo` 缺席 ⇒ `io.warn` 一次。这不是礼貌：
  不 warn 的话，「校验那一条路由永远 501」这件事只在有人真的去校验那天才知道，
  而形状与同一文件里那条「本入口未接图运行时」的告警一模一样。

**校验人是谁，不是鉴权。** `bindingVerifier` 是**署名来源**，`markVerified` 仍然不判调用者是谁
（它判的是 HMAC + 回环，见 `http/auth.ts` 与本篇 §1）。
「凭什么是他说了算」这件事**仍然没有答案** —— 0030 §9 ①/② 挂的就是它，本篇没有解决它，
只是让「谁校验的」这一格**不会被人自己填**。

## 3. 桌面侧只开读通道：这一格是【判断】，不是【未完成】—— 所以我给它配了一条测试

`IMPLEMENTED_ENDPOINTS` 从 8 条变 12 条，而渲染进程只多了一个方法 `listBindings`。
三条写路由**落地了但没有 IPC 通道**。

这跟本仓那条一般口径（「已实现而未暴露」通常是漏做）**不同**，所以理由必须写在代码里，
而且要配一条测试 —— 否则下一个人（包括下一次的我）看到「四缺一」会**照着补齐**，
而那一次补齐不需要回答任何一个问题。三条理由在 `ipc-surface.ts:110` 起：

1. 那三条的语义前提是「**操作者知道自己在校验谁**」，而渲染进程里没有任何东西能证明这一点。
   桌面壳的渲染进程是一个浏览器上下文；给它一条「把这个账号校验成 CEO」的通道，
   等于让**任何能在渲染进程里执行脚本的东西**拿到那一次写 ——
   一次 XSS 就从「读看板」升级成「自封身份」。
   审批那条通道**没有**这个问题，因为【规格】§11.4 给它准备了更弱的一档（远程只能批可逆项）；
   **校验绑定没有对应的更弱一档**，它本身就是那条最高的门。
2. 那三条今天真正的调用方是**人 + CLI**：校验一个身份要先在**另一个渠道**上跟本人核对
   （0028 §2 说得很明白，签名验的是消息不是人）。那次核对**不发生在渲染进程里**，
   所以做成一个按钮会**伪造出「点一下就行」**这个假象 —— 那比少一个按钮更糟，
   而 0030 §3 末尾记的就是同一种错误（把设计意图写成已兑现的性质）。
3. 因此合法入口是 curl / 将来的 CLI，那条路上站着的是**同机的一个终端**，
   不是**一个能跑远程脚本的上下文**。

**测试**（`test/desktop/ipc-surface.test.ts`）判的是三个方向：
那三条**在** `IMPLEMENTED_ENDPOINTS` 里而 `channelFor()` **返回 null**；
反向对照 `channelFor("GET /bindings")` **等于** `hub:listBindings`（防「判据恒返回 null」）；
主进程源码里**不出现** `/bindings/verify|rebind` 的字面量、暴露方法集里**没有**任何
`/verify|rebind/i`。⇒ 有人加通道时会红，而红的那句话会把他送去读上面那三条。

顺手把 `preload/api.ts` 那格也定了：**不留注释掉的 verify/rebind 桩**。
留了就会有人解开注释，而解开注释这个动作的成本是**一行删除**，
低到他不会在上面停下来读那三条理由。

## 4. 一次假绿：变异跑了 32 发全绿，而我差点把「代码没上场」记成「测试不够」

**现象**：变异 M-B（把 `verifyBindingRoute` 里「只用装配来源」改成「优先用请求体里的
`verified_by`，缺省再回落」）**跑完全绿**。
针对它的断言在 `bindings-route.test.ts:470`，判据正是 §2 那一格。

**我当时的第一反应是错的**：「那发断言没写到位」。
差一步我就去补一条**本来就成立**的测试 —— 而补出来的那条会**更弱**
（因为我会去加一条「形状检查」而不是重跑行为），并把这条真判据埋得更深。

**我做的第二个动作救了这一篇**：先确认变异**有没有真的打进去**。
`grep` 那段字符串在改后的文件里能匹配到 ⇒ 代码确实改了 ⇒ 问题不在补丁，在**加载**。

**真因**：`@opc/contracts` 的 `package.json` 把 `exports` / `types` 都指到 `./dist/index.js`，
而 `node_modules/@opc/contracts` 是指向 `packages/contracts` 的符号链接。
所以运行时 `import { bindingVerifyRequestSchema } from "@opc/contracts"` 拿到的是
**`dist/` 里那份编译产物**，我改的 `src/api.ts` 在那一轮里**一字未被加载**。
`node --experimental-transform-types` 只处理**入口**那一侧的 TS，跨包 import 走的是 Node 解析。

`tsc -b --force` 重跑（重建 `dist/`）之后再跑同一发变异 ⇒ 当场红在**那一条**断言上。

⇒ **写进本仓的一条常规**：**改过 `packages/contracts/src/**` 之后，必须先 `tsc -b --force`
再跑测试，否则那一轮测试跑的是上一版契约**。
这一条对**新增 schema** 尤其致命：新增的键/新增的 schema 在旧 `dist` 里**根本不存在**，
症状不是「行为不对」而是 **import 到一个 `undefined`**，
而 `.strict()` 挂在一个 `undefined` 上会抛在别处，看起来像另一个 bug。

**这一条属于哪一族**：本仓抓过「恒绿的断言」（0006 §7 那一族、0016 那个「什么都没看见的断言引擎」、
0029 §3 那个恒真判据）。这一族此前只登记过**判据坏掉**这一支。
本篇补的是另一支：**判据好好的、被测的东西不在场**。
区分两者的唯一动作是**问一句「我改的那个字节，进程读到了吗」** ——
而这个问题不能靠「测试红了/绿了」回答，因为它两种情况都答得出。

**同族还有一次，方向相反**：我写了一发断言说 `'Feishu'`（大写）应当被拒成 422。
实跑 **201**，库里落的是 `'feishu'`。
**这次是代码对、我错**：`normalizePlatform` 做的是 `trim().toLowerCase()`**在校验白名单之前**
（0030 §2 明写「归一化在校验之前，顺序反了会变成用户手滑打个大写 ⇒ 一句数据库报错」）。
我把 0030 §2 里那句「大小写敏感」读成了**写侧**的行为，而它讲的是**绕过写侧直接改库**那一支
（SQLite TEXT 的 BINARY 排序，所以列里只可能有三种精确写法）。
⇒ 断言改成了「`' Feishu '` ⇒ 201 且库里落 `'feishu'`」，并在测试注释里写明读错的那一层。
**两条错合起来是同一课的两侧**：绿的时候要先问「这一绿是谁给的」，
红的时候也要 —— 那一发红**也可能是我读错了**，而不是代码错了。

## 5. 三处「我把估计当成实测」的老毛病，这次被 doc-refs 抓的正是它

端点从 8 条加到 12 条，`api.ts` / `app.ts` / `ipc-surface.ts` 整体下移，
`test/arch/doc-refs.test.ts` 的快照**六条红**。这一族在本仓是第【六】次，
而这一轮有两个新东西值得记：

**① 快照红有两种，修法完全不同，而屏幕上一样。**
- **目标行内容变了** ⇒ 那句引用可能已经不成立，**必须重读那段论据**再决定改不改文档；
- **只是行被顶走、内容一字未变** ⇒ 只需要挪号。

  本轮六条**全是第二种**（我加的全是注释与 schema，没改任何被引用的语句）。
  但「是第二种」这件事**只能靠逐条 `sed -n '<n>p'` 读原文得到**，不能按 diff 行数推算
  （0027 §5 已经写过这条，本轮照做）。
  我把这个区分补进了 0012 §那条漂移注记里，因为**下一次红的人不会有这段上下文**。

**② 我写那条漂移注记时，自己造了两条新违规。**
第一版写的是「`api.ts` 的第 29 行挪到了第 39 行」这种带行号的形态，而 `doc-refs` 的提取器把它当真引用抓走，
报「**仓库里找不到该文件，或同名歧义没指定目录**」——
`api.ts` 这个基名在仓库里**有两个**（`packages/contracts/src/api.ts` 与
`packages/desktop/src/preload/api.ts`），裸基名 + 歧义 ⇒ 拒。

这个报错**完全正确**，而且它抓的正是我想干的事：**「在文档里叙述我引用过什么」
与「我在引用」这两种写法，在提取器眼里必须长得一样**，
否则任何一条过期引用都可以自称「我只是在叙述」。
⇒ 修法**不是**给守卫加豁免、**不是**把基名换成 `contracts/src/api.ts`（那会让叙述变成活坐标，
以后每次漂移都要来改这句历史记录），而是**改写成不带 `文件:行号` 形状的自然语言**。
这一条与 0030 末尾那条「刻意不写成坐标形态」是同一个手法的第二次使用。

## 6. 判据形状上值得抄的几处

- **路由匹配用字面值而不是通配。** `/bindings/verify` 与 `/bindings/rebind`
  共用前缀，`matchRoute` 里必须**点名第二段的字面量**，匹不上就 `null`（404）而不是
  把这一段当 id。有一条测试专门打 `POST /bindings/verfy`（拼错一个字母）⇒ 期望 `null`，
  另有一条反向对照：既有路由**没被新前缀抢走**。
  被顶替的那种失效长这样：`/bindings/verify` 与 `/bindings/:id` 都注册 ⇒
  顺序决定命运，而两个 handler **都返回 200**，只是做的事不同。
- **方法不互换**：`GET` 打不到写路由、`POST` 打不到读路由，各一发。
- **501 与 500 的分工**：装配缺失 ⇒ 501；判决类型绕不过 `never` 而运行期出现陌生 kind ⇒
  **抛**（500）。后者宁可炸也不当成功，注释里写明「漏分支会被 `never` 在编译期拦住，
  走到运行期这一发说明它绕过了类型系统」。
- **脏行【跳过】而不是 500**，但这个决定住在 `im.ts` 的 `listBindings`，
  HTTP 层不补一份（`http/bindings.ts:132` 写清了方向）：那种行今天物理上不可能存在，
  出现只可能是有人直接改库，而「列表照旧、那一行不在」与「整条列表 500」都拒掉了它当身份用。
  列表接口的读者是扫一眼的人，不是排查的人。
- **`toBindingView` 解析不过就抛，不 skip**，与 `toTaskView` 同一条：
  对外契约的键**恰好**八个（有测试点名键集合），库里多一列不会自动变成契约。
- **`issuesOf` 不 import `ZodError`。** hub 没有直接的 zod 依赖（§5.6.1 的边界），
  所以收一个手写的结构类型。这里我踩了三次编译才找到真形：
  zod 4 的 issue `path` 是 **`PropertyKey[]`**（含 `symbol`），不是 `(string | number)[]`。
  写宽之后**如实记下代价**：`[Symbol()].join(".")` 运行期会抛，
  而这与 `app.ts` 既有行为一致（不是本次新引入的缝）。
  **没有**为了少一行类型去 `import type { ZodError }` —— 那会把依赖边界从 HTTP 这一层拆掉。
