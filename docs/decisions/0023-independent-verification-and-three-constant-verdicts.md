# 0023　独立验证的四维，与三次「恒判定」

- **状态**：已定案（Task 5.4 的产出）。本篇的重心不是那四维怎么分，而是
  **三次「门控在动、结论在出、审计在写，而结论与产出无关」的缺陷**——
  它们全都长在我自己写的代码里，而且全都是我**写完并写了注释之后**才发现的。
- **产出**：`packages/hub/src/harness/verifier.ts` + `test/harness/verifier.test.ts`（33 条用例）。
  另动了 `test/acceptance/phase3.test.ts`（那条「`evaluateGate` 零调用方」的到期断言，见 §6）
- **一句话结论**：这一层最危险的失败不是拦错方向，而是**给出一个与输入无关的结论**；
  三种形态（恒 escalate、恒 reject、恒 pass 的前置条件永远凑不齐）在测试里**都能全绿**，
  因为当时的用例只断言「有一次结论产生」。

## 0. 这一层同样没接上线（0021 §0 / 0022 §0 同一格）

`verifyFix` 在生产里**零调用方**。这一条不是照抄前两篇的句式，它被钉成了断言
（`phase3.test.ts` 里 `callersOf("verifyFix", …)` 为 `[]`），而且它决定了
本篇所有结论的强度：现在是「**凡是走独立验证的**都会过那四维」，不是「每次交接都做独立验证」。

## 1. ⭐ 三次「恒判定」，以及它们为什么能全绿

三个缺陷的**共同形状**：门控调用是真的、结论类型是合法的、审计行是真的落下去了，
而**结论与被审的东西无关**。测试当时全绿，因为它们断言的是「有结论」。

| # | 缺陷 | 后果 | 为什么全绿 |
|---|---|---|---|
| 1 | `evaluateGate` 的 `producer` 与 `reviewer` 两侧都填审阅方 | 每次都 `escalate`，理由「作者不给自己打分」 | 用例只断言「产出了 test_report」，而它确实产出了 |
| 2 | `gate` 默认 `dev_to_test`，而本层产的是 `test_report`（那张表要 `code_diff`） | 每次都 `reject`，理由「包类型不符」 | 用例断言「reject」——**方向对上了，原因是假的** |
| 3 | 没有 `integrityOk` 这个入参 | `evaluateGate` 记一条 unresolved ⇒ 末尾那条「有标准没判成 ⇒ 不能 pass」⇒ 每次 `escalate` | 用例断言「unresolved 里有完整性那一格」，**它正是坏消息本身** |

**#1 的成因是一句听起来对的话**：「这份 test_report 是审阅方产的，所以 producer 填审阅方」。
错在门控问的是「**谁的工作**在被 gate」，不是「这份文件的作者是谁」——
`producer` 是**被审的那一方**。填完之后 `reviewer.roleId === producer.roleId` 恒成立，
而那条判据是**直接 return** 的（不看后面的标准），所以业务标准一次都没被读到过。

**#3 最值得记**：它是三个里唯一一个**修法不是改代码而是补一个入参**的，
而它能全绿是因为我把「坏消息的形状」当成了「正确的形状」写进断言。
`evaluateGate` 那条「unresolved 非空 ⇒ escalate」本身是对的设计
（它自己的注释：最省事的假绿不是伪造覆盖率而是**不提覆盖率**），
我却把它在我这一层的**副作用**（永远判不了完整性）当成了预期行为。
顺带定下一条：本模块**不核磁盘**——制品哈希是 `assemble` 从真实文件算出来的，
我再算一遍就是编第二份证据；所以 `integrityOk` 只能由调用方给，
**缺省时不填**（把它变成 `true` 就是我替调用方对账）。

三次的判别力都由**翻转**证明，不是由「跑绿」证明：
`#1` 的对照是 `verdict.decision !== "escalate"` **且** `bundle.produced_by_role === "test"`
（两格必须能分别坏）；`#2` 的对照是显式传 `gate: "dev_to_test"` ⇒ **必须**因类型被拒；
`#3` 是三条一组：不给 ⇒ escalate、给 `false` ⇒ reject、给 `true` ⇒ pass。

## 2. 派生目录与自己的判据**互相矛盾**（而两边各自都合理）

第一版：`independentWorkspace(authorWorkspace, taskId)` ⇒ `<作者仓库>/.verify/<taskId>`；
同一文件里的 `nested_workspace` 判据拒的正是**互为嵌套**的两个目录。
合起来 = `verifyFix` 拒掉自己发起的**每一次**调用，第一条用例（「一次正常调用应当成功」）当场红。

修的时候有两条路，而**选哪条不该由「测试想要哪个」决定**：
- 放宽嵌套判据（「只是个子目录而已」）；
- 把派生挪出作者工作区。

决定性的是一条**权限不对称**（【规格】§12.7 第 2 层的口径）：作者的 sandbox 是
`workspace-write`，写范围就是他的工作区。审阅目录长在里面 ⇒ **作者有权往审阅目录放东西**
⇒「独立工作区跑出来的结果」是一份作者能预先写入的材料 ⇒ 第一维等于没有。
所以默认根改成 `/tmp/opc-verify/<taskId>`（`DEFAULT_VERIFY_ROOT`），
并留 `verifyRoot` 让生产上指到作者账号写不到的挂载点。

两个佐证：【规格】§12.6 那条示例命令自己写的就是 `/tmp/test-workspace`；
而 `authorWorkspace` 这个入参**只用来比对、不再参与派生**——这个区分被写进类型注释，
否则下一个人会「顺手」用它派生（那是同一个 bug 的最佳再生路径）。

代价说清楚：`/tmp` 重启会清、多用户机器上别人也能写。这一格**没被解决**，
它只是从「作者能写」换成「同机用户能写」，后者要靠部署层解决。

## 3. 第四维（否决权）是我第一版**整条判据都不存在**的那一维

独立性我第一版只写了三维：目录、会话、模型家族。
「审阅这一侧必须是 `enforced`」整条不存在，而漏掉它很自然——
独立性讲的是「**谁**在看」，「看的那一家会不会被我们问到」看起来是网关那一层的事（0021 §6）。

它其实是同一件事：**审阅方的结论要能变成一次拦下，靠的是我们有权不让它继续**。
一家 `toolApproval=false` 的执行器整场不会问我们一次，于是那次「独立验证」
在审计上与一次**观察**完全等价——而 §12.7 第 2 层要的是「测试 Agent 的通过必须能拦住交付」。
所以 `independenceBlock` 的 `pre_call` 分支里加了 `verifier_not_enforced`，
它复用 0022 提出的 `preventionFor`（同一份判据，不写第二份）。

顺带钉了一条**两个条件**的用例：`toolApproval=false` ⇒ 拒、`approvalPolicy="never"` ⇒ 也拒。
只测前者的话，将来有人把 `preventionFor` 改成只看策略，那条用例照样绿。

## 4. 「谎报不在场」这句设计的**边界**，以及它证不了的那一半

§12.6 末段那句「禁止把程序员的『自测通过』文本作为可信输入」，我第一版的反应是写一个
模式表去**识别**谎报。真做的时候发现识别不是主判据：`VerifyInput` 里
**没有任何字段**用来放作者的自测文本——谎报不需要被识破，它**不在场**。
`stripSelfReported` 降级成兜底（防的是将来有人把作者证据包整个传进来）。

但「不在场」只对**入参形状**成立，对**运行期**不做保证：`instruction` 是调用方给的自由文本，
「顺手把 dev 那句话拼进指令」在类型上完全写得出来。这里两条路都不对：

- **拒**：误伤一句**正当**提到这句话的提示词——「不要采信程序员的『自测通过』声明」
  本身就命中模式表，而它是**对的**提示词。误伤的代价是调用方绕开这一层自己拼请求。
- **静默放过**：文件头那句「不在场」变成一句假话。

取中间那一格：**命中就记，不拒**（`instructionFlags`，随审计进回放页）。
「设计上有这道保护」与「这道保护运行期可被绕过」是两句不同的话，
后者必须写在同一处，否则前者会被读成一条运行期保证。

## 5. 我自己这一轮写错的（按被抓顺序）

1. **注释写完、代码没改，而我以为改了。** §1 那张表的 #1（producer 两侧同源）
   我在上一段会话里**记下了「已修复」**，注释也改成了修复后的说法，
   而那一行代码一个字没动。是本轮的**变异脚本**抓出来的：
   变异 #1「把 producer 换成审阅方」报**命中 0 次**——要注入的就是当前已有的那一行。
   这条排第一不是因为它最难，因为它最危险：
   **注释与决策记录都在描述一个不存在的修复**，而那种东西会让人不再去查代码。
   之前的「注释承诺了实现没有的性质」（0022 §4.1）至少还是「性质没实现」，
   这一次是「修复没发生而记录说发生了」。判据补上一条：**变异脚本的注入串
   必须先 `assert` 它命中恰好 1 次**（这条本来就在，本轮正是它救的）。
2. **`condition` 的方向写反**（同一次会话里第二次，0015 §7 记过第一次）：
   我写 `metric:coverage >= 90` 配 `action: reject`，
   而 `GateCriterion.condition` 的语义是「**不合格的情形**」（条件成立 = violated）。
   后果不是报错而是**方向整个反过来**：覆盖率 95 打回、61 放行，
   而「61 ⇒ reject」那条用例当时**是绿的**——它绿的原因是判据反了。
   抓到它靠的是我照计划写的那条**反向对照**（「审阅方报 95 ⇒ pass」）。
   **一条反向对照用例救下了一条方向反了的安全判据**，这是它在这一层最实在的一次回报。
3. **一条永远不通的断言**：`expect("没有返回点的码：" + missing.join(", ")).toBe("")`
   —— 前缀无条件在，所以对任何代码都红。这是「恒绿断言」的**镜像**，
   本文件一路在防恒绿，结果自己写出一条恒红。
   害处不只是吵：它会把人引去改**代码**，而问题在断言。
   想要「红的时候能看见缺哪些码」，消息得放在**分支里**（`if (missing.length > 0) throw`）。
4. **一条恒绿的夹具断言**：`expect(JSON.stringify(req)).not.toContain("自测通过")`，
   而**夹具里从来没有那句话**。它与恒绿断言同族但更隐蔽，因为它的**句式**是标准的
   「负向断言」，读起来完全像在证东西。判据：**负向断言引用的那个串，
   必须先确认真的在输入里**，否则它测的是夹具而不是代码。
5. **一次把 transform 输出再 parse 一遍的断言**：`harnessRequestSchema.parse(req)`——
   适配器拿到的是 transform **之后**的 camelCase，schema 吃 snake_case 输入，必然整包被拒。
   要钉的性质其实是「字段一个不少」，那就直接比键集合。
6. **`VERIFY_REJECT_CODES` 里四个码没有返回点**（`no_workspace_suffix` /
   `author_workspace_unbounded` / `no_criteria` / `no_result`）。删掉并把「每个码都有返回点」
   钉成断言（连 `seen.size === 码表长度` 一起，否则 record 全部没跑起来也会「缺 0 个」）。
7. **两处「我以为存在」的接口**：一度想 import `RISK_TIER_INDEX`，以及把
   `sameFamilyReviewBlock` 的返回码当成我自己的码表直接透传。都是**按印象补事实**
   （0021 §9 第 13 条 / 0022 §6 第 5、6 条同一族），这次靠 tsc 与一次 grep 拦住。

## 6. `phase3.test.ts` 那条「零调用方」断言**如期到期**，而缺口只是上移了一环

`test/acceptance/phase3.test.ts` 钉着 `callersOf("evaluateGate") === []`，
并且那段注释**明说**它是「一条会过期的断言：有人消掉一条缺口，`callersOf` 那两发就会红」。
本轮它红了。

红之后**不能直接把期望值改成新值收工**，得先问：**缺口真的消了吗？**
实测没有——`harness/verifier.ts` 开始调 `evaluateGate`，而 `verifyFix` 自己零调用方。
所以缺口**上移一环**：以前是「门控对，但没人对门的时机调它」，
现在是「有一个正确的调用方，但没人调它」。**结论强度没有变化**。

于是那条断言改成配对判：门控的调用方**是** verifier，而 verifier 的调用方**是空**，
并在 blocker 清单里把那句话从「零调用方」改成「上移一环，没被填上」。
这一格的处理方式是本篇最想留的一条纪律之一：
**一条断言变红时，先判它是「缺口被填上」还是「缺口换了位置」**，
两者的正确反应完全不同（前者更新断言并前进，后者更新断言并**写下没前进**）。

## 7. 这一层证不了的（写在这里而不是等人踩）

1. **四维里有两维在调用之后才知道**（会话、实际模型家族）。那时审阅已跑完、预算已花掉。
   我的口径是「事后不过 ⇒ 结论不采信」，而不是「跑了但照样算通过」。
   代价：**花钱买一次不算数的审阅**这件事本身没有任何拦截——
   要拦得住，得能事前预知适配器会用哪家模型，而那正是适配器可以不听我们的地方。
2. **「独立工作区」在这里是路径字符串 + 一次权限论证，不是一次隔离证明。**
   没有 chroot / 容器 / 单独用户。§2 那条权限不对称只保证**默认根**不在作者写范围里，
   不保证审阅方进程不会通过绝对路径读到别处（那要靠 harness 侧沙箱，Task 5.5）。
3. **`assemble` 是完全信任的回调**。本模块只核 sha256 的**形状**，不核内容来源。
   一个说谎的 `assemble`（交回编造的 metrics）在这一层**结构上不可检**——
   能检它的是 `integrityOk`（调用方对账磁盘）与门控之后的抽样，都不在这一层。
4. **`SELF_REPORTED_PATTERNS` 是子串表**，漏检面显然存在（换一种说法就绕过）。
   它不是主判据（§4），所以漏检的代价是「兜底少兜一句」，
   但这也意味着**不要**因为「表不全」去把它升级成主判据。
5. **同家族判据只比 `modelFamily` 字符串**。两家不同厂商但同族（或一家谎报家族名）
   在这一层判不出来——这与门控层是同一个已知边界（0013 / 0016 记过），不重复论证。
6. **本模块不产 sha256**（文件头那条）。所以「证据可验证」这句话在这一层只到
   「形状对 + 由调用方算」，**没到**「内容与磁盘一致」。后者要等接上 `EvidenceStore.verify`
   的调用点，而那个调用点今天不存在（§0 / §6）。

## 8. 需要 CEO 定的两项

### 8.1 独立验证的**默认预算与触发范围**

【规格】§12.6 第 2 条要求「修复后独立验证」，但没说**每个任务**都要，还是**只有风险档
不可逆的**任务要。这一层是纯增支（多一次 harness 调用、多一个会话），而它当前的
成本参数只能由调用方每次现填（`maxBudgetUsd`），没有任何默认。三个候选：

- **A**：每个 `bugfix` / `feature` 任务都做一次独立验证，预算默认 = 开发段预算的固定比例；
  代价是**简单任务也要花两份钱**，且比例是我编的（规格里没有这个数）。
- **B**：只有风险档 = `irreversible` 的任务做（复用 0022 §4 那条风险轴）；
  代价是**风险档由被约束方标记**这一老问题（0022 §4 就是因为它才只做收紧那半边）。
- **C**：由测试角色的岗位书声明触发条件（最贴 §12.6 的「岗位书硬约束」口径），
  代价是**今天没有可写的岗位书**——0015 §1 记过 `role_charters` 跑完迁移是 0 行。

我倾向 **A + C**（默认都做，具体阈值进岗位书），但 A 里那个「固定比例」的值我不编。

### 8.2 `verifier_not_enforced` 在**只有一家可用**时怎么办

现在这一条是**硬拒**：如果唯一接通的执行器 `toolApproval=false`，独立验证**根本不能跑**。
两个候选：

- **甲**：维持硬拒。代价是「只装了一家非审批型 harness」的部署**永远没有独立验证**，
  而它看起来会像 bug（没有任何地方说「你缺一家审批型执行器」，只在调用时报拒）。
- **乙**：允许跑，但把结论降级为「**观察**」并**禁止**它满足任何门控（§12.7 第 2 层
  要求测试 Agent 的通过能拦住交付，观察不能）。代价是多了一条「有验证记录但不算数」的
  状态，而它极易被误读成「验证过了」。

我倾向 **甲 + 一处改进**：硬拒保留，但在**启动时**（而不是调用时）就报
「当前没有任何具备审批能力的执行器，独立验证不可用」，让它成为一条能看见的部署缺口。
