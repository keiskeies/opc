## 0. 你要的东西，一句话

不只是任务状态机。你要的是一个**群**：

- **一个群 = 一个任务。** 建群即立项；群里所有角色围着这一个任务转。
- **每个角色你都可以单独私聊**——比如直接找助理问「最近所有项目进度」，她要能给你汇报。
- 你在群里发任务 → **交给特助** → 特助把任务层层分发下去；**各级领导自己拉人**（CEO 只发布任务，要什么人领导定）。
- 群里的角色各用自己的「任职方式」干活：开发跑 claude-code、测试调 MCP 平台、运营跑内置角色插件 + 指定模型、总监们用纯模型执行器。
- 只有**需要你拍板**的事，特助才 @ 你；你做一个决定，然后流转继续。
- 你看到的是**群的对话流动**（还有每个角色的一张脸），而不是一堆状态卡。

## 1. 现在系统是什么（现状，不粉饰）

仓库 `D:\item\opc` 是一个底层流转平台。已经有的：

| 层 | 有 | 缺 |
|---|---|---|
| 任务流转 | 任务状态机（tasks 表）、handoff/拆解边、返工上限、状态卡 | 「群」这个容器概念；会话（消息流）视角 |
| 角色 | `COMPANY_NODES`：intake / charter / product / tech / dev / test / report 7 个固定节点；每个节点一份 YAML 岗位书（`roles/loader.ts` + `resources/charter-templates/`） | 角色集合是**写死的**；没有「我在群里任命一个角色」的动作；没有角色↔模型/工具绑定 |
| 审批/拍板 | 审批卡（approvals/cards.ts）、人席卡（engine/seat-card.ts）、CEO 批准路径、门控 review_gates | 「@ 我」的呈现（群消息式）；特助视角的「该找老板了」动作 |
| 角色执行 | 引擎路线：一个节点 = 一次 `claude -p`（engine/claude.ts + work.ts），下一步找谁由模型自己说 | 只能跑 claude-code 一个执行器；没有「测试角色调 web 平台/MCP」「运营角色跑插件+指定模型」这种执行器分派 |
| 界面 | 看板（表格/卡片视图）：任务、审批、组织图、预算 | 对话/会话界面（类飞书群） |
| 群/会话概念 | —（完全空白） | 群、成员、消息流、@ 提醒 |

一句话：**流转的心跳有了（状态机/门控/审批/岗位书/审计），缺「一群角色围着项目说话的壳」+「每个角色的手脚怎么接」**。

**设计师汇报线（2026-11-23 搜证落定，你让我搜的）**——真实公司两种主流形态：

  完整公司需要**角色表可配置**（B.1 的 `role_id: test_engineer`、`reports_to` 树），
  群成员 = 这个角色谱系里的实例。

### 1.1.2 还缺的角色：两张清单（搜证：传统公司 + AI 原生组织 + 一人公司实操）

§1.1 摊的是主设计文档的角色；但主设计文档自己是**产品技术型公司**视角。对照
「一个稳定的公司架构是公司稳定的基石」——传统公司该有的职能和 AI 组织特有的
治理角色，还缺两类。缺的列全，**「现在要不要」由 §4 决定，这里只做缺口盘点**。

**A. 传统公司的支撑职能（现在完全没有）**——参照六类岗位分法（战略决策/运营交付/
财务风控/人力组织/市场增长/技术数字化）与经典述职（CEO/CFO/COO/CTO/CMO/HR）：

| 缺失职能 | 在真实公司里干什么 | 现在的底线 | 现在的底子 |
|---|---|---|---|
| **财务 / CFO** | 预算、现金流、成本、应收应付、经营报表 | 一人公司不一定要真账本；但**预算硬停**（Paperclip 有，我们的章程/预算机制雏形有）需要「谁管钱」 | ⚠️ 已有 `charter/budget-sync.ts` 预算机制，但没有「财务」这个角色视角 |
| **人力 / CHRO** | 招聘、绩效、能力梯队、组织发展 | 一人公司里 = **角色任职配置**（谁能干什么、谁被提升/降级、谁离职），是「任职」的另一个名字 | ❌ 只有岗位书文件，没有「人力资源」决策动作 |
| **法务 / 合规** | 合同审查、风险拦截、合规留痕 | AI 一人公司里被反复强调为**最关键的第七个 Agent**（不让老板变成所有 Agent 的对接人/审核员/背锅侠） | ❌ 没有合规/风控角色 |
| **市场 / CMO** | 品牌、增长、获客 | 我们已有「内容创作/平台适配」但没有「**获客与增长策略**」这一层 | ⚠️ §15 运营子组织缺「增长」这条线 |
| **销售 / 客户成功** | 成交、交付后维护 | 一人公司做订阅/交付时，谁跟进客户 | ❌ 没有客户侧角色 |
| **行政 / 运营支持** | 日常运转、跨部门协调 | 一人公司里这部份被特助吸收 | ✅ 特助已覆盖，不入列 |

**B. AI 组织特有的治理角色（现有组织范式没写）**——AI-native 组织共识：
「组织需要能说'不'的 AI」——AI 审计、AI 合规官、AI 投委会成员；管理者的角色在
变成「编排者」；新涌现 AI Agent Manager / Intent Engineer（把业务目标翻译成 agent
可执行指令、监督自治 agent 运行、验证输出）。

| 缺失角色 | 干什么 | 现在的底子 |
|---|---|---|
| **AI Agent Manager（编排/监督自治 Agent）** | 监督自治 agent 运行、验证输出、把业务目标翻译成 agent 指令 | ⚠️ 特助的分发逻辑将来是它的雏形，但「监督/验证/回滚」没有角色化 |
| **AI 审计 / 合规官** | 定期抽查 Agent 产出、看合规风险、看权限有没有被滥用 | ⚠️ 有事件/审计表 + review_gates 门控，但审计是**机制不是角色** |
| **数据/复盘（已有雏形）** | 看趋势、出经营分析 | ✅ report 节点 + 数据复盘 Agent 已在 §15 |

**缺口总判**：完整公司 = A（经营端支撑）+ 现有谱系（生产端）+ B（AI 治理）。
「一个稳定的公司架构是公司稳定的基石」——这句话指向的正是**别只有生产端**：
没有财务/合规/审计的「公司」跑久了，预算超支没人拦、风险没人兜、依赖单点。

**v3 定稿**：你已拍板——
- **A 类全部第一版就有人**（你第 9 条：财务/人力/法务/市场/销售都先进第一版）→ 种子角色表全部激活（§1.1 树已加）。
- **B 类在底层、不展示**（你第 10 条：治理角色在底层支撑流转，谁说话/谁拍板/谁指定下一步靠调度，不能全 CEO/助理决断）→ §2.6 底层治理/调度层。

### 1.1.3 群与完整公司怎么合一

你要的「群里拉各种角色」= 从上面这张角色谱里**选人建组**：

- **群 = 一个任务**（v3 定稿，你第 1 条）；成员 = 角色谱中的角色实例（`role_id` + 任职配置）。
- 默认就是 §3.1 的完整公司树（含支撑职能，全激活）；你建群时可以**自定义选择**（你第 7 条）+ 各级领导拉自己人（你第 2 条）。
- 特助默认加进来（你第 7 条）、系统内置席位（你第 3 条）；你（CEO）是群的最高拍板人。
- 每个角色实例携带自己的任职配置：执行器类型 + 模型配置 + 岗位书（选哪份 YAML / 覆写）。

这时「项目经理 / 测试工程师 / 开发 / 产品经理 / 运营 + CEO 特助」的群就是角色谱的一个子集实例——
同一个谱系，你拉谁进群、怎么配，随你。

§1.1.2 的两份清单不是「角色不够先不做」：它们是不想被 `COMPANY_NODES` 7 节点钉死的理由——
**角色表要可配置、能加角色**。v3 定稿：A 类全第一版激活（§1.1 树），B 类在底层不展示（§2.6）；
自定义角色（如你的设计师、将来别的）随时可加，改的是**角色表的种子数据 + 一份岗位书**，不是改引擎。

## 2. 目标形态（要做成什么样）

三层：

```
┌─ 群层（你要的应用）──────────────────────────────┐
│  群（=一个任务）→ 成员（角色实例）→ 会话流（消息）   │
│  发任务 → 特助分派 → 角色们干活 → 拍板@你 → 继续   │
├─ 角色任职层（角色↔执行器绑定）───────────────────┤
│  程序员=claude-code / 测试=某web平台(MCP) /         │
│  运营=内置角色插件+指定模型 / 特助=分发器+@老板     │
├─ 现有流转内核（不改动，借底层）───────────────────┤
│  tasks 状态机 / approvals / review_gates /           │
│  org graph / 岗位书 / 审计 / evidence              │
└──────────────────────────────────────────────────┘
```

### 2.1 群（Group）——一个群 = 一个任务（已拍板）

- **一个群 = 一个任务**（你拍板：群=任务，不是群属多个任务）。建群 = 立项。
  群的属性：群名、任务描述、所有者（你）、成员列表、关联的 org graph 子路径/进行中的任务 id。
- **任务即群**：你在群里发的那条「任务」就是本群的唯一任务；群的整个运转（成员、会议、门禁、汇报）都围绕它。
  一个任务做完，群可以归档，也可以换个新任务复用同一批成员（同一个群容器，任务换绑）。
- 建群动作：`新建群（=新建任务）→ 写任务描述 → 特助默认拉进来 → 各级领导拉自己人要的角色 → 群成立`。
- 成员 = **角色实例**，不是裸角色：同一个「产品经理 雷军」可以出现在两个群里，但各自独立
  （各自的任职配置、各自的上下文）。这正好落在现有 7 节点 + 岗位书之上：**成员 = CompanyNode + 该群的实例配置**。

#### 2.1.1 单角色私聊（你拍板：每个角色都可以单独跟我聊）

- 除了群聊，每个成员对你都有一个**私聊会话**（1:1 线程）。
- 例子：你直接找特助/助理 → 「最近所有项目的进度」→ 她要能**汇总所有群**给你汇报。
- **私聊跨群默认放开**（你最后一条：每个角色自己加入的群都能看，每个角色都是个正常人）——
  **所有成员**都看得见自己加入的每个群（能读各自的群消息/进度/backlog），特助/产品经理不需要特殊跨群权；
  跨群 = 成员自己群列表的自然展开，不是给谁开的特权。
  读放开、写仍限职权：跨群能**读**自己的群（汇报/上下文），**写**（发布/拍板/操作面板）仍限本群本岗位书职权
  ——「正常人」也不会在没被授权的群里发号施令。
- 私聊与群聊并存：群聊是事件流（会议/门禁/流转），私聊是你对单个成员的询问/指示。
- 私聊同样入库（`messages`），可审计；这里走 `conversations` 表，群聊走 `group_messages`，两者同源不同视图。

### 2.2 特助（Chief-of-Staff / 分发中枢）——系统内置席位（已拍板）

- **特助是系统内置席位**（不是你可删可建的角色）：每个群都有特助，分发中枢。
  你拍板：特助**可以自定义模型和形象**（跟其他成员一样能配 persona/modelTier），但席位本身系统内置、必在群里。
- 特助要做：
  1. **理解任务** → 拆成子任务/阶段（现有 dispatch 的 DECOMPOSING/拆解边可借）。
  2. **层层分发** → 按群成员的角色能力分配给最合适的人（现有委派边 + 组织图可借，
     但「群成员映射」是新增）。
  3. **汇总与上报** → 子任务结果汇回特助；只有需要你拍板的事，特助 @ 你
     （现有 approvals/人席卡/CEO 批准路径可借，**呈现方式**要新）。
- 关键判据「什么时候该 @ 老板」初定：需要授权花钱/改边界/超出成员职权的事件，
  现有 `HUMAN_EDGES` + `seat-card` 已有雏形，转成「特助说：老板，这个要你定」。

#### 2.2.1 特助的系统内置与非内置边界

- 席位系统内置（不能删、建群自动带）；但**占位/模型/形象可配**——它是系统席位，不是系统机器人。
- 特助的「人格」也可以挂蒸馏（如范冰冰做特助），但**分发逻辑本身是系统能力**，不随人格换。
- 其他角色（产品/开发/测试…）= 普通席位，可自定义（见 §2.3.2）。

### 2.3 角色任职（Role Assignment）——核心空白

成员不是「挑个执行器」，而是**一个有名字、有脸、有人格的数字员工**——像招聘一样办入职：

```
成员 = {
  persona: {  名字, 头像, 口头禅/相处基调（可选）, 人设简介,
             characterPrompt（提示词，你第 12 条：蒸馏数据 = 一段提示词） },  ← 外貌 + 人设提示词
  roleId,                                                           ← 岗位（power）
  skill: [ 人格蒸馏（雷军 / 范冰冰…= 一段提示词，女娲 skills 现成）... ],  ← 人格（脑子）§14
  executor: { 类型, 参数 },                                          ← 手脚
  modelTier,                                                        ← 模型
  context,                                                          ← 上下文/记忆
}
```

三个例子就是你刚说的：

#### 2.3.1 招聘流程（你拍板：完整招聘页，未来做人才市场）

建成员不是「表单里挑个角色」，而是一个**完整招聘页**（你拍板）：

1. **选岗位**（roleId 从角色表选：产品经理/开发/测试/…）。
2. **填人设**（persona：名字、头像、口头禅、人设简介——张三、雷军、范冰冰都是这一格的取值）。
3. **挂人格**（可选）：从人格库选蒸馏包（`leijun-skill-v2` 等），**挂哪个、来自哪、置信边界**写进审计（§14 红线 2）。你第 12 条说透了：**蒸馏数据只是角色的一段提示词**，不是别的玄学机制——它就是 persona 里的 character prompt。
4. **定手脚**（executor：claude-code / 插件 / 纯模型 / MCP 平台…）。
5. **定模型**（modelTier 覆写）。
6. **入职** → 产生成员实例 → 可被拉进群、可被任务分派。

- **人格（skill）与岗位（roleId）分离**：雷军蒸馏可以挂产品经理，也可以将来挂运营总监；换人格 = 重挂 skill，不换岗位书（§14）。
- **所有数据入库**（你第 13 条）：persona / skill 挂载 / executor 绑定 / 入职动作全部落库（`members` / `member_skills` / `member_executors` / `hire_events`）——不然没法分群分任务。
- **人才市场**（你第 11 条 + 你最后一条「都要放第一版」）：招聘页就是共享/买卖特色员工的入口——大家都可共享自己的特色员工（如「雷军产品经理」），每个员工 = 一段有特色的提示词 + 配置（persona / skill / executor / modelTier 全落库）。**共享 / 导出 / 导入一并做进第一版**：
  - **导出** = 员工打包成可迁移的「提示词+配置包」（persona / characterPrompt / skill 引用 / executor / modelTier 的 JSON 或 skill 包）；
  - **导入** = 从市场或他人分享的包直接入职为成员实例；
  - **挂牌发布** = 发布到人才市场（名称/描述/版本/售价可选）。

#### 2.3.2 自定义角色（你拍板：内置不可删、自定义可删、结构约束）

- **内置角色不可删除**（`role_id` 属于内置集合），**自定义角色可删除**（但要先解除入驻——它一旦用了就不能有成员还在岗）。
- **结构约束**（你第 6 条）：在公司树里加角色必须**先保证组织层级结构**——比如你要在产品总监下加「设计师」，位置必须在产品总监的子树内（reports_to=product_director），不能挂到别的部门下。角色表是树，插入节点 = 指定 `reports_to`。
- **内置先在角色表里补「设计师」**（你第 6 条：这个设计师你应该先加入内置角色）：产品总监 → 设计师，执行器默认 pure-model + 指定模型（视觉生成可接内置插件，见 §2.4 builtin-plugin）。
- 自定义角色可以改名字/头像/人格/执行器/模型（同 §2.3.1），但**不能改内置角色的 role_id 与汇报线**。

### 2.5 流转节奏（DevOps 化）——什么时候埋头做、什么时候开会、什么时候汇报

你要的「DeVops 那种 CI/CD 可持续开发/持续部署」落到任务流转上，不是把任务当
「一个接一个」，而是当**一条有门禁的管线**：主线的节奏感来自「会议/定期事件」，
防错靠「门禁」，机会靠「产品经理持续调研 → 进面板 → 开会 → 升级任务」。这套节奏直接借
敏捷 + DevOps 的既定实践，映射到本系统：

**节奏事件（Scrum 五事件 → 群事件）**

| 敏捷事件 | 本系统的对应 | 频率/时长 |
|---|---|---|
| Sprint 计划会 | **冲刺计划会**：特助拉群成员排优先级，定本冲刺目标 + 拆任务 | 每 1-2 周一次（群内一条「计划会」消息） |
| 每日站会 | **每日巡检**：特助代你问「昨天做了什么 / 今天做什么 / 有什么卡点」，成员各自报（不进群刷屏，汇成一条摘要） | 每天一次，15 分钟量级 |
| Sprint 评审会 | **冲刺评审**：特助汇总本冲刺产出，演示/展示给相关人（你 + 产品经理） | 每冲刺末 |
| Sprint 回顾会 | **冲刺回顾**：数据复盘 Agent 出「什么好什么不好」，改进清单进下个冲刺 | 每冲刺末 |
| 持续调研 | **产品经理每日调研**（你明确要的）：竞品/开源/商用/技术新方向 → 产出「升级建议」→ 进任务面板（§2.5.2）→ 开会讨论（§2.5.1）→ 采纳才进执行线 | 每天（可配频率） |

**关键点：会议不是路演，是产出决策。**（搜证的升级机制教训之一：会议没结论 == 没开会）
群里的每条「会议消息」必须带三样：**决策 / owner / 截止时间**，哪怕决策是「暂缓」也要写明截止。

**门禁（DevOps 质量门 → 任务门禁）**

- 现有 `review_gates` 本来就是质量门——测试未过/P0 未解决不得标记通过。**但要 MySQL 那 72%/26% 的教训：门禁不强制等于没有。** 规则写进 `quality_gates`（门槛 + 阈值），不达标直接拦。
- **门禁从基线出发逐步收紧**（DevOps 指南）：一开始要求过高把团队逼到绕开门禁，就会失去信任；先定先生效的少量门槛，逐步加。
- **快而准的检查放前面**（测试金字塔）：单元（提交时）→ 集成（合并时）→ E2E（发布前）。越便宜越快越前。

**升级/汇报（escalation，什么时候找老板）**

现有 `HUMAN_EDGES` 已有人席卡雏形；价值在「阈值清单」：

| 升级触发 | 找谁 | 携带 | 对应现有 |
|---|---|---|---|
| 超出本级职权（花钱/改边界/对外承诺） | CEO（你） | 请求内容 + 需要你批的东西 + 影响 | approvals/人席卡 |
| 技术卡点超 2 次返工/方案冲突 | 技术总监 | 冲突双方方案 + 证据 | review_conflict_rounds |
| 冲刺目标严重偏离（时间/范围/质量） | 特助汇总 → CEO | 偏差 + 建议 | 进度延误 |
| 产品经理的升级建议（新方向） | CEO 拍板要不要采纳 | 竞品/技术调研 + 预期收益 | —（新增） |

**升级是请求决策/资源，不是告状；升级必有答复，不能「再看看」。** 系统保证：升上去的事，
在时限内必须有一个明确答复（批准 / 否决 / 再收集但给截止日）——否则升级者得不到回应，
下次就不升了，慢慢事故才浮出来。

**产品经理持续调研 → 升级任务的闭环**（你要的核心，可按你第 15 条：不立马下发）：

```
每天：产品经理（雷军人格）调研竞品/开源/商用/技术新方向
  → 产出「升级建议卡」（依据 + 预期收益 + 影响面）
  → 进任务面板（§2.5.2，草稿/待评审）——不是自动下发
  → 开会讨论能不能做（§2.5.1 真实会议）→ 采纳才转成任务进执行线
  → 执行线进入常规门禁管线：计划会排期 → 开发 → 测试 → 评审 → 是否上线
  → 产品经理在面板可 取消/前移/delay/改优先级/拆分/合并（§2.5.2）
  → 你的角色只在「值得不值得做」和「上线放不放行」上出现
```

**项目经理决定上线/升级**（你要的另一条）：项目经理（或你任命的角色）拥有
「共系列程线内标志生产/上线」的权限——门禁全过 + 评审通过，他就能标记「可上线」；
需要你拍板的是**超出门禁范围的放行**（改动边界/换技术栈/花钱超线）。这就是「产品经理
持续向下发升级任务」+「项目经理决定上线」两条自主线，而你只在「边界/钱/战略」三件事上出现。

**一句话总结**：埋头做（成员独立执行）→ 每天对节奏（站会摘要）→ 定期对齐（冲刺计划/评审/回顾）→
升级只在「超出本级范围」时发生（阈值清单）→ 门禁决定能不能交 → 产品/项目经理的自主线
让系统不需要事事找你，你只在边界/钱/战略三件事上出现。

#### 2.5.1 真实会议（你拍板：每个角色的发言、下一步谁发言、会议结论都要有）

不是「发一条会议消息」，是**跑一场真会议**（你第 14 条原话：不同角色和模型给出的想法不一样，我要一个真实的会议）：

- **会议 = 一个真实流程**：谁主持、有哪些与会角色、谁先发言、谁有资格接话、每个人说什么。
- **发言序列**（你拍板）：不是所有人一拥而上，而是**按主持人的议程走**——主持人问「产品经理先说」，雷军（产品经理）发言；他说完，主持人点名「技术总监怎么看」，技术总监回应；每一步**下一位发言者由主持人/上一位指定**，形成活的对话流（就像真会议里「老王你接着说」）。
- **每个角色的发言按他自己的 persona + 模型产出**（你第 14 条：不同角色和模型给的想法不一样）——同一件事，雷军产品经理（deepseek-flash + 雷军蒸馏）和范冰冰助理（glm5.3 + 范冰冰蒸馏）说的就是不一样。
- **会议结论必须落定**：会议结束必须产出 **决策 / owner / 截止时间** 三件套；没有结论的会 = 没开（§2.5 一致性）。
- 会议记录 = 发言序列 + 每一步谁说的 + 最终结论，全部入库 `meetings` 表，可回放、可审计（现有回放视图可借）。
- 决策 → 直接变成任务流转的输入（会议结论进 dispatch，成为下一步动作）。

#### 2.5.2 任务管理面板（你拍板：不是「调研就立马下发」，而是进任务面板）

你第 15 条说透了：**产品经理调研了就一定要立马下发？** 能不能做还要会议讨论；而且新改动该进**任务管理面板**（像正常项目进度管理工具那样）：

- 产品经理的调研/升级建议 → 进**任务面板**（草稿/待评审），不是自动变成群里下发的任务。是否值得做 → **开会讨论**（§2.5.1）→ 决定采纳才进执行线。
- 任务面板 = 正常的项目进度管理工具视图：**待办 / 进行中 / 待评审 / 已上线 / 已取消** + 甘特/看板（现有看板可借）。
- 产品经理（或授权角色）在面板上能做的操作（你拍板）：**取消 / 前移 / 后移（delay）/ 改优先级 / 拆分 / 合并**——像操作一个真正的项目 backlog。
- 任务面板与群关系：群 = 当前任务，面板 = 这个群的任务流视图（一个群的 backlog）；不同群的 backlog 彼此独立；
  成员都能看自己加入的群的 backlog（§2.1.1 跨群默认放开）；产品经理对面板的**操作权**（改期/取消/拆分/合并…）按岗位书职权限定。

### 2.6 底层治理/调度层（你拍板：治理在底层，不展示；不能让 CEO/助理包办一切决断）

你第 10 条是治理层的定调：**任务流转靠底层支撑，不是 CEO/助理事事拍板**——群里谁说话、
谁拍板、谁指定下一步，都要有调度。这不是「角色在界面里」，是**引擎在底下转**：

- **谁说话**：§2.5.1 真实会议做到发言序列化——主持人点名，不是所有人抢话；这一步是**调度逻辑**在转方向盘，不是 CEO 在场。
- **谁拍板**：门禁 + 角色职权表（§2.4）决定「这个级别的决定谁能批」——测试能不能过是测试岗位书 + review_gates 说了算，不需要老板；超出职权才升级到人（§2.5 升级阈值清单）。
- **谁指定下一步**：特助的分发逻辑 + 各角色的岗位书职权 + 会议结论 → 下一步动作。是**系统在编排**，不是 CEO 遥控。
- **治理位（AI 审计/合规/AI Agent Manager）不展示、不演人**：它们跑在底层（审计抽查 / 门禁强制 / 分发编排），界面上看不见它们——你只看到群在正常转，出问题它自动纠偏。
- **真人感在界面层，调度在底层**（你第 16 条：每个角色要像真人，而不是机械的门禁）：
  门禁/审计/职权表是**底层引擎**，界面上角色是**有脸有性格会开会的人**——「产品经理否了你这个方案」在界面里是雷军开会时说的那句有性格的话（§2.5.1），在底层是一条 review_gates 记录。两层分离，谁也抢不了谁的活。

- **全局文档中心**：所有群的文档汇总成**统一库**（列表/树/搜索/筛选：按类型/群/日期/作者），参照飞书知识库/云空间；

### 4.1 第 8 条「你定」：我定的完整实现（v3.1：完整非缩水）

## 5. 完整实施范围与验收形状（定稿 v3.2：完整可上线，不是 MVP）

§3 的 11 个新增面 + §2 的目标形态，全部第一版交付。这条验收链的每一格现有内核都能撑（状态机/审批/证据/岗位书全在），
新的只是：群容器、单角色私聊、会话呈现、真实会议、任务面板、特助分发视角、
执行器七种、人才市场（共享/导出/导入）、@ 拍板呈现、底层治理不展示、真人感全量（头像/TTS/语气）。

**验收形状（端到端完整走通一条公司）**：

> 建一个群（=一个任务）→ 拉成员（完整公司树默认全激活：产品/技术/运营三线 + 财务/人力/法务/市场/销售 + 设计师 + 特助 + 你 CEO）→
> 你在群里发任务 → 特助拆成 2 个子任务 → 开发（claude-code / codex-cli / qoder-cli）干第一段 → 产出汇回特助 → 特助转给测试（MCP 平台桥）验第二段 →
> 特助汇报「有个事要你定：预算/边界」→ @ 你 → 你在群里拍板 → 流转继续。
> 节奏在跑：产品经理每天调研 → 出「升级建议卡」→ 进任务面板 → 开会讨论（§2.5.1 真实会议，发言序列+结论三件套）→ 采纳才进执行线 + 站会摘要每天一条。
> 你随时可以私聊任何一个成员——问特助「所有项目进度」，她能跨群汇报（所有成员都能看自己加入的群）。
> 真人感：每个角色有名字/头像/口头禅/人设/语音（TTS），按 persona 发言，私聊有语气。
> 人才市场：导出一个员工包 → 再导入 → 立即入职为可用的成员实例。
> 页面：三栏布局（应用导航栏/会话列表/主内容区 + 顶栏），建群→拉人→发任务→拍板→开会全在群界面走完。

>   doc/excel/markdown 都能编辑能导出；30 天版本历史可还原；你本地 docx/xlsx 能传进文档中心再编辑。

**交付形态**：完整可上线，不是 MVP、不是第一块地。内部开发可以按 11 个新增面分批推进，但交付物是完整系统，
